Lambda, ECS, EKS, Fargate — 언제 무엇을

EC2(0010~0012)는 서버를 직접 고르고 관리합니다. 오늘은 그 관리를 AWS에 점점 더 넘기는 선택지들입니다. 시험은 "실행 시간", "Kubernetes", "운영 부담 최소", "GPU" 같은 단어로 답을 가릅니다.

왜 이것부터인가

시험에서: "최소 운영 오버헤드"는 거의 항상 관리형·서버리스 쪽이 정답입니다. 단, Lambda의 15분 제한이나 Fargate의 GPU 미지원 같은 한계를 넘는 시나리오가 함정으로 나옵니다.
실무에서: 이벤트 처리는 Lambda, 장시간 서비스는 컨테이너, 특수 하드웨어는 EC2라는 분업이 현대 아키텍처의 기본 골격입니다.

Lambda: 이벤트가 오면 코드가 돈다

Lambda는 서버를 프로비저닝하거나 관리하지 않고 코드를 실행하는 서버리스 컴퓨팅 서비스입니다. 서버 유지 관리, 용량 프로비저닝, 확장, 패치를 AWS가 맡습니다. 핸들러 함수를 API Gateway, S3, SQS, EventBridge 등 200개 이상의 AWS 서비스 트리거에 연결하며, 요청 수와 실행 시간(GB-초)만큼 과금됩니다.[1]

컨테이너: 오케스트레이터 × 컴퓨팅

AWS의 컨테이너 결정 가이드는 두 단계로 고르라고 합니다. 먼저 오케스트레이터, 그다음 그 위의 컴퓨팅 모델입니다.[6]

비교 내용은 결정 가이드와 ECS 개발자 안내서 기준입니다.[6][7] EKS도 Fargate나 관리형 노드 그룹, Auto Mode 위에서 돌릴 수 있습니다.[6] ECS 용어로 작업 정의(task definition)는 컨테이너 청사진(JSON), 작업(task)은 그 실행 인스턴스, 서비스는 원하는 작업 수를 계속 유지합니다.[7]

AWS Batch는 배치 작업을 제출하면 필요한 컴퓨팅을 알아서 프로비저닝하고 작업을 스케줄링하는 완전 관리형 서비스입니다. ECS·EKS 위에서 EC2(온디맨드·Spot), Fargate 용량을 씁니다. HPC·ML·시뮬레이션 같은 대규모 배치에 씁니다.[8]

연습

Q1. 사용자가 S3 버킷에 사진을 올리면 썸네일을 만들어 다른 버킷에 저장해야 합니다. 업로드는 하루 몇 건에서 수천 건까지 불규칙하고, 한 장 처리는 몇 초면 끝납니다. 운영 오버헤드가 가장 적은 방법은?

짧고(몇 초), 이벤트 기반이며, 양이 불규칙한 작업은 Lambda의 정석입니다. S3 이벤트가 함수를 직접 호출하고, 요청이 없으면 비용도 거의 없습니다. EC2 폴링이나 상시 EKS 서비스는 서버·클러스터 관리 부담과 유휴 비용이 생깁니다.

Q2. 매일 밤 컨테이너 이미지로 패키징된 데이터 변환 작업을 실행합니다. 작업 한 번에 약 40분이 걸립니다. 회사는 서버를 관리하고 싶지 않습니다. 가장 적합한 방법은?

Lambda의 최대 제한 시간은 900초(15분)라 60분 설정은 불가능합니다. 40분짜리 컨테이너 작업을 서버 관리 없이 돌리려면 Fargate가 맞습니다(대규모 배치라면 Fargate를 쓰는 AWS Batch도 후보). 상시 EC2는 서버 관리와 유휴 비용이 생기고, 하나의 변환 작업을 40개로 쪼개려면 코드 재설계가 필요해 요구사항을 벗어납니다.

Q3. 회사는 온프레미스에서 Kubernetes로 수십 개 마이크로서비스를 운영하며, Helm 차트와 Kubernetes 매니페스트, 관련 도구에 많이 투자했습니다. 컨트롤 플레인 관리 부담은 줄이고 기존 자산은 그대로 쓰고 싶습니다. 무엇을 써야 하나요?

Kubernetes API·생태계를 유지하면서 고가용성 컨트롤 플레인 관리를 AWS에 넘기는 것이 EKS입니다. ECS도 관리형이지만 매니페스트와 Helm 차트를 작업 정의로 다시 써야 해서 "기존 자산 그대로" 요구에 어긋납니다. EC2에 직접 설치하면 컨트롤 플레인 부담이 그대로 남습니다.

Q4. 이미지 변환 Lambda 함수가 메모리 128 MB로 설정되어 있고, CloudWatch를 보면 CPU 바운드라 실행 시간이 깁니다. 코드를 바꾸지 않고 처리 속도를 높이는 방법은?

Lambda는 CPU를 메모리에 비례해 할당하며, vCPU를 따로 설정하는 항목은 없습니다. 메모리를 올리면 CPU도 함께 늘어 CPU 바운드 함수가 빨라집니다. 제한 시간을 늘리면 시간 초과는 피해도 속도는 그대로이고, 예약 동시성은 동시 실행 몫을 다루는 설정입니다.

Q5. ECS 작업을 Fargate로 실행할 때의 특징으로 옳은 것을 두 개 고르세요.

Fargate는 EC2 인스턴스 없이 컨테이너를 돌리는 서버리스 엔진이고, 작업마다 VPC 안의 ENI와 작업 수준 IAM 역할을 받습니다. GPU는 지원하지 않으며, GPU가 필요하면 EC2 시작 유형(또는 ECS Managed Instances)을 씁니다. AMI를 고르고 패치하는 것은 EC2 시작 유형의 일입니다.

Q6. API Gateway 뒤 Lambda 함수가 아침 출근 시간마다 첫 요청들에서 초기화 지연(콜드 스타트)으로 응답이 느립니다. 지연을 줄이는 방법은?

프로비저닝된 동시성은 실행 환경을 미리 초기화해 두어 콜드 스타트를 없앱니다(추가 요금). 예약 동시성은 몫과 상한을 정할 뿐 환경을 미리 데우지 않으므로 콜드 스타트는 그대로입니다. 동시성 한도 증가는 스로틀링 문제의 해법입니다.

Q7. (복습 · 0010) 회사가 EC2, ECS on Fargate, Lambda를 함께 쓰며, 앞으로 워크로드가 이 셋 사이를 오갈 수 있습니다. 하나의 1년 약정으로 셋 모두에 할인을 받으려면?

Compute Savings Plans만 EC2 사용량과 함께 Fargate와 Lambda에도 적용되고, 패밀리·리전이 바뀌어도 할인이 이어집니다. EC2 Instance Savings Plans와 RI는 EC2 인스턴스에만 해당합니다.

Q8. ML 추론 서비스를 컨테이너로 ECS에 배포합니다. 추론에는 GPU가 필요하고, 팀은 특정 GPU 인스턴스 유형을 직접 고르고 싶습니다. 어떤 구성이 맞나요?

Fargate는 GPU를 지원하지 않고, AWS 문서도 GPU 같은 특수 하드웨어가 필요하면 EC2 인스턴스를 쓰라고 안내합니다. Lambda나 Fargate의 메모리를 올려도 CPU·메모리가 늘 뿐 GPU가 생기지 않습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) Lambda의 핵심 한도 세 가지(제한 시간, 메모리-CPU 관계, 기본 동시성)는? (2) 예약 동시성과 프로비저닝된 동시성은 각각 어떤 문제를 푸나? (3) ECS vs EKS, Fargate vs EC2 시작 유형을 고르는 기준은?

(1) 제한 시간 기본 3초·최대 900초(15분). 메모리 128 MB~10,240 MB, CPU는 메모리에 비례(1,769 MB ≈ vCPU 1개). 계정 동시성 리전당 기본 1,000.

(2) 예약: 함수 몫을 떼어 주고 상한을 둠 → 다른 함수 때문에 스로틀링, 다운스트림 보호. 무료. 프로비저닝: 실행 환경을 미리 초기화 → 콜드 스타트 제거. 유료.

(3) ECS: AWS 네이티브, 낮은 운영 부담. EKS: Kubernetes API·생태계·이식성. Fargate: 서버 관리 없음, GPU 없음. EC2 시작 유형: GPU·특정 인스턴스·사용자 지정 AMI·특권 기능.
