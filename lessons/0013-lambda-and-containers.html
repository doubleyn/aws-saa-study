왜 서버리스와 컨테이너를 배워야 할까요?

시험 관점: 시험 문제에서 "운영 오버헤드 최소화(Least operational overhead)"라는 문구가 나오면 거의 대부분 완전 관리형 또는 서버리스(Lambda, Fargate) 아키텍처가 정답의 강력한 후보입니다. 하지만 무조건 서버리스를 고르면 안 됩니다. Lambda의 최대 실행 시간 15분 제한이나 Fargate의 GPU 미지원과 같은 기술적 한계를 교묘하게 넘나드는 시나리오들이 오답 함정으로 자주 출제되기 때문입니다.
실무 관점: 이벤트 기반의 짧고 간헐적인 처리는 Lambda, 마이크로서비스 형태의 지속적인 웹 서비스나 복잡한 의존성을 가진 애플리케이션은 컨테이너(ECS/EKS on Fargate), GPU 머신러닝 학습이나 특수한 커널 제어가 필요한 작업은 EC2에 맡기는 '적재적소의 분업'이 클라우드 네이티브 아키텍처 설계의 기본 표준입니다.

Lambda: 이벤트가 발생하면 코드가 즉각 실행되는 서버리스 컴퓨팅

AWS Lambda는 가상 서버를 직접 프로비저닝하거나 운영체제를 관리할 필요 없이 코드만 등록해 두면 실행되는 대표적인 서버리스 컴퓨팅 서비스입니다. 고가용성 유지보수, 용량 산정, 오토 스케일링, OS 보안 패치 등을 모두 AWS가 백그라운드에서 전담합니다. 개발자가 작성한 핸들러 함수를 API Gateway, S3 버킷, SQS 대기열, EventBridge 등 200개 이상의 다양한 AWS 서비스 이벤트에 트리거로 연결할 수 있습니다. 특히 서버가 켜져 있는 시간 전체에 과금되는 것이 아니라, 오직 요청 횟수와 코드가 실제로 실행된 실행 시간(밀리초 단위 및 메모리 할당량에 따른 GB-초)에 대해서만 비용을 지불하므로 유휴 상태일 때는 비용이 0원입니다.[1]

설정 및 주요 한도상세 수치시험 핵심 포인트
제한 시간 (Timeout)기본값 3초, 최대 900초 (15분)[4]단일 실행에 15분을 초과하는 장시간 작업(대규모 배치, 비디오 인코딩 등)에는 Lambda를 사용할 수 없습니다. ECS/Fargate나 AWS Batch를 선택해야 합니다.
메모리 할당량 및 CPU 관계128 MB ~ 10,240 MB (10 GB) 설정 가능. CPU 파워는 할당한 메모리에 비례하여 자동으로 배정되며, 1,769 MB에서 vCPU 1개 상당의 연산 능력을 얻음[3]Lambda 설정 화면에는 vCPU를 독립적으로 지정하는 항목이 없습니다. 따라서 CPU 연산 집약적인 작업이 느려서 속도를 높여야 한다면 메모리 할당량을 증설하는 것이 올바른 해법입니다.
동시성 (Concurrency)리전당 계정 기본 한도 1,000 (요청을 통해 증설 가능). 이 한도를 초과하면 429 Too Many Requests 스로틀링 발생[5]필요한 동시성 계산 공식: 초당 요청 수(RPS) × 평균 실행 시간(초). (예: 초당 100건 요청에 실행 시간이 평균 2초라면 동시성은 200)
페이로드 크기 한도동기식(Request-Response) 요청/응답: 각 6 MB, 비동기식(이벤트): 256 KB[2]대용량 파일(수십 MB~GB)을 함수에 직접 전달하면 실패합니다. 파일을 먼저 S3 버킷에 업로드하고, Lambda에는 S3 객체의 키(Key/경로)만 이벤트로 전달하는 패턴을 사용합니다.
패키지 및 임시 스토리지배포 패키지(.zip) 압축 기준 50 MB, 압축 해제 기준 250 MB. 컨테이너 이미지 배포 시 최대 10 GB까지 지원. 로컬 임시 디스크(/tmp)는 512 MB ~ 10,240 MB 설정 가능[2]라이브러리 크기가 큰 복잡한 머신러닝 모델이나 무거운 의존성 패키지도 컨테이너 이미지(Docker Image) 형태로 패키징하여 Lambda에 배포할 수 있습니다.

콜드 스타트와 동시성 제어: 예약 동시성 vs 프로비저닝된 동시성

Lambda 함수가 처음 호출되거나 트래픽이 급증하여 새로운 실행 환경이 생성될 때, 런타임을 다운로드하고 코드를 메모리에 적재하며 초기화(Init) 코드를 실행하는 동안 수백 밀리초에서 수 초의 지연이 발생하는데, 이를 콜드 스타트(Cold Start)라고 합니다. AWS는 동시성과 콜드 스타트 문제를 해결하기 위해 두 가지 상이한 동시성 모델을 제공합니다.[5]

구분예약 동시성 (Reserved Concurrency)프로비저닝된 동시성 (Provisioned Concurrency)
동작 방식계정 전체의 동시성 풀에서 특정 함수만을 위해 전용 실행 용량을 일정 수량만큼 미리 떼어내어 할당합니다. 이는 해당 함수의 보장된 최소 용량이자 동시에 최대 실행 상한선이 됩니다. 다른 함수들은 이 예약된 용량을 절대 침범할 수 없습니다.지정한 수량만큼의 실행 컨테이너 환경을 사전에 완전히 초기화(데워 둠)하여 호출 대기 상태로 유지합니다.
해결하는 문제(1) 덜 중요한 다른 함수의 트래픽 폭주로 인해 핵심 비즈니스 함수가 스로틀링되는 것을 방지합니다.
(2) 함수가 무제한으로 동시 실행되어 다운스트림 관계형 데이터베이스(RDS 등)에 과도한 커넥션을 열어 DB를 다운시키는 것을 방어합니다.		함수 최초 호출 시 발생하는 콜드 스타트(Cold Start) 지연 시간을 완전히 제거하여, 지연 시간에 극도로 민감한 대화형 웹/모바일 API에 두 자릿수 밀리초 미만의 일관된 응답 속도를 제공합니다.
비용 체계설정에 따른 추가 요금이 전혀 없습니다 (실제 호출된 시간만 과금).사전에 띄워 둔 컨테이너 리소스에 대해 시간당 추가 요금이 발생합니다.

컨테이너: 오케스트레이터 × 컴퓨팅 모델의 2단계 선택

AWS에서 컨테이너 기반 워크로드를 설계할 때는 AWS 공식 결정 가이드에 따라 1단계: 컨테이너 오케스트레이터를 먼저 결정하고, 2단계: 그 아래에서 동작할 컴퓨팅(인프라) 모델을 선택하는 2단계 프레임워크를 적용합니다.[6]

1단계: 오케스트레이터 선택 (ECS vs EKS)

오케스트레이터선택하는 이유 및 특징
Amazon ECS (Elastic Container Service)AWS가 자체 개발한 AWS 네이티브 오케스트레이터입니다. IAM, CloudWatch, ALB 등 AWS 생태계와 매우 깊고 단순하게 통합되어 있어 러닝 커브가 낮고 운영 오버헤드가 극히 적습니다. Kubernetes의 복잡한 컨트롤 플레인이나 애드온을 관리하고 싶지 않고 AWS 환경에서 컨테이너를 가장 간편하게 운영하고자 할 때 최적의 선택입니다.
Amazon EKS (Elastic Kubernetes Service)오픈소스 표준 Kubernetes API 및 생태계를 완벽하게 지원하는 관리형 서비스입니다. Helm 차트, K8s 매니페스트, 오퍼레이터(Operator) 등 기존 Kubernetes 기술 자산과 도구를 그대로 활용할 수 있으며, 온프레미스 데이터센터나 다른 퍼블릭 클라우드 간의 뛰어난 애플리케이션 이식성이 필요할 때 선택합니다. 마스터 노드(컨트롤 플레인)의 고가용성과 패치는 AWS가 완전 관리형으로 책임집니다.

2단계: 컴퓨팅 모델 선택 (Fargate vs EC2 시작 유형)

컴퓨팅 모델관리 오버헤드적합한 시나리오 및 기술적 제약
AWS Fargate
(서버리스 엔진)		가상 서버 관리 부담 제로. 사용자가 관리할 EC2 인스턴스가 아예 없으며, 컨테이너 작업(Task)이 요청한 vCPU와 메모리 리소스만큼만 초 단위로 과금됩니다.기저 인프라 패치나 클러스터 용량 관리에 신경 쓰지 않고 애플리케이션 코드에만 집중하고 싶을 때. 트래픽 변동이 심하거나 예측하기 어려운 마이크로서비스.
핵심 제약사항: Linux 작업당 최대 32 vCPU 및 244 GiB 메모리 지원, GPU를 지원하지 않음 (GPU 기반 AI/ML 학습 및 추론 불가능). 작업마다 독립적인 VPC ENI와 작업 수준의 세분화된 IAM 역할이 할당됩니다.
EC2 시작 유형
(EC2 Launch Type)		인스턴스 패밀리 선택, 스토리지 크기, OS 구성, 보안 패치, 클러스터 오토 스케일링을 관리자가 직접 운영해야 합니다.GPU 인스턴스(G/P 패밀리)를 활용해야 하는 머신러닝 워크로드, 특정 인스턴스 패밀리나 예약 인스턴스(RI)/세이빙스 플랜을 최대한 활용해야 할 때, 컨테이너 호스트 수준의 파일시스템이나 도커 데몬을 직접 조작해야 하는 특권(Privileged) 컨테이너, 사용자 지정 AMI가 필요한 환경에 필수적입니다.
ECS Managed Instances실제 컴퓨팅은 EC2 인스턴스 위에서 실행되지만, 인스턴스의 프로비저닝, 패치, 수평 확장을 AWS가 자동화합니다.Fargate의 운영 단순성을 누리면서도, Fargate에서 지원하지 않는 GPU 인스턴스 유형 선택권이나 특수한 하드웨어 구성이 필요할 때 절충안으로 활용됩니다.

ECS 핵심 용어 정리: ECS를 다룰 때 반드시 알아야 할 3대 개념입니다.[7]

  • 작업 정의(Task Definition): 컨테이너의 청사진(Blueprint)입니다. 사용할 도커 이미지 URL, 필요한 CPU/메모리 사양, 포트 매핑, 환경 변수, IAM 작업 역할 등을 정의한 JSON 파일입니다.
  • 작업(Task): 작업 정의에 따라 실제로 메모리에 올라가 실행 중인 컨테이너 인스턴스 묶음입니다.
  • 서비스(Service): 지정한 수량(예: 3개)의 작업이 항상 정상적으로 실행 상태를 유지하도록 감시하고, 작업이 비정상 종료되면 즉시 새 작업을 띄워 자동 복구하며, ALB와 연동하여 트래픽을 분산해 주는 관리 단위입니다.

AWS Batch란? AWS Batch는 엔지니어링 시뮬레이션, 금융 리스크 분석, 유전체 데이터 분석, 대규모 머신러닝 데이터 전처리 등 수십만 건의 대규모 배치 컴퓨팅 작업을 효율적으로 실행할 수 있도록 지원하는 완전 관리형 서비스입니다. 사용자가 작업 대기열(Job Queue)에 작업을 제출하면, AWS Batch가 작업의 리소스 요구사항에 맞추어 최적의 컴퓨팅 인프라(EC2 온디맨드, 스팟 인스턴스, 또는 Fargate)를 자동으로 프로비저닝하고, 작업이 끝나면 인스턴스를 즉시 자동 회수하여 비용을 극대화합니다.[8]

연습

Q1. 사용자가 S3 버킷에 사진을 올리면 썸네일을 만들어 다른 버킷에 저장해야 합니다. 업로드는 하루 몇 건에서 수천 건까지 불규칙하고, 한 장 처리는 몇 초면 끝납니다. 운영 오버헤드가 가장 적은 방법은?

정답은 S3 이벤트 알림으로 Lambda를 호출해 처리하는 것입니다. 실행 시간이 수 초 이내로 매우 짧고, 요청이 간헐적이고 불규칙하게 들어오는 워크로드는 AWS Lambda의 전형적인 표준 사용 사례입니다. S3 버킷에 이미지가 업로드될 때마다 이벤트 알림이 Lambda 함수를 즉시 트리거하며, 이미지가 업로드되지 않는 유휴 시간에는 단 1원의 서버 비용도 발생하지 않아 비용과 운영 효율이 가장 뛰어납니다. 반면 EC2나 상시 EKS 클러스터를 띄워 두면 지속적인 서버 인프라 관리 부담과 유휴 서버 비용이 낭비됩니다.

Q2. 매일 밤 컨테이너 이미지로 패키징된 데이터 변환 작업을 실행합니다. 작업 한 번에 약 40분이 걸립니다. 회사는 서버를 관리하고 싶지 않습니다. 가장 적합한 방법은?

정답은 ECS on Fargate 예약 작업으로 실행하는 것입니다. AWS Lambda의 하드 리밋(최대 실행 제한 시간)은 900초(15분)이므로 40분이 걸리는 단일 작업을 60분으로 늘려 Lambda에서 돌리는 것은 기술적으로 완전히 불가능합니다. 15분을 초과하는 장시간 컨테이너 워크로드를 기저 서버 관리 없이 서버리스 형태로 실행하려면 AWS Fargate가 정답입니다. EventBridge Scheduler로 매일 밤 ECS Fargate 작업을 트리거하면 작업이 끝난 후 컨테이너가 자동으로 종료되어 비용도 최소화됩니다.

Q3. 회사는 온프레미스에서 Kubernetes로 수십 개 마이크로서비스를 운영하며, Helm 차트와 Kubernetes 매니페스트, 관련 도구에 많이 투자했습니다. 컨트롤 플레인 관리 부담은 줄이고 기존 자산은 그대로 쓰고 싶습니다. 무엇을 써야 하나요?

정답은 EKS 기반 관리형 Kubernetes를 사용하는 것입니다. Amazon EKS는 표준 Kubernetes와 100% 호환되므로, 기존에 온프레미스에서 구축해 둔 Helm 차트, YAML 매니페스트 파일, 로깅/모니터링 오픈소스 도구들을 코드 수정 없이 그대로 AWS로 마이그레이션할 수 있습니다. 동시에 고가용성 멀티 AZ 컨트롤 플레인의 설치, 업그레이드, 백업 부담은 AWS가 대신 책임집니다. 반면 Amazon ECS는 AWS 고유의 작업 정의(Task Definition) 형식으로 모든 아키텍처를 전면 재작성해야 하므로 기존 투자 자산을 활용하고자 하는 요구사항에 맞지 않습니다.

Q4. 이미지 변환 Lambda 함수가 메모리 128 MB로 설정되어 있고, CloudWatch를 보면 CPU 바운드라 실행 시간이 깁니다. 코드를 바꾸지 않고 처리 속도를 높이는 방법은?

정답은 함수의 메모리 설정을 크게 늘려 주는 것입니다. AWS Lambda에서는 CPU 코어 수를 별도로 지정하는 독립된 설정 옵션이 존재하지 않습니다. 대신 할당한 메모리 용량에 비례하여 CPU 파워가 선형적으로 자동 배정됩니다 (약 1,769 MB 메모리 할당 시 vCPU 1개 상당 부여). 따라서 CPU 연산 병목으로 처리가 지연되는 함수는 메모리 할당량을 증설하면 CPU 성능도 함께 강력해져 전체 실행 시간을 대폭 단축시킬 수 있습니다. 제한 시간을 늘리는 것은 타임아웃 에러를 방지할 뿐 처리 속도 자체를 개선하지 못합니다.

Q5. ECS 작업을 Fargate로 실행할 때의 특징으로 옳은 것을 두 개 고르세요.

정답은 EC2 인스턴스를 프로비저닝·패치할 필요 없음과 작업마다 ENI와 IAM 역할을 받을 수 있음입니다. AWS Fargate는 컨테이너를 위한 완전 관리형 서버리스 컴퓨팅 엔진으로, 사용자가 기본 가상 머신(EC2)을 프로비저닝하거나 OS 보안 패치를 적용할 필요가 전혀 없습니다. 또한 awsvpc 네트워크 모드를 통해 실행되는 각 작업(Task)마다 VPC 내의 전용 탄력적 네트워크 인터페이스(ENI)와 프라이빗 IP가 부여되며, 작업 수준에서 세분화된 Task IAM Role을 독립적으로 연결할 수 있습니다. 주의할 점은 Fargate는 GPU 가속을 지원하지 않는다는 것입니다.

Q6. API Gateway 뒤 Lambda 함수가 아침 출근 시간마다 첫 요청들에서 초기화 지연(콜드 스타트)으로 응답이 느립니다. 지연을 줄이는 방법은?

정답은 함수에 프로비저닝된 동시성을 구성하는 것입니다. 프로비저닝된 동시성(Provisioned Concurrency)은 지정된 수량만큼의 실행 환경 컨테이너를 사전에 미리 초기화하고 웜업(Warm-up) 상태로 유지함으로써, 트래픽 유입 시 즉각 두 자릿수 밀리초 이내의 응답을 반환하여 콜드 스타트를 완벽히 제거합니다. 반면 예약 동시성은 특정 함수가 사용할 수 있는 동시 실행 인스턴스의 '상한선과 전용 슬롯'을 지정할 뿐, 컨테이너 환경을 미리 초기화해 두지 않으므로 최초 호출 시의 콜드 스타트를 해결할 수 없습니다.

Q7. (복습 · 0010) 회사가 EC2, ECS on Fargate, Lambda를 함께 쓰며, 앞으로 워크로드가 이 셋 사이를 오갈 수 있습니다. 하나의 1년 약정으로 셋 모두에 할인을 받으려면?

정답은 Compute Savings Plans를 1년간 구매하는 것입니다. Savings Plans 상품 중 'Compute Savings Plans'만이 EC2 인스턴스 사용량뿐만 아니라 AWS Fargate와 AWS Lambda 컴퓨팅 사용량에도 자동으로 적용됩니다. 또한 인스턴스 패밀리, 운영체제(OS), 심지어 리전을 변경하더라도 할인 혜택이 유연하게 유지됩니다. 반면 EC2 Instance Savings Plans나 예약 인스턴스(RI)는 오직 EC2 인스턴스에만 적용되며 Fargate나 Lambda에는 적용되지 않습니다.

Q8. ML 추론 서비스를 컨테이너로 ECS에 배포합니다. 추론에는 GPU가 필요하고, 팀은 특정 GPU 인스턴스 유형을 직접 고르고 싶습니다. 어떤 구성이 맞나요?

정답은 GPU 인스턴스 기반 ECS EC2 시작 유형을 사용하는 것입니다. AWS Fargate는 현재 GPU 가속을 지원하지 않으므로, 기계학습 모델 추론이나 고성능 그래픽 처리를 위해 GPU 하드웨어가 필수적인 컨테이너 워크로드는 반드시 EC2 시작 유형(EC2 Launch Type, 예: G4dn, G5, P4 인스턴스 등)을 선택해야 합니다. Lambda나 Fargate의 메모리 할당량을 아무리 최대로 올리더라도 범용 CPU와 메모리 용량만 증설될 뿐 전용 GPU 가속기가 장착되지는 않습니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 기억을 떠올려 직접 정리해 보세요. (1) Lambda의 세 가지 핵심 제약 사항(최대 실행 제한 시간, 메모리와 CPU의 비례 관계, 기본 동시성 한도)은 무엇인가요? (2) 예약 동시성과 프로비저닝된 동시성은 각각 어떤 구체적인 기술 문제를 해결하나요? (3) 컨테이너 오케스트레이터(ECS vs EKS)와 컴퓨팅 모델(Fargate vs EC2 시작 유형)을 선택하는 핵심 기준은 무엇인가요?

(1) 최대 실행 제한 시간: 기본 3초, 최대 900초(15분). 15분 초과 작업은 Lambda 실행 불가. 메모리-CPU 관계: 128 MB ~ 10,240 MB, CPU는 별도 설정 없이 메모리 크기에 비례하여 자동 배정(1,769 MB = 1 vCPU). 기본 동시성: 리전당 계정 기본 1,000 (초과 시 429 스로틀링 발생).

(2) 예약 동시성: 계정 동시성 풀에서 특정 함수 전용 몫을 분리 예약하여, 다른 함수의 트래픽 폭주로부터 핵심 함수를 보호하고, 과도한 동시 실행으로 다운스트림 DB(RDS)가 마비되는 것을 방지(비용 무료). 프로비저닝된 동시성: 실행 컨테이너 환경을 미리 웜업 초기화해 두어 최초 호출 시 발생하는 콜드 스타트 지연을 완전히 제거(시간당 추가 요금 발생).

(3) ECS vs EKS: ECS는 AWS 네이티브로 운영 오버헤드가 극히 적고 AWS 서비스와 단순하게 결합됨. EKS는 표준 Kubernetes 생태계, Helm 매니페스트 자산 활용 및 멀티클라우드 이식성이 필요할 때 선택. Fargate vs EC2 시작 유형: Fargate는 EC2 관리 없는 서버리스이나 GPU를 미지원함. EC2 시작 유형은 GPU 등 특수 하드웨어, 특권 컨테이너, 커스텀 AMI가 필요할 때 필수 선택.
