왜 이것인가

시험에서: GuardDuty와 Inspector, Macie를 바꿔 끼운 보기, Shield와 WAF를 섞은 보기가 전형적인 함정입니다.
실무에서: 코드에 박힌 DB 비밀번호, 웹 공격, 유출된 자격 증명은 실제 사고의 단골 원인입니다. 각각을 막는 관리형 서비스가 따로 있습니다.

보안 암호: Secrets Manager vs Parameter Store

둘 다 애플리케이션이 실행 중에 값을 꺼내 쓰는 저장소이고, 둘 다 KMS로 암호화할 수 있습니다. 갈림길은 교체(rotation)입니다.[2]

AWS 문서도 명확합니다. Parameter Store의 SecureString은 암호화가 필요한 설정값용이고, DB 자격 증명·API 키·토큰 같은 보안 암호에는 자동 교체와 리전 간 복제를 제공하는 Secrets Manager를 권장합니다.[2]

교체 방식은 두 가지입니다.[3]

  • 관리형 교체: Amazon RDS, Aurora, Redshift, DocumentDB 등이 마스터 사용자 자격 증명의 교체를 서비스가 직접 설정·관리합니다. Lambda 함수가 필요 없습니다.[4]
  • Lambda 함수에 의한 교체: 그 밖의 보안 암호는 Lambda 함수가 보안 암호와 대상 DB·서비스를 함께 갱신합니다.[3]

복제된 보안 암호는 기본 리전에서 교체하면 새 값이 모든 복제본으로 전파됩니다.[5] 그리고 0008과 연결되는 지점: 고객 관리형 키로 암호화된 보안 암호를 읽으려면, Secrets Manager가 호출자를 대신해 KMS Decrypt를 부르므로 호출자에게 그 키의 사용 권한이 있어야 합니다.[6]

막기 vs 찾기

나머지 서비스는 두 무리로 나누면 헷갈리지 않습니다. 요청 경로에 서서 막는 서비스(Shield, WAF)와, 로그·데이터·소프트웨어를 들여다보고 찾아서 알려 주는 서비스(GuardDuty, Macie, Inspector)입니다.

막기 ①: Shield (DDoS)

Shield StandardShield Advanced
가입모든 고객에게 자동 적용, 추가 요금 없음[8]유료 구독[7]
방어 범위가장 흔한 네트워크·전송 계층(L3/L4) DDoS 공격. 특히 Route 53 호스팅 영역, CloudFront, Global Accelerator에서 효과가 큼[8]EC2, ELB, CloudFront, Route 53 호스팅 영역, Global Accelerator에 대한 확장 보호. L3/L4와 애플리케이션 계층(L7)까지[7]

막기 ②: AWS WAF (웹 애플리케이션 방화벽)

WAF는 보호 대상 리소스로 들어오는 HTTP/HTTPS 요청을 검사합니다. 붙일 수 있는 곳은 정해져 있습니다: CloudFront 배포, API Gateway REST API, Application Load Balancer, AppSync GraphQL API, Cognito 사용자 풀, App Runner, Verified Access, Amplify 등.[7] 목록에 NLB는 없습니다. 시험에서 "NLB에 WAF 연결"은 오답 신호입니다.

규칙에 쓸 수 있는 조건은 출발 IP, 국가, 헤더 값, 문자열·정규식, 요청 길이, 그리고 악성일 가능성이 높은 SQL 코드(SQL 주입)와 스크립트(크로스 사이트 스크립팅, XSS)입니다. 동작은 허용, 차단(HTTP 403), 카운트, CAPTCHA/챌린지이고, AWS와 Marketplace의 관리형 규칙 그룹도 쓸 수 있습니다.[7]

속도 기반 규칙(rate-based rule)은 들어오는 요청을 세다가 너무 빠르게 오는 요청을 제한합니다. IP 등 기준별로 묶어 평가 창 동안의 요청 수를 셉니다.[10] "특정 IP들이 로그인 페이지에 요청을 퍼붓는다" → 속도 기반 규칙입니다. 여러 계정에 WAF·Shield Advanced 정책을 한 번에 적용하려면 AWS Firewall Manager를 씁니다.[7]

연습

기억으로 푸세요. 보기 길이는 모두 같게 맞춰 두었습니다.

Q1. (시험형) 애플리케이션 코드에 Amazon RDS for MySQL의 자격 증명이 하드코딩되어 있습니다. 자격 증명을 코드에서 빼고 30일마다 자동으로 교체해야 합니다. 운영 오버헤드가 가장 적은 방법은?

Secrets Manager는 RDS 자격 증명에 대해 자동 교체를 제공하고, RDS는 마스터 사용자 자격 증명의 관리형 교체까지 지원합니다. Parameter Store에는 자격 증명 교체 기능이 없어서, 교체하려면 직접 만들어야 합니다. 나머지 둘은 암호화만 될 뿐 교체는 전부 수작업입니다.

Q2. (시험형) 여러 애플리케이션이 공통으로 쓰는 승인된 AMI ID, 엔드포인트 URL, 환경 이름을 중앙에서 관리하려 합니다. 비밀 값은 없고 교체도 필요 없으며, 추가 비용을 최소화해야 합니다.

AMI ID·엔드포인트 URL은 AWS 문서가 Parameter Store의 전형적인 데이터로 꼽는 예이고, 표준 계층은 추가 요금이 없습니다. Secrets Manager도 저장은 되지만 보안 암호당 월 요금이 붙어 "비용 최소화"에 어긋납니다. CloudHSM은 암호화 키용 HSM입니다(0008).

Q3. (시험형) Application Load Balancer 뒤의 공개 웹 애플리케이션이 SQL 주입과 크로스 사이트 스크립팅 공격을 받고 있습니다. 이런 요청을 애플리케이션에 닿기 전에 차단하려면?

SQL 주입·XSS는 HTTP 요청 내용을 검사해야 하는 L7 공격이고, WAF는 ALB에 직접 연결됩니다. GuardDuty는 위협을 탐지해 결과를 만들 뿐 요청을 차단하지 않습니다. Shield Standard는 흔한 L3/L4 DDoS 방어이고, Inspector는 트래픽이 아니라 소프트웨어 취약점을 스캔합니다.

Q4. (시험형) CloudFront 뒤의 로그인 페이지에 소수의 IP가 짧은 시간에 수많은 요청을 보냅니다. IP가 계속 바뀌므로, 일정 속도를 넘는 IP를 자동으로 차단하고 싶습니다.

속도 기반 규칙은 IP 등 기준별로 요청을 세다가 너무 빠른 요청을 자동으로 제한합니다. IP 집합은 IP가 바뀔 때마다 사람이 갱신해야 하고, WAF는 NLB에 붙지 않으며, Macie는 S3의 민감 데이터를 찾는 서비스입니다.

Q5. (시험형) 자주 DDoS 공격을 받는 유명 웹사이트가 공격 중 AWS DDoS 전문가 팀(SRT)의 지원을 받고, 공격으로 늘어난 요금에 대한 보호도 원합니다. 필요한 조치 두 개를 고르세요.

SRT 지원과 비용 보호(서비스 크레딧)는 Shield Advanced의 기능이고, SRT를 이용하려면 Business 또는 Enterprise Support 플랜도 구독해야 합니다. Shield Standard는 모든 고객에게 자동 적용되므로 신청할 것이 없습니다.

Q6. 다음 세 요구 사항에 맞는 서비스를 순서대로 고르세요. (a) S3에 저장된 고객 PII 찾기 (b) EC2 인스턴스와 ECR 이미지의 CVE 취약점 지속 스캔 (c) CloudTrail과 VPC 흐름 로그로 유출된 자격 증명·암호화폐 채굴 탐지

Macie = S3의 민감 데이터, Inspector = 워크로드의 소프트웨어 취약점, GuardDuty = 로그 기반 위협 탐지. 마지막 두 개를 바꾼 보기가 가장 흔한 함정입니다. "취약점·CVE"면 Inspector, "위협·악성 활동"이면 GuardDuty로 외우세요.

Q7. (시험형, 0002 연결) 모바일 앱 사용자가 Google 계정으로 로그인한 뒤, 앱에서 자신의 사진을 S3에 직접 업로드해야 합니다. 장기 자격 증명을 앱에 넣지 않는 가장 적절한 설계는?

사용자 풀이 Google 페더레이션 로그인을 처리하고 JWT를 주면, 자격 증명 풀이 그 토큰을 IAM 역할의 임시 AWS 자격 증명으로 바꿉니다. S3 API는 AWS 자격 증명으로 서명된 요청을 받으므로 사용자 풀 JWT만으로는 부족합니다. 액세스 키 내장은 0002에서 본 대로 장기 자격 증명 노출이라 오답입니다.

Q8. (0008 복습) Lambda 함수가 Secrets Manager의 보안 암호를 읽습니다. 보안 암호는 고객 관리형 KMS 키로 암호화되어 있고, Lambda 역할에는 secretsmanager:GetSecretValue가 허용되어 있습니다. 그런데 KMS에서 AccessDenied가 납니다. 키 정책에는 이 역할도, 계정에 위임하는 문장도 없습니다. 해결책은?

Secrets Manager는 호출자를 대신해 KMS Decrypt를 호출하므로 호출자에게 키 사용 권한이 필요합니다. 그리고 0008에서 본 대로 키 정책이 허용하지 않으면 IAM 정책으로는 허용할 수 없습니다. 오류는 KMS에서 났으니 Secrets Manager 권한을 늘려도 해결되지 않습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) GuardDuty, Macie, Inspector가 각각 무엇을 보고 무엇을 찾는지 한 줄씩. (2) Shield Standard와 Advanced의 차이 세 가지. (3) Secrets Manager와 Parameter Store를 가르는 기준과, Cognito 사용자 풀과 자격 증명 풀이 각각 주는 것.

(1) GuardDuty: CloudTrail·VPC 흐름·DNS 로그 → 위협(유출 자격 증명, 채굴, 악성 통신). Macie: S3 → 민감 데이터(PII)와 버킷 보안 문제. Inspector: EC2·ECR 이미지·Lambda → 소프트웨어 취약점(CVE)과 네트워크 노출. 셋 다 탐지만 하고 차단은 EventBridge 자동화로.

(2) Standard는 자동·무료·흔한 L3/L4 공격 방어. Advanced는 유료이며 L7 자동 완화(WAF 연동), SRT 지원(Business/Enterprise Support 필요), 비용 보호 크레딧.

(3) 자동 교체가 필요한 보안 암호면 Secrets Manager, 교체 없는 설정값이면 Parameter Store(표준 계층 무료). 사용자 풀은 로그인과 JWT, 자격 증명 풀은 임시 AWS 자격 증명.
