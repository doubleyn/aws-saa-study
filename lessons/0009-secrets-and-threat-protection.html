이름이 비슷한 보안 서비스 가려내기:
Secrets Manager, Shield, WAF, GuardDuty, Macie, Cognito 완벽 정리

AWS의 수많은 보안 서비스들은 이름이 비슷비슷해서 초심자를 가장 혼란스럽게 만듭니다. 하지만 시험 문제는 아주 명확합니다. "이 서비스가 무엇을 들여다보고(입력), 무엇을 찾아내며(출력), 악성 트래픽의 길목에서 실시간으로 막아주는가(차단) 아니면 백그라운드에서 분석해 알려주는가(탐지)?"라는 기준만 잡으면 네 개 보기 중 세 개를 단 2초 만에 지울 수 있습니다. 이번 레슨에서는 보안 암호 저장소인 Secrets Manager와 Parameter Store의 결정적 차이부터, 웹 공격을 막는 Shield와 WAF, 3대 탐지 서비스(GuardDuty, Macie, Inspector), 그리고 앱 인증과 임시 권한을 주는 Cognito의 두 가지 풀까지 원리부터 상세히 풀어냅니다.

왜 보안 암호와 위협 방어 서비스를 배워야 할까요?

시험 관점: GuardDuty, Inspector, Macie의 감시대상과 역할을 교묘하게 뒤바꾼 보기, Shield와 WAF의 방어 계층을 섞어놓은 보기, Secrets Manager와 Parameter Store의 자동 교체 가능 여부를 묻는 문제가 매 시험마다 단골로 출제됩니다. 시나리오에 등장하는 단어 하나로 정답을 판별할 수 있어야 합니다.
실무 관점: 소스 코드에 하드코딩된 데이터베이스 비밀번호, 관리되지 않는 API 토큰, 웹 계층을 파고드는 SQL 주입(SQL Injection) 공격, 계정 자격 증명 유출 및 비정상적인 암호화폐 채굴 등은 실제 클라우드 환경에서 발생하는 보안 침해 사고의 대표적 원인입니다. AWS가 제공하는 전용 보안 관리형 서비스를 적재적소에 배치하는 것은 현대 클라우드 보안 아키텍처의 필수 요건입니다.

보안 암호 관리: Secrets Manager vs Systems Manager Parameter Store 한눈에 비교하기

AWS Secrets Manager와 Systems Manager Parameter Store는 둘 다 애플리케이션이 실행 중에 설정값이나 비밀 정보를 중앙에서 안전하게 꺼내 쓰도록 돕는 저장소입니다. 두 서비스 모두 AWS KMS를 연동하여 저장 데이터를 안전하게 암호화할 수 있습니다. 그렇다면 둘 중 무엇을 선택해야 할까요? 핵심 분기점은 바로 "자격 증명 자동 교체(Rotation)"와 "저장 데이터의 성격"입니다.[2]

비교 항목AWS Secrets ManagerSystems Manager Parameter Store
주요 용도 및 데이터 성격데이터베이스 접속 비밀번호, 서드파티 API 키, OAuth 토큰 등 주기적으로 교체해야 하는 민감한 보안 암호[1]골든 AMI ID, 데이터베이스 엔드포인트 도메인, 빌드 버전, 환경 변수(DEV/PROD) 같은 정적인 일반 구성 설정값

AWS 공식 가이드의 권장 사항은 매우 명확합니다. Parameter Store의 SecureString은 라이선스 키나 간단한 패스워드처럼 암호화 저장이 필요하지만 자주 바뀌지 않는 정적 구성값에 적합합니다. 반면, 데이터베이스 로그인 비밀번호나 API 토큰처럼 유출 시 치명적이고 주기적인 자동 교체 및 멀티 리전 복제가 필요한 데이터에는 반드시 Secrets Manager를 사용할 것을 강력히 권장합니다.[2]

Secrets Manager의 두 가지 비밀번호 교체 방식

Secrets Manager의 자동 교체(Rotation)는 다음 두 가지 메커니즘으로 동작합니다.[3]

  • 관리형 교체 (Managed Rotation): Amazon RDS, Aurora, Redshift, DocumentDB 등의 마스터 사용자 자격 증명에 대해, AWS 서비스가 백그라운드에서 교체 프로세스를 완전히 자체 관리합니다. 사용자가 별도의 AWS Lambda 함수를 작성하거나 관리할 필요가 전혀 없습니다.[4]
  • Lambda 함수 기반 교체: 자체 호스팅 데이터베이스나 서드파티 SaaS API 키 등은 AWS가 제공하는 템플릿 Lambda 함수를 사용하여 교체를 수행합니다. Lambda 함수가 새 비밀번호를 생성하고 대상 데이터베이스와 Secrets Manager의 값을 동시에 안전하게 갱신합니다.[3]

멀티 리전으로 복제된 보안 암호는 기본 리전에서 비밀번호가 교체되면 모든 복제 대상 리전으로 새 비밀번호가 자동 전파됩니다.[5] 또한 레슨 0008과 연결되는 중요한 보안 원리: Secrets Manager가 고객 관리형 KMS 키로 암호화되어 있는 경우, 애플리케이션(예: Lambda, EC2의 IAM 역할)이 보안 암호 값을 조회할 때 Secrets Manager가 호출자를 대신하여 KMS Decrypt를 호출합니다. 따라서 호출자의 IAM 정책 및 해당 KMS 키의 키 정책 양쪽 모두에서 그 호출자에게 kms:Decrypt 권한이 반드시 허용되어 있어야 합니다.[6]

요청 경로에서 '막기(차단)' vs 백그라운드에서 '찾기(탐지)'

보안 서비스들을 이해하는 가장 명쾌한 방법은 서비스를 두 가지 진영으로 분류하는 것입니다. 사용자의 네트워크 요청 길목에 직접 서서 악성 트래픽을 실시간으로 막아내는(차단하는) 인라인 서비스(Shield, WAF)와, 백그라운드에서 비동기로 로그, 데이터, 소프트웨어 패키지를 분석하여 취약점과 이상 징후를 찾아내어 보고해 주는 비인라인 탐지 서비스(GuardDuty, Macie, Inspector)입니다.

막기 ①: AWS Shield (DDoS 공격 방어)

DDoS(분산 서비스 거부 공격)는 대규모 비정상 트래픽을 퍼부어 웹 서비스를 마비시키는 공격입니다. AWS는 두 가지 계층의 Shield 서비스를 제공합니다.[8]

비교 항목AWS Shield StandardAWS Shield Advanced
가입 및 활성화모든 AWS 고객에게 기본 자동 활성화, 완전 무료[8]유료 구독 플랜 (조직당 월 $3,000 기본 요금)[7]
방어 계층 및 범위가장 보편적인 네트워크 및 전송 계층(OSI 3계층/4계층)의 DDoS 공격(SYN 플러드, UDP 반사 공격 등)을 자동 완화. 특히 CloudFront, Route 53, Global Accelerator와 연계 시 탁월한 방어 효과[8]EC2, ELB, CloudFront, Route 53, Global Accelerator에 대한 광범위한 고도화 보호. 3계층/4계층은 물론 애플리케이션 계층(7계층) DDoS 공격까지 방어[7]

2. 24/7 연중무휴 AWS DDoS 대응팀(SRT, Shield Response Team)의 긴급 지원 (단, Enterprise 또는 Business Support 플랜 필수)
3. DDoS 공격으로 인스턴스 확장이 발생해 청구된 요금 폭탄에 대한 비용 보호(DDoS Cost Protection, 서비스 크레딧 환급)
4. 보호 대상 리소스에 대한 AWS WAF 표준 규칙 비용 면제[9]

막기 ②: AWS WAF (웹 애플리케이션 방화벽)

AWS WAF는 보호 대상 리소스로 유입되는 HTTP 및 HTTPS 요청(OSI 7계층)의 세부 내용을 정밀 검사하는 웹 애플리케이션 방화벽입니다.[7]

WAF를 연결할 수 있는 서비스는 다음과 같이 명확히 정해져 있습니다: Amazon CloudFront 배포, Application Load Balancer(ALB), Amazon API Gateway(REST API), AWS AppSync GraphQL API, Amazon Cognito 사용자 풀, AWS App Runner 등입니다.[7]
시험의 절대적인 오답 함정: 이 지원 목록에 Network Load Balancer(NLB)는 절대 포함되지 않습니다! NLB는 전송 계층(4계층) 로드 밸런서이므로 7계층 WAF를 직접 연결할 수 없습니다. 시험 문제에서 "NLB에 WAF 웹 ACL 연결"이라는 보기가 나오면 무조건 오답으로 소거하세요.

WAF 규칙(Web ACL)에서 검사하고 차단할 수 있는 주요 조건들은 다음과 같습니다:

  • 출발지 IP 및 지리적 위치: 특정 악성 IP 대역 차단 또는 특정 국가(Geo-match)로부터의 접속 차단/허용.
  • 웹 취약점 패턴 차단: 데이터베이스를 탈취하려는 SQL 주입(SQL Injection) 공격 패턴, 브라우저를 악용하는 크로스 사이트 스크립팅(XSS) 악성 스크립트 차단. AWS가 제공하는 관리형 규칙 그룹(AWS Managed Rules)을 클릭 한 번으로 적용할 수 있습니다.
  • 속도 기반 규칙 (Rate-based Rules): 시험의 초단골 기능입니다! 특정 클라이언트 IP가 5분 동안 지정된 횟수(예: 100건, 2,000건) 이상의 비정상적으로 빠른 요청을 보낼 때 해당 IP를 자동으로 일정 시간 차단(Block)합니다. 브루트 포스(무차별 대입) 로그인 시도, 악성 웹 크롤러 스크래핑, HTTP 플러드 공격을 방어할 때 가장 비용 효율적인 해결책입니다.[10]

만약 기업 내 여러 AWS 계정에 분산된 수많은 ALB나 CloudFront에 WAF 규칙 및 Shield 정책을 중앙에서 한 번에 강제 적용하고 관리해야 한다면 AWS Firewall Manager를 선택해야 합니다.[7]

찾기: GuardDuty, Macie, Inspector 3대 탐지 서비스 비교

이 세 서비스는 모두 보안 위협이나 취약점을 '탐지(Detect)'하여 결과(Findings)를 생성하는 비인라인 서비스입니다. 시험에서는 각 서비스가 "어떤 데이터를 분석하고, 무엇을 찾아내는가?"를 물어봅니다.[11][12][13]

서비스무엇을 들여다보나 (데이터 소스)무엇을 찾아내나 (탐지 대상)핵심 키워드
Amazon GuardDuty에이전트 설치 없이 AWS 계정의 CloudTrail 관리 및 데이터 이벤트, VPC 흐름 로그(VPC Flow Logs), DNS 쿼리 로그를 자동으로 수집 및 분석. EKS 감사 로그, RDS 로그인 이벤트 등으로 확장 가능[11]계정 및 워크로드에 대한 지능형 보안 위협. 유출된 IAM 자격 증명 사용, 손상된 EC2 인스턴스의 무단 암호화폐 채굴(Crypto Mining), 알려진 악성 C&C 도메인/IP와의 비정상 통신 등을 머신러닝과 위협 인텔리전스로 탐지위협 탐지, 악성 IP 통신, 비정상 API 호출, 암호화폐 채굴
Amazon MacieAmazon S3 버킷 및 저장된 객체의 데이터 내용[12]S3에 저장된 주민등록번호, 신용카드 번호, 여권 번호, 개인 주소 등 개인 식별 정보(PII, Personally Identifiable Information) 및 금융 데이터. 또한 퍼블릭으로 잘못 열린 S3 버킷 같은 구성 취약점 발견S3, 개인 식별 정보(PII), 민감 데이터 검색, 데이터 프라이버시
Amazon InspectorEC2 인스턴스, ECR 컨테이너 이미지, AWS Lambda 함수의 소스 코드 및 종속성[13]소프트웨어 패키지의 알려진 보안 취약점(CVE)과 의도치 않은 네트워크 노출. 인스턴스에 새 패키지가 설치되거나 전 세계적으로 새로운 CVE 취약점이 공개되면 자동으로 재스캔을 수행소프트웨어 취약점, CVE, ECR 이미지 스캔, 네트워크 도달 가능성

가장 중요한 공통 동작 원리: 이 세 가지 탐지 서비스는 자체적으로 침해 사고나 트래픽을 능동 차단하지 않습니다! 대신 탐지된 결과(Findings)를 Amazon EventBridge로 즉시 발행합니다. 사용자는 EventBridge 규칙을 트리거로 설정하여 Lambda 함수를 실행(예: 감염된 EC2 인스턴스의 보안 그룹 격리, 유출된 IAM 자격 증명 비활성화)하거나 Amazon SNS를 통해 보안 담당자에게 긴급 알림을 전송하는 완전 자동화된 침해 대응 파이프라인을 구축합니다.[12][13]
한편, 여러 계정과 여러 보안 서비스에서 쏟아지는 결과들을 한곳에 취합하여 보안 점수를 매기고 중앙 대시보드를 제공하는 서비스는 AWS Security Hub이며, 발견된 보안 위협의 근본 원인과 공격 경로를 그래프 기반으로 심층 분석(포렌식 조사)하는 서비스는 Amazon Detective입니다.[11]

Amazon Cognito: 사용자 풀(User Pool) vs 자격 증명 풀(Identity Pool)

Amazon Cognito는 웹 및 모바일 애플리케이션 사용자를 위한 인증 및 권한 부여 관리 서비스입니다. Cognito는 전혀 다른 목적을 가진 두 가지 핵심 컴포넌트로 구성되며, 초심자가 가장 많이 헷갈려 하는 영역입니다.[14]

비교 항목사용자 풀 (User Pool)자격 증명 풀 (Identity Pool / Federated Identities)
해결하려는 질문"이 사용자는 누구인가?" (인증, Authentication)"이 인증된 사용자가 어떤 AWS 리소스에 접근할 수 있는가?" (인가/권한 부여, Authorization)
최종적으로 발급하는 것표준 JWT 토큰 (ID 토큰, Access 토큰, Refresh 토큰)일시적이고 제한된 권한의 AWS 임시 자격 증명 (STS AssumeRole 자격 증명)
제공하는 핵심 기능사용자 디렉터리 데이터베이스, 회원가입 및 로그인 페이지 UI(호스팅 UI), 이메일/전화번호 인증, 다중 인증(MFA), 비밀번호 재설정. Google, Apple, Facebook 등 소셜 자격 증명 및 SAML/OIDC 기반 회사 엔터프라이즈 IdP 연동사용자 풀의 JWT 토큰이나 소셜 로그인 토큰을 입력받아 AWS IAM 역할로 교환. 로그인하지 않은 익명(게스트) 사용자에게도 제한된 임시 AWS 자격 증명 발급 가능
실제 연동 시나리오모바일 앱 사용자가 이메일/비밀번호나 Google 계정으로 로그인하게 만들고 싶을 때 단독 사용모바일 앱 사용자가 로그인한 뒤, 백엔드 서버를 거치지 않고 사용자 개인의 S3 폴더에 사진을 직접 업로드하거나 DynamoDB에 직접 쓰게 하고 싶을 때 사용자 풀과 연계하여 사용

모바일 앱이나 싱글 페이지 웹 앱(SPA)을 개발할 때 두 컴포넌트는 완벽한 콤비를 이룹니다. 먼저 사용자 풀을 통해 사용자에게 로그인을 시키고 JWT 토큰을 발급받습니다. 그런 다음, 이 JWT 토큰을 자격 증명 풀로 가져가 제출하면, 자격 증명 풀이 사전에 매핑된 IAM 역할의 권한을 담은 임시 AWS 자격 증명(Access Key, Secret Key, Session Token)을 발급해 줍니다.[14] 이렇게 하면 클라이언트 앱 코드에 어떠한 고정된 IAM 자격 증명도 하드코딩하지 않고도 S3나 DynamoDB를 안전하게 직접 호출할 수 있습니다.

시험에 자주 나오는 핵심 패턴

실전 연습 문제

학습한 내용을 바탕으로 문제를 풀어보세요. 보기 길이는 실제 시험처럼 균형 있게 구성되어 있습니다.

Q1. (시험형) 회사의 애플리케이션 소스 코드에 Amazon RDS for MySQL 데이터베이스 접속 비밀번호가 하드코딩되어 있는 것이 보안 감사에서 지적되었습니다. 규정 준수를 위해 이 자격 증명을 코드에서 즉시 분리하고, 30일마다 자동으로 교체(Rotation)해야 합니다. 개발 및 운영 오버헤드를 최소화하는 가장 좋은 해결책은 무엇인가요?

AWS Secrets Manager는 RDS 데이터베이스 자격 증명에 대한 완전 자동 교체(Rotation) 기능을 기본으로 내장하고 있으며, RDS 마스터 자격 증명에 대해서는 추가 Lambda 코드 없이도 관리형 교체를 지원합니다. Parameter Store는 자격 증명 자동 교체 기능이 전혀 없으므로 교체 로직을 개발자가 직접 만들어야 합니다. Lambda 환경 변수나 S3 저장 방식은 암호화는 가능하지만 자동 교체 작업이 전적으로 수작업이 되어 운영 오버헤드가 매우 큽니다.

Q2. (시험형) 여러 마이크로서비스 애플리케이션이 공통으로 참조하는 사내 승인 AMI ID, 백엔드 서비스 엔드포인트 URL, 배포 환경 이름(DEV/STAGE/PROD)을 중앙 저장소에서 일괄 관리하려 합니다. 저장할 값들은 비밀 정보가 아니며 주기적인 교체도 필요하지 않습니다. 추가 비용 발생을 최소화하는 가장 적절한 서비스는 무엇인가요?

AMI ID, 엔드포인트 URL, 환경 이름 등은 AWS 공식 문서가 Systems Manager Parameter Store의 표준 활용 사례로 정확히 명시하고 있는 대표적인 구성 데이터입니다. Parameter Store의 표준(Standard) 계층은 파라미터 10,000개까지 완전 무료로 제공됩니다. Secrets Manager는 저장된 보안 암호마다 월 $0.40의 비용이 부과되므로 비용 최소화 요건에 맞지 않습니다. CloudHSM은 암호화 키를 전용 하드웨어에 보관하는 서비스입니다.

Q3. (시험형) Application Load Balancer(ALB) 뒤에서 운영 중인 인터넷 공개 웹 사이트가 악의적인 공격자들로부터 빈번한 SQL 주입(SQL Injection) 및 크로스 사이트 스크립팅(XSS) 공격을 받고 있습니다. 이러한 악성 요청이 백엔드 웹 서버에 도달하기 전에 사전에 차단하기 위한 가장 적합한 조치는 무엇인가요?

SQL 인젝션과 XSS는 HTTP/HTTPS 요청 내용(본문, 쿼리 파라미터, 헤더)을 검사해야 하는 대표적인 애플리케이션 계층(OSI 7계층) 공격입니다. AWS WAF는 ALB에 직접 연결되어 이러한 악성 패턴을 실시간으로 검사하고 즉시 차단(Block)할 수 있습니다. GuardDuty는 로그를 분석해 위협을 사후에 탐지할 뿐 트래픽을 직접 차단하지 못합니다. Shield Standard는 L3/L4 수준의 DDoS 방어이며, Inspector는 소프트웨어의 취약점을 점검하는 도구입니다.

Q4. (시험형) Amazon CloudFront 배포 뒤에 위치한 웹 애플리케이션의 로그인 페이지에 몇몇 특정 IP 대역에서 비정상적으로 짧은 시간 동안 수천 건의 무차별 대입 로그인 요청이 쏟아지고 있습니다. 공격자들의 IP 주소는 수시로 변경되므로, 단위 시간당 일정 요청 속도를 초과하는 IP를 자동으로 탐지하여 즉시 차단하고 싶습니다. 올바른 해결책은 무엇인가요?

AWS WAF의 속도 기반 규칙(Rate-based Rule)은 클라이언트 IP별로 들어오는 요청 건수를 실시간으로 추적하여, 평가 기간(예: 5분) 동안 지정된 임계값을 초과하는 IP에 대해 자동으로 차단(HTTP 403) 조치를 취합니다. 공격 IP가 계속 바뀌더라도 사람의 개입 없이 자동 차단됩니다. IP 집합 규칙에 수동 등록하는 것은 실시간 대응이 불가능하며, WAF는 NLB에 연결할 수 없고, Macie는 S3 민감 데이터를 찾는 서비스입니다.

Q5. (시험형) 대규모 전자상거래 웹 사이트를 운영하는 기업이 빈번한 대규모 DDoS 공격에 노출되어 있습니다. 공격이 발생했을 때 AWS DDoS 전담 전문가 팀(SRT)의 즉각적인 개입 지원을 받고, 공격으로 인한 비정상적인 인스턴스 자동 확장 비용 급증에 대한 재정적 보호(비용 환급)를 받고자 합니다. 이를 위해 필요한 조치 두 개를 고르세요.

AWS Shield Advanced를 구독하면 연중무휴 24/7 Shield Response Team(SRT)의 전문적인 완화 지원과 DDoS 공격으로 인한 사용량 급증 시 비용 크레딧을 제공하는 '비용 보호' 혜택을 받을 수 있습니다. 단, SRT의 직접 지원을 요청하기 위한 필수 전제 조건으로 회사가 최소 Business 또는 Enterprise Support 플랜에 가입되어 있어야 합니다. Shield Standard는 모든 고객에게 기본 무료 자동 적용되므로 별도로 신청할 수 없습니다.

Q6. 다음 세 가지 보안 요구사항 (a), (b), (c)를 충족하기 위해 사용해야 하는 AWS 서비스를 순서대로 바르게 나열한 것을 고르세요.
(a) Amazon S3 버킷에 저장된 고객 데이터 중 주민등록번호, 신용카드 번호 등 PII 민감 데이터 발견
(b) EC2 인스턴스와 ECR 컨테이너 이미지에 존재하는 소프트웨어 보안 취약점(CVE) 지속 스캔
(c) CloudTrail 관리 이벤트 및 VPC 흐름 로그를 분석하여 계정 자격 증명 유출 및 무단 암호화폐 채굴 탐지

(a) S3 내부의 개인 식별 정보(PII) 탐지는 Amazon Macie의 전담 영역입니다. (b) EC2, ECR, Lambda의 소프트웨어 패키지 취약점(CVE) 및 네트워크 도달 가능성 스캔은 Amazon Inspector가 담당합니다. (c) CloudTrail, VPC Flow Logs, DNS 로그를 머신러닝으로 분석해 자격 증명 유출이나 암호화폐 채굴 등 지능형 위협을 탐지하는 것은 Amazon GuardDuty의 핵심 역할입니다. 따라서 정답은 Macie · Inspector · GuardDuty 순서입니다.

Q7. (시험형, 0002 연계) 신규 모바일 앱 사용자가 사내 계정이나 Google 소셜 계정으로 로그인한 후, 백엔드 웹 서버를 거치지 않고 자신의 스마트폰에서 Amazon S3 버킷의 개인 폴더에 직접 프로필 사진을 업로드할 수 있도록 아키텍처를 설계하려 합니다. 모바일 앱 코드에 장기적인 IAM 자격 증명을 노출하지 않으면서 이를 구현하는 가장 안전하고 표준적인 설계는 무엇인가요?

Amazon Cognito 사용자 풀(User Pool)이 사용자 로그인 및 소셜 페더레이션을 처리하여 JWT 토큰을 발급하면, 앱은 이 토큰을 Cognito 자격 증명 풀(Identity Pool)에 전달합니다. 자격 증명 풀은 사전에 연결된 IAM 역할의 일시적이고 권한이 제한된 AWS 임시 자격 증명(STS)으로 교환해 줍니다. S3 API는 AWS 자격 증명 서명을 요구하므로 사용자 풀의 JWT 토큰만으로는 S3를 직접 호출할 수 없습니다. 수만 명의 사용자마다 IAM 사용자를 만들거나 앱 바이너리에 IAM 액세스 키를 하드코딩하는 것은 절대 금지되는 안티 패턴입니다.

Q8. (0008 복습 연계) AWS Lambda 함수가 고객 관리형 KMS 키로 암호화된 AWS Secrets Manager의 데이터베이스 비밀번호를 읽어오도록 구성되어 있습니다. Lambda 함수의 실행 역할(IAM Role)에는 secretsmanager:GetSecretValue 권한이 정상적으로 부여되어 있습니다. 하지만 Lambda 함수가 실행될 때 KMS로부터 AccessDeniedException이 발생하며 실패합니다. 조사 결과 KMS 키 정책에는 해당 Lambda 실행 역할도, 계정에 권한을 위임하는 문장도 포함되어 있지 않았습니다. 올바른 해결책은 무엇인가요?

Secrets Manager는 고객 관리형 키로 암호화된 보안 암호를 읽을 때, 호출자(여기서는 Lambda 함수)를 대신하여 KMS kms:Decrypt API를 호출합니다. 따라서 호출자에게 KMS 키 복호화 권한이 반드시 필요합니다. 그리고 레슨 0008에서 배웠듯이, KMS 키 정책이 직접 허용하거나 계정 루트에 위임하지 않은 상태에서는 IAM 정책에 아무리 Allow를 선언해도 효력이 없습니다. 오류가 KMS에서 발생했으므로 KMS 키의 키 정책을 수정하여 Lambda 역할에 kms:Decrypt를 명시적으로 허용해야 합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 직접 머릿속에서 인출하여 적어보세요.
(1) GuardDuty, Macie, Inspector가 각각 무엇을 데이터 소스로 삼아 어떤 보안 문제를 찾아내는지 핵심만 요약해 보세요.
(2) AWS Shield Standard와 Shield Advanced의 결정적인 차이 세 가지(방어 범위, SRT, 비용 보호)는 무엇인가요?
(3) Secrets Manager와 Parameter Store를 선택하는 핵심 기준은 무엇이며, Cognito 사용자 풀과 자격 증명 풀이 각각 발급하는 것은 무엇인가요?

(1) GuardDuty: CloudTrail·VPC Flow Logs·DNS 로그 분석 → 자격 증명 유출, 암호화폐 채굴, 악성 IP 통신 등 지능형 위협 탐지. Macie: S3 버킷 및 객체 분석 → 주민번호·카드번호 등 PII 민감 데이터 및 버킷 노출 발견. Inspector: EC2·ECR 이미지·Lambda 분석 → 소프트웨어 취약점(CVE)과 네트워크 노출 스캔. (셋 다 백그라운드 탐지 서비스이며, 차단은 EventBridge 연계를 통해 자동화).
(2) Standard: 전 고객 무료 자동 적용, L3/L4 일반 DDoS 방어. Advanced: 유료 구독, L7 공격 자동 완화(WAF 연동), 24/7 전담 대응팀(SRT 지원, Business/Enterprise Support 필요), 공격으로 인한 요금 급증 비용 보호(크레딧 환급).
(3) Secrets Manager vs Parameter Store: 주기적인 자동 교체(Rotation)가 필요한 DB 비밀번호/토큰은 Secrets Manager, 교체 없는 정적 설정값이나 무료 저장은 Parameter Store. Cognito: 사용자 풀은 로그인/인증을 담당하며 JWT 토큰을 발급, 자격 증명 풀은 권한 부여를 담당하며 AWS 임시 자격 증명(STS)을 발급.
