장애 격리의 단위와 DNS 라우팅:
리전·AZ와 Route 53

진정한 고가용성(HA) 아키텍처 설계는 "무엇이 한꺼번에 장애를 겪을 수 있는가"라는 물리적 장애 격리 경계를 정확히 이해하는 것에서 시작합니다. 이번 레슨에서는 AWS 글로벌 인프라의 핵심인 리전과 가용 영역(AZ)의 구조적 차이를 파악하고, 장애 경계를 넘어 트래픽을 안전하고 유연하게 제어하는 Route 53의 7가지 라우팅 정책과 상태 확인 메커니즘을 완벽히 마스터합니다.

왜 리전·AZ와 Route 53부터 배워야 할까요?

시험 관점에서: AWS Certified Solutions Architect - Associate (SAA-C03) 도메인 2는 '복원력 있는 아키텍처 설계'로 전체 시험의 26% 비중을 차지합니다. 시험 문제에서 "단일 장애 지점(SPOF)을 제거하라"는 요구사항이 나오면 십중팔구 "여러 가용 영역(Multi-AZ)에 걸친 구성"이 정답의 핵심 조건으로 등장합니다. 또한 Route 53 문제는 지문에 제시된 핵심 키워드(비율 배분, 최저 지연 시간, 사용자 접속 국가, 주-보조 장애 조치 등) 하나만으로 정답 라우팅 정책이 명확하게 갈리는 대표적인 빈출 영역입니다.[5]

실무 관점에서: 대규모 클라우드 시스템에서 하드웨어나 데이터센터 장애는 "일어날 것인가"가 아니라 "언제 일어날 것인가"의 문제입니다. 화재나 정전, 침수 같은 물리적 재난이 닥쳐도 사용자가 서비스를 중단 없이 이용하게 하려면 리전과 AZ의 물리적 격리 수준을 꿰뚫고 있어야 합니다. 또한 실무에서 신규 버전을 점진적으로 배포하는 카나리(Canary) 배포, 블루/그린 배포, 리전 단위 재해 복구(DR) 전환, 글로벌 사용자를 위한 지역별 콘텐츠 분기 등이 모두 Route 53의 정교한 라우팅 규칙 몇 개로 구현됩니다.

리전, AZ, 엣지 로케이션의 물리적 구조와 장애 격리

AWS 인프라는 전 세계에 걸쳐 지리적·물리적 계층 구조로 설계되어 있습니다. 각 단위의 정의와 장애 격리 특성을 이해하는 것이 아키텍처 설계의 기본입니다.[1]

구분물리적 정의 및 구성설계 및 장애 격리 측면의 의미
리전 (Region)데이터센터들이 밀집된 전 세계의 독립적인 지리적 위치(예: 서울 리전 ap-northeast-2, 버지니아 북부 us-east-1). 각 퍼블릭 리전은 완전히 독립된 최소 3개 이상의 가용 영역(AZ)으로 구성됩니다.[1]완전한 장애 격리 경계입니다. 한 리전에서 대규모 지진이나 대정전이 발생해도 다른 리전에는 기술적·물리적 영향이 전혀 미치지 않습니다. 고객이 복제(Replication) 기능을 명시적으로 구성하지 않는 한, 데이터와 리소스는 생성된 리전 밖으로 절대 나가지 않아 데이터 주권(Data Sovereignty) 규정을 만족합니다.
가용 영역 (AZ, Availability Zone)독립적인 전력, 냉각 설비, 물리 보안, 이중화된 네트워크 연결을 갖춘 하나 이상의 개별 데이터센터 묶음입니다. 같은 리전 내의 AZ들은 물리적 재해로부터 서로 영향을 받지 않도록 유의미한 거리(수십 km 이상)로 떨어져 있습니다.[2]같은 리전 내의 AZ들은 AWS가 자체 구축한 전용 초고속 광섬유망으로 연결되어 있어, 한 자릿수 밀리초(low single-digit ms) 수준의 초저지연 통신과 동기식 데이터 복제(Synchronous Replication)가 가능합니다. 따라서 단일 AZ 장애에 대비하는 고가용성(HA) 구성의 기본 단위가 됩니다.
엣지 로케이션 (Edge Location)CloudFront(CDN), Route 53(DNS), AWS Global Accelerator 등이 동작하는 전 세계 수백 개 이상의 네트워크 거점(PoP, Point of Presence)입니다.[4]리전보다 훨씬 촘촘하게 전 세계 사용자 바로 근처에 위치합니다. 정적 콘텐츠를 캐싱하여 반환하고 디도스(DDoS) 공격을 최전선에서 흡수하여, 오리진 서버의 부하를 줄이고 최종 사용자 응답 지연을 극적으로 낮춥니다.

다중 AZ 구성과 정적 안정성(Static Stability)의 원리

흔히 "Auto Scaling이 있으니 AZ 하나가 죽어도 새 인스턴스가 다른 AZ에 자동으로 뜨면 되지 않을까?"라고 생각하기 쉽습니다. 하지만 대규모 재해가 발생해 특정 AZ 전체가 중단되면, 수많은 사용자의 시스템이 동시에 대체 인스턴스 생성을 요청하게 됩니다. 이때 인스턴스를 프로비저닝하는 EC2 컨트롤 플레인(Control Plane API)에 일시적인 병목이나 지연이 발생할 수 있습니다.[3]

진정한 고가용성을 달성하기 위해 AWS가 강력히 권장하는 원칙이 바로 정적 안정성(Static Stability)입니다. 정적 안정성이란 장애가 발생했을 때 시스템이 복구되기 위해 새로운 리소스를 생성하거나 컨트롤 플레인 API에 의존할 필요 없이, 이미 가동 중인 데이터 플레인(Data Plane) 환경 자체만으로 정상 동작을 유지하는 성질을 의미합니다.[3]

예를 들어 서비스 운영에 상시 6대의 EC2 인스턴스가 필요하다면, 3개 AZ에 2대씩(총 6대) 배치하는 대신, 3개 AZ에 각각 3대씩 총 9대를 사전 프로비저닝해 둡니다. 이렇게 설계하면 AZ 하나가 완전히 마비되더라도, 추가 인스턴스를 생성하는 지연 시간 없이 남은 2개 AZ의 6대(3대 + 3대)가 즉시 전체 트래픽을 100% 정상 수용할 수 있습니다.

Route 53 라우팅 정책 한눈에 비교하기

Amazon Route 53은 고가용성 DNS 및 도메인 이름 등록 서비스로, 전 세계 엣지 로케이션을 통해 100% 가용성 SLA를 보장합니다. 다양한 비즈니스 요구사항에 맞춰 다음 7가지 핵심 라우팅 정책을 제공합니다.[5]

라우팅 정책동작 원리 및 분산 기준시험 핵심 키워드 및 대표 사용 사례
단순 (Simple)도메인에 대해 특정 단일 리소스(또는 무작위 순서의 여러 IP 주소 목록)를 반환합니다. 상태 확인(Health Check)과 연동되지 않습니다.[5]단일 웹 서버, 특별한 라우팅 규칙이 필요 없는 기본 구성
가중치 (Weighted)각 레코드에 할당된 가중치 비율(해당 가중치 ÷ 전체 가중치 합)에 따라 트래픽을 정밀하게 분할 전송합니다. 가중치를 0으로 설정하면 해당 엔드포인트로의 트래픽이 즉시 중단됩니다.[6]"트래픽의 10%만 새 버전으로", 카나리(Canary) 배포, 블루/그린 배포, A/B 테스트
지연 시간 (Latency)사용자의 네트워크 지연 시간을 기준으로, 가장 빠른 응답 시간(최저 RTT)을 제공하는 AWS 리전으로 트래픽을 자동 라우팅합니다. 전 세계 네트워크 환경 변화에 따라 동적으로 조정됩니다.[7]"여러 리전에 배포, 사용자에게 가장 빠른 성능 제공", 글로벌 다중 리전 웹 서비스
장애 조치 (Failover)액티브-패시브(Active-Passive) 전용 정책입니다. 평소에는 주(Primary) 리소스로만 트래픽을 보내다가, 상태 확인에서 주 리소스 장애가 감지되면 보조(Secondary) 리소스로 트래픽을 자동 전환합니다.[11]"재해 복구(DR) 리전으로 자동 전환", "기본 서버 장애 시 S3 점검 중(Maintenance) 페이지 노출"
지리 위치 (Geolocation)사용자의 실제 접속 위치(대륙, 국가, 미국 주 단위 IP 매핑)를 기반으로 라우팅합니다. 매핑되지 않은 지역 사용자를 위한 기본 레코드(Default Record)를 반드시 생성해야 합니다(누락 시 '응답 없음' 반환).[8]"국가별 현지 언어 페이지", "특정 국가 전용 라이선스/콘텐츠 배포", "유럽 GDPR 등 법적 규정 준수"
지리 근접 (Geoproximity)사용자의 지리적 위치와 AWS 리소스의 물리적 위치를 동시에 계산합니다. 바이어스(Bias, -99 ~ +99) 값을 조정하여 특정 리전이 커버하는 지리적 영역을 인위적으로 확장하거나 축소할 수 있습니다.[9]"특정 리전의 서버 용량을 늘렸으니 해당 리전으로 트래픽을 더 많이 유인하고 싶을 때" (Traffic Flow 필요)
다중 값 응답 (Multivalue Answer)DNS 쿼리에 대해 상태 확인을 통과한 정상 IP를 최대 8개까지 무작위로 골라 응답합니다. 클라이언트는 받은 목록 중 하나를 선택해 접속합니다.[10]"DNS 수준의 단순 부하 분산 및 상태 확인 기능이 필요할 때" (정교한 로드 밸런서인 ALB/NLB를 완전히 대체하지는 않음)

※ 이 밖에도 클라이언트의 원본 서브넷 IP CIDR 블록에 따라 사내망이나 특정 통신사 트래픽을 구분하는 IP 기반 라우팅(IP-based Routing)도 제공됩니다.[5]

시험에서 가장 헷갈리는 핵심 구분 2가지

  1. 액티브-액티브 vs 액티브-패시브: "장애 조치(Failover) 정책"만이 장애 조치를 할 수 있는 것은 아닙니다. 가중치 라우팅이나 지연 시간 라우팅 레코드에 상태 확인(Health Check)을 연결하면, 비정상으로 판정된 엔드포인트는 DNS 응답에서 자동으로 제외되므로 자연스러운 액티브-액티브 장애 조치가 완성됩니다. 반면 "장애 조치 정책"은 오직 기본(Primary)과 보조(Secondary)가 명확히 분리된 액티브-패시브 구성 전용입니다.[11]
  2. 지리 위치(Geolocation) vs 지연 시간(Latency): 두 정책을 혼동하기 쉽습니다. 지리 위치는 "사용자가 어디에 있는가"(언어, 라이선스, 규정 준수)를 기준으로 고정 라우팅하는 반면, 지연 시간은 "어느 리전이 지금 가장 빠른가"(네트워크 성능 극대화)를 기준으로 라우팅합니다. 지리적으로 가까운 리전이라도 해저 케이블 상황이나 혼잡도에 따라 다른 리전이 더 빠를 수 있으므로 두 정책의 목적은 완전히 다릅니다.

Route 53 상태 확인(Health Check)의 작동 원리

Route 53의 상태 확인은 전 세계에 분산된 상태 확인기(Health Checker)들이 대상 엔드포인트를 주기적으로 모니터링하여 DNS 라우팅에 반영하는 기능입니다.[12]

  • 세 가지 상태 확인 유형:
    1. 엔드포인트 감시: 인터넷을 통해 공용 IP나 도메인(FQDN)으로 직접 HTTP/HTTPS/TCP 연결을 요청하여 응답 상태 코드(2xx/3xx)를 검사합니다.
    2. 계산된 상태 확인 (Calculated Health Check): 여러 개의 하위 상태 확인 결과를 조합(예: 5개 중 3개 이상 정상이면 정상)하여 복합적인 판정을 내립니다.
    3. CloudWatch 경보 감시: 외부 인터넷에서 직접 접근할 수 없는 프라이빗 리소스의 상태를 감시할 때 사용합니다.[12]
  • 정상 판정 기준: 전 세계의 상태 확인기들이 기본 30초(빠른 확인은 10초) 간격으로 핑을 보내며, 전 세계 확인기의 18%를 초과하는 확인기가 정상이라고 보고해야 정상 상태로 판정됩니다.[13]
  • 프라이빗 서브넷 리소스 모니터링 (시험 빈출!): Route 53 상태 확인기는 VPC 외부의 퍼블릭 인터넷 공간에 위치합니다. 따라서 퍼블릭 IP가 없는 프라이빗 서브넷의 EC2 인스턴스에는 직접 HTTP 요청을 보낼 수 없습니다. 이 경우 인스턴스의 CloudWatch 지표(예: StatusCheckFailed)에 경보를 걸고, 해당 CloudWatch 경보를 감시하는 상태 확인을 만들어 연결해야 합니다.[14]
  • 별칭 레코드와 대상 상태 평가 (Evaluate Target Health): ALB, NLB 등 AWS 리소스를 가리키는 별칭 레코드에서는 별도의 유료 상태 확인을 생성할 필요가 없습니다. 별칭 레코드 설정에서 Evaluate Target Health(대상 상태 평가)를 'Yes'로 켜기만 하면, 로드 밸런서 내부의 백엔드 대상 그룹(Target Group) 상태를 Route 53이 즉시 감지하여 DNS 라우팅에 반영합니다.[11]

DNS 표준에 따른 일반 레코드와 AWS가 독자적으로 확장한 별칭(Alias) 레코드의 차이는 시험과 실무 모두에서 매우 중요합니다.[15]

DNS 표준(RFC 1034)에 따라 Zone Apex에는 SOA, NS 레코드가 이미 존재하므로 CNAME 생성 불가
대상 리소스AWS 내부 리소스(ALB, NLB, CloudFront, S3 정적 웹사이트, API Gateway, Global Accelerator, VPC 인터페이스 엔드포인트 등) 및 동일 호스팅 영역의 다른 레코드모든 일반 DNS 도메인 이름 (AWS 내부 및 외부 호스트 모두 가능)
DNS 쿼리 비용AWS 리소스를 대상으로 하는 별칭 레코드 쿼리는 완전 무료표준 DNS 쿼리 요금이 건당 과금됨
대상 IP 변경 시 동작ALB나 CloudFront의 IP 주소가 동적으로 바뀌어도 Route 53 내부 엔진이 자동으로 감지하여 실시간 반영클라이언트가 CNAME 대상 도메인을 다시 질의해야 하므로 추가 DNS 조회가 발생함
상태 확인 연동Evaluate Target Health 옵션으로 백엔드 대상의 상태를 무료로 즉시 연동 가능별도의 Route 53 상태 확인을 직접 생성해 연결해야 함

시험에 자주 나오는 핵심 패턴

  • "단일 AZ 장애에도 서비스가 중단 없이 지속되도록 설계하라" → Application Load Balancer(ALB) + 여러 AZ에 걸친 Auto Scaling 그룹(ASG). 장애 발생 시 즉각 용량을 유지하려면 남은 AZ들만으로도 전체 트래픽을 처리할 수 있도록 사전에 용량을 충분히 프로비저닝(정적 안정성)해 둡니다.
  • "신규 버전 배포 시 10%의 트래픽만 먼저 보내 검증" → 가중치 라우팅(Weighted Routing) 정책을 사용해 비율을 조절합니다.
  • "글로벌 사용자에게 가장 빠른 응답 속도를 보장" → 지연 시간 라우팅(Latency-based Routing)을 적용합니다.
  • "특정 국가 사용자는 현지 법률 및 언어에 맞는 서버로 라우팅" → 지리 위치 라우팅(Geolocation Routing) + 매핑되지 않은 트래픽을 위한 기본 레코드(Default Record) 필수 구성.
  • "특정 리전의 인프라 용량을 증설하여 주변 트래픽 유입 영역을 확대" → 지리 근접 라우팅(Geoproximity Routing)에서 해당 리전 레코드에 양수 바이어스(Positive Bias)를 부여합니다.
  • "기본 리전 장애 시 대기 중인 재해 복구(DR) 리전이나 S3 점검 페이지로 자동 전환" → 장애 조치 라우팅(Failover Routing) + Route 53 상태 확인(Health Check) 구성.
  • "회사 도메인 루트(example.com, Apex)를 ALB나 CloudFront에 연결하고 쿼리 비용을 절감" → 별칭(Alias) 레코드 (CNAME은 Apex에 생성 불가).
  • "퍼블릭 IP가 없는 프라이빗 서브넷의 인스턴스를 상태 확인에 포함" → 인스턴스의 StatusCheckFailed 지표에 대한 CloudWatch 경보 기반 상태 확인 생성.

실전 연습: 직접 풀어보세요

배운 핵심 개념을 떠올리며 직접 정답을 판정해 보세요. 문제가 풀리지 않을 때는 각 라우팅 정책의 결정적 조건(비율, 지연 시간, 사용자 위치, 장애 조치)과 별칭 레코드의 특징을 되짚어보세요.

Q1. 전자상거래 웹 애플리케이션이 단일 가용 영역(AZ)에 속한 2대의 EC2 인스턴스에서 실행 중입니다. 데이터센터 수준의 화재나 정전 등 AZ 하나가 완전히 중단되어도 서비스가 중단 없이 유지되도록 아키텍처를 개선하려 합니다. 가장 적절한 조치는 무엇입니까?

가용 영역(AZ)은 독립된 전력, 냉각, 네트워크를 갖춘 물리적 장애 격리 경계입니다. 따라서 동일한 AZ 내부에서 인스턴스 대수를 늘리거나(수평 확장), 사양을 높이거나(수직 확장), 배치 그룹을 적용하더라도 해당 AZ 데이터센터 전체가 마비되면 모든 서버가 동시에 중단됩니다. ALB 뒤에서 최소 2개 이상의 AZ에 걸쳐 Auto Scaling 그룹을 배포해야 진정한 단일 장애 지점(SPOF) 제거가 이루어집니다.

Q2. 새로운 버전의 웹 애플리케이션을 배포하면서, 처음에는 전체 사용자 트래픽의 10%만 새 버전 스택으로 유입시켜 오류 여부를 검증하고, 점진적으로 비중을 높여 최종적으로 100%로 전환하려 합니다. 두 애플리케이션 스택은 서로 다른 ALB 뒤에 배포되어 있습니다. 어떤 Route 53 라우팅 정책을 사용해야 합니까?

특정 비율(예: 90% vs 10%)로 트래픽을 나누고 이를 점진적으로 조정하는 요구사항(카나리 배포, 블루/그린 전환)에는 가중치 라우팅(Weighted Routing)이 가장 적합합니다. 가중치를 90과 10으로 설정하면 총합 100에 대해 정확히 9:1 비율로 트래픽이 분배됩니다. 지연 시간 라우팅은 네트워크 왕복 시간에 따라 결정되므로 비율 제어가 불가능하고, 장애 조치는 주 리소스가 죽었을 때만 동작하며, 다중 값 응답은 여러 IP를 무작위로 반환할 뿐 고정 비율을 지정할 수 없습니다.

Q3. 법적 데이터 거버넌스 규정에 따라 독일(Germany)에 거주하는 사용자의 웹 요청은 반드시 유럽(프랑크푸르트) 리전 인프라에서만 처리되어야 합니다. 그 외 전 세계 다른 모든 국가의 사용자 요청은 미국(버지니아 북부) 리전 스택에서 처리하고자 합니다. Route 53에서 어떤 구성을 적용해야 합니까?

사용자가 접속한 "지리적 위치(국가)"를 기준으로 특정 리전으로 강제 라우팅해야 하므로 지리 위치 라우팅(Geolocation Routing)을 선택해야 합니다. 이때 가장 중요한 핵심은 독일 이외의 국가 및 IP 위치를 식별할 수 없는 접속자를 위해 기본 레코드(Default Record)를 반드시 함께 생성해야 한다는 점입니다. 기본 레코드가 없으면 독일 외 사용자는 '응답 없음(NODATA)' 오류를 겪게 됩니다. 지연 시간 라우팅은 독일 사용자가 일시적으로 버지니아 리전으로 연결될 수 있어 규정 위반이 됩니다.

Q4. 동일한 백엔드 REST API를 서울 리전과 미국 오레곤 리전에 '리전(Regional)' 엔드포인트 API Gateway로 각각 배포하고 동일한 커스텀 도메인 이름을 연결했습니다. 전 세계 클라이언트가 물리적으로 가장 응답 속도가 빠른 리전으로 자동 접속하게 하려면 Route 53에서 어떤 정책을 적용해야 합니까?

여러 리전에 동일한 서비스를 배포하고 사용자에게 가장 빠른 응답(최저 지연 시간)을 제공하고자 할 때는 지연 시간 라우팅(Latency-based Routing)이 정답입니다. AWS는 전 세계 사용자 위치와 자사 리전 간의 네트워크 왕복 시간(RTT)을 지속적으로 측정하여 지연 시간이 가장 짧은 리전의 IP를 반환합니다. 지리 위치 라우팅은 물리적 거리만 볼 뿐 실제 네트워크 경로의 지연 시간을 최적화하지 못합니다.

Q5. 기본 리전의 Application Load Balancer(ALB)에 장애가 발생하면, 다른 리전의 S3 버킷에 호스팅된 정적 웹사이트("서비스 점검 중" 안내 페이지)로 트래픽을 자동 우회시키고자 합니다. 이를 위해 Route 53에서 구성해야 할 필수 설정 2가지를 고르세요.

정답은 첫 번째(장애 조치 라우팅 레코드 생성)와 네 번째(Evaluate Target Health 설정)입니다.
① 정상 상태에서는 기본 리전의 ALB로만 서비스하다가 장애 시 보조(S3)로 넘기는 전형적인 액티브-패시브 구성이므로 장애 조치(Failover) 라우팅 정책을 사용해야 합니다.
② ALB처럼 AWS 리소스를 가리키는 별칭 레코드에서는 별도의 유료 상태 확인을 만들지 않고 Evaluate Target Health를 'Yes'로 켜면 ALB의 대상 그룹 헬스 상태가 DNS 페일오버 조건에 즉시 반영됩니다.
(다중 값 응답은 정상 상태일 때 무작위로 섞여 응답하므로 평소에도 점검 페이지가 노출되며, 루트 도메인(Apex)에는 CNAME을 생성할 수 없습니다.)

Q6. 회사의 대표 도메인인 example.com(Zone Apex) 자체를 퍼블릭 Application Load Balancer(ALB)로 직접 연결하고자 합니다. 동시에 수억 건의 사용자 DNS 조회에 대한 쿼리 비용을 최대한 아끼고, ALB의 IP가 동적으로 변경되어도 안정적으로 접속되어야 합니다. 어떤 레코드를 생성해야 합니까?

DNS 표준 규약상 호스팅 영역의 루트(Zone Apex, 예: example.com)에는 CNAME 레코드를 절대 생성할 수 없습니다(SOA 및 NS 레코드와 충돌). AWS Route 53의 별칭(Alias) 레코드는 Apex에서도 생성이 가능하며, 대상 ALB의 IP 변경을 Route 53이 내부적으로 실시간 추적하여 자동 갱신해 줍니다. 무엇보다 AWS 리소스를 가리키는 별칭 레코드 쿼리는 완전 무료이므로 대규모 트래픽에서 비용을 획기적으로 절감할 수 있습니다.

Q7. VPC 내부의 프라이빗 호스팅 영역(Private Hosted Zone)에서 장애 조치(Failover) 라우팅을 구성하려 합니다. 주 엔드포인트는 퍼블릭 IP가 없는 프라이빗 서브넷의 EC2 인스턴스입니다. 이 인스턴스의 장애 상태를 Route 53 장애 조치 메커니즘에 정상적으로 반영하려면 어떻게 해야 합니까?

Route 53 상태 확인기(Health Checker)는 VPC 외부의 퍼블릭 인터넷 공간에 위치하므로, 퍼블릭 IP가 없는 프라이빗 서브넷 내부의 인스턴스로는 직접 핑이나 HTTP 요청을 보낼 수 없습니다. 따라서 인스턴스의 StatusCheckFailed 같은 CloudWatch 지표에 경보를 설정한 뒤, 해당 CloudWatch 경보 상태를 모니터링하는 Route 53 상태 확인을 생성하여 레코드에 연결해야 합니다.

Q8. 미국 오레곤, 독일 프랑크푸르트, 일본 도쿄 3개 리전에서 지리 근접(Geoproximity) 라우팅을 운영하고 있습니다. 최근 오레곤 리전의 서버 용량을 대폭 증설하여, 기존에 도쿄나 프랑크푸르트 리전으로 가던 인접 국가 사용자 트래픽을 오레곤 리전 쪽으로 더 넓게 흡수하고 싶습니다. 가장 간단한 조치는 무엇입니까?

지리 근접 라우팅(Geoproximity Routing)에서 양수 바이어스(1 ~ 99)를 설정하면 해당 리소스가 트래픽을 처리하는 지리적 영역(반경)이 인위적으로 확대되어 인접 지역의 트래픽을 더 많이 끌어오게 됩니다. 반대로 음수 바이어스(-1 ~ -99)는 해당 영역을 축소시킵니다. AWS는 트래픽이 한 번에 과도하게 몰리지 않도록 바이어스를 조금씩 단계적으로 변경하는 것을 권장합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 다음 세 가지 핵심 질문에 대해 머릿속의 지식을 직접 정리해 적어보세요.
(1) Route 53의 핵심 라우팅 정책 7가지와 각각을 결정짓는 핵심 시험 키워드는 무엇인가요?
(2) 별칭(Alias) 레코드가 일반 CNAME 레코드보다 압도적으로 유리한 점 3가지는 무엇인가요?
(3) "단일 AZ 장애가 발생해도 서비스 용량 부족이나 과부하 없이 버티려면" 아키텍처를 어떻게 구성해야 할까요?

(1) Route 53 라우팅 정책과 핵심 키워드:
- 단순(Simple): 단일 리소스 매핑, 상태 확인 없음.
- 가중치(Weighted): 비율 기반 트래픽 분할, 카나리/블루그린 배포.
- 지연 시간(Latency): 최저 네트워크 지연 시간(RTT), 글로벌 사용자 대상 최고 성능.
- 장애 조치(Failover): 주(Primary)-보조(Secondary) 액티브-패시브 DR 전환.
- 지리 위치(Geolocation): 사용자 접속 국가/대륙 기준, 현지 언어/규정 준수, 기본(Default) 레코드 필수.
- 지리 근접(Geoproximity): 리소스 위치 + 바이어스(-99~+99)로 서비스 반경 확대/축소.
- 다중 값 응답(Multivalue): 정상 상태 IP 최대 8개 무작위 반환, DNS 수준 단순 분산.

(2) 별칭(Alias) 레코드의 장점:
① Zone Apex(example.com) 지원: CNAME이 절대 쓸 수 없는 루트 도메인에 생성 가능.
② 비용 절감: AWS 리소스로 향하는 별칭 쿼리는 완전 무료.
③ 자동 갱신 및 헬스체크: 대상 리소스(ALB 등)의 IP가 바뀌어도 Route 53이 자동 반영하며, Evaluate Target Health로 백엔드 헬스를 무료로 즉시 연동.

(3) 정적 안정성(Static Stability) 기반 Multi-AZ 구성:
Auto Scaling이 새 서버를 띄울 때까지 기다리지 않고, 남은 AZ들만으로도 100% 용량을 처리할 수 있도록 사전에 인스턴스를 초과 프로비저닝해 둡니다. (예: 평소 6대가 필요하다면 3개 AZ에 3대씩 총 9대를 띄워두어, 1개 AZ가 마비되어 3대를 잃어도 즉시 6대가 남아 장애 조작 없이 안정적으로 서비스를 유지합니다.)

추가 학습 및 실습

콘솔 실습 안내 (선택 사항): 개인 소유 도메인이 있다면 Route 53 호스팅 영역에서 가중치 레코드 2개(예: 가중치 1과 3)를 생성한 뒤, 로컬 터미널에서 dig 또는 nslookup 명령어를 반복 호출하여 실제로 1:3 비율로 IP가 반환되는지 확인해 보세요. 호스팅 영역과 상태 확인은 소액의 월 사용료가 발생하므로 실습 후 반드시 레코드와 호스팅 영역을 삭제하세요. 도메인이 없더라도 콘솔 레코드 생성 마법사에서 라우팅 정책별 옵션을 살펴보는 것만으로도 학습 효과가 큽니다.
