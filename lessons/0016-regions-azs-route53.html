장애 격리의 단위와 DNS 라우팅:
리전·AZ와 Route 53

고가용성 설계는 "무엇이 한꺼번에 망가질 수 있나"를 아는 데서 시작합니다. 오늘은 AWS의 장애 격리 경계(리전, AZ)와, 그 경계를 넘어 트래픽을 돌리는 Route 53의 라우팅 정책 일곱 가지와 상태 확인을 익힙니다.

왜 이것부터인가

  • 시험에서: "단일 장애 지점 제거"는 거의 항상 "여러 AZ에 걸쳐"이고, Route 53 라우팅 정책은 지문 키워드 하나(비율, 지연, 위치, 장애 조치)로 정답이 갈리는 문제입니다.
  • 실무에서: 배포 비율 조정(카나리), 리전 장애 조치, 국가별 서비스 분리가 모두 Route 53 레코드 몇 개로 끝납니다.

리전, AZ, 엣지 로케이션

단위정의설계 의미
리전데이터 센터를 묶은 지리적 위치. 독립되고 물리적으로 분리된 여러 AZ로 구성되며, 퍼블릭 리전은 최소 3개 AZ[1]리전끼리 격리되어 장애가 한 리전에 국한됨. 리소스와 데이터는 복제·복사 기능을 쓰지 않는 한 다른 리전에 존재하지 않음[1]
가용 영역(AZ)독립적이고 이중화된 전력·네트워크·연결을 갖춘 하나 이상의 데이터 센터. 같은 리전의 AZ끼리 최대 약 100km 떨어져 있지만 한 자릿수 밀리초 지연으로 동기 복제 가능[2]여러 AZ를 쓰면 한 AZ의 물리 인프라 문제로부터 격리됨[2]
엣지 로케이션CloudFront가 콘텐츠 사본을 캐시하는 전 세계 데이터 센터(POP)[4]사용자 가까이에서 응답해 지연을 줄임 (레슨 0025)

여러 AZ로 단일 장애 지점 없애기

AZ 3개에 배포한 서비스는 AZ 하나를 잃으면 용량의 1/3을 잃어 과부하가 올 수 있습니다. Auto Scaling이 대체 인스턴스를 띄우게 할 수도 있지만, 그러면 복구가 EC2 컨트롤 플레인(인스턴스 시작)에 의존합니다. AWS가 쓰는 방법은 남은 AZ에 미리 용량을 확보해 두는 사전 프로비저닝이고, 장애 중에 새로 무언가를 만들 필요가 없는 이 성질을 정적 안정성이라 부릅니다.[3] 예를 들어 평소 6대가 필요하면 3개 AZ에 3대씩(총 9대) 두면, AZ 하나를 잃어도 6대가 남습니다.

Route 53 라우팅 정책

정책무엇을 기준으로시험 키워드
단순한 기능을 하는 단일 리소스[5]리소스 하나, 특별한 요구 없음
가중치지정한 비율(레코드 가중치 ÷ 전체 합). 가중치 0이면 트래픽 중단[6]"10%만 새 버전", 카나리, 블루/그린
지연 시간사용자에게 지연이 가장 낮은 AWS 리전. 지연 데이터는 시간에 따라 바뀜[7]"여러 리전, 가장 빠른 응답"
장애 조치액티브-패시브. 기본이 비정상이면 보조로[11]"DR 리전", "점검 페이지로 전환"
지리 위치사용자 위치(대륙·국가·미국 주). 겹치면 가장 작은 지역 우선. 일치 없으면 기본 레코드, 없으면 "응답 없음"[8]"현지 언어", "배포 권한이 있는 국가만", 규정
지리 근접사용자와 리소스의 위치. 바이어스(1~99 확장, -1~-99 축소)로 영역 조정[9]"특정 리전으로 트래픽을 더/덜 보내기"
다중 값 응답정상인 레코드 최대 8개를 무작위로 응답. 로드 밸런서 대체는 아님[10]"DNS로 여러 IP, 상태 확인 포함"

이 밖에 사용자의 원본 IP 주소 범위로 라우팅하는 IP 기반 정책도 있습니다.[5]

장애 조치 정책이 아니어도 장애 조치는 됩니다. 장애 조치 정책이 아닌 정책(가중치, 지연 시간 등)에 상태 확인을 붙이면 액티브-액티브가 되어, Route 53이 비정상 레코드를 응답에서 뺍니다. 장애 조치 정책은 액티브-패시브용입니다.[11] 지리 위치와 지연 시간이 헷갈린다면: 지리 위치는 "어디서 왔나"(규정, 언어), 지연 시간은 "어디가 빠른가"(성능)입니다.

상태 확인

  • 세 종류: 엔드포인트 감시(IP 또는 도메인 이름으로 인터넷을 통해 요청), 다른 상태 확인 감시(계산된 상태 확인), CloudWatch 경보 감시.[12]
  • 판정: 전 세계 상태 확인기가 10초 또는 30초 간격으로 요청을 보내고, 18%를 초과하는 확인기가 정상이라 보고하면 정상입니다.[13]
  • 프라이빗 리소스: 상태 확인기는 VPC 밖에 있습니다. 프라이빗 IP만 가진 인스턴스는 CloudWatch 지표(예: StatusCheckFailed)에 경보를 걸고, 그 경보 기반 상태 확인을 씁니다.[14]
  • 별칭 레코드로 가리킬 수 있는 AWS 리소스(ELB 등)는 별도 상태 확인 대신 Evaluate Target Health를 Yes로 둡니다.[11]

시험 단골

  • "한 AZ 장애에도 서비스 유지" → ALB + 여러 AZ에 걸친 Auto Scaling 그룹. 용량 손실 없이 버티려면 남은 AZ만으로 충분하게 사전 프로비저닝
  • "일부 비율만", "점진적 전환" → 가중치 · "가장 낮은 지연" → 지연 시간 · "국가별 규정·언어" → 지리 위치(+기본 레코드) · "특정 리전 쪽으로 더" → 지리 근접 바이어스
  • "기본 리전 장애 시 보조로" → 장애 조치 정책 + 상태 확인
  • "example.com을 ALB/CloudFront로" → 별칭 레코드 (CNAME은 apex 불가)
  • "프라이빗 서브넷 인스턴스 상태 확인" → CloudWatch 경보 기반 상태 확인

연습

기억으로 푸세요.

Q1. 웹 애플리케이션이 한 AZ의 EC2 인스턴스 두 대에서 돌고 있습니다. AZ 하나에 장애가 나도 서비스가 계속되게 하려면 가장 적절한 변경은?

AZ는 독립된 전력·네트워크를 가진 장애 격리 단위라서, 한 AZ 안에서 아무리 대수나 크기를 늘려도 그 AZ가 멈추면 함께 멈춥니다. ALB와 Auto Scaling 그룹을 여러 AZ에 걸치면 한 AZ의 문제로부터 격리됩니다.

Q2. 새 버전을 배포하면서 처음에는 사용자 트래픽의 10%만 새 스택으로 보내고, 문제가 없으면 점차 늘리려 합니다. 두 스택은 서로 다른 ALB 뒤에 있습니다. 어떤 Route 53 정책이 맞습니까?

가중치 라우팅은 레코드 가중치 ÷ 전체 합의 비율로 트래픽을 나누고, 가중치를 바꿔 점진적으로 이동할 수 있습니다(새 버전 테스트가 AWS 문서의 대표 용도). 다중 값 응답은 무작위라 비율을 정할 수 없고, 장애 조치는 기본이 비정상일 때만 보조로 보냅니다.

Q3. 규정상 독일 사용자의 요청은 반드시 프랑크푸르트 리전 스택에서 처리해야 하고, 나머지 국가 사용자는 버지니아 리전 스택에서 처리하면 됩니다. 어떤 구성이 맞습니까?

"어디서 왔는가"로 고정 라우팅해야 하므로 지리 위치입니다. 독일 레코드 외에 기본 레코드를 만들어야 다른 국가와 위치를 알 수 없는 IP도 응답을 받습니다(없으면 "응답 없음"). 지연 시간 라우팅은 독일 사용자가 버지니아로 갈 수도 있어 규정을 보장하지 못합니다.

Q4. (0015 복습) 같은 API를 서울과 오레곤 리전에 리전 엔드포인트 API Gateway로 배포하고 같은 사용자 지정 도메인을 붙였습니다. 사용자가 응답이 가장 빠른 리전으로 가게 하려면?

리전 API는 여러 리전에 같은 사용자 지정 도메인을 둘 수 있고, Route 53 지연 시간 라우팅과 함께 쓰는 것이 API Gateway 문서의 예입니다.[16] 지리 위치는 위치 기준이라 반드시 가장 빠른 리전을 고르지 않습니다.

Q5. 기본 리전의 ALB가 비정상이면 다른 리전의 S3 정적 웹 사이트("점검 중" 페이지)로 자동 전환하려 합니다. 필요한 구성은? (두 개를 고르세요)

액티브-패시브는 장애 조치 정책입니다. ALB처럼 별칭으로 가리킬 수 있는 AWS 리소스는 상태 확인을 따로 만들지 않고 별칭 레코드의 Evaluate Target Health를 Yes로 둡니다. S3 웹 사이트를 보조로 두는 구성은 Route 53 문서에 그대로 나옵니다. 다중 값 응답은 둘 다 정상이면 무작위로 섞어 응답하고, apex에는 CNAME을 만들 수 없습니다.

Q6. 회사 도메인 example.com(영역 apex) 자체를 ALB로 연결하려 합니다. DNS 쿼리 비용도 줄이고 싶습니다. 어떤 레코드를 만들어야 합니까?

CNAME은 apex에 만들 수 없고, 별칭은 가능합니다. 별칭은 ALB IP가 바뀌면 Route 53이 자동 반영하며, AWS 리소스로의 별칭 쿼리는 무료입니다. ALB IP를 A 레코드에 고정하면 IP가 바뀔 때 깨집니다.

Q7. 프라이빗 호스팅 영역의 장애 조치 레코드가 프라이빗 서브넷의 EC2 인스턴스(퍼블릭 IP 없음)를 가리킵니다. 이 인스턴스의 상태를 Route 53 장애 조치에 반영하려면?

Route 53 상태 확인기는 VPC 밖에서 인터넷으로 요청하므로 프라이빗 IP에 닿지 않습니다. StatusCheckFailed 같은 CloudWatch 지표에 경보를 걸고, 그 경보의 데이터 스트림을 감시하는 상태 확인을 만듭니다. 계산된 상태 확인은 하위 상태 확인이 있어야 의미가 있습니다.

Q8. 오레곤·프랑크푸르트·도쿄 리전에 지리 근접 레코드를 두고 있습니다. 오레곤에 용량을 증설해서, 주변 지역 사용자를 더 많이 오레곤으로 보내고 싶습니다. 가장 간단한 방법은?

양수 바이어스(1~99)는 그 리소스로 트래픽이 가는 지리적 영역을 넓히고 인접 영역을 줄입니다. 음수는 반대입니다. AWS는 갑작스러운 트래픽 이동을 피하려면 바이어스를 조금씩 바꾸라고 권합니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) Route 53 라우팅 정책 일곱 가지와 각각의 시험 키워드. (2) 별칭 레코드가 CNAME보다 나은 점 세 가지. (3) "AZ 하나를 잃어도 용량이 모자라지 않게" 하려면 어떻게 배치하나?

(1) 단순(리소스 하나), 가중치(비율·카나리), 지연 시간(가장 빠른 리전), 장애 조치(액티브-패시브), 지리 위치(사용자 위치·규정·언어, 기본 레코드 필수), 지리 근접(리소스 위치 + 바이어스), 다중 값 응답(정상 레코드 최대 8개 무작위). 그 외 IP 기반.

(2) 영역 apex에 생성 가능, AWS 리소스로의 쿼리 무료, 대상 IP 변경 자동 반영(+ Evaluate Target Health로 상태 반영).

(3) 여러 AZ에 걸쳐 배치하고, 남은 AZ만으로 필요한 용량이 나오도록 미리 더 둔다(사전 프로비저닝, 정적 안정성). 예: 6대 필요 → 3개 AZ에 3대씩.
