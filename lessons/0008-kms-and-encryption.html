왜 이것인가

시험에서: "규정상 키 사용을 감사하고 교체를 직접 통제해야 한다", "기존 암호화되지 않은 RDS를 암호화하라" 같은 문제가 Task 1.3의 단골입니다.

시험에서 가장 중요한 차이 하나: AWS 관리형 키로 암호화한 리소스는 다른 계정과 공유할 수 없습니다.[1] SSE-KMS 데이터를 교차 계정으로 공유하려면 고객 관리형 키를 써서 키 정책에 상대 계정을 허용해야 합니다.[7] RDS도 AWS 관리형 키로 암호화한 스냅샷은 공유할 수 없습니다.[13]

키 정책: 0002의 예외가 여기서 나온다

0002에서 "같은 계정이면 한쪽만 허용해도 되지만, KMS 키 정책은 예외"라고 했습니다. 그 이유가 이것입니다.[2]

  1. 모든 KMS 키에는 키 정책이 정확히 하나 있습니다. 키 정책이 접근 제어의 1차 수단입니다.
  2. 키 정책이 허용하지 않으면 IAM 정책으로 허용할 수 없습니다. 키 정책의 허락 없이는 Allow하는 IAM 정책이 효과가 없습니다. 루트 사용자나 키를 만든 사람도 예외가 아닙니다. (반대로 IAM 정책으로 Deny하는 것은 키 정책 없이도 됩니다.)
  3. 기본 키 정책은 IAM 정책을 활성화합니다. 계정에 권한을 위임하는 문장이 있으면 그때부터 IAM 정책으로 키 사용을 허용할 수 있습니다.

또 키 정책은 IAM 정책과 달리 리전 단위입니다. 같은 리전의 키에만 효과가 있습니다.[2]

봉투 암호화 (개념만)

봉투 암호화는 평문 데이터를 데이터 키로 암호화하고, 그 데이터 키를 다시 다른 키로 암호화하는 방식입니다. KMS 키는 FIPS 140-3 Security Level 3 검증 HSM을 암호화되지 않은 상태로는 절대 떠나지 않습니다.[3] 그래서 큰 데이터는 KMS로 보내지 않고, KMS에서 받은 데이터 키로 가까운 곳에서 암호화합니다. S3 SSE-KMS의 실제 흐름은 다음과 같습니다.[7]

ACM: 전송 중 암호화의 인증서

AWS Certificate Manager(ACM)는 퍼블릭·프라이빗 SSL/TLS 인증서의 생성, 저장, 갱신을 대신 처리합니다. 외부 CA에서 받은 인증서를 가져올(import) 수도 있습니다.[14]

  • 붙는 곳: Elastic Load Balancing, CloudFront, API Gateway(사용자 지정 도메인) 등 통합 서비스.[15] EC2 인스턴스에 ACM 관리형 인증서를 직접 붙이려면 Nitro Enclave가 필요하므로, 보통은 앞단 ALB나 CloudFront에서 TLS를 종료합니다.
  • 리전 리소스: 리전 간 복사 불가. 그리고 CloudFront에 쓰려면 반드시 미국 동부(버지니아 북부, us-east-1)에서 요청하거나 가져와야 합니다.[14]
  • 자동 갱신: DNS 검증으로 발급한 인증서는 AWS 서비스에서 사용 중이고 검증용 CNAME 레코드가 남아 있으면 완전 자동으로 갱신됩니다.[17] 가져온 인증서는 관리형 갱신 대상이 아닙니다.[16] 만료 감시와 재가져오기는 고객 책임이며, EventBridge로 만료 임박 알림을 받을 수 있습니다.[18]

연습

기억으로 푸세요. 보기 길이는 모두 같게 맞춰 두었습니다.

Q1. (시험형) 금융 회사가 S3에 보고서를 저장합니다. 규정상 암호화 키의 사용 내역을 감사할 수 있어야 하고, 키 교체 일정과 비활성화를 회사가 직접 통제해야 합니다. 운영 부담이 가장 적은 방법은?

고객 관리형 키는 키 정책·교체·비활성화를 직접 통제하고 CloudTrail로 사용을 감사할 수 있습니다. SSE-S3는 키를 S3가 관리하므로 통제 요구를 충족하지 못합니다. SSE-C와 클라이언트 측 암호화는 통제는 되지만 키 보관·교체를 전부 회사가 떠안아 "운영 부담 최소"에 어긋납니다.

Q2. (0002 복습) 같은 계정의 역할 AppRole에 고객 관리형 키에 대한 kms:Decrypt를 허용하는 자격 증명 기반 정책이 있습니다. 그런데 키 정책에는 AppRole도, 계정에 권한을 위임하는 문장도 없습니다. AppRole이 Decrypt를 호출합니다.

KMS 키 정책은 0002 규칙 4(같은 계정 합집합)의 예외입니다. 키 정책이 허용하지 않으면 IAM 정책의 Allow는 효과가 없습니다. 기본 키 정책처럼 계정에 위임하는 문장이 있어야 IAM 정책이 비로소 작동합니다. Deny 문장은 없으니 "명시적 거부"는 아닙니다.

Q3. (시험형) 팀이 eu-west-2 리전에서 ACM 퍼블릭 인증서를 발급받았습니다. CloudFront 배포에 사용자 지정 도메인 HTTPS를 설정하려는데 인증서 목록에 그 인증서가 보이지 않습니다. 해결책은?

CloudFront에서 ACM 인증서를 쓰려면 미국 동부(버지니아 북부) 리전에서 요청하거나 가져와야 합니다. ACM 인증서는 리전 리소스라 리전 간 복사가 불가능하므로 "복사" 보기는 틀립니다.

Q4. (시험형) 운영 중인 RDS for MySQL DB 인스턴스가 암호화 없이 생성되었습니다. 감사 지적으로 저장 데이터를 암호화해야 합니다. 올바른 절차는?

RDS는 생성 시에만 암호화할 수 있습니다. 대신 암호화되지 않은 스냅샷의 암호화된 사본은 만들 수 있으므로, 그 사본에서 복원하면 됩니다. 읽기 전용 복제본은 원본과 암호화 상태가 같아야 해서 "암호화된 복제본" 보기는 불가능한 구성입니다.

Q5. 고객 관리형 대칭 KMS 키에 자동 키 교체를 켰습니다. 옳은 설명 두 개를 고르세요.

교체는 키 자료만 바꾸고, 예전 키 자료를 보관해 기존 암호문을 자동으로 복호화합니다. 데이터를 재암호화하지 않습니다. 비대칭·HMAC 키는 자동 교체를 지원하지 않아 수동 교체해야 하고, AWS 관리형 키는 매년 교체되며 끌 수 없습니다.

Q6. (시험형) 외부 CA에서 산 인증서를 ACM으로 가져와 ALB에 붙여 두었는데, 갱신을 잊어 서비스 장애가 났습니다. 재발을 막는 방법 중 운영 부담이 가장 적은 것은?

가져온 인증서는 ACM 관리형 갱신 대상이 아니라서 "자동 갱신 활성화"라는 옵션 자체가 없습니다. ACM이 DNS 검증으로 발급한 인증서는 사용 중이고 CNAME이 남아 있으면 자동 갱신됩니다. Lambda 알림은 감지일 뿐 갱신 작업은 여전히 사람 몫입니다.

Q7. (시험형) 규제상 암호화 키는 회사가 독점 통제하는 단일 테넌트 HSM에 있어야 하고, 기존 애플리케이션은 PKCS #11 인터페이스로 키를 사용합니다. 가장 적합한 서비스는?

"단일 테넌트 HSM", "독점 통제", "PKCS #11"은 모두 CloudHSM 신호입니다. 고객 관리형 키도 통제력은 높지만 키 자료는 AWS가 운영하는 HSM 플릿에 있습니다. Secrets Manager는 암호화 키가 아니라 자격 증명 같은 보안 암호를 저장하는 서비스입니다(0009).

Q8. (0002 + 오늘) 계정 A의 S3 버킷은 SSE-KMS로 암호화되어 있고 키는 aws/s3입니다. 버킷 정책으로 계정 B에 GetObject를 허용했지만 계정 B 사용자는 객체를 읽지 못합니다. 올바른 해결책은?

AWS 관리형 키로 암호화한 데이터는 교차 계정으로 공유할 수 없고, 그 키 정책은 수정할 수도 없습니다. 고객 관리형 키로 다시 암호화한 뒤 키 정책에 계정 B를 허용하고, 계정 B도 자기 사용자에게 kms:Decrypt를 줘야 합니다. 0002 규칙 5대로 교차 계정은 양쪽 모두의 허용이 필요하기 때문입니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) KMS 키 세 종류를 키 정책 통제, 교체, 교차 계정 공유 관점에서 비교하라. (2) S3 암호화 옵션 다섯 가지와 각각을 고르는 신호는? (3) 암호화되지 않은 RDS를 암호화하는 절차는?

(1) 고객 관리형: 키 정책을 내가 통제, 자동 교체 선택(기본 365일·주기 지정 가능), 키 정책으로 다른 계정 허용 가능. AWS 관리형: 정책은 조회만, 매년 자동 교체(변경 불가), 교차 계정 공유 불가. AWS 소유: 볼 수도 감사할 수도 없음, 무료.

(2) SSE-S3(기본값, 요구 없음) · SSE-KMS(감사·접근 통제·교체 제어) · DSSE-KMS(이중 계층) · SSE-C(고객이 요청마다 키 제공, S3는 키 저장 안 함) · 클라이언트 측(AWS도 평문을 보면 안 됨).

(3) 스냅샷 생성 → 스냅샷을 암호화된 사본으로 복사 → 그 사본에서 새 DB 인스턴스 복원. EBS도 같은 원리(스냅샷 → 암호화된 새 볼륨).
