왜 KMS와 암호화를 배워야 할까요?

시험 관점: "규정상 키 사용 내역을 완벽히 감사하고 키 교체 주기를 회사가 직접 통제해야 한다", "기존에 암호화되지 않은 RDS DB 인스턴스를 다운타임을 최소화하여 암호화하라", "다른 AWS 계정과 암호화된 데이터를 안전하게 공유하라" 같은 실무형 시나리오가 Task 1.3에서 가장 높은 빈도로 출제됩니다.
실무 관점: 클라우드 환경에서 암호화 키는 모든 데이터 자산의 생명줄입니다. 암호화 키 하나를 실수로 삭제하거나 접근 정책을 잘못 구성하면, 그 키로 암호화된 수 테라바이트의 비즈니스 데이터가 한순간에 영구히 복구 불가능한 상태가 됩니다. 반대로 KMS의 키 정책과 봉투 암호화 원리를 정확히 꿰뚫고 있다면, 외부 유출이나 권한 남용 위협으로부터 철통같은 보안 아키텍처를 설계할 수 있습니다.

저장 중 암호화(At Rest) vs 전송 중 암호화(In Transit)

데이터 보안은 데이터가 존재하는 상태에 따라 크게 두 가지 영역으로 나뉩니다. AWS 공식 문서에 따르면 전송 중(In Transit)은 데이터가 클라이언트와 AWS 간, 또는 서비스 간 네트워크를 타고 이동하는 동안을 의미하며, 저장 중(At Rest)은 데이터 센터의 물리 디스크나 스토리지 매체에 영구적으로 기록되어 머무르는 상태를 뜻합니다.[6]

구분저장 중 암호화 (At Rest)전송 중 암호화 (In Transit)
주요 위협스토리지 디스크 도난, 백업 스냅샷 불법 유출, 물리 장비 폐기 시 데이터 노출공공망 네트워크 도청(Sniffing), 패킷 변조, 중간자 공격(Man-in-the-Middle)
대표적인 구현 수단AWS KMS 키를 이용한 서버 측 암호화(S3 SSE, EBS, RDS 볼륨 암호화), 애플리케이션 레벨의 클라이언트 측 암호화TLS/SSL 기반의 암호화 통신(HTTPS). SSL/TLS 디지털 인증서는 AWS Certificate Manager(ACM)를 통해 무료 발급 및 자동 갱신
규정 준수 강제 방법S3 버킷 기본 암호화 강제, EBS 계정별 기본 암호화(Encryption by default) 활성화S3 버킷 정책에서 "aws:SecureTransport": "false"인 모든 요청에 대해 Deny를 선언하여 일반 HTTP 접속을 차단[10]

KMS 키의 세 가지 종류: 한눈에 비교하기

AWS Key Management Service(KMS)에서 사용하는 KMS 키(과거 CMK로 불림)는 키를 생성하고 관리하는 주체와 권한의 범위에 따라 세 가지로 명확히 나뉩니다.[1]

비교 항목고객 관리형 키 (Customer Managed Key)AWS 관리형 키 (AWS Managed Key)AWS 소유 키 (AWS Owned Key)

시험에서 가장 결정적인 차이점 하나를 반드시 기억하세요: AWS 관리형 키(aws/s3 등)로 암호화한 리소스는 다른 AWS 계정과 절대 공유할 수 없습니다.[1] AWS 관리형 키의 키 정책은 AWS가 소유하므로 외부 계정의 접근을 허용하도록 수정할 수 없기 때문입니다. 따라서 SSE-KMS로 암호화된 S3 객체나 암호화된 RDS 스냅샷을 교차 계정(Cross-Account)으로 공유해야 한다면, 무조건 고객 관리형 키를 생성하여 키 정책에 상대 계정을 명시적으로 허용해야 합니다.[7][13]

KMS 키 정책: IAM 정책과의 관계와 예외 규칙

레슨 0002에서 "동일 계정 내부에서는 IAM 정책이나 리소스 정책 중 어느 한쪽만 Allow해도 접근할 수 있다(합집합 규칙)"고 배웠습니다. 하지만 KMS 키 정책은 이 규칙의 가장 대표적인 예외입니다.[2]

  1. 모든 KMS 키에는 반드시 하나의 키 정책(Key Policy)이 존재합니다. 키 정책은 해당 키에 대한 접근을 결정하는 최우선이자 필수적인 관문입니다.
  2. 키 정책이 허용하지 않으면 IAM 정책의 Allow는 아무런 효력이 없습니다. 키 정책이 닫혀 있다면, 계정의 루트 사용자(Root User)나 관리자 권한(AdministratorAccess)을 가진 IAM 사용자라도 키에 접근할 수 없습니다. 오직 키 정책이 명시적으로 권한을 위임하거나 허용해야만 IAM 정책이 비로소 작동합니다. (단, IAM 정책의 Deny는 언제나 즉시 적용됩니다.)
  3. 기본 키 정책(Default Key Policy)의 핵심 문장: 콘솔에서 고객 관리형 키를 생성할 때 기본 적용되는 정책에는 "루트 계정에 모든 권한을 위임한다"는 문장이 들어 있습니다. 이 문장이 있어야 비로소 계정 관리자가 IAM 사용자나 역할에 붙인 IAM 정책으로 키 권한을 제어할 수 있게 됩니다. 만약 이 위임 문장을 지워버리면 IAM 정책으로는 키를 제어할 수 없게 됩니다.

또한 KMS 키는 리전 단위의 독립적인 리소스입니다. 한 리전에서 만든 키와 그 키 정책은 오직 해당 리전 내에서만 효력을 발휘합니다.[2]

봉투 암호화(Envelope Encryption): 왜 데이터 키를 따로 쓸까요?

봉투 암호화란 실제 데이터는 데이터 키(Data Encryption Key, DEK)라는 별도의 대칭 키로 암호화하고, 그 데이터 키를 다시 상위의 KMS 키(Key-encrypting key)로 감싸서 암호화하는 이중 암호화 구조를 말합니다.[3]

왜 대용량 데이터를 KMS로 직접 보내서 암호화하지 않고 이런 복잡한 방식을 쓸까요?

  • KMS 키의 절대적 보호: KMS 키는 FIPS 140-3 보안 레벨 3 검증을 받은 AWS의 하드웨어 보안 모듈(HSM) 내부에 영구히 머무르며, 평문 상태로는 절대로 HSM 바깥으로 빠져나오지 않습니다.
  • 네트워크 대역폭과 성능 병목 방지: 수 기가바이트(GB)에 달하는 큰 파일이나 데이터베이스를 네트워크를 통해 일일이 KMS로 전송하여 암호화/복호화한다면 엄청난 네트워크 병목과 심각한 지연 시간(Latency)이 발생하며, KMS API 호출 제한(Quota)에도 걸리게 됩니다. 따라서 KMS API(Encrypt)는 최대 4KB 크기의 데이터만 직접 암호화하도록 설계되어 있습니다.
  • 고성능 로컬 암호화: 대용량 데이터는 데이터가 존재하는 로컬(예: S3, EBS, 애플리케이션 메모리)에서 빠른 속도로 직접 암호화하고, 오직 아주 작은 크기의 '데이터 키'만 KMS와 주고받음으로써 최고의 보안성과 성능을 동시에 달성합니다.

S3 SSE-KMS의 실제 암호화 및 복호화 흐름을 살펴보면 이해가 훨씬 명확해집니다.[7]

  1. 업로드 시점: 클라이언트가 S3에 데이터를 올리면, S3 서비스가 KMS에 kms:GenerateDataKey API를 호출합니다. KMS는 평문 데이터 키와 암호화된 데이터 키 사본을 함께 S3에 전달합니다. S3는 평문 데이터 키로 객체 데이터를 로컬에서 초고속으로 암호화한 뒤, 평문 데이터 키를 메모리에서 즉시 영구 삭제합니다. 그리고 [암호화된 객체]와 [암호화된 데이터 키]를 디스크에 함께 저장합니다.
  2. 다운로드 시점: 사용자가 S3 객체를 요청하면, S3는 저장되어 있던 [암호화된 데이터 키]를 꺼내 KMS에 kms:Decrypt API를 호출합니다. KMS는 내부의 KMS 키로 이를 복호화하여 평문 데이터 키를 S3에 돌려줍니다. S3는 이 키로 암호화된 데이터를 복호화하여 사용자에게 전달한 뒤, 평문 키를 메모리에서 즉시 지웁니다.

따라서 SSE-KMS로 암호화된 S3 버킷에 객체를 업로드하려면 kms:GenerateDataKey 권한이 필요하고, 객체를 다운로드하려면 kms:Decrypt 권한이 반드시 필요합니다.[7] 시험 문제에서 "S3 버킷 정책과 IAM 정책에는 분명 s3:GetObject 권한이 있는데 AccessDenied 오류가 발생한다"는 상황이 나오면, 십중팔구 해당 객체를 암호화한 KMS 키에 대한 kms:Decrypt 권한이 누락된 것입니다.

KMS 키 교체(Rotation)와 삭제 수명 주기

보안 규정 준수(Compliance)를 위해서는 주기적으로 암호화 키를 교체해야 합니다. KMS의 키 교체와 삭제 메커니즘은 다음과 같이 운영됩니다.[4][5]

구분상세 동작 및 원리
자동 키 교체 (선택)고객 관리형 대칭 키에서 활성화 여부를 선택할 수 있습니다. 활성화하면 기본 365일(1년)마다 자동 교체되며, 필요에 따라 90일~2,560일 사이의 주기를 직접 지정할 수 있습니다. 즉시 교체가 필요한 경우 온디맨드 키 교체를 실행할 수도 있습니다.[4]
교체 시 바뀌는 것KMS 내부의 백그라운드 키 자료(Key Material)만 새로 생성됩니다. 중요한 점은 키 ID, 키 ARN, 키 별칭(Alias), 키 정책은 전혀 바뀌지 않는다는 사실입니다. 이전 세대의 키 자료는 KMS 내부에 영구 보관되므로, 과거에 암호화된 데이터도 아무런 추가 조치 없이 자동으로 복호화됩니다. 따라서 애플리케이션 코드를 수정하거나 기존 데이터를 재암호화할 필요가 전혀 없습니다.[4]
자동 교체 미지원 대상비대칭 KMS 키, HMAC 키, 사용자가 직접 가져온 키 자료(Imported Key Material) 등은 자동 교체를 지원하지 않습니다. 이 경우 새 키를 생성하고 기존 키 별칭(Alias)을 새 키로 가리키도록 변경하는 수동 교체(Manual Rotation) 방식을 사용해야 합니다.[4]
AWS 관리형 키의 교체AWS가 1년(365일)마다 100% 자동으로 교체합니다. 고객이 이 주기를 끄거나 변경할 수 없습니다.[4]
키 삭제 절차와 대기 기간고객 관리형 키는 실수로 인한 즉각적인 데이터 영구 손실을 방지하기 위해 즉시 삭제가 불가능합니다. 반드시 7일~30일(기본값 30일)의 대기 기간을 설정하여 삭제를 예약해야 합니다. 대기 기간 중에는 언제든 삭제를 취소할 수 있습니다. 대기 기간이 끝나 키가 완전히 삭제되면, 해당 키로 암호화된 모든 데이터는 절대 복구할 수 없습니다. 따라서 영구 삭제에 확신이 없을 때는 삭제 예약 대신 키를 비활성화(Disable)하여 이상 여부를 먼저 모니터링하는 것이 권장됩니다.[5]

S3 암호화 옵션 완벽 정리

2023년 1월부터 Amazon S3에 업로드되는 모든 새로운 객체는 추가 비용 없이 기본적으로 SSE-S3(256비트 AES) 방식으로 자동 암호화됩니다.[6] 따라서 시험에서는 "기본 암호화 이상의 엄격한 보안 요건이 주어졌을 때 어떤 방식을 선택해야 하는가?"를 집중적으로 평가합니다.

암호화 옵션키 관리 주체핵심 특징 및 선택 기준 (시험 키워드)
SSE-S3 (서버 측 암호화)Amazon S3가 완전 관리S3의 기본 암호화 설정. 추가 비용이나 운영 부담 없이 기본적인 저장 데이터 암호화 규정을 충족할 때 선택
SSE-KMS (KMS 서버 측 암호화)AWS KMS 키 (AWS 관리형 또는 고객 관리형)키 정책을 통한 접근 통제, CloudTrail을 통한 키 사용 내역 감사, 사용자가 직접 주도하는 키 교체 및 비활성화가 필요할 때 선택.[7] KMS 키는 S3 버킷과 반드시 동일한 리전에 있어야 함
DSSE-KMS (이중 계층 KMS 암호화)AWS KMS 키금융이나 국방 등 매우 엄격한 규정 준수를 위해 스토리지 계층에서 서로 다른 키로 이중(Dual-layer) 암호화를 의무화할 때 선택[6]
SSE-C (고객 제공 키 암호화)고객이 요청마다 키를 HTTP 헤더로 전송암호화 연산은 S3 서버가 수행하지만, S3는 암호화 키를 절대 저장하지 않음. 통신 구간 도청을 막기 위해 반드시 HTTPS 통신 필수. 만약 고객이 키를 분실하면 해당 객체는 영원히 복구 불가. (2026년 4월부터 신규 버킷 기본 비활성화)[8]
클라이언트 측 암호화 (Client-Side)고객이 업로드 전 자체 환경에서 암호화AWS를 포함한 그 누구에게도 원본 평문 데이터가 노출되어서는 안 될 때 선택. 애플리케이션 코드가 데이터를 암호화한 뒤 S3에 올리므로, S3는 이미 암호화된 불투명한 바이트 덩어리만 수신하여 보관함[9]

비용 최적화 팁 (S3 Bucket Key): SSE-KMS를 사용할 때 객체 요청 수가 수백만~수억 건에 달하면 KMS API 호출 비용이 크게 증가할 수 있습니다. 이때 S3 Bucket Key 기능을 활성화하면, S3가 버킷 레벨의 임시 키를 생성하여 KMS 호출 횟수를 획기적으로 줄여줌으로써 KMS 요청 비용을 최대 99%까지 절감할 수 있습니다.[7]
기존 데이터 처리 팁: 버킷의 기본 암호화 설정을 SSE-KMS로 변경하더라도, 이전에 이미 업로드되어 있던 기존 객체들은 자동으로 소급 암호화되지 않습니다. 기존 객체까지 새로운 암호화 설정으로 전환하려면 S3 Batch Operations를 실행하여 객체를 자기 자신 위치로 복사(Copy)하는 작업을 수행해야 합니다.[6]

EBS와 RDS: "나중에 클릭 한 번으로 켜기"가 불가능한 이유

EBS 볼륨과 RDS 데이터베이스 인스턴스는 처음 생성할 때 암호화를 켜지 않았다면, 나중에 실행 중인 상태에서 클릭 한 번으로 암호화를 켤 수 없습니다. 이미 디스크 블록 레벨에 평문으로 기록된 데이터를 실시간으로 인플레이스(In-place) 암호화할 수 없기 때문입니다.[11][13]

비교 항목Amazon EBS 볼륨Amazon RDS DB 인스턴스
암호화 보호 범위볼륨에 저장된 데이터, 인스턴스와 볼륨 간 전송 데이터, 해당 볼륨에서 생성된 스냅샷, 그 스냅샷으로 생성한 모든 파생 볼륨[11]기본 DB 스토리지, 트랜잭션 로그, 자동 백업 파일, 읽기 전용 복제본(Read Replica), DB 스냅샷 전체[13]
기존 미암호화 리소스 암호화 절차1. 기존 볼륨의 스냅샷 생성
2. 스냅샷을 복사하면서 암호화 옵션 활성화
3. 암호화된 스냅샷으로 새로운 암호화 볼륨 생성 후 교체[11]		1. DB 인스턴스의 스냅샷 생성
2. 스냅샷을 복사하면서 암호화 옵션(KMS 키) 활성화
3. 암호화된 스냅샷 사본에서 새로운 DB 인스턴스 복원[13]
암호화 해제 가능 여부한 번 암호화된 볼륨은 암호화 해제 불가한 번 암호화된 DB 인스턴스는 암호화 해제 불가
강제 및 제약 사항계정 단위 기본 암호화(Encryption by default) 설정 가능. 켜면 이후 생성되는 모든 신규 볼륨이 자동 암호화됨 (기존 볼륨 소급 적용 X)[12]읽기 전용 복제본은 반드시 원본 DB와 암호화 상태가 동일해야 함. 스냅샷을 다른 리전으로 복사할 때는 대상 리전의 KMS 키를 새로 지정해야 함[13]

ACM (AWS Certificate Manager): 전송 중 암호화를 위한 인증서 관리

AWS Certificate Manager(ACM)는 웹 애플리케이션의 SSL/TLS 퍼블릭 및 프라이빗 디지털 인증서를 손쉽게 요청, 발급, 배포, 그리고 자동 갱신해 주는 완전관리형 서비스입니다. 타사 외부 CA(Certificate Authority)에서 구입한 인증서를 가져와(Import) 등록할 수도 있습니다.[14]

  • 인증서가 연결되는 대상: Application Load Balancer(ALB), Network Load Balancer(NLB), CloudFront 배포, API Gateway(사용자 지정 도메인) 등 AWS 통합 서비스의 엔드포인트에 직접 바인딩됩니다.[15] ACM 퍼블릭 인증서의 개인 키는 외부로 내보낼(Export) 수 없으므로, 개별 백엔드 EC2 인스턴스에 직접 설치하는 대신 앞단의 ALB나 CloudFront에서 TLS 핸드셰이크를 종료(SSL Termination)하는 아키텍처가 표준입니다.
  • 리전 리소스의 특성과 CloudFront의 필수 규칙: ACM 인증서는 특정 리전에 귀속되며 다른 리전으로 복사할 수 없습니다. 특히 시험에서 가장 중요한 규칙: 글로벌 엣지 서비스인 Amazon CloudFront에 사용자 지정 도메인용 HTTPS 인증서를 적용하려면, 반드시 미국 동부(버지니아 북부, us-east-1) 리전의 ACM에서 인증서를 발급받거나 가져와야 합니다.[14]
  • 자동 갱신(Managed Renewal)의 조건과 한계: ACM에서 DNS 검증 방식으로 발급받은 인증서는 AWS 통합 서비스에서 실제로 사용 중이고 DNS CNAME 검증 레코드가 유지되는 한, 만료 60일 전부터 100% 완전 자동으로 갱신됩니다.[17] 하지만 외부 CA에서 직접 가져온 인증서(Imported Certificate)는 ACM이 자동으로 갱신할 수 없습니다.[16] 가져온 인증서의 만료일을 추적하고 외부에서 재발급받아 다시 가져오는 것은 고객의 책임이며, 만료 임박 알림은 Amazon EventBridge와 CloudWatch 경보를 연동하여 구성해야 합니다.[18]

KMS vs CloudHSM: 언제 무엇을 선택해야 할까?

시험에서 전용 하드웨어 보안 장비와 관련된 문제가 나오면 KMS와 CloudHSM의 명확한 차이점을 파악해야 합니다.[19][20]

비교 항목AWS KMSAWS CloudHSM
기반 인프라AWS가 중앙에서 멀티테넌트로 공유 운영하는 FIPS 140-3 Level 3 검증 HSM 하드웨어 풀[20]고객 전용 VPC 내에 프로비저닝되는 단일 테넌트(Single-tenant) 전용 HSM 어플라이언스. FIPS 140-2 / 140-3 Level 3 검증[19]
사용자 및 권한 제어AWS IAM 정책 및 KMS 키 정책과 완벽히 통합되어 권한 제어고객이 HSM 어플라이언스의 암호화 사용자(CU/CO)를 직접 관리. AWS 직원은 물론 IAM으로도 HSM 내부 키에 접근 불가[19]
운영 및 관리 부담매우 낮음. 고가용성, 내구성, 패치, 확장을 AWS가 완전 관리매우 높음. 고가용성 클러스터 구성, 백업, 장애 조치 관리를 고객이 직접 담당
핵심 선택 신호 (시나리오 키워드)"완전관리형 암호화", "AWS 서비스와의 완벽한 기본 통합", "최소한의 운영 오버헤드""단일 테넌트 전용 하드웨어 필요", "기업이 암호화 키를 배타적으로 독점 통제", PKCS #11, JCE, Microsoft CNG 표준 인터페이스를 사용하는 기존 레거시 앱 이전[19]

두 서비스의 절충안으로 KMS 사용자 지정 키 스토어(Custom Key Store with CloudHSM)가 있습니다. 이는 애플리케이션 인터페이스는 KMS API를 그대로 사용하면서, 실제 키 자료는 고객 소유의 CloudHSM 클러스터 내부에 생성·보관하는 방식입니다. 하지만 대칭 키만 지원하고 자동 교체가 지원되지 않으며 지연 시간이 늘어날 수 있으므로, 엄격한 법적·규제적 단일 테넌트 요건이 명시된 경우에만 제한적으로 검토해야 합니다.[20]

"키 사용 내역 감사 + 키 교체 일정 회사가 직접 통제" → SSE-KMS + 고객 관리형 키 · "추가 요건 없이 최소 비용으로 기본 암호화" → SSE-S3(기본값) · "AWS를 포함한 제3자에게 평문 절대 노출 금지" → 클라이언트 측 암호화 · "다른 AWS 계정과 암호화된 S3 객체/스냅샷 공유" → 고객 관리형 키 생성 후 키 정책에 상대 계정 ID 허용 · "기존 암호화되지 않은 EBS/RDS 암호화" → 스냅샷 생성 → 복사하면서 암호화 활성화 → 암호화된 스냅샷에서 새 볼륨/DB 복원 · "CloudFront 배포 설정 시 ACM 인증서가 보이지 않음" → us-east-1(버지니아 북부) 리전에서 인증서 발급 · "단일 테넌트 HSM, 독점적 키 제어, PKCS #11 호환" → AWS CloudHSM · "S3 버킷에 HTTPS 접속만 강제" → 버킷 정책에서 aws:SecureTransport: "false" 요청에 대해 Deny 선언

실전 연습 문제

학습한 내용을 바탕으로 문제를 풀어보세요. 보기 길이는 실제 시험처럼 균형 있게 구성되어 있습니다.

Q1. (시험형) 한 금융 회사가 규정 준수 보고서를 Amazon S3 버킷에 저장하고 있습니다. 금융 규정상 암호화 키의 모든 사용 내역을 완벽히 감사할 수 있어야 하며, 키 교체 주기와 특정 시점의 키 비활성화를 회사가 직접 통제할 수 있어야 합니다. 운영 오버헤드를 최소화하면서 이러한 규제 요건을 충족하는 아키텍처는 무엇인가요?

고객 관리형 KMS 키(Customer Managed Key)를 사용하면 CloudTrail을 통해 키 사용 내역을 완전히 감사할 수 있고, 키 정책 관리, 교체 주기 설정, 긴급 비활성화(Disable)를 회사가 직접 통제할 수 있습니다. SSE-S3는 키를 S3가 관리하므로 감사 및 통제 요구를 만족하지 못합니다. SSE-C나 클라이언트 측 암호화는 통제는 가능하지만 키 보관, 버전 관리, 교체 작업을 회사가 전적으로 구현해야 하므로 '운영 오버헤드 최소화'에 어긋납니다.

Q2. (0002 복습 연계) 동일한 AWS 계정 내부의 IAM 역할 AppRole에 고객 관리형 KMS 키에 대한 kms:Decrypt를 허용하는 IAM 정책이 연결되어 있습니다. 하지만 해당 KMS 키의 키 정책에는 AppRole도, 계정 전체에 권한을 위임하는 문장도 누락되어 있습니다. AppRole이 해당 키로 암호화된 데이터를 복호화하려고 시도하면 어떻게 되나요?

KMS 키 정책은 레슨 0002에서 다룬 '동일 계정 합집합 허용 규칙'의 가장 대표적인 예외입니다. KMS 키 정책이 직접 허용하거나 계정 루트에 위임하지 않으면, IAM 정책의 Allow는 아무런 효과가 없습니다. 키 정책의 허가가 없으므로 기본 거부(Implicit Deny)에 의해 요청이 거부됩니다. 명시적 거부(Explicit Deny) 문장이 존재해서 거부된 것은 아니므로 네 번째 보기는 틀립니다.

Q3. (시험형) 한 개발팀이 eu-west-2(런던) 리전의 ACM에서 퍼블릭 SSL/TLS 인증서를 성공적으로 발급받았습니다. 이후 전 세계 사용자를 위해 Amazon CloudFront 배포를 생성하고 사용자 지정 도메인 HTTPS를 적용하려 했으나, 인증서 선택 드롭다운 목록에 발급받은 인증서가 나타나지 않습니다. 이 문제를 해결하기 위한 올바른 방법은 무엇인가요?

Amazon CloudFront는 글로벌 서비스이지만, 사용자 지정 도메인에 연결할 SSL/TLS 인증서는 기술적 구조상 반드시 미국 동부(버지니아 북부, us-east-1) 리전의 ACM에서 발급받거나 해당 리전으로 가져와야 합니다. 또한 ACM 인증서는 특정 리전에 종속된 리소스이므로 다른 리전으로 복사하는 기능 자체가 지원되지 않습니다.

Q4. (시험형) 현재 프로덕션 환경에서 실행 중인 Amazon RDS for MySQL DB 인스턴스가 생성 당시 암호화되지 않은 상태로 프로비저닝되었습니다. 내부 보안 감사 지적으로 인해 저장 데이터를 반드시 암호화해야 합니다. 다운타임과 데이터 손실을 최소화하면서 이 요구사항을 충족하는 올바른 절차는 무엇인가요?

Amazon RDS는 이미 생성된 기존 인스턴스에 사후 암호화를 직접 켤 수 없습니다. 올바른 해결 절차는 (1) 기존 DB 인스턴스의 스냅샷을 생성하고, (2) 그 스냅샷을 복사하면서 KMS 암호화 옵션을 활성화하여 '암호화된 스냅샷 사본'을 만든 뒤, (3) 해당 사본으로부터 새로운 암호화된 DB 인스턴스를 복원하는 것입니다. 원본이 암호화되지 않은 경우 읽기 전용 복제본만 따로 암호화하여 생성하는 것은 기술적으로 불가능합니다.

Q5. 고객 관리형 대칭 KMS 키에서 '자동 키 교체(Automatic Key Rotation)'를 활성화했습니다. 이 기능의 동작 방식으로 옳은 설명 두 개를 고르세요.

KMS 키 교체는 키 ID, ARN, 별칭, 정책을 전혀 변경하지 않으며, 오직 내부의 백그라운드 키 자료만 바꿉니다. 이전 키 자료가 보존되므로 기존 데이터를 다시 암호화(Re-encrypt)할 필요 없이 자동으로 복호화됩니다. 고객 관리형 키의 기본 교체 주기는 365일이며 90~2,560일 사이로 직접 설정할 수 있습니다. 비대칭 키는 자동 교체를 지원하지 않으며, AWS 관리형 키는 매년 자동 교체되지만 사용자가 기능을 끌 수 없습니다.

Q6. (시험형) 외부 상용 CA에서 구매한 SSL/TLS 인증서를 ACM으로 가져와(Import) Application Load Balancer에 연결해 두었습니다. 하지만 담당자가 갱신 시점을 놓쳐 인증서가 만료되면서 대규모 서비스 접속 장애가 발생했습니다. 향후 이러한 사고를 방지하고 운영 부담을 최소화하는 가장 좋은 대책은 무엇인가요?

외부에서 가져온 인증서(Imported Certificate)는 ACM이 자체적으로 재발급하거나 자동 갱신할 수 없습니다. 따라서 운영 오버헤드를 없애는 가장 확실한 방법은 ACM에서 직접 퍼블릭 인증서를 요청하고 DNS 검증 방식을 사용하는 것입니다. 도메인 CNAME 레코드가 유지되고 서비스에 연결되어 있는 한 ACM이 100% 완전 자동으로 갱신을 수행합니다.

Q7. (시험형) 한 회사가 전자금융거래 규정에 따라 암호화 키를 회사가 물리적으로 독점 통제하는 단일 테넌트(Single-tenant) FIPS 140-2/3 Level 3 검증 하드웨어 보안 모듈에 보관해야 합니다. 또한 기존 레거시 온프레미스 애플리케이션은 PKCS #11 인터페이스를 통해 키와 직접 통신합니다. 가장 적합한 AWS 서비스는 무엇인가요?

"단일 테넌트 전용 하드웨어", "고객의 배타적 독점 통제", "PKCS #11 / JCE / CNG 인터페이스 지원"은 모두 AWS CloudHSM을 지목하는 핵심 키워드입니다. AWS KMS의 고객 관리형 키 역시 매우 안전하지만, 하드웨어 풀은 AWS가 관리하는 멀티테넌트 환경입니다. Secrets Manager는 암호화 키가 아닌 데이터베이스 비밀번호나 API 토큰을 보관하는 서비스입니다.

Q8. (0002 + 오늘 연계) 계정 A의 S3 버킷에 저장된 객체들이 AWS 관리형 키(aws/s3)로 SSE-KMS 암호화되어 있습니다. 계정 A의 관리자가 버킷 정책에 계정 B의 IAM 역할을 Principal로 지정하여 s3:GetObject를 허용했습니다. 하지만 계정 B의 사용자는 여전히 객체를 읽을 수 없습니다. 올바른 원인 분석과 해결책은 무엇인가요?

AWS 관리형 키(aws/s3)는 AWS 서비스 계정이 소유하므로 고객이 키 정책을 직접 수정할 수 없으며, 따라서 기술적으로 교차 계정(Cross-Account) 공유가 불가능합니다. 교차 계정 접근을 허용하려면 반드시 '고객 관리형 키'를 생성하여 데이터를 재암호화한 뒤, 키 정책에 계정 B를 허용하고, 계정 B 측 IAM 정책에서도 kms:Decrypt를 허용해야 합니다(교차 계정 양방향 허용 원칙).

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 직접 머릿속에서 인출하여 적어보세요.
(1) KMS 키 세 종류(고객 관리형, AWS 관리형, AWS 소유)를 키 정책 통제권, 자동 교체 주기, 교차 계정 공유 가능 여부 관점에서 비교해 보세요.
(2) S3 암호화 옵션 다섯 가지(SSE-S3, SSE-KMS, DSSE-KMS, SSE-C, 클라이언트 측)와 각각을 선택하는 핵심 시나리오 신호는 무엇인가요?
(3) 이미 암호화되지 않은 상태로 생성된 EBS 볼륨과 RDS DB 인스턴스를 암호화하는 표준 3단계 절차는 무엇인가요?

(1) 고객 관리형 키: 고객이 키 정책을 100% 통제, 자동 교체 선택 가능(기본 365일 또는 주기 직접 지정), 키 정책을 통해 다른 계정과 공유 가능. AWS 관리형 키: 키 정책 읽기만 가능(수정 불가), 매년 365일마다 AWS가 자동 교체(끌 수 없음), 교차 계정 공유 절대 불가. AWS 소유 키: 고객 계정에서 보이지 않으며 완전 무료.
(2) SSE-S3(추가 요구 없는 기본 무료 암호화) · SSE-KMS(CloudTrail 감사, 키 정책 제어, 직접 교체 통제 필요 시) · DSSE-KMS(규정 준수를 위한 이중 계층 암호화) · SSE-C(고객이 요청마다 키를 보내고 S3는 키 미저장, HTTPS 필수) · 클라이언트 측 암호화(AWS에게도 평문 노출을 절대 허용할 수 없을 때).
(3) 기존 리소스의 스냅샷 생성 → 스냅샷을 복사하면서 암호화(KMS 키) 활성화 → 암호화된 스냅샷 사본에서 새로운 볼륨 또는 DB 인스턴스 복원. (EBS는 계정별 기본 암호화 설정으로 향후 신규 볼륨 자동 암호화 가능).
