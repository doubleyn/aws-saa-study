S3를 싸고 안전하고 빠르게:
스토리지 클래스, 수명 주기, 버전 관리, 복제, 성능

Amazon S3 관련 문제는 접근 빈도, 복구 지연 시간, 최소 보관 기간, 가용 영역(AZ) 개수라는 4대 판단 축만 정확히 꿰뚫고 있으면 어떤 변형 문제도 손쉽게 풀어낼 수 있습니다. 이번 레슨에서는 8가지 S3 스토리지 클래스의 비용 구조를 분석하고, 수명 주기 규칙으로 비용을 자동 절감하는 원리, 그리고 버전 관리, 교차 리전 복제(CRR), Object Lock을 통해 데이터를 무결하게 보호하는 엔터프라이즈 설계 기법을 완벽히 정리합니다.

왜 S3 스토리지 클래스와 수명 주기부터 배워야 할까요?

시험 관점에서: SAA-C03 시험의 Task 4.1(비용 효율적인 스토리지 설계)과 Task 3.1(고성능 스토리지 설계)에서 가장 빈번하게 마주치는 유형이 바로 S3 스토리지 클래스 선택 문제입니다. 보기 4개가 모두 서로 다른 S3 클래스로만 주어지고 "비용이 가장 저렴하면서도 요구조건을 만족하는 구성은?"을 묻는 문제가 자주 출제됩니다. "언제든 다시 만들 수 있는 썸네일", "접근 패턴을 예측할 수 없는 파일", "규제상 7년간 루트 사용자도 삭제할 수 없는 감사 로그"와 같은 지문 속 결정적 단서를 읽어내는 눈을 길러야 합니다.[1]

실무 관점에서: 클라우드 환경에서 테라바이트(TB)에서 페타바이트(PB) 단위로 누적되는 비정형 데이터(로그 파일, 사용자 업로드 미디어, 백업 아카이브 등)는 아무 조치도 취하지 않으면 매달 막대한 보관 비용을 발생시킵니다. 적절한 S3 수명 주기 규칙(Lifecycle Rule) 하나만 정의해 두어도 오래된 데이터를 자동으로 저렴한 티어로 이동시켜 스토리지 비용의 70~90%를 절감할 수 있습니다. 또한 실수로 인한 객체 삭제나 랜섬웨어 공격으로부터 데이터를 복구하기 위해 버전 관리와 WORM(Write Once, Read Many) 스토리지 메커니즘을 올바르게 이해해야 합니다.

S3 스토리지 클래스 한눈에 비교하기

모든 S3 객체는 업로드 시 스토리지 클래스가 지정되며, 별도로 지정하지 않으면 기본값인 S3 Standard로 저장됩니다.[1]

아키텍처 설계 시 가장 먼저 기억해야 할 절대적인 사실은, 모든 S3 스토리지 클래스는 99.999999999%(일레븐 나인, 11 9s)의 동일한 데이터 내구성(Durability)을 제공한다는 점입니다.[1] 심지어 단일 가용 영역에만 저장되는 One Zone-IA조차 해당 AZ 내부에서는 동일한 11 9s 내구성을 갖도록 설계되었습니다. 따라서 "내구성 수치"를 근거로 클래스를 선택하는 것은 오답이며, 오직 접근 빈도, 복구 시간, 최소 보관 기간, AZ 개수라는 4대 기준으로 선택해야 합니다.

Intelligent-Tiering과 One Zone-IA의 핵심 메커니즘

  • Intelligent-Tiering의 자동 계층화 동작: 객체가 업로드되면 기본적으로 Frequent Access(자주 접근) 계층에 머뭅니다. 이후 30일 연속으로 접근이 없으면 Infrequent Access(드물게 접근) 계층으로, 90일 연속으로 접근이 없으면 Archive Instant Access 계층으로 자동 강등됩니다. 중요한 점은, 이후 언제라도 사용자가 해당 객체를 다시 읽으면 추가 검색 요금 없이 즉시 Frequent Access 계층으로 자동 승격된다는 것입니다. 따라서 관리자가 접근 패턴을 일일이 분석하거나 수명 주기 규칙을 변경할 필요가 없습니다.[1]
  • One Zone-IA의 올바른 정체성: AWS 공식 문서가 명시한 One Zone-IA의 권장 용도는 "AZ 장애로 유실되더라도 언제든 원본으로부터 다시 만들어낼 수 있는 데이터"(예: 이미지 썸네일, 트랜스코딩된 중간 비디오 파일) 또는 다른 리전의 데이터를 백업 복제해 둔 2차 사본입니다. 유실되면 안 되는 원본 데이터는 반드시 다중 AZ 기반의 Standard-IA에 저장해야 합니다.[1]

수명 주기(Lifecycle) 규칙: 자동 전환과 만료

S3 수명 주기 규칙(Lifecycle Rule)은 버킷 내부의 객체들을 대상으로 비용 절감과 데이터 정리를 완전 자동화합니다. 두 가지 핵심 동작이 있습니다.[4]

  1. 전환(Transition): 객체 생성 후 경과 일수(예: 30일 후, 90일 후)에 따라 더 저렴한 스토리지 클래스로 자동 이동시킵니다.
  2. 만료(Expiration): 객체가 지정된 기간에 도달하면 자동으로 삭제 처리합니다.

수명 주기 규칙은 새로 업로드되는 객체뿐만 아니라 이미 버킷에 존재하는 기존 객체들에도 소급 적용됩니다.[4]

수명 주기 설계 시 반드시 알아야 할 4가지 제약 조건

  • 일방통행 전환: Glacier Flexible Retrieval에서 Deep Archive로의 이동은 가능하지만, Deep Archive에서 수명 주기 규칙을 사용해 상위 클래스로 되돌아가는 것은 불가능합니다. 다시 상위 클래스로 옮기려면 객체를 수동 복원한 후 덮어쓰기 복사해야 합니다.[2]
  • 128KB 미만 소형 객체 제약: 기본적으로 128KB 미만의 작은 객체는 수명 주기 전환 대상에서 제외됩니다. 객체 전환 시 API 요청 요금이 부과되므로 소형 객체는 클래스를 낮춰 얻는 이익보다 전환 수수료가 더 클 수 있기 때문입니다.[2]
  • 최소 보관 기간 위반 수수료: Standard-IA(30일), Glacier(90일), Deep Archive(180일)에 저장된 객체를 최소 보관 기간이 지나기 전에 삭제하거나 다른 클래스로 전환하면, 남은 기간에 대한 보관 요금이 일할 계산되어 청구됩니다.[1]
  • 불완전한 멀티파트 업로드 자동 정리: 대용량 파일을 분할 업로드하다가 중단되면 조각(Parts)들이 버킷에 숨겨진 채 계속 보관 요금을 발생시킵니다. 수명 주기 규칙에서 AbortIncompleteMultipartUpload를 설정하여 7일 이상 중단된 멀티파트 조각을 자동 삭제하도록 구성해야 합니다.[14]

데이터 보호: 버전 관리, 복제, Object Lock

S3 버전 관리 (Versioning)

버킷의 버전 관리 상태는 비버전(기본) → 활성화(Enabled) → 일시 중지(Suspended) 3가지입니다. 한 번 활성화된 버킷은 절대 최초의 비버전 상태로 되돌릴 수 없으며, 오직 일시 중지만 가능합니다.[5]

  • 객체 삭제 메커니즘: 버전 관리가 켜진 버킷에서 버전 ID를 지정하지 않고 일반 삭제를 실행하면, 객체가 실제로 지워지는 것이 아니라 삭제 마커(Delete Marker)라는 특수 객체가 최신 버전으로 덮어씌워집니다. 이후 해당 객체를 조회하면 404 Not Found가 반환되지만, 콘솔에서 '버전 표시'를 켠 뒤 해당 삭제 마커를 삭제하면 이전 버전의 객체가 즉시 마술처럼 복원됩니다. 영구 삭제를 원할 때는 반드시 해당 버전의 고유 버전 ID를 지정해 삭제해야 합니다.
  • 비용 주의사항: 버전 관리가 켜지면 객체를 덮어쓸 때마다 파일 전체 크기만큼 새로운 버전이 누적 저장됩니다(차분 저장이 아님). 따라서 수명 주기 규칙에서 '이전 버전 만료(NoncurrentVersionExpiration)'를 설정해 두지 않으면 스토리지 비용이 급증할 수 있습니다.[5]
  • MFA Delete: 버전 영구 삭제나 버전 관리 상태 변경 시 물리적/가상 MFA 토큰 인증을 강제합니다. 오직 버킷을 소유한 루트(Root) 계정만 CLI/API를 통해 설정할 수 있습니다.[6]

복제를 성공적으로 구성하기 위한 4대 필수 요건은 다음과 같습니다.[8]

  1. 양쪽 버킷 버전 관리 필수: 원본 버킷과 대상 버킷 모두 버전 관리가 활성화되어 있어야 합니다.
  2. IAM 서비스 역할 권한: S3 서비스가 원본에서 객체를 읽고 대상에 쓸 수 있도록 권한을 위임해야 합니다.
  3. 교차 계정 복제 시 대상 버킷 정책: 원본과 대상 버킷의 AWS 계정이 다를 경우, 대상 계정의 버킷 정책(Bucket Policy)에서 원본 계정의 IAM 역할에게 복제 쓰기 권한을 명시적으로 허용해야 합니다. (대상 버킷은 요청자 지불(Requester Pays)일 수 없음)
  4. 기존 객체 복제는 S3 Batch Replication 사용: 일반 복제 규칙은 설정 시점 이후에 새로 생성되는 신규 객체만 복제합니다. 버킷에 이미 있던 기존 객체들을 복제하려면 S3 Batch Replication(배치 복제) 작업을 실행해야 합니다.[7]
  5. 예측 가능한 복제 시간 (S3 RTC): 금융권 등에서 규제 준수를 위해 객체의 99.99%를 15분 이내에 복제하도록 법적 SLA를 보장하는 옵션입니다.[7]

S3 Object Lock (WORM 스토리지)

S3 Object Lock은 한 번 기록된 데이터를 일정 기간 또는 영구적으로 변경/삭제할 수 없도록 강제하는 WORM(Write Once, Read Many) 스토리지 기능입니다. 반드시 버전 관리가 켜진 버킷에서만 작동합니다.[10]

객체 공유와 성능 최적화 패턴

  • 미리 서명된 URL (Presigned URL): AWS IAM 자격 증명이 없는 외부 사용자나 클라이언트에게 특정 객체를 다운로드하거나 업로드할 수 있는 임시 기한부 URL을 발급합니다. 버킷 정책을 퍼블릭으로 열지 않고도 안전하게 파일을 공유할 수 있습니다. IAM 사용자 자격 증명으로 생성 시 최대 7일간 유효합니다.[11]
  • 요청자 지불 (Requester Pays): 객체 다운로드 시 발생하는 데이터 전송 비용과 API 요청 비용을 다운로드하는 요청자(Requester)가 부담하도록 합니다. 버킷 소유자는 오직 순수 저장 용량 비용만 부담합니다. 대규모 오픈소스 데이터셋이나 공공 연구 데이터를 배포할 때 유용합니다.[12]
  • 접두사(Prefix) 기반 성능 확장: S3는 버킷 전체가 아니라 접두사(Prefix, 폴더 경로)당 초당 최소 3,500회의 PUT/POST/DELETE 및 5,500회의 GET/HEAD 요청을 처리합니다. 버킷 내부 접두사 수에는 제한이 없으므로, 서로 다른 10개의 접두사로 요청을 고르게 분산하면 초당 55,000건의 읽기 요청을 손쉽게 병렬 처리할 수 있습니다.[13]
  • 멀티파트 업로드 (Multipart Upload): 100MB 이상의 대용량 파일에 권장되며 5GB 초과 파일에는 필수입니다. 파일을 여러 조각(Part)으로 나누어 병렬로 업로드하므로 전송 속도가 극대화되며, 네트워크 오류 발생 시 실패한 조각만 재전송하면 되므로 안정성이 뛰어납니다.[14]
  • S3 Transfer Acceleration: 전 세계에 분산된 CloudFront 엣지 로케이션을 경유하여 AWS 백본 전용망을 타고 S3 버킷으로 빠르게 업로드합니다. "전 세계 지사에서 미국 리전 버킷으로 기가바이트 단위 영상 업로드 시 속도 개선" 요구의 대표적인 정답입니다.[15]

시험에 자주 나오는 핵심 패턴

  • "데이터의 접근 패턴을 미리 알 수 없거나 불규칙하게 변함" → S3 Intelligent-Tiering (검색 요금 없음, 자동 이동).
  • "유실되어도 언제든 다시 생성할 수 있는 데이터, 드물게 접근, 최저 비용" → S3 One Zone-IA (단일 AZ 저장).
  • "드물게 열어보지만 필요 시 밀리초(즉시)로 열람해야 함" → S3 Standard-IA (월 1회) 또는 S3 Glacier Instant Retrieval (분기 1회).
  • "연 1회 미만 접근, 12~48시간 복원 지연 허용, 가장 저렴한 비용" → S3 Glacier Deep Archive.
  • "아카이브 데이터를 긴급히 몇 분(1~5분) 이내에 복원해야 함" → S3 Glacier Flexible Retrieval의 신속(Expedited) 복원 (Deep Archive는 신속 복원 불가!).
  • "실수로 인한 객체 삭제 및 덮어쓰기 방지" → S3 버전 관리 (Versioning) (+ 최고 권한 관리는 MFA Delete).
  • "최고 관리자나 루트 사용자조차도 지정된 기간 동안 백업을 삭제할 수 없음" → S3 Object Lock (규정 준수 모드, Compliance Mode).
  • "다른 리전에 복제본 생성, 15분 이내 복제 SLA 보장" → S3 Cross-Region Replication (CRR) + Replication Time Control (RTC).
  • "버킷 정책 변경 없이 외부 사용자에게 일시적 다운로드/업로드 허용" → 미리 서명된 URL (Presigned URL).
  • "전 세계 사용자가 대용량 파일을 중앙 S3 버킷으로 업로드할 때 네트워크 지연 단축" → S3 Transfer Acceleration + 멀티파트 업로드.

실전 연습: 직접 풀어보세요

배운 핵심 원리를 토대로 시나리오 문제를 분석해 보세요. 막히면 4대 판단 축(접근 빈도, 복구 시간, 최소 보관 기간, AZ 개수)으로 보기를 하나씩 소거해 보세요.

Q1. 사용자가 업로드하는 사진을 저장하는 모바일 앱이 있습니다. 어떤 사진은 업로드 직후 수개월 동안 매일 수천 번씩 조회되지만, 어떤 사진은 업로드된 후 한 번도 열람되지 않습니다. 사진별 접근 패턴을 미리 예측할 수 없으며, 운영팀이 수동으로 수명 주기 규칙을 관리할 여력도 없습니다. 가장 비용 효율적인 S3 스토리지 클래스는 무엇입니까?

"접근 패턴을 예측할 수 없거나 자주 변함 + 관리 부담 없음"이라는 조건은 S3 Intelligent-Tiering의 교과서적인 정의입니다. 객체별 접근 여부를 모니터링하여 30일, 90일 동안 접근이 없으면 자동으로 저렴한 티어로 내리고, 다시 접근이 발생하면 검색 요금 없이 즉시 핫 티어로 복귀시켜 줍니다. One Zone-IA는 자주 접근되는 사진에서 데이터 검색 요금이 눈덩이처럼 불어나며, Express One Zone은 고성능 AI용이라 비용 최적화와 거리가 멉니다. Glacier Deep Archive는 복원에 수 시간이 걸리므로 매일 사진을 보여주어야 하는 서비스에 적합하지 않습니다.

Q2. 미디어 회사에서 원본 고해상도 이미지로부터 생성한 웹용 썸네일 이미지들을 저장하려 합니다. 원본이 안전하게 보관되어 있어 썸네일은 유실되더라도 언제든 스크립트로 다시 생성할 수 있습니다. 썸네일은 대략 한 달에 한 번 정도 드물게 조회되며, 사용자가 요청할 때는 밀리초 단위로 즉시 표시되어야 합니다. 가장 저렴한 스토리지 클래스는 무엇입니까?

"유실 시 언제든 다시 생성 가능(Reproducible) + 드문 접근 + 밀리초 즉시 응답"을 만족하는 가장 경제적인 클래스는 S3 One Zone-IA입니다. 단일 가용 영역에만 저장하므로 Standard-IA보다 저장 비용이 20% 더 저렴합니다. 만약 해당 AZ에 재해가 발생해 썸네일이 유실되더라도 원본에서 다시 만들어내면 되므로 비즈니스 영향이 없습니다. Glacier Deep Archive는 복원에 수 시간이 소요되므로 밀리초 즉각 응답 요구를 충족하지 못합니다.

Q3. 금융 규정에 따라 모든 고객 거래 내역 감사 보고서를 10년간 의무 보존해야 합니다. 감사 요청은 1년에 한 번 있을까 말까 할 정도로 매우 드물며, 규제 기관에 제출할 때 요청 접수 후 48시간 이내에만 데이터를 준비해 제공하면 됩니다. 전체 보관 비용을 절대적으로 최소화하기 위한 가장 적합한 아키텍처는 무엇입니까?

연 1회 미만의 극히 드문 접근, 48시간의 넉넉한 복구 허용 시간, 그리고 "비용의 절대적 최소화"가 주어졌을 때는 S3 Glacier Deep Archive가 독보적인 정답입니다. Deep Archive의 대량(Bulk) 복원은 48시간 이내에 가장 저렴한 비용으로 데이터를 인출합니다. Glacier Instant Retrieval이나 Standard-IA는 밀리초 즉각 조회가 가능한 대신 보관 요금이 Deep Archive보다 훨씬 비쌉니다. Flexible Retrieval의 신속 복원은 1~5분 이내 긴급 복구용으로 비용이 과다하게 발생합니다.

Q4. 증권 거래 규제 기관이 증권 거래 감사 로그를 7년 동안 어떤 사용자도, 심지어 AWS 계정의 최고 권한을 가진 루트(Root) 사용자조차도 임의로 삭제하거나 덮어쓸 수 없도록 완벽히 보존하라고 명령했습니다. 어떤 S3 데이터 보호 기능을 구성해야 합니까?

"루트 사용자를 포함해 그 누구도 삭제 불가"는 S3 Object Lock의 규정 준수 모드(Compliance Mode)의 고유한 특성입니다. 규정 준수 모드가 걸린 객체는 보존 기간 동안 AWS 루트 계정도, AWS 고객지원팀도 삭제할 수 없습니다. 거버넌스 모드는 특정 권한(s3:BypassGovernanceRetention)을 가진 관리자가 우회 삭제할 수 있어 최고 권한 탈취를 막지 못합니다. MFA Delete는 삭제를 엄격하게 통제할 뿐 루트 사용자가 MFA 코드를 입력하면 삭제가 가능하며, 버킷 정책 역시 관리자가 수정할 수 있습니다.

Q5. 미국 버지니아 리전(us-east-1)의 S3 버킷에 저장되는 모든 신규 객체를 유럽 아일랜드 리전(eu-west-1)의 버킷으로 자동 복제(CRR)하려 합니다. 이 구성을 완성하기 위해 반드시 갖추어야 할 필수 요구조건 2가지를 고르세요.

정답은 두 번째(양쪽 버킷 버전 관리 활성화)와 네 번째(IAM 복제 역할 부여)입니다.
S3 복제(CRR/SRR)의 절대적인 기술적 전제조건은 ① 원본과 대상 버킷 모두에 버전 관리가 켜져 있어야 한다는 점과, ② S3 서비스가 고객을 대신해 객체를 복제할 수 있는 IAM 역할(Service Role)이 연결되어 있어야 한다는 점입니다.
(Transfer Acceleration은 클라이언트 파일 업로드 고속화 기능이라 복제와 무관하며, 교차 계정 복제 시 대상 버킷은 요청자 지불 버킷일 수 없습니다.)

Q6. 계정 A의 S3 버킷에서 계정 B의 S3 버킷으로 교차 계정 복제(CRR)를 구성했습니다. 계정 A의 IAM 복제 역할과 양쪽 버킷의 버전 관리는 완벽하게 설정되었으나, 실제로 객체를 올려도 계정 B의 버킷으로 복제되지 않고 권한 오류가 발생합니다. 무엇이 누락되었을 가능성이 가장 높습니까?

레슨 0002에서 배운 교차 계정 권한의 교집합 원칙이 그대로 적용됩니다. 서로 다른 AWS 계정 간에 리소스 접근이 일어나려면, 요청 주체 측의 자격 증명 기반 정책(계정 A의 복제 IAM 역할)뿐만 아니라 리소스 소유자 측의 리소스 기반 정책(계정 B의 대상 버킷 정책)에서도 해당 역할을 향한 명시적 Allow가 반드시 존재해야 합니다. 대상 버킷 정책에서 쓰기 권한을 열어주지 않으면 계정 A의 역할은 객체를 대상 버킷에 복제해 넣을 수 없습니다.

Q7. 전 세계 20여 개국에 분산된 지사 사무소에서 매일 수 기가바이트(GB) 크기의 고해상도 그래픽 데이터 파일을 미국 버지니아 리전의 중앙 S3 버킷으로 업로드하고 있습니다. 특히 아시아 및 오세아니아 지사에서 업로드 속도가 극도로 느리고 네트워크 순단으로 인한 재시도 실패가 빈번합니다. 애플리케이션 코드를 크게 수정하지 않고 이 문제를 해결할 가장 효과적인 아키텍처는 무엇입니까?

원거리 글로벌 클라이언트가 중앙의 단일 S3 버킷으로 대용량 파일을 고속 업로드할 때의 최적 조합은 S3 Transfer Acceleration + 멀티파트 업로드입니다. Transfer Acceleration은 전 세계 CloudFront 엣지 로케이션을 통해 트래픽을 접수한 뒤 AWS의 고속 글로벌 사설 백본망을 타고 버킷으로 전달하므로 인터넷 구간 병목을 획기적으로 줄여줍니다. 또한 멀티파트 업로드는 대용량 파일을 여러 조각으로 나누어 병렬 전송하므로 실패 시 끊긴 조각만 재전송하여 전송 안정성을 극대화합니다.

Q8. 회사가 외부 회계 감사 법인의 감사관에게 비공개(Private) S3 버킷에 보관된 재무제표 엑셀 파일 하나를 24시간 동안만 다운로드할 수 있도록 임시 접근 권한을 주고자 합니다. 외부 감사인은 AWS 계정이 없으며, 회사는 버킷 전체의 프라이빗 정책을 일체 변경하고 싶지 않습니다. 가장 안전하고 적절한 조치는 무엇입니까?

AWS 자격 증명이 없는 외부 사용자에게 프라이빗 객체에 대한 안전한 기한부 임시 접근 권한을 부여하는 가장 표준적인 방법은 미리 서명된 URL(Presigned URL)을 생성해 공유하는 것입니다. 버킷 정책이나 ACL을 퍼블릭으로 개방할 필요가 전혀 없으며, 지정한 유효 기간(24시간)이 지나면 URL이 자동으로 무효화되므로 보안상 가장 완벽합니다. IAM 사용자 장기 키 발급은 보안상 위험하며, Requester Pays는 인증되지 않은 익명 사용자의 접근을 지원하지 못합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 다음 3가지 핵심 질문에 대한 답을 머릿속에서 인출하여 직접 적어보세요.
(1) S3 스토리지 클래스 8가지를 '최소 보관 기간'과 '저장 가용 영역(AZ) 수'를 기준으로 분류해 보세요.
(2) Glacier Flexible Retrieval과 Glacier Deep Archive의 복원 옵션별 소요 시간의 결정적 차이는 무엇인가요?
(3) 교차 리전 복제(CRR)를 성공적으로 구성하기 위해 반드시 필요한 전제조건 2가지와, 교차 계정일 때 추가로 필요한 것은 무엇인가요?

(1) 최소 보관 기간 및 저장 AZ 수 기준 분류:
- 최소 보관 기간 없음: S3 Standard, S3 Intelligent-Tiering, S3 Express One Zone.
- 30일: S3 Standard-IA, S3 One Zone-IA.
- 90일: S3 Glacier Instant Retrieval, S3 Glacier Flexible Retrieval.
- 180일: S3 Glacier Deep Archive.
- 단일 AZ(1개): S3 One Zone-IA, S3 Express One Zone. (그 외 모든 클래스는 3개 이상의 다중 AZ에 분산 저장)

(2) Glacier Flexible vs Deep Archive 복원 시간 차이:
- Flexible Retrieval: 신속(Expedited, 1~5분), 표준(Standard, 3~5시간), 대량(Bulk, 5~12시간).
- Deep Archive: 신속(Expedited) 티어 지원 불가!, 표준(Standard, 12시간 이내), 대량(Bulk, 48시간 이내).
※ "몇 분 안에 복구" 요구가 있다면 Deep Archive는 절대 선택할 수 없습니다.

(3) 교차 리전 복제(CRR) 필수 요건:
① 원본 및 대상 버킷 모두 버전 관리(Versioning) 활성화 필수.
② S3 서비스에 복제 권한을 위임하는 IAM 서비스 역할 구성.
③ 교차 계정 복제 시: 대상 계정의 버킷 정책(Bucket Policy)에서 원본 복제 역할에 쓰기 권한을 반드시 명시적 허용.
(+ 기존에 이미 있던 객체들은 S3 Batch Replication으로 별도 복제 실행)
