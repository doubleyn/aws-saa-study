수명 주기: 자동으로 내려보내고 지우기

수명 주기 규칙의 동작은 두 가지입니다. 전환(Transition)은 더 싼 클래스로 옮기고, 만료(Expiration)는 삭제합니다. 규칙은 새 객체뿐 아니라 기존 객체에도 적용됩니다.[4] 전환은 아래로만 흐르는 "폭포(waterfall)" 모델입니다.

  • Glacier Flexible Retrieval → Deep Archive만 가능, Deep Archive에서는 수명 주기로 어디로도 못 갑니다. 다른 클래스로 바꾸려면 복원한 뒤 복사해 덮어써야 합니다.[2]
  • 128KB 미만 객체는 기본적으로 전환되지 않습니다. 객체마다 전환 요청 요금이 붙어 작은 객체는 손해일 수 있기 때문입니다. 필요하면 객체 크기 필터로 바꿉니다.[2]
  • 최소 보관 기간 전에 옮기거나 지우면 남은 기간 요금을 냅니다. 예: IA 클래스에서 30일 전에 삭제하면 30일치가 청구됩니다.[1]
  • 멀티파트 업로드가 중단되면 조각이 계속 과금되므로 AbortIncompleteMultipartUpload 수명 주기 동작으로 정리하라고 AWS가 권장합니다.[14]

참고: AWS 스토리지 선택 가이드(2026-10 갱신)는 S3가 Standard-IA·One Zone-IA로의 전환에 더 이상 30일 최소 기간을 적용하지 않는다고 밝힙니다.[16] 문제 은행이 예전 기준으로 쓰였을 수 있으니, 보기에 "30일 후 IA로 전환"이 나와도 그 자체를 오답 근거로 삼지는 마세요.

데이터 보호: 버전 관리, 복제, Object Lock

버전 관리

버킷 상태는 비버전(기본) · 활성화 · 일시 중지 세 가지이며, 한 번 활성화하면 비버전으로 되돌릴 수 없고 일시 중지만 가능합니다. 버전 ID 없이 삭제하면 객체가 지워지는 대신 삭제 마커가 현재 버전이 되므로, 이전 버전을 되살릴 수 있습니다. 버전마다 전체 객체로 과금됩니다(차분이 아님).[5] 버전 관리 버킷에 만료 규칙을 쓸 때는 이전(noncurrent) 버전 만료 규칙도 함께 넣어야 예전처럼 영구 삭제됩니다.[5]

MFA Delete는 버전 영구 삭제와 버전 관리 상태 변경에 MFA 코드를 요구합니다. 버킷 소유자(루트 계정)만 켤 수 있고, 콘솔이 아니라 CLI/API로 설정합니다.[6]

공유와 비용 분담

  • 미리 서명된 URL(presigned URL): 버킷 정책을 바꾸지 않고 객체에 기한부 다운로드·업로드 권한을 줍니다. URL은 만든 주체의 권한으로 동작하고, IAM 사용자 자격 증명(SigV4)으로 만들면 최대 7일, 임시 자격 증명으로 만들면 그 자격 증명이 끝날 때 함께 만료됩니다.[11]
  • Requester Pays: 요청과 다운로드 비용을 요청자가 내고, 저장 비용은 항상 버킷 소유자가 냅니다. 익명 접근은 허용되지 않으며 요청자는 x-amz-request-payer 헤더로 비용 부담에 동의해야 합니다. 대용량 공개 데이터셋 공유에 씁니다.[12]

성능

  • 접두사(prefix)당 초당 최소 3,500 PUT/COPY/POST/DELETE, 5,500 GET/HEAD를 처리하며 버킷의 접두사 수에는 제한이 없습니다. 접두사를 10개로 나눠 병렬로 읽으면 읽기를 초당 55,000까지 늘릴 수 있습니다. 확장 중에는 503(Slow Down)이 잠시 보일 수 있습니다.[13]
  • 멀티파트 업로드: 100MB 이상 객체에 권장. 조각을 병렬 업로드해 처리량을 높이고, 실패한 조각만 재전송하면 됩니다.[14]
  • Transfer Acceleration: CloudFront 엣지 로케이션을 거쳐 최적화된 경로로 S3에 들어갑니다. "전 세계 고객이 중앙 버킷 하나로 업로드", "대륙 간 GB~TB 정기 전송"이 신호입니다. 버킷 이름에 마침표(.)가 없어야 하고 bucket.s3-accelerate.amazonaws.com 엔드포인트를 쓰며, 추가 요금이 있을 수 있습니다.[15]

시험 단골: 키워드 → 답

접근 패턴을 모름 / 예측 불가 → Intelligent-Tiering · 다시 만들 수 있음 + 드물게 접근 → One Zone-IA · 드물지만 밀리초로 즉시 → Glacier Instant Retrieval(분기 1회) 또는 Standard-IA(월 1회) · 연 1회 미만 + 12~48시간 허용 + 최저가 → Glacier Deep Archive · 몇 분 안에 아카이브 복원 → Glacier Flexible Retrieval의 Expedited.

실수로 삭제·덮어쓰기 방지 → 버전 관리(+MFA Delete) · 루트도 못 지우게 → Object Lock 규정 준수 모드 · 다른 리전에 사본, 15분 SLA → CRR + RTC · 기존 객체까지 복제 → Batch Replication · 외부인에게 임시 접근 → 미리 서명된 URL · 원거리 대용량 업로드 느림 → Transfer Acceleration + 멀티파트.

연습

기억으로 푸세요. 막히면 위의 네 축(접근 빈도, 복구 시간, 최소 보관 기간, AZ 개수)으로 보기를 하나씩 지워 보세요.

Q1. 사용자 업로드 사진을 저장합니다. 어떤 사진은 몇 달간 매일 조회되고, 어떤 사진은 업로드 후 거의 안 열립니다. 접근 패턴을 미리 알 수 없고, 운영팀이 규칙을 관리할 여력도 없습니다. 가장 비용 효율적인 클래스는?

"패턴을 모름 + 관리 부담 없이"는 Intelligent-Tiering의 정의입니다. 객체 단위로 접근이 없으면 30일, 90일 기준으로 자동으로 내려가고 검색 요금이 없습니다. One Zone-IA는 자주 읽히는 사진에서 GB당 검색 요금이 쌓이고 AZ 하나에만 저장됩니다. Express One Zone은 지연에 민감한 워크로드용 고성능 클래스라 비용 최적화 답이 아니고, Deep Archive는 복원에 몇 시간이 걸려 매일 조회되는 사진을 보여 줄 수 없습니다.

Q2. 원본 이미지로부터 언제든 다시 만들 수 있는 썸네일을 보관합니다. 한 달에 한 번 정도 읽히며, 읽을 때는 밀리초로 응답해야 합니다. 가장 저렴한 클래스는?

"재생성 가능"은 One Zone-IA의 신호입니다. AZ 하나에만 저장해 Standard-IA보다 싸고, AZ를 잃어도 다시 만들면 됩니다. Standard-IA도 조건은 맞지만 더 비쌉니다. Deep Archive는 복원에 시간이 걸려 밀리초 요구를 만족하지 못합니다.

Q3. 규정상 금융 기록을 10년 보관해야 합니다. 감사 때 1년에 한 번도 안 열 수도 있고, 요청이 오면 48시간 안에만 제출하면 됩니다. 가장 비용 효율적인 방법은?

연 1회 미만 접근, 48시간 허용이면 Deep Archive(Bulk 48시간 이내, Standard 12시간 이내)가 가장 쌉니다. Flexible Retrieval의 Expedited는 몇 분이 필요할 때 쓰는 비싼 옵션이라 이 요구에는 과합니다. Instant Retrieval은 밀리초 접근 비용을 낼 이유가 없습니다.

Q4. 규제 기관이 거래 기록을 7년간 어떤 사용자도, 루트 사용자조차 삭제하거나 덮어쓰지 못하게 하라고 요구합니다. 무엇을 써야 합니까?

"루트 포함 누구도"는 규정 준수 모드입니다. 거버넌스 모드는 s3:BypassGovernanceRetention 권한이 있으면 풀립니다. MFA Delete는 삭제를 어렵게 할 뿐 루트 소유자는 MFA로 삭제할 수 있고, 버킷 정책은 정책을 수정할 권한이 있는 사람이 바꿀 수 있습니다.

Q5. us-east-1 버킷의 새 객체를 eu-west-1 버킷으로 자동 복제(CRR)하려 합니다. 반드시 필요한 것은? (두 개를 고르세요)

복제의 필수 조건은 양쪽 버전 관리와 S3에 복제 권한을 주는 것입니다. Transfer Acceleration은 클라이언트 업로드 가속 기능이라 복제와 관계없고, 교차 계정 복제에서는 대상 버킷이 오히려 Requester Pays일 수 없습니다.

Q6. (0002 복습) 계정 A의 버킷에서 계정 B의 버킷으로 복제를 설정했는데 복제가 실패합니다. 계정 A 쪽 복제 역할과 버전 관리는 정상입니다. 무엇이 빠졌을 가능성이 가장 큽니까?

교차 계정은 양쪽이 모두 허용해야 한다는 0002의 규칙 그대로입니다. 원본 쪽 역할(자격 증명 기반 정책)만으로는 부족하고, 대상 버킷 소유자가 버킷 정책으로 원본 소유자에게 복제를 허용해야 합니다. 나머지 보기는 복제의 필수 조건이 아닙니다.

Q7. 전 세계 지사에서 수 GB짜리 영상 파일을 버지니아 리전의 버킷 하나로 업로드하는데, 아시아 지사의 업로드가 느리고 자주 실패합니다. 코드 변경을 최소화하면서 개선하는 방법은?

원거리 클라이언트 → 중앙 버킷 업로드는 Transfer Acceleration(엣지 경유), 큰 파일의 재시도 문제는 멀티파트 업로드(실패한 조각만 재전송)가 답입니다. SRR은 같은 리전 안 복제라 업로드 경로를 바꾸지 못하고, Express One Zone은 단일 AZ 저지연 클래스이지 대륙 간 전송 문제를 풀지 않습니다.

Q8. 외부 감사인에게 비공개 버킷의 보고서 파일 하나를 24시간 동안만 내려받게 하려 합니다. 감사인은 AWS 계정이 없고, 버킷 정책은 바꾸고 싶지 않습니다.

미리 서명된 URL은 버킷 정책을 고치지 않고 기한부 접근을 줍니다. "*"는 익명 전체 공개라 위험하고, IAM 사용자 발급은 장기 자격 증명을 외부에 주는 것이며, Requester Pays는 익명·비인증 접근을 오히려 막습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) 8개 클래스를 "최소 보관 기간"과 "AZ 개수"로 분류해 보세요. (2) Glacier Flexible Retrieval과 Deep Archive의 복원 옵션별 시간은? (3) 복제를 설정하기 위한 필수 조건 두 가지와, 교차 계정일 때 하나 더 필요한 것은?

(1) 최소 보관 없음: Standard, Intelligent-Tiering, Express One Zone. 30일: Standard-IA, One Zone-IA. 90일: Glacier Instant, Glacier Flexible. 180일: Deep Archive. AZ 1개: One Zone-IA, Express One Zone. 나머지는 3개 이상.

(2) Flexible: Expedited 1–5분, Standard 3–5시간, Bulk 5–12시간. Deep Archive: Expedited 없음, Standard 12시간 이내, Bulk 48시간 이내.

(3) 원본·대상 버킷 모두 버전 관리, S3에 복제 권한(IAM 역할). 교차 계정이면 대상 버킷 정책이 원본 소유자에게 복제를 허용. 기존 객체는 Batch Replication.
