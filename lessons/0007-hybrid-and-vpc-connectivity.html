왜 이것인가

시험에서: "VPC A–B, A–C가 피어링되어 있는데 B에서 C로 안 된다"는 피어링의 비전이성(non-transitive) 문제로, 거의 매번 형태를 바꿔 나옵니다.
실무에서: 계정과 VPC가 늘어나면 피어링 그물이 관리 불가능해지는 순간이 옵니다. 그때 Transit Gateway로 넘어가는 판단을 할 수 있어야 합니다.

VPC 피어링

VPC 피어링은 두 VPC를 사설 IPv4·IPv6 주소로 라우팅하는 연결입니다. 내 VPC끼리, 다른 계정의 VPC와, 다른 리전의 VPC와도 맺을 수 있습니다. 게이트웨이나 VPN이 아니라 기존 VPC 인프라를 쓰므로 단일 장애 지점이나 대역폭 병목이 없습니다.[1] 연결 생성은 무료이고, 같은 AZ 안의 전송은 무료, AZ나 리전을 넘는 전송에는 요금이 붙습니다.[1]

제약이 시험의 핵심입니다.[2]

  • CIDR이 겹치면 맺을 수 없습니다. CIDR 블록이 여러 개라면 하나라도 겹치면 불가합니다.
  • 전이 피어링은 지원하지 않습니다. A–B, A–C가 피어링되어 있어도 B에서 A를 거쳐 C로 갈 수 없습니다. B–C 피어링을 따로 만들어야 합니다.
  • 엣지 투 엣지 라우팅도 안 됩니다. B는 A의 IGW, NAT 장치, VPN, Direct Connect, S3 게이트웨이 엔드포인트를 빌려 쓸 수 없습니다.
  • 양쪽 VPC 소유자가 각자 라우팅 테이블에 상대 CIDR로 가는 라우트를 직접 추가해야 합니다. 같은 리전이면 상대 VPC의 보안 그룹을 규칙에서 참조할 수 있습니다.

Transit Gateway

AWS Transit Gateway는 VPC와 온프레미스 네트워크를 서로 잇는 네트워크 전송 허브입니다. VPC, VPN 연결, Direct Connect 게이트웨이, 다른 Transit Gateway와의 피어링(리전 간 포함) 등을 연결(attachment)로 붙이고, Transit Gateway 라우팅 테이블이 연결 사이의 다음 홉을 정합니다.[3] 요금은 연결당 시간 요금과 처리한 트래픽 양입니다.[3] AWS 문서는 피어링의 제약에 부딪힐 때 Transit Gateway 연결을 대안으로 제시합니다.[2]

온프레미스와 잇기: Site-to-Site VPN

AWS Site-to-Site VPN은 온프레미스 네트워크와 VPC 사이의 IPsec VPN 연결입니다.[4] 인터넷 위에 만들어집니다.[5]

  • AWS 쪽 끝은 가상 프라이빗 게이트웨이(VGW)(VPC 하나에 연결) 또는 Transit Gateway. 내 쪽은 고객 게이트웨이 장치(물리 장비 또는 소프트웨어)이고, AWS에는 그 정보를 담은 고객 게이트웨이 리소스를 만듭니다.[4]
  • VPN 연결 하나에는 터널이 2개 있어 동시에 써서 고가용성을 얻습니다. 표준 터널은 터널당 최대 1.25 Gbps이고, Transit Gateway·Cloud WAN에 붙인 연결은 최대 5 Gbps의 대역폭 큰 터널을 쓸 수 있습니다.[4]
  • 요금은 VPN 연결이 프로비저닝된 시간과 데이터 전송입니다.[4]

온프레미스와 잇기: Direct Connect

AWS Direct Connect(DX)는 내 네트워크를 Direct Connect 로케이션에 표준 이더넷 광케이블로 연결해, 인터넷 서비스 공급자를 거치지 않고 AWS에 닿게 합니다.[6] 인터넷 기반 연결보다 네트워크 비용을 줄이고 대역폭을 늘리며 더 일관된 네트워크 경험을 줍니다.[7]

  • 전용 연결(dedicated): 1·10·100 Gbps 포트. 호스팅 연결(hosted): DX 파트너가 프로비저닝해 공유, 50 Mbps~10 Gbps. 데이터 센터까지의 회선은 파트너와 함께 구성해야 할 수 있습니다.[7]
  • 가상 인터페이스(VIF): 프라이빗 VIF는 VPC에 사설 IP로, 퍼블릭 VIF는 S3 같은 AWS 퍼블릭 서비스에, 전송 VIF는 Direct Connect 게이트웨이에 연결된 Transit Gateway에 접근합니다.[6]
  • Direct Connect 게이트웨이는 전역 리소스로, VIF 하나로 여러 리전·계정의 VPC나 Transit Gateway에 연결하게 해 줍니다.[7]
  • 고가용성을 위해서는 DX 연결을 추가로, 가능하면 서로 다른 DX 로케이션에 두라고 권합니다.[7] 비용을 아끼려면 백업 IPsec VPN을 둘 수도 있습니다. DX와 VPN을 같은 VPC에 함께 쓰는 것은 장애 조치용으로만 되며, DX 경로가 있으면 항상 DX가 우선합니다.[8]

DX는 기본적으로 암호화되지 않는다

Direct Connect는 전송 중 트래픽을 기본적으로 암호화하지 않습니다.[9] 선택지는 두 가지입니다.

  • DX 위의 VPN: 퍼블릭 VIF로 AWS VPN 엔드포인트에 닿은 뒤 IPsec 연결을 만듭니다. IPsec의 종단 간 보안과 DX의 낮은 지연·높은 대역폭을 함께 얻어, 인터넷 VPN보다 일관된 경험을 줍니다.[10]
  • MACsec: 10·100 Gbps 전용 연결에서 쓸 수 있는 링크 계층 암호화. 1 Gbps 이하라면 VPN 터널을 얹는 방식을 씁니다.[7]

"A–B, A–C 피어링인데 B↔C 불가" → 전이 피어링 미지원. B–C 피어링 추가 또는 Transit Gateway.

"여러 리전 VPC를 DX 하나로" → Direct Connect 게이트웨이.

연습

Q1. VPC A는 VPC B, VPC C와 각각 피어링되어 있고, 모든 라우트와 보안 그룹이 올바르게 설정되어 있습니다. VPC B의 인스턴스가 VPC C의 인스턴스와 통신하려 합니다.

피어링은 전이 관계를 지원하지 않습니다. B와 C가 통신하려면 B–C 피어링을 따로 만들어야 합니다.[2] 한 VPC가 여러 피어링을 가질 수는 있으므로 마지막 보기는 틀렸습니다. 계정이 같든 다르든 규칙은 같습니다.

Q2. (시험형) 회사가 여러 계정에 걸쳐 VPC 40개를 운영하며, 모든 VPC가 서로 통신하고 온프레미스 데이터 센터와도 연결되어야 합니다. 운영 부담이 가장 적은 설계는?

Transit Gateway는 VPC와 온프레미스를 잇는 허브이며 라우팅 테이블로 연결 사이를 중계합니다.[3] 40개 전체 피어링은 780개 연결이 필요하고, 중계 VPC 방식은 전이 피어링 금지와 엣지 투 엣지 금지 때문에 동작하지 않습니다.[2]

Q3. (시험형) 회사가 1 Gbps Direct Connect 전용 연결로 AWS와 통신합니다. 규정상 온프레미스와 AWS 사이의 모든 트래픽은 전송 중 암호화되어야 하고, DX의 일관된 성능도 유지해야 합니다. 무엇을 해야 하는가?

DX는 기본적으로 암호화하지 않습니다.[9] MACsec은 10·100 Gbps 전용 연결용이고, 1 Gbps 이하는 VPN 터널을 얹는 방식입니다.[7] 인터넷 VPN으로만 바꾸면 암호화는 되지만 일관된 성능 요구를 버립니다.

Q4. (시험형) 지사 하나가 VPC의 내부 애플리케이션에 접근해야 합니다. 트래픽은 적고, 연결은 암호화되어야 하며, 가능한 한 빨리 저렴하게 구축하려 합니다. 지사에는 IPsec을 지원하는 라우터가 있습니다.

Site-to-Site VPN은 인터넷 위의 IPsec 연결이라 기존 장비로 바로 만들 수 있고 암호화가 기본입니다.[4] DX는 로케이션 교차 연결과 회선 작업이 필요하고 기본 암호화도 없습니다. 피어링은 VPC끼리만 맺습니다. 내부 앱을 인터넷에 공개하는 것은 요구 사항에 어긋납니다.

Q5. (시험형) 회사의 주 연결은 Direct Connect 하나입니다. DX 장애 시에도 연결이 끊기지 않게 하되, 비용은 최소화하려 합니다. 가장 적절한 것은?

DX와 VPN은 같은 VPC에 장애 조치용으로 함께 쓸 수 있고, DX가 살아 있으면 DX가 항상 우선합니다.[8] 두 번째 DX가 복원력은 더 높지만(가능하면 다른 로케이션) 비용이 큽니다.[7] 속도를 올려도 회선이 끊기면 소용없습니다.

Q6. VPC 피어링에 대한 설명으로 옳은 것을 두 개 고르세요.

피어링은 계정·리전을 넘어 맺을 수 있고, CIDR이 겹치면 불가합니다.[1][2] 상대의 IGW는 엣지 투 엣지 라우팅 금지로 쓸 수 없고, 라우트는 양쪽 소유자가 직접 추가해야 합니다.

Q7. (0006 복습) VPC A에는 S3 게이트웨이 엔드포인트가 있고, VPC B는 A와 피어링되어 있습니다. VPC B의 프라이빗 서브넷 인스턴스가 NAT 없이 같은 리전의 S3에 접근해야 합니다. 비용이 가장 적은 방법은?

피어링 상대의 게이트웨이 엔드포인트는 엣지 투 엣지 라우팅 금지 때문에 쓸 수 없습니다.[2] 게이트웨이 엔드포인트는 무료이니 VPC B에 하나 더 만들면 됩니다.[11] NAT는 요구 사항("NAT 없이")과 비용 모두에 어긋납니다.

Q8. (0005 복습) 같은 리전의 VPC A(앱)와 VPC B(DB)가 피어링되어 있습니다. DB 인스턴스는 VPC A의 앱 서버(Auto Scaling 그룹)에서 오는 트래픽만 받아야 합니다. DB 보안 그룹 규칙으로 가장 알맞은 것은?

같은 리전의 피어링이면 상대 VPC의 보안 그룹을 규칙에서 참조할 수 있습니다.[2] 그러면 Auto Scaling으로 IP가 바뀌어도 규칙을 고칠 필요가 없습니다(0005). IP를 손으로 등록하면 확장 때마다 깨지고, IGW는 소스가 될 수 없습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) VPC 피어링의 제약 세 가지. (2) Site-to-Site VPN과 Direct Connect를 경로, 암호화, 성능으로 비교하고, "DX + 암호화"의 답은?

(1) CIDR 겹침 불가, 전이 피어링 불가, 엣지 투 엣지 라우팅 불가(상대의 IGW·NAT·VPN·DX·게이트웨이 엔드포인트를 못 씀). 라우트는 양쪽이 직접 추가.

(2) VPN: 인터넷 위 IPsec, 기본 암호화, 성능은 인터넷에 좌우, 빠르고 저렴. DX: 전용 회선, 기본 암호화 없음, 일관된 성능·대역폭. "DX + 암호화" → DX 위에 Site-to-Site VPN(10·100 Gbps 전용이면 MACsec도 가능).
