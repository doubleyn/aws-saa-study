VPC 간 및 하이브리드 연결:
피어링, Transit Gateway, Site-to-Site VPN, Direct Connect

AWS 클라우드에서 여러 VPC끼리 서로 통신하는 두 가지 핵심 방법(피어링 vs Transit Gateway), 그리고 회사 온프레미스 데이터 센터와 AWS를 연결하는 두 가지 핵심 방법(Site-to-Site VPN vs Direct Connect)을 깊이 있게 정리합니다. 시험과 실무에서는 "연결할 VPC가 몇 개인가", "전이 라우팅이 필요한가", "전송 중 암호화가 필요한가", "일관된 대역폭 성능이 필요한가"라는 4가지 기준을 바탕으로 최적의 아키텍처를 선택하도록 요구합니다.

왜 VPC 간 및 하이브리드 연결을 배워야 할까요?

시험 관점에서: AWS Certified Solutions Architect - Associate (SAA-C03) 시험에서 네트워킹 파트의 대표적인 단골 문제는 바로 "VPC A와 B, 그리고 VPC A와 C가 각각 피어링으로 연결되어 있는데 왜 B에서 C로는 통신이 안 될까?"라는 피어링의 비전이성(Non-transitive) 문제입니다.[2] 또한 "온프레미스와 AWS 사이에 대용량 데이터를 일관된 고속으로 전송하면서 전송 중 암호화 규정을 만족해야 한다"(정답: Direct Connect + Site-to-Site VPN 또는 MACsec)처럼 하이브리드 연결 기술을 결합하는 복합 문제가 반드시 출제됩니다.

실무 관점에서: 기업의 클라우드 환경이 커지면 업무 도메인과 보안 격리를 위해 AWS 계정과 VPC가 수십~수백 개로 폭발적으로 늘어납니다. 초기에 단순하게 맺었던 VPC 피어링 그물(Full Mesh)은 연결 개수가 $N(N-1)/2$로 급증하여 라우팅 관리가 완전히 불가능해집니다. 이때 중앙 허브인 Transit Gateway로 아키텍처를 전환하거나, 온프레미스 본사와 고속 전용선(Direct Connect) 및 백업 VPN을 안정적으로 구성하는 능력은 시니어 클라우드 아키텍트의 필수 핵심 역량입니다.

VPC 피어링: 두 VPC 간의 1:1 고속 직통 연결

VPC 피어링 (VPC Peering)은 두 개의 VPC를 사설 IPv4 또는 IPv6 주소로 직접 라우팅하여, 마치 동일한 내부 네트워크 안에 있는 것처럼 서로 통신할 수 있게 해주는 1:1 네트워크 연결입니다.[1] 동일한 AWS 계정 내부는 물론이고, 서로 다른 AWS 계정(Cross-Account)이나 서로 다른 리전(Cross-Region)에 있는 VPC끼리도 피어링을 맺을 수 있습니다. 별도의 가상 게이트웨이나 VPN 암호화 장치를 거치지 않고 AWS의 기존 물리 인프라 위에서 직접 패킷이 오가므로 단일 장애 지점(SPOF)이나 대역폭 병목 현상이 발생하지 않습니다.[1] 피어링 연결 자체를 생성하고 유지하는 비용은 **완전 무료**이며, 동일 AZ 내의 데이터 전송은 무료, AZ나 리전을 넘나드는 트래픽에 대해서만 표준 데이터 전송료가 발생합니다.

VPC 피어링의 절대적인 제약 사항 (시험 핵심 단골!)

피어링의 편리함 뒤에는 시험과 실무에서 수시로 발목을 잡는 중요한 기술적 제약들이 있습니다.[2]

  • 1. CIDR 블록 중복 절대 불가: 두 VPC의 IP 주소 대역(CIDR)이 단 하나라도 겹치면(Overlapping) 피어링 연결을 아예 맺을 수 없습니다. VPC에 여러 개의 보조 CIDR 블록이 연결되어 있는 경우에도 하나라도 겹치면 생성되지 않습니다.
  • 2. 전이적 라우팅(Transitive Routing) 미지원: VPC 피어링은 전이되지 않습니다! 즉, VPC A와 VPC B가 피어링되어 있고 VPC A와 VPC C가 피어링되어 있더라도, B에서 A를 거쳐 C로 통신할 수는 없습니다 (B → A → C 통신 불가). B와 C가 통신하려면 반드시 B와 C 사이에 별도의 1:1 피어링 연결을 직접 맺어야 합니다.
  • 3. 엣지 투 엣지(Edge-to-Edge) 라우팅 미지원 (대리 전달 불가): VPC B는 피어링된 상대방 VPC A의 인터넷 게이트웨이(IGW), NAT 게이트웨이, Site-to-Site VPN, Direct Connect, S3 게이트웨이 엔드포인트 등을 빌려서 외부로 나갈 수 없습니다. 모든 외부 연결 게이트웨이는 자기 VPC에 직접 연결되어 있어야 합니다.
  • 4. 수동 라우팅 등록 필수: 피어링 연결을 맺고 양쪽 소유자가 수락(Accept)했다고 해서 통신이 바로 되는 것이 아닙니다. 양쪽 VPC 소유자가 각자의 서브넷 라우팅 테이블에 상대방 CIDR 대역으로 향하는 타깃을 피어링 연결(pcx-xxxx)로 직접 등록해 주어야 통신이 시작됩니다. (동일 리전 내의 피어링이라면 상대방 VPC의 보안 그룹을 규칙 소스로 참조할 수 있습니다.)

AWS Transit Gateway: 대규모 엔터프라이즈의 네트워크 전송 허브

VPC가 2~3개뿐일 때는 피어링이 가장 저렴하고 단순합니다. 하지만 VPC가 10개, 50개, 100개로 늘어나면 모든 VPC를 1:1로 잇는 풀 메시(Full Mesh) 구조는 연결 개수가 $N(N-1)/2$로 폭발적으로 늘어나 수백 개의 라우팅 테이블을 관리하다가 통제 불능에 빠지게 됩니다.

AWS Transit Gateway (TGW)는 수많은 VPC와 온프레미스 네트워크를 중앙에서 단 하나의 전송 허브로 묶어주는 **중앙 집중식 네트워크 허브 앤 스포크 (Hub and Spoke)** 서비스입니다.[3] VPC, Site-to-Site VPN, Direct Connect 게이트웨이, 다른 리전의 Transit Gateway 피어링 등을 **연결(Attachment)**로 간단히 꽂기만 하면, Transit Gateway의 라우팅 테이블이 패킷을 원하는 곳으로 자유롭게 중계해 줍니다.[3] 요금은 연결당 시간 요금과 처리한 트래픽 양(GB당 요금)이 청구됩니다.

온프레미스와 잇기 (1): AWS Site-to-Site VPN

AWS Site-to-Site VPN은 회사 온프레미스 본사나 지사와 AWS VPC 사이를 기존 공용 인터넷망 위에 **IPsec 암호화 터널**로 안전하게 연결하는 관리형 서비스입니다.[4][5]

  • AWS 측 게이트웨이: 단일 VPC만 연결할 때는 **가상 프라이빗 게이트웨이 (VGW, Virtual Private Gateway)**를 VPC에 붙여 사용하고, 여러 VPC가 함께 통신해야 할 때는 **Transit Gateway**를 타깃으로 사용합니다.[4]
  • 고객 측 게이트웨이: 데이터 센터에 설치된 물리 방화벽/라우터인 **고객 게이트웨이 장치(Customer Gateway Device)**가 필요하며, AWS 콘솔에는 그 공인 IP 정보를 등록한 **고객 게이트웨이(Customer Gateway, CGW)** 리소스를 생성합니다.
  • 이중 터널(2 Tunnels)을 통한 기본 고가용성: AWS Site-to-Site VPN 연결을 하나 생성하면, AWS는 서로 다른 가용 영역에 걸쳐 **2개의 독립된 IPsec 터널**을 자동으로 프로비저닝해 줍니다. 고객 라우터에서 두 터널을 모두 활성화해 두면 하나의 터널에 문제가 생겨도 즉시 다른 터널로 자동 장애 조치(Failover)되어 연결이 유지됩니다.[4]
  • 대역폭 성능: 표준 터널당 최대 대역폭은 1.25 Gbps입니다. Transit Gateway에 연결할 경우 ECMP(등가 다중 경로)를 통해 여러 터널의 대역폭을 집계하여 확장할 수 있습니다.
  • 핵심 장점: 기존 인터넷 회선과 회사 라우터를 그대로 활용하므로 **수 시간 안에 매우 빠르고 저렴하게 구축**할 수 있으며, 모든 트래픽이 IPsec으로 기본 암호화됩니다.

온프레미스와 잇기 (2): AWS Direct Connect (DX)

AWS Direct Connect (DX)는 공용 인터넷을 완전히 우회하여, 회사 데이터 센터에서 AWS Direct Connect 로케이션까지 **표준 이더넷 광케이블 전용 물리 회선**으로 1:1 직결하는 서비스입니다.[6] 인터넷 통신사(ISP)의 정체나 패킷 손실에 영향을 받지 않아 **극도로 일관되고 예측 가능한 네트워크 성능과 매우 낮은 지연 시간(Low Latency)**을 제공하며, 대용량 데이터를 지속적으로 전송할 때 인터넷 요금 대비 훨씬 저렴한 데이터 송신료가 적용됩니다.[7]

  • 연결 방식: 전용 포트를 독점하는 **전용 연결 (Dedicated, 1·10·100 Gbps)**과 통신 파트너사를 통해 공유 회선을 임대하는 **호스팅 연결 (Hosted, 50 Mbps~10 Gbps)**이 있습니다.[7]
  • 가상 인터페이스 (VIF, Virtual Interface)의 종류:
    • 프라이빗 VIF (Private VIF): VPC 내부의 사설 IP 대역(EC2, RDS 등)과 통신할 때 사용합니다.[6]
    • 퍼블릭 VIF (Public VIF): Amazon S3, DynamoDB 등 AWS의 퍼블릭 서비스 엔드포인트에 인터넷을 거치지 않고 전용선으로 사설 접근할 때 사용합니다.
    • 전송 VIF (Transit VIF): Direct Connect 게이트웨이를 통해 AWS Transit Gateway에 연결할 때 사용합니다.
  • Direct Connect 게이트웨이 (DXGW): 전역(Global) 리소스로서, 하나의 VIF를 통해 전 세계 여러 리전과 여러 계정에 분산된 VPC나 Transit Gateway에 손쉽게 연결할 수 있도록 중계해 줍니다.[7]
  • 고가용성 및 백업 설계: 최상위 복원력을 위해서는 서로 다른 DX 로케이션에 두 번째 DX 회선을 구축해야 합니다. 비용 효율적인 백업 경로로는 **Site-to-Site VPN을 장애 조치(Failover)용 백업**으로 함께 구성할 수 있습니다. 동일한 VPC에 DX와 VPN이 모두 연결되어 있을 때 정상 상태에서는 **Direct Connect 경로가 항상 우선순위**를 가집니다.[8]

매우 중요한 시험 포인트: Direct Connect는 기본적으로 암호화되지 않는다!

Direct Connect는 사설 물리 전용선이지만, 케이블을 통과하는 패킷 자체는 **기본적으로 암호화(Encryption)되지 않은 평문(Plaintext)**으로 전송됩니다![9] 금융 규제나 기업 보안 규정상 "전송 중 암호화(Encryption in Transit)"가 필수 요건인 경우, 다음 두 가지 해결책을 사용해야 합니다.

  1. Direct Connect 위에 Site-to-Site VPN 터널 얹기 (DX + VPN - 시험 최빈출!): Direct Connect의 퍼블릭 VIF를 통해 AWS VPN 엔드포인트에 도달한 뒤 그 위에 IPsec VPN 터널을 생성합니다. 이렇게 하면 **DX의 일관된 고속 성능과 IPsec의 종단 간 강력한 암호화**를 동시에 완벽히 만족할 수 있습니다. 1 Gbps 이하 회선에서도 완벽히 지원됩니다.[10]
  2. MACsec (IEEE 802.1AE) 링크 계층 암호화: 10 Gbps 또는 100 Gbps 전용 연결(Dedicated Connection)에서 지원되는 하드웨어 수준의 고속 암호화 기술입니다. 1 Gbps 이하 회선에서는 사용할 수 없습니다.[7]

실제 시험에서 높은 오답률을 자랑하는 VPC 간 및 하이브리드 연결 실전 8문항입니다. 앞서 배운 제약과 원리를 바탕으로 풀어보세요.

Q1. VPC A는 VPC B, 그리고 VPC C와 각각 1:1로 VPC 피어링이 체결되어 있으며, 관련된 모든 서브넷 라우팅 테이블과 보안 그룹이 정상적으로 설정되어 있습니다. 이때 VPC B에 있는 인스턴스가 VPC C에 있는 인스턴스와 직접 통신을 시도하면 어떻게 될까요?

VPC 피어링은 **전이적 라우팅(Transitive Routing)을 절대 지원하지 않습니다**.[2] VPC A가 가운데 끼어 있더라도 B에서 C로 패킷을 넘겨줄 수 없습니다. B와 C가 통신하려면 B와 C 사이에 별도의 1:1 피어링 연결을 직접 생성해야 합니다. 하나의 VPC가 여러 VPC와 각각 피어링을 맺는 것은 가능하며, 계정이 같든 다르든 전이 라우팅 불가 규칙은 동일합니다.

Q2. (시험형) 한 글로벌 기업이 여러 AWS 계정에 걸쳐 총 40개의 VPC를 운영하고 있으며, 모든 VPC가 서로 자유롭게 통신해야 하고 회사 온프레미스 데이터 센터와도 연결되어야 합니다. 관리 및 운영 오버헤드를 최소화하면서 이를 구현할 수 있는 가장 적절한 네트워크 아키텍처는 무엇일까요?

수십 개 이상의 VPC와 온프레미스를 하나로 잇는 최적의 관리형 솔루션은 바로 **AWS Transit Gateway (허브 앤 스포크)**입니다.[3] 40개 VPC를 모두 1:1 피어링으로 묶으려면 무려 $40 \times 39 / 2 = 780$개의 연결과 수천 줄의 라우팅 테이블을 관리해야 하므로 운영이 불가능합니다. 또한 중계용 VPC를 통한 경유는 피어링의 비전이성과 엣지 투 엣지 라우팅 금지 제약 때문에 동작하지 않습니다.[2]

Q3. (시험형) 한 금융 회사가 1 Gbps AWS Direct Connect 전용 연결을 통해 본사 데이터 센터와 AWS VPC를 연결하여 사용 중입니다. 최근 개정된 금융 보안 규정에 따라 온프레미스와 AWS 사이를 오가는 모든 네트워크 트래픽은 반드시 "전송 중 암호화"되어야 하며, Direct Connect의 일관된 고속 성능 또한 유지해야 합니다. 가장 적절한 조치는 무엇일까요?

Direct Connect는 전용선이지만 **기본적으로 암호화되지 않은 평문**으로 통신합니다.[9] MACsec은 10 Gbps 또는 100 Gbps 전용선에서만 지원되므로 1 Gbps 회선에는 적용할 수 없습니다. 따라서 **Direct Connect의 퍼블릭 VIF 위에 Site-to-Site VPN 터널을 얹는 구성(DX + VPN)**을 사용해야 DX의 일관된 성능과 IPsec 암호화를 동시에 달성할 수 있습니다.[10] 단순 인터넷 VPN으로 바꾸면 일관된 성능 요건을 만족할 수 없습니다.

Q4. (시험형) 한 해외 지사가 AWS VPC 내부에 호스팅된 사내 ERP 시스템에 안전하게 접속해야 합니다. 트래픽 양은 그다지 많지 않으며, 연결은 반드시 암호화되어야 하고, 가능한 한 가장 빠르고 저렴하게 구축해야 합니다. 지사에는 IPsec 표준 프로토콜을 지원하는 라우터 장비가 구비되어 있습니다. 가장 적절한 솔루션은 무엇일까요?

AWS Site-to-Site VPN은 기존 공용 인터넷 회선과 지사의 IPsec 라우터를 그대로 활용하므로, 몇 시간 만에 가장 빠르고 저렴하게 구축할 수 있으며 IPsec으로 기본 암호화됩니다.[4] Direct Connect는 물리 회선 공사로 인해 수주 이상 소요되고 비용도 훨씬 비쌉니다. VPC 피어링은 VPC끼리만 맺는 연결이며, 내부 ERP를 공용 인터넷에 공개하는 것은 보안상 절대 금지됩니다.

Q5. (시험형) 한 엔터프라이즈 기업의 주 네트워크 연결은 단일 Direct Connect 전용선입니다. 이 전용선에 장애가 발생하더라도 사내 시스템의 연결이 끊기지 않도록 백업 경로를 마련하되, 평상시 비용 지출은 최소화하고자 합니다. 가장 적절한 백업 아키텍처는 무엇일까요?

Direct Connect와 Site-to-Site VPN은 동일한 VPC에 함께 구성하여 **비용 효율적인 백업 장애 조치(Failover)**로 활용할 수 있습니다.[8] 평상시에는 우선순위에 따라 고속 DX 전용선으로 통신하다가, DX 회선에 장애가 발생하면 즉시 VPN 터널로 트래픽이 자동 전환됩니다. 두 번째 DX 회선을 구축하는 것이 복원력은 가장 높지만 비용이 훨씬 비쌉니다.[7] 포트 대역폭을 늘리는 것은 회선 단선 장애에 아무런 도움이 되지 않습니다.

Q6. **VPC 피어링(VPC Peering)**에 대한 설명으로 옳은 것을 **두 개** 고르세요.

VPC 피어링은 서로 다른 계정과 다른 리전의 VPC 간에도 체결할 수 있으며, CIDR 대역이 겹치면 절대 생성할 수 없습니다.[1][2] 상대방 VPC의 게이트웨이를 경유하는 통신은 엣지 투 엣지 라우팅 금지로 인해 불가능하며, 라우팅 테이블의 피어링 라우트는 양쪽 소유자가 직접 수동으로 등록해 주어야 합니다.

Q7. (0006 복습) VPC A에는 Amazon S3용 게이트웨이 엔드포인트가 정상 구성되어 있으며, VPC B는 VPC A와 VPC 피어링으로 연결되어 있습니다. VPC B의 프라이빗 서브넷에 있는 인스턴스가 NAT 게이트웨이 비용 없이 동일 리전의 S3에 안전하게 접근해야 합니다. 가장 비용 효율적인 해결책은 무엇일까요?

VPC 피어링은 엣지 투 엣지 라우팅을 지원하지 않으므로, VPC B가 피어링을 타고 VPC A 안에 있는 게이트웨이 엔드포인트를 빌려 쓸 수 없습니다.[2] **게이트웨이 엔드포인트는 추가 비용이 전혀 없는 완전 무료 서비스**이므로, VPC B 자체에 S3 게이트웨이 엔드포인트를 하나 새로 생성하여 라우팅 테이블에 연결해 주는 것이 가장 완벽하고 비용 효율적인 정답입니다.[11]

Q8. (0005 복습) 동일한 리전에 위치한 애플리케이션용 VPC A와 데이터베이스용 VPC B가 VPC 피어링으로 연결되어 있습니다. VPC B의 데이터베이스 인스턴스는 오직 VPC A의 웹/앱 서버들(Auto Scaling 그룹에 의해 동적으로 증감)에서 오는 트래픽만 수신해야 합니다. VPC B 데이터베이스의 보안 그룹 인바운드 규칙으로 가장 올바른 구성은 무엇일까요?

동일 리전 내에서 VPC 피어링으로 연결되어 있다면, **상대방 VPC에 있는 보안 그룹 ID를 내 보안 그룹 규칙의 소스로 직접 참조(Security Group Referencing)**할 수 있습니다.[2] 이렇게 하면 Auto Scaling에 의해 웹 서버의 개수가 바뀌거나 사설 IP가 동적으로 변경되어도 규칙을 수정할 필요가 전혀 없습니다(0005 레슨 참조). IP를 수동으로 등록하는 것은 확장에 대응할 수 없고, IGW는 보안 그룹 규칙의 소스가 될 수 없습니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 머릿속에서 내용을 직접 정리해 적어보세요.
(1) VPC 피어링이 가진 3대 기술적 제약(CIDR, 라우팅 전이성, 엣지 경유)을 설명해 보세요.
(2) Site-to-Site VPN과 Direct Connect를 물리 경로, 암호화 여부, 성능 일관성 관점에서 비교하고, "Direct Connect 전용선에 전송 중 암호화 필수"라는 조건이 주어졌을 때의 해결책은 무엇인가요?

(1) VPC 피어링 3대 핵심 제약:
① CIDR 중복 불가: 두 VPC의 IP 대역이 단 하나라도 겹치면 연결 불가.
② 전이적 라우팅(Transitive Routing) 미지원: A–B, A–C 피어링 상태여도 B가 A를 거쳐 C로 갈 수 없음 (B–C 직접 피어링 필요).
③ 엣지 투 엣지 라우팅 불가: 상대방 VPC의 IGW, NAT 게이트웨이, VPN, Direct Connect, S3 게이트웨이 엔드포인트를 빌려 쓸 수 없음.

(2) Site-to-Site VPN vs Direct Connect 및 암호화 방안:
- VPN: 공용 인터넷 위 IPsec 터널, 기본 암호화 제공, 성능은 인터넷 품질에 좌우됨, 수 시간 내 빠르고 저렴하게 구축.
- Direct Connect (DX): 인터넷을 우회하는 전용 광케이블 물리 회선, 기본적으로 암호화되지 않음, 극도로 일관된 성능과 낮은 지연 시간 제공.
- "Direct Connect + 암호화" 해결책: Direct Connect의 퍼블릭 VIF 위에 Site-to-Site VPN 터널을 중첩 구성(DX + VPN)하거나, 10G/100G 전용선인 경우 MACsec 링크 계층 암호화를 활성화합니다.

콘솔 실습 (선택 사항, 실습 비용 무료): 동일 리전에 CIDR이 서로 겹치지 않는 2개의 테스트 VPC(예: 10.1.0.0/16과 10.2.0.0/16)를 만들고 피어링 연결을 생성한 후 수락(Accept)해 보세요. 수락만으로는 양쪽 VPC의 인스턴스가 통신할 수 없으며, 양쪽 VPC의 라우팅 테이블에 상대방 CIDR 대역으로 향하는 타깃을 pcx-(피어링 연결)로 직접 등록해 주어야만 통신이 개시된다는 사실을 직접 확인할 수 있습니다. VPC 피어링 연결 생성 및 동일 AZ 내의 통신은 완전 무료입니다.
