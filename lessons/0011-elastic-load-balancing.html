ALB vs NLB vs GWLB 완벽 비교 가이드

AWS의 세 가지 핵심 로드 밸런서(ALB, NLB, GWLB)는 이름은 비슷하지만 네트워크 트래픽을 처리하는 OSI 계층(Layer)과 작동 방식이 근본적으로 다릅니다. Application Load Balancer는 HTTP/HTTPS 요청의 내용(URL 경로, 호스트, 헤더)을 보고 라우팅하고, Network Load Balancer는 TCP/UDP의 네트워크 연결(Connection)을 보며 초당 수백만 건의 트래픽을 초저지연으로 처리하며, Gateway Load Balancer는 IP 패킷 자체를 서드파티 가상 보안 어플라이언스로 투명하게 보냅니다. 이 동작 원리 하나만 명확히 이해하면 로드 밸런서 관련 시험 문제의 80% 이상을 단숨에 풀어낼 수 있습니다.

왜 Elastic Load Balancing(ELB)을 배워야 할까요?

시험 관점: "URL 경로별 마이크로서비스 라우팅", "고객사 방화벽을 위한 고정 IP(탄력적 IP) 할당", "UDP 프로토콜 및 초당 수백만 건의 초저지연 처리", "서드파티 차세대 방화벽(NGFW) 가상 어플라이언스 수평 확장" 같은 핵심 요구사항 단어 하나로 정답 로드 밸런서가 단번에 갈립니다. 또한 바로 다음 레슨에서 다룰 EC2 Auto Scaling의 핵심 동작(대상 그룹 상태 확인, 스케일 인/아웃 시 안전한 연결 드레이닝)이 모두 ELB 아키텍처를 전제로 작동하므로 필수적인 기반 지식입니다.
실무 관점: Elastic Load Balancing은 다중 가용 영역(Multi-AZ) 기반 고가용성 클라우드 시스템의 최전방 정문(Gate)입니다. 초기에 서비스 성격에 맞지 않는 로드 밸런서를 선택하면, 나중에 고정 IP 화이트리스트 요구, 실시간 스트리밍 UDP 통신, 웹 소켓 및 세부 URL 라우팅 요건을 맞추기 위해 인프라 전체를 갈아엎어야 하는 거대한 마이그레이션 부담이 발생합니다.

ELB 공통 아키텍처: 리스너, 라우팅 규칙, 대상 그룹

모든 AWS Elastic Load Balancer는 리스너(Listener), 라우팅 규칙(Rules), 그리고 대상 그룹(Target Group)이라는 공통된 3계층 아키텍처를 기반으로 동작합니다.[2]

  • 리스너 (Listener): 클라이언트의 연결 요청을 수신 대기하는 프로세스입니다. 프로토콜(HTTP, HTTPS, TCP, TLS, UDP)과 포트 번호(예: 80, 443)를 설정하여 트래픽을 받습니다.
  • 규칙 (Rules): 리스너로 들어온 트래픽을 검사하여 어떤 대상 그룹으로 라우팅할지 결정하는 조건문입니다(기본 규칙 및 우선순위 규칙).
  • 대상 그룹 (Target Group): 요청을 전달받아 실제로 비즈니스 로직을 처리하는 백엔드 타깃들의 논리적 집합입니다(EC2 인스턴스, 컨테이너, 프라이빗 IP, Lambda 함수 등). 하나의 대상을 여러 대상 그룹에 중복 등록할 수도 있습니다.
  • 상태 확인 (Health Check): 대상 그룹 단위로 개별 설정됩니다. 로드 밸런서는 주기적으로 각 타깃에 헬스 체크 요청을 보내 응답을 확인하며, 오직 정상(Healthy)으로 판정된 대상에게만 트래픽을 전달합니다. 비정상(Unhealthy) 대상은 자동으로 감지되어 트래픽 전달 대상에서 즉시 제외됩니다.

가용 영역(AZ) 활성화 규칙: 로드 밸런서 설정에서 특정 가용 영역의 서브넷을 활성화하면, 해당 AZ에 로드 밸런서 전용 관리형 노드가 프로비저닝됩니다. 만약 활성화하지 않은 AZ에 백엔드 인스턴스가 존재하더라도, 그 인스턴스는 트래픽을 전혀 전달받을 수 없습니다. 특히 ALB는 고가용성 보장을 위해 반드시 최소 2개 이상의 가용 영역(AZ)을 활성화해야만 생성할 수 있습니다.[1]

인터넷 경계(Internet-facing) vs 내부(Internal) 로드 밸런서

로드 밸런서는 배포되는 위치와 서브넷에 따라 두 가지 모드로 나뉩니다.[1]

  • 인터넷 경계(Internet-facing) 로드 밸런서: 퍼블릭 서브넷에 배치되며, 퍼블릭 IP 주소와 공용 DNS 이름을 갖습니다. 인터넷에 공개되어 외부 사용자의 요청을 수신합니다.
  • 내부(Internal) 로드 밸런서: 프라이빗 서브넷에 배치되며, 프라이빗 사설 IP 주소만 갖습니다. VPC 내부의 백엔드 서비스 간 통신이나 온프레미스 기업망(VPN/Direct Connect)에서만 접속할 수 있습니다.

핵심 보안 설계 포인트: 로드 밸런서가 인터넷 경계이든 내부이든, 로드 밸런서 노드와 백엔드 타깃(EC2 인스턴스 등) 간의 통신은 항상 VPC 내부의 프라이빗 IP를 통해 이루어집니다. 따라서 백엔드 EC2 인스턴스에는 퍼블릭 IP가 전혀 필요 없습니다! 백엔드 EC2는 안전한 프라이빗 서브넷에 두고, 보안 그룹 인바운드 규칙에서 오직 로드 밸런서의 보안 그룹 ID만을 허용하도록 구성하는 다계층(Multi-tier) 방어가 AWS 공식 보안 모범 사례입니다.[1]

Application Load Balancer (ALB)만의 독보적인 기능

  • 경로 기반(Path-based) 및 호스트 기반(Host-based) 라우팅: example.com/api/*는 주문 서비스 대상 그룹으로, example.com/images/*는 이미지 처리 대상 그룹으로 라우팅할 수 있으며, app.example.com과 blog.example.com을 단 하나의 ALB로 나누어 서비스할 수 있습니다.[4]
  • 스마트 리디렉션 및 고정 응답: HTTP(포트 80) 요청을 HTTPS(포트 443)로 자동 리디렉션하거나, 백엔드 서버를 거치지 않고 ALB 자체에서 HTTP 403, 503 오류 또는 커스텀 JSON 응답을 즉시 반환할 수 있습니다.
  • 사용자 인증 통합: Cognito 사용자 풀이나 기업용 OIDC/SAML 자격 증명 공급자(IdP)와 연동하여, 애플리케이션 코드 수정 없이 ALB 수준에서 사용자를 먼저 인증한 후 백엔드로 요청을 넘길 수 있습니다.[2]
  • AWS WAF 완벽 연동: 웹 ACL 규칙을 ALB에 직접 연결하여 SQL 인젝션, XSS 등의 7계층 공격을 사전에 차단합니다.
  • Lambda 함수 대상 지원: 대상 그룹에 단일 Lambda 함수를 등록하여 서버리스 RESTful API를 구축할 수 있습니다. 요청 본문과 응답은 JSON 직렬화되어 처리됩니다.[10]
  • 하이브리드 온프레미스 대상 등록: ip 타깃 유형을 사용하면 Direct Connect나 Site-to-Site VPN으로 연결된 온프레미스 사내 데이터센터의 서버 사설 IP도 대상 그룹에 등록하여 로드 밸런싱할 수 있습니다(단, 공인 인터넷 라우팅 가능 IP는 등록 불가).[3]

Gateway Load Balancer (GWLB)의 동작 방식: 여러 VPC의 네트워크 트래픽을 중앙의 보안 검사 전용 VPC로 모아서 검사하고 싶을 때 사용합니다. 사용자 VPC의 라우팅 테이블에서 Gateway Load Balancer 엔드포인트(GWLBE, PrivateLink 기술 기반)를 다음 홉(Next Hop)으로 지정하면, 모든 인바운드/아웃바운드 패킷이 GWLB를 거쳐 방화벽 어플라이언스 풀로 전달되어 검사받은 뒤 안전하게 원래 목적지로 이동합니다.[7]

교차 영역 로드 밸런싱 (Cross-Zone Load Balancing)

교차 영역 로드 밸런싱은 각 로드 밸런서 노드가 클라이언트 요청을 자신이 속한 가용 영역(AZ)에 있는 타깃뿐만 아니라, **다른 가용 영역에 등록된 모든 타깃에게까지 골고루 분배(1/N)**해 주는 기능입니다.[1]

등록 취소 지연 (Deregistration Delay / Connection Draining)

배포나 점검, 혹은 Auto Scaling의 스케일 인(축소)으로 인해 특정 인스턴스를 대상 그룹에서 제거해야 할 때, 즉시 연결을 강제로 끊어버리면 사용자가 진행 중이던 결제 요청이나 파일 업로드가 중간에 에러로 튕기게 됩니다.[9]

이때 등록 취소 지연이 활성화되어 있으면, 해당 인스턴스는 즉시 draining 상태로 전환됩니다. 로드 밸런서는 새로운 신규 요청은 해당 인스턴스로 일체 보내지 않으면서, 이미 진행 중인 기존 요청(In-flight requests)이 정상적으로 완료될 때까지 기본 300초(0~3,600초 사이 설정 가능) 동안 안전하게 기다려 줍니다. 모든 진행 중 요청이 완료되거나 타임아웃이 지나면 인스턴스가 안전하게 연결 해제됩니다.

느린 시작 (Slow Start)

새로 인스턴스가 부팅되어 정상(Healthy) 판정을 받는 순간 갑자기 수천 건의 트래픽이 한 번에 쏟아지면, 캐시나 커넥션 풀이 예열되지 않은 신규 인스턴스가 즉시 과부하로 뻗어버릴 수 있습니다. 느린 시작을 설정하면 새로 등록된 타깃에 대해 정해진 워밍업 시간 동안 트래픽을 선형적으로 서서히 늘려주어 안전하게 예열될 시간을 벌어줍니다.[9]

고정 세션 (Sticky Sessions / Session Affinity)

웹 애플리케이션이 사용자 로그인 세션 상태나 장바구니 데이터를 Redis 같은 외부 공용 캐시가 아니라 개별 EC2 인스턴스의 로컬 메모리에 저장하고 있는 경우, 사용자가 페이지를 이동할 때마다 요청이 다른 인스턴스로 전달되면 강제로 로그아웃되는 현상이 발생합니다.[9]

고정 세션을 켜면, ALB가 HTTP 응답에 AWSALB라는 특수 쿠키(기간 기반)를 심거나 애플리케이션 자체 쿠키를 활용하여, 동일한 클라이언트의 모든 연속된 HTTP 요청을 항상 동일한 백엔드 인스턴스로 바인딩(고정)해 줍니다. 소스 코드를 크게 뜯어고치지 않고 레거시 세션 문제를 해결하는 가장 빠른 방법입니다. (단, 해당 인스턴스가 장애로 죽으면 새로운 정상 인스턴스로 세션이 이동합니다).

실전 연습 문제

학습한 내용을 바탕으로 문제를 풀어보세요. 보기 길이는 실제 시험처럼 균형 있게 구성되어 있습니다.

Q1. (시험형) 한 전자상거래 기업의 웹 애플리케이션에서 /api/* 경로로 들어오는 API 요청은 백엔드 주문 처리 서비스로, /images/* 경로로 들어오는 정적 파일 요청은 이미지 렌더링 서비스로 분기하여 전달해야 합니다. 두 서비스는 각각 서로 다른 EC2 Auto Scaling 그룹에 속해 독립적으로 운영됩니다. 아키텍처의 복잡성과 관리 오버헤드를 최소화하면서 이를 구현하는 가장 적합한 로드 밸런싱 구성은 무엇인가요?

HTTP URL 요청 경로(Path Pattern)를 검사하여 트래픽을 분기하는 것은 OSI 7계층 Application Load Balancer(ALB)의 고유한 핵심 기능입니다. 단 하나의 ALB에 리스너 규칙을 추가하고 경로 조건에 따라 서로 다른 대상 그룹(Auto Scaling 그룹)으로 트래픽을 라우팅하면 최소의 관리 비용으로 깔끔하게 해결됩니다. NLB는 4계층 전송 계층에서 동작하므로 HTTP URL 경로를 전혀 해석할 수 없으며 "NLB에 경로 기반 규칙"이라는 기능은 존재하지 않습니다. GWLB는 보안 가상 어플라이언스를 위한 서비스입니다.

Q2. (시험형) 한 글로벌 게임 회사가 실시간 멀티플레이어 배틀로얄 게임 서버를 AWS 환경에 배포하려 합니다. 게임 클라이언트는 지연 시간을 최소화하기 위해 UDP 프로토콜을 사용하여 초당 수백만 건의 고주파 패킷을 서버와 주고받아야 합니다. 또한 일부 기관 및 기업 네트워크 환경의 플레이어들은 방화벽 정책상 고정된 공인 IP 주소만 접속 허용(화이트리스트) 목록에 등록할 수 있습니다. 가장 적합한 로드 밸런서는 무엇인가요?

"UDP 프로토콜 지원", "초당 수백만 건의 초저지연 패킷 처리", "방화벽 등록을 위한 고정 IP 및 Elastic IP(탄력적 IP) 할당"은 모두 Network Load Balancer(NLB)를 선택해야 하는 결정적인 핵심 키워드입니다. ALB는 HTTP/HTTPS/gRPC 전용이므로 UDP 트래픽을 수신할 수 없으며 고정 IP를 지원하지 않고 DNS 이름으로만 접근 가능합니다.

Q3. (시험형) 기업 보안팀이 VPC로 유입되고 유출되는 모든 네트워크 트래픽을 타사(Third-party) 차세대 방화벽(NGFW) 가상 소프트웨어 어플라이언스 풀을 통과시켜 심층 패킷 검사를 수행하려 합니다. 보안 어플라이언스는 트래픽 증가에 따라 자동으로 수평 확장되어야 하며, 특정 어플라이언스에 장애가 발생하더라도 전체 네트워크 트래픽 흐름이 끊기지 않고 고가용성을 유지해야 합니다. 어떤 서비스를 도입해야 하나요?

서드파티 가상 보안 어플라이언스(방화벽, 침입 탐지/방지 시스템 IDS/IPS, 심층 패킷 검사 DPI)를 손쉽게 수평 확장하고 고가용성을 제공하는 것이 바로 Gateway Load Balancer(GWLB)의 존재 이유입니다. 사용자 VPC의 라우팅 테이블에서 GWLB 엔드포인트(GWLBE)를 다음 홉(Next Hop)으로 지정하면 패킷이 투명하게 보안 어플라이언스를 거쳐 검사됩니다. AWS WAF는 7계층 HTTP 요청을 거르는 관리형 방화벽으로 "타사 어플라이언스 구동" 요건에 맞지 않습니다.

Q4. (시험형) 기본 설정으로 Network Load Balancer(NLB)를 생성하고 두 개의 가용 영역(AZ A, AZ B)을 활성화했습니다. 대상 그룹에는 AZ A에 EC2 인스턴스 2대, AZ B에 8대가 등록되어 있습니다. 외부 DNS가 두 AZ의 NLB 노드에 트래픽을 정확히 50%씩 균등하게 전달할 때, 기본 설정 상태에서 AZ A에 위치한 인스턴스 한 대가 감당하게 되는 트래픽 비율은 전체 트래픽의 몇 %인가요?

Network Load Balancer는 교차 영역 로드 밸런싱(Cross-Zone Load Balancing)이 기본적으로 비활성화(False)되어 있습니다. 따라서 AZ A의 NLB 노드가 받은 전체 트래픽의 50%는 오직 AZ A 내부에 있는 2대의 인스턴스에만 분배되므로, 인스턴스 1대당 25%(50% ÷ 2)의 과도한 트래픽이 몰리게 됩니다. (AZ B의 인스턴스는 50% ÷ 8 = 6.25%만 받음). 전체 대상 10대에 10%씩 균등 분배하려면 대상 그룹 속성에서 교차 영역 로드 밸런싱을 수동으로 활성화해야 합니다.

Q5. Application Load Balancer(ALB)에서는 지원되지만, Network Load Balancer(NLB)에서는 기술적으로 지원되지 않는 고유한 기능을 두 개 고르세요.

ALB는 대상 그룹에 AWS Lambda 함수를 직접 등록할 수 있으며, HTTP 호스트 헤더나 URL 경로 같은 요청 내용을 검사하여 타깃을 결정할 수 있습니다. 반면 서브넷별 Elastic IP 할당과 UDP 프로토콜 지원은 4계층인 NLB에서만 지원되는 고유 기능입니다.

Q6. (시험형) 온프레미스에서 오랜 기간 운영되던 레거시 웹 애플리케이션을 AWS ALB 뒤의 EC2 인스턴스들로 마이그레이션했습니다. 이 애플리케이션은 사용자의 로그인 인증 상태를 개별 웹 서버의 로컬 메모리에 직접 저장하고 있습니다. 마이그레이션 직후 사용자들이 웹 사이트에서 페이지를 클릭할 때마다 불규칙하게 로그아웃되는 현상이 발생하고 있습니다. 애플리케이션 소스 코드를 수정하지 않고 가장 신속하게 이 문제를 해결하는 방법은 무엇인가요?

고정 세션(Sticky Sessions / Session Affinity)을 활성화하면 ALB가 HTTP 쿠키를 생성하여 동일한 사용자의 모든 연속적인 요청을 항상 처음 연결된 동일한 백엔드 EC2 인스턴스로 라우팅해 줍니다. 따라서 인스턴스 로컬 메모리에 세션이 저장되어 있더라도 세션 끊김 현상이 발생하지 않습니다. 등록 취소 지연은 인스턴스 제거 시 진행 중 요청을 보호하는 기능이며, 느린 시작은 신규 인스턴스의 트래픽 워밍업을 다루므로 이 문제와 무관합니다.

Q7. (0010 복습 연계) 전원이나 네트워크 장애가 동시에 발생하면 안 되는 핵심 데이터베이스 및 미들웨어 서버 6대를 단일 가용 영역(AZ) 내부에서 물리적으로 서로 완전히 격리된 별도의 랙(하드웨어)에 분산하여 배치하려 합니다. 어떤 EC2 배치 그룹 전략을 선택해야 하나요?

분산 배치 그룹(Spread Placement Group)은 인스턴스마다 서로 다른 물리적 하드웨어 랙(독립된 전원 공급 장치와 네트워크 스위치)에 각각 배치하여 하드웨어 장애가 다른 인스턴스로 전파되는 것을 차단합니다. 가용 영역(AZ)당 실행 가능한 인스턴스가 최대 7개로 제한되므로 6대 배치에 완벽하게 부합합니다. 클러스터 배치 그룹은 인스턴스를 최대한 가까이 모으는 구성이므로 동시 장애 방지 목적과 정반대입니다.

Q8. (시험형) 새롭게 배포한 ALB의 대상 그룹에 속한 모든 EC2 인스턴스들이 지속적으로 unhealthy(비정상) 상태로 표시되고 있습니다. 하지만 서버 내부에서 직접 확인한 결과 웹 애플리케이션은 정상 동작하고 있으며, 루트 경로(/)로 접근 시 인증되지 않은 사용자를 로그인 페이지(/login)로 보내기 위해 HTTP 302 리디렉션 코드를 정상적으로 반환하고 있습니다. 현재 ALB 대상 그룹의 상태 확인 설정은 모두 기본값입니다. 정상 상태로 복구하기 위한 올바른 조치는 무엇인가요?

ALB 상태 확인의 기본 설정은 경로가 /이고 성공 판정 응답 코드(Matcher)는 오직 200뿐입니다. 애플리케이션이 / 경로에서 HTTP 302 리디렉션을 돌려주면 ALB는 이를 상태 확인 실패로 간주합니다. 이 문제를 해결하려면 HTTP 200을 명시적으로 반환하는 전용 헬스 체크 경로(예: /health)로 상태 확인 경로를 변경하거나, 성공 응답 코드 범위에 200,302 또는 200-399를 추가해 주어야 합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 직접 머릿속에서 인출하여 적어보세요.
(1) ALB, NLB, GWLB의 동작 계층, 지원 타깃 유형, 그리고 각각을 선택하게 만드는 대표적인 시나리오 키워드는 무엇인가요?
(2) 교차 영역 로드 밸런싱(Cross-Zone Load Balancing)의 ALB와 NLB 기본값 차이는 무엇인가요?
(3) 등록 취소 지연(Deregistration Delay)과 고정 세션(Sticky Sessions)은 각각 프로덕션 환경의 어떤 실무 문제를 해결해 주나요?

(1) ALB: 7계층, 타깃: instance/ip/lambda, 키워드: URL 경로 및 호스트 라우팅, 컨테이너 마이크로서비스, WAF 연동, 사용자 인증. NLB: 4계층, 타깃: instance/ip/alb, 키워드: 가용 영역별 고정 IP/탄력적 IP 할당, 방화벽 화이트리스트, UDP 프로토콜, 초당 수백만 요청 초저지연 처리, 원본 클라이언트 IP 보존. GWLB: 3계층, 타깃: 가상 어플라이언스, 키워드: 서드파티 방화벽 및 IDS/IPS 투명 수평 확장, GENEVE 포트 6081, GWLB 엔드포인트.
(2) 기본값: ALB는 로드 밸런서 생성 시 기본적으로 항상 켜짐(True, 데이터 전송 무료). NLB와 GWLB는 기본적으로 꺼짐(False, 활성화 시 AZ 간 데이터 전송 요금 발생 가능).
(3) 등록 취소 지연: 인스턴스를 뺄 때 신규 요청은 차단하고 진행 중인 기존 요청이 완료될 때까지 기본 300초 기다려 주어 사용자의 트랜잭션이 끊기는 현상 방지. 고정 세션: 쿠키를 사용해 동일 사용자의 요청을 동일 인스턴스로 바인딩하여, 서버 메모리에 세션 상태가 저장된 레거시 앱의 잦은 로그아웃 문제 해결.

추가 학습 및 실습

콘솔 실습 (선택 사항, 비용 주의): EC2 프리 티어 인스턴스 2대에 간단한 아파치 웹 서버를 띄우고 서로 다른 HTML 페이지(/app1/index.html, /app2/index.html)를 생성한 뒤, 하나의 ALB를 만들어 경로 기반 라우팅 규칙(/app1/*, /app2/*)을 구성해 보세요. 브라우저 주소창에 경로를 입력할 때마다 서로 다른 서버로 요청이 깔끔하게 분기되는 것을 직접 확인할 수 있습니다. (※ 로드 밸런서는 실행 시간당 요금이 부과되므로 실습이 끝난 즉시 로드 밸런서와 대상 그룹을 삭제하세요).
