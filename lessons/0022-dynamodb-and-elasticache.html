밀리초에서 마이크로초로:
DynamoDB와 ElastiCache

데이터베이스의 성능을 한 단계 끌어올리는 비관계형(NoSQL) 아키텍처의 두 기둥입니다. Amazon DynamoDB는 트래픽이 무한히 폭증해도 한 자릿수 밀리초(ms) 지연 시간을 보장하는 서버리스 키-값 데이터베이스이며, Amazon ElastiCache는 데이터베이스 앞단에서 응답 속도를 마이크로초(µs) 수준으로 단축하는 초고속 인메모리 캐시입니다. 온디맨드와 프로비저닝 용량 모드, 전용 가속기 DAX, 글로벌 테이블, Streams·TTL·PITR 삼총사, 그리고 캐싱 전략 두 가지를 시험 키워드와 함께 깊이 있게 정리합니다.

⏱ 약 20분🎯 오늘의 승리: 시나리오 8문항📌 데이터베이스 치트시트

왜 DynamoDB와 ElastiCache를 배워야 할까요?

시험에서: "트래픽 패턴을 전혀 예측할 수 없는 신규 서비스" → DynamoDB 온디맨드, "자주 읽히는 플레이어 프로필을 마이크로초 단위로 극속 조회" → DAX, "전 세계 여러 대륙에서 로컬 지연 시간으로 읽기와 쓰기를 모두 처리" → DynamoDB 글로벌 테이블, "실시간 게임 순위표(리더보드)" → Valkey / Redis OSS 정렬 집합(Sorted Sets). 이러한 핵심 키워드 매핑만 정확히 이해해도 시험 문제의 절반은 즉시 풀립니다.
실무에서: DynamoDB의 용량 모드(온디맨드 vs 프로비저닝)를 잘못 선택하면 불필요하게 수백만 원의 비용이 청구되거나 스로틀링(Throttling) 장애가 발생하며, 캐시 전략(지연 로딩 vs 라이트 스루)을 잘못 설계하면 사용자 화면에 유효하지 않은 오래된(Stale) 데이터가 노출되는 치명적인 결함이 발생합니다.

Amazon DynamoDB: 규모와 무관하게 한 자릿수 밀리초를 보장하는 NoSQL

Amazon DynamoDB는 완전관리형, 서버리스 분산 NoSQL 데이터베이스입니다. 데이터가 기가바이트(GB)이든 페타바이트(PB)이든, 초당 수백 건이든 수천만 건이든 상관없이 언제나 일관된 한 자릿수 밀리초(Single-digit millisecond) 레이턴시를 보장합니다.[1]

  • 데이터 모델: 스키마가 유연한 키-값(Key-Value) 및 문서(JSON Document) 구조를 지원합니다. 기본 키(Primary Key)는 단일 파티션 키(Partition Key)만으로 구성하거나, 파티션 키와 정렬 키(Sort Key)의 복합 키로 구성할 수 있습니다. DynamoDB는 내부적으로 파티션 키를 해싱하여 물리적인 스토리지 노드들에 데이터를 균등하게 분산 저장합니다.
  • 서버리스와 고가용성: 프로비저닝할 서버나 OS 패치, 데이터베이스 버전 업그레이드가 전혀 없습니다. 테이블에 데이터를 쓰면 AWS가 자동으로 3개 가용 영역(AZ)에 걸쳐 데이터를 복제하여 강력한 내구성과 고가용성을 제공합니다.[1]
  • 관계형 DB와의 결정적 차이: DynamoDB는 테이블 간 JOIN을 지원하지 않습니다! 따라서 설계 시점에 데이터를 비정규화(Denormalization)하여 하나의 테이블 안에서 필요한 정보를 조회할 수 있도록 모델링해야 합니다.
  • 인증 및 권한 관리: 데이터베이스 계정(ID/비밀번호)을 생성하는 것이 아니라, AWS IAM 정책을 통해 특정 속성(컬럼) 수준까지 세밀하게 접근 권한을 제어합니다.
  • 보조 인덱스 (LSI vs GSI):
    • LSI (Local Secondary Index): 기본 테이블과 동일한 파티션 키를 사용하되 다른 정렬 키를 가집니다. 테이블 생성 시점에만 만들 수 있으며 사후 추가나 삭제가 불가능합니다. 파티션당 10GB 크기 제약을 공유합니다.
    • GSI (Global Secondary Index): 기본 테이블과 완전히 다른 파티션 키 및 정렬 키를 자유롭게 정의할 수 있습니다. 테이블 생성 후 운영 중에도 언제든 추가하거나 삭제할 수 있으며, 자체적인 독립 처리량(RCU/WCU)을 가집니다.

용량 모드: 온디맨드 vs 프로비저닝

구분온디맨드 (On-Demand) 모드프로비저닝 (Provisioned) 모드
과금 체계실제 실행된 요청당(Request) 과금 (사용한 만큼만 비용 지불)시간당 사전 할당된 RCU / WCU 용량 단위로 과금 (실제 사용 여부 무관)
권장 시나리오기본값이자 AWS 공식 권장 모드. 트래픽 패턴을 전혀 알 수 없는 신규 서비스, 예측 불가능한 스파이크 트래픽, 용량 계획에 엔지니어링 리소스를 쓰고 싶지 않을 때[2]트래픽이 꾸준하고 예측 가능한 애플리케이션, 월별 인프라 비용 예측성이 매우 중요할 때[2]
스케일링 동작완전 자동 확장. 트래픽 급증 시 즉시 용량을 늘리며, 유휴 시간대에는 0까지 축소되어 콜드 스타트 지연 없이 대기합니다.[1]Application Auto Scaling: 최소·최대 용량과 목표 사용률(보통 70%)을 지정하여 트래픽 추이에 따라 용량을 자동으로 조정합니다.[3]

용량 단위의 수학적 이해:
- 1 RCU (Read Capacity Unit): 최대 4 KB 크기의 항목에 대해 초당 1회의 강력히 일관된 읽기(Strongly Consistent Read), 또는 초당 2회의 최종적 일관된 읽기(Eventually Consistent Read)를 제공합니다. (기본 조회는 최종적 일관성입니다.)
- 1 WCU (Write Capacity Unit): 최대 1 KB 크기의 항목에 대해 초당 1회의 쓰기(Write)를 제공합니다.
※ 모드 전환: 프로비저닝에서 온디맨드로는 24시간 동안 최대 4회까지 전환할 수 있고, 온디맨드에서 프로비저닝으로는 언제든 즉시 전환할 수 있습니다.[3]

DAX (DynamoDB Accelerator): 마이크로초 지연 시간을 제공하는 전용 인메모리 캐시

Amazon DynamoDB Accelerator(DAX)는 DynamoDB 전용으로 설계된 완전관리형 인메모리 캐시 클러스터입니다. DynamoDB의 응답 시간을 기존 한 자릿수 밀리초(ms)에서 마이크로초(µs, 100만 분의 1초) 단위로 최대 10배 이상 단축시킵니다.[4]

  • 완벽한 API 호환성: 애플리케이션 소스 코드의 쿼리 로직을 새로 짤 필요 없이, DAX SDK 엔드포인트로 클라이언트만 교체하면 기존의 GetItem, BatchGetItem, Query 호출이 투명하게 캐시를 거칩니다.
  • 비용 절감 효과: 반복적으로 대량 조회되는 핫 키(Hot Key) 읽기 요청을 DAX 메모리가 흡수하므로, 기본 테이블의 읽기 용량(RCU)을 과도하게 증설할 필요가 없어 전체 인프라 비용을 아낄 수 있습니다.
  • 시험에 반드시 출제되는 부적합 사례 (오답 함정!):
    1. 강력히 일관된 읽기(Strongly Consistent Read)가 필수인 애플리케이션: DAX는 최종적 일관된 읽기만 캐싱합니다. 강력히 일관된 읽기 요청은 캐시를 거치지 않고 기본 DynamoDB 테이블로 그냥 통과(Pass-through)시켜 버립니다.[4]
    2. 쓰기 위주(Write-heavy)의 애플리케이션: DAX는 읽기 가속기입니다. 쓰기 작업은 DAX를 거쳐 기본 테이블에 기록되므로 쓰기 성능 향상에는 도움이 되지 않습니다.
    3. 캐시 적중률(Cache Hit Rate)이 낮은 애플리케이션: 동일한 데이터를 반복해서 읽지 않고 매번 다른 데이터를 조회하는 워크로드에서는 DAX의 캐시 이점이 없습니다 (적중률 90% 이상에서 최적).

글로벌 테이블, Streams, TTL, PITR: 엔터프라이즈 필수 기능 4대 천왕

  • 글로벌 테이블 (Global Tables): 완전관리형 다중 리전, 다중 활성(Active-Active) 복제 테이블입니다. 전 세계 어느 리전의 복제 테이블에 쓰기를 수행하든 다른 모든 리전으로 데이터가 자동 양방향 복제됩니다. 특정 주(Primary) 리전이 따로 없으므로 리전 재해 발생 시 복잡한 장애 조치(Failover) 절차 없이 다른 리전으로 트래픽만 라우팅하면 즉시 무중단 운영이 가능합니다.[5]
  • DynamoDB Streams: 테이블의 항목 수준 변경 사항(생성, 수정, 삭제)을 시간 순서대로 캡처하여 최대 24시간 동안 스트림 로그에 보관합니다. 변경 전 이미지와 변경 후 이미지를 모두 보존할 수 있습니다. 가장 전형적인 패턴은 AWS Lambda 함수를 스트림의 트리거로 연결하여, 신규 회원 가입 시 웰컴 메일 발송이나 외부 검색 엔진 동기화 같은 이벤트 기반 비동기 처리를 수행하는 것입니다.[6]
  • TTL (Time to Live): 항목마다 만료 시각(Unix Epoch 시간 단위 초, Number 타입)을 지정해 두면, 만료 시간이 지난 항목을 테이블의 쓰기 처리량(WCU)을 일절 소모하지 않고 무료로 백그라운드 자동 삭제해 주는 기능입니다.[7] 사용자 세션 관리, 임시 인증 토큰 정리, 접속 로그 파기 등에 필수입니다. (만료 후 실제 디스크에서 삭제되기까지 수일이 걸릴 수 있으므로, 엄격한 필터링이 필요할 때는 조회 쿼리에서 expiresAt > current_time 조건을 함께 사용합니다.)
  • PITR (Point-in-Time Recovery): 연속적인 자동 증분 백업을 수행하여 지난 최대 35일 이내의 어느 특정 초 단위 시점으로든 테이블을 새 테이블로 완벽 복원합니다. 프로비저닝된 처리량을 전혀 소모하지 않으며 운영 성능에도 아무런 영향을 주지 않습니다. 개발자의 실수로 인한 대량 데이터 삭제(DROP, DELETE) 사고에 대비하는 최고의 안전망입니다.[8]

Amazon ElastiCache: 어떤 캐시 엔진을 선택해야 할까?

Amazon ElastiCache는 Valkey, Memcached, Redis OSS 오픈소스 엔진을 지원하는 완전관리형 인메모리 데이터 스토어 및 캐시 서비스입니다. 용량 계획이 필요 없는 Serverless 모델과 노드 타입을 직접 선택하는 노드 기반 클러스터 모델을 지원합니다.[9]

캐시 전략: 지연 로딩(Lazy Loading) vs 라이트 스루(Write-Through)

비교 항목지연 로딩 (Lazy Loading / Cache-Aside)라이트 스루 (Write-Through)
동작 방식애플리케이션이 먼저 캐시를 조회합니다. 데이터가 있으면(Cache Hit) 바로 반환하고, 없으면(Cache Miss) 데이터베이스에서 직접 읽어와 캐시에 저장한 뒤 반환합니다.애플리케이션이 데이터베이스에 데이터를 쓸 때(INSERT/UPDATE), 캐시에도 동시에 동일한 데이터를 기록합니다.
핵심 장점실제 요청된 데이터만 캐시에 적재되므로 메모리 낭비가 없습니다. 캐시 노드가 장애로 다운되거나 재시작되어도 애플리케이션은 DB에서 데이터를 읽어오므로 서비스가 계속 동작합니다.캐시의 데이터가 데이터베이스와 항상 일치하므로 데이터가 절대 오래되지(Stale) 않습니다.
단점 및 한계캐시 미스 발생 시 3번의 네트워크 왕복(캐시 조회 → DB 조회 → 캐시 쓰기)으로 지연 시간이 발생합니다. DB가 직접 변경되면 캐시에 오래된 데이터가 남아 불일치가 발생할 수 있습니다.자주 읽히지 않는 데이터까지 캐시에 쓰이므로 불필요한 메모리 낭비(Cache Churn)가 발생합니다. 새 노드가 뜨면 캐시 미스가 발생하며, 쓰기 시 2번의 네트워크 쓰기가 필요합니다.

실무 아키텍처 베스트 프랙티스: 보통 지연 로딩을 기본으로 사용하되, 데이터에 적절한 TTL(Time to Live) 만료 시간을 부여하여 오래된 데이터가 캐시에 영구히 남아있는 것을 방지합니다. 또한 즉각적인 최신성이 필수인 데이터는 라이트 스루와 혼합하여 구성합니다.[11]

읽기 위주 vs 쓰기 위주, 그리고 세션 저장소와 순위표

  • 읽기 위주 워크로드: 캐시가 최고의 효과를 발휘합니다. DynamoDB 앞단이라면 DAX를, RDS나 Aurora 앞단이라면 ElastiCache(또는 읽기 전용 복제본)를 배치하여 부하를 분산합니다.
  • 쓰기 위주 워크로드: 캐시는 해결책이 아닙니다! 캐시에 아무리 써봤자 뒤단 DB로 결국 써야 하므로 병목이 풀리지 않습니다. DynamoDB의 쓰기 용량(WCU)을 확장하거나 온디맨드 모드로 전환하고, Kinesis나 SQS를 버퍼로 두어 쓰기 압력을 완화해야 합니다.
  • 무상태(Stateless) 세션 저장소: 여러 대의 EC2 웹 서버가 Auto Scaling으로 수시로 생성되고 종료될 때, 사용자 로그인 세션을 EC2 로컬 메모리에 저장하면 서버 종료 시 로그아웃이 발생합니다. 세션 데이터를 외부의 DynamoDB(영속적 NoSQL)나 ElastiCache(초저지연 인메모리)에 중앙 집중 저장하면 서버가 몇 대가 꺼져도 사용자 로그인이 완벽히 유지됩니다.[13]
  • 실시간 게임 순위표 (Leaderboard): Valkey / Redis OSS의 정렬 집합(Sorted Sets, ZSET)을 사용하면, 점수가 업데이트될 때마다 $O(\log N)$의 극히 빠른 속도로 순위가 즉시 재계산되어 수백만 명의 실시간 TOP 100 랭킹을 손쉽게 구현할 수 있습니다.[12]

시험에 자주 나오는 핵심 패턴

  • "트래픽 예측 불가, 신규 론칭, 용량 계획 불필요, 쓴 만큼만 과금" → DynamoDB 온디맨드 모드
  • "예측 가능하고 꾸준한 트래픽, 비용 최적화" → DynamoDB 프로비저닝 모드 + Auto Scaling
  • "DynamoDB 읽기 응답을 마이크로초(µs)로 단축, 코드 수정 최소화" → DAX (단, 강력히 일관된 읽기가 필수라면 DAX는 오답!)
  • "전 세계 여러 리전에서 활성 읽기 및 쓰기(Active-Active)", "리전 장애 조치" → DynamoDB 글로벌 테이블
  • "테이블 항목 변경 시 실시간 Lambda 실행" → DynamoDB Streams
  • "일정 기간 후 오래된 항목을 무료로 자동 삭제" → DynamoDB TTL (Time To Live)
  • "실수로 손상된 테이블을 35일 이내 특정 초 단위 시점으로 복구" → DynamoDB PITR (Point-in-Time Recovery)
  • "실시간 순위표(리더보드), 복잡한 자료구조, 고가용성 복제/장애조치, 백업/복원" → ElastiCache Valkey / Redis OSS
  • "단순 객체 캐싱, 대용량 멀티스레드 코어 활용" → ElastiCache Memcached
  • "캐시 데이터가 DB와 항상 최신 일치해야 함" → 라이트 스루 (Write-Through)
  • "실제 요청된 데이터만 효율적으로 캐싱, 캐시 장애 시에도 DB로 우회 동작" → 지연 로딩 (Lazy Loading)

연습

Q1. 한 초기 스타트업이 새로운 모바일 소셜 앱을 글로벌 시장에 론칭하려 합니다. 초기 사용자 유입량과 트래픽 패턴을 전혀 예측할 수 없으며, 개발팀은 인프라 용량 계획이나 프로비저닝 튜닝에 엔지니어링 시간을 쓰고 싶지 않습니다. DynamoDB 테이블을 생성할 때 선택해야 할 가장 적합한 용량 설정은 무엇입니까?

정답은 온디맨드 모드 선택입니다! 온디맨드 모드는 DynamoDB의 기본 권장 모드로, 사전 용량 계획 없이 유입되는 트래픽에 맞춰 자동으로 처리량을 확장/축소하며 실제 사용한 요청 수만큼만 비용을 지불합니다. 트래픽이 없으면 0원입니다. 높은 고정 RCU/WCU는 트래픽이 없어도 시간당 비용이 청구되어 낭비이며, 예약 용량은 패턴이 일정한 장기 워크로드용입니다. DAX는 읽기 캐시이므로 쓰기 용량 문제와 무관합니다.

Q2. 한 대규모 온라인 게임에서 수십만 명의 동시 접속자가 플레이어 프로필 정보를 DynamoDB에서 초당 수만 건씩 반복적으로 읽고 있습니다. 데이터베이스의 읽기 응답 지연 시간을 기존 한 자릿수 밀리초(ms)에서 마이크로초(µs) 수준으로 대폭 낮추어야 하며, 기존 애플리케이션의 쿼리 코드는 거의 수정하지 않아야 합니다. 최종적 일관성 읽기는 완전히 허용됩니다. 가장 적합한 아키텍처는 무엇입니까?

정답은 Amazon DAX 배포입니다! DAX는 DynamoDB와 100% API 호환되는 전용 인메모리 캐시로, 애플리케이션의 복잡한 캐싱 코드 재작성 없이 SDK 엔드포인트만 변경하면 최종적 일관된 읽기를 마이크로초(µs) 수준으로 가속해 줍니다. ElastiCache도 빠르지만 캐시 미스/적중 로직을 개발자가 애플리케이션 코드에 직접 구현해야 하므로 '코드 수정 최소화' 요건을 충족하지 못합니다. RCU를 늘려도 기본 지연 시간은 여전히 밀리초 수준입니다.

Q3. 한 글로벌 SaaS 기업이 북미, 유럽, 아시아 태평양에 거주하는 수백만 명의 사용자에게 각 대륙 현지 리전에서 로컬 수준의 초저지연 읽기 및 쓰기를 동시에 제공해야 합니다. 또한 특정 리전 전체에 장애가 발생하더라도 사용자 트래픽을 다른 대륙 리전으로 즉시 우회하여 중단 없이 비즈니스를 지속할 수 있어야 합니다. 가장 적합한 데이터베이스 솔루션은 무엇입니까?

정답은 DynamoDB 글로벌 테이블입니다! 글로벌 테이블은 전 세계 여러 리전에 걸친 다중 활성(Active-Active) 복제 테이블을 완전관리형으로 제공합니다. 사용자는 가장 가까운 리전에서 로컬 지연 시간으로 읽기와 쓰기를 모두 수행할 수 있으며, 특정 리전에 재해가 발생하면 Route 53 등을 통해 다른 리전으로 즉시 장애 조치(Failover)할 수 있습니다. DAX는 타 리전에서의 원격 쓰기 지연을 줄이지 못하며, Streams와 Lambda로 직접 양방향 복제를 구현하는 것은 극심한 운영 오버헤드를 유발합니다.

Q4. 한 웹 포털이 수백만 명의 로그인 세션 데이터를 Amazon DynamoDB 테이블에 보관하고 있습니다. 마지막 사용자 활동 후 24시간이 경과한 세션 데이터는 자동으로 테이블에서 영구 삭제되어야 하며, 이 대량 삭제 작업으로 인해 프로덕션 애플리케이션의 쓰기 용량(WCU) 비용이 청구되거나 테이블 성능에 악영향을 주어서는 안 됩니다. 가장 적합한 구현 방식은 무엇입니까?

정답은 DynamoDB TTL 활성화입니다! TTL은 각 항목의 만료 타임스탬프(Unix Epoch 초)를 평가하여 만료된 항목을 백그라운드에서 추가 비용 및 쓰기 용량(WCU) 소모 없이 무료로 자동 삭제합니다. 전체 Scan 후 DeleteItem을 실행하는 것은 대량의 읽기 및 쓰기 용량을 낭비하는 최악의 안티패턴입니다. PITR 기간과 Streams 보존 기간은 테이블 내부 항목의 삭제와 아무런 관련이 없습니다.

Q5. 인메모리 캐시 서비스를 도입할 때, Memcached 대신 Amazon ElastiCache for Valkey 또는 Redis OSS를 반드시 선택해야 하는 기술적 요구 사항 두 가지를 고르세요.

정답은 두 번째(고가용성 복제 및 자동 장애 조치)와 세 번째(정렬 집합을 활용한 리더보드)입니다!
Valkey / Redis OSS는 다중 가용 영역 복제와 자동 장애 조치를 지원하여 캐시 데이터의 가용성을 완벽히 보장하며, 정렬 집합(Sorted Sets)과 같은 고급 자료구조를 지원하여 실시간 순위표를 손쉽게 구축할 수 있습니다.
오답 분석: 멀티스레드 처리와 "가장 단순한 객체 캐시 모델"은 AWS 공식 가이드에서 Memcached를 선택해야 하는 결정적 이유로 제시하는 항목들입니다.

Q6. 한 쇼핑몰 애플리케이션이 상품 가격 정보를 Amazon ElastiCache에 캐싱하고 있습니다. 백엔드 데이터베이스에서 상품 가격이 변경되는 즉시, 캐시를 조회하는 모든 사용자는 절대로 오래된 이전 가격을 보아서는 안 되며 항상 최신 가격을 조회할 수 있어야 합니다. 이 엄격한 데이터 최신성 요구 조건을 가장 직접적으로 만족하는 캐싱 전략은 무엇입니까?

정답은 라이트 스루(Write-Through) 전략입니다! 라이트 스루는 애플리케이션이 DB에 데이터를 쓸 때 캐시에도 즉시 동일한 값을 기록하므로, 캐시 내부의 데이터가 데이터베이스와 항상 일치하여 데이터가 절대 오래되지(Stale) 않습니다. 반면 지연 로딩은 DB 값이 수정되어도 캐시를 즉시 갱신하지 않으므로 캐시에 오래된 가격이 남아 사용자에게 잘못된 정보가 노출되는 문제가 발생합니다.

Q7. (0021 복습) Amazon Aurora MySQL 클러스터를 운영 중인데, 주간 피크 시간대에는 읽기 쿼리가 폭증하고 심야 시간대에는 읽기 트래픽이 급감합니다. 피크 시에는 읽기 처리 성능을 자동으로 확장하고, 한가한 시간대에는 복제본을 줄여 클러스터 비용을 최적화할 수 있는 가장 적합한 메커니즘은 무엇입니까?

정답은 Aurora Auto Scaling 정책 적용입니다! Aurora는 CloudWatch CPU 사용률이나 연결 수 지표를 기반으로 Aurora 읽기 복제본(Reader)을 최대 15대까지 자동으로 추가하고 부하가 줄면 회수하는 Aurora Auto Scaling을 기본 지원합니다. RDS Proxy는 커넥션 풀링 서비스일 뿐 인스턴스를 스스로 생성하지 못하며, Multi-AZ 대기 인스턴스는 읽기 처리가 절대 불가능합니다.

Q8. 전자상거래 시스템의 주문 테이블(DynamoDB)에 새로운 주문 항목이 INSERT될 때마다, 고객에게 주문 확인 알림 톡을 발송하는 AWS Lambda 함수를 실행해야 합니다. 데이터베이스에 부하를 주는 주기적인 폴링(Polling) 없이 가장 단순하고 안정적인 이벤트 기반 아키텍처를 구현하는 방법은 무엇입니까?

정답은 DynamoDB Streams 활성화 및 Lambda 트리거 연결입니다! DynamoDB Streams는 항목의 생성, 수정, 삭제 이벤트를 실시간으로 기록하며, 이를 AWS Lambda의 이벤트 소스 매핑(Trigger)으로 연결하면 폴링 없이 변경 즉시 Lambda가 호출되어 비즈니스 로직(알림 발송 등)을 완벽히 실행합니다. 매분 전체 Scan은 극심한 비용과 부하를 유발하며, TTL은 만료 삭제 시점이므로 새 주문 접수와 완전히 무관합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속 기억만으로 정리해 보세요.
(1) DynamoDB에서 온디맨드 모드와 프로비저닝 모드를 선택하는 기준을 각각 설명해 보세요.
(2) DynamoDB Accelerator(DAX)를 도입하면 안 되는 대표적인 부적합 사례 2가지를 적어 보세요.
(3) 캐시 엔진으로 Memcached 대신 Valkey 또는 Redis OSS를 반드시 선택해야 하는 결정적 이유 3가지를 들어 보세요.
(4) 캐시 전략 중 지연 로딩(Lazy Loading)과 라이트 스루(Write-Through)의 가장 큰 단점을 각각 하나씩 설명해 보세요.

(1) 용량 모드 선택 기준:
- 온디맨드 모드: 트래픽을 예측할 수 없거나 스파이크가 심한 신규 서비스, 사용량 계획 없이 실제 요청 수만큼만 비용을 내고 싶을 때 (기본 권장, 유휴 시 0까지 축소).
- 프로비저닝 모드: 트래픽이 꾸준하고 예측 가능하여 사전에 용량을 할당하고 비용 예측성을 극대화하고자 할 때 (Application Auto Scaling과 병행 사용).

(2) DAX 부적합 사례 2가지:
- 강력히 일관된 읽기(Strongly Consistent Read)가 반드시 필요한 경우 (DAX는 최종적 일관된 읽기만 캐싱하며, 강력한 일관 읽기는 캐시 없이 기본 테이블로 통과).
- 쓰기 위주(Write-heavy) 워크로드 (DAX는 읽기 캐시이므로 쓰기 성능은 향상시키지 못함).

(3) Valkey / Redis OSS 선택 이유 3가지:
- 다중 AZ 복제 및 자동 장애 조치(Failover)를 통한 고가용성 확보.
- 정렬 집합(Sorted Sets), 해시, 리스트 등 풍부한 고급 자료구조 (실시간 게임 순위표 구현).
- 스냅샷을 통한 데이터 지속성 및 백업/복원 기능, 또는 Pub/Sub 메시징 지원.

(4) 캐시 전략의 단점:
- 지연 로딩: DB 데이터가 수정되어도 캐시가 즉시 갱신되지 않아 오래된(Stale) 데이터가 노출될 위험이 있고, 캐시 미스 시 3번의 왕복 지연 발생.
- 라이트 스루: 자주 읽히지 않을 데이터까지 무조건 캐시에 기록되므로 불필요한 캐시 메모리 낭비(Churn)가 발생하며, 쓰기 시 DB와 캐시 2번의 네트워크 지연 발생. (두 방식 모두 적절한 TTL을 부여하여 보완).

추가 학습 및 실습

1차 공식 문서 정독 (10분 투자): AWS ElastiCache 가이드의 "Caching strategies" 문서를 꼭 확인하세요. 지연 로딩, 라이트 스루, TTL의 실제 구현 의사 코드와 아키텍처 다이어그램이 매우 상세히 설명되어 있습니다.

실습 가이드 (상시 프리 티어 활용): AWS 콘솔에서 DynamoDB로 이동하여 온디맨드 테이블을 하나 생성해 보세요. DynamoDB는 매월 25GB 스토리지와 25 WCU/RCU(또는 2억 회 요청)의 상시 무료 티어를 제공하므로 비용 걱정 없이 실습할 수 있습니다.[1] 테스트 항목을 몇 개 넣고 TTL 속성(expiresAt)을 지정해 보거나 "내보내기 및 스트림" 탭에서 Streams 활성화 화면을 둘러보세요. (주의: DAX 및 ElastiCache 클러스터는 시간당 인스턴스 요금이 발생하므로 생성했다면 실습 직후 즉시 삭제해야 합니다.)
