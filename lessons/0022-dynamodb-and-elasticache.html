밀리초에서 마이크로초로:
DynamoDB와 ElastiCache

관계형이 아닌 두 축입니다. DynamoDB는 서버리스 키-값 데이터베이스, ElastiCache는 그 앞이나 RDS 앞에 놓는 인메모리 캐시입니다. 용량 모드, DAX, 글로벌 테이블, Streams/TTL/PITR, 그리고 캐시 전략 두 가지를 시험 키워드와 함께 정리합니다.

왜 이것부터인가

시험에서: "예측 불가한 트래픽" → 온디맨드, "마이크로초 읽기" → DAX, "다중 리전 쓰기" → 글로벌 테이블, "리더보드" → Valkey/Redis OSS 정렬 집합. 키워드만 알아도 절반은 풀립니다.
실무에서: 용량 모드 선택이 DynamoDB 비용을 좌우하고, 캐시 전략 선택이 데이터 신선도와 장애 시 동작을 좌우합니다.

DynamoDB 한 단락 요약

DynamoDB는 서버리스, 완전 관리형, 분산 NoSQL 데이터베이스로 규모와 무관하게 한 자릿수 밀리초 성능을 냅니다. 키-값과 문서 데이터 모델을 지원하고, 서버·버전·유지 관리 기간이 없습니다. JOIN은 지원하지 않으므로 데이터 모델을 비정규화하라고 권장합니다.[1] 기본적으로 데이터를 AZ 세 곳에 복제하며, 접근 제어는 사용자 이름·비밀번호가 아니라 IAM으로 합니다.[1]

용량 모드: 온디맨드 vs 프로비저닝

온디맨드프로비저닝
과금요청당 (사용한 만큼)프로비저닝한 시간당 용량 (실제 사용량 무관)
언제기본값이자 권장. 용량 계획이 필요 없음[2]예측 가능한 꾸준한 트래픽, 비용 예측성이 중요할 때[2]
확장자동. 트래픽이 없으면 0까지 축소, 콜드 스타트 없음[1]Auto Scaling: 최소·최대와 목표 사용률(권장 70%)을 정하면 Application Auto Scaling이 조정[3]

프로비저닝 단위: 1 RCU = 4 KB 이하 항목의 강력히 일관된 읽기 1회/초(또는 최종적 일관 읽기 2회/초), 1 WCU = 1 KB 이하 항목 쓰기 1회/초. 읽기는 기본이 최종적 일관성입니다. 프로비저닝 → 온디맨드 전환은 24시간에 최대 4번, 반대 방향은 언제든 가능합니다.[3]

DAX: DynamoDB 전용 캐시

DAX는 DynamoDB와 API 호환되는 인메모리 캐시로, 최종적 일관 읽기의 응답 시간을 한 자릿수 밀리초에서 마이크로초로 줄이며 기존 앱에 최소한의 변경만 필요합니다. 읽기 위주·버스트 워크로드에서 읽기 용량 과다 프로비저닝을 줄여 비용도 아낍니다.[4]

AWS가 명시한 부적합 사례: 강력히 일관된 읽기가 필요한 앱, 마이크로초가 필요 없는 앱, 쓰기 위주 앱, 반복 읽기가 적은 앱(캐시 적중률 90% 이상에서 최적).[4]

글로벌 테이블, Streams, TTL, PITR

  • 글로벌 테이블: 완전 관리형 다중 리전·다중 활성 복제. 어느 복제본이든 읽기와 쓰기를 모두 처리합니다. 일관성 모드는 기본값 MREC(다중 리전 최종적 일관성)와 MRSC(다중 리전 강력한 일관성)가 있고 생성 후 바꿀 수 없습니다.[5] 기본 주 테이블이 없어 리전 간 장애 조치가 복잡하지 않습니다.[1]
  • DynamoDB Streams: 항목 수준 변경을 시간 순서대로 최대 24시간 로그에 저장하고, 변경 전후 이미지를 담을 수 있습니다. Lambda 트리거로 이벤트 기반 처리를 합니다.[6]
  • TTL: 항목별 만료 시각(Unix epoch 초, Number 타입 속성)을 두면, 만료 후 보통 며칠 안에 쓰기 처리량을 소비하지 않고 자동 삭제합니다.[7] 만료 즉시 사라지는 것은 아니므로 조회 시 필터로 거릅니다.
  • PITR: 자동 연속 백업으로 최대 35일 안의 어느 초로든 복구합니다(기간은 1–35일 설정). 프로비저닝 용량을 쓰지 않고 성능에 영향이 없습니다. 장기 보관은 온디맨드 백업을 씁니다.[8][1]

ElastiCache: 어떤 엔진을 고를까

ElastiCache는 Valkey, Memcached, Redis OSS 엔진을 지원하는 관리형 인메모리 데이터 스토어/캐시이며, 용량 관리가 필요 없는 Serverless와 노드를 직접 고르는 노드 기반 클러스터 두 형태가 있습니다.[9]

필요한 것MemcachedValkey / Redis OSS
가장 단순한 모델, 객체 캐싱✓
멀티스레드 (큰 다중 코어 노드)✓✗
복잡한 데이터 타입 (정렬 집합, 해시, 리스트 등)✗ (단순)✓
복제를 통한 고가용성, 자동 장애 조치✗✓
백업·복원 (노드 기반 클러스터)✗✓
Pub/Sub, 지리 공간 인덱스✗✓

표 출처: ElastiCache 엔진 비교 페이지.[10] 시험 수준 요약: 고급 기능이나 가용성이 하나라도 필요하면 Valkey/Redis OSS, 단순·멀티스레드·수평 확장이면 Memcached.

캐시 전략: 지연 로딩 vs 라이트 스루

지연 로딩 (lazy loading)라이트 스루 (write-through)
동작캐시 조회 → 없으면 DB에서 읽어 캐시에 씀DB에 쓸 때마다 캐시도 갱신
장점요청된 데이터만 캐싱. 노드가 죽어도 지연만 늘고 앱은 동작캐시 데이터가 절대 오래되지 않음
단점캐시 미스 시 왕복 3번. 오래된(stale) 데이터새 노드에 데이터 누락. 읽히지 않을 데이터로 캐시 낭비(churn). 쓰기마다 왕복 2번

두 방식을 함께 쓰고 TTL을 더하면 각각의 장점을 얻으면서 캐시가 쓸데없는 데이터로 차는 것을 줄일 수 있습니다.[11] 캐싱 후보는 느리거나 비싼 쿼리(여러 테이블 조인 등), 자주 읽히고 잘 바뀌지 않는 데이터입니다.[12]

읽기 위주 vs 쓰기 위주, 그리고 세션 저장소

  • 읽기 위주: 반복 읽기를 캐시로 흡수합니다. DynamoDB 앞이면 DAX, RDS/Aurora 앞이면 ElastiCache(또는 0021의 읽기 전용 복제본).[4]
  • 쓰기 위주: 캐시는 해결책이 아닙니다. DAX는 쓰기 위주 앱에 부적합하다고 명시되어 있고,[4] 쓰기 처리량 자체를 늘려야 합니다(DynamoDB 용량 모드·Auto Scaling 등).
  • 세션 저장소: AWS 선택 가이드는 DynamoDB의 대표 용도로 세션 저장소·장바구니를, 마이크로초 지연이 필요한 실시간 앱(캐싱, 세션 저장소, 리더보드)에 인메모리 서비스를 꼽습니다.[13] 핵심은 세션을 EC2 인스턴스 밖에 두어 Auto Scaling으로 인스턴스가 사라져도 로그인이 유지되게 하는 것입니다.
  • 리더보드: Valkey/Redis OSS의 정렬 집합이 순위 계산을 클러스터로 옮겨 줍니다.[12]

시험 단골: 키워드 → 정답

  • "예측 불가", "새 앱", "용량 계획 없이" → DynamoDB 온디맨드. "꾸준하고 예측 가능", "비용 예측" → 프로비저닝 + Auto Scaling.
  • "DynamoDB 읽기를 마이크로초로", "코드 변경 최소" → DAX. 단 "강력히 일관된 읽기"가 조건이면 DAX는 오답.
  • "여러 리전에서 읽기·쓰기", "다중 활성" → 글로벌 테이블.
  • "항목 변경 시 Lambda 실행" → Streams. "오래된 항목 자동 삭제, 비용 없이" → TTL. "실수로 지운 데이터 복구" → PITR.
  • "리더보드", "Pub/Sub", "복제·장애 조치" → Valkey/Redis OSS. "단순, 멀티스레드" → Memcached.
  • "캐시가 항상 최신" → 라이트 스루. "요청된 것만 캐싱, 노드 장애에 강함" → 지연 로딩.

연습

Q1. 스타트업이 새 모바일 앱을 출시합니다. 트래픽 패턴을 전혀 예측할 수 없고, 팀은 용량 계획에 시간을 쓰고 싶지 않습니다. DynamoDB 테이블에 가장 적합한 설정은?

온디맨드는 기본값이자 권장 모드로 용량 계획 없이 자동 확장하고 쓴 만큼만 냅니다. 높은 고정 용량은 쓰지 않아도 시간당 과금되고, 예약 용량은 예측 가능한 꾸준한 사용에 맞습니다. DAX는 읽기 캐시라 쓰기 용량 문제를 풀지 않습니다.

Q2. 게임 서비스가 DynamoDB에서 같은 플레이어 프로필을 초당 수만 번 읽습니다. 읽기 지연을 마이크로초 수준으로 낮추고 애플리케이션 코드 변경은 최소화해야 합니다. 최종적 일관성은 허용됩니다.

DAX는 DynamoDB와 API 호환이라 변경이 최소이고, 최종적 일관 읽기를 마이크로초로 줄입니다. ElastiCache도 빠르지만 캐시 로직을 직접 짜야 하므로 "코드 변경 최소"를 못 맞춥니다. 용량을 늘려도 밀리초 수준은 그대로입니다.

Q3. 글로벌 SaaS가 미국·유럽·아시아 사용자 모두에게 로컬 지연의 읽기와 쓰기를 제공하고, 한 리전이 중단되면 트래픽을 다른 리전으로 옮겨야 합니다. 가장 적합한 것은?

글로벌 테이블은 다중 활성이라 어느 리전 복제본이든 읽기·쓰기를 처리하고, 직접 복제 솔루션을 만들 필요가 없습니다. DAX는 쓰기를 로컬로 만들지 못하고, PITR 복원은 장애 대응이 느립니다. Streams로 직접 만드는 것은 운영 부담이 큽니다.

Q4. 웹 앱이 사용자 세션을 DynamoDB에 저장합니다. 마지막 활동 후 24시간이 지난 세션은 자동으로 지워져야 하며, 삭제 작업에 쓰기 용량 비용을 쓰고 싶지 않습니다.

TTL은 항목별 만료 시각(epoch 초)이 지나면 쓰기 처리량을 소비하지 않고 자동 삭제합니다(보통 며칠 안). Scan+삭제는 읽기·쓰기 용량을 모두 씁니다. PITR 기간과 Streams 보존 기간은 테이블 항목 삭제와 무관합니다.

Q5. 캐시 엔진으로 Memcached 대신 Valkey 또는 Redis OSS를 선택해야 하는 요구 사항은? (두 개를 고르세요)

복제·자동 장애 조치와 정렬 집합 같은 복잡한 데이터 타입은 Valkey/Redis OSS에만 있습니다. 멀티스레드와 "가장 단순한 모델"은 AWS가 Memcached를 고를 이유로 꼽는 항목입니다.

Q6. 상품 가격을 ElastiCache에 캐싱합니다. 가격이 DB에서 바뀌면 그 직후의 캐시 조회도 반드시 새 가격을 돌려줘야 합니다. 어떤 캐시 전략이 이 요구에 가장 직접적으로 맞나요?

라이트 스루는 DB에 쓸 때마다 캐시를 갱신하므로 캐시 데이터가 오래되지 않습니다. 지연 로딩은 DB가 바뀌어도 캐시를 갱신하지 않아 stale 데이터가 남는 것이 대표 단점입니다. 비동기 읽기 전용 복제본도 지연이 있을 수 있습니다.

Q7. (0021 복습) Aurora MySQL 클러스터의 읽기 부하가 하루 중 크게 출렁입니다. 피크에는 리더를 늘리고 한가할 때는 줄여 비용을 아끼려면?

Aurora Auto Scaling은 CloudWatch 지표와 목표값에 따라 Aurora 복제본(리더) 수를 늘리고 줄입니다. RDS Proxy는 연결 풀링이지 인스턴스를 만들지 않습니다. 참고로 RDS(비 Aurora) 읽기 전용 복제본은 자동 확장이 없습니다.

Q8. 주문 테이블(DynamoDB)에 새 주문 항목이 들어올 때마다 확인 이메일을 보내는 Lambda 함수를 실행해야 합니다. 폴링 없이 가장 간단한 방법은?

Streams는 항목 생성·수정·삭제를 시간 순서대로 기록하고, Lambda 트리거가 이 변경에 자동으로 반응합니다. 매분 Scan은 비싸고 지연이 있습니다. TTL은 삭제 시점이라 새 주문과 무관합니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) 온디맨드와 프로비저닝을 언제 쓰나? (2) DAX가 맞지 않는 경우 두 가지. (3) Memcached 대신 Valkey/Redis OSS를 고를 이유 세 가지. (4) 지연 로딩과 라이트 스루의 단점 하나씩.

(1) 온디맨드: 기본·권장, 예측 불가, 요청당 과금, 0까지 축소. 프로비저닝: 꾸준하고 예측 가능, 시간당 과금, Auto Scaling(목표 사용률)과 함께.

(2) 강력히 일관된 읽기가 필요한 앱, 쓰기 위주 앱 (그 밖에 반복 읽기가 적은 앱, 마이크로초가 필요 없는 앱).

(3) 복제·자동 장애 조치, 정렬 집합 등 복잡한 데이터 타입, Pub/Sub, 백업·복원, 지리 공간 인덱스.

(4) 지연 로딩: stale 데이터, 미스 시 왕복 3번. 라이트 스루: 새 노드의 데이터 누락, 안 읽힐 데이터로 캐시 낭비. 둘 다 TTL로 보완.
