앞선 레슨 0014가 컴포넌트 사이를 떼어 놓는 비동기 결합이었다면, 이번 레슨에서는 외부 클라이언트의 요청을 가장 먼저 맞이하는 앞문(API Gateway), 여러 단계의 마이크로서비스 작업을 순서대로 오케스트레이션하는 지휘자(Step Functions), 그리고 동일한 연산이나 조회를 반복하지 않도록 시스템 부하를 획기적으로 줄여주는 캐싱(Caching) 전략을 배웁니다. 시험에서는 "REST API와 HTTP API의 기능 차이", "Step Functions 워크플로 유형(Standard vs Express)의 선택", "요청 경로의 3단계 캐시 계층 배치"를 묻는 문제가 집중 출제됩니다.

왜 API Gateway와 Step Functions를 배워야 할까요?

  • 시험 관점: "REST API와 HTTP API 중 무엇을 골라야 하는가", "Standard 워크플로와 Express 워크플로 중 어떤 유형이 적합한가", "시스템 병목을 줄이기 위해 캐시를 어느 계층에 두어야 하는가"와 같은 질문은 보기 4개가 모두 정상 동작하는 것처럼 보여 수험생들이 가장 많이 헷갈리는 영역입니다. 서비스별 고유한 제약과 판단 기준을 명확히 정리해 두어야 오답 함정을 피할 수 있습니다.
  • 실무 관점: 현대 서버리스 아키텍처의 기본 골격은 'API Gateway → AWS Lambda'입니다. 하지만 주문 결제, 재고 차감, 배송 요청, 관리자 승인과 같이 여러 단계를 거치는 복잡한 비즈니스 로직을 단 하나의 Lambda 함수 안에 모놀리식으로 작성하거나 여러 함수를 동기식으로 무리하게 이어 붙이면, 중간 장애 시 보상 트랜잭션 실패와 타임아웃 오류가 발생합니다. Step Functions를 도입하면 시각적인 워크플로 상태 머신으로 장애 복구와 재시도를 완벽히 자동화할 수 있습니다.

한눈에 비교하기: API Gateway의 두 가지 모델 (REST API vs HTTP API)

Amazon API Gateway는 개발자가 RESTful API와 WebSocket API를 손쉽게 생성, 게시, 유지 관리, 모니터링할 수 있게 해주는 완전 관리형 서비스입니다. RESTful API를 만들 때는 풍부한 엔터프라이즈 기능을 제공하는 REST API와, 핵심 기능에 집중하여 지연 시간을 줄이고 비용을 대폭 낮춘 HTTP API 중 하나를 선택해야 합니다.[1]

REST API의 3대 엔드포인트 유형 상세

  • 엣지 최적화(Edge-optimized): 전 세계에 분산된 CloudFront Edge Location(POP)을 통해 클라이언트 요청을 수신하여 AWS 백본 네트워크를 타고 API Gateway로 라우팅합니다. 전 세계 여러 대륙에 흩어져 있는 지리적 분산 사용자에게 최적의 짧은 왕복 지연 시간을 제공하며, REST API 생성 시의 기본값입니다.[2]
  • 리전(Regional): API Gateway가 배포된 동일한 AWS 리전 내의 클라이언트(예: 같은 리전의 EC2, ECS, 웹 프론트엔드)를 주 대상으로 합니다. 자체적인 CloudFront 배포를 직접 구성하여 API 앞단에 붙이고 세부 캐싱 정책을 제어하고자 할 때도 리전 엔드포인트를 선택합니다.[2]
  • 프라이빗(Private): 인터넷 공용망에 API를 일체 공개하지 않고, 오직 내부 VPC 안에서 인터페이스 VPC 엔드포인트(AWS PrivateLink)를 통해서만 안전하게 호출할 수 있는 내부 전용 비공개 엔드포인트입니다.[2]

API Gateway의 요청 제어: 스로틀링(Throttling)

API Gateway는 백엔드 시스템(Lambda, 내부 DB 등)이 트래픽 폭주로 마비되는 것을 막기 위해 토큰 버킷(Token Bucket) 알고리즘을 사용하여 지속적인 요청 속도(RPS)와 순간적인 폭발 요청량(Burst)을 정밀하게 제어합니다. 허용된 한도를 초과하여 유입된 요청에 대해 API Gateway는 백엔드를 호출하지 않고 클라이언트에게 즉시 429 Too Many Requests HTTP 상태 코드를 반환합니다.[3]

스로틀링 한도는 가장 좁고 세분화된 범위부터 순차적으로 평가됩니다: (1) 사용량 계획의 클라이언트/API 키별 한도 → (2) 스테이지 내 메서드별 한도 → (3) 계정 전체 리전 기본 한도 (초당 10,000건, 버스트 5,000건) 순으로 적용됩니다.[4]

Lambda 프록시 통합과 29초 타임아웃 제한

Lambda 프록시 통합(Lambda Proxy Integration)은 가장 보편적으로 사용되는 통합 방식으로, API Gateway가 클라이언트의 HTTP 요청 전체(헤더, 쿼리 파라미터, 경로 변수, 바디, 인증 컨텍스트 등)를 가공 없이 단일 JSON 객체로 묶어 Lambda 함수의 이벤트 파라미터로 그대로 전달합니다. 이때 Lambda 함수는 반드시 약속된 정해진 JSON 규격(statusCode, headers, body 필드)으로 응답해야 하며, 응답 형식이 어긋나면 API Gateway는 클라이언트에게 502 Bad Gateway 에러를 반환합니다.[7]

결정적 제약: 통합 시간 제한(29초): API Gateway REST API의 백엔드 통합 시간 제한(Integration Timeout)은 최대 29초입니다 (엣지 최적화 API는 증설 불가).[6] 비디오 트랜스코딩이나 대용량 데이터 분석처럼 29초 이상 걸리는 무거운 작업을 동기식 API 뒤에 그대로 두면 504 Gateway Timeout이 발생합니다. 따라서 긴 작업은 동기 호출을 피하고, API Gateway가 요청을 SQS 큐에 넣거나 Step Functions 상태 머신을 비동기 실행시킨 뒤 클라이언트에게는 202 Accepted 접수 확인 응답을 즉시 돌려주는 비동기 분리 패턴을 구축해야 합니다. (API Gateway는 Lambda 외에도 SQS, SNS, DynamoDB 등 다양한 AWS 서비스와 직접 통합할 수 있습니다.[1])

핵심 특징: Step Functions 워크플로 오케스트레이션 (Standard vs Express)

AWS Step Functions는 분산된 여러 마이크로서비스와 서버리스 함수들을 시각적인 상태 머신(State Machine)으로 엮어주는 워크플로 오케스트레이션 서비스입니다. 각 단계를 '상태(State)'로 정의하며, Task(Lambda 호출, ECS 작업 실행 등), Choice(데이터 조건에 따른 분기), Retry/Catch(지수 백오프 기반 재시도 및 실패 시 대체 경로), Parallel(동시 병렬 실행), Map(동적 컬렉션 배열 처리) 등의 강력한 빌트인 기능을 제공합니다.[8] 복잡한 오류 처리와 재시도 로직을 함수 코드에서 완전히 분리해 낼 수 있다는 점이 핵심입니다.

Lambda 함수의 단일 타임아웃은 최대 15분(900초)이며[10], SQS 가시성 제한 시간도 최대 12시간입니다.[14] 따라서 15분을 넘거나 며칠 이상 지속되는 복잡한 비즈니스 프로세스는 단일 함수나 단순 큐로 해결할 수 없으며, 반드시 Step Functions Standard 워크플로로 잘게 쪼개어 오케스트레이션해야 합니다.

캐싱 전략: 요청 경로의 3대 캐시 계층 (어느 계층에 둘 것인가?)

시스템의 응답 지연을 낮추고 백엔드 데이터베이스의 부하를 덜어주기 위해, 요청이 이동하는 네트워크 경로의 각 지점에 캐시를 배치할 수 있습니다.

캐시 계층무엇을 캐시하는가핵심 특징 및 주의사항
Amazon CloudFront전 세계 사용자에게 정적 웹 에셋(HTML, CSS, JS, 이미지, 미디어) 및 캐시 가능한 동적 웹 콘텐츠를 최전선에서 제공전 세계 수백 개 이상의 엣지 로케이션에 사본을 캐시하여 오리진(S3, ALB) 서버의 대역폭과 부하를 극적으로 절감. 기본 TTL은 24시간.[11]
API Gateway 캐시특정 배포 스테이지의 REST API 엔드포인트 응답 결과를 캐시REST API에서만 지원 (HTTP API 미지원). TTL 기본값 300초(5분), 최대 3,600초(1시간). 기본적으로 GET 메서드 응답만 캐시됨. 주의: 프로비저닝된 캐시 메모리 크기(0.5 GB~237 GB)에 따라 시간당 요금이 상시 부과되므로 프리 티어가 아닙니다.[5]
Amazon ElastiCache
(Redis / Memcached)		자주 실행되는 비싼 관계형 DB 쿼리 결과, 사용자 인증 세션, 실시간 리더보드 데이터초당 수백만 건의 읽기/쓰기를 서브 밀리초(1ms 미만)의 극도로 짧은 지연 시간으로 제공하는 인메모리 캐시. 데이터베이스 바로 앞단에 위치하여 DB 읽기 부하를 대폭 줄임.[12] (자세한 내용은 레슨 0022에서 다룸)

무엇을 캐시해야 할까? AWS 공식 권장 질문 3가지:[12] (1) 데이터를 원본에서 가져오는 데 많은 시간과 비용이 드는가? (2) 데이터가 여러 사용자에게 빈번하게 반복 조회되는가? (3) 약간 오래된(Stale) 데이터가 일시적으로 반환되어도 비즈니스상 허용되는가?

상태 비저장(Stateless) 아키텍처와 세션 외부화

AWS Well-Architected 신뢰성 원칙(REL05-BP06)에서는 "개별 요청 처리 시 특정 가상 서버의 로컬 메모리나 로컬 디스크에 존재하는 상태 데이터에 의존하지 말 것"을 강력히 권고합니다.[13]
사용자의 로그인 세션 정보를 웹 서버의 로컬 메모리에 저장하면, Auto Scaling 그룹이 트래픽 감소로 인스턴스를 축소(Scale-in)하여 종료하거나 인스턴스 하드웨어에 고장이 발생했을 때, 해당 서버에 연결되어 있던 사용자들이 강제로 로그아웃되는 심각한 사용자 경험 저하가 발생합니다. 세션 정보를 서버 밖의 Amazon ElastiCache나 Amazon DynamoDB와 같은 외부 고가용성 인메모리/NoSQL 저장소로 분리(세션 외부화)하면, 모든 웹 서버가 완벽한 **상태 비저장(Stateless)**이 되어 어느 서버든 모든 요청을 자유롭게 처리할 수 있으며, 무중단 오토 스케일링과 완벽한 내결함성이 달성됩니다.

  • "여러 단계의 비즈니스 로직 + 재시도/대체 경로 + 사람의 승인 대기 + 90일 실행 이력 감사", "15분 이상 실행" → Step Functions Standard 워크플로
  • "초당 수천~수만 건의 대량 이벤트 수집", "짧은 실행 시간", "비용 최소화", "멱등성 보장" → Step Functions Express 워크플로
  • "전 세계 사용자의 정적 웹 에셋 다운로드 지연 단축" → Amazon CloudFront 엣지 캐시
  • "동일한 복잡한 DB 쿼리 반복 호출로 인한 데이터베이스 병목 해결" → Amazon ElastiCache 인메모리 캐시
  • "Auto Scaling 축소(Scale-in) 시 사용자 로그인 세션이 끊김" → 세션을 ElastiCache 또는 DynamoDB로 외부화하여 상태 비저장(Stateless) 웹 계층 구축
  • "API Gateway 뒤 백엔드가 29초 타임아웃 제한에 걸림" → API Gateway에서 SQS 큐로 요청을 즉시 버퍼링하거나 Step Functions 비동기 호출 후 202 응답 반환

연습

Q1. 회사가 외부 파트너에게 API를 공개합니다. 파트너마다 API 키를 발급하고, 파트너별로 초당 요청 수와 월 할당량을 다르게 제한해야 합니다. 어떤 구성이 맞습니까?

정답은 REST API에 API 키와 사용량 계획(Usage Plan)을 구성하는 것입니다. API 키 발급 및 고객/파트너별로 초당 요청 속도(Rate)와 월간 총 할당량(Quota)을 세분화하여 차등 제한하는 기능은 오직 API Gateway REST API에서만 제공됩니다. HTTP API는 가격이 더 저렴하지만 API 키와 사용량 계획 기능을 아예 지원하지 않으며, JWT 권한 부여자는 인증용일 뿐 파트너별 사용량을 제한하지 못합니다.

Q2. 할인 행사 중 API Gateway를 호출하는 일부 클라이언트가 429 Too Many Requests를 받았습니다. 백엔드 Lambda에는 오류가 없습니다. 무엇이 일어난 것입니까?

정답은 요청이 스로틀링의 속도와 버스트 한도를 초과한 것입니다. HTTP 상태 코드 429 Too Many Requests는 API Gateway에 설정된 토큰 버킷의 요청 속도(RPS) 또는 버스트 한도를 초과하여 API Gateway 서비스 자체에서 클라이언트의 호출을 차단했음을 의미합니다. Lambda 통합 시간 초과는 504, 권한 부여자 토큰 거부는 401/403, 프록시 응답 규격 불일치는 502 에러로 나타납니다.

Q3. REST API의 GET /products가 전체 호출의 90%를 차지하며 매번 같은 카탈로그를 Lambda가 DB에서 읽어 반환합니다. 카탈로그는 몇 분 늦게 반영돼도 괜찮습니다. 코드 변경 없이 Lambda 호출과 지연을 줄이는 방법은?

정답은 해당 스테이지에 API 캐싱을 켜고 TTL을 설정하는 것입니다. API Gateway REST API의 배포 스테이지에서 API 캐싱을 활성화하면, 동일한 GET 요청에 대한 응답 결과를 TTL(기본 300초) 동안 캐시 메모리에 보관합니다. 캐시가 적중(Cache Hit)하는 동안에는 백엔드 Lambda와 DB가 아예 호출되지 않으므로 코드 수정 없이 지연 시간을 대폭 단축하고 백엔드 비용을 크게 절감할 수 있습니다. HTTP API에는 내장 캐싱 기능이 지원되지 않습니다.

Q4. (0013 복습 포함) 주문 처리는 결제 → 재고 차감 → 배송 요청 순서이며, 고액 주문은 담당자 승인을 받느라 길게는 며칠 걸립니다. 단계별 재시도와 실패 시 보상 처리, 실행 이력 감사가 필요합니다. 가장 적합한 것은?

정답은 Step Functions Standard 워크플로로 구성하는 것입니다. Standard 워크플로는 최대 1년까지 워크플로를 유지할 수 있으며, 결제와 같은 금융 트랜잭션에 필수적인 '정확히 한 번(Exactly-once)' 실행을 보장합니다. 또한 작업 토큰(.waitForTaskToken)을 통해 관리자의 승인이 올 때까지 수일간 안전하게 대기할 수 있고, 90일간의 상세 실행 이력을 콘솔에서 시각적으로 추적 및 감사할 수 있습니다. 반면 Express 워크플로는 최대 실행 시간이 5분으로 제한되고 콜백 토큰 패턴을 지원하지 않으며, 단일 Lambda 함수는 최대 15분 타임아웃 제한으로 인해 며칠간 대기하는 워크플로를 구현할 수 없습니다.

Q5. IoT 장치에서 하루 수백만 건의 이벤트가 들어오고, 이벤트마다 몇 초 안에 끝나는 변환 후 DynamoDB에 PUT하는 짧은 워크플로를 실행합니다. 비용 효율이 중요합니다. 올바른 선택은? (두 개를 고르세요)

정답은 Express 워크플로로 새 상태 머신을 생성한다와 재실행돼도 안전하게 각 단계를 멱등하게 설계해 둔다입니다. 초당 수천 건 이상 대량으로 발생하는 단시간(수 초 이내) 이벤트 처리에는 Step Functions Express가 가장 비용 효율적입니다. Standard는 상태 전환마다 과금되어 대량 이벤트 시 비용이 매우 커지지만, Express는 실행 횟수와 실행 시간/메모리 기준으로 과금되기 때문입니다. 또한 비동기 Express 워크플로는 최소 한 번 이상(At-least-once) 실행 모델이므로 동일 이벤트가 재실행될 가능성이 있으므로 각 단계가 멱등성을 갖도록 설계해야 합니다. Express에서는 .waitForTaskToken 콜백이 지원되지 않습니다.

Q6. ALB 뒤 Auto Scaling 그룹의 EC2 웹 서버들이 로그인 세션을 각 인스턴스 메모리에 저장합니다. 축소 이벤트 때마다 일부 사용자가 로그아웃됩니다. 가장 적절한 해결책은?

정답은 세션을 ElastiCache로 옮겨 상태 비저장(Stateless)화하는 것입니다. 웹 서버의 로컬 메모리에 사용자 세션을 저장하면 인스턴스 종료 시 세션이 소멸됩니다. 세션 데이터를 Redis/Memcached 기반의 ElastiCache나 DynamoDB 같은 중앙화된 외부 저장소로 분리하면, 웹 서버는 완전한 상태 비저장(Stateless)이 되어 어떤 인스턴스가 종료되거나 교체되더라도 사용자의 로그인 세션이 끊기지 않고 안정적으로 유지됩니다.

Q7. 서울 리전의 S3에 있는 이미지·JS 파일을 유럽과 미국 사용자가 느리게 받는다고 합니다. 오리진 부하도 줄이고 싶습니다. 가장 적합한 것은?

정답은 CloudFront 배포를 만들고 S3를 오리진으로 설정하는 것입니다. Amazon CloudFront는 전 세계 수백 개 엣지 로케이션을 보유한 글로벌 CDN 서비스입니다. 해외 사용자가 정적 웹 에셋을 요청하면 지리적으로 가장 가까운 엣지 로케이션에서 캐시된 사본을 밀리초 단위로 응답하므로 전송 지연이 극적으로 줄어들며, 오리진인 서울 리전 S3 버킷으로의 직접 요청도 대폭 감소합니다. ElastiCache는 데이터베이스 앞단의 인메모리 캐시이므로 글로벌 정적 파일 배포에 사용되지 않습니다.

Q8. (0014 복습) API Gateway 뒤의 백엔드가 주문 폭주를 감당하지 못합니다. 클라이언트에게는 "접수됨"만 즉시 돌려주고, 주문은 백엔드가 감당할 속도로 처리하면 됩니다. 운영 부담이 가장 적은 방법은?

정답은 API Gateway에서 SQS로 넣고 작업자가 처리하도록 비동기 결합하는 것입니다. API Gateway는 중간에 Lambda 코드 없이도 AWS SQS 서비스와 직접 통합(Service Integration)하여 수신한 요청을 큐에 바로 적재할 수 있습니다. 클라이언트에게는 200 OK 또는 202 Accepted를 즉각 반환하고, 백엔드 작업자 풀은 데이터베이스가 감당할 수 있는 안정적인 속도로 큐의 주문을 소비합니다. REST API의 통합 제한 시간(29초)을 늘리는 것은 불가능하거나 문제를 근본적으로 해결하지 못합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 기억을 떠올려 직접 정리해 보세요. (1) API Gateway REST API에만 있고 HTTP API에는 없는 대표적인 기능 5가지는 무엇인가요? (2) Step Functions의 Standard 워크플로와 Express 워크플로의 4대 차이점(최대 실행 시간, 실행 보장 모델, 요금 체계, 콜백 토큰 지원 여부)은 무엇인가요? (3) CloudFront, API Gateway 스테이지 캐시, ElastiCache의 세 캐시 계층을 배치 목적에 따라 구분해 보세요.

(1) REST API 전용 기능: API 키 및 사용량 계획(클라이언트별 스로틀링·할당량), API 스테이지 캐싱, AWS WAF 보안 통합, 요청 유효성 검증(Request Validation), 프라이빗/엣지 최적화 엔드포인트 지원 (HTTP API는 리전 전용이자 네이티브 JWT 지원).

(2) Standard vs Express: 최대 실행 시간(Standard: 최대 1년 vs Express: 최대 5분), 실행 보장(Standard: 정확히 한 번 / Exactly-once vs Express 비동기: 최소 한 번 / At-least-once → 멱등성 필수), 과금 기준(Standard: 상태 전환 횟수당 과금 vs Express: 실행 수·시간·메모리 기준 과금), 콜백 기능(Standard: .waitForTaskToken 지원 vs Express: 미지원).

(3) CloudFront: 전 세계 사용자에게 가장 가까운 엣지에서 정적/동적 웹 에셋 배포. API Gateway 스테이지 캐시: REST API 엔드포인트의 반복되는 GET 응답 캐시(TTL 기본 300초, 시간당 유료). ElastiCache: 관계형 데이터베이스 앞단에서 복잡한 쿼리 결과 및 사용자 로그인 세션(상태 비저장 아키텍처)을 서브 밀리초로 제공하는 인메모리 캐시.

추가 학습 및 실습

1차 공식 문서 (권장 읽기, 약 10분): AWS Step Functions 공식 개발자 가이드의 "Choosing workflow type in Step Functions" 문서를 꼭 확인하세요. Standard와 Express의 비교표는 자격증 시험에 직접 출제되는 핵심 요약본입니다. 시간 여유가 있다면 API Gateway의 "Choose between REST APIs and HTTP APIs" 문서도 함께 훑어보시길 권장합니다. (한국어 번역본은 URL의 docs.aws.amazon.com/ 뒤에 ko_kr/를 추가하면 열람 가능합니다.)

핸즈온 실습 (선택, 프리 티어 범위): Step Functions 콘솔에서 기본 샘플 템플릿(예: Catch failure 패턴)을 선택하여 Standard 상태 머신을 하나 생성해 보세요. 콘솔에서 "실행 시작(Start Execution)"을 누르고, 시각적 워크플로 그래프 뷰에서 각 단계의 성공/실패 색상 변화와 상태별 입력/출력 JSON 데이터가 어떻게 흘러가는지 직접 관찰해 보십시오. (주의: API Gateway 캐싱 기능은 프리 티어가 아니며 시간당 상시 과금되므로, 실습할 경우 테스트 후 즉시 비활성화해야 합니다.)
