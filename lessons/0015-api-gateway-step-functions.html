API의 앞문과 작업의 지휘자:
API Gateway, Step Functions, 캐싱 전략

0014가 구성 요소 사이를 떼어 놓는 법이었다면, 오늘은 바깥 요청을 받는 앞문(API Gateway), 여러 단계를 순서대로 엮는 지휘자(Step Functions), 그리고 같은 일을 반복하지 않게 하는 캐시를 어디에 둘지 고릅니다.

왜 이것부터인가

  • 시험에서: "REST API냐 HTTP API냐", "Standard냐 Express냐", "캐시를 어느 계층에"는 보기 네 개가 모두 그럴듯해 보이는 유형입니다. 판단 기준 몇 개만 외우면 갈립니다.
  • 실무에서: 서버리스 백엔드의 기본 골격이 API Gateway → Lambda이고, 여러 Lambda를 이어 붙이는 순간 Step Functions가 필요해집니다.

API Gateway: REST API vs HTTP API

둘 다 RESTful API 제품입니다. REST API는 기능이 많고, HTTP API는 기능을 줄여 더 낮은 가격에 제공됩니다. AWS 문서의 기준은 간단합니다. API 키, 클라이언트별 스로틀링, 요청 검증, AWS WAF 통합, 프라이빗 엔드포인트가 필요하면 REST API, 아니면 HTTP API입니다.[1]

표 전체 출처: Choose between REST APIs and HTTP APIs [1]

엔드포인트 유형: 엣지 최적화는 가장 가까운 CloudFront POP으로 요청을 보내 지리적으로 흩어진 클라이언트에 유리하며 REST API의 기본값입니다. 리전은 같은 리전의 클라이언트용, 프라이빗은 VPC 안에서 인터페이스 VPC 엔드포인트로만 접근합니다.[2]

스로틀링

API Gateway는 토큰 버킷 알고리즘으로 계정·리전 단위의 요청 속도와 버스트를 검사하고, 한도를 넘으면 클라이언트는 429 Too Many Requests를 받습니다. 한도는 좁은 쪽부터 사용량 계획의 클라이언트별·메서드별 → 스테이지의 메서드별 → 계정(리전별) → AWS 리전 순으로 적용됩니다.[3] 계정 기본값은 리전당 초당 10,000건, 버킷 용량 5,000건이며 증가를 요청할 수 있습니다(일부 리전은 더 낮음).[4]

Lambda 통합과 시간 제한

Lambda 프록시 통합에서는 API Gateway가 클라이언트 요청 전체(헤더, 쿼리 문자열, 경로 변수, 본문 등)를 Lambda의 이벤트로 넘기고, 함수는 정해진 형식(statusCode, headers, body)으로 응답해야 합니다. 형식이 틀리면 502 Bad Gateway입니다.[7] REST API의 통합 시간 제한은 50밀리초~29초입니다. 리전·프라이빗 API는 29초 초과로 올릴 수 있지만 계정 스로틀 한도가 줄어들 수 있고, 엣지 최적화 API는 올릴 수 없습니다.[6] 오래 걸리는 작업을 동기 API 뒤에 두면 안 되는 이유입니다. 이럴 땐 요청을 SQS나 Step Functions로 넘기고 바로 응답합니다(API Gateway는 Lambda 외에 AWS 서비스와도 직접 통합됩니다[1]).

Step Functions: 워크플로 오케스트레이션

Step Functions는 상태 머신(워크플로) 위에서 동작합니다. 각 단계가 상태이고, Task 상태가 Lambda 호출 같은 작업 단위를 맡습니다. 기본 제공 기능으로 Choice(데이터 기반 분기), Retry/Catch(재시도·대체 경로), Parallel, Map(항목별 병렬 처리), 그리고 콜백 토큰으로 사람의 승인을 기다리는 패턴이 있습니다.[8] 오류 처리·재시도·순서 제어를 함수 코드 대신 워크플로가 맡는다는 것이 핵심입니다.

상태 비저장 설계

Well-Architected 신뢰성 원칙 REL05-BP06은 요청 사이에 로컬 디스크나 메모리의 데이터에 의존하지 않도록 상태를 빼내라고 합니다. 그러면 서버를 언제든 교체할 수 있고, 어느 인스턴스든 아무 요청이나 처리하므로 수평 확장이 됩니다. 세션 데이터를 옮길 곳으로 ElastiCache, DynamoDB, EFS, MemoryDB를 예로 듭니다.[13] 상태 비저장이 되어야 Auto Scaling 축소나 인스턴스 장애 때 사용자가 로그아웃되지 않습니다.

시험 단골

  • "API 키", "파트너별 사용량 제한", "WAF", "캐싱", "프라이빗 API" → REST API. "가장 저렴한", "단순 프록시", "JWT" → HTTP API
  • "429" → 스로틀링. 백엔드 보호는 스테이지/사용량 계획 스로틀링, 같은 읽기 반복은 캐시
  • "여러 단계 + 재시도 + 사람 승인 + 감사", "15분 넘는 흐름" → Step Functions Standard
  • "초당 대량 이벤트", "짧고 멱등" → Express
  • "전 세계 사용자, 정적 콘텐츠 느림" → CloudFront. "같은 DB 쿼리 반복" → ElastiCache
  • "축소 시 사용자 로그아웃" → 세션을 ElastiCache/DynamoDB로 외부화(상태 비저장)

연습

기억으로 푸세요.

Q1. 회사가 외부 파트너에게 API를 공개합니다. 파트너마다 API 키를 발급하고, 파트너별로 초당 요청 수와 월 할당량을 다르게 제한해야 합니다. 어떤 구성이 맞습니까?

API 키와 클라이언트별 스로틀링·할당량(사용량 계획)은 REST API에만 있습니다. HTTP API는 더 저렴하지만 이 기능이 없고, JWT 권한 부여자는 인증일 뿐 파트너별 사용량을 제한하지 않습니다.

Q2. 할인 행사 중 API Gateway를 호출하는 일부 클라이언트가 429 Too Many Requests를 받았습니다. 백엔드 Lambda에는 오류가 없습니다. 무엇이 일어난 것입니까?

429는 토큰 버킷의 속도·버스트 한도를 넘어 API Gateway가 스로틀링했다는 뜻입니다. 프록시 응답 형식 오류는 502, 권한 거부는 401/403 계열입니다. 대응은 클라이언트 재시도(속도 제한), 스로틀링 한도 조정이나 증가 요청, 반복 읽기라면 캐싱입니다.

Q3. REST API의 GET /products가 전체 호출의 90%를 차지하며 매번 같은 카탈로그를 Lambda가 DB에서 읽어 반환합니다. 카탈로그는 몇 분 늦게 반영돼도 괜찮습니다. 코드 변경 없이 Lambda 호출과 지연을 줄이는 방법은?

API Gateway 캐시는 스테이지 단위로 켜고, 기본으로 GET을 TTL(기본 300초) 동안 캐시해 엔드포인트 호출을 줄입니다. HTTP API에는 캐싱 기능이 없습니다. 캐시는 시간당 과금이라는 점도 기억하세요.

Q4. (0013 복습 포함) 주문 처리는 결제 → 재고 차감 → 배송 요청 순서이며, 고액 주문은 담당자 승인을 받느라 길게는 며칠 걸립니다. 단계별 재시도와 실패 시 보상 처리, 실행 이력 감사가 필요합니다. 가장 적합한 것은?

Standard는 최대 1년 실행, 정확히 한 번 실행(결제 같은 비멱등 작업), 콜백 토큰으로 사람 승인 대기, 90일 실행 기록을 제공합니다. Express는 5분이 한계이고 콜백 패턴을 지원하지 않습니다. Lambda 하나는 최대 15분이라 며칠짜리 흐름을 담을 수 없습니다.

Q5. IoT 장치에서 하루 수백만 건의 이벤트가 들어오고, 이벤트마다 몇 초 안에 끝나는 변환 후 DynamoDB에 PUT하는 짧은 워크플로를 실행합니다. 비용 효율이 중요합니다. 올바른 선택은? (두 개를 고르세요)

대량·단시간 이벤트 처리는 Express가 맞고, 요금도 실행 수·시간·메모리 기준이라 상태 전환마다 과금되는 Standard보다 유리합니다. 비동기 Express는 최소 한 번 실행이라 같은 이벤트가 두 번 돌 수 있으므로 단계를 멱등하게 설계해야 합니다. 콜백 패턴은 Express에서 지원하지 않습니다.

Q6. ALB 뒤 Auto Scaling 그룹의 EC2 웹 서버들이 로그인 세션을 각 인스턴스 메모리에 저장합니다. 축소 이벤트 때마다 일부 사용자가 로그아웃됩니다. 가장 적절한 해결책은?

세션을 ElastiCache나 DynamoDB 같은 외부 저장소로 옮기면 어느 인스턴스든 어떤 요청이든 처리할 수 있어, 인스턴스가 종료돼도 세션이 남습니다(REL05-BP06). 축소를 막거나 늦추는 것은 비용만 늘리고 장애로 인한 인스턴스 교체에는 효과가 없습니다.

Q7. 서울 리전의 S3에 있는 이미지·JS 파일을 유럽과 미국 사용자가 느리게 받는다고 합니다. 오리진 부하도 줄이고 싶습니다. 가장 적합한 것은?

CloudFront는 사용자에게 지연이 가장 낮은 엣지 로케이션에서 캐시된 사본을 주고, 없을 때만 S3 오리진에서 가져옵니다. ElastiCache는 애플리케이션 뒤쪽의 데이터 캐시라 전 세계 사용자에게 파일을 직접 전달하는 용도가 아닙니다.

Q8. (0014 복습) API Gateway 뒤의 백엔드가 주문 폭주를 감당하지 못합니다. 클라이언트에게는 "접수됨"만 즉시 돌려주고, 주문은 백엔드가 감당할 속도로 처리하면 됩니다. 운영 부담이 가장 적은 방법은?

API Gateway는 Lambda뿐 아니라 AWS 서비스와 직접 통합되므로 요청을 SQS에 넣고 바로 응답할 수 있습니다. 큐가 급증을 흡수하고 작업자는 자기 속도로 처리합니다(0014의 버퍼링). 시간 제한을 늘리면 백엔드 과부하는 그대로이고, 계정 스로틀 한도가 줄어들 수도 있습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) REST API에만 있는 기능 다섯 가지. (2) Step Functions Standard와 Express의 차이(시간·실행 보장·요금·콜백). (3) 캐시 계층 세 개와 각각 언제 쓰는지.

(1) API 키·사용량 계획(클라이언트별 스로틀링), API 캐싱, AWS WAF, 요청 검증, 프라이빗·엣지 최적화 엔드포인트 (리소스 정책도). HTTP API는 기능이 적은 대신 더 저렴하고 JWT 권한 부여자를 지원.

(2) Standard: 최대 1년, 정확히 한 번, 상태 전환 수로 과금, 콜백·.sync 지원, 90일 실행 기록. Express: 최대 5분, 비동기는 최소 한 번(동기는 최대 한 번), 실행 수·시간·메모리로 과금, 콜백 미지원, 기록은 CloudWatch Logs.

(3) CloudFront: 전 세계 사용자에게 정적·동적 콘텐츠를 엣지에서. API Gateway 캐시: REST API 스테이지의 반복 GET 응답(TTL 기본 300초, 최대 3600초, 시간당 과금). ElastiCache: 비싼 DB 쿼리 결과와 세션(상태 비저장 설계).
