EC2 문제의 절반은 "어떤 인스턴스를", 나머지 절반은 "어떻게 사서" 돌릴지입니다. 오늘은 인스턴스 이름 읽는 법, 구매 옵션 일곱 가지, 배치 그룹 세 가지, 최대 절전을 한 번에 정리합니다.

왜 이것부터인가

시험에서: "가장 비용 효율적인" 문제의 단골 무대가 EC2 구매 옵션입니다. 워크로드 설명(상시/간헐/중단 가능)만 보고 답을 고르게 출제됩니다.

최대 절전 (hibernation)

최대 절전은 RAM 내용을 EBS 루트 볼륨에 저장하고 멈춥니다. 다시 시작하면 RAM이 다시 올라오고 프로세스가 이어서 실행되며, 인스턴스 ID도 유지됩니다. 부팅과 메모리 적재에 오래 걸리는 앱을 "미리 데워 두는" 용도입니다. 멈춰 있는 동안 인스턴스 사용료는 없고, RAM 내용을 포함한 EBS 스토리지 요금만 냅니다.[16]

조건: 시작할 때 활성화해야 하며(기존 인스턴스에는 불가), 루트 볼륨은 인스턴스 스토어가 아닌 EBS여야 하고, 암호화되어 있어야 합니다. RAM 크기도 제한이 있습니다(Linux 150 GiB 미만). 온디맨드와 Spot 모두 가능합니다.[17]

연습

Q1. 회사가 24시간 상시 운영되는 프로덕션 웹 서버(m5 패밀리)의 비용을 3년간 줄이려 합니다. 내년에 c 패밀리로 바꾸거나 일부를 Amazon ECS on Fargate로 옮길 수도 있습니다. 가장 적합한 방법은?

Compute Savings Plans는 패밀리·리전에 묶이지 않고 Fargate와 Lambda에도 적용됩니다. EC2 Instance Savings Plans는 할인은 더 크지만 특정 패밀리에 묶여 c 패밀리 이전이나 Fargate를 덮지 못합니다. Standard RI는 교환이 안 됩니다. 프로덕션 웹 서버를 전부 Spot에 올리면 중단 위험을 감수해야 합니다.

Q2. 매일 밤 로그를 처리하는 배치 작업이 있습니다. 작업은 체크포인트를 저장해 중단되어도 다시 시작할 수 있고, 아침까지만 끝나면 됩니다. 가장 비용 효율적인 구매 옵션은?

"중단 가능"과 "시작 시간 유연"이 Spot의 정의 그대로입니다. AWS 문서도 배치 작업과 데이터 분석을 Spot의 적합 사례로 듭니다. 매일 몇 시간만 도는 작업에 3년 약정(RI)은 놀리는 시간이 많아 손해이고, 온디맨드는 할인이 없으며, 전용 호스트는 라이선스·규정 요건이 있을 때 고르는 옵션입니다.

Q3. 유체 역학 시뮬레이션을 수십 대의 EC2 인스턴스로 돌립니다. 노드끼리 끊임없이 데이터를 주고받아 네트워크 지연이 성능을 좌우합니다. 어떤 배치 그룹을 써야 하나요?

클러스터 배치 그룹은 한 AZ 안에서 인스턴스를 같은 고대역폭 네트워크 구간에 모아 지연을 낮추고 처리량을 높입니다. 분산과 파티션은 장애 격리가 목적이라 오히려 서로 떨어뜨립니다.

Q4. 수백 대 규모의 Apache Cassandra 클러스터를 EC2에 구축합니다. 랙 단위 하드웨어 장애가 복제본 전체로 번지지 않게 하고, 어떤 노드가 어떤 장애 영역에 있는지 애플리케이션이 알 수 있어야 합니다. 가장 적합한 것은?

파티션 배치 그룹은 파티션마다 랙을 분리하고, 어떤 인스턴스가 어느 파티션에 있는지 보여 줘서 Cassandra·HDFS 같은 토폴로지 인식 시스템이 복제 위치를 정할 수 있습니다. 분산 배치 그룹도 하드웨어를 분리하지만 AZ당 실행 인스턴스 7개가 한계라 수백 대 클러스터에는 맞지 않습니다.

Q5. EC2 최대 절전(hibernation)을 쓰기 위한 조건으로 옳은 것을 두 개 고르세요.

RAM 내용이 루트 볼륨에 기록되므로 루트는 EBS이고 암호화되어 있어야 하며, 최대 절전은 시작 시점에만 켤 수 있습니다. 실행 중이든 중지 상태든 기존 인스턴스에는 나중에 켤 수 없습니다.

Q6. 회사가 물리 코어 단위로 라이선스가 매겨지는 기존 데이터베이스 소프트웨어를 AWS로 옮기려 합니다. 라이선스 준수를 위해 소켓과 물리 코어 수를 확인할 수 있어야 하고, 인스턴스를 같은 물리 서버에 계속 배치해야 합니다. 무엇을 써야 하나요?

소켓·코어 가시성, 호스트 선호도(같은 물리 서버에 계속 배치), 소켓/코어 단위 BYOL은 Dedicated Hosts의 기능입니다. Dedicated Instances도 전용 하드웨어지만 소켓·코어 가시성과 호스트 선호도가 지원되지 않습니다. 이 차이가 시험의 핵심 함정입니다.

Q7. (복습 · 0002) EC2 인스턴스의 애플리케이션이 같은 계정의 DynamoDB 테이블에 써야 합니다. 보안 모범 사례에 맞는 방법은?

0002에서 본 대로 EC2 위 워크로드는 인스턴스 프로파일로 연결한 IAM 역할에서 자동 갱신되는 임시 자격 증명을 씁니다. 최소 권한으로 필요한 테이블과 작업만 허용하세요. 장기 키를 사용자 데이터나 AMI에 넣으면 유출 위험이 크고, 루트 키는 절대 쓰지 않습니다.

Q8. 다음 주 이틀간 대형 이벤트가 있어 특정 AZ에서 c7i 인스턴스 50대를 반드시 시작할 수 있어야 합니다. 1년 이상 약정은 하고 싶지 않습니다. 가장 적합한 것은?

온디맨드 용량 예약은 특정 AZ의 용량을 확보하고, 즉시 사용형은 기간 약정이 없어 이벤트 후 취소하면 됩니다. Savings Plans와 리전 RI는 할인만 주고 용량은 보장하지 않으며, 둘 다 1년 이상 약정입니다. Spot은 용량이 있을 때만 실행되고 회수될 수 있습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) 워크로드 세 종류(중단 가능 / 상시 프로덕션 / 단기·불규칙·중단 불가)에 맞는 구매 옵션은? (2) Compute SP, EC2 Instance SP, Standard RI, Convertible RI의 유연성 차이는? (3) 배치 그룹 세 가지의 목표와 한계 숫자는?

(1) 중단 가능 → Spot(최대 90% 할인, 2분 전 알림). 상시 프로덕션 → Savings Plans/RI(1년·3년). 특정 AZ 용량 보장이 필요하면 용량 예약을 더함. 단기·불규칙·중단 불가 → 온디맨드.

(2) Compute SP: 패밀리·리전·OS 무관 + Fargate·Lambda(최대 66%). EC2 Instance SP: 한 리전의 한 패밀리(최대 72%). Standard RI: 수정만, 교환 불가, Marketplace 판매 가능. Convertible RI: 다른 Convertible RI로 교환 가능, 판매 불가. AWS는 RI보다 SP 권장.

(3) 클러스터: 단일 AZ, 저지연·고처리량. 분산: 서로 다른 하드웨어, AZ당 실행 인스턴스 7개. 파티션: 랙 분리, AZ당 파티션 7개, HDFS·HBase·Cassandra.
