복제본이라고 다 같은 복제본이 아니다:
RDS Multi-AZ, 읽기 전용 복제본, Aurora

시험은 "고가용성"과 "읽기 확장"을 섞어 놓고 어느 쪽을 묻는지 가려내게 합니다. 오늘은 동기식 대기 복제본과 비동기식 읽기 전용 복제본을 확실히 구분하고, RDS Proxy와 Aurora(Serverless, Global Database)가 어떤 문제를 푸는지 정리합니다.

왜 이것부터인가

시험에서: "AZ 장애에 대비" → Multi-AZ, "보고서 쿼리가 주 DB를 느리게 함" → 읽기 전용 복제본, "Lambda가 연결을 너무 많이 엶" → RDS Proxy. 이 세 줄이 가장 자주 나오는 오답 함정입니다.
실무에서: 운영 DB의 가용성 설계와 비용(대기 인스턴스, 복제본 요금)을 결정하는 기준이 됩니다.

Multi-AZ DB 인스턴스: 고가용성 전용

Multi-AZ DB 인스턴스 배포에서 RDS는 다른 AZ에 동기식 대기 복제본을 자동으로 만들고 유지합니다.[1] 핵심 함정은 이것입니다. AWS 문서는 이 옵션이 읽기 확장 솔루션이 아니며 대기 복제본으로 읽기 트래픽을 처리할 수 없다고 분명히 말합니다.[1] 동기식 복제 때문에 Single-AZ보다 쓰기·커밋 지연이 늘 수 있습니다.[1]

주 인스턴스 호스트 장애, 네트워크 단절, 스토리지 장애, OS 패치 등이 생기면 RDS가 자동으로 장애 조치하며, 일반적으로 60–120초가 걸립니다. 장애 조치는 DB 인스턴스의 DNS 레코드를 대기 인스턴스로 바꾸는 방식이라 애플리케이션은 같은 엔드포인트로 다시 연결하면 됩니다.[2] "Reboot with failover"로 수동 장애 조치도 가능합니다.[2]

Multi-AZ DB 클러스터: 읽을 수 있는 대기 두 개

Multi-AZ DB 클러스터는 라이터 1개와 읽기 가능한 리더 2개를 같은 리전의 서로 다른 AZ 세 곳에 둡니다. 복제는 반동기식(리더 최소 1개의 확인이 있어야 커밋)이고, 리더는 장애 조치 대상이면서 읽기 트래픽도 처리합니다. Multi-AZ DB 인스턴스보다 쓰기 지연이 낮습니다.[3] 이름이 비슷하지만 Aurora DB 클러스터와는 다른 것이라고 문서가 따로 경고합니다.[3]

읽기 전용 복제본: 읽기 확장 + 리전 간 DR

읽기 전용 복제본은 DB 인스턴스의 읽기 전용 사본이며, 주 인스턴스의 변경을 비동기식으로 복사합니다.[4] AWS가 꼽는 사용 사례는 읽기 위주 워크로드 확장, 보고서·데이터 웨어하우징 쿼리 분리, 그리고 복제본을 독립 인스턴스로 승격하는 재해 복구입니다. 복제본은 다른 리전에도 둘 수 있습니다.[4]

  • RDS는 읽기 전용 복제본의 자동 확장을 지원하지 않습니다. 수동으로 만들고 지웁니다.[4]
  • 같은 리전 안의 소스와 복제본 사이 복제 데이터 전송은 요금이 없습니다. 복제본 자체는 일반 인스턴스 요금입니다.[4]
  • Multi-AZ 대기와 읽기 전용 복제본을 함께 구성할 수 있습니다.[4]

RDS Proxy: 연결 폭주를 흡수하는 풀

RDS Proxy는 DB 연결을 풀링·공유해 애플리케이션 확장성을 높이고, 장애 시 애플리케이션 연결을 유지한 채 대기 인스턴스로 자동 연결해 복원력을 높입니다. 클라이언트에 IAM 인증을 강제할 수 있고, 프록시는 IAM DB 인증 또는 Secrets Manager에 저장된 자격 증명으로 DB에 연결합니다.[5] 대부분의 애플리케이션은 코드 변경 없이 쓸 수 있습니다.[5]

AWS가 꼽는 좋은 후보: "too many connections" 오류가 나는 DB, 짧은 연결을 자주 여는 Lambda 함수, 연결 풀링이 없는 앱. 또한 DNS 캐시를 우회해 Multi-AZ DB 인스턴스의 장애 조치 시간을 최대 66% 줄입니다.[6] 제약: 프록시는 DB와 같은 VPC에 있어야 하고 퍼블릭 액세스가 불가하며, 복제 구성에서는 읽기 전용 복제본이 아닌 라이터에만 연결할 수 있습니다.[5]

백업과 스토리지 자동 확장

  • 자동 백업: 백업 기간에 스토리지 볼륨 스냅샷을 만들고, 보존 기간 안의 어느 시점으로든 복구할 수 있습니다.[7] DB 인스턴스의 보존 기간은 0–35일이며 0은 자동 백업 비활성화입니다.[8]
  • 수동 스냅샷: 인스턴스를 삭제해도 지워지지 않습니다. 첫 스냅샷 이후는 증분입니다. 수동 스냅샷은 공유할 수 있고 자동·수동 모두 복사할 수 있습니다.[7]
  • 스토리지 자동 확장: 예측하기 어려운 워크로드용입니다. 여유 공간이 할당량의 10% 이하로 5분 이상 지속되면 자동으로 늘리고, 상한은 사용자가 정한 최대 스토리지 임곗값입니다. 줄이지는 못합니다.[9]

Aurora: 컴퓨팅과 스토리지의 분리

Aurora DB 클러스터는 DB 인스턴스들과, 여러 AZ에 걸친 가상 클러스터 볼륨으로 구성됩니다. 라이터(주 인스턴스) 1개와 같은 볼륨을 공유하는 Aurora 복제본 최대 15개를 둘 수 있고, 주 인스턴스가 불가용해지면 Aurora 복제본으로 자동 장애 조치합니다.[10] 클러스터 볼륨에는 AZ 세 곳에 데이터 사본이 있고, 복제량은 인스턴스 수와 무관합니다. 볼륨은 데이터 증가에 따라 자동으로 커집니다.[11]

스토리지를 공유하므로 복제본 지연은 보통 100밀리초보다 훨씬 짧고, 복제본 승격은 주 인스턴스를 새로 만드는 것보다 훨씬 빠릅니다. 복제본이 하나도 없으면 복구 동안 클러스터를 쓸 수 없습니다.[12] 연결은 클러스터 엔드포인트(쓰기)와 복제본 간 연결을 분산하는 리더 엔드포인트(읽기)를 씁니다.[13] RDS와 달리 Aurora Auto Scaling이 CloudWatch 지표에 맞춰 Aurora 복제본 수를 자동 조정합니다(라이터는 대상 아님).[14]

Aurora Serverless (v2)

수요에 따라 용량을 자동 조정하고 사용한 만큼만 과금하는 구성으로, 변동이 크고 예측 불가한 워크로드, 개발·테스트, 멀티테넌트, 새 애플리케이션에 적합합니다. 용량은 ACU 단위로 0.5 ACU씩 세밀하게 늘고 줄며, 리더·Multi-AZ·Global Database·RDS Proxy와 함께 쓸 수 있습니다.[15] 최소 용량을 0 ACU로 두면 연결이 없을 때 자동 일시 중지되어 인스턴스 요금이 0이 됩니다(스토리지 요금은 계속). 재개에는 보통 약 15초가 걸립니다.[16] (현재 AWS 문서는 이 기능을 "Aurora serverless"라고 부릅니다.)

Aurora Global Database

주 리전 1개와 읽기 전용 보조 리전 최대 10개로 구성되며, 데이터베이스 엔진이 아닌 스토리지 계층으로 복제하고 지연은 보통 1초 미만입니다. 리전 전체 장애에서 기존 복제 방식보다 낮은 RTO·RPO로 복구하고, 멀리 떨어진 사용자에게 로컬 지연의 읽기를 제공합니다.[17] 계획된 리전 이동은 데이터 손실 없는 switchover, 리전 장애 복구는 failover를 씁니다. 쓰기 전달(write forwarding)로 보조 클러스터가 쓰기를 주 클러스터에 보내게 할 수도 있습니다.[17]

시험 단골: 키워드 → 정답

  • "AZ 장애에도 DB 가용", "자동 장애 조치" → Multi-AZ. 대기에서 읽기를 시키는 보기는 오답.
  • "읽기 위주", "보고서/분석 쿼리가 운영 DB 부하" → 읽기 전용 복제본 (Aurora라면 리더 엔드포인트, Auto Scaling).
  • "다른 리전에 DR", "리전 장애" → 리전 간 읽기 전용 복제본 승격, Aurora라면 Global Database (RPO 초 단위).
  • "Lambda", "too many connections", "장애 조치 시간 단축", "자격 증명을 코드에 두지 않음" → RDS Proxy.
  • "예측 불가, 간헐적, 개발/테스트, 쓰지 않을 때 비용 최소" → Aurora Serverless (최소 0 ACU).
  • "스토리지가 예측 불가하게 증가" → RDS 스토리지 자동 확장. "35일보다 오래 보관" → 수동 스냅샷 (또는 AWS Backup).

연습

Q1. 회사의 RDS for MySQL DB 인스턴스가 단일 AZ에서 운영 중입니다. AZ 장애가 나도 애플리케이션 변경 없이 자동으로 DB를 계속 쓸 수 있어야 합니다. 가장 적합한 방법은?

Multi-AZ는 다른 AZ에 동기식 대기를 두고 장애 시 DNS를 대기로 바꿔 자동 장애 조치합니다. 읽기 전용 복제본은 비동기식이고 승격이 수동이라 "자동, 앱 변경 없음"을 만족하지 못합니다. 스냅샷 복원은 시간이 오래 걸립니다.

Q2. RDS for PostgreSQL 운영 DB에서 야간 보고서 쿼리가 돌 때마다 주문 처리 응답이 느려집니다. 보고서는 몇 분 지연된 데이터여도 괜찮습니다. 가장 비용 효율적인 해결책은?

보고서 쿼리 분리는 AWS가 명시한 읽기 전용 복제본의 대표 사용 사례이고, 약간의 지연(비동기)은 허용됩니다. Multi-AZ 대기는 읽기 트래픽을 처리할 수 없으므로 두 번째 보기가 가장 유혹적인 오답입니다. RDS Proxy는 연결 풀링이지 쿼리 캐시가 아닙니다.

Q3. 트래픽 급증 시 수천 개의 Lambda 함수가 동시에 RDS for MySQL에 연결해 "too many connections" 오류가 납니다. 코드 변경을 최소화하면서 해결하려면?

RDS Proxy는 연결 풀을 유지하며 재사용하므로, 짧은 연결을 자주 여는 Lambda의 대표 해결책입니다. 복제본 추가는 쓰기 연결을 줄이지 못하고 앱이 엔드포인트를 나눠 써야 합니다. 동시성 1은 확장성을 없앱니다.

Q4. 글로벌 서비스가 Aurora PostgreSQL을 씁니다. 유럽·아시아 사용자에게 낮은 지연의 읽기를 제공하고, 주 리전 전체 장애 시 초 단위 RPO로 다른 리전에서 복구해야 합니다. 가장 적합한 것은?

Global Database는 스토리지 계층에서 보통 1초 미만 지연으로 보조 리전에 복제하고, 리전 장애 시 낮은 RTO·RPO로 failover합니다. 하루 단위 스냅샷 복사는 RPO가 최대 하루입니다. 같은 리전 복제본은 리전 장애를 막지 못합니다.

Q5. RDS Multi-AZ DB 인스턴스 배포의 대기 복제본에 대한 설명으로 옳은 것은? (두 개를 고르세요)

대기는 다른 AZ의 동기식 복제본이고, 장애 조치는 DNS 레코드 전환으로 이루어집니다. 대기는 읽기를 처리할 수 없고(읽기가 필요하면 Multi-AZ DB 클러스터나 읽기 전용 복제본), 같은 리전 안에서만 동작합니다. 다른 리전은 읽기 전용 복제본의 영역입니다.

Q6. 개발팀의 테스트 DB는 근무 시간에만 간헐적으로 쓰이고 밤·주말에는 전혀 쓰이지 않습니다. Aurora MySQL을 유지하면서 컴퓨팅 비용을 가장 줄이는 방법은?

최소 0 ACU면 연결이 없을 때 자동 일시 중지되어 인스턴스 요금이 0이 됩니다(재개 약 15초, 개발·테스트에 적합). 작은 인스턴스도 쉬는 시간에 요금이 나갑니다. Auto Scaling은 리더만 조정하며 라이터는 그대로입니다.

Q7. 신규 모바일 게임의 RDS 데이터가 얼마나 빨리 늘지 예측할 수 없습니다. 스토리지 부족으로 인한 장애를 운영 부담 없이 피하려면?

스토리지 자동 확장은 여유 공간이 10% 이하로 5분 이상 지속되면 최대 임곗값까지 자동으로 늘립니다. AWS 문서가 바로 "빠르게 성장하는 모바일 게임"을 예로 듭니다. 처음부터 최대 할당은 비용 낭비이고, 복제본은 전체 사본이라 데이터를 나누지 않습니다.

Q8. (0017 DR 복습) 규정상 RDS 데이터베이스의 백업을 1년간 보관해야 하고, DB 인스턴스를 삭제해도 백업이 남아야 합니다. 자동 백업만으로 부족한 이유와 대안으로 옳은 것은?

DB 인스턴스의 자동 백업 보존 기간은 0–35일입니다. 수동 스냅샷은 인스턴스를 삭제해도 지워지지 않으므로 장기 보관에 씁니다. 7일은 콘솔 기본값일 뿐 상한이 아닙니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) Multi-AZ DB 인스턴스, Multi-AZ DB 클러스터, 읽기 전용 복제본을 복제 방식·읽기 가능 여부·범위로 비교하세요. (2) Aurora 클러스터 볼륨, 복제본, Serverless, Global Database의 핵심을 한 줄씩. (3) RDS Proxy를 떠올려야 하는 키워드 세 개.

(1) Multi-AZ 인스턴스: 동기식, 대기 읽기 불가, 같은 리전 다른 AZ, 자동 장애 조치(DNS 전환, 보통 60–120초). Multi-AZ 클러스터: 반동기식, 리더 2개 읽기 가능, AZ 3곳. 읽기 전용 복제본: 비동기식, 읽기 가능, 다른 리전 가능, 수동 승격, RDS는 복제본 자동 확장 없음.

(2) 클러스터 볼륨은 AZ 3곳에 사본, 자동 증가. 복제본 최대 15개가 같은 볼륨 공유(지연 보통 100ms 미만), 장애 조치 대상, 리더 엔드포인트로 분산, Aurora Auto Scaling. Serverless는 0.5 ACU 단위 자동 조정, 최소 0 ACU면 자동 일시 중지. Global Database는 보조 리전 최대 10개, 스토리지 기반 복제 1초 미만, switchover/failover.

(3) Lambda, too many connections, 장애 조치 시간 단축(최대 66%), Secrets Manager/IAM 인증.

더 해볼 것

1차 자료 (꼭 읽기, 10분): "Working with DB instance read replicas". 사용 사례, Multi-AZ와의 결합, 리전 간 복제본이 한 페이지에 있습니다. (한국어: URL의 docs.aws.amazon.com/ 뒤에 ko_kr/)

실습 (선택, 비용 주의): 프리 티어 대상 클래스로 RDS for MySQL Single-AZ 인스턴스를 만들고 "Modify"에서 Multi-AZ 옵션과 스토리지 자동 확장 항목을 확인만 해 보세요. Multi-AZ나 읽기 전용 복제본을 실제로 켜면 인스턴스 요금이 추가되므로, 실습 후 바로 삭제하세요(삭제 시 최종 스냅샷도 보관 요금이 생길 수 있습니다).
