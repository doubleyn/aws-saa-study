복제본이라고 다 같은 복제본이 아니다:
RDS Multi-AZ, 읽기 전용 복제본, Aurora

AWS 시험에서 가장 매력적이면서도 수험생을 많이 낚는 함정이 바로 "고가용성(HA)"과 "읽기 성능 확장(Scale-out)"을 교묘하게 뒤섞어 출제하는 문제입니다. 이번 레슨에서는 동기식 대기 복제본과 비동기식 읽기 전용 복제본의 근본적인 메커니즘 차이를 완벽히 정리하고, Lambda 환경의 연결 폭주를 해결하는 RDS Proxy, 그리고 컴퓨팅과 스토리지를 분리해 데이터베이스 패러다임을 바꾼 Amazon Aurora의 핵심 아키텍처를 학습합니다.

왜 RDS와 Aurora를 깊이 있게 배워야 할까요?

시험에서: "가용 영역(AZ) 장애가 발생해도 다운타임 없이 자동으로 서비스를 지속해야 한다"는 요구에는 Multi-AZ가 정답이고, "야간 분석 보고서 쿼리 때문에 주 데이터베이스의 온라인 주문 처리가 느려진다"는 문제에는 읽기 전용 복제본이 정답입니다. 또한 "수천 개의 Lambda 함수가 동시에 실행되면서 DB 연결 초과 에러가 발생한다"는 상황에는 RDS Proxy가 유일한 해법입니다. 이 세 가지 패턴은 시험에 매번 반복 출제되는 단골 주제입니다.
실무에서: 데이터베이스는 서비스의 심장입니다. Multi-AZ 대기 인스턴스와 읽기 전용 복제본의 차이를 모르면 장애 상황에서 데이터 유실이나 서비스 중단이 발생할 수 있고, 잘못된 복제 아키텍처 설계로 수백만 원의 인프라 비용이 낭비될 수 있습니다.

Multi-AZ DB 인스턴스: 가용 영역 장애에 대비하는 고가용성 전용 설계

RDS의 Multi-AZ DB 인스턴스 배포는 같은 리전 내의 서로 다른 가용 영역(AZ)에 동기식 대기(Standby) 복제본을 자동으로 생성하고 유지 관리하는 고가용성(High Availability) 솔루션입니다.[1]

  • 동기식 복제의 원리: 애플리케이션이 주(Primary) 인스턴스에 쓰기(Write/Commit) 작업을 요청하면, 주 인스턴스와 대기 인스턴스 양쪽의 디스크에 데이터가 모두 기록된 후에야 트랜잭션 성공 응답을 반환합니다. 따라서 데이터 유실이 원천적으로 발생하지 않지만, 단일 AZ 구성에 비해 약간의 쓰기 지연 시간(Write Latency)이 증가할 수 있습니다.[1]
  • 가장 중요한 시험 함정: 대기(Standby) 인스턴스는 평상시에 절대로 읽기(Read) 트래픽을 처리할 수 없습니다! 대기 인스턴스는 오직 장애 발생 시 교체 투입되기 위해 백그라운드에서 대기만 하는 인스턴스입니다. 만약 시험 보기에서 "대기 복제본으로 읽기 쿼리를 분산한다"는 내용이 나오면 100% 오답입니다.[1]
  • 자동 장애 조치(Failover) 메커니즘: 주 인스턴스의 하드웨어 결함, 네트워크 단절, 스토리지 오류, OS 자동 패치 등이 발생하면 RDS 시스템이 이를 감지하고 대기 인스턴스로 자동 장애 조치를 실행합니다(일반적으로 60~120초 소요). 이때 RDS는 데이터베이스의 DNS CNAME 레코드를 자동으로 대기 인스턴스의 IP로 전환하므로, 애플리케이션 코드는 엔드포인트 주소를 바꿀 필요 없이 동일한 도메인으로 재연결하기만 하면 됩니다.[2]

Multi-AZ DB 클러스터: 읽기 가능한 대기 복제본 2개를 갖춘 최신 구성

기존 Multi-AZ DB 인스턴스의 "대기 인스턴스를 평상시에 읽기 용도로 놀려둔다"는 아쉬움을 개선하기 위해 도입된 구성이 바로 Multi-AZ DB 클러스터입니다.[3]

  • 구성: 1개의 라이터(Writer) 인스턴스와 읽기 트래픽을 처리할 수 있는 리더(Reader) 인스턴스 2개를 서로 다른 3개 가용 영역에 각각 하나씩 배치합니다.
  • 반동기식(Semi-synchronous) 복제: 라이터에 트랜잭션이 커밋될 때, 최소 1개의 리더 인스턴스로부터 확인 응답을 받으면 즉시 커밋이 완료됩니다. 기존의 완전 동기식 Multi-AZ보다 쓰기 지연 시간이 훨씬 짧고 성능이 우수합니다.
  • 역할: 2개의 리더 인스턴스는 평소에 애플리케이션의 읽기 요청을 분산 처리하며, 주 라이터 인스턴스에 장애가 발생하면 최신 데이터를 가진 리더 인스턴스 중 하나가 즉시 새로운 라이터로 자동 승격됩니다.

읽기 전용 복제본 (Read Replica): 읽기 부하 분산과 재해 복구(DR)

읽기 전용 복제본(Read Replica)은 주 데이터베이스의 변경 사항을 비동기식(Asynchronous)으로 복제하여 읽기 전용으로 서비스하는 복제본입니다.[4]

  • 비동기식 복제의 특징: 주 인스턴스는 복제본에 데이터가 도달하기를 기다리지 않고 클라이언트에게 즉시 커밋을 완료합니다. 따라서 주 인스턴스의 쓰기 성능에는 전혀 영향을 주지 않지만, 미세한 복제 지연(Replication Lag)이 발생할 수 있으므로 최종적 일관성(Eventual Consistency)을 감수할 수 있는 읽기 워크로드에 사용해야 합니다.
  • 주요 활용 사례:
    1. 읽기 워크로드 확장: 조회 수가 압도적으로 많은 웹 사이트나 쇼핑몰에서 읽기 트래픽을 여러 복제본으로 분산합니다.
    2. 무거운 분석 및 보고서 쿼리 분리: 정기 감사나 대시보드 리포트 생성과 같이 데이터베이스 리소스를 심하게 소모하는 무거운 집계 쿼리를 복제본으로 격리하여 운영 트랜잭션을 보호합니다.
    3. 교차 리전 재해 복구(Cross-Region DR): 읽기 전용 복제본은 주 인스턴스와 다른 AWS 리전(Cross-Region)에도 생성할 수 있습니다. 이를 통해 물리적으로 먼 지역의 사용자에게 초저지연 읽기를 제공함과 동시에, 주 리전 전체가 마비되는 대규모 재난 발생 시 복제본을 독립 데이터베이스로 승격(Promote)시켜 비즈니스를 신속하게 복구할 수 있습니다.
  • 시험 핵심 주의사항: 표준 RDS의 읽기 전용 복제본은 자동 확장(Auto Scaling)을 지원하지 않습니다. 관리자가 수동으로 생성하고 삭제해야 합니다(Aurora는 Aurora Auto Scaling 지원). 또한 Multi-AZ 고가용성과 읽기 전용 복제본은 상호 배타적인 것이 아니라 동시에 함께 구성하여 사용할 수 있습니다.[4]

RDS Proxy: 서버리스 연결 폭주를 흡수하는 완전관리형 커넥션 풀러

서버리스 아키텍처(예: AWS Lambda)에서는 이벤트가 몰릴 때 수천 개의 함수 인스턴스가 순식간에 기동됩니다. 각 Lambda 함수가 RDS에 직접 데이터베이스 연결(Connection)을 열면, DB의 최대 연결 수 한도를 초과하여 Too many connections 에러가 터지고 데이터베이스가 뻗어버립니다.
Amazon RDS Proxy는 애플리케이션과 RDS 사이에 위치하여 데이터베이스 연결을 풀링(Pooling) 및 공유(Multiplexing)해 주는 완전관리형 데이터베이스 프록시입니다.[5]

  • 연결 풀링: 수천 개의 Lambda 요청이 들어와도 실제 RDS와의 물리적 연결은 미리 맺어 둔 수십~수백 개의 커넥션 풀을 효율적으로 재사용하므로 DB의 메모리와 CPU 고갈을 방지합니다.
  • 장애 조치(Failover) 시간 단축: Multi-AZ 장애 조치 시 클라이언트의 DNS 캐시 문제로 발생하는 지연을 우회하여, 기존 60~120초 걸리던 장애 조치 시간을 최대 66% 단축시킵니다. 클라이언트 연결을 프록시가 유지한 상태에서 뒤단의 데이터베이스 연결만 새 인스턴스로 매끄럽게 교체합니다.[6]
  • 강력한 보안 및 자격 증명 관리: 클라이언트는 IAM 인증을 통해 프록시에 접속하고, 프록시는 AWS Secrets Manager에 안전하게 저장된 데이터베이스 암호를 꺼내어 DB에 접속합니다. 개발자가 소스 코드나 환경 변수에 DB 암호를 하드코딩할 필요가 전혀 없습니다.[5]
  • 제약 조건: RDS Proxy는 반드시 데이터베이스와 동일한 VPC 내부에 위치해야 하며, 공용 인터넷으로의 퍼블릭 액세스는 지원하지 않습니다.[5]

백업과 스토리지 자동 확장

  • 자동 백업 (Automated Backup): 일일 백업 기간(Backup Window)에 전체 스토리지 볼륨의 스냅샷을 생성하고 트랜잭션 로그를 지속적으로 S3에 보관합니다. 보존 기간(Retention Period: 0~35일, 0일 설정 시 자동 백업 비활성화) 내의 초 단위 특정 시점(Point-In-Time)으로 언제든 복원할 수 있습니다. 단, DB 인스턴스를 삭제하면 기본적으로 자동 백업 데이터도 함께 삭제됩니다.[8]
  • 수동 스냅샷 (Manual Snapshot): 사용자가 원할 때 수동으로 생성하는 스냅샷입니다. DB 인스턴스를 영구 삭제하더라도 수동 스냅샷은 사용자가 직접 삭제하기 전까지 영구적으로 보존됩니다. 따라서 35일을 초과하는 장기 보존(예: 규정 준수 백업)이나 다른 리전/계정으로 스냅샷을 공유·복제할 때 반드시 사용합니다.[7]
  • 스토리지 자동 확장 (Storage Auto Scaling): 데이터 증가량을 예측하기 어려운 워크로드에서 디스크 풀 장애를 방지하기 위해 사용합니다. 가용 여유 공간이 할당량의 10% 이하로 떨어져 5분 이상 지속되면 스토리지를 자동으로 증설합니다. 사용자가 설정한 최대 스토리지 임곗값(Maximum Storage Threshold)까지만 늘어나 비용 폭탄을 방지합니다. 주의할 점은 스토리지는 늘릴 수만 있고 다시 줄이는(축소) 것은 불가능합니다.[9]

Amazon Aurora: 컴퓨팅과 스토리지를 분리한 클라우드 네이티브 RDBMS

기존 상용 관계형 데이터베이스는 인스턴스 하나에 컴퓨팅(CPU/RAM)과 스토리지(디스크)가 물리적으로 묶여 있었습니다. 반면 Amazon Aurora(MySQL 및 PostgreSQL과 100% 호환)는 컴퓨팅 엔진과 스토리지 계층을 완전히 분리하여 클라우드에 최적화된 완전히 새로운 아키텍처로 설계되었습니다.[10]

혁신적인 클러스터 볼륨(Cluster Volume) 스토리지

Aurora 클러스터의 데이터는 특정 인스턴스 내부 디스크가 아니라, 3개 가용 영역(AZ)에 걸쳐 6개의 데이터 복제본(각 AZ마다 2개씩)으로 분산 저장되는 거대한 가상 '클러스터 볼륨'에 기록됩니다.[11]

  • 쿼럼(Quorum) 기반 신뢰성: 6개의 사본 중 4개의 사본에 쓰기가 완료되면 성공으로 처리하고, 읽을 때는 3개의 사본을 확인합니다. 따라서 1개 AZ 전체가 붕괴되고 추가로 다른 AZ의 디스크 1개가 고장 나도(총 3개 사본 손실) 데이터 유실 없이 읽기와 쓰기를 완벽하게 지속할 수 있습니다.
  • 자가 치유(Self-Healing) 스토리지: 백그라운드에서 스토리지 블록과 디스크를 상시 검사하여 손상된 블록이 발견되면 자동으로 다른 사본에서 복구합니다. 스토리지 볼륨은 10GB 단위로 데이터 증가에 맞춰 최대 128TiB까지 자동으로 확장됩니다.[11]
  • 최대 15개의 Aurora 읽기 복제본 (Aurora Replicas): 라이터와 리더 인스턴스들이 동일한 클러스터 볼륨을 공유하기 때문에 복제 지연 시간이 밀리초 단위(보통 10~20ms 이하)로 극히 짧습니다. 또한 표준 RDS와 달리 Aurora Auto Scaling을 통해 CPU 사용률이나 커넥션 수에 따라 리더 복제본을 자동으로 늘리고 줄일 수 있습니다.[14]
  • 엔드포인트 구분:
    • 클러스터 엔드포인트(Cluster Endpoint): 항상 현재의 주 라이터(Primary Writer) 인스턴스를 가리키며, 쓰기 트랜잭션에 사용됩니다.
    • 리더 엔드포인트(Reader Endpoint): 사용 가능한 여러 Aurora 리더 복제본들 사이에서 읽기 트래픽을 자동으로 로드 밸런싱해 줍니다.[13]

Aurora Serverless (v2)

애플리케이션의 트래픽 변동이 극심하거나 사용 패턴을 전혀 예측할 수 없는 경우, 혹은 밤이나 주말에는 전혀 사용되지 않는 개발/테스트 환경에 최적인 완전 탄력적 배포 모델입니다.[15]

  • 세밀하고 즉각적인 용량 조절: 데이터베이스 용량을 ACU(Aurora Capacity Unit, 1 ACU ≈ 2 GiB 메모리 + 해당 CPU) 단위로 0.5 ACU 단위로 수 밀리초 만에 부드럽게 스케일 업/다운합니다.
  • 최소 0 ACU 자동 일시 중지 (Auto-Pause): 최소 용량을 0 ACU로 설정하면 접속 연결이 없을 때 인스턴스가 자동으로 일시 중지되어 컴퓨팅 비용이 0원이 됩니다(스토리지 비용만 청구). 새로운 연결이 들어오면 약 15초 만에 자동으로 깨어나 정상 서비스를 재개합니다.[16]

Aurora Global Database

단일 AWS 리전을 넘어 전 세계를 무대로 서비스를 제공하거나 리전 단위 대재앙에 대비하기 위한 아키텍처입니다.[17]

  • 1개의 주(Primary) 리전과 최대 10개의 보조(Secondary) 읽기 전용 리전으로 구성됩니다.
  • 데이터베이스 엔진 레벨이 아니라 전용 AWS 글로벌 백본을 통한 스토리지 계층 복제를 수행하므로 리전 간 복제 지연 시간이 보통 1초 미만에 불과합니다.
  • 재해 복구: 주 리전 전체가 마비되는 재해 발생 시 보조 리전을 주 리전으로 승격하는 데 걸리는 시간(RTO)은 1분 미만이며, 데이터 손실(RPO)은 1초 미만으로 극히 적습니다. 정기 점검 시에는 데이터 손실이 전혀 없는 계획된 리전 전환(Switchover)을 사용합니다.[17]

시험에 자주 나오는 핵심 패턴

  • "AZ 장애에도 고가용성 보장", "자동 장애 조치(Failover)" → Multi-AZ 배포 선택. (주의: 대기 인스턴스로 읽기를 처리한다는 보기는 100% 오답!)
  • "읽기 워크로드 확장", "보고서/BI 쿼리가 운영 DB 성능을 저하시킴" → 읽기 전용 복제본(Read Replica) 생성. (Aurora인 경우 리더 엔드포인트 및 Aurora Auto Scaling)
  • "교차 리전 재해 복구(DR)", "다른 리전 사용자에게 빠른 읽기" → 교차 리전 읽기 전용 복제본, Aurora인 경우 Aurora Global Database(스토리지 기반 1초 미만 복제).
  • "Lambda 함수 연결 폭주", "Too many connections 에러", "장애 조치 시간 단축", "DB 비밀번호 소스코드 노출 방지" → RDS Proxy (Secrets Manager 연동).
  • "트래픽 예측 불가, 간헐적 사용, 야간/주말 비용 절감(최소 0원)" → Aurora Serverless (최소 0 ACU 자동 일시 중지).
  • "데이터 증가량이 불규칙하여 디스크 고갈 위험" → RDS 스토리지 자동 확장.
  • "35일을 초과하여 규정상 수년간 백업 보관", "DB 인스턴스 삭제 후에도 백업 유지" → 수동 스냅샷(Manual Snapshot) 또는 AWS Backup.

연습

Q1. 한 회사가 단일 가용 영역(Single-AZ)에서 Amazon RDS for MySQL 인스턴스를 운영하고 있습니다. 최근 데이터센터 전원 장애 위험을 겪은 후, 데이터센터 수준의 가용 영역(AZ) 장애가 발생하더라도 애플리케이션의 연결 설정이나 코드를 변경하지 않고 자동으로 데이터베이스 서비스를 지속할 수 있는 고가용성 구조를 요구받았습니다. 가장 적합한 조치는 무엇입니까?

정답은 Multi-AZ 배포 활성화입니다! Multi-AZ 배포는 다른 AZ에 동기식 대기 복제본을 유지하며, 주 인스턴스나 AZ 장애 시 RDS가 DNS CNAME 레코드를 대기 인스턴스로 자동 전환하므로 애플리케이션 코드나 연결 문자열을 변경할 필요가 전혀 없습니다. 반면 읽기 전용 복제본은 비동기식 복제이며 장애 시 수동으로 승격해야 하므로 자동 장애 조치를 만족하지 못합니다. 스냅샷 복원은 시간이 오래 걸려 다운타임이 큽니다.

Q2. 한 전자상거래 기업의 RDS for PostgreSQL 운영 데이터베이스에서 매일 밤 복잡한 정산 및 통계 보고서 쿼리가 실행될 때마다, 일반 고객들의 상품 주문 처리 트랜잭션 응답 속도가 심각하게 느려지는 현상이 발생합니다. 경영진에 제출되는 정산 보고서는 실시간 데이터와 수초에서 수 분 정도의 복제 시차가 있어도 무방합니다. 운영 DB의 성능 저하를 방지하는 가장 비용 효율적인 아키텍처는 무엇입니까?

정답은 읽기 전용 복제본 생성 후 보고서 쿼리 분리입니다! 복잡한 집계 및 보고서 쿼리를 비동기식 읽기 전용 복제본으로 분리하는 것은 AWS가 권장하는 전형적인 읽기 부하 분산 패턴입니다. 가장 유혹적인 오답인 Multi-AZ 대기 인스턴스는 평상시 읽기 트래픽을 절대 처리할 수 없습니다. 인스턴스 상시 증설은 비용 낭비이며, RDS Proxy는 커넥션 풀러이지 쿼리 결과를 저장하는 캐시가 아닙니다.

Q3. 대규모 프로모션 이벤트가 시작되면서 수천 개의 AWS Lambda 함수가 동시에 실행되었고, 이들이 동시에 RDS for MySQL 데이터베이스로 직접 연결을 시도하면서 데이터베이스에 'Too many connections' 오류가 발생하고 대량의 요청이 실패했습니다. 애플리케이션의 코드를 거의 수정하지 않고 이 연결 폭주 문제를 해결할 수 있는 가장 적합한 서비스는 무엇입니까?

정답은 Amazon RDS Proxy 도입입니다! RDS Proxy는 유휴 데이터베이스 연결을 풀링하고 공유하여 수천 개의 일시적인 Lambda 동시 실행 요청을 소수의 안정적인 DB 커넥션으로 멀티플렉싱합니다. 애플리케이션 코드 변경 없이 엔드포인트 주소만 프록시로 변경하면 됩니다. 동시성을 1로 제한하면 시스템 전체가 심각한 병목 상태에 빠지며, 복제본을 추가하는 것은 쓰기 트랜잭션의 연결 한도 문제를 해결하지 못합니다.

Q4. 전 세계 사용자를 대상으로 운영 중인 글로벌 미디어 서비스가 Amazon Aurora PostgreSQL을 주 데이터베이스로 사용하고 있습니다. 유럽 및 아시아의 현지 사용자들에게 1초 미만의 빠른 읽기 응답을 제공해야 하며, 주 리전 전체가 마비되는 대규모 재해 상황에서도 1분 미만의 RTO(복구 시간 목표)와 수 초 미만의 RPO(복구 시점 목표)로 타 리전에서 즉시 서비스를 복구할 수 있어야 합니다. 가장 적합한 솔루션은 무엇입니까?

정답은 Aurora Global Database입니다! Aurora Global Database는 전용 스토리지 복제 계층을 사용하여 보통 1초 미만의 지연 시간으로 최대 10개의 보조 리전에 데이터를 복제합니다. 이를 통해 각 대륙 사용자에게 초저지연 로컬 읽기를 제공하고, 주 리전 장애 시 보조 리전을 주 리전으로 승격하여 RTO 1분 미만, RPO 1초 미만으로 비즈니스를 완벽히 복구할 수 있습니다. 일일 스냅샷 복제는 RPO가 최대 24시간에 달해 요건을 만족할 수 없으며, 단일 리전 복제본은 타 리전 재해 복구를 제공하지 못합니다.

Q5. Amazon RDS Multi-AZ DB 인스턴스 배포에서 유지되는 대기(Standby) 복제본에 대한 설명으로 옳은 것 두 가지를 고르세요.

정답은 첫 번째(동기식 복제)와 네 번째(DNS 레코드 전환 장애 조치)입니다!
Multi-AZ DB 인스턴스의 대기 인스턴스는 동일 리전 내 다른 AZ에 위치하며 완전 동기식으로 데이터를 복제합니다. 장애가 발생하면 RDS가 DNS 레코드를 대기 인스턴스로 자동 전환하여 장애 조치를 완료합니다.
오답 분석: 대기 인스턴스는 평상시에 절대로 읽기 트래픽을 처리할 수 없습니다(읽기 분산은 읽기 전용 복제본의 역할). 또한 Multi-AZ 인스턴스는 같은 리전 내에서만 동작하며, 다른 리전에 두는 것은 교차 리전 읽기 전용 복제본의 영역입니다.

Q6. 한 소프트웨어 개발팀이 내부 테스트용 Aurora MySQL 데이터베이스를 운영하고 있습니다. 이 데이터베이스는 평일 업무 시간에만 개발자들에 의해 간헐적으로 사용되며, 야간과 주말에는 일체의 데이터베이스 접근이 전혀 발생하지 않습니다. Aurora의 고유 기능과 MySQL 호환성을 유지하면서 데이터베이스 컴퓨팅 인프라 비용을 최소화할 수 있는 가장 효과적인 방안은 무엇입니까?

정답은 Aurora Serverless v2 전환 및 최소 0 ACU 설정입니다! Aurora Serverless v2에서 최소 용량을 0 ACU로 설정하면, 지정된 시간 동안 연결이 없을 때 인스턴스가 자동으로 일시 중지(Auto-Pause)되어 컴퓨팅 비용이 0원이 됩니다. 새로운 연결 요청이 들어오면 약 15초 내외로 자동 재개됩니다. 가장 작은 고정 인스턴스라도 쉬는 시간 동안 시간당 요금이 계속 부과되며, Auto Scaling은 리더 복제본만 조절할 뿐 주 라이터 인스턴스의 기본 비용을 없애지 못합니다.

Q7. 새로 출시된 글로벌 모바일 게임의 인기로 인해 RDS 데이터베이스의 사용자 데이터 증가 속도를 사전에 가늠하기 어렵습니다. 관리자가 일일이 모니터링하지 않더라도 스토리지 용량 고갈로 인한 데이터베이스 다운타임을 완벽히 방지하고, 예상치 못한 과도한 비용 청구를 통제할 수 있는 가장 적합한 기능은 무엇입니까?

정답은 RDS 스토리지 자동 확장 활성화 및 최대 임곗값 설정입니다! 스토리지 자동 확장은 남은 스토리지 여유 공간이 10% 미만으로 떨어져 5분 이상 지속되면 자동으로 용량을 증설합니다. 또한 사용자가 정의한 '최대 스토리지 임곗값'까지만 증설되므로 예산을 초과하는 무제한 확장을 방지할 수 있습니다. 수동 증설은 운영 오버헤드가 크고 야간 장애에 취약하며, 처음부터 최대 크기를 잡는 것은 극심한 비용 낭비입니다.

Q8. (0017 DR 복습) 전자금융 규제 준수를 위해 회사의 프로덕션 RDS 데이터베이스 백업을 반드시 최소 1년(365일) 이상 안전하게 보관해야 하며, 해당 DB 인스턴스가 실수로 종료 및 삭제되더라도 백업 데이터는 온전히 보존되어야 합니다. RDS의 기본 자동 백업(Automated Backup)만으로 이 요구 사항을 충족할 수 없는 이유와 올바른 대응 방안은 무엇입니까?

정답은 자동 백업의 최대 보존 기간이 35일이고 인스턴스 삭제 시 함께 삭제되기 때문입니다! RDS 자동 백업의 보존 기간은 0일에서 최대 35일까지로 제한되어 있어 1년 보관 규정을 충족할 수 없습니다. 또한 DB 인스턴스를 삭제하면 자동 백업도 함께 제거됩니다. 반면 수동 스냅샷(Manual Snapshot)이나 AWS Backup을 사용하면 DB 인스턴스가 삭제되어도 스냅샷이 영구적으로 보존되며, 수년간 안전하게 보관할 수 있습니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속 기억만으로 정리해 보세요.
(1) Multi-AZ DB 인스턴스, Multi-AZ DB 클러스터, 읽기 전용 복제본(Read Replica)의 세 가지 방식을 복제 방식(동기/반동기/비동기), 복제본의 읽기 쿼리 가능 여부, 배포 가용 범위 측면에서 비교해 보세요.
(2) Amazon Aurora의 클러스터 볼륨 스토리지 아키텍처(사본 수, AZ 수, 복제 lag), Aurora Auto Scaling, Aurora Serverless v2(0 ACU), Global Database의 핵심 특징을 각각 설명해 보세요.
(3) 시험 문제에서 Amazon RDS Proxy를 반드시 정답으로 떠올려야 하는 핵심 키워드 3가지를 적어 보세요.

(1) 세 가지 복제 방식 완벽 비교:
- Multi-AZ DB 인스턴스: 동기식 복제, 대기 인스턴스는 읽기 절대 불가, 동일 리전 2개 AZ, DNS 전환을 통한 자동 장애 조치(보통 60~120초).
- Multi-AZ DB 클러스터: 반동기식 복제, 2개의 리더 복제본 모두 읽기 처리 가능, 동일 리전 3개 AZ, 최신 리더로 자동 장애 조치.
- 읽기 전용 복제본 (Read Replica): 비동기식 복제, 읽기 트래픽 처리 가능, 동일 리전 및 다른 리전(Cross-Region) 가능, 장애 시 수동으로 독립 DB로 승격 (표준 RDS는 복제본 자동 확장 미지원).

(2) Aurora 아키텍처 핵심 요약:
- 클러스터 볼륨: 3개 AZ에 걸쳐 6개의 사본 분산 저장, 4/6 쓰기 쿼럼, 자가 치유 스토리지, 복제본 지연 시간 수십 밀리초 이하(동일 스토리지 공유), 최대 15개 복제본 지원.
- Aurora Auto Scaling: CPU 또는 커넥션 지표에 따라 Aurora 읽기 복제본을 자동 증설/축소.
- Aurora Serverless v2: 0.5 ACU 단위 즉각 확장, 최소 0 ACU 설정 시 미사용 시 자동 일시 중지(컴퓨팅 요금 0원, 15초 내 자동 재개).
- Aurora Global Database: 전용 스토리지 복제 계층을 통해 1초 미만 지연으로 최대 10개 보조 리전에 복제, 리전 재해 시 1분 미만 RTO 복구.

(3) RDS Proxy 핵심 키워드:
- 수천 개의 AWS Lambda 동시 실행 환경
- Too many connections (연결 고갈) 오류 해결
- Multi-AZ 장애 조치(Failover) 시간 최대 66% 단축 및 AWS Secrets Manager 자격 증명 연동 (하드코딩 제거).

추가 학습 및 실습

1차 공식 문서 정독 (10분 투자): AWS 공식 설명서의 "Working with DB instance read replicas" 문서를 정독하세요. 읽기 복제본의 사용 사례, Multi-AZ 배포와의 결합 아키텍처, 교차 리전 복제본을 활용한 재해 복구(DR) 절차가 그림과 함께 명확하게 설명되어 있습니다.

실습 가이드 (비용 절감 주의): AWS 콘솔에서 프리 티어(db.t3.micro/db.t4g.micro)를 선택하여 RDS for MySQL 인스턴스를 단일 AZ로 생성해 보고, 인스턴스 수정(Modify) 메뉴에 들어가 Multi-AZ 설정 옵션과 스토리지 자동 확장(Storage Auto Scaling) 임곗값 지정 화면을 눈으로 확인해 보세요. Multi-AZ나 복제본을 실제로 활성화하면 인스턴스 요금이 2배로 청구되므로 실습 확인 후 인스턴스를 즉시 삭제하세요.

궁금한 점이 있으신가요?

퀴즈 점수와 헷갈렸던 문제를 확인해 보세요. 특히 Q2(Multi-AZ 대기는 읽기가 불가능하다는 점)와 Q3(Lambda의 연결 고갈은 RDS Proxy로 해결한다는 점)은 실무와 시험 모두에서 매번 등장하는 핵심 포인트입니다. 궁금한 점이 있다면 언제든 질문해 주세요. 다음 레슨(0022)에서는 초저지연 NoSQL의 절대강자 DynamoDB와 인메모리 캐시 ElastiCache를 파헤칩니다!
