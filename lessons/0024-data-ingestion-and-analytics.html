데이터 분석 서비스는 얼핏 이름도 많고 복잡해 보이지만, 시험에서는 항상 일관된 흐름을 묻습니다. 바로 "수집(Ingestion) → 저장(Storage) → 변환·카탈로그(Transform & Catalog) → 조회(Query) → 시각화(Visualization)"로 이어지는 파이프라인의 각 단계에 어떤 서비스를 배치해야 가장 효율적인가 하는 점입니다. 오늘 레슨을 통해 이 전체 데이터 파이프라인의 큰 그림과 핵심 선택 기준을 머릿속에 확실히 정리해 둡니다.

왜 데이터 수집과 분석을 배워야 할까요?

시험 관점: SAA-C03 시험 가이드의 Task 3.5는 실시간 스트리밍 수집(Kinesis), 데이터 변환 및 카탈로그화(AWS Glue, CSV에서 Parquet 변환), 대화형 분석과 거버넌스(Amazon Athena, AWS Lake Formation), 비즈니스 인텔리전스 시각화(Amazon Quick / QuickSight), 대규모 빅데이터 처리용 분산 컴퓨팅(Amazon EMR), 그리고 데이터 수집 경로의 보안(VPC 엔드포인트 및 KMS 암호화)을 명시적으로 요구합니다.[1]
실무 관점: "애플리케이션 로그나 IoT 센서 데이터를 S3에 모아 두고, 서버 없이 표준 SQL로 빠르게 분석하여 비즈니스 대시보드로 보고 싶다"는 요구는 거의 모든 엔지니어링 조직에서 반복해서 마주치는 핵심 과제입니다. 관리할 서버가 없는 완전 서버리스 데이터 레이크 아키텍처를 올바르게 구성하면, 복잡한 인프라 운영 부담 없이 단 하루 만에 안정적인 엔드투엔드 파이프라인을 구축할 수 있습니다.

한눈에 보는 파이프라인

수집: Kinesis Data Streams vs Amazon Data Firehose

스트리밍 데이터를 실시간으로 받아들이는 서비스는 크게 두 가지가 있습니다. 공식 명칭부터 확인하면, 과거 Kinesis Data Firehose로 불리던 서비스는 현재 공식 문서상 Amazon Data Firehose로 명칭이 변경되었습니다. 시험 문제에는 두 명칭이 혼용되어 출제될 수 있으나 완벽히 동일한 서비스입니다.[4] 두 서비스의 동작 원리와 차이점을 명확히 짚어보겠습니다.

구분Kinesis Data Streams (KDS)Amazon Data Firehose
한 줄 정의대량의 연속 스트림 데이터를 실시간으로 수집하고 처리하는 플랫폼. 레코드 인입 후 소비까지 보통 1초 미만(밀리초 단위) 소요[2]스트리밍 데이터를 지원되는 목적지 저장소로 자동 배달(전송)하는 완전 관리형 서비스. 사용자가 소비자 애플리케이션을 개발하거나 인프라를 프로비저닝할 필요가 전혀 없음[4]
데이터 소비 방식소비자(Consumer) 애플리케이션 코드를 직접 작성(Kinesis Client Library(KCL), AWS SDK, AWS Lambda 등). 서로 다른 목적을 가진 여러 애플리케이션이 동일한 스트림을 각자의 속도로 독립적으로 읽을 수 있음[2]목적지만 지정하는 구성 방식: Amazon S3, Amazon Redshift, Amazon OpenSearch Service, Splunk, Apache Iceberg 테이블, 사용자 지정 HTTP 엔드포인트 등으로 자동 적재[4]
데이터 보관 및 재처리기본 24시간에서 설정에 따라 최대 365일(8,760시간)까지 보관 가능. 데이터 보관 기간 내에는 과거 특정 시점으로 오프셋을 되돌려 데이터를 처음부터 다시 읽거나 재처리(Replay)할 수 있음[3]내부적인 영구 보관소가 아님. 지정한 버퍼 크기(1~128MB) 또는 버퍼 간격(60~900초) 조건 중 먼저 충족되는 시점에 데이터를 묶어서 목적지로 밀어 넣음(근실시간)[4]
용량 관리 모드온디맨드 모드(용량 계획 없이 트래픽에 맞춰 자동 확장) 또는 프로비저닝 모드(필요한 처리량에 맞춰 샤드(Shard) 개수를 직접 지정)[5]완전 서버리스로 인입되는 데이터 볼륨에 따라 자동 확장
인라인 변환소비자 애플리케이션 코드 내부에서 직접 비즈니스 로직으로 처리배달 도중에 AWS Lambda를 호출하여 인라인 데이터 변환 가능.[6] 인입된 JSON 데이터를 압축률이 높은 Parquet 또는 ORC 컬럼형 형식으로 자동 변환하여 S3에 저장 가능(스키마는 Glue Data Catalog를 참조)[7]

선택 가이드: "초 단위 이하의 극도로 빠른 실시간 반응", "동일한 스트림을 여러 분석 시스템이 각자 독립적으로 읽어야 함", "과거 데이터를 다시 재생하여 재처리해야 함"이라는 조건이 붙는다면 무조건 Kinesis Data Streams를 선택해야 합니다. 반면 "데이터를 가공하거나 그대로 S3, Redshift, OpenSearch에 단순 적재만 하면 된다", "소비자 코드를 작성하거나 인프라를 관리하고 싶지 않다(최소 운영 오버헤드)"라는 조건이 나오면 Amazon Data Firehose가 정답입니다. 실무에서는 대량의 실시간 데이터를 KDS로 먼저 안전하게 흡수한 뒤, 실시간 경보 시스템은 KDS에서 직접 읽고 장기 저장은 Firehose를 연결해 S3로 쏟아붓는 하이브리드 아키텍처도 매우 널리 쓰입니다.

참고: Kinesis 제품군에는 동영상 및 오디오 스트림을 안전하게 수집·처리하는 Kinesis Video Streams와, 스트리밍 데이터 위에서 실시간으로 복잡한 SQL 쿼리나 Apache Flink 코드를 실행하는 Amazon Managed Service for Apache Flink(구 Kinesis Data Analytics)도 있습니다. 영상 데이터는 Video Streams, 스트림 상의 실시간 윈도우 집계 및 패턴 감지는 Flink로 기억해 두시면 충분합니다.[2]

변환과 카탈로그: AWS Glue

AWS Glue는 완전 관리형 서버리스 데이터 통합(ETL: Extract, Transform, Load) 서비스입니다. 데이터 탐색부터 스키마 추론, 변환 작업, 그리고 중앙 메타데이터 저장소 역할을 하는 카탈로그까지 통합 제공합니다.[8]

  • Glue Data Catalog: 데이터 레이크에 저장된 파일들의 테이블 정의, 스키마(컬럼 이름, 데이터 타입), 파일 위치, 파티션 정보를 모아 둔 중앙 메타데이터 저장소입니다. Apache Hive 메타스토어와 완벽히 호환되며, Amazon Athena, Amazon EMR, Amazon Redshift Spectrum 같은 분석 엔진들이 이 카탈로그를 조회하여 S3 파일들을 마치 일반 데이터베이스 테이블처럼 인식하고 쿼리할 수 있게 해 줍니다.[8]
  • Glue 크롤러(Crawler): S3, RDS, DynamoDB 등의 원천 저장소를 주기적으로 스캔하여 데이터 형식을 스스로 파악하고, 스키마를 자동으로 추론해 Glue Data Catalog에 테이블을 생성하거나 최신 상태로 업데이트합니다. 특히 S3 경로가 year=2026/month=11/day=17/ 같은 하이브(Hive) 스타일 폴더 구조로 되어 있다면 이를 날짜별 파티션(Partition)으로 자동 인식하여 등록해 줍니다.[9]
  • Glue ETL 작업: 서버리스 Apache Spark 환경 위에서 실행되는 분산 변환 작업입니다. 사용자가 서버를 띄우거나 관리할 필요 없이 스케줄러, 온디맨드, 또는 이벤트(EventBridge)에 의해 자동으로 실행됩니다.[8] 시험에서 자주 나오는 "S3에 쌓인 원본 CSV/JSON 로그를 쿼리 성능이 뛰어나고 압축률이 높은 Parquet 형식으로 주기적으로 일괄 변환한다"는 요구의 표준 해법이 바로 Glue ETL 작업입니다.[11]

조회: Athena, 그리고 왜 Parquet인가

Amazon Athena는 S3 데이터 레이크에 저장된 정형·반정형 데이터를 표준 SQL 문법으로 손쉽게 대화형 쿼리(Interactive Query)할 수 있는 완전 서버리스 분석 서비스입니다. 데이터베이스 서버나 클러스터를 전혀 프로비저닝할 필요가 없으며, 실제로 실행한 쿼리가 스캔한 데이터의 양(TB 단위)에 비례해서만 비용을 지불합니다(1TB 스캔당 $5 수준).[10] 따라서 Athena의 성능을 극대화하고 비용을 파격적으로 절감하는 핵심 원리는 단 하나, "쿼리가 읽어 들이는 S3 데이터 스캔량을 최소화하는 것"입니다.

최적화 기법구체적인 동작 원리와 효과
컬럼형(Columnar) 형식 변환
(Apache Parquet, ORC)		CSV나 JSON 같은 행 기반(Row-oriented) 형식은 특정 컬럼 하나만 필요해도 행 전체 데이터를 디스크에서 전부 읽어야 합니다. 반면 Parquet 같은 컬럼 기반 형식은 필요한 컬럼의 데이터 블록만 골라서 읽으며, 데이터 타입별 압축률이 매우 뛰어납니다. 또한 블록 헤더에 저장된 통계값을 활용해 조건에 맞지 않는 블록 자체를 통째로 건너뛰는 프레디케이트 푸시다운(Predicate Pushdown)이 적용되어 스캔 데이터양과 비용이 80~90% 이상 절감됩니다.[11]
파티셔닝(Partitioning)
(예: 날짜, 리전별 디렉터리 분할)		데이터를 날짜별(예: /year=2026/month=11/)로 분할하여 S3에 저장해 두면, 쿼리의 WHERE 절에 해당 날짜 조건을 걸었을 때 관련 없는 날짜의 파일들을 아예 열어보지도 않는 파티션 프루닝(Partition Pruning)이 일어납니다. 수 테라바이트의 전체 로그 중 분석 대상이 되는 특정 기간의 파일만 핀포인트로 스캔하므로 쿼리 속도가 수십 배 빨라지고 비용도 크게 줄어듭니다.[12]

거버넌스: Lake Formation

AWS Lake Formation은 S3 기반 데이터 레이크의 구축, 보안, 거버넌스를 중앙에서 간편하게 구성하고 관리해 주는 서비스입니다. 기존 S3 버킷 정책이나 IAM 정책만으로는 달성하기 어려운 세분화된 접근 제어(Fine-grained Access Control)를 제공합니다.[13]

왜 S3 버킷 정책만으로 부족할까요? S3 버킷 정책은 특정 객체나 접두사(Prefix, 폴더) 단위로만 접근 권한을 줄 수 있습니다. 만약 하나의 파일(테이블) 안에 일반 고객 정보와 주민등록번호·신용카드 같은 민감 정보(PII)가 함께 섞여 있다면, S3 권한만으로는 특정 팀에게 "이메일 컬럼만 보여주고 카드번호 컬럼은 가리는" 식의 제어가 불가능합니다. Lake Formation은 데이터베이스, 테이블 수준은 물론, 특정 열(Column), 특정 행(Row), 나아가 특정 셀(Cell) 수준까지 RDBMS의 GRANT/REVOKE처럼 세밀하게 권한을 통제할 수 있습니다. 이 보안 규칙은 Athena, Redshift Spectrum, EMR, Glue, Amazon QuickSight에 일관되게 적용되며, 조직 내 여러 계정 간의 안전한 데이터 공유도 중앙 집중식으로 관리합니다.[13]

시험 힌트: 문제에 "분석가 그룹별로 고객 개인정보(PII)가 포함된 특정 열(Column)만 숨기거나 마스킹해야 한다", "데이터 레이크의 권한을 S3 버킷 정책이 아닌 단일 창구에서 행·열 단위로 세밀하게 관리하고 싶다"는 표현이 나오면 주저 없이 AWS Lake Formation을 떠올려야 합니다.

처리: EMR (Amazon EMR)

Amazon EMR(과거 Elastic MapReduce)은 Apache Hadoop, Apache Spark, Apache Hive, Presto, Trino, HBase 같은 검증된 오픈 소스 빅데이터 분석 프레임워크를 AWS 상에서 손쉽게 대규모로 실행할 수 있도록 지원하는 관리형 분산 클러스터 플랫폼입니다.[14]

시험에서 EMR이 정답이 되는 핵심 시나리오는 명확합니다: "온프레미스에서 이미 운영 중이던 수백 개의 기존 Apache Spark나 Hadoop 분산 처리 스크립트를 코드 변경 없이 그대로 AWS로 이전(Lift-and-Shift)하려 할 때", 혹은 "페타바이트 규모의 대규모 데이터를 클러스터의 메모리 및 컴퓨팅 자원을 세밀하게 튜닝하며 분산 처리해야 할 때"입니다. 단순한 표준 SQL 조회라면 서버 관리가 전혀 없는 Athena가 훨씬 유리하고, 정형적인 ETL 데이터 파이프라인이라면 완전 서버리스인 AWS Glue가 운영 부담 면에서 더 우수합니다.

시각화: Amazon Quick (구 QuickSight)

공식 시험 안내서에는 시각화 서비스 항목이 "Amazon Quick"으로 기재되어 있습니다.[1] 최근 AWS 공식 문서는 이 비즈니스 분석 제품군 전체를 AWS Quick이라 부르고, 대화형 시각화 및 BI 대시보드 제작 기능을 AWS Quick Sight로 세부 안내하고 있습니다.[15] 시험 문제의 보기에 QuickSight, Amazon Quick, AWS Quick Sight 중 어떤 이름이 표기되어 있더라도 "다양한 원천 데이터(Athena, RDS, Redshift, S3 등)에 직접 연결하여 초고속 인메모리 엔진(SPICE)을 바탕으로 대화형 대시보드와 리포트를 제공하는 완전 관리형 BI 서비스"로 이해하시면 됩니다.

수집 지점 보안

  • 저장 시 암호화(Encryption at Rest): Kinesis Data Streams는 AWS KMS 기반 서버 측 암호화(SSE)를 지원하여 데이터가 샤드에 저장되기 전에 안전하게 암호화되도록 보장합니다. 서로 다른 AWS 계정 간에 스트림 데이터를 읽고 쓰려면, KMS 키 정책(Key Policy)과 외부 계정의 IAM 역할 정책 양쪽 모두에 암호화/복호화 권한이 반드시 명시되어야 합니다(0002 리소스 기반 정책의 교차 계정 규칙).[16]
  • 사설 네트워크 경로(Private Connectivity): 프라이빗 서브넷에 위치한 데이터 생산자(EC2 인스턴스, Lambda 등)가 Kinesis로 데이터를 전송할 때 인터넷 게이트웨이나 NAT 게이트웨이를 거치지 않으려면, AWS PrivateLink 기반의 인터페이스 VPC 엔드포인트(Interface VPC Endpoint)를 생성해야 합니다. 이렇게 하면 모든 트래픽이 AWS 내부 프라이빗 백본망을 통해서만 이동하며, VPC 엔드포인트 정책이나 IAM 조건 키(aws:sourceVpce)를 걸어 오직 인가된 내부 경로를 통해서만 데이터 인입이 가능하도록 강력히 격리할 수 있습니다.[17]
  • 데이터 레이크 거버넌스 및 감사: 데이터 레이크로 유입된 데이터는 Lake Formation을 통해 분석가별로 허용된 열과 행만 열람할 수 있도록 엄격히 제어하며, 모든 데이터 접근 내역은 AWS CloudTrail을 통해 상세히 감사 로그로 보관합니다.[13]

시험에 자주 나오는 핵심 패턴: 키워드 → 정답 공식

실시간 스트리밍, 다중 독립 소비자, 데이터 재생(Replay) → Kinesis Data Streams · S3/Redshift/OpenSearch에 단순 적재, 코드 및 서버 관리 없음 → Amazon Data Firehose · S3 원본 데이터에 즉각적인 애드혹(Ad-hoc) SQL 질의, 완전 서버리스 → Amazon Athena · 데이터 원천을 탐색해 자동으로 스키마 및 파티션 발견 → AWS Glue 크롤러 & Data Catalog · CSV/JSON을 Parquet로 일괄 변환 → AWS Glue ETL(또는 Firehose 포맷 변환, Athena CTAS) · Athena 쿼리 비용 절감 및 속도 향상 → Parquet 컬럼형 변환 + 날짜별 파티셔닝 · 특정 열(컬럼)이나 행(로우) 단위의 세밀한 권한 통제 → AWS Lake Formation · 기존 온프레미스 Hadoop/Spark 작업 이전, 클러스터 튜닝 → Amazon EMR · 인터랙티브 대시보드 및 리포트 시각화 → Amazon Quick (Quick Sight)

연습

Q1. 대규모 전자상거래 웹사이트의 클릭스트림 데이터를 초 단위 이하로 수집해야 합니다. 하나의 애플리케이션은 실시간 통계 집계를 수행해야 하고, 또 다른 독립된 애플리케이션은 동일한 원본 데이터를 S3에 아카이빙해야 합니다. 또한 장애 발생 시 과거 데이터를 특정 시점부터 다시 읽어 복구할 수 있어야 합니다. 가장 적합한 서비스는 무엇입니까?

정답은 Kinesis Data Streams(KDS)입니다.
KDS는 실시간 대용량 스트리밍 인입을 담당하며, 서로 다른 목적을 가진 여러 소비자 애플리케이션이 동일한 스트림 데이터를 각자의 처리 속도에 맞춰 완전히 독립적으로 읽어갈 수 있습니다. 또한 데이터 보관 기간(기본 24시간, 최대 365일)이 제공되므로 장애 발생 시 샤드의 오프셋을 과거 시점으로 되돌려 데이터를 안전하게 다시 읽기(재처리)할 수 있습니다.
- 오답 분석: - Amazon Data Firehose: 지정된 단일 목적지로 데이터를 자동 배달하는 서비스입니다. 사용자가 직접 작성한 여러 소비자 앱이 각자의 로직으로 동시에 읽거나 과거 시점으로 오프셋을 되돌려 재처리하는 아키텍처를 지원하지 않습니다. - Amazon SQS: 큐 방식은 한 소비자가 메시지를 읽어 처리한 뒤 삭제(Delete)하는 파괴적 읽기 모델입니다. 따라서 여러 독립된 애플리케이션이 동일한 메시지를 동시에 각각 소비해야 하는 시나리오에는 단독으로 적합하지 않습니다(SNS 팬아웃을 함께 조합해야 함). - AWS Glue 스트리밍 ETL: 데이터 변환 작업 엔진이지 대용량 다중 소비자를 위한 스트리밍 수집 저장소 플랫폼이 아닙니다.

Q2. 수만 대의 IoT 센서에서 생성되는 실시간 JSON 로그를 Amazon S3 데이터 레이크에 Parquet 형식으로 저장하여 Amazon Athena로 빠르게 쿼리하려고 합니다. 개발 및 운영 오버헤드를 최소화하면서 이를 구현할 수 있는 가장 적합한 아키텍처는 무엇입니까?

정답은 Amazon Data Firehose의 레코드 형식 변환 기능 활성화입니다.
Amazon Data Firehose는 수집된 JSON 스트림 데이터를 S3에 쓰기 직전에 Parquet 또는 ORC 컬럼형 형식으로 자동 변환해 주는 내장 기능(Record Format Conversion)을 제공합니다. 스키마는 Glue Data Catalog를 참조하도록 지정하기만 하면 되며, 사용자가 서버 인프라를 띄우거나 별도의 변환 코드를 작성할 필요가 전혀 없으므로 "최소 운영 오버헤드" 요구에 완벽히 부합합니다.
- 오답 분석: - EC2 스크립트: 인스턴스 패치, 고가용성 구성, 스케일링, cron 모니터링 등 막대한 관리 부담이 발생합니다. - 상시 가동 EMR: 지속적인 클러스터 유지 비용과 인프라 관리 오버헤드가 발생하여 단순 포맷 변환용으로는 지나치게 과도합니다. - KDS 소비자 애플리케이션 직접 개발: 소비자 코드 작성, 배포, 인프라 관리가 수반되므로 운영 오버헤드가 큽니다.

Q3. 한 데이터 분석팀이 S3에 저장된 수 테라바이트(TB) 용량의 원본 CSV 웹 액세스 로그에 대해 매일 Amazon Athena로 쿼리를 실행하고 있습니다. 이로 인해 청구되는 Athena 쿼리 비용이 매우 큽니다. 대부분의 쿼리는 최근 7일 치 데이터 중 특정 몇 개 열(컬럼)만을 조건으로 조회합니다. 쿼리 성능을 대폭 끌어올리면서 비용을 가장 크게 줄일 수 있는 방법은 무엇입니까?

정답은 CSV 데이터를 Parquet 형식으로 변환하고 날짜별로 파티셔닝하는 것입니다.
Amazon Athena는 실행된 쿼리가 S3에서 스캔한 총 데이터 용량에 비례하여 과금됩니다. 행 기반의 CSV 대신 컬럼 기반의 Parquet 형식을 도입하면 쿼리가 요구하는 특정 컬럼 데이터만 디스크에서 읽어 들이므로 스캔량이 극적으로 감소합니다. 여기에 날짜별 파티셔닝을 적용하면 WHERE date >= ... 조건을 주었을 때 최근 7일 치 폴더 외의 과거 데이터는 아예 읽지 않고 건너뛰므로(Partition Pruning), 쿼리 응답 속도가 비약적으로 향상되고 비용을 80~90% 이상 획기적으로 줄일 수 있습니다.
- 오답 분석: - S3 Standard-IA 전환: 데이터 저장 요금은 일부 줄어들 수 있으나, Athena가 매일 데이터를 읽을 때마다 S3 데이터 검색(Retrieval) 요금이 추가로 발생하며, 정작 가장 큰 원인인 Athena의 쿼리 스캔 데이터양 자체는 1바이트도 줄어들지 않습니다. - 상시 EMR 배포: 클러스터 운영 비용과 복잡성이 상시 발생하여 비용 절감 목표에 역행합니다. - zip 압축: Athena는 분할 가능한(splittable) 압축 형식을 선호하며, 단순 압축 알고리즘 변경은 필요한 컬럼만 골라 읽는 근본적인 스캔량 감축을 만들어내지 못합니다.

Q4. 한 기업의 S3 데이터 레이크에 저장된 통합 고객 테이블에 대해 여러 분석 부서가 Amazon Athena를 사용해 쿼리합니다. 보안 규정상 마케팅 분석가는 고객의 이메일과 전화번호 같은 개인식별정보(PII) 열을 절대 열람할 수 없어야 하며, 재무 분석가는 특정 국가의 결제 행 데이터만 조회할 수 있어야 합니다. 최소한의 관리 노력으로 이 접근 제어를 구현하는 방법은 무엇입니까?

정답은 AWS Lake Formation을 도입하여 열 및 행 수준 권한을 부여하는 것입니다.
AWS Lake Formation은 S3 데이터 레이크와 Glue Data Catalog 상의 데이터에 대해 열(Column) 및 행(Row) 수준의 세밀한 권한 통제(Fine-grained Access Control)를 중앙에서 일괄 관리해 주는 전용 서비스입니다. 이를 통해 마케팅 분석가에게는 PII 열을 제외한 권한을 부여하고, 재무 분석가에게는 특정 국가 필터링 조건을 부여할 수 있으며, 이 통제는 Athena 쿼리 실행 시 즉시 강제 적용됩니다.
- 오답 분석: - S3 버킷 정책: S3는 객체 및 접두사(파일/폴더) 단위로만 접근 권한을 판단할 수 있으며, 하나의 파일 내부에 존재하는 특정 열이나 행을 분리해서 필터링할 수 없습니다. - 별도 CSV 사본 생성: 데이터 중복 저장 비용이 발생하고, 동기화 불일치 위험과 관리 오버헤드가 극심해집니다. - IAM 정책 Condition: IAM 정책 문법에는 파일 내부의 특정 데이터 열이나 필드 이름을 인식하여 차단하는 조건 키가 존재하지 않습니다.

Q5. 회사의 파트너사들이 매일 대량의 새로운 CSV 로그 파일을 S3 버킷에 업로드합니다. 새로 들어온 파일들의 스키마 변화를 자동으로 감지하여 중앙 메타데이터 카탈로그에 등록하고, 관리할 서버 없이 주기적으로 Parquet 형식으로 변환하여 저장하려 합니다. 이 요구 사항을 만족하는 두 가지 구성 요소는 무엇입니까? (두 개를 고르세요)

정답은 Glue 크롤러 구성(0)과 Glue ETL 작업 실행(3)입니다.
1. AWS Glue 크롤러는 주기적으로 S3 저장소를 탐색하여 새로운 파일과 스키마 변경 사항을 자동으로 감지하고, Glue Data Catalog 테이블 및 파티션 메타데이터를 자동으로 생성하고 갱신해 줍니다.
2. AWS Glue ETL 작업은 완전 서버리스 Spark 환경에서 실행되며, 원본 CSV 파일을 읽어 들여 압축률과 쿼리 성능이 뛰어난 Parquet 포맷으로 변환한 뒤 S3에 다시 저장하는 ETL 파이프라인을 손쉽게 구축할 수 있습니다.
- 오답 분석: - EC2 Hive 메타스토어: 서버 프로비저닝, 패치, 이중화 등 지속적인 운영 관리가 수반되므로 서버리스 지향에 어긋납니다. - Kinesis Video Streams: 비디오 및 오디오 미디어 스트리밍 전용 서비스로 일반 로그 파일 적재와 무관합니다. - S3 수명 주기 규칙: S3 수명 주기 기능은 스토리지 클래스 간의 이동(예: Standard → Glacier)이나 객체 삭제/만료만 수행할 수 있을 뿐, 파일 내부 데이터 형식을 CSV에서 Parquet로 변환하는 컴퓨팅 작업은 지원하지 않습니다.

Q6. 한 금융 기업이 사내 온프레미스 Hadoop 클러스터에서 운영하던 수백 개의 복잡한 Apache Spark 및 MapReduce 배치 작업들을 애플리케이션 코드 수정 없이 가장 빠르게 AWS로 마이그레이션하려고 합니다. 가장 적합한 서비스는 무엇입니까?

정답은 Amazon EMR 클러스터입니다.
Amazon EMR은 오픈 소스 빅데이터 프레임워크인 Apache Hadoop, Spark, Hive, Presto 등을 완벽히 지원하는 관리형 클러스터 서비스입니다. 기존 온프레미스 Hadoop 생태계에서 작성된 대규모 Spark/Hadoop 코드베이스를 거의 수정하지 않고 그대로 이식(Lift-and-Shift)하여 대규모 클러스터에서 분산 처리할 수 있습니다.
- 오답 분석: - Amazon Athena: S3 데이터에 대한 대화형 표준 SQL 조회 전용 엔진이며, 기존의 복잡한 Spark/MapReduce 분산 애플리케이션 코드를 직접 실행할 수 없습니다. - Amazon Quick: 비즈니스 인텔리전스(BI) 및 대시보드 시각화 도구입니다. - AWS Lake Formation: 데이터 레이크 거버넌스 및 세부 권한 통제 관리 도구입니다.

Q7. (복습 0006) 프라이빗 서브넷에 위치한 수십 대의 백엔드 EC2 인스턴스가 대량의 애플리케이션 로그를 Kinesis Data Streams로 직접 전송하고 있습니다. 보안 감사 결과, 이 전송 트래픽이 퍼블릭 인터넷 게이트웨이나 NAT 게이트웨이를 일절 거치지 않고 오직 사설망을 통해서만 이동해야 합니다. 가장 안전하고 적합한 네트워크 설계는 무엇입니까?

정답은 Kinesis Data Streams 전용 인터페이스 VPC 엔드포인트를 생성하는 것입니다.
Kinesis Data Streams는 AWS PrivateLink 기반의 인터페이스 VPC 엔드포인트(Interface VPC Endpoint)를 지원합니다. 이를 VPC 내 프라이빗 서브넷에 생성하면 프라이빗 IP를 가진 탄력적 네트워크 인터페이스(ENI)가 생성되며, 백엔드 EC2 인스턴스들은 인터넷 게이트웨이나 NAT 장치를 전혀 거치지 않고 AWS 글로벌 내부 사설 백본망을 통해서만 안전하게 Kinesis로 데이터를 전송할 수 있습니다.
- 오답 분석: - NAT 게이트웨이 경유: 인터넷을 경유하지 말아야 한다는 보안 요구 사항을 정면으로 위반합니다. - 게이트웨이 VPC 엔드포인트: AWS에서 게이트웨이 엔드포인트(Gateway Endpoint)를 지원하는 서비스는 오직 Amazon S3와 Amazon DynamoDB 단 두 가지뿐입니다. Kinesis용 게이트웨이 엔드포인트는 존재하지 않는 대표적인 함정 선택지입니다. - 탄력적 IP 할당: 프라이빗 인스턴스를 퍼블릭 인터넷에 직접 노출시키는 위험한 조치입니다.

Q8. (복습 0002·0008) 계정 A에 생성된 Kinesis Data Streams 스트림이 고객 관리형 KMS 키(CMK)를 사용하여 서버 측 암호화(SSE)되어 있습니다. 계정 B에서 실행되는 소비자(Consumer) IAM 역할이 이 스트림의 데이터를 복호화하여 안전하게 읽어가야 합니다. KMS 암호화 권한 관점에서 반드시 충족해야 하는 조건은 무엇입니까?

정답은 KMS 키 정책과 소비자 계정 IAM 정책 양쪽 모두에서 권한을 허용해야 한다는 것입니다.
AWS의 교차 계정(Cross-Account) 접근 제어 원칙에 따라, 리소스가 속한 계정(계정 A)과 접근을 요청하는 주체가 속한 계정(계정 B)이 다를 경우 반드시 양쪽 계정 모두에서 명시적 허용(Allow)이 이루어져야 합니다. 즉, 계정 A의 KMS 키 정책(Key Policy)에서 계정 B의 IAM 역할(또는 계정 루트)에 kms:Decrypt 권한을 위임해야 하고, 동시에 계정 B의 IAM 역할 정책에서도 해당 KMS 키에 대한 kms:Decrypt 권한을 명시적으로 부여해야 비로소 정상적인 복호화가 가능합니다.
- 오답 분석: - 한쪽 정책에만 허용 추가: 교차 계정 통신에서는 둘 중 어느 한쪽이라도 누락되면 접근이 즉시 거부(Implicit Deny)됩니다. - AWS 관리형 키 사용: AWS 관리형 키(예: aws/kinesis)는 키 정책을 사용자가 직접 편집할 수 없으므로 다른 계정과의 교차 계정 공유 자체가 아예 불가능합니다. 따라서 교차 계정 암호화 공유가 필요한 시나리오에서는 반드시 고객 관리형 키(Customer Managed Key)를 사용해야 합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속에서 직접 떠올려 적어 보세요.
(1) Kinesis Data Streams(KDS)와 Amazon Data Firehose를 구분하는 핵심 기술 기준 세 가지는 무엇인가요?
(2) 데이터 파이프라인의 5단계(수집 → 저장 → 카탈로그/변환 → 조회 → 시각화)에 배치되는 대표적인 AWS 서비스들과, 이 전체 레이크의 열/행 세분화 권한을 통제하는 서비스는 무엇인가요?
(3) Amazon Athena의 쿼리 실행 비용을 획기적으로 줄이고 조회 속도를 높이기 위한 두 가지 핵심 기법은 무엇인가요?

(1) KDS vs Firehose 핵심 차이:
- KDS: 밀리초~1초 미만의 실시간 수집, 사용자가 직접 소비자 애플리케이션(KCL, SDK, Lambda)을 개발, 여러 독립된 소비자가 동일 스트림을 동시 구독 가능, 최대 365일까지 데이터가 보관되어 장애 시 재처리(Replay) 가능, 샤드 기반 온디맨드/프로비저닝 용량 관리.
- Firehose: 버퍼링 조건(크기/시간) 충족 시 목적지로 밀어 넣는 완전 관리형 배달 서비스, 코드 작성이나 인프라 프로비저닝 불필요, S3/Redshift/OpenSearch 등으로 직접 적재, 인라인 Lambda 변환 및 JSON의 Parquet/ORC 자동 포맷 변환 지원.

(2) 파이프라인 5단계 서비스 및 거버넌스:
- 수집: Kinesis Data Streams, Amazon Data Firehose
- 저장: Amazon S3 (데이터 레이크)
- 카탈로그 및 변환: AWS Glue 크롤러 및 Data Catalog (메타데이터), AWS Glue ETL (서버리스 Spark 변환)
- 조회: Amazon Athena (서버리스 대화형 SQL), Amazon EMR (오픈소스 Hadoop/Spark 대규모 클러스터)
- 시각화: Amazon Quick / QuickSight (인터랙티브 대시보드 BI)
- 거버넌스 및 권한 통제: AWS Lake Formation (데이터베이스, 테이블, 열, 행, 셀 단위의 세분화된 접근 권한 관리)

(3) Athena 비용 최적화 2대 기법:
- 컬럼형 저장 포맷(Parquet, ORC) 도입: 필요한 열만 디스크에서 스캔하고 높은 압축률과 프레디케이트 푸시다운을 통해 스캔 데이터양을 대폭 절감.
- 파티셔닝(Partitioning): 날짜나 리전 등의 조건에 따라 S3 폴더를 분할하여, 쿼리 조건에 해당하는 파티션 외의 파일들을 통째로 건너뜀(파티션 프루닝).

간단 실습 가이드 (비용 거의 없음): 간단한 CSV 로그 파일 몇 개를 생성하여 s3://내버킷이름/logs/dt=2026-11-16/과 같은 하이브 스타일 파티션 경로에 업로드해 보세요. 그 후 AWS Glue 콘솔에서 크롤러를 생성해 해당 버킷을 스캔하면 Glue Data Catalog에 dt가 파티션 컬럼으로 자동 생성되는 것을 확인할 수 있습니다. Athena 쿼리 편집기에서 SELECT * FROM 테이블이름 WHERE dt='2026-11-16'을 실행해 보고, 화면에 표시되는 '스캔된 데이터양(Data scanned)'이 파티션 조건이 없을 때와 비교해 얼마나 극적으로 줄어드는지 직접 확인해 보세요. 크롤러와 쿼리는 소량 테스트 시 몇 센트 미만으로 실습할 수 있습니다.
