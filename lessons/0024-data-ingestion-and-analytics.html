한 장으로 보는 파이프라인

수집: Kinesis Data Streams vs Amazon Data Firehose

서비스 이름부터 확인합니다. AWS 문서의 현재 이름은 Amazon Data Firehose입니다(예전 이름 Kinesis Data Firehose). 시험 보기에 둘 중 어느 이름이 나와도 같은 서비스입니다.[4]

Kinesis Data Streams (KDS)Amazon Data Firehose
한 줄 정의대량 스트림을 실시간으로 수집·처리. 넣고 꺼내기까지 보통 1초 미만[2]스트리밍 데이터를 목적지까지 배달하는 완전 관리형 서비스. "애플리케이션을 작성하거나 리소스를 관리할 필요 없음"[4]
소비 방식소비자 앱을 직접 작성(KCL, Lambda 등). 여러 앱이 같은 스트림을 독립적으로 읽을 수 있음[2]목적지 지정만: S3, Redshift, OpenSearch, Splunk, Iceberg 테이블, HTTP 엔드포인트 등[4]
데이터 보관기본 24시간, 최대 8760시간(365일). 보관 기간 안에는 다시 읽기(재처리) 가능[3]버퍼 크기(MB) 또는 버퍼 간격(초)이 차면 목적지로 배달[4]
용량온디맨드(용량 계획 불필요, 예측 불가 트래픽) 또는 프로비저닝(샤드 수 지정, 예측 가능 트래픽)[5]자동
변환소비자 코드에서 직접Lambda로 변환 후 배달 가능.[6] JSON을 Parquet/ORC로 변환해 S3에 저장 가능(스키마는 Glue Data Catalog에서 참조)[7]

고르는 법: "실시간 처리", "여러 소비자", "재처리", "밀리초~초 단위 반응"이면 KDS. "S3/Redshift/OpenSearch에 적재만", "코드 없이", "최소 운영"이면 Firehose. 둘을 이어 KDS로 받고 Firehose로 S3에 보관하는 구성도 흔합니다.

Kinesis 제품군에는 Kinesis Video Streams와 Managed Service for Apache Flink도 있습니다. 영상 스트림이면 Video Streams, 스트림 위에서 SQL/Flink로 실시간 분석이면 Flink라는 정도만 기억하세요.[2]

변환과 카탈로그: AWS Glue

AWS Glue는 서버리스 데이터 통합 서비스로, 데이터 탐색·ETL·정제·중앙 카탈로그를 한 서비스에 묶었습니다.[8]

  • Data Catalog: 테이블 정의(스키마, 위치, 파티션) 같은 메타데이터 저장소. Athena, EMR, Redshift Spectrum이 이 카탈로그로 바로 조회합니다.[8]
  • 크롤러: 데이터 저장소를 훑어 형식과 스키마를 추론하고 Data Catalog에 테이블을 만들거나 갱신합니다. 일정으로 반복 실행하면 새 파일과 파티션을 찾아 줍니다. S3의 year=2019/month=Jan/ 같은 폴더는 파티션으로 인식합니다.[9]
  • ETL 작업: Spark 기반 서버리스 엔진에서 실행. 일정·온디맨드·이벤트로 트리거합니다.[8] 시험의 ".csv → .parquet 변환"은 Glue 작업(또는 Athena CTAS 쿼리)이 정답입니다.[11]

조회: Athena, 그리고 왜 Parquet인가

Amazon Athena는 S3에 있는 데이터를 표준 SQL로 바로 분석하는 대화형 쿼리 서비스입니다. 서버리스라 설정할 인프라가 없고 실행한 쿼리에 대해서만 비용을 냅니다.[10] 그래서 Athena 비용·성능 최적화는 곧 스캔하는 데이터를 줄이는 것입니다.

기법효과
컬럼형 형식(Parquet, ORC)열 단위 압축, 필요한 블록만 읽는 predicate pushdown, 병렬 읽기 분할[11]
파티셔닝(예: 날짜별 폴더)쿼리마다 스캔하는 데이터 양을 제한해 성능 향상·비용 절감. WHERE에 파티션을 지정하면 그 파티션만 스캔[12]

거버넌스: Lake Formation

AWS Lake Formation은 S3 데이터 레이크의 데이터와 Glue Data Catalog 메타데이터에 대한 세분화된 접근 제어를 중앙에서 관리합니다. IAM 권한 모델을 보강하는 자체 권한 모델을 쓰며, RDBMS처럼 grant/revoke로 권한을 주고, 데이터베이스·테이블·열·행·셀 수준까지 제한합니다. 이 권한은 Athena, Redshift Spectrum, EMR, Glue, AWS Quick에서 강제됩니다. 여러 계정 간 데이터 공유도 지원합니다.[13]

시험 신호: "분석가 그룹마다 특정 열(PII)만 숨기고 싶다", "데이터 레이크 권한을 한곳에서" → Lake Formation. S3 버킷 정책으로 열 단위 제어는 할 수 없습니다.

처리: EMR

Amazon EMR(예전 Elastic MapReduce)은 Apache Hadoop, Apache Spark 같은 빅데이터 프레임워크를 실행하는 관리형 클러스터 플랫폼입니다.[14] 시험 신호: "기존 Hadoop/Spark 작업을 그대로 옮기고 싶다", "대규모 분산 처리를 직접 튜닝". 단순 SQL 조회라면 Athena가, 코드 최소 ETL이라면 Glue가 운영 부담이 더 적습니다.

시각화: Amazon Quick (구 QuickSight)

시험 가이드는 시각화 서비스를 "Amazon Quick"이라고 적습니다.[1] 이번에 확인한 AWS 문서(2026년 11월 기준)는 서비스를 AWS Quick이라 부르고, 대화형 시각화·BI 기능을 AWS Quick Sight로 소개합니다. 문서의 설명은 "AWS Quick은 Amazon QuickSight에서 발전했고, QuickSight는 Quick 안의 기능 AWS Quick Sight로 이어진다"입니다.[15] 즉 보기에 QuickSight, Amazon Quick, AWS Quick Sight 중 무엇이 나오든 "데이터 소스에 연결해 대시보드를 만드는 관리형 BI"로 읽으면 됩니다.

수집 지점 보안

  • 저장 시 암호화: KDS 서버 측 암호화는 지정한 KMS 키로 데이터가 저장되기 전에 암호화합니다. 다른 계정과 공유하면 KMS 키 정책 그리고 외부 계정의 IAM 정책 양쪽에 권한이 필요합니다(0002의 교차 계정 규칙).[16]
  • 사설 경로: VPC 안의 생산자는 인터페이스 VPC 엔드포인트(PrivateLink)로 KDS에 연결하면 인터넷 게이트웨이나 NAT 없이 AWS 네트워크 안에서 통신합니다. 엔드포인트 정책이나 IAM 조건 aws:sourceVpce로 특정 엔드포인트를 통한 접근만 허용할 수 있습니다.[17]
  • 데이터 레이크 접근: Lake Formation으로 열·행 단위 권한, CloudTrail로 접근 감사.[13]

시험 단골: 키워드 → 정답

실시간, 여러 소비자, 재처리 → Kinesis Data Streams · S3/Redshift에 적재만, 코드 없이 → Data Firehose · S3 데이터에 임시(ad-hoc) SQL, 서버리스 → Athena · 스키마 자동 발견 → Glue 크롤러 · CSV → Parquet → Glue ETL(또는 Firehose 형식 변환, Athena CTAS) · Athena 비용 절감 → Parquet + 파티셔닝 · 열·행 단위 권한 → Lake Formation · 기존 Hadoop/Spark → EMR · 대시보드 → Amazon Quick(Quick Sight)

연습

Q1. 웹 클릭스트림을 초 단위로 받아, 한 애플리케이션은 실시간 집계를 하고 다른 애플리케이션은 같은 데이터를 독립적으로 아카이브해야 합니다. 장애 시 지난 데이터를 다시 읽을 수 있어야 합니다. 가장 적합한 서비스는?

여러 소비자 앱이 같은 스트림을 독립적으로 읽고, 보관 기간(기본 24시간, 최대 365일) 안에서 다시 읽을 수 있는 것은 KDS입니다. Firehose는 목적지로 배달하는 서비스라 직접 작성한 여러 소비자가 재처리하는 구조가 아닙니다. SQS는 메시지를 소비하면 삭제하므로 여러 앱이 같은 메시지를 독립적으로 읽는 용도가 아닙니다(0014).

Q2. IoT 기기의 JSON 데이터를 S3에 Parquet 형식으로 쌓아 Athena로 조회하려 합니다. 운영 오버헤드가 가장 적은 방법은?

Firehose는 JSON을 Parquet/ORC로 변환해 S3에 저장할 수 있고, 스키마는 Glue Data Catalog에서 참조합니다. 코드도 서버도 없습니다. EMR과 EC2는 클러스터·인스턴스 관리가 필요하고, KDS 소비자 앱은 직접 작성·운영해야 합니다.

Q3. 분석팀이 S3에 쌓인 수 TB의 CSV 로그에 Athena로 매일 쿼리하는데 비용이 큽니다. 대부분 쿼리는 최근 7일, 몇 개 열만 봅니다. 비용을 가장 크게 줄이는 방법은?

Athena는 실행한 쿼리에 비용을 내므로 스캔량을 줄이는 것이 핵심입니다. 컬럼형 형식은 필요한 열과 블록만 읽고, 날짜 파티션은 WHERE로 지정한 기간만 스캔합니다. Standard-IA는 저장 요금을 줄이지만 자주 읽는 데이터라 조회 요금이 붙고 쿼리 스캔량은 그대로입니다(0018). 상시 EMR은 운영과 비용이 늘어납니다.

Q4. 데이터 레이크의 고객 테이블에서 마케팅 분석가는 이메일·전화번호 열을 볼 수 없어야 하고, 재무 분석가는 특정 국가 행만 봐야 합니다. 둘 다 Athena를 씁니다. 가장 적합한 방법은?

Lake Formation은 데이터베이스·테이블·열·행·셀 수준 권한을 중앙에서 관리하고, Athena 같은 분석 서비스에서 이를 강제합니다. 버킷 정책은 객체(접두사) 단위라 한 파일 안의 열을 가릴 수 없고, 사본을 만들면 관리 부담과 불일치가 생깁니다.

Q5. 새로운 CSV 파일이 매일 S3에 도착합니다. 스키마를 자동으로 파악해 카탈로그에 등록하고, 서버 관리 없이 Parquet로 변환해 두려 합니다. 어떤 조합이 맞습니까? (두 개를 고르세요)

크롤러가 스키마를 추론해 Data Catalog에 테이블을 만들고, 서버리스 Glue ETL 작업이 CSV를 Parquet로 변환합니다. EC2 메타스토어는 서버 관리가 필요하고, Video Streams는 영상용입니다. S3 수명 주기 규칙은 스토리지 클래스 전환과 만료만 할 뿐 파일 형식을 바꾸지 않습니다(0018).

Q6. 회사가 온프레미스 Hadoop 클러스터에서 돌던 Spark 작업 수백 개를 코드 변경을 최소화해 AWS로 옮기려 합니다. 가장 적합한 서비스는?

EMR은 Hadoop, Spark 같은 프레임워크를 실행하는 관리형 클러스터 플랫폼이라 기존 작업을 거의 그대로 옮길 수 있습니다. Athena는 SQL 조회, Quick은 시각화, Lake Formation은 권한 관리로 역할이 다릅니다.

Q7. (복습 0006) 프라이빗 서브넷의 EC2 생산자가 Kinesis Data Streams에 데이터를 보냅니다. 보안팀은 트래픽이 인터넷 게이트웨이나 NAT를 거치지 않기를 원합니다. 가장 적합한 방법은?

Kinesis Data Streams는 PrivateLink 기반 인터페이스 VPC 엔드포인트를 지원하며, 인터넷 게이트웨이나 NAT 없이 AWS 네트워크 안에서 통신합니다. 게이트웨이 엔드포인트는 S3와 DynamoDB 전용이라 함정입니다.

Q8. (복습 0002·0008) KDS 스트림이 고객 관리형 KMS 키로 서버 측 암호화되어 있습니다. 다른 계정의 소비자 역할이 이 스트림을 읽어야 합니다. KMS 측면에서 무엇이 필요합니까?

교차 계정은 양쪽이 모두 허용해야 합니다(0002 규칙 5). KDS 문서도 키 정책과 외부 계정 IAM 정책 양쪽에 권한을 주라고 합니다. 오히려 리소스 정책으로 공유하려면 AWS 관리형 키가 아니라 고객 관리형 키를 써야 합니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) KDS와 Firehose를 구분하는 기준 세 가지. (2) 파이프라인의 다섯 칸(수집·저장·카탈로그/변환·조회·시각화)에 들어가는 서비스, 그리고 권한은 누가 관리하나? (3) Athena 비용을 줄이는 두 가지 방법.

(1) KDS: 실시간, 소비자 앱을 직접 작성, 여러 소비자가 독립적으로 읽음, 보관 기간(기본 24시간~최대 365일) 동안 재처리, 온디맨드/프로비저닝 용량. Firehose: 완전 관리형 배달, 코드 없음, 버퍼가 차면 S3·Redshift·OpenSearch 등으로 적재, Lambda 변환과 Parquet/ORC 변환.

(2) 수집 Kinesis/Firehose → 저장 S3 → 카탈로그 Glue 크롤러·Data Catalog, 변환 Glue ETL → 조회 Athena(SQL)·EMR(Spark/Hadoop) → 시각화 Amazon Quick(Quick Sight). 권한은 Lake Formation이 열·행·셀 수준까지.

(3) Parquet/ORC 같은 컬럼형 형식으로 변환, 날짜 등으로 파티셔닝. 둘 다 스캔하는 데이터를 줄입니다.

더 해볼 것

1차 자료 (꼭 읽기, 10분): "Use columnar storage formats"와 이어지는 "Partition your data". 시험의 "Athena 비용 최적화"와 ".csv → .parquet"가 한꺼번에 정리돼 있습니다. (한국어: URL의 docs.aws.amazon.com/ 뒤에 ko_kr/)

실습 (선택, 거의 무료): 작은 CSV 몇 개를 s3://내버킷/logs/dt=2026-11-16/처럼 올리고, Glue 크롤러로 테이블을 만든 뒤 Athena에서 SELECT ... WHERE dt='2026-11-16'을 실행해 보세요. Athena 결과 화면에 표시되는 스캔 데이터 양을 파티션 조건이 있을 때와 없을 때 비교하면 오늘 내용이 손에 잡힙니다. 크롤러와 쿼리는 사용량만큼 과금되니 데이터는 작게 유지하세요.
