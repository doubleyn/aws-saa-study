늘리고 줄이고 바꾸기:
EC2 Auto Scaling의 조정 정책과 수명 주기

Auto Scaling 그룹(ASG)은 서비스 수요에 맞추어 "인스턴스를 몇 대 유지할지"와 "언제 인스턴스를 늘리고 줄일지"를 지능적으로 자동 관리해 주는 서비스입니다. AWS 시험에서는 주어진 트래픽 패턴과 요구사항에 맞추어 다섯 가지 조정 정책 중 최적의 방식을 고르는 시나리오와, 상태 확인(Health Check) 및 수명 주기 후크(Lifecycle Hook)의 세부 동작 원리를 파고드는 함정 문제가 단골로 출제됩니다.

왜 EC2 Auto Scaling을 배워야 할까요?

시험 관점: "예측할 수 없는 불규칙한 트래픽", "매주 특정 요일과 시간대에 집중되는 부하", "인스턴스 부팅과 애플리케이션 초기화에 오랜 시간이 소요됨", "인스턴스가 완전히 종료되기 전에 로그 파일을 안전하게 백업"과 같은 핵심 단서들이 제시됩니다. 이 단서들은 각각 대상 추적, 예약 조정, 예측 조정, 수명 주기 후크라는 서로 다른 기능을 정확하게 가리킵니다.
실무 관점: 앞선 레슨 0011에서 배운 탄력적 로드 밸런서(ALB/NLB) 뒤편에 여러 가용 영역(Multi-AZ)에 걸친 Auto Scaling 그룹을 배치하는 구조는, 고가용성과 내결함성을 갖춘 클라우드 웹 계층을 설계할 때 가장 기본적이면서도 강력한 표준 아키텍처입니다.

Auto Scaling 그룹의 뼈대: 최소·원하는·최대 용량, 시작 템플릿, 다중 AZ

Auto Scaling 그룹(ASG)은 동일한 역할을 수행하는 EC2 인스턴스들을 논리적인 하나의 단위로 묶어서 관리합니다. 관리자는 세 가지 기본 용량 속성을 설정하여 그룹의 크기를 제어합니다.[1]

  • 최소 용량(Minimum Capacity): 트래픽이 아무리 줄어들더라도 인스턴스 수가 이 값 아래로는 절대 줄어들지 않습니다. 최소한의 서비스 가용성을 보장하는 안전장치입니다.
  • 최대 용량(Maximum Capacity): 트래픽이 폭증하더라도 인스턴스 수가 이 한도를 초과하여 늘어나지 않습니다. 과도한 비용 청구를 막는 상한선 역할을 합니다.
  • 원하는 용량(Desired Capacity): Auto Scaling 그룹이 현재 시점에 실제로 유지하려고 노력하는 인스턴스 목표 개수입니다. 다양한 동적 조정 정책들은 이 원하는 용량 값을 최소 용량과 최대 용량 범위 내에서 자동으로 변경합니다.

참고로 Auto Scaling 서비스 자체에는 별도의 추가 요금이 부과되지 않으며, 그룹에 의해 실제로 시작되어 동작하는 EC2 인스턴스와 EBS 볼륨 등의 기본 리소스 요금만 지불합니다.[1]

핵심 구성 요소

  • 시작 템플릿(Launch Template): 인스턴스를 시작할 때 필요한 AMI ID, 인스턴스 패밀리 및 크기, 키 페어, 보안 그룹, 사용자 데이터(User Data) 스크립트 등의 모든 구성 정보를 담고 있는 청사진입니다. 시작 템플릿은 버전 관리를 지원하므로 애플리케이션 업데이트나 패치 시 손쉽게 버전을 롤백하거나 전환할 수 있습니다. 과거에 사용되던 시작 구성(Launch Configuration)은 더 이상 새로운 기능이 지원되지 않으며, 온디맨드 인스턴스와 스팟 인스턴스를 하나의 그룹에 혼합 구성하거나 여러 인스턴스 유형을 동시에 지정하여 가용성을 극대화하는 기능은 오직 시작 템플릿에서만 가능합니다.[3]
  • 다중 가용 영역(Multi-AZ) 분산과 자동 재조정(Rebalancing): Auto Scaling 그룹을 생성할 때 여러 가용 영역에 속한 서브넷들을 지정하면, ASG는 가용 영역 간에 인스턴스 개수를 항상 균등하게 맞추어 배포합니다. 만약 특정 가용 영역에 장애가 발생하여 인스턴스가 중단되면, ASG는 즉시 정상 동작 중인 다른 가용 영역에 새 인스턴스를 프로비저닝하여 서비스 가용성을 유지합니다. 이후 장애가 발생했던 가용 영역이 복구되면 ASG는 인스턴스 분포의 균형을 맞추기 위해 자동으로 재조정 활동을 수행합니다. 이때 서비스 중단을 방지하기 위해 새 인스턴스를 먼저 성공적으로 시작한 후, 기존의 초과 인스턴스를 안전하게 종료하는 방식을 취합니다.[2]
  • 로드 밸런서 대상 그룹 연동: Auto Scaling 그룹을 ALB나 NLB의 대상 그룹(Target Group)에 연결해 두면, 확장이 발생하여 새 인스턴스가 생성되는 즉시 대상 그룹에 자동으로 등록(Registration)되어 트래픽을 받기 시작하고, 축소되어 종료되는 인스턴스는 자동으로 등록 취소(Deregistration)되어 안전하게 트래픽이 차단됩니다.[1]

한눈에 비교하기: 수평 확장(Scale Out/In) vs 수직 확장(Scale Up/Down)

부하가 증가할 때 시스템 성능을 증설하는 방식에는 크게 두 가지 방향이 있습니다. 클라우드 아키텍처에서는 결함 격리와 무중단 운영을 위해 수평 확장을 강력하게 권장합니다.

구분수평 확장 (Scale Out / Scale In)수직 확장 (Scale Up / Scale Down)
확장 방법인스턴스의 개수(대수)를 늘리고 줄입니다. (Auto Scaling 그룹 활용)기존 인스턴스의 사양(유형)을 더 크거나 작게 바꿉니다. (예: t3.micro → c5.2xlarge)
서비스 중단 여부기존 인스턴스들이 정상 작동하는 상태에서 새 인스턴스가 추가되므로 무중단 확장이 가능합니다.EBS 기반 인스턴스는 인스턴스 유형을 변경하려면 반드시 인스턴스를 중지(Stop)한 후 변경하고 다시 시작해야 하므로 필연적으로 다운타임이 발생합니다.[15]
Well-Architected 관점AWS Well-Architected 신뢰성 기둥의 핵심 설계 원칙: "단일 대형 리소스에 의존하지 말고, 여러 개의 작은 리소스로 분산하여 단일 장애 지점(SPOF)의 영향을 최소화하라." 수평 확장은 하나의 인스턴스가 고장 나더라도 전체 서비스가 중단되지 않는 견고한 내결함성을 제공합니다.[14]

핵심 특징: 다섯 가지 조정 방식(Scaling Policies)

Auto Scaling 그룹은 워크로드의 성격과 예측 가능성에 따라 다양한 조정 방식을 제공합니다.

방식동작 원리적합한 시나리오
대상 추적
(Target Tracking)		관리자가 추적할 지표와 목표값(예: "평균 CPU 사용률 50% 유지", "대상당 요청 수 1,000건 유지")만 지정하면, Auto Scaling이 필요한 CloudWatch 경보를 직접 자동으로 생성하고 관리합니다. 실내 온도를 일정하게 맞추는 에어컨 온도 조절기(Thermostat)처럼 동작합니다.[5] AWS가 가장 강력하게 권장하는 기본 동적 조정 방식입니다.[4]트래픽 변동을 사전에 정확히 예측하기 어려운 대부분의 일반적인 웹/애플리케이션 부하.
단계 조정
(Step Scaling)		CloudWatch 경보의 임계값을 초과한 크기(격차)에 따라 단계별로 서로 다른 조정 크기를 적용합니다 (예: CPU 사용률이 임계값보다 10% 높으면 +1대, 30% 이상 폭증하면 +5대). CloudWatch 경보는 관리자가 직접 생성해야 합니다.[6]부하의 급격한 변동에 대응하여 경보 초과 정도에 따라 공격적이고 유연한 증설이 필요할 때.
단순 조정
(Simple Scaling)		단 하나의 CloudWatch 경보에 반응하여 고정된 수량만큼 조정하고, 조정 활동이 일어날 때마다 휴지 기간(Cooldown, 기본 300초) 동안 모든 추가 조정을 잠급니다. AWS는 지연 반응과 비효율성 때문에 단순 조정 정책의 사용을 지양하고 대상 추적이나 단계 조정을 사용할 것을 권장합니다.[7]시험 시나리오에서는 대부분 비권장되는 구형 방식이자 오답 보기로 자주 등장합니다.
예약 조정
(Scheduled Scaling)		특정 날짜와 시각(1회성 작업) 또는 cron 표현식 형태의 반복 주기에 맞추어 원하는 용량, 최소 용량, 최대 용량을 정해진 시점에 미리 변경합니다.[8]매주 월요일 오전 9시 업무 시작, 매월 말일 결산, 정기 세일 행사 등 트래픽 증가 시점을 정확히 알고 있을 때.
예측 조정
(Predictive Scaling)		최대 14일간의 과거 CloudWatch 사용량 지표를 머신러닝 알고리즘으로 분석하여 일간 및 주간 패턴을 학습한 뒤, 향후 48시간의 부하를 예측하여 트래픽 스파이크가 발생하기 전에 미리 선제적으로 인스턴스를 확장합니다. 최소 24시간 이상의 과거 데이터가 축적되어야 활성화되며, 오버프로비저닝을 방지하기 위해 예측 조정 단독으로는 축소(Scale-in)를 수행하지 않습니다 (축소는 대상 추적과 같은 동적 정책에 맡김).[10]주기적이고 반복적인 트래픽 패턴이 있으면서, 애플리케이션 부팅과 초기 설정에 10~20분 이상 오랜 시간이 걸려 동적 조정만으로는 초기 트래픽 급증을 제때 받아내지 못하는 환경.[9]

만약 동일한 Auto Scaling 그룹에 여러 정책이 구성되어 있고 동시에 발동된다면, Auto Scaling은 가용성을 최우선으로 보호하기 위해 가장 큰 용량을 요구하는 정책의 결정을 채택합니다.[4] 또한 예약 조정으로 기본 베이스라인 용량을 정해두고, 그 위에 대상 추적 정책을 결합하여 예측하지 못한 스파이크에 대응하는 하이브리드 구성도 실무에서 널리 활용됩니다.[8]

대상 추적에 적합한 지표 고르기

대상 추적 정책이 정상적으로 작동하려면 선택하는 지표가 인스턴스 개수와 정비례하거나 반비례하는 관계를 가져야 합니다. 즉, 인스턴스 수가 2배로 늘어나면 지표 값이 절반(1/2)으로 떨어지는 특성을 가진 지표여야만 시스템이 안정적으로 수렴할 수 있습니다.[4]

  • 적합한 지표 (미리 정의된 표준 지표):
    • ASGAverageCPUUtilization: 그룹 전체 인스턴스의 평균 CPU 사용률 (인스턴스를 늘리면 평균 사용률이 즉시 희석되어 내려감)
    • ALBRequestCountPerTarget: ALB 대상 그룹에 속한 정상 인스턴스 1대당 처리하는 평균 요청 수 (인스턴스가 늘어나면 1대당 할당되는 요청 수가 감소함)
    • ASGAverageNetworkIn / ASGAverageNetworkOut: 인스턴스당 평균 네트워크 인/아웃 바이트 수
  • 부적합한 지표 (오답 단골 함정):
    • 로드 밸런서의 전체 요청 수(RequestCount): 외부에서 유입되는 총 요청 수는 인스턴스를 아무리 늘려도 줄어들지 않으므로, ASG가 인스턴스를 최대치까지 무한정 증설해 버립니다.
    • 로드 밸런서 요청 지연 시간(TargetResponseTime / Latency): 지연 시간은 백엔드 데이터베이스 병목, 외부 API 지연, 락(Lock) 경합 등 서버 대수와 무관한 다양한 요인으로 발생하므로 인스턴스 수 증감과 선형적인 비례 관계를 갖지 않습니다.
    • SQS 대기열의 대기 메시지 수(ApproximateNumberOfMessagesVisible) 그 자체: 인스턴스가 몇 대 있든 대기열에 쌓인 총 메시지 수는 즉각적으로 희석되지 않습니다.

EC2 지표는 기본적으로 5분 간격으로 수집되므로, 트래픽 변화에 민첩하게 반응하려면 1분 단위로 지표를 수집하는 세부 모니터링(Detailed Monitoring)을 활성화하는 것이 모범 사례입니다.[5]

SQS 작업자(Worker) 풀의 스케일링 공식: SQS 큐의 메시지를 소비하는 EC2 인스턴스 풀을 대상 추적으로 확장할 때는, 인스턴스당 백로그(Backlog per Instance)라는 사용자 지정 지표를 생성하여 추적해야 합니다. 이 지표는 큐의 대기 메시지 수 ÷ 현재 서비스 중인(InService) 인스턴스 수로 계산됩니다. 그리고 목표값으로는 허용 가능한 메시지 지연 시간 ÷ 메시지 1건당 평균 처리 시간을 설정합니다.[11] (예: 10초 내 처리를 원하고 메시지당 0.1초가 걸린다면 목표 백로그는 100건). 이렇게 설계해야만 큐에 쌓인 작업량과 현재 처리 인스턴스 수의 균형을 정확하게 맞출 수 있습니다.

휴지 기간(Cooldown) vs 인스턴스 준비 시간(Warmup)

과거의 단순 조정(Simple Scaling) 정책에서는 스케일 아웃이 발생하면 설정된 휴지 기간(Cooldown, 기본 300초) 동안 다른 모든 스케일링 활동이 전면 중단되었습니다. 새 인스턴스가 뜰 때까지 기다려서 중복 확장을 막기 위함이었지만, 급격한 트래픽 유입 시 제때 대응하지 못하는 치명적인 단점이 있었습니다.[7]
반면 최신의 대상 추적(Target Tracking)과 단계 조정(Step Scaling) 정책은 전역 휴지 기간을 기다리지 않고 추가 확장이 즉시 일어날 수 있습니다. 대신 새로 생성된 개별 인스턴스마다 인스턴스 준비 시간(Warmup Period)을 부여합니다.[7] 준비 시간이 끝나기 전까지 해당 인스턴스는 그룹의 전체 지표 집계에서 제외되며, 확장이 진행되어 새로운 인스턴스가 준비 중인 동안에는 불필요한 축소(Scale-in) 활동이 일시적으로 차단되어 시스템의 진동을 방지합니다.[5]

상태 확인(Health Check)과 수명 주기 후크(Lifecycle Hook)

  • EC2 상태 확인 vs ELB 상태 확인의 결정적 차이:

    Auto Scaling 그룹의 기본 설정에서는 오직 EC2 상태 확인(EC2 Status Check) 결과만을 참조합니다. 즉, 하이퍼바이저 수준의 시스템 상태 확인과 OS 커널 부팅 여부만 확인하며, 인스턴스 상태가 running이고 상태 확인이 impaired가 아니라면 인스턴스를 완전히 정상으로 간주합니다. 하지만 실제 서비스에서는 OS는 멀쩡히 살아있으나 웹 서버 데몬이 죽었거나 메모리 누수로 인해 웹 애플리케이션 프로세스가 5xx 에러를 뿜으며 응답하지 않는 상황이 흔히 발생합니다.
    이때 로드 밸런서(ALB)는 상태 확인 프로브 실패로 해당 대상을 unhealthy로 감지하지만, Auto Scaling 그룹은 기본적으로 ELB의 상태 확인 결과를 완전히 무시하므로 해당 인스턴스를 교체하지 않고 방치합니다. 따라서 애플리케이션 레벨의 장애 인스턴스를 자동으로 종료하고 새 인스턴스로 자동 교체하려면, 반드시 Auto Scaling 그룹 설정에서 ELB 상태 확인 유형을 활성화해야 합니다.[12]

  • 수명 주기 후크(Lifecycle Hooks)의 동작 원리:

    수명 주기 후크는 인스턴스가 생성되어 트래픽을 받기 직전(Pending:Wait 상태)이나, 축소되어 완전히 종료되기 직전(Terminating:Wait 상태)에 인스턴스를 일시 정지(Pause) 상태로 붙잡아 두는 기능입니다. 기본 대기 제한 시간은 1시간(3,600초)이며, 이 대기 시간 동안 관리자는 다음과 같은 커스텀 작업을 안전하게 수행할 수 있습니다:[13]

    • 시작 후크(Launch Lifecycle Hook): 인스턴스가 로드 밸런서에 등록되어 실제 사용자 트래픽을 전달받기 전에, 대용량 데이터베이스 캐시를 미리 워밍업하거나 필요한 소프트웨어 패키지 설치 및 환경 구성을 완벽히 완료할 수 있습니다.
    • 종료 후크(Termination Lifecycle Hook): 인스턴스가 완전히 소멸하기 전에 EventBridge 알림을 트리거하여 Lambda 함수나 내부 스크립트를 통해 인스턴스 로컬 디스크에 남아있는 중요한 애플리케이션 로그, 트랜잭션 덤프 파일 등을 S3 버킷으로 안전하게 추출 및 백업할 수 있습니다.

    원하는 사전/사후 작업이 완료되면 AWS CLI나 API로 complete-lifecycle-action 명령을 호출하여 인스턴스를 다음 상태(InService 또는 Terminated)로 즉시 전환시킬 수 있습니다.

시험에 자주 나오는 핵심 패턴

  • "평균 CPU 사용률을 약 50%로 유지하고 싶음", "경보 관리 오버헤드를 최소화" → 대상 추적(Target Tracking) 조정 정책
  • "매주 금요일 18시", "분기 말일 오전 9시"처럼 트래픽 증가 시점을 정확히 알고 있음 → 예약 조정(Scheduled Scaling)
  • "일간/주간 반복 패턴 존재" + "인스턴스 부팅과 초기화에 오랜 시간 소요" + "사전에 미리 확장" → 예측 조정(Predictive Scaling)
  • "경보 임계값 초과 크기(격차)에 따라 단계별로 서로 다른 증설 수량 지정" → 단계 조정(Step Scaling) (단순 조정이나 휴지 기간은 비권장/오답)
  • "OS는 정상 작동 중이나 웹 애플리케이션이 먹통인데 인스턴스가 교체되지 않음" → Auto Scaling 그룹에서 ELB 상태 확인(Health Check) 켜기
  • "인스턴스가 종료되기 전에 로그를 S3에 보관", "시작 시 소프트웨어 설치가 완전히 끝난 뒤에만 트래픽 투입" → 수명 주기 후크(Lifecycle Hooks)
  • "SQS 큐의 메시지를 처리하는 EC2 작업자 풀 확장" → 인스턴스당 백로그(Backlog per Instance) 지표 기반 대상 추적
  • "단일 대형 인스턴스 사용 중이며, 스펙 변경 시 다운타임 발생" → 작은 인스턴스 여러 대 + 다중 AZ Auto Scaling 그룹을 통한 수평 확장(Scale Out)

연습

Q1. ALB 뒤 Auto Scaling 그룹의 웹 앱 트래픽이 예측 불가능하게 오르내립니다. 회사는 그룹의 평균 CPU 사용률을 약 50%로 유지하고 싶고, CloudWatch 경보를 직접 관리하고 싶지 않습니다. 가장 적합한 것은?

정답은 CPU 50% 대상 추적 정책을 사용하는 것입니다. 대상 추적 정책은 관리자가 목표값(예: CPU 50%)만 지정하면 Auto Scaling 서비스가 CloudWatch 경보를 백그라운드에서 직접 생성하고 능동적으로 관리해 줍니다. 반면 단계 조정이나 단순 조정은 관리자가 CloudWatch 경보를 직접 수동으로 만들어 연결해야 하며, 단순 조정과 전역 휴지 기간은 AWS가 공식적으로 사용을 지양하는 구형 방식입니다. 또한 예측할 수 없이 변동하는 트래픽에는 정해진 시간에만 실행되는 예약 조정이 적합하지 않습니다.

Q2. 매월 1일 오전 9시에 정산 작업이 시작되어 정확히 그 시각부터 인스턴스 20대가 필요합니다. 나머지 기간에는 4대면 충분합니다. 가장 간단한 방법은?

정답은 cron 일정의 반복 예약 조정 작업을 생성하는 것입니다. 트래픽이나 작업 부하가 급증하는 시점을 정확하게 알고 있을 때는 예약 조정(Scheduled Scaling)이 가장 단순하고 확실한 솔루션입니다. 최소 용량을 항상 20대로 고정해 두면 한 달 중 나머지 29일 동안 16대의 인스턴스가 유휴 상태로 방치되어 막대한 비용 낭비가 발생합니다. 대상 추적이나 단계 조정은 실제 부하가 발생하여 CPU가 치솟은 사후에 반응하므로, 9시 정각에 20대의 준비된 인스턴스를 즉시 확보해 주지 못합니다.

Q3. 사내 업무 시스템이 평일 업무 시간에 바쁘고 밤과 주말에는 한가한 패턴을 몇 달째 반복합니다. 인스턴스는 시작 후 준비되는 데 10분 이상 걸려, 동적 조정만으로는 아침마다 응답이 느려집니다. 일정을 사람이 관리하고 싶지 않습니다. 무엇을 추가해야 하나요?

정답은 과거 패턴을 학습하는 예측 조정 정책입니다. 문제의 핵심 단서는 세 가지입니다: (1) 주기적이고 반복적인 트래픽 패턴, (2) 인스턴스 부팅 및 애플리케이션 초기화에 10분 이상 소요되어 반응형 동적 조정으로는 지연이 발생함, (3) 관리자가 스케줄을 일일이 수동 관리하고 싶지 않음. 예측 조정은 과거 사용량을 머신러닝으로 분석하여 부하가 몰려오기 전에 미리 인스턴스를 띄워 둡니다. 예약 조정도 가능은 하지만 일정을 사람이 직접 생성하고 지속적으로 유지보수해야 하므로 요구사항에 부합하지 않습니다.

Q4. ALB 뒤 Auto Scaling 그룹에서 한 인스턴스의 웹 프로세스가 멈췄습니다. ALB는 이 대상을 unhealthy로 표시하지만, Auto Scaling 그룹은 몇 시간째 인스턴스를 교체하지 않습니다. 원인과 해결책은?

정답은 EC2 상태 확인만 쓰니 ELB 상태 확인을 켜는 것입니다. Auto Scaling 그룹의 기본 상태 확인은 오직 EC2 상태 확인뿐입니다. OS 커널과 하이퍼바이저가 정상 동작 중이라면 웹 애플리케이션 프로세스가 완전히 멈춰서 ALB가 unhealthy로 판정하더라도 ASG는 이를 인지하지 못하고 정상으로 간주합니다. 그룹 설정에서 ELB 상태 확인 유형을 활성화해야만 ALB의 판정을 수용하여 비정상 인스턴스를 즉시 종료하고 새 인스턴스로 자동 교체합니다.

Q5. Auto Scaling 그룹의 대상 추적 정책 지표로 적합하지 않은 것을 두 개 고르세요.

정답은 로드 밸런서의 전체 요청 수 지표와 로드 밸런서 요청 지연 시간 지표입니다. 대상 추적 정책에 사용되는 지표는 인스턴스 개수와 비례/반비례 관계가 명확해야 합니다. 로드 밸런서의 전체 요청 수는 인스턴스를 아무리 늘려도 줄어들지 않으므로 제어 루프가 통제 불능이 됩니다. 또한 지연 시간(Latency)은 데이터베이스 쿼리 병목이나 외부 네트워크 문제 등 인스턴스 대수와 무관한 변수에 크게 좌우되므로 부적합하다고 공식 문서에 명시되어 있습니다. 반면 평균 CPU 사용률과 대상당 요청 수(ALBRequestCountPerTarget)는 인스턴스를 늘리면 비례하여 값이 감소하므로 대상 추적에 완벽히 부합하는 사전 정의 지표입니다.

Q6. 축소(scale in) 때 종료되는 인스턴스의 애플리케이션 로그를 S3에 업로드한 뒤에 종료되게 해야 합니다. 어떤 기능을 써야 하나요?

정답은 종료 수명 주기 후크로 잡아 두고 업로드하는 것입니다. 종료 수명 주기 후크(Termination Lifecycle Hook)를 설정하면 인스턴스가 종료되기 직전 Terminating:Wait 상태로 대기하며, 기본 1시간 동안 인스턴스가 살아있는 상태를 유지합니다. 이 시간 동안 EventBridge와 Lambda, 혹은 내부 스크립트를 통해 로그 파일을 안전하게 S3로 백업한 후 작업을 완료(complete-lifecycle-action)하면 인스턴스가 정상 종료됩니다. 등록 취소 지연(Deregistration Delay)은 이미 진행 중인 인플라이트 HTTP 요청을 마무리하기 위한 로드 밸런서의 기능이며 인스턴스 종료를 보류하는 기능이 아닙니다.

Q7. (복습 · 0011) Auto Scaling 그룹의 TCP 서비스를 외부 파트너가 호출합니다. 파트너는 방화벽에 고정 IP 주소를 등록해야만 연결할 수 있습니다. 앞단에 무엇을 두어야 하나요?

정답은 NLB에 Elastic IP를 연결하는 것입니다. NLB(Network Load Balancer)는 각 가용 영역의 서브넷마다 고정 IP를 가지며, 인터넷 경계 서브넷에 탄력적 IP(Elastic IP)를 직접 할당할 수 있습니다. 반면 ALB는 IP가 동적으로 계속 변하며 항상 DNS 도메인 이름으로만 접근해야 하므로 고정 IP 방화벽 요구사항을 충족할 수 없습니다. Auto Scaling 그룹은 ALB뿐만 아니라 NLB 대상 그룹의 백엔드로도 완벽하게 연동됩니다.

Q8. 한 대의 대형 EC2 인스턴스에서 웹 앱을 운영합니다. 트래픽이 늘 때마다 인스턴스 유형을 키우는데, 그때마다 서비스가 중단되고 그 인스턴스가 고장 나면 전체가 멈춥니다. 가장 적합한 개선은?

정답은 작은 인스턴스 여러 대의 다중 AZ 그룹으로 전환하는 것입니다. 기존의 단일 대형 인스턴스 방식(수직 확장)은 인스턴스 유형을 바꿀 때마다 인스턴스를 중지(Stop)해야 하므로 다운타임이 불가피하고, 인스턴스 고장 시 서비스 전체가 중단되는 단일 장애 지점(SPOF)을 만듭니다. AWS Well-Architected 신뢰성 원칙에 따라 로드 밸런서 뒤에 작은 인스턴스 여러 대를 다중 AZ Auto Scaling 그룹으로 배치하면 무중단 수평 확장(Scale Out)과 뛰어난 고가용성을 동시에 달성할 수 있습니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 기억을 떠올려 직접 정리해 보세요. (1) Auto Scaling 조정 정책 다섯 가지와 각 정책을 선택하게 만드는 핵심 상황 단서는 무엇인가요? (2) 대상 추적에 적합한 지표의 수학적 특성과 부적합한 대표 지표 두 가지는 무엇인가요? (3) Auto Scaling의 기본 상태 확인과 ELB 상태 확인의 차이점 및 관계는 무엇인가요?

(1) 대상 추적: 특정 목표값(CPU 50% 등)을 지정하면 CloudWatch 경보를 자동 관리하는 기본 권장 정책. 단계 조정: 경보 임계값 초과 크기(격차)에 따라 단계별로 차등 증설. 단순 조정: 1개 경보에 반응하며 전역 휴지 기간 동안 모든 조정이 잠김(AWS 비권장). 예약 조정: cron이나 특정 시각 등 트래픽 증가 시점을 정확히 알 때 사용. 예측 조정: 반복되는 일/주 패턴 + 10분 이상 긴 초기화 부팅 시간, 선제적으로 미리 확장(단독 축소는 미수행), 최소 24시간 데이터 필요.

(2) 적합 조건: 인스턴스 개수를 늘리면 지표 값이 정비례 또는 반비례하여 감소/희석되는 지표 (평균 CPU 사용률, ALBRequestCountPerTarget, SQS 인스턴스당 백로그). 부적합 지표: 로드 밸런서 전체 요청 수(인스턴스를 늘려도 줄지 않음), 로드 밸런서 지연 시간(Latency는 DB 등 외부 요인에 좌우되므로 인스턴스 수와 비례하지 않음), SQS 대기열의 단순 총 메시지 수.

(3) Auto Scaling 그룹의 기본 상태 확인은 EC2 상태 확인뿐입니다. 하이퍼바이저와 OS가 정상이면 웹 애플리케이션이 죽어서 ALB가 unhealthy로 표시하더라도 기본적으로 무시합니다. 애플리케이션 수준의 장애 인스턴스를 자동으로 감지하고 새 인스턴스로 교체하려면 Auto Scaling 그룹에서 반드시 ELB 상태 확인 유형을 활성화해야 합니다.

추가 학습 및 실습

1차 공식 문서 (권장 읽기, 약 10분): AWS 공식 가이드인 "Target tracking scaling policies for Amazon EC2 Auto Scaling" 문서를 꼭 확인해 보세요. 특히 "Choose metrics" 섹션에서 다루는 대상 추적 부적합 지표 목록은 자격증 시험에 매우 높은 빈도로 출제됩니다. (한국어 번역본은 URL의 docs.aws.amazon.com/ 뒤에 ko_kr/를 추가하면 열람 가능합니다.)

핸즈온 실습 (선택, 프리 티어 범위): t2.micro 또는 t3.micro 기반 시작 템플릿을 생성하고, 최소 1대 · 원하는 용량 1대 · 최대 2대로 구성된 Auto Scaling 그룹을 만들어 보세요. 인스턴스가 InService 상태가 된 후 EC2 콘솔에서 해당 인스턴스를 임의로 강제 종료(Terminate)해 보십시오. Auto Scaling 그룹이 이를 감지하고 몇 분 내에 새로운 인스턴스를 자동으로 프로비저닝하여 원하는 용량을 회복하는 자가 치유(Self-Healing) 과정을 직접 확인할 수 있습니다. 실습이 끝난 후에는 불필요한 인스턴스가 계속 재생성되지 않도록 Auto Scaling 그룹을 먼저 삭제해야 합니다.
