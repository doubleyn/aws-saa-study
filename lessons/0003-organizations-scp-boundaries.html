왜 이것인가

시험에서: "개발 계정에서는 특정 리전 밖의 리소스 생성을 막아라", "관리자 권한이 있어도 CloudTrail을 끄지 못하게 하라" 같은 문제의 정답은 대개 SCP입니다.
실무에서: 계정을 여러 개로 나누고, 사람은 IAM 사용자 대신 IAM Identity Center로 로그인시키는 것이 AWS가 권하는 기본 구조입니다.

AWS Organizations의 구조

조직(organization)은 여러 AWS 계정을 중앙에서 관리하는 트리 구조입니다. 맨 위에 루트(root)가 하나 있고, 그 아래에 조직 단위(OU)를 중첩해 계정을 묶습니다. 조직을 만든 계정이 관리 계정(management account)이고 나머지는 회원 계정(member account)입니다. 회원 계정은 한 번에 한 조직에만 속할 수 있습니다.[1]

  • 관리 계정은 조직 전체 요금을 내는 지불 계정이며, 바꿀 수 없습니다.[1]
  • 기능 세트는 모든 기능(all features)과 통합 결제(consolidated billing)만 두 가지입니다. SCP는 모든 기능을 켠 조직에서만 쓸 수 있습니다.[2]
  • AWS는 관리 계정에 워크로드를 두지 말라고 권합니다. 이유는 바로 아래에서 볼 것처럼 SCP가 관리 계정을 제한하지 않기 때문입니다.[1]

새 규칙 세 개

  1. SCP는 아무것도 허용하지 않는다. 상한선만 긋는다. SCP는 회원 계정의 IAM 사용자·역할이 가질 수 있는 최대 권한을 정합니다. 실제 권한은 여전히 자격 증명 기반 정책이나 리소스 기반 정책으로 줘야 합니다. IAM 정책이 하나도 없는 사용자는 SCP가 모든 것을 허용해도 아무것도 못 합니다.[2]
  2. SCP의 Allow는 루트부터 계정까지 모든 단계에 있어야 하고, Deny는 어느 한 단계에만 있어도 된다. 경로 중 한 곳이라도 Allow가 빠지면 그 아래는 암묵적 거부입니다. 그래서 SCP를 켜면 AWS가 모든 루트·OU·계정에 FullAWSAccess를 자동으로 붙입니다.[3]
  3. 권한 경계도 상한선이다. 유효 권한은 교집합. 권한 경계는 사용자나 역할에 붙이는 관리형 정책으로, 자격 증명 기반 정책이 줄 수 있는 최대치를 정합니다. 둘 다 허용한 작업만 할 수 있습니다. SCP까지 있으면 SCP, 권한 경계, 자격 증명 기반 정책 셋 모두가 허용해야 합니다.[4]

0001의 규칙 3(일치하는 Deny는 무조건 이긴다)은 SCP와 권한 경계에도 그대로 적용됩니다. 어느 정책 유형이든 명시적 거부가 하나라도 있으면 거부입니다.[4]

참고: 리소스 쪽 상한선을 긋는 RCP(resource control policy)도 있습니다. SCP가 주체 중심이라면 RCP는 리소스 중심 가드레일입니다.[1]

평가 흐름에 끼워 넣기

0001·0002에서 본 판정을 AWS가 실제로 처리하는 순서로 다시 쓰면 이렇습니다.[5]

  1. 명시적 거부 확인: SCP·RCP·리소스 기반·자격 증명 기반·권한 경계·세션 정책 전부에서 일치하는 Deny를 찾음. 하나라도 있으면 즉시 거부.
  2. RCP: 적용되는 Allow가 없으면 거부.
  3. SCP: 적용되는 Allow가 없으면 거부.
  4. 리소스 기반 정책: 같은 계정이면 여기서 허용이 나올 수 있음(규칙 4).
  5. 자격 증명 기반 정책: Allow가 없으면 암묵적 거부.
  6. 권한 경계: 경계가 있는데 허용하지 않으면 암묵적 거부.
  7. 세션 정책: 역할 세션 등에서 전달된 경우 마찬가지로 확인.

세부 예외 하나: 같은 계정에서 리소스 기반 정책이 IAM 사용자 ARN에 직접 허용하면, 자격 증명 기반 정책이나 권한 경계의 암묵적 거부에는 막히지 않습니다. 역할 ARN에 허용한 경우는 권한 경계의 암묵적 거부에 막힙니다.[4] 시험에서는 "권한 경계 = 교집합"으로 기억하면 충분합니다.

권한 경계는 언제 쓰나: 위임

대표 용도는 권한 관리의 위임입니다. 예컨대 개발자에게 IAM 사용자·역할 생성을 맡기되, iam:PermissionsBoundary 조건 키로 "반드시 지정한 경계 정책을 붙여서만 만들 수 있다"고 강제합니다. 그러면 개발자가 만든 주체는 경계를 넘지 못합니다.[4]

Control Tower: 잘 차려진 다중 계정

AWS Control Tower는 Organizations, IAM Identity Center, Service Catalog 등을 조합해 모범 사례대로 다중 계정 환경(랜딩 존)을 구성하고 관리합니다. 컨트롤(가드레일)은 예방·탐지·사전(preventive, detective, proactive) 세 종류이며, Account Factory로 승인된 구성의 새 계정을 찍어 냅니다.[6] 시험 보기에 "여러 계정을 모범 사례대로 빠르게 설정하고 지속적으로 거버넌스"가 나오면 Control Tower를 떠올리세요.

사람은 어떻게 들어오나: IAM Identity Center와 페더레이션

AWS는 사람(human user)에게 개별 IAM 사용자를 만들지 말고, 자격 증명 공급자(IdP)를 통한 페더레이션으로 접근하게 하라고 권합니다. 페더레이션된 사용자는 장기 액세스 키 대신 단기 자격 증명을 받습니다.[7]

출처: IAM 사용 설명서의 페더레이션 유형 비교표[7]

IAM Identity Center의 핵심 부품은 권한 세트(permission set)입니다. 권한 세트를 사용자·그룹과 계정에 할당하면, Identity Center가 각 계정에 IAM 역할을 만들고 정책을 붙입니다. 사용자는 AWS 액세스 포털에서 그 역할을 맡습니다. 즉 0002의 "역할을 맡아 임시 자격 증명을 받는다"가 그대로 쓰입니다. 권한 세트의 세션 기간은 기본 1시간, 최대 12시간입니다.[8] 조직 인스턴스는 관리 계정에 배포되며, 계정 접근 관리를 위한 모범 사례입니다.[9]

시험 단골

"관리자 권한이 있어도 X를 못 하게" / "모든 계정에 일괄 적용" → SCP (Deny 문장).
"특정 서비스만 쓸 수 있게" → FullAWSAccess를 떼고 허용 목록 SCP.
"개발자가 역할을 만들되 자기보다 큰 권한은 못 주게" → 권한 경계 + iam:PermissionsBoundary 조건.
"기존 사내 디렉터리(AD) 계정으로 여러 AWS 계정에 로그인, 최소 운영 오버헤드" → IAM Identity Center.
"모바일 앱 사용자에게 S3 업로드 권한" → Cognito (IAM 사용자 생성은 오답).
"다중 계정 환경을 모범 사례대로 빠르게 구축" → Control Tower.
함정: SCP로 권한을 주려는 보기, 관리 계정에 SCP를 걸어 막으려는 보기는 오답입니다.

연습

조직 구조는 위 그림과 같습니다. 별도 언급이 없으면 루트와 모든 OU·계정에 FullAWSAccess가 붙어 있습니다.

Q1. 계정 D1의 개발자에게 AdministratorAccess(모든 작업 Allow)가 붙어 있습니다. Dev OU에는 ec2:*를 Deny하는 SCP가 있습니다. 개발자가 RunInstances를 호출합니다.

규칙 8: Deny는 경로 중 한 단계에만 있어도 됩니다. Dev OU의 Deny가 D1까지 상속되고, 명시적 거부는 어떤 Allow보다 우선합니다. AWS 문서는 "AdministratorAccess를 붙여도" 쓸 수 없다고 명시합니다.[2] 권한 경계는 선택 사항이라 없다고 거부되지 않습니다.

Q2. Prod OU에서 FullAWSAccess를 떼고 s3:*, ec2:*만 Allow하는 SCP를 붙였습니다. 루트와 계정 P에는 여전히 FullAWSAccess가 있습니다. 계정 P 사용자의 IAM 정책은 dynamodb:*를 허용합니다. DynamoDB 테이블을 조회하면?

규칙 8의 Allow 쪽입니다. 루트→Prod OU→계정 P 경로의 모든 단계에 Allow가 있어야 하는데, Prod OU가 DynamoDB를 허용하지 않습니다. Deny 문장이 없어도 거부됩니다(암묵적 거부). 위·아래 단계의 넓은 허용이 중간 단계의 빈칸을 메워 주지 않습니다.[3]

Q3. 보안팀이 루트에 s3:DeleteBucket을 Deny하는 SCP를 붙였습니다. 관리 계정의 관리자(모든 작업 Allow)가 관리 계정 안의 버킷을 삭제합니다.

SCP는 회원 계정에만 적용되고 관리 계정의 사용자·역할에는 영향이 없습니다. 루트에 붙여도 마찬가지입니다.[1] "명시적 거부는 어디서든 이긴다"는 맞는 원칙이지만, 이 SCP는 애초에 관리 계정의 요청에 적용되는 정책이 아닙니다. 그래서 관리 계정에는 워크로드를 두지 말라는 것입니다.

Q4. 사용자 Shirley의 권한 경계는 s3:*와 cloudwatch:*를 Allow합니다. 자격 증명 기반 정책은 ec2:*와 s3:GetObject를 Allow합니다. Shirley가 할 수 있는 것은?

규칙 9: 교집합입니다. EC2는 경계가 허용하지 않고, CloudWatch는 정책이 허용하지 않습니다. 둘 다 허용하는 것은 s3:GetObject뿐입니다. "S3 전체와 CloudWatch"는 경계가 권한을 준다고 착각했을 때 고르는 보기입니다.[4]

Q5. (시험형) 회사가 개발자들이 Lambda용 IAM 역할을 직접 만들 수 있게 하려 합니다. 단, 개발자가 만든 역할이 회사가 정한 권한 범위를 넘으면 안 됩니다. 가장 적절한 방법은?

권한 경계의 대표 용도인 위임입니다. iam:PermissionsBoundary 조건으로 "지정한 경계를 붙인 경우에만 생성 허용"을 강제합니다.[4] iam:* 거부 SCP는 역할 생성 자체를 막아 요구 사항을 못 채우고, SCP는 권한을 부여하지 않습니다.

Q6. (시험형) 직원 800명이 이미 사내 Active Directory 계정을 갖고 있습니다. 이들이 조직의 여러 AWS 계정에 기존 계정으로 로그인하게 하려 합니다. 운영 오버헤드가 가장 적은 방법은?

여러 계정 + 직원(workforce) + 기존 디렉터리 → IAM Identity Center입니다. Active Directory를 자격 증명 소스로 쓰고, 권한 세트를 할당하면 각 계정에 역할이 자동으로 만들어집니다.[7] Cognito는 앱 최종 사용자용이고, Account Factory는 계정을 찍어 내는 도구이지 사람의 로그인 수단이 아닙니다. 800명 × 계정 수만큼 IAM 사용자를 만드는 것은 최악의 오버헤드입니다.

Q7. SCP에 대한 설명으로 옳은 것을 두 개 고르세요.

SCP는 권한을 주지 않는 가드레일이고, 회원 계정의 루트 사용자까지 제한합니다. 관리 계정과 서비스 연결 역할은 SCP의 영향을 받지 않습니다.[2] 0001에서 "루트 사용자는 기본 거부의 예외"라고 했지만, 회원 계정이라면 SCP의 상한선 아래에 있습니다.

Q8. (0002 복습) 조직의 회원 계정 A에 버킷이 있고, 계정 A에는 s3:GetObject를 Deny하는 SCP가 붙어 있습니다. 버킷 정책은 조직 밖 계정 C의 사용자 carol에게 GetObject를 허용하고, carol의 자격 증명 기반 정책도 허용합니다. carol이 GetObject 합니다.

SCP는 그 계정이 관리하는 주체(사용자·역할)에만 적용되고, 리소스 기반 정책이나 조직 밖 사용자에게는 직접 영향을 주지 않습니다. AWS 문서가 바로 이 버킷 예시를 듭니다.[2] 나머지는 0002의 규칙 5대로 양쪽(carol의 정책, 버킷 정책)이 모두 허용했으니 허용입니다. 리소스 쪽을 조직 차원에서 막고 싶다면 RCP를 쓰는 것이 맞습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) SCP의 Allow와 Deny는 조직 트리에서 각각 어떻게 작동하나? (2) SCP의 영향을 받지 않는 대상 두 가지는? (3) SCP, 권한 경계, 자격 증명 기반 정책이 모두 있을 때 유효 권한은?

(1) Allow는 루트부터 대상 계정까지 모든 단계에 있어야 하고, Deny는 경로 중 어느 한 단계에만 있어도 아래 전체에 적용됩니다. SCP는 권한을 부여하지 않습니다.

(2) 관리 계정의 사용자·역할, 서비스 연결 역할. (조직 밖 주체도 직접 영향 없음.) 회원 계정의 루트 사용자는 영향을 받습니다.

(3) 셋의 교집합. 셋 중 하나라도 명시적 거부가 있으면 거부.
