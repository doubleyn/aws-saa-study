왜 Organizations와 권한 가드레일을 배워야 할까요?

시험 관점에서: "개발 계정에서는 서울 리전 이외의 리소스 생성을 일괄 차단하라", "개별 계정 관리자라도 CloudTrail 감사 로그를 끄지 못하도록 강제하라"처럼 다중 계정 전체에 적용되는 보안 가드레일을 묻는 문제의 정답은 거의 대부분 SCP(서비스 제어 정책)입니다.
실무 관점에서: 기업 규모가 커지면 하나의 AWS 계정만 쓰는 것이 아니라 개발, 검증, 운영 계정 등으로 환경을 분리합니다. 이때 계정들을 중앙에서 효율적으로 관리하고, 사람들에게 개별 IAM 사용자 대신 사내 계정(SSO)으로 접속하게 만드는 구조(IAM Identity Center)가 AWS 공식 엔터프라이즈 모범 사례의 기본 뼈대입니다.

AWS Organizations의 기본 구조와 핵심 개념

AWS Organizations는 여러 개의 AWS 계정을 하나의 중앙 조직으로 묶어 계층적 트리(Tree) 구조로 관리할 수 있게 해주는 서비스입니다.[1] 트리의 최상위에는 단 하나의 루트(Root)가 있고, 그 아래에 계정들을 성격별로 묶기 위한 폴더 역할을 하는 조직 단위(OU, Organizational Unit)를 생성하여 중첩 구성할 수 있습니다.

  • 관리 계정(Management Account): 조직을 최초로 생성한 마스터 계정입니다. 조직 전체의 요금을 하나로 합산해 결제하는 통합 결제(Consolidated Billing)의 지불 계정 역할을 하며, 관리 계정은 다른 계정으로 변경할 수 없습니다.[1]
  • 회원 계정(Member Account): 조직에 소속된 나머지 모든 계정입니다. 하나의 회원 계정은 동시에 여러 조직에 속할 수 없고 오직 한 조직에만 소속될 수 있습니다.
  • 기능 세트(Feature Sets): 조직은 '통합 결제 기능만 사용(Consolidated billing only)'하거나, 보안 정책까지 모두 제어할 수 있는 '모든 기능 활성화(All features)' 중 하나를 선택합니다. SCP 같은 중앙 정책 제어 기능은 모든 기능이 활성화된 조직에서만 사용할 수 있습니다.[2]
  • ⚠️ 관리 계정의 워크로드 배치 금지: AWS는 관리 계정에 실제 서비스 애플리케이션(EC2, RDS 등)을 절대 배치하지 말라고 강력히 권장합니다. 그 결정적인 이유는 아래에서 자세히 살펴보겠지만, 서비스 제어 정책(SCP)이 관리 계정 내부의 사용자나 리소스에는 전혀 적용되지 않기 때문입니다.[1]

권한 가드레일을 이해하는 확장 규칙 세 가지

  1. 규칙 7. SCP는 어떤 권한도 직접 부여하지 않는다. 오직 '최대 상한선'만 긋는다.
    SCP(Service Control Policy)는 회원 계정 내의 IAM 사용자나 역할이 가질 수 있는 최대 권한의 경계선을 설정합니다. 실제 리소스를 다루기 위한 권한은 여전히 개별 계정 내부의 자격 증명 기반 정책이나 리소스 기반 정책을 통해 명시적으로 부여해야 합니다. 따라서 SCP가 모든 작업을 허용(FullAWSAccess)하고 있더라도, 사용자에게 IAM 정책이 하나도 연결되어 있지 않다면 그 사용자는 아무런 작업도 수행할 수 없습니다.[2]
  2. 규칙 8. SCP의 Allow는 루트부터 대상 계정까지 모든 단계에 존재해야 하고, Deny는 단 한 단계에만 있어도 전체에 적용된다.
    조직 트리 구조에서 어떤 요청이 통과하려면 루트 → 상위 OU → 하위 OU → 대상 계정으로 이어지는 모든 경로마다 일치하는 Allow SCP가 존재해야 합니다. 경로 중 어느 한 곳에서라도 Allow가 빠져 있다면 그 하위의 모든 계정은 해당 작업에 대해 암묵적 거부를 당합니다. (이 때문에 조직을 생성하면 AWS가 모든 루트와 OU, 계정에 기본적으로 FullAWSAccess SCP를 자동으로 붙여주는 것입니다.) 반면, 명시적 Deny는 경로 중 단 한 곳에만 존재해도 그 하위 계층 전체로 상속되어 모든 것을 차단합니다.[3]
  3. 규칙 9. 권한 경계(Permissions Boundary) 역시 개별 주체의 상한선이며, 최종 권한은 '교집합'으로 결정된다.
    권한 경계는 특정 IAM 사용자나 역할에 연결하는 관리형 정책으로, 자격 증명 기반 정책이 부여할 수 있는 최대 권한 범위를 제한합니다. 사용자는 '자격 증명 기반 정책'과 '권한 경계' 둘 다 허용한 작업만 실제로 수행할 수 있습니다. 만약 여기에 조직의 SCP까지 걸려 있다면, SCP · 권한 경계 · 자격 증명 정책 셋 모두가 허용해야만 최종 작업이 가능합니다.[4]

0001에서 배운 절대 규칙, "일치하는 Deny는 다른 모든 허용을 이긴다"는 원칙은 SCP와 권한 경계에도 똑같이 적용됩니다. 어떤 정책 계층에서든 일치하는 명시적 Deny가 단 하나라도 있다면 요청은 즉시 거부됩니다.[4]

SCP가 적용되는 대상과 예외 대상

대상SCP의 제한 적용 여부상세 설명
회원 계정의 모든 IAM 사용자 및 역할적용됨계정 내부 관리자가 아무리 강력한 권한 정책을 부여해도 SCP 상한선을 넘을 수 없습니다.
회원 계정의 루트(Root) 사용자적용됨0001에서 "루트는 암묵적 거부의 예외"라고 배웠지만, Organizations 회원 계정이라면 루트 사용자도 SCP의 가드레일에 제한됩니다.[2]
관리 계정(Management Account)의 사용자·역할적용되지 않음조직의 최상위 관리 계정은 SCP의 어떤 제한도 받지 않습니다. 바로 이 점 때문에 워크로드를 관리 계정에 두어서는 안 됩니다.
서비스 연결 역할 (Service-linked Role)적용되지 않음AWS 서비스들이 내부적으로 상호작용하기 위해 사용하는 서비스 연결 역할은 SCP로 차단되지 않습니다.
조직 외부 계정의 주체 (교차 계정 접근 등)적용되지 않음SCP는 조직 내부에서 관리하는 주체에만 적용됩니다. 외부 계정 사용자가 버킷 정책을 통해 들어올 때는 해당 회원 계정의 SCP가 직접 작용하지 않습니다.[2]

참고: 리소스 자체에 상한선을 긋는 리소스 제어 정책(RCP, Resource Control Policy)도 최근 도입되었습니다. SCP가 '요청하는 주체'를 제한하는 가드레일이라면, RCP는 '데이터를 담은 리소스'를 보호하는 가드레일 역할을 합니다.[1]

AWS 권한 평가 엔진의 종합 평가 순서

0001부터 배운 모든 정책 유형들을 종합하여, AWS가 실제 API 요청을 검증하는 전체 논리 순서를 정리하면 다음과 같습니다.[5]

  1. 1단계: 명시적 거부(Deny) 최우선 검사
    SCP, RCP, 리소스 기반 정책, 자격 증명 기반 정책, 권한 경계, 세션 정책 등 관련된 모든 정책을 통틀어 일치하는 Deny가 단 하나라도 있으면 즉시 거부됩니다.
  2. 2단계: 조직 가드레일(SCP/RCP) 검사
    적용 대상 계정인 경우, SCP와 RCP에서 해당 작업을 허용하고 있는지 확인합니다. 허용되지 않았다면 즉시 거부됩니다.
  3. 3단계: 리소스 기반 정책 검사
    대상 리소스에 정책이 연결되어 있고 명시적 Allow가 있다면, 동일 계정 환경에서는 여기서 허용 판정이 내려질 수 있습니다 (규칙 4).
  4. 4단계: 자격 증명 기반 정책 검사
    사용자나 역할에 일치하는 Allow가 없다면 기본 규칙에 따라 암묵적 거부가 발생합니다.
  5. 5단계: 권한 경계(Permissions Boundary) 검사
    주체에게 권한 경계가 연결되어 있다면, 경계 정책에서도 해당 작업을 허용하고 있는지 확인합니다. 경계에서 허용하지 않으면 거부됩니다.
  6. 6단계: 세션 정책 검사
    임시 역할을 맡을 때 세션 정책이 전달되었다면, 세션 정책에서도 작업을 허용해야 최종 통과됩니다.

권한 경계(Permissions Boundary)는 언제 사용할까요?

권한 경계의 대표적인 실무 활용처는 "하위 관리자에게 IAM 권한을 안전하게 위임할 때"입니다. 예를 들어 개발팀 리더에게 "팀원들을 위한 IAM 역할이나 사용자를 직접 생성할 수 있는 권한"을 주되, 그 리더가 회사 정책을 벗어나는 관리자급 역할을 마음대로 만들어서 권한을 탈취(Privilege Escalation)하지 못하도록 막고 싶을 때 사용합니다.
이때 조건 키 iam:PermissionsBoundary를 사용하여 "새 역할을 생성할 때는 반드시 회사가 지정한 권한 경계 정책을 첨부해야만 생성을 허용한다"고 강제합니다. 이렇게 하면 개발팀 리더가 만든 모든 역할은 지정된 경계선 내부에서만 동작하므로 안전하게 관리를 위임할 수 있습니다.[4]

AWS Control Tower: 모범 사례 기반의 다중 계정 랜딩 존 자동화

AWS Control Tower는 Organizations, IAM Identity Center, Service Catalog 등을 종합적으로 활용하여 AWS 공식 모범 사례(Well-Architected)에 맞춘 다중 계정 환경(랜딩 존, Landing Zone)을 자동으로 구성하고 지속 관리해주는 서비스입니다.[6]

  • 가드레일(컨트롤, Controls): 필수적인 보안 규칙들을 일괄 적용합니다. 작업 자체를 원천 차단하는 예방적(Preventive) 컨트롤(SCP 기반), 규정 위반을 실시간 감지하여 알리는 탐지적(Detective) 컨트롤(AWS Config 기반), 배포 전에 설정을 검증하는 사전적(Proactive) 컨트롤(CloudFormation Guard 기반)을 제공합니다.
  • Account Factory: 보안과 네트워크 설정이 사전에 승인된 표준 템플릿 형태의 새 AWS 계정을 몇 번의 클릭만으로 자동으로 찍어내어 프로비저닝할 수 있습니다.

시험 문제에서 "여러 개의 AWS 계정을 보안 모범 사례에 맞춰 빠르고 일관되게 구축하고, 지속적인 중앙 거버넌스를 유지해야 한다"는 문장이 나오면 주저 없이 AWS Control Tower를 정답으로 선택하세요.

사람의 로그인은 어떻게 처리할까: IAM Identity Center와 페더레이션

AWS 보안 모범 사례에서는 실제 사람(직원) 한 명 한 명을 위해 개별 AWS 계정에 직접 IAM 사용자를 만들지 말라고 권고합니다. 대신 중앙의 자격 증명 공급자(IdP, Identity Provider)와 연동(Federation)하여 싱글 사인온(SSO) 방식으로 접속하게 만들어야 합니다. 이렇게 접속한 직원은 영구 액세스 키 대신 안전하게 자동 만료되는 단기 임시 자격 증명을 부여받습니다.[7]

(구 AWS SSO)		AWS Organizations로 묶인 여러 계정에 사내 직원(Workforce)들이 접속할 때사내 Active Directory, Okta, Azure AD(Entra ID), 자체 디렉터리 등 (SAML 2.0 기반)

IAM Identity Center의 핵심 관리 개념은 권한 세트(Permission Set)입니다. 관리자가 직원의 직무에 맞는 권한 세트를 정의하고 이를 특정 사용자와 대상 AWS 계정에 매핑해두면, IAM Identity Center가 대상 계정 내부에 자동으로 IAM 역할을 생성하고 해당 정책을 연결해 둡니다. 직원이 웹 브라우저의 'AWS 액세스 포털'에 접속해 로그인하면, 백그라운드에서 해당 역할로 sts:AssumeRole이 실행되어 안전한 임시 세션을 얻게 됩니다. 권한 세트 세션의 기본 유효 기간은 1시간이며, 필요에 따라 최대 12시간까지 설정할 수 있습니다.[8]

시험에 자주 나오는 핵심 키워드 정리

"계정 관리자라도 특정 작업(예: CloudTrail 중지)을 절대 못 하게 전체 계정에 일괄 강제" → SCP (Deny 선언문 작성)
"조직의 특정 계정에서는 승인된 서비스만 사용하도록 제한" → FullAWSAccess를 제거하고 허용 목록 방식의 SCP 적용
"개발팀 리더가 IAM 역할을 직접 만들 수 있게 하되, 권한 상승은 엄격히 차단" → 권한 경계(Permissions Boundary)와 iam:PermissionsBoundary 조건 키 결합
"기존 사내 Active Directory(AD) 계정 하나로 여러 AWS 계정에 원클릭 로그인(SSO)" → IAM Identity Center
"모바일 앱의 일반 사용자가 프로필 이미지를 S3에 직접 업로드" → Amazon Cognito 자격 증명 풀 (IAM 사용자 생성을 유도하는 보기는 100% 오답)
"다중 계정 환경을 보안 모범 사례에 맞춰 빠르게 자동 구축" → AWS Control Tower (랜딩 존)
⚠️ 주의해야 할 오답 함정: SCP를 통해 특정 사용자에게 '권한을 직접 부여한다'는 보기는 무조건 오답입니다. 또한 '관리 계정에 SCP를 걸어 통제한다'는 보기 역시 SCP가 관리 계정에는 적용되지 않으므로 오답입니다.

실전 연습: 시나리오 판정해 보기

조직 구조는 위 다이어그램과 같습니다. 별도의 언급이 없다면 루트와 모든 OU 및 계정에는 기본값인 FullAWSAccess SCP가 연결되어 있습니다.

Q1. 계정 D1에 속한 개발자에게 AdministratorAccess(모든 AWS 작업 허용) 정책이 연결되어 있습니다. 그런데 Dev OU에는 ec2:* 작업을 명시적으로 거부하는 Deny SCP가 적용되어 있습니다. 개발자가 EC2 인스턴스를 생성(RunInstances)하려고 하면 결과는 어떻게 될까요?

규칙 8에 관한 문제입니다. 명시적 Deny SCP는 조직 트리의 어느 한 단계에만 존재해도 그 하위의 모든 OU와 계정으로 그대로 상속됩니다. 또한 "명시적 Deny는 모든 Allow를 이긴다"는 절대 원칙에 따라 사용자에게 AdministratorAccess 정책이 있더라도 EC2 작업은 완전히 차단됩니다. AWS 공식 문서에서도 "AdministratorAccess 정책이 있는 사용자라도 상위 SCP에서 거부된 서비스는 결코 실행할 수 없다"고 명시하고 있습니다.[2] (권한 경계는 선택적 옵션이므로 없다고 해서 거부되지 않습니다.)

Q2. 보안팀이 Prod OU에서 기본 FullAWSAccess SCP를 제거하고, 오직 s3:*와 ec2:*만 Allow하는 SCP를 연결했습니다. 루트와 하위 계정 P에는 여전히 FullAWSAccess가 붙어 있습니다. 계정 P에 속한 사용자의 IAM 정책에 dynamodb:* 허용이 있을 때, 사용자가 DynamoDB 테이블 조회를 시도하면 어떻게 될까요?

규칙 8의 Allow 상속 원리입니다. 조직 트리에서 특정 작업이 허용되려면 루트 → Prod OU → 계정 P로 이어지는 모든 단계마다 해당 작업을 허용하는 SCP가 반드시 존재해야 합니다. 중간의 Prod OU에서 DynamoDB를 허용하지 않았기 때문에 문이 닫히며 암묵적 거부가 발생합니다. 상위나 하위 계층에 아무리 넓은 허용 SCP가 있더라도 중간 계층의 빈자리를 채워줄 수 없습니다.[3]

Q3. 보안팀이 실수로 루트에 s3:DeleteBucket을 명시적으로 거부(Deny)하는 SCP를 연결했습니다. 관리 계정(Management Account)의 관리자가 관리 계정 내부의 S3 버킷을 삭제하려고 합니다. 작업은 어떻게 처리될까요?

SCP는 관리 계정에 결코 영향을 미치지 않습니다. 최상위 루트에 SCP를 붙였더라도 관리 계정에 속한 IAM 사용자와 역할에는 해당 정책이 아예 평가 대상조차 되지 않습니다.[1] "명시적 거부는 항상 이긴다"는 맞는 말이지만, 애초에 정책이 적용되는 범위 밖에 있기 때문에 성립하지 않습니다. 바로 이러한 보안 취약성 때문에 AWS는 관리 계정에 실제 운영 리소스를 배치하지 말라고 경고하는 것입니다.

Q4. 사용자 Shirley에게 연결된 권한 경계(Permissions Boundary)는 s3:*와 cloudwatch:*를 허용하고 있습니다. 반면 Shirley의 자격 증명 기반 정책은 ec2:*와 s3:GetObject를 허용하고 있습니다. Shirley가 실제로 실행할 수 있는 유효 작업은 무엇일까요?

규칙 9에 관한 문제입니다. 유효 권한은 권한 경계와 자격 증명 정책의 '교집합'으로 결정됩니다. EC2는 자격 증명 정책에는 있지만 권한 경계에서 허용하지 않아 차단되고, CloudWatch는 권한 경계에는 있지만 사용자 정책에서 허용하지 않아 차단됩니다. 둘 다 허용하고 있는 작업은 s3:GetObject뿐입니다. "S3 전체와 CloudWatch"를 고르는 실수는 권한 경계가 직접 권한을 부여하는 정책이라고 착각했을 때 발생하는 대표적인 오답입니다.[4]

Q5. (실제 시험 유형) 회사의 개발팀 리더들이 새로운 마이크로서비스용 Lambda 실행 IAM 역할을 직접 생성할 수 있도록 허용하려고 합니다. 하지만 개발팀이 생성하는 역할에 과도한 관리자 권한이 부여되는 권한 상승을 원천 차단해야 합니다. 가장 적절한 아키텍처 설계는?

권한 경계의 가장 대표적인 실무 활용 사례인 안전한 권한 위임 시나리오입니다. iam:PermissionsBoundary 조건 키를 정책에 설정하여 "회사가 사전에 정의한 권한 경계 정책을 필수적으로 첨부하여 역할을 생성할 때만 iam:CreateRole을 허용한다"고 제약합니다.[4] 이렇게 하면 생성된 역할은 경계 정책 이상의 권한을 절대 가질 수 없습니다. IAM 전체 거부 SCP는 역할 생성 자체를 막아버리므로 요구사항을 만족하지 못하며, SCP로는 권한을 직접 부여할 수 없습니다.

Q6. (실제 시험 유형) 회사 직원 800명이 이미 사내 온프레미스 Active Directory 계정을 사용하고 있습니다. 회사는 다중 AWS 계정 환경을 구축하고 직원들이 기존 AD 계정으로 여러 AWS 계정에 원활하게 싱글 사인온(SSO)할 수 있기를 원합니다. 운영 오버헤드를 최소화할 수 있는 가장 적합한 솔루션은?

다중 계정 + 기업 임직원(Workforce) + 기존 기업 디렉터리(AD) 조합의 정답은 무조건 AWS IAM Identity Center입니다. 사내 AD를 Identity Center의 자격 증명 공급자(IdP)로 연동하고 권한 세트를 구성하면, 각 계정에 필요한 역할이 자동으로 프로비저닝되어 직원들이 포털을 통해 한 번의 로그인으로 접근할 수 있습니다.[7] 직원 800명 × 계정 수만큼 IAM 사용자를 만드는 것은 관리 오버헤드가 극도로 크며, Cognito는 엔드유저 앱 고객을 위한 서비스입니다.

Q7. 서비스 제어 정책(SCP)의 동작 방식에 대한 설명으로 옳은 것을 두 개 고르세요.

옳은 설명은 1번과 4번입니다. SCP는 권한을 부여하지 않고 최대 상한선만 설정하는 필터이며, 놀랍게도 회원 계정의 루트 사용자까지 철저하게 통제합니다.[2] 반면 관리 계정의 모든 주체와 AWS 서비스 연결 역할은 SCP의 영향을 전혀 받지 않습니다.

Q8. (심화 복습) 조직의 회원 계정 A에 S3 버킷이 있고, 계정 A에는 s3:GetObject를 거부하는 Deny SCP가 적용되어 있습니다. 버킷 정책은 조직 외부 계정 C의 사용자 carol에게 GetObject를 허용하고 있으며, carol의 자격 증명 정책도 이를 허용하고 있습니다. carol이 버킷의 객체를 다운로드하면 어떻게 될까요?

많은 분들이 혼동하는 심화 포인트입니다. SCP는 해당 계정이 직접 관리하는 내부 주체(사용자, 역할)에만 적용됩니다. 즉, 조직 외부 계정의 사용자가 리소스 정책을 통해 접근할 때는 리소스가 위치한 계정의 SCP 검사를 거치지 않습니다. AWS 공식 문서에서도 이 버킷 예시를 들어 설명하고 있습니다.[2] 외부 사용자 carol의 자격 증명 정책과 버킷 정책이 둘 다 허용했으므로 정상 허용됩니다. (만약 리소스 자체에 대한 외부 접근까지 조직 차원에서 차단하고 싶다면 최근 도입된 RCP(리소스 제어 정책)를 사용해야 합니다.)

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 직접 정리해 보세요.
(1) SCP의 Allow와 Deny는 조직 계층 트리에서 각각 어떻게 전파되고 상속되나요?
(2) SCP의 제한 가드레일이 전혀 적용되지 않는 예외 대상 두 가지는 무엇인가요?
(3) 한 사용자에게 SCP, 권한 경계, 자격 증명 기반 정책이 모두 적용되어 있을 때 최종 권한은 어떻게 결정되나요?

(1) SCP의 Allow vs Deny 상속 원리:
- Allow: 루트부터 대상 계정까지 이어지는 모든 경로의 계층마다 반드시 허용되어 있어야 작업이 통과합니다 (하나라도 빠지면 암묵적 거부). SCP 자체는 권한을 부여하지 않습니다.
- Deny: 조직 트리의 어느 한 단계에만 Deny가 명시되어 있어도, 그 하위의 모든 계층으로 상속되어 다른 모든 허용을 무시하고 차단합니다.

(2) SCP의 예외 대상:
최상위 관리 계정(Management Account)의 사용자 및 역할, 그리고 AWS 내부 통신용 서비스 연결 역할(Service-linked Role)은 SCP의 영향을 받지 않습니다. (단, 회원 계정의 루트 사용자는 SCP의 제한을 확실히 받습니다.)

(3) 종합 유효 권한:
SCP, 권한 경계, 자격 증명 기반 정책 셋 모두의 '교집합'으로 결정됩니다. 셋 중 어느 하나라도 작업을 허용하지 않거나 명시적으로 거부하면 요청은 차단됩니다.
