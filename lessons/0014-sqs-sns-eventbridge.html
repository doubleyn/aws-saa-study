느슨한 결합:
SQS, SNS, EventBridge, 팬아웃

시스템의 구성 요소들이 서로를 직접 동기식으로 호출(강한 결합)하면, 한쪽 서비스가 지연되거나 다운되는 순간 연쇄적으로 전체 시스템이 마비됩니다. 컴포넌트 사이에 메시지 대기열(SQS), 게시/구독 주제(SNS), 또는 이벤트 버스(EventBridge)를 배치하여 '느슨한 결합(Loose Coupling)'을 구현하면, 각 서비스가 서로의 상태에 구애받지 않고 독립적으로 자기 속도에 맞추어 작업을 처리할 수 있습니다. 이번 레슨에서는 세 서비스의 역할 차이와 SQS의 4대 핵심 설정값을 완벽히 마스터합니다.

왜 느슨한 결합(Decoupling)을 배워야 할까요?

  • 시험 관점: "플래시 세일 중 트래픽 폭증으로 주문 데이터가 유실됨", "동일한 주문 이벤트를 결제, 재고, 배송, 분석 등 여러 다운스트림 시스템이 각각 독립적으로 처리해야 함"과 같은 시나리오는 AWS SAA 시험 복원력(도메인 2)의 최다 빈출 유형입니다. 정답은 거의 항상 SQS 버퍼링이나 SNS 팬아웃(Fanout) 구조로 귀결됩니다.
  • 실무 관점: 웹 프론트엔드와 백엔드 데이터베이스 사이에 SQS 큐를 하나 끼워 넣는 것만으로도, 데이터베이스 점검 시간이나 장애 상황에서도 프론트엔드는 고객의 주문을 정상적으로 계속 접수할 수 있으며, 백엔드는 복구된 후 대기열에 쌓인 작업을 안전하게 순차 처리할 수 있습니다.

한눈에 비교하기: 세 서비스의 본질과 통신 방식 (SQS vs SNS vs EventBridge)

세 서비스는 모두 애플리케이션 통합에 쓰이지만, 데이터가 흐르는 통신 방식과 목적이 근본적으로 다릅니다.

비교 항목Amazon SQS (메시지 큐)Amazon SNS (게시/구독 토픽)Amazon EventBridge (이벤트 버스)
전달 방식소비자(Consumer)가 큐를 주기적으로 폴링(Pull/Polling)하여 메시지를 직접 가져감생산자가 주제에 메시지를 게시하면, 연결된 구독자들에게 즉시 밀어 넣음 (Push)[9]이벤트가 들어오면 규칙 엔진이 JSON 패턴 매칭을 수행하여 일치하는 대상으로 선별 라우팅[13]
수신 대상하나의 메시지는 큐를 폴링한 단 하나의 소비자가 처리한 후 큐에서 삭제함 (1:1 경쟁적 소비자 모델)주제에 게시된 하나의 메시지는 구독 중인 모든 엔드포인트에 복제되어 사본이 전달됨 (1:N 브로드캐스트)[8]규칙 패턴에 부합하는 대상들에게 전달 (규칙 1개당 최대 5개 대상 지정 가능)[13]
메시지 보관성메시지를 큐 디스크에 안전하게 보관 (기본 4일, 설정 시 최대 14일까지 영구 보관)[7]메시지를 자체 보관하지 않음. 전달 시점에 수신자가 없거나 실패하면 유실됨 (메시지를 보관하려면 SQS를 구독자로 연결해야 함)기본적으로 보관하지 않음 (이벤트 아카이브 및 재생 기능은 별도 설정 필요)
대표적인 용도작업 버퍼링, 배치 처리, 속도 차이 완충(Rate Smoothing), 비동기 워크플로팬아웃(Fanout), 다중 시스템 동시 통보, 모바일 푸시 알림, 이메일/SMS 전송AWS 서비스 상태 변화 이벤트 라우팅, Datadog/Zendesk 등 SaaS 파트너 이벤트 통합, 스케줄링(Scheduler)

SNS 구독자 엔드포인트 종류: SQS 큐, AWS Lambda 함수, HTTP/HTTPS 웹훅 엔드포인트, 이메일, 모바일 푸시, SMS 텍스트 메시지, Amazon Kinesis Data Firehose 등 다양한 수신처를 지원합니다.[8] 기본적으로 구독자는 해당 주제로 발행되는 모든 메시지를 받지만, 구독 설정에 메시지 필터 정책(Filter Policy)을 적용하면 특정 속성(Attribute)을 가진 메시지만 골라서 선별 수신할 수 있습니다.[10]

핵심 특징: SQS 대기열 유형 (표준 큐 vs FIFO 큐)

SQS는 처리량 우선이냐, 순서와 중복 방지 우선이냐에 따라 두 가지 큐 유형을 제공합니다.[1]

비교 항목표준 큐 (Standard Queue)FIFO 큐 (First-In-First-Out Queue)
처리량 (Throughput)사실상 무제한 (초당 처리할 수 있는 API 호출 및 메시지 수에 제한 없음)기본적으로 배치 없이 API 메서드당 초당 300건, 10개 배치 처리 시 초당 3,000건. 높은 처리량 모드(High Throughput Mode) 활성화 시 초당 최대 70,000건까지 지원[1]
전달 보장 (Delivery)최소 한 번 이상 전달 (At-least-once). 분산 시스템 특성상 드물게 동일 메시지가 두 번 이상 전달될 수 있으므로 소비자는 멱등성(Idempotency)을 반드시 보장하도록 구현해야 함정확히 한 번 처리 (Exactly-once Processing). 5분 중복 제거 시간(Deduplication Interval) 내에 동일한 중복 ID를 가진 메시지가 재전송되더라도 중복 적재되지 않음[6]
순서 보장 (Ordering)최선의 노력(Best-effort) 순서화. 일반적으로는 보낸 순서대로 전달되지만 엄격한 순서는 보장하지 않음메시지가 전송된 순서 그대로 엄격한 선입선출(FIFO) 보장. 큐 이름 뒤에 반드시 .fifo 접미사가 붙어야 함

FIFO 큐의 메시지 그룹화 (MessageGroupId): FIFO 큐에 메시지를 보낼 때는 반드시 MessageGroupId 속성을 지정해야 합니다.[7] SQS FIFO는 동일한 MessageGroupId를 가진 메시지들 사이에서만 엄격한 순서를 보장합니다. 따라서 "고객 A의 주문 변경 사항"과 "고객 B의 주문 변경 사항"이 있을 때, 고객 ID를 MessageGroupId로 지정하면 각 고객 내부에서는 순서가 철저하게 보장되면서도, 서로 다른 고객들의 메시지는 여러 소비자 작업자에 의해 완전히 독립적이고 병렬적으로 고속 처리될 수 있습니다.

SQS의 4대 핵심 설정값과 동작 메커니즘

SQS를 구성할 때 반드시 정확한 수치와 동작 원리를 이해해야 하는 4대 파라미터입니다.

설정 항목역할 및 동작 원리기본값·제한 및 시험 함정
가시성 제한 시간
(Visibility Timeout)		소비자가 큐에서 메시지를 성공적으로 수신(ReceiveMessage)한 직후, 다른 소비자가 동일한 메시지를 중복으로 가져가지 못하도록 큐 안에서 해당 메시지를 일시적으로 보이지 않게 숨겨 두는 보호 시간입니다. 소비자가 이 시간 내에 처리를 끝내고 메시지를 삭제(DeleteMessage)하지 못하면, 메시지가 다시 보이기 시작하여 다른 작업자에 의해 중복 처리됩니다.[2]기본값 30초, 최소 0초, 최대 12시간.
핵심 함정: 메시지 실제 처리 시간이 가시성 제한 시간보다 길면 동일 메시지가 반복 처리됩니다. 따라서 처리 시간보다 충분히 길게 설정해야 합니다. Lambda를 소비자로 둘 때는 함수 타임아웃의 최소 6배 이상으로 설정하는 것이 공식 권장 사항입니다.[16] 작업이 예상보다 오래 걸리면 ChangeMessageVisibility API를 호출해 제한 시간을 연장할 수 있습니다.
배달 못한 편지 큐
(Dead-Letter Queue, DLQ)		포맷 손상이나 코드 버그 등으로 인해 정상 처리가 불가능한 결함 메시지(독약 메시지, Poison Pill)가 큐를 계속 맴돌며 리소스를 낭비하지 않도록, 소비자가 maxReceiveCount 횟수만큼 수신을 시도했음에도 삭제되지 못한 메시지를 별도의 실패 전용 대기열로 자동 격리합니다.[3]필수 조건: DLQ는 원본 큐와 반드시 동일한 AWS 계정 및 리전에 있어야 하며, 큐 유형이 일치해야 합니다 (표준 큐는 표준 DLQ, FIFO 큐는 FIFO DLQ에만 연결 가능).[4] 또한 표준 큐의 메시지 보존 기간은 원본 큐에 처음 들어간 시점부터 계산되므로, DLQ의 메시지 보존 기간을 원본 큐보다 더 길게 설정해야 만료로 유실되지 않습니다.
긴 폴링
(Long Polling)		소비자가 메시지를 요청했을 때 큐가 비어 있으면 즉시 빈 응답(Empty Response)을 반환하는 대신, 새로운 메시지가 도착할 때까지 최대 20초 동안 소켓 연결을 열어두고 기다렸다가 메시지가 들어오는 즉시 응답합니다.[5]WaitTimeSeconds > 0(최대 20초)으로 설정하면 긴 폴링이 활성화됩니다. 불필요한 빈 응답 횟수를 획기적으로 줄여 SQS API 호출 비용을 대폭 절감하고 거짓 빈 응답(False Empty Response)을 방지합니다. 반대인 짧은 폴링(기본값 0초)은 즉시 반환하지만 비용이 낭비됩니다.
메시지 보존 및 전송 지연
(Retention & Delay)		메시지 보존 기간은 소비자가 꺼내가지 않은 메시지가 큐에 남아있는 유효 기간이며, 전송 지연(Delivery Delay)은 생산자가 메시지를 보낸 후 소비자에게 처음 보이기까지 대기시키는 시간입니다.보존 기간은 기본 4일, 최소 60초, 최대 14일까지 설정 가능합니다. 전송 지연(Delivery Delay)은 최대 15분까지 설정할 수 있습니다.[7]

팬아웃(Fanout) 아키텍처: SNS 주제 → 여러 SQS 큐

하나의 비즈니스 이벤트가 발생했을 때 여러 개의 서로 다른 독립적인 시스템들이 각자의 목적에 맞추어 동시에 이벤트를 수신하여 처리해야 하는 경우, SNS 팬아웃(Fanout) 패턴을 적용합니다. 예를 들어 쇼핑몰에서 "주문 완료" 이벤트가 1건 발생하면, 생산자는 SNS 주제에 메시지를 딱 1번만 게시(Publish)합니다. 그러면 SNS가 해당 주제를 구독하고 있는 '결제 처리용 SQS 큐', '재고 차감용 SQS 큐', '데이터 분석용 SQS 큐'로 메시지 사본을 즉각 복제하여 밀어 넣어 줍니다.[8]

팬아웃 구성 시 주의해야 할 결정적 함정 두 가지

  • 큐 리소스 기반 정책(Queue Policy) 권한 부여: SNS가 SQS 큐로 메시지를 성공적으로 전달하려면, 수신하는 SQS 큐의 리소스 기반 정책에서 보안 주체(Principal)인 sns.amazonaws.com에게 sqs:SendMessage 권한을 명시적으로 허용해야 합니다. 이때 보안 모범 사례에 따라 조건문(Condition)의 aws:SourceArn을 사용하여 특정 SNS 주제 ARN에서 오는 호출만 허용하도록 잠가야 합니다.[11]
  • FIFO 팬아웃 조합 규칙: 전체 파이프라인에서 순서 보장과 중복 제거가 필수적이라면, SNS FIFO 주제와 SQS FIFO 큐를 짝지어 구성해야 합니다. 이때 SNS FIFO 주제는 오직 SQS FIFO 큐만을 유효한 구독자로 지원하며, 이메일, SMS, 모바일 푸시, 일반 표준 SQS 큐로는 메시지를 보낼 수 없습니다.[12]

EventBridge: 규칙 기반의 지능형 이벤트 라우터

Amazon EventBridge는 다양한 이벤트 소스로부터 실시간 이벤트를 수신하여, 선언적인 규칙(Rules)을 통해 원하는 대상(Targets)으로 전달하는 완전 관리형 서버리스 이벤트 버스(Event Bus)입니다.[14]

  • 이벤트 소스의 3대 축:
    1. AWS 서비스 이벤트: 모든 AWS 계정에는 '기본(Default) 이벤트 버스'가 내장되어 있어, EC2 인스턴스 상태 변경, S3 객체 생성, Auto Scaling 수명 주기 이벤트 등을 코드 없이 자동으로 수집합니다.[13]
    2. 사용자 지정 애플리케이션: 자체 구축한 애플리케이션에서 PutEvents API를 호출하여 커스텀 이벤트를 발행할 수 있습니다.
    3. SaaS 파트너 이벤트: Datadog, Zendesk, PagerDuty, Auth0 등 외부 SaaS 플랫폼의 이벤트를 별도의 웹훅 수신 서버 구축 없이 파트너 이벤트 소스(Partner Event Source)를 통해 직접 이벤트 버스로 안전하게 유입시킬 수 있습니다.[15]
  • 규칙 및 JSON 이벤트 패턴 매칭: 이벤트 본문의 특정 필드(예: {"detail": {"status": ["CRITICAL"]}})와 일치하는 JSON 패턴 규칙을 작성하여, 일치하는 이벤트만을 Lambda 함수, SQS 대기열, Step Functions 상태 머신 등 최대 5개의 대상에 동시 라우팅합니다.[13]
  • EventBridge Scheduler: 수백만 건의 정기적인 cron 표현식 또는 rate 주기 스케줄링 작업을 지원하는 강력한 독립 스케줄러입니다.[14]

큐를 통한 트래픽 급증 흡수와 인스턴스당 백로그 기반 오토 스케일링

클라이언트의 쓰기 요청을 데이터베이스에 직접 전달하지 않고 중간에 SQS 큐를 배치하여 버퍼링하면, 데이터베이스가 일시적인 점검이나 락(Lock) 경합으로 지연되더라도 사용자 요청을 유실 없이 안전하게 받아낼 수 있습니다.[17]
이때 큐의 메시지를 소비하는 EC2 인스턴스 풀(Auto Scaling 그룹)은 큐의 단순 총 메시지 수만을 보고 확장하면 안 됩니다. 레슨 0012에서 배운 인스턴스당 백로그(Backlog per Instance = 큐의 대기 메시지 수 ÷ 현재 서비스 중인 인스턴스 수)를 지표로 하는 대상 추적(Target Tracking) 정책을 적용해야 워크로드 변화에 과부하나 불필요한 과소/과대 프로비저닝 없이 완벽하게 스케일링됩니다.[18]

Lambda를 SQS 소비자로 활용할 때의 메커니즘: Lambda 서비스를 소비자로 연결(Event Source Mapping)하면, Lambda 서비스가 내부 폴러(Poller)를 통해 큐를 지속적으로 폴링하여 여러 메시지를 배치(Batch)로 묶어 함수를 호출합니다. 함수가 에러 없이 성공적으로 반환되면 Lambda 서비스가 큐에서 해당 메시지 배치를 자동으로 삭제합니다. 만약 함수 실행 중 에러가 발생하면 배치는 삭제되지 않고 가시성 제한 시간이 지난 후 다시 큐에 노출되어 재시도되므로, Lambda 함수 로직은 반드시 멱등성을 지니도록 설계되어야 합니다.[19]

시험에 자주 나오는 핵심 패턴

  • "엄격한 처리 순서 보장 필수", "중복 처리 절대 불가(금융/결제)", "그룹 단위 순차 처리" → Amazon SQS FIFO 큐 (MessageGroupId 필수)
  • "초고속 무제한 처리량", "순서가 다소 섞여도 무관", "소비자의 멱등성 보장 가능" → Amazon SQS 표준 큐
  • "동일한 메시지가 다른 소비자에게 중복 처리되는 문제 발생" → 가시성 제한 시간(Visibility Timeout)을 메시지 실제 처리 시간보다 길게 늘려 설정
  • "형식이 잘못된 특정 결함 메시지가 무한 반복 실패하며 큐를 마비시킴" → DLQ(배달 못한 편지 큐) 연결 및 maxReceiveCount 지정
  • "소비자의 ReceiveMessage 호출 중 빈 응답이 너무 많아 SQS API 비용이 과도하게 청구됨" → 긴 폴링(Long Polling) 활성화 (WaitTimeSeconds > 0, 최대 20초)
  • "1건의 이벤트를 여러 개의 독립된 마이크로서비스가 각자 자기 속도로 처리해야 함" → Amazon SNS 주제로 발행 → 서비스별 SQS 큐로 팬아웃(Fanout) 구독
  • "SNS 주제에 메시지를 게시했는데 구독 중인 SQS 큐에 메시지가 들어오지 않음" → SQS 큐 리소스 기반 정책에서 SNS 서비스의 sqs:SendMessage 허용 여부 확인
  • "트래픽 폭증 시 데이터베이스 과부하 및 요청 유실 방지" → SQS 큐로 쓰기 요청 버퍼링, 백엔드 워커는 인스턴스당 백로그 지표로 대상 추적 확장
  • "AWS 리소스의 상태 변화나 서드파티 SaaS 파트너 이벤트에 반응하여 서버리스 실행" → Amazon EventBridge (이벤트 버스 + JSON 이벤트 패턴 규칙)

연습

Q1. 주문 시스템에서 같은 고객의 주문 변경은 반드시 보낸 순서대로, 중복 없이 처리돼야 합니다. 서로 다른 고객의 주문은 병렬로 처리해도 됩니다. 가장 적합한 설계는?

정답은 SQS FIFO 큐에 고객 ID를 그룹 ID(MessageGroupId)로 쓰는 것입니다. SQS FIFO 큐는 MessageGroupId가 동일한 메시지들 사이에서 엄격한 선입선출(FIFO) 순서를 보장하고 중복 처리를 방지합니다. 따라서 고객 ID를 그룹 ID로 지정하면, 동일 고객의 주문 변경 내역은 정확한 순서대로 순차 처리되면서도, 서로 다른 고객들의 메시지는 독립적인 여러 워커 프로세스에 의해 병렬로 고속 처리될 수 있습니다. 반면 표준 큐는 순서가 뒤바뀔 수 있으며 소비자 인스턴스 수를 늘린다고 순서 문제가 해결되지 않습니다.

Q2. EC2 소비자가 SQS 표준 큐에서 받은 메시지 하나를 처리하는 데 약 2분이 걸립니다. 큐는 기본 설정 그대로이며, 같은 주문이 두 번씩 처리되는 일이 잦습니다. 가장 먼저 바꿀 것은?

정답은 가시성 제한 시간을 처리 시간보다 길게 늘리는 것입니다. SQS 큐의 기본 가시성 제한 시간은 30초입니다. 작업자가 메시지 1건을 처리하는 데 2분(120초)이 걸린다면, 처리 시작 후 30초가 경과하는 순간 해당 메시지가 큐에서 다시 보이게(Visible) 됩니다. 그 결과 다른 소비자 인스턴스가 동일한 메시지를 가져가 처리하게 되므로 중복 처리가 발생합니다. 따라서 가시성 제한 시간을 실제 처리 시간인 2분보다 충분히 긴 3분~5분으로 늘려 주어야 합니다. 긴 폴링은 빈 응답 비용을 줄이는 기능이므로 중복 처리와 무관합니다.

Q3. 형식이 잘못된 일부 메시지가 매번 처리에 실패해 큐로 되돌아오며 소비자 자원을 계속 잡아먹습니다. 정상 메시지 처리는 이어가면서 실패 메시지를 나중에 분석하고 싶습니다. 가장 적합한 방법은?

정답은 DLQ(배달 못한 편지 큐)를 연결하고 maxReceiveCount를 설정하는 것입니다. 형식이 잘못된 독약 메시지는 소비자가 처리할 수 없어 계속 실패하고 큐로 되돌아옵니다. 원본 큐에 DLQ를 연결하고 최대 수신 시도 횟수(maxReceiveCount, 예: 3회)를 지정하면, 3번 실패한 메시지는 DLQ로 자동 격리되어 정상 메시지들의 처리를 방해하지 않으며, 엔지니어가 나중에 원인을 안전하게 분석할 수 있습니다. 메시지 보존 기간을 1분으로 줄이면 아직 처리되지 못한 정상적인 메시지까지 대량 유실되는 대참사가 발생합니다.

Q4. 소비자가 1초마다 ReceiveMessage를 호출하는데 대부분 빈 응답이 돌아오고, SQS 요청 비용이 예상보다 큽니다. 지연 시간을 크게 늘리지 않고 비용을 줄이려면?

정답은 긴 폴링을 켜고 WaitTimeSeconds를 20초로 설정하는 것입니다. 기본 짧은 폴링 방식(WaitTimeSeconds=0)에서는 큐가 비어 있으면 즉시 빈 응답을 반환하므로 무의미한 API 호출 횟수와 비용이 급증합니다. 대기 시간을 20초로 설정하여 긴 폴링을 활성화하면, 큐가 비어 있을 때 최대 20초 동안 소켓 연결을 열고 대기하다가 메시지가 도착하는 즉시 지연 없이 바로 반환합니다. 이를 통해 빈 응답 수를 극적으로 줄여 비용을 대폭 절감할 수 있습니다.

Q5. 주문이 생성될 때마다 결제, 재고, 분석 세 시스템이 같은 주문 이벤트를 각자 받아 자기 속도로 처리해야 합니다. 한 시스템이 잠시 멈춰도 그 시스템의 이벤트는 유실되면 안 됩니다. 어떤 조합이 맞습니까? (두 개를 고르세요)

정답은 주문 서비스가 SNS 주제에 이벤트를 게시함과 시스템마다 SQS 큐를 만들어 주제를 구독함입니다. 이것이 바로 전형적인 SNS 팬아웃(Fanout) 패턴입니다. 주문 서비스가 SNS 주제에 메시지를 1회 발행하면, SNS가 이를 복제하여 결제 큐, 재고 큐, 분석 큐로 각각 푸시합니다. 각 시스템은 자신만의 전용 SQS 큐를 독립적으로 폴링하므로, 특정 시스템에 장애가 발생해 처리가 지연되더라도 해당 시스템의 큐에 메시지가 안전하게 보관되어 유실되지 않습니다. 만약 세 시스템이 큐 하나를 공유해 폴링하면, 1건의 메시지는 3개 시스템 중 가장 먼저 가져간 단 하나의 시스템만 처리하고 삭제해 버립니다.

Q6. 웹 계층이 주문을 RDS에 직접 씁니다. 프로모션 때 쓰기가 몰리면 DB가 포화되어 주문이 유실됩니다. 주문은 몇 분 늦게 처리돼도 괜찮습니다. 가장 적합한 설계는?

정답은 SQS에 버퍼링하고, 작업자는 큐 백로그로 확장하는 것입니다. 웹 계층이 주문을 수신하면 즉시 RDS에 직접 쓰지 않고 SQS 큐에 메시지로 적재(버퍼링)합니다. 백엔드 워커 인스턴스들은 데이터베이스가 감당할 수 있는 안정적인 속도로 큐에서 작업을 꺼내어 DB에 기록합니다. 이때 워커 풀은 '인스턴스당 백로그' 지표 기반의 대상 추적 정책으로 오토 스케일링하여 밀려드는 대기열을 신속히 해소합니다. 웹 계층 서버 대수를 늘리는 것은 오히려 DB에 더 많은 동시 쓰기 폭주를 유발하여 데이터베이스 장애를 가속화시킬 뿐입니다.

Q7. 보안팀이 SaaS 헬프데스크(EventBridge 파트너)의 티켓 이벤트 중 "긴급" 티켓만 골라 Lambda와 Step Functions로 보내고 싶습니다. 코드를 최소화하는 방법은?

정답은 파트너 이벤트 소스를 이벤트 버스에 연결한 후 규칙을 생성하는 것입니다. Amazon EventBridge는 검증된 SaaS 파트너(Zendesk, Datadog 등)와의 네이티브 통합인 '파트너 이벤트 소스'를 제공합니다. 사용자는 웹훅을 받기 위한 별도의 EC2 웹 서버를 개발하거나 운영할 필요가 없으며, 이벤트 버스에 규칙(Rule)을 등록하여 JSON 이벤트 패턴으로 "긴급(Urgent)" 속성을 가진 이벤트만 선별 필터링한 후 Lambda와 Step Functions로 직접 라우팅할 수 있어 운영 코드 작성을 최소화할 수 있습니다.

Q8. (0002 복습) SQS 큐를 SNS 주제에 구독시켰는데, 게시한 메시지가 큐에 들어오지 않습니다. 같은 계정이며, 구독은 확인된 상태입니다. 가장 가능성 높은 원인과 해결은?

정답은 큐 정책(Queue Policy)에서 SNS 서비스에 sqs:SendMessage 권한을 허용하는 것입니다. SNS 주제가 메시지를 수신했을 때, 이를 구독 중인 SQS 큐로 실제로 집어넣는(Push) 주체는 최초 발행자가 아니라 바로 **SNS 서비스(Principal: sns.amazonaws.com)**입니다. 따라서 대상 SQS 큐의 리소스 기반 정책(큐 정책)에서 SNS 서비스 보안 주체에게 sqs:SendMessage 권한을 부여해야 정상적으로 메시지가 수신됩니다. 최초 발행자의 IAM 권한에는 오직 sns:Publish 권한만 있으면 충분합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 기억을 떠올려 직접 정리해 보세요. (1) SQS 표준 큐와 FIFO 큐의 3대 핵심 차이점(처리량, 전달 보장 및 중복 방지, 순서 보장)은 무엇인가요? (2) 가시성 제한 시간, 배달 못한 편지 큐(DLQ), 긴 폴링이 각각 해결하는 구체적인 시스템 장애 증상은 무엇인가요? (3) SQS, SNS, EventBridge를 한 문장씩 본질적 차이로 구분해 보세요.

(1) 표준 큐: 사실상 무제한 처리량, 최소 한 번 이상 전달(중복 가능 → 소비자의 멱등성 필수), 최선의 노력 순서화. FIFO 큐: 기본 초당 300~3,000건(높은 처리량 모드로 최대 7만 건), 정확히 한 번 처리(5분 중복 제거), MessageGroupId 기반 엄격한 선입선출(FIFO) 순서 보장.

(2) 가시성 제한 시간: 작업자가 처리 중인 메시지가 다른 작업자에게 노출되어 발생하는 '동일 메시지 중복 처리' 현상 방지. DLQ: 버그나 손상된 페이로드로 인해 반복 실패하는 '독약 메시지(Poison Pill)'를 격리하여 정상 큐 흐름 보호. 긴 폴링: 큐가 비어 있을 때 발생하는 빈 응답(Empty Response) 횟수를 줄여 '불필요한 SQS API 호출 비용' 절감.

(3) SQS는 소비자가 큐를 폴링하여 1:1로 작업을 꺼내어 버퍼링하는 대기열 서비스이고, SNS는 1건의 이벤트를 여러 구독자에게 사본으로 즉시 푸시하는 1:N 팬아웃 게시/구독 서비스이며, EventBridge는 JSON 이벤트 패턴 매칭 규칙을 통해 AWS 서비스 및 SaaS 파트너 이벤트를 지능적으로 라우팅하는 서버리스 이벤트 버스입니다.

핸즈온 실습 (선택, 프리 티어 범위): SNS 콘솔에서 표준 주제 1개를 생성하고, SQS 콘솔에서 표준 큐 2개(예: order-payment-queue, order-analytics-queue)를 생성해 보세요. 각 SQS 큐의 콘솔 화면에서 "SNS 주제 구독"을 클릭하여 방금 만든 SNS 주제를 연결합니다(이때 SQS 콘솔이 큐 정책을 자동으로 안전하게 추가해 줍니다). 그 후 SNS 주제에서 테스트 메시지 1건을 게시하고, 두 SQS 큐 콘솔의 "메시지 송수신(Poll for messages)" 메뉴에서 동일한 메시지 사본이 양쪽 큐에 모두 즉각 전달되었음을 확인해 보십시오. 실습이 끝난 후 생성한 주제와 큐를 삭제해 주세요.

퀴즈 점수와 틀렸던 문제가 있다면 언제든 질문해 주세요! 특히 Q5(큐 1개 공유 vs 시스템별 큐 분리)나 Q8(SNS와 SQS 간의 IAM/리소스 정책 권한 주체)은 실무와 시험 모두에서 가장 잦은 실수가 발생하는 지점입니다. EventBridge와 SNS 중 무엇을 골라야 할지 헷갈리는 아키텍처 상황이 있다면 편하게 남겨 주세요.
