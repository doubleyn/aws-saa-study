팬아웃: SNS → 여러 SQS

SNS 주제에 게시된 메시지가 복제되어 구독한 여러 엔드포인트로 푸시되는 것을 팬아웃이라 합니다. 주문 이벤트 하나를 처리용 큐와 분석용 큐가 각각 받는 것이 AWS 문서의 대표 예입니다.[8] SQS를 끼우면 즉시 알림을 받으면서 메시지가 큐에 남아 나중에 처리할 수도 있습니다.[9]

설정 함정 두 가지. 첫째, SNS가 큐에 넣으려면 큐 정책(리소스 기반 정책)이 sns.amazonaws.com에게 sqs:SendMessage를 허용해야 하고, aws:SourceArn으로 주제를 한정하는 것이 권장됩니다.[11] 둘째, 순서와 중복 제거가 필요하면 SNS FIFO 주제 + SQS FIFO 큐입니다. SNS FIFO 주제는 이메일·SMS·HTTP(S) 같은 엔드포인트로는 보낼 수 없습니다.[12]

EventBridge: 규칙으로 라우팅

EventBridge 이벤트 버스는 이벤트를 받아 0개 이상의 대상으로 전달하는 라우터입니다. 소스는 AWS 서비스, 직접 만든 애플리케이션, SaaS 파트너입니다.[14] 모든 계정의 기본 이벤트 버스는 AWS 서비스 이벤트(예: EC2 상태 변경)를 자동으로 받고, 규칙의 이벤트 패턴(JSON)과 일치하면 대상(예: Lambda)으로 보냅니다.[13] Zendesk, Datadog 같은 SaaS의 이벤트는 파트너 이벤트 소스를 이벤트 버스에 연결해 받습니다.[15] 일정 기반 실행은 EventBridge Scheduler(cron·rate 식)가 맡습니다.[14]

큐로 급증을 흡수하고, 큐 깊이로 확장

쓰기 요청을 SQS에 버퍼링하면 기본 DB가 잠시 불가해도 고객 요청을 계속 받을 수 있습니다.[17] 소비자 Auto Scaling 그룹은 큐 길이 자체가 아니라 인스턴스당 백로그(ApproximateNumberOfMessages ÷ InService 인스턴스 수)를 지표로, 허용 가능한 인스턴스당 백로그(허용 지연 ÷ 메시지당 평균 처리 시간)를 목표값으로 하는 대상 추적 정책을 씁니다. 메시지 수만 보면 인스턴스 수를 고려하지 못해 과하게 늘어날 수 있습니다.[18] 예: 인스턴스 10대, 메시지 1,500개, 허용 지연 10초, 처리 0.1초 → 목표 100, 현재 150이므로 확장.

Lambda를 소비자로 쓰면 Lambda가 큐를 폴링해 배치로 함수를 호출하고, 성공하면 메시지를 삭제합니다. 실패한 배치는 가시성 제한 시간이 지나면 다시 보이므로 함수는 멱등해야 합니다.[19]

시험 단골

  • "순서 보장", "중복 불가" → SQS FIFO (+ 그룹 ID). "처리량 최대", "순서 무관" → 표준
  • "같은 메시지가 두 번 처리됨" → 가시성 제한 시간을 처리 시간보다 길게
  • "계속 실패하는 메시지가 큐를 막음" → DLQ + maxReceiveCount
  • "빈 응답이 많고 비용이 큼" → 긴 폴링 (최대 20초)
  • "하나의 이벤트를 여러 시스템이 각자 처리" → SNS 팬아웃 → 시스템별 SQS 큐
  • "트래픽 급증 시 유실", "백엔드가 못 따라감" → SQS로 버퍼링, 소비자는 인스턴스당 백로그로 확장
  • "AWS 서비스 이벤트·SaaS 이벤트에 반응", "일정 실행" → EventBridge

연습

기억으로 푸세요.

Q1. 주문 시스템에서 같은 고객의 주문 변경은 반드시 보낸 순서대로, 중복 없이 처리돼야 합니다. 서로 다른 고객의 주문은 병렬로 처리해도 됩니다. 가장 적합한 설계는?

FIFO 큐는 메시지 그룹 안에서 순서를 보장하고 정확히 한 번 처리합니다. 고객 ID를 그룹으로 쓰면 고객별 순서는 지키면서 고객 간에는 병렬 처리됩니다. 표준 큐는 순서가 최선 노력이고 중복이 생길 수 있어 "소비자 수를 늘린다"가 해결책이 되지 못합니다.

Q2. EC2 소비자가 SQS 표준 큐에서 받은 메시지 하나를 처리하는 데 약 2분이 걸립니다. 큐는 기본 설정 그대로이며, 같은 주문이 두 번씩 처리되는 일이 잦습니다. 가장 먼저 바꿀 것은?

기본 가시성 제한 시간은 30초입니다. 2분 처리 중 30초가 지나면 메시지가 다시 보여 다른 소비자가 또 가져갑니다. 긴 폴링은 빈 응답을 줄이는 기능이라 중복 처리와는 무관합니다. (표준 큐는 원래 드물게 중복이 있으므로 소비자를 멱등하게 만드는 것도 함께 권장됩니다.)

Q3. 형식이 잘못된 일부 메시지가 매번 처리에 실패해 큐로 되돌아오며 소비자 자원을 계속 잡아먹습니다. 정상 메시지 처리는 이어가면서 실패 메시지를 나중에 분석하고 싶습니다. 가장 적합한 방법은?

DLQ는 maxReceiveCount번 받고도 삭제되지 않은 메시지를 격리해 분석할 수 있게 합니다. 보존 기간을 줄이면 정상 메시지까지 사라지고, 분석할 기회도 없습니다. 가시성 제한 시간을 12시간으로 하면 실패 메시지가 재시도까지 오래 숨을 뿐 해결되지 않습니다.

Q4. 소비자가 1초마다 ReceiveMessage를 호출하는데 대부분 빈 응답이 돌아오고, SQS 요청 비용이 예상보다 큽니다. 지연 시간을 크게 늘리지 않고 비용을 줄이려면?

긴 폴링은 메시지가 올 때까지(최대 20초) 기다렸다가 응답하므로 빈 응답과 거짓 빈 응답이 줄어 비용이 내려가고, 메시지가 오면 바로 반환합니다. SNS를 앞에 두어도 SQS 소비자는 여전히 폴링해야 합니다.

Q5. 주문이 생성될 때마다 결제, 재고, 분석 세 시스템이 같은 주문 이벤트를 각자 받아 자기 속도로 처리해야 합니다. 한 시스템이 잠시 멈춰도 그 시스템의 이벤트는 유실되면 안 됩니다. 어떤 조합이 맞습니까? (두 개를 고르세요)

SNS 팬아웃입니다. 주제는 구독자 전원에게 사본을 보내고, 각 SQS 큐가 메시지를 보관하므로 한 시스템이 멈춰도 자기 큐에 쌓였다가 나중에 처리됩니다. 큐 하나를 함께 폴링하면 메시지 하나를 한 소비자만 처리하고 삭제하므로 세 시스템이 모두 받지 못합니다.

Q6. 웹 계층이 주문을 RDS에 직접 씁니다. 프로모션 때 쓰기가 몰리면 DB가 포화되어 주문이 유실됩니다. 주문은 몇 분 늦게 처리돼도 괜찮습니다. 가장 적합한 설계는?

큐가 급증을 흡수하고, 작업자는 DB가 감당할 속도로 씁니다. 작업자 Auto Scaling 그룹은 인스턴스당 백로그를 목표로 대상 추적하면 쌓인 일에 비례해 확장됩니다. 웹 계층을 늘리면 DB에 쓰기가 더 몰려 문제가 커집니다. SNS는 메시지를 보관하지 않아 버퍼가 되지 못합니다.

Q7. 보안팀이 SaaS 헬프데스크(EventBridge 파트너)의 티켓 이벤트 중 "긴급" 티켓만 골라 Lambda와 Step Functions로 보내고 싶습니다. 코드를 최소화하는 방법은?

EventBridge는 SaaS 파트너 이벤트를 파트너 이벤트 소스로 받고, 규칙의 이벤트 패턴으로 "긴급"만 골라 여러 대상(규칙당 최대 5개)에 보냅니다. EC2 웹훅 서버나 Lambda 분기 코드는 같은 일을 직접 구현하는 것이라 운영 부담이 큽니다.

Q8. (0002 복습) SQS 큐를 SNS 주제에 구독시켰는데, 게시한 메시지가 큐에 들어오지 않습니다. 같은 계정이며, 구독은 확인된 상태입니다. 가장 가능성 높은 원인과 해결은?

큐에 메시지를 넣는 주체는 게시자가 아니라 SNS 서비스입니다. 그래서 큐의 리소스 기반 정책이 Principal sns.amazonaws.com에게 sqs:SendMessage를 허용해야 하고, aws:SourceArn으로 주제를 한정합니다. 게시자 IAM 정책은 sns:Publish만 있으면 됩니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) SQS 표준과 FIFO의 차이 세 가지(처리량·전달·순서). (2) 가시성 제한 시간, DLQ, 긴 폴링이 각각 해결하는 증상. (3) SQS·SNS·EventBridge를 한 줄씩 구분.

(1) 표준: 사실상 무제한 처리량, 최소 한 번 전달(중복 가능 → 멱등), 최선 노력 순서. FIFO: 배치 없이 초당 300건(배치 시 3,000메시지, 높은 처리량 모드로 확장), 정확히 한 번 처리(5분 중복 제거), 메시지 그룹 안에서 순서 보장.

(2) 가시성 제한 시간(기본 30초, 최대 12시간): 같은 메시지 중복 처리. DLQ(maxReceiveCount, 같은 유형·계정·리전): 반복 실패하는 메시지 격리. 긴 폴링(최대 20초): 빈 응답과 비용.

(3) SQS: 소비자가 폴링하는 버퍼, 메시지당 소비자 하나. SNS: 구독자 전원에게 푸시하는 팬아웃. EventBridge: 이벤트 패턴 규칙으로 AWS·SaaS·커스텀 이벤트를 대상에 라우팅.
