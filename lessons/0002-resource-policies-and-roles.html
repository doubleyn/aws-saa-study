두 번째 종류의 정책

0001에서 다룬 자격 증명 기반 정책은 사용자·그룹·역할에 붙습니다. 정책을 리소스 쪽에 붙일 수도 있습니다. S3 버킷 정책, SQS 큐 정책, KMS 키 정책이 그런 리소스 기반 정책입니다.[1]

// S3 버킷 정책 (버킷 acme-reports에 연결)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:user/alice" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::acme-reports/*"
  }]
}

새로 나온 요소는 Principal, 즉 누구에게 허용하는지입니다. 리소스 기반 정책에는 Principal이 필수이고, 자격 증명 기반 정책에는 쓸 수 없습니다. 정책이 붙은 대상이 곧 주체이기 때문입니다.[2]

Principal에 쓸 수 있는 것뜻
arn:aws:iam::111122223333:user/alice그 사용자 한 명
arn:aws:iam::111122223333:role/Auditor그 역할
arn:aws:iam::111122223333:root 또는 "111122223333"계정 전체에 위임. 루트 사용자만 뜻하는 것이 아니며, 그 계정 관리자가 자기 사용자에게 다시 권한을 줘야 함[2]
"*"모든 주체. Allow와 함께 쓰면 익명 사용자까지 포함

IAM 그룹은 Principal이 될 수 없습니다. AWS 설명은 그룹이 "relate to permissions, not authentication"이라는 것입니다. 그룹은 권한 묶음일 뿐 인증 주체가 아닙니다. 그룹 안에 그룹을 넣을 수도 없습니다.[3]

새 규칙 세 개

  1. 같은 계정이면 어느 한쪽만 허용해도 허용(합집합). 자격 증명 기반 정책이든 리소스 기반 정책이든, 하나가 Allow하면 됩니다.[4]
    예외: 역할 신뢰 정책과 KMS 키 정책은 반드시 그 정책 자체가 명시적으로 허용해야 합니다.[5]
  2. 다른 계정이면 양쪽이 모두 허용해야 허용(교집합). 요청자 계정의 자격 증명 기반 정책 그리고 리소스 계정의 리소스 기반 정책이 둘 다 Allow해야 합니다.[6]
  3. 역할을 맡으면 원래 권한은 잠시 내려놓는다. 역할 사용 중에는 역할이 허용한 것만 할 수 있고, 원래 사용자 권한은 중지됩니다.[7]

0001의 규칙 3(일치하는 Deny는 무조건 이긴다)은 여기서도 그대로입니다. 어느 계정의 어느 정책에 있든 명시적 거부가 있으면 거부입니다.

역할 = 신뢰 정책 + 권한 정책

IAM 역할은 사용자처럼 권한을 가진 자격 증명이지만, 비밀번호나 액세스 키 같은 장기 자격 증명이 없습니다. 역할을 맡으면(sts:AssumeRole) 임시 보안 자격 증명을 받습니다.[8] 역할에는 정책이 두 장 붙습니다.

신뢰 정책 (trust policy)권한 정책 (permissions policy)
질문누가 이 역할을 맡을 수 있나?맡은 뒤 무엇을 할 수 있나?
종류리소스 기반 정책 (Principal 필수)자격 증명 기반 정책

그래서 계정 A의 사용자가 계정 B의 역할을 맡으려면 규칙 5에 따라 두 관문이 필요합니다. 계정 B 역할의 신뢰 정책 Principal에 계정 A가 있어야 하고, 계정 A에서 그 사용자에게 해당 역할 ARN에 대한 sts:AssumeRole 권한을 줘야 합니다.[7]

시험 단골: EC2 위의 애플리케이션

EC2에서 도는 앱이 S3를 읽어야 할 때 정답은 거의 항상 IAM 역할을 인스턴스 프로파일로 연결하는 것입니다. 인스턴스 프로파일이 역할을 담아 임시 자격 증명을 제공하므로, 인스턴스에 액세스 키를 배포할 필요가 없습니다. 한 인스턴스에는 한 번에 역할 하나만 연결할 수 있습니다.[9] 보기에 "액세스 키를 인스턴스에 저장"이 나오면 오답 후보입니다. IAM 모범 사례 2번이 "워크로드는 IAM 역할의 임시 자격 증명을 사용"하라는 것입니다.[10]

연습

등장인물: 계정 111122223333(버킷 acme-reports 소유)의 사용자 alice, 그리고 다른 계정 444455556666의 사용자 bob. 기억으로 푸세요.

Q1. alice에게는 S3 관련 자격 증명 기반 정책이 하나도 없습니다. alice가 acme-reports/q3.pdf를 GetObject 합니다.

// acme-reports 버킷 정책
{ "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:user/alice" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

alice와 버킷이 같은 계정입니다. 규칙 4에 따라 리소스 기반 정책 하나만 허용해도 충분합니다.

Q2. bob의 자격 증명 기반 정책은 arn:aws:s3:::acme-reports/*에 대한 s3:GetObject를 허용합니다. 버킷 정책에는 계정 444455556666에 대한 내용이 없습니다. bob이 GetObject 합니다.

bob은 다른 계정입니다. 자기 계정에서 아무리 허용해도 리소스 계정의 버킷 정책이 허용하지 않으면 관문 ②에서 막힙니다. 자기 계정 권한만으로 남의 계정 리소스에 들어갈 수 있다면 큰일이겠죠.

Q3. 버킷 정책이 아래와 같고, bob의 자격 증명 기반 정책도 acme-reports/*에 대한 s3:GetObject를 허용합니다. bob이 GetObject 합니다.

{ "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::444455556666:root" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

:root는 루트 사용자만이 아니라 계정 444455556666 전체에 위임한다는 뜻입니다. 그 계정이 bob에게 다시 허용했으니 두 관문을 모두 통과합니다. 실무에서 흔한 교차 계정 공유 패턴입니다.

Q4. Q3과 같은 설정인데, bob에게 아래 정책이 하나 더 붙어 있습니다.

{ "Effect": "Deny", "Action": "s3:*",
  "Resource": "arn:aws:s3:::acme-reports/*" }

0001 복습입니다. 계정이 몇 개든, Allow가 몇 개든, 일치하는 Deny가 이깁니다.

Q5. alice의 자격 증명 기반 정책은 같은 계정의 역할 role/Auditor에 대한 sts:AssumeRole을 허용합니다. 그런데 Auditor의 신뢰 정책 Principal에는 alice도, 계정 111122223333도 없습니다. alice가 역할을 맡으려 합니다.

함정 문제입니다. 같은 계정이라 규칙 4(합집합)가 떠올랐다면, 그 예외를 기억하세요. 역할 신뢰 정책은 반드시 직접 허용해야 합니다. 그래서 같은 계정이어도 양쪽이 모두 필요합니다. Deny 문장은 없으니 "명시적 거부"는 아닙니다.

Q6. (시험형) EC2 인스턴스에서 도는 애플리케이션이 S3 버킷의 객체를 읽어야 합니다. 가장 안전한 방법은?

역할은 인스턴스 프로파일을 통해 자동으로 갱신되는 임시 자격 증명을 줍니다. 장기 키를 저장하는 보기는 유출 위험이 있고, 루트 키는 절대 쓰면 안 되며, "*" Allow는 익명 사용자까지 엽니다.

Q7. (시험형) 계정 A의 개발자가 계정 B의 역할로 전환(switch role)했습니다. 역할을 쓰는 동안, 원래 계정 A 사용자 정책이 허용하던 작업은?

규칙 6입니다. 공식 문서 표현으로는 원래 권한이 "suspended", 즉 중지되었다가 역할을 빠져나오면 되돌아옵니다.[7]

Q8. S3 버킷 정책의 Principal에 넣을 수 없는 것은?

그룹은 권한 묶음일 뿐 인증 주체가 아니라서 Principal이 될 수 없습니다. 팀 전체에 버킷 접근을 주려면 그룹에 자격 증명 기반 정책을 붙이거나(같은 계정), 역할을 만들어 신뢰하게 합니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) 같은 계정과 다른 계정에서 판정 규칙이 어떻게 다른가? (2) 계정 A의 사용자가 계정 B의 역할을 맡으려면 어디에 무엇을 설정해야 하나?

(1) 같은 계정은 자격 증명 기반 정책과 리소스 기반 정책 중 하나만 허용해도 됩니다. 단, 역할 신뢰 정책과 KMS 키 정책은 예외로 직접 허용해야 합니다. 다른 계정은 양쪽 모두 허용해야 합니다. 어느 경우든 명시적 거부가 이깁니다.

(2) 계정 B: 역할의 신뢰 정책 Principal에 계정 A(또는 그 사용자)를 넣습니다. 계정 A: 사용자의 자격 증명 기반 정책에서 그 역할 ARN에 대한 sts:AssumeRole을 허용합니다. 맡은 뒤 할 수 있는 일은 역할의 권한 정책이 정합니다.
