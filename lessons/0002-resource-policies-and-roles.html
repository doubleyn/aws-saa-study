두 번째 정책 유형: 리소스 기반 정책(Resource-based Policy)

0001에서 다룬 자격 증명 기반 정책(Identity-based Policy)은 요청을 보내는 주체(사용자, 그룹, 역할)에 직접 연결했습니다. 반면, AWS에서는 정책을 리소스 쪽에 직접 연결할 수도 있습니다. S3 버킷 정책, SQS 대기열 정책, KMS 키 정책 등이 대표적인 리소스 기반 정책입니다.[1]

// S3 버킷 정책 예시 (acme-reports 버킷에 직접 연결)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:user/alice" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::acme-reports/*"
  }]
}

리소스 기반 정책에서 새롭게 등장하는 필수 요소는 바로 Principal(주체)입니다. 즉, "이 리소스에 접근할 수 있는 대상이 누구인가"를 지정하는 항목입니다. 리소스 기반 정책에는 Principal이 반드시 포함되어야 하지만, 자격 증명 기반 정책에는 사용할 수 없습니다. 자격 증명 기반 정책은 정책이 붙어 있는 사용자나 역할 자체가 이미 명확한 주체이기 때문입니다.[2]

Principal에 지정할 수 있는 값의미 및 상세 설명
arn:aws:iam::111122223333:user/alice특정 IAM 사용자 한 명에게만 직접 접근을 허용합니다.
arn:aws:iam::111122223333:role/Auditor특정 IAM 역할을 맡은 주체에게 접근을 허용합니다.
arn:aws:iam::111122223333:root 또는 "111122223333"해당 AWS 계정 전체에 권한 위임을 허용합니다. 루트 사용자 개인만을 뜻하는 것이 아니며, 해당 계정의 관리자가 자기 계정 내부의 사용자나 역할에게 자격 증명 기반 정책으로 권한을 재부여할 수 있도록 위임한다는 뜻입니다.[2]
"*"모든 주체에게 접근을 허용합니다. Allow와 함께 쓰면 인증되지 않은 익명 사용자(인터넷 전체)까지 공개되므로 퍼블릭 웹사이트 호스팅 등이 아니라면 각별히 주의해야 합니다.

⚠️ 주의: IAM 그룹은 Principal에 지정할 수 없습니다.
AWS 공식 문서에서는 IAM 그룹이 "인증 주체가 아니라 권한을 묶어서 관리하기 위한 단위(relate to permissions, not authentication)"라고 설명합니다. 그룹은 사용자들을 한 번에 관리하기 위한 묶음일 뿐 로그인이나 서명을 수행하는 독립된 주체가 아닙니다. 따라서 Principal에는 개별 사용자, 역할, 계정 단위만 올 수 있습니다. (또한 IAM 그룹 안에 하위 그룹을 중첩해서 넣는 것도 지원되지 않습니다.)[3]

권한 평가의 확장 규칙 세 가지

  1. 규칙 4. 같은 계정 안에서는 둘 중 한쪽만 허용해도 접근이 허용됩니다 (합집합 방식).
    요청자와 리소스가 동일한 AWS 계정에 속해 있다면, 사용자의 자격 증명 기반 정책이나 리소스 쪽의 리소스 기반 정책 중 어느 한쪽에서만 Allow를 선언해도 최종적으로 작업이 허용됩니다.[4]
    ⚠️ 중요 예외 두 가지: IAM 역할의 신뢰 정책(Trust Policy)과 KMS 키 정책(Key Policy)은 반드시 해당 정책 자체에서 명시적으로 Allow를 해주어야 합니다. 사용자의 정책에서 아무리 허용해도, 신뢰 정책이나 키 정책이 열려있지 않으면 접근할 수 없습니다.[5]
  2. 규칙 5. 서로 다른 계정 간(교차 계정)에는 양쪽 정책 모두에서 허용해야만 접근할 수 있습니다 (교집합 방식).
    요청자 계정의 자격 증명 기반 정책 그리고 리소스 소유 계정의 리소스 기반 정책이 둘 다 Allow해야만 작업이 허용됩니다.[6] 내 계정에서 아무리 허용 정책을 작성했더라도, 상대방 계정의 리소스 정책에서 문을 열어주지 않으면 다른 계정 리소스에는 절대 접근할 수 없습니다.
  3. 규칙 6. IAM 역할을 맡으면(AssumeRole), 기존 사용자의 원래 권한은 일시 중지됩니다.
    역할을 임시로 위임받아 사용하는 동안에는 오직 그 '역할'에 연결된 권한만 적용됩니다. 원래 사용자가 개인적으로 가지고 있던 기존 권한은 역할 사용 중에는 모두 정지되며, 역할을 벗어났을 때 원래대로 복귀합니다.[7]

0001에서 배운 절대 규칙, "일치하는 Deny는 다른 모든 허용을 이긴다"는 원칙은 교차 계정 상황에서도 변함없이 그대로 적용됩니다. 어느 계정의 어떤 정책에서든 일치하는 명시적 Deny가 단 하나라도 존재한다면 요청은 즉시 차단됩니다.

IAM 역할의 핵심: 신뢰 정책(Trust Policy)과 권한 정책(Permissions Policy)

IAM 역할(Role)은 특정 권한을 가진 IAM 자격 증명이지만, 비밀번호나 액세스 키 같은 장기적인 보안 자격 증명을 갖지 않습니다. 대신 역할을 필요로 하는 주체가 임시로 역할을 맡는 순간(sts:AssumeRole API 호출), AWS Security Token Service(STS)로부터 자동으로 만료되는 임시 보안 자격 증명(Temporary Security Credentials)을 발급받습니다.[8] IAM 역할에는 항상 두 종류의 정책이 함께 붙어 있습니다.

구분신뢰 정책 (Trust Policy)권한 정책 (Permissions Policy)
핵심 질문"누가 이 역할을 맡을 수 있는가?" (역할의 대문)"역할을 맡은 뒤 무엇을 할 수 있는가?" (활동 범위)
정책의 유형리소스 기반 정책 (Principal 지정 필수)자격 증명 기반 정책

따라서 계정 A의 사용자 bob이 계정 B에 있는 감사 역할을 맡으려면 규칙 5에 따라 두 가지 관문이 모두 충족되어야 합니다. 첫째, 계정 B에 위치한 역할의 신뢰 정책 Principal 항목에 계정 A(또는 사용자 bob)가 명시되어 있어야 하고, 둘째, 계정 A의 bob에게 해당 역할 ARN에 대한 sts:AssumeRole 호출을 허용하는 자격 증명 기반 정책이 부여되어 있어야 합니다.[7]

시험 및 실무 핵심: EC2 인스턴스 위의 애플리케이션

EC2 인스턴스에서 실행되는 백엔드 애플리케이션이 S3나 DynamoDB 같은 AWS 리소스에 안전하게 접근해야 할 때, AWS가 강력하게 권고하는 정답은 항상 IAM 역할을 인스턴스 프로파일(Instance Profile)로 인스턴스에 연결하는 것입니다. 인스턴스 프로파일이 역할을 전달하여 내부 메타데이터 서비스를 통해 자동으로 갱신되는 임시 자격 증명을 공급하므로, 인스턴스 내부의 코드나 파일에 영구 액세스 키를 저장할 필요가 전혀 없습니다. (인스턴스 하나에는 한 번에 하나의 인스턴스 프로파일만 연결할 수 있습니다.)[9] 시험 보기에서 "액세스 키를 인스턴스 파일이나 AMI에 저장한다"는 보기가 나오면 보안 위험이 있는 오답 후보입니다. IAM 보안 모범 사례에서도 "워크로드는 반드시 IAM 역할의 임시 자격 증명을 사용할 것"을 강조합니다.[10]

실전 연습: 시나리오 판정해 보기

등장인물: 계정 111122223333(S3 버킷 acme-reports 소유)의 IAM 사용자 alice, 그리고 별도의 외부 계정 444455556666에 속한 IAM 사용자 bob. 방금 학습한 규칙들을 떠올리며 풀어보세요.

Q1. alice에게는 S3 관련 자격 증명 기반 정책이 하나도 없습니다. alice가 acme-reports/q3.pdf 객체를 다운로드(GetObject)하려고 합니다.

// acme-reports 버킷 정책
{ "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:user/alice" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

사용자 alice와 S3 버킷이 동일한 AWS 계정에 속해 있습니다. 규칙 4에 따라 동일 계정 내부에서는 자격 증명 기반 정책이나 리소스 기반 정책 중 어느 한쪽에서만 허용해도 충분히 요청이 승인됩니다.

Q2. 다른 계정의 사용자 bob의 자격 증명 기반 정책에는 arn:aws:s3:::acme-reports/*에 대한 s3:GetObject가 명시적으로 허용되어 있습니다. 하지만 대상 버킷 정책에는 bob의 계정(444455556666)에 대한 허용 규칙이 전혀 없습니다. bob이 GetObject를 호출하면 어떻게 될까요?

bob은 다른 외부 계정의 사용자입니다(교차 계정 접근). 규칙 5에 따라 자기 계정 정책에서 아무리 허용했더라도, 리소스를 소유한 계정 쪽의 버킷 정책에서 허용해주지 않으면 관문 ②에서 막혀 암묵적 거부가 발생합니다. 내 계정의 설정만으로 다른 회사의 S3 파일에 무단으로 들어갈 수 있다면 심각한 보안 사고가 되겠죠.

Q3. 버킷 정책이 아래와 같이 설정되어 있고, bob의 자격 증명 기반 정책에서도 acme-reports/*에 대한 s3:GetObject를 허용하고 있습니다. bob이 GetObject를 호출하면 어떻게 될까요?

{ "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::444455556666:root" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

Principal에 명시된 :root는 루트 사용자 개인만을 뜻하는 것이 아니라 계정 444455556666 전체에 권한 관리를 위임한다는 의미입니다. 버킷 소유 계정이 bob의 계정에 접근을 개방했고, bob의 계정 관리자가 bob 사용자에게 자격 증명 기반 정책으로 GetObject 권한을 주었으므로 두 관문을 모두 성공적으로 통과합니다. 이것이 실무에서 가장 권장되는 안전한 교차 계정 공유 패턴입니다.

Q4. Q3과 완전히 동일한 설정이지만, bob의 사용자 정책에 아래와 같은 Deny 규칙이 하나 더 연결되어 있습니다. bob이 GetObject를 호출하면?

{ "Effect": "Deny", "Action": "s3:*",
  "Resource": "arn:aws:s3:::acme-reports/*" }

0001의 핵심 규칙 복습입니다. 교차 계정이든 단일 계정이든, Allow가 몇 개가 존재하든 간에, 요청과 일치하는 명시적 Deny는 무조건 이깁니다. bob에게 붙은 Deny 정책 때문에 요청은 즉시 차단됩니다.

Q5. alice의 자격 증명 기반 정책에는 동일 계정의 역할 role/Auditor에 대한 sts:AssumeRole 권한이 허용되어 있습니다. 그런데 해당 역할의 신뢰 정책(Trust Policy) Principal에는 alice도, 계정 111122223333도 지정되어 있지 않습니다. alice가 역할을 맡으려고 하면 어떻게 될까요?

자주 걸려 넘어지는 함정 문제입니다. 동일 계정 내부라도 규칙 4의 핵심 예외를 기억해야 합니다. IAM 역할의 신뢰 정책과 KMS 키 정책은 반드시 리소스 정책 자체에서 대상을 직접 명시적으로 허용해주어야 합니다. 따라서 같은 계정이라 하더라도 신뢰 정책의 Principal에 허용되어 있지 않으면 역할을 맡을 수 없습니다. (명시적 Deny 문장이 있는 것은 아니므로 명시적 거부가 아닌 암묵적 거부입니다.)

Q6. (실제 시험 유형) EC2 인스턴스에서 구동되는 프로덕션 웹 애플리케이션이 S3 버킷에 저장된 이미지 파일들을 읽어와야 합니다. AWS 보안 모범 사례에 부합하는 가장 안전하고 효율적인 아키텍처 설계는?

정답은 IAM 역할을 인스턴스 프로파일로 연결하는 것입니다. 이렇게 하면 EC2 내부 메타데이터 서비스를 통해 자동으로 교체되는 안전한 임시 자격 증명을 제공받으므로 영구 키를 관리할 필요가 없습니다. 파일이나 환경 변수에 장기 액세스 키를 저장하는 것은 유출 위험이 매우 크며, 루트 키는 절대 사용해서는 안 됩니다. 또한 Principal을 "*"로 여는 것은 인터넷 전체에 데이터를 공개하는 위험한 설정입니다.

Q7. (실제 시험 유형) 계정 A의 개발자가 임시 문제 해결을 위해 계정 B의 특정 역할로 전환(Switch Role)했습니다. 이 개발자가 계정 B의 역할을 사용하고 있는 동안, 원래 계정 A의 사용자 정책이 허용하던 작업들은 어떻게 처리될까요?

규칙 6에 관한 문제입니다. AWS 공식 문서에서는 역할을 맡는 동안 기존 사용자의 원래 권한은 "일시 중지(Suspended)" 상태가 된다고 설명합니다. 즉, 역할을 사용하는 동안에는 오직 그 역할에 연결된 권한만 행사할 수 있으며, 역할 세션이 종료되어 본래 사용자 상태로 돌아왔을 때 비로소 원래의 권한이 복원됩니다.[7]

Q8. S3 버킷 정책의 Principal 항목에 유효한 값으로 지정할 수 없는 것은?

IAM 그룹은 Principal이 될 수 없습니다. 그룹은 권한을 모아서 여러 사용자에게 한 번에 부여하기 위한 관리 도구일 뿐, 직접 인증을 거치는 주체가 아니기 때문입니다. 특정 개발팀 전체에 버킷 접근 권한을 부여하고 싶다면, 동일 계정 내에서 해당 그룹에 S3 허용 정책을 붙이거나, 역할을 만든 뒤 그룹 구성원들에게 그 역할을 맡을 수 있는 권한을 주는 방식을 사용해야 합니다.

(1) 동일 계정 내부와 서로 다른 교차 계정 간에 권한 평가 규칙(합집합 vs 교집합)은 어떻게 다른가요?
(2) 계정 A의 사용자가 계정 B의 특정 역할을 맡으려면 양쪽 계정에 각각 어떤 설정을 해주어야 하나요?

(1) 동일 계정 vs 교차 계정:
- 동일 계정: 자격 증명 기반 정책이나 리소스 기반 정책 중 어느 한쪽에서만 허용해도 접근이 가능합니다(합집합). 단, 예외적으로 역할 신뢰 정책과 KMS 키 정책은 반드시 리소스 정책 자체에서 허용해야 합니다.
- 교차 계정: 요청자 계정의 자격 증명 기반 정책과 리소스 계정의 리소스 기반 정책 양쪽 모두에서 허용해야만 접근할 수 있습니다(교집합). 어느 경우든 명시적 Deny가 있으면 무조건 차단됩니다.

(2) 계정 간 역할 위임 설정:
- 계정 B (리소스/역할 계정): 역할의 신뢰 정책(Trust Policy) Principal에 계정 A(또는 계정 A의 특정 사용자 ARN)를 지정하여 역할을 맡을 수 있는 문을 열어줍니다.
- 계정 A (요청자 계정): 사용자의 자격 증명 기반 정책에 계정 B 역할의 ARN에 대한 sts:AssumeRole API 호출을 허용해줍니다.
- 역할을 맡은 후 실제로 어떤 작업을 할 수 있는지는 계정 B 역할에 연결된 권한 정책(Permissions Policy)이 결정합니다.

추가 학습 및 실습

1차 공식 문서 (권장, 약 10분): AWS IAM 사용 설명서의 "Cross-account policy evaluation logic"을 읽어보세요. 오늘 배운 규칙 5(교차 계정 평가 논리)가 AWS 공식 다이어그램과 함께 상세히 정리되어 있습니다. (한국어 문서: URL의 docs.aws.amazon.com/ 뒤에 ko_kr/ 추가)

콘솔 실습 (선택 사항): 개인 AWS 계정이 하나라도 있다면, 콘솔에서 임의의 테스트용 IAM 역할을 생성하고 신뢰 정책에 본인 사용자를 등록한 뒤, 콘솔 우측 상단의 프로필 메뉴에서 "역할 전환(Switch Role)"을 직접 실행해 보세요. 상단 바 색상이 바뀌며 역할에 지정된 권한으로 즉시 전환되는 흐름을 체감할 수 있습니다.

퀴즈를 풀면서 헷갈렸거나 오답을 고른 문항이 있다면 언제든 알려주세요. 특히 Q5(신뢰 정책의 예외적 성격)와 Q3(:root가 계정 전체 권한 위임을 뜻한다는 점)는 처음 접할 때 가장 많이 혼동하는 포인트입니다. 편하게 질문해 주시면 함께 짚어보겠습니다.
