이 요청은 허용될까?
IAM 정책을 평가하는 세 가지 핵심 규칙

어떤 IAM 정책 JSON과 특정 API 요청이 주어졌을 때, 해당 요청이 허용(Allow)될지 거부(Deny)될지 빠르게 정확히 판정하는 원리를 쉽게 배웁니다.

왜 IAM 정책 평가부터 배워야 할까요?

시험 관점에서: AWS Certified Solutions Architect - Associate (SAA-C03) 시험에서 '보안' 도메인은 전체 채점 비중의 30%를 차지하는 가장 중요한 영역입니다. 그 첫 번째 핵심 과제가 바로 "AWS 리소스에 대한 안전한 접근 제어 설계"입니다.[1] 실제 시험에서는 복잡한 IAM 정책 JSON을 보여주고 "이 정책이 적용된 사용자가 수행할 수 있는 작업은 무엇인가?" 또는 "특정 리소스에 접근하지 못하는 이유는 무엇인가?"를 묻는 문제가 자주 출제됩니다.

실무 관점에서: AWS 환경을 운영하다 보면 수시로 마주치는 오류가 바로 AccessDenied(접근 거부)입니다. 이때 "어떤 정책의 어떤 규칙이 이 요청을 차단하고 있는가?"를 빠르게 찾아내려면, AWS 내부에서 권한을 평가하는 논리적 순서를 정확하게 꿰뚫고 있어야 합니다.

IAM 정책(JSON)의 기본 구조

사용자(User), 그룹(Group), 역할(Role)처럼 요청을 보내는 주체에 연결하는 정책을 자격 증명 기반 정책(Identity-based Policy)이라고 부릅니다.[2] 기본 구조는 다음과 같이 생겼습니다.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::acme-reports/*"
    }
  ]
}
요소역할 및 상세 설명
Version정책 언어의 문법 버전을 나타냅니다. 현재 표준은 항상 "2012-10-17"로 작성해야 합니다. 구버전인 "2008-10-17"은 정책 변수 등의 최신 기능을 지원하지 않으므로 새 정책에 사용하면 안 됩니다.[3]
Effect해당 요청을 허용할 것인지("Allow"), 아니면 명시적으로 차단할 것인지("Deny")를 선언합니다.
Action어떤 AWS API 작업(함수 호출)을 대상으로 할지 명시합니다. 예를 들어 "s3:GetObject"는 S3 객체 다운로드 작업을 뜻합니다. 여러 글자를 대체하는 와일드카드 *나 한 글자를 대체하는 ?를 조합해 "s3:*"(모든 S3 작업), "iam:*AccessKey*"처럼 유연하게 범위를 지정할 수 있습니다.[4]
Resource위 Action이 적용될 구체적인 AWS 리소스를 지정합니다. 고유 식별자인 ARN(Amazon Resource Name) 형식으로 표현하며, 예를 들어 "arn:aws:s3:::acme-reports/*"는 'acme-reports'라는 이름의 S3 버킷 내부의 모든 객체를 의미합니다.

특정 API 요청이 정책의 Statement(선언문)와 일치한다(Match)는 것은, 그 Statement에 적힌 Action과 Resource 조건이 모두 해당 요청과 맞아떨어진다는 뜻입니다. 둘 중 하나라도 맞지 않으면 그 Statement는 해당 요청에 아무런 영향도 주지 않습니다.

IAM 정책을 판정하는 세 가지 절대 규칙

단일 AWS 계정 안에서 자격 증명 기반 정책만 평가할 때는 다음 세 가지 규칙만 순서대로 적용하면 어떤 복잡한 상황도 명쾌하게 풀어낼 수 있습니다.[5]

  1. 1. 기본값은 항상 거부입니다 (암묵적 거부, Implicit Deny).
    어떤 정책에서도 명시적으로 허용하지 않은 모든 요청은 기본적으로 차단됩니다. 이를 '암묵적 거부'라고 부릅니다. (계정의 모든 권한을 태생적으로 가진 루트(Root) 사용자만 예외입니다.)
  2. 2. 일치하는 Allow가 하나라도 있으면 허용됩니다 (명시적 허용, Explicit Allow).
    요청과 일치하는 Allow 선언문이 하나라도 존재하면 작업이 정상적으로 수행됩니다. 이 정책이 사용자에게 직접 부여되었든, 사용자가 속한 IAM 그룹을 통해 물려받았든 똑같이 유효합니다.
  3. 3. 일치하는 Deny는 다른 모든 허용을 이깁니다 (명시적 거부 우선, Explicit Deny Overrides Allow).
    AWS 공식 문서의 핵심 원칙 그대로, "명시적 거부는 항상 명시적 허용보다 우선(An explicit deny overrides an explicit allow)"합니다. 다른 수많은 정책에서 허용(Allow)하고 있더라도, 요청과 일치하는 Deny 선언문이 단 하나라도 있다면 다른 모든 허용은 무시되고 요청이 즉시 차단됩니다.

오늘의 학습 범위 안내

실제 AWS 엔터프라이즈 환경에서는 리소스 기반 정책, 권한 경계(Permissions Boundary), 조직의 서비스 제어 정책(SCP), 임시 세션 정책 등도 권한 평가에 참여합니다. 이러한 심화 요소들은 다음 레슨들에서 이 세 가지 기본 규칙 위에 하나씩 얹어가며 차근차근 배울 예정입니다. 오늘은 먼저 가장 뼈대가 되는 위 세 가지 판정 흐름을 확실하게 마스터하세요.

실전 연습: 직접 판정해 보세요

모든 문제의 주인공은 AWS 계정 111122223333에 속한 IAM 사용자 alice입니다. 각 정책은 alice에게 직접 연결되어 있거나, alice가 속한 IAM 그룹에 연결되어 있습니다. 위로 스크롤하지 말고 방금 익힌 세 가지 규칙을 머릿속에 떠올리며 풀어보세요.

Q1. alice가 s3:GetObject API를 호출하여 acme-reports/q3.pdf 파일을 다운로드하려고 합니다.

{ "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

요청한 작업(Action)이 s3:GetObject로 정확히 일치하고, 대상 객체 경로인 acme-reports/q3.pdf도 acme-reports/* 와일드카드 패턴에 완벽하게 일치합니다. 정책에 다른 Deny 문장이 없으므로, 일치하는 명시적 Allow에 따라 요청이 정상 허용됩니다.

Q2. 위와 동일한 정책이 적용된 상태에서, alice가 s3:PutObject API로 acme-reports/q3.pdf 파일을 업로드(덮어쓰기)하려고 합니다.

{ "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

대상 리소스(Resource)는 맞지만, 요청한 작업(Action)이 s3:PutObject이므로 정책에 허용된 s3:GetObject와 일치하지 않습니다. 정책에 명시적으로 차단하는 Deny 문장이 있는 것은 아니지만, 이 작업을 허용한 문장도 없기 때문에 기본 규칙에 따라 암묵적 거부(Implicit Deny)가 적용됩니다.

Q3. alice가 s3:DeleteObject를 호출하여 파일을 삭제하려고 합니다. alice에게는 다음 두 가지 정책이 동시에 적용되어 있습니다.

// Developers 그룹에 연결된 정책
{ "Effect": "Allow", "Action": "s3:*", "Resource": "*" }

// alice 사용자에게 직접 연결된 정책
{ "Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "*" }

Developers 그룹 정책의 s3:*에 의해 작업이 허용되는 것처럼 보이지만, alice에게 직접 부여된 정책에 일치하는 Deny 선언문이 있습니다. "일치하는 명시적 Deny는 모든 Allow를 무조건 이긴다"는 절대 규칙에 따라 요청은 거부됩니다. 정책이 그룹에서 왔는지 사용자에게 직접 붙었는지는 우선순위에 아무런 영향을 주지 않습니다.

Q4. alice가 ec2:TerminateInstances API를 호출하여 EC2 인스턴스를 종료하려고 합니다.

{ "Effect": "Allow", "Action": "ec2:Describe*", "Resource": "*" }

ec2:Describe*는 DescribeInstances, DescribeVolumes처럼 '조회(Describe)'로 시작하는 작업에만 일치하는 전형적인 읽기 전용 패턴입니다. 인스턴스를 영구 종료하는 TerminateInstances 작업은 어디에서도 허용되지 않았으므로 기본 규칙인 암묵적 거부가 적용됩니다.

Q5. alice가 iam:ListAccessKeys API를 호출하여 액세스 키 목록을 조회하려고 합니다.

{ "Effect": "Allow", "Action": "iam:*AccessKey*", "Resource": "*" }

와일드카드 *는 Action 이름의 앞, 중간, 뒤 어디에나 올 수 있습니다. iam:ListAccessKeys는 List + AccessKey + s 구조이므로 *AccessKey* 패턴에 정확히 들어맞습니다. 따라서 일치하는 명시적 Allow가 적용되어 정상 허용됩니다.[4]

Q6. alice가 s3:GetObject로 민감한 경로의 acme-reports/secret/pay.csv를 읽으려고 합니다. 다음 두 정책이 함께 적용되어 있습니다.

{ "Effect": "Allow", "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

{ "Effect": "Deny", "Action": "s3:*",
  "Resource": "arn:aws:s3:::acme-reports/secret/*" }

두 Statement 모두 대상 리소스(acme-reports/secret/pay.csv)와 일치합니다. 이때 더 구체적인 경로나 Action을 가진 쪽이 우선하는 것이 아니라, 무조건 명시적 Deny가 우선합니다. 실무에서도 "버킷 전체는 안전하게 열어두되, 특정 민감한 하위 폴더만 확실하게 차단"하고자 할 때 바로 이 패턴을 사용합니다.

Q7. alice가 Users 테이블에 대해 dynamodb:GetItem API를 호출하여 데이터를 조회하려고 합니다.

{ "Effect": "Allow", "Action": "dynamodb:GetItem",
  "Resource": "arn:aws:dynamodb:ap-northeast-2:111122223333:table/Orders" }

요청한 작업(Action)은 맞지만 대상 리소스(Resource)가 일치하지 않습니다(Orders 테이블 ≠ Users 테이블). Statement가 일치하여 허용되려면 Action과 Resource 조건이 둘 다 만족해야 합니다. 따라서 허용 선언문이 적용되지 않아 암묵적 거부로 처리됩니다. 이렇게 필요한 리소스만 정밀하게 좁혀서 허용하는 방식이 바로 클라우드 보안의 핵심 원칙인 최소 권한 원칙(Principle of Least Privilege)의 실제 모습입니다.[6]

학습 내용 되짚어보기 (인출 연습)

화면을 위로 올려보지 말고, 방금 배운 세 가지 판정 규칙과 '명시적 거부'와 '암묵적 거부'의 결정적인 차이를 머릿속에서 정리해 직접 적어보세요.

세 가지 판정 규칙: ① 기본값은 거부 (암묵적 거부) ② 일치하는 Allow가 하나라도 있으면 허용 ③ 일치하는 Deny가 단 하나라도 있으면 다른 모든 허용을 무시하고 무조건 거부.

명시적 거부와 암묵적 거부의 차이:
명시적 거부(Explicit Deny)는 정책 안에 요청과 일치하는 "Effect": "Deny" 문장이 직접 명시되어 있을 때 발생합니다. 반면 암묵적 거부(Implicit Deny)는 Deny 문장은 없지만 해당 작업을 허용한 Allow 문장도 전혀 없을 때 기본값으로 적용되는 차단입니다.
실무에서 이 둘의 차이가 매우 중요한 이유는, 암묵적 거부는 허용(Allow) 정책을 하나 추가해주면 바로 해결되지만, 명시적 거부는 Allow 정책을 아무리 많이 추가해도 절대 풀리지 않기 때문입니다.
