IAM 정책을 읽는 세 가지 규칙

왜 이것부터인가

시험에서: 보안 도메인이 채점 문항의 30%로 가장 크고, 그 첫 태스크가 "AWS 리소스에 대한 보안 접근 설계"입니다.[1] 정책 JSON을 보여주고 "이 사용자는 무엇을 할 수 있는가"를 묻는 문제가 이 태스크에 해당합니다.

실무에서: AccessDenied 에러를 만나면 결국 같은 질문으로 돌아옵니다. 어떤 정책이 이 요청을 막았는가?

정책 한 장의 구조

사용자·그룹·역할에 붙는 자격 증명 기반 정책(identity-based policy)은 이렇게 생겼습니다.[2]

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::acme-reports/*"
    }
  ]
}
요소뜻
Version정책 언어 버전. 항상 2012-10-17을 씁니다. 2008-10-17은 옛 버전이라 새 정책에 쓰면 안 됩니다.[3]
EffectAllow 또는 Deny
Action어떤 API 호출인가. *(여러 글자)와 ?(한 글자) 와일드카드를 쓸 수 있습니다. 예: s3:*, iam:*AccessKey*[4]
Resource어떤 리소스(ARN)에 대한 호출인가

요청 하나가 Statement와 일치한다는 것은 그 Statement의 Action과 Resource가 둘 다 요청과 맞는다는 뜻입니다.

세 가지 규칙

한 계정 안에서 자격 증명 기반 정책만 있을 때, 판정은 이 세 규칙으로 끝납니다.[5]

  1. 기본값은 거부. 아무 정책도 허용하지 않으면 요청은 암묵적으로 거부됩니다. (루트 사용자만 예외)
  2. 일치하는 Allow가 있으면 허용. 사용자에게 직접 붙은 정책이든 그룹을 통해 받은 정책이든 상관없습니다.
  3. 일치하는 Deny는 무조건 이긴다. AWS 문서 표현 그대로 "An explicit deny overrides an explicit allow". Allow가 몇 개 있든 상관없습니다.

오늘의 범위

실제 평가에는 리소스 기반 정책, 권한 경계, SCP, 세션 정책도 끼어듭니다. 이것들은 다음 레슨에서 이 세 규칙 위에 하나씩 쌓아 올립니다. 오늘은 위 흐름만 확실하게 익히세요.

연습: 판정해 보세요

모든 문제의 주인공은 계정 111122223333의 IAM 사용자 alice입니다. 정책은 alice에게 직접 붙었거나 alice가 속한 그룹에 붙어 있습니다. 위로 스크롤하지 말고 기억으로 풀어 보세요.

Q1. alice가 s3:GetObject로 acme-reports/q3.pdf를 읽으려 합니다.

{ "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

Action이 같고, acme-reports/q3.pdf는 acme-reports/*에 맞습니다. Deny가 없으니 일치하는 Allow로 허용됩니다.

Q2. 같은 정책에서, alice가 s3:PutObject로 acme-reports/q3.pdf를 덮어쓰려 합니다.

{ "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

Resource는 맞지만 Action이 다릅니다. Deny 문장은 없으니 "명시적" 거부가 아닙니다. 아무것도 허용하지 않았기 때문에 기본값인 암묵적 거부입니다.

Q3. alice가 s3:DeleteObject를 호출합니다. 정책이 두 개 있습니다.

// Developers 그룹 정책
{ "Effect": "Allow", "Action": "s3:*", "Resource": "*" }

// alice에게 직접 붙은 정책
{ "Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "*" }

그룹의 s3:* Allow도 일치하지만, 일치하는 Deny가 있으면 Deny가 이깁니다. 정책이 그룹에서 왔는지 사용자에게 직접 붙었는지는 판정에 영향이 없습니다.

Q4. alice가 ec2:TerminateInstances로 인스턴스를 종료하려 합니다.

{ "Effect": "Allow", "Action": "ec2:Describe*", "Resource": "*" }

ec2:Describe*는 DescribeInstances, DescribeVolumes처럼 Describe로 시작하는 Action에만 맞습니다. 흔히 쓰는 "읽기 전용" 패턴입니다. Terminate는 어디에도 허용되지 않았으니 암묵적 거부입니다.

Q5. alice가 iam:ListAccessKeys를 호출합니다.

{ "Effect": "Allow", "Action": "iam:*AccessKey*", "Resource": "*" }

*는 Action 이름의 앞·중간·뒤 어디에나 올 수 있습니다. List + AccessKey + s이므로 *AccessKey*에 맞습니다. 이 예시는 AWS 공식 문서에 나오는 패턴입니다.[4]

Q6. alice가 s3:GetObject로 acme-reports/secret/pay.csv를 읽으려 합니다.

{ "Effect": "Allow", "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::acme-reports/*" }

{ "Effect": "Deny", "Action": "s3:*",
  "Resource": "arn:aws:s3:::acme-reports/secret/*" }

두 문장 모두 일치합니다. 더 "구체적인" 쪽이 이기는 것이 아니라 Deny가 이깁니다. 실무에서 "버킷 전체는 열되 민감한 접두사만 막는다"를 이렇게 구현합니다.

Q7. alice가 Users 테이블에 dynamodb:GetItem을 호출합니다.

{ "Effect": "Allow", "Action": "dynamodb:GetItem",
  "Resource": "arn:aws:dynamodb:ap-northeast-2:111122223333:table/Orders" }

이번엔 Action은 맞고 Resource가 다릅니다(Orders ≠ Users). Statement가 일치하려면 Action과 Resource가 둘 다 맞아야 합니다. 그래서 암묵적 거부입니다. 이렇게 리소스를 좁히는 것이 최소 권한의 실제 모습입니다.[6]

기억에서 꺼내기

화면을 보지 말고, 판정의 세 가지 규칙과 "명시적 거부"와 "암묵적 거부"의 차이를 직접 써 보세요.

① 기본값은 거부 ② 일치하는 Allow가 있으면 허용 ③ 일치하는 Deny는 항상 이긴다.

명시적 거부는 일치하는 "Effect": "Deny" 문장이 있을 때입니다. 암묵적 거부는 Deny 문장은 없지만 허용한 문장도 없을 때입니다. 실무에서 이 차이가 중요한 이유는, 암묵적 거부는 Allow를 추가하면 풀리지만 명시적 거부는 Allow를 아무리 추가해도 풀리지 않기 때문입니다.
