프라이빗 서브넷에서 밖으로:
NAT 게이트웨이, VPC 엔드포인트, PrivateLink

프라이빗 서브넷의 인스턴스가 바깥에 나가는 길은 세 가지입니다. 인터넷 전체로 나가는 NAT, S3·DynamoDB로 가는 무료 지름길인 게이트웨이 엔드포인트, 그 밖의 서비스로 가는 사설 통로인 인터페이스 엔드포인트. 시험은 "가용성"과 "비용"으로 이 셋을 고르게 합니다.

⏱ 약 20분🎯 오늘의 승리: 시나리오 8문항📌 VPC 치트시트

왜 이것인가

시험에서: "프라이빗 인스턴스가 S3에 대량으로 쓰는데 NAT 비용이 크다 → 가장 비용 효율적인 방법은?"은 대표적인 비용 최적화 문제입니다.
실무에서: NAT 게이트웨이는 시간당 요금과 처리량(GB) 요금이 함께 붙어 청구서에서 눈에 띄는 항목이 되곤 합니다. 엔드포인트로 줄일 수 있는 몫을 아는 것이 곧 비용 절감입니다.

NAT 게이트웨이

NAT 게이트웨이는 프라이빗 서브넷의 인스턴스가 VPC 밖 서비스에 연결을 시작할 수 있게 하되, 외부에서 그 인스턴스로 연결을 시작하지는 못하게 하는 관리형 NAT 서비스입니다.[1]

  • 퍼블릭 NAT 게이트웨이(기본값): 퍼블릭 서브넷에 만들고 생성 시 탄력적 IP를 연결합니다. 프라이빗 서브넷의 라우팅 테이블에 0.0.0.0/0 → NAT 게이트웨이를 넣고, NAT 게이트웨이가 있는 퍼블릭 서브넷은 IGW로 라우팅합니다.[1]
  • 프라이빗 NAT 게이트웨이: 다른 VPC나 온프레미스로만 나갈 때 사용. 탄력적 IP를 연결할 수 없습니다.[1]
  • 대역폭은 5 Gbps에서 시작해 100 Gbps까지 자동 확장됩니다. 보안 그룹은 연결할 수 없고, NAT 게이트웨이가 있는 서브넷의 NACL로 제어합니다.[2]
  • 요금: NAT 게이트웨이가 존재하는 시간과 처리한 데이터(GB)에 대해 청구됩니다.[3]

AZ마다 하나 vs 하나를 공유

NAT 게이트웨이는 특정 AZ에 만들어지고 그 AZ 안에서만 이중화됩니다. 여러 AZ의 리소스가 NAT 게이트웨이 하나를 공유하는데 그 AZ가 다운되면, 다른 AZ의 리소스도 인터넷 접근을 잃습니다. 복원력을 높이려면 AZ마다 NAT 게이트웨이를 만들고, 각 AZ의 프라이빗 서브넷이 같은 AZ의 NAT 게이트웨이를 쓰도록 라우팅합니다.[2]

AWS의 비용 절감 안내도 같은 방향입니다. AZ를 넘는 트래픽이 많으면 리소스를 NAT 게이트웨이와 같은 AZ에 두거나 AZ마다 NAT 게이트웨이를 만들고, NAT를 지나는 트래픽 대부분이 AWS 서비스로 간다면 엔드포인트를 만들라고 권합니다.[3]

참고: 최근 AWS는 AZ 단위(zonal)가 아닌 리전 NAT 게이트웨이도 제공합니다. 워크로드가 있는 AZ로 자동 확장되고 퍼블릭 서브넷이 필요 없지만, 프라이빗 NAT는 지원하지 않습니다.[4] 시험 문제는 대부분 고전적인 "AZ마다 하나" 패턴으로 출제되니, 그 논리를 먼저 확실히 하세요.

NAT 인스턴스는 자신이 출발지·목적지가 아닌 트래픽도 주고받아야 하므로 소스/대상 확인(source/destination check)을 꺼야 합니다.[6] AWS는 NAT 게이트웨이를 권장하며, 기존 NAT AMI는 지원이 끝난 Amazon Linux AMI 기반이라 마이그레이션을 권합니다.[7]

VPC 엔드포인트: 인터넷을 거치지 않고 AWS 서비스로

게이트웨이 엔드포인트 (S3, DynamoDB 전용)

  • IGW나 NAT 장치 없이 Amazon S3와 DynamoDB에 연결합니다. PrivateLink를 쓰지 않으며, 추가 요금이 없습니다.[8]
  • 만들 때 고른 라우팅 테이블에 "대상 = 서비스의 접두사 목록, 타깃 = 게이트웨이 엔드포인트" 라우트가 자동으로 추가됩니다. 가장 긴 접두사 일치 덕분에 0.0.0.0/0 라우트보다 우선합니다.[8]
  • 접두사 목록은 리전별이므로 다른 리전의 S3로 가는 트래픽은 엔드포인트를 타지 않습니다. 또 온프레미스에서는 쓸 수 없습니다.[8][9]

인터페이스 엔드포인트 (PrivateLink)

  • 지정한 서브넷마다 엔드포인트 네트워크 인터페이스(ENI)가 생기고, 서브넷의 사설 IP를 받습니다. 서비스로 가는 트래픽은 DNS로 이 사설 IP에 해석됩니다.[10]
  • 프라이빗 DNS를 켜면 기존 앱이 서비스의 공개 엔드포인트 이름을 그대로 써도 엔드포인트로 갑니다. AWS는 이를 켜라고 권합니다.[10]
  • 고가용성을 위해 최소 두 AZ에 구성하라고 권합니다.[10]
  • 요금: AZ별 프로비저닝 시간과 처리 데이터(GB)에 청구됩니다.[10]

출처: S3 사용 설명서의 엔드포인트 유형 비교[9]. 둘은 같은 VPC에 함께 둘 수 있습니다. VPC 안의 트래픽은 무료인 게이트웨이 엔드포인트로, 온프레미스 트래픽만 인터페이스 엔드포인트로 보내는 구성이 문서에 나옵니다.

PrivateLink로 내 서비스를 공개하기

PrivateLink는 AWS 서비스 전용이 아닙니다. 서비스 제공자가 로드 밸런서를 지정해 엔드포인트 서비스를 만들고 특정 주체에 권한을 주면, 서비스 소비자는 자기 VPC에 인터페이스 엔드포인트를 만들어 연결합니다. 연결은 소비자가 시작하고, 트래픽은 공용 인터넷을 지나지 않습니다.[11] VPC 전체를 이어 붙이는 피어링과 달리 특정 서비스 하나만 노출한다는 점이 핵심입니다.

시험 단골

"프라이빗 인스턴스가 인터넷으로 패치를 받되, 외부에서 접속 불가" → 퍼블릭 서브넷의 NAT 게이트웨이.
"NAT 고가용성" → AZ마다 NAT 게이트웨이 + AZ별 라우팅 테이블.
"프라이빗 서브넷 → S3/DynamoDB, 가장 비용 효율적" → 게이트웨이 엔드포인트(무료).
"온프레미스에서 VPN/DX로 S3에 사설 접근" → 인터페이스 엔드포인트.
"다른 계정 고객에게 내 서비스만 사설로 제공" → PrivateLink 엔드포인트 서비스.
"최소 운영 오버헤드" → NAT 인스턴스보다 NAT 게이트웨이.

연습

Q1. (시험형) 프라이빗 서브넷의 EC2 인스턴스가 인터넷에서 OS 패치를 내려받아야 합니다. 인터넷에서 이 인스턴스로 연결을 시작할 수는 없어야 합니다. 무엇을 해야 하는가?

퍼블릭 NAT 게이트웨이는 퍼블릭 서브넷에 만들고, 프라이빗 서브넷의 0.0.0.0/0을 NAT로 보냅니다.[1] NAT가 프라이빗 서브넷에 있으면 NAT 자신이 IGW로 나갈 길이 없습니다. 탄력적 IP + IGW 라우트는 인스턴스를 퍼블릭으로 만들어 요구 사항에 어긋나고, 게이트웨이 엔드포인트는 S3·DynamoDB에만 갑니다.

Q2. (시험형) 앱 서버가 AZ 세 곳의 프라이빗 서브넷에 있고, 모두 AZ-a의 NAT 게이트웨이 하나로 인터넷에 나갑니다. AZ-a 장애 때 다른 AZ의 서버도 외부 API를 호출하지 못했습니다. 재발을 막는 방법은?

NAT 게이트웨이는 한 AZ 안에서만 이중화됩니다. AZ 독립적인 구조를 만들려면 AZ마다 하나씩 두고, 각 AZ의 라우팅 테이블이 같은 AZ의 NAT를 가리키게 합니다.[2] 같은 AZ에 하나를 더 두면 그 AZ가 죽을 때 둘 다 죽습니다. NAT 게이트웨이에는 인스턴스 유형 개념이 없습니다.

Q3. (시험형) 프라이빗 서브넷의 배치 작업이 매일 수 TB를 같은 리전의 S3 버킷에 씁니다. 현재 트래픽은 NAT 게이트웨이를 지나며 데이터 처리 요금이 큽니다. 가장 비용 효율적인 개선은?

같은 리전의 S3로 가는 트래픽에는 추가 요금이 없는 게이트웨이 엔드포인트가 정답입니다.[8] 인터페이스 엔드포인트도 NAT를 피하지만 시간당·GB당 요금이 붙습니다. NAT를 늘리면 비용이 오히려 늘고, 퍼블릭 서브넷 이동은 보안을 희생합니다.

Q4. (시험형) 온프레미스 데이터 센터가 Direct Connect로 VPC에 연결되어 있습니다. 온프레미스 서버가 인터넷을 거치지 않고 사설 IP로 S3에 접근해야 합니다. 무엇을 쓰는가?

게이트웨이 엔드포인트는 온프레미스에서 접근할 수 없고, 인터페이스 엔드포인트는 VPN·Direct Connect를 통해 온프레미스에서 접근할 수 있습니다.[9] "온프레미스 + S3 사설 접근"은 인터페이스 엔드포인트의 대표 키워드입니다.

Q5. NAT 인스턴스를 직접 구성할 때 반드시 해야 하는 일은?

EC2는 기본적으로 자신이 출발지나 목적지인 트래픽만 처리합니다. 남의 트래픽을 중계하는 NAT 인스턴스는 이 확인을 꺼야 합니다.[6] NAT 인스턴스는 퍼블릭 서브넷에 두고 퍼블릭 IP가 있어야 하며, 보안 그룹을 붙일 수 있고, 패치는 직접 해야 합니다.[5]

Q6. 게이트웨이 엔드포인트에 대한 설명으로 옳은 것을 두 개 고르세요.

게이트웨이 엔드포인트는 S3·DynamoDB 전용이고, 라우팅 테이블에 접두사 목록 → 엔드포인트 라우트로 동작합니다.[8] ENI와 사설 IP, 온프레미스 접근은 인터페이스 엔드포인트의 특징입니다.

Q7. (시험형) SaaS 회사가 자사 VPC의 API 서비스를 수백 개 고객 계정의 VPC에 사설로 제공하려 합니다. 고객 VPC의 CIDR이 서로, 그리고 자사 VPC와 겹치는 경우가 많고, 고객에게 자사 VPC의 다른 리소스는 노출하면 안 됩니다. 가장 적절한 것은?

PrivateLink는 특정 서비스만 노출하고, 소비자는 자기 VPC 안의 엔드포인트 사설 IP로 접근합니다.[11] 피어링은 VPC 전체를 라우팅으로 잇는 방식이라 서비스 하나만 노출하는 데 맞지 않고, 피어 VPC와 겹치는 CIDR은 쓸 수 없습니다(0007).[12]

Q8. (0005 복습) 운영자가 NAT 게이트웨이를 지나는 트래픽을 제한하려고 NAT 게이트웨이에 보안 그룹을 붙이려 했지만 할 수 없었습니다. 대신 쓸 수 있는 방법은?

NAT 게이트웨이에는 보안 그룹을 연결할 수 없습니다. 뒤쪽 리소스의 보안 그룹으로 인바운드·아웃바운드를 제어하고, NAT 게이트웨이가 있는 서브넷의 NACL로 서브넷 경계에서 거릅니다.[5] 라우팅 테이블에는 "거부" 라우트가 없고, IAM 정책은 패킷을 거르지 않습니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) NAT 게이트웨이를 고가용성으로 만드는 배치와 그 이유. (2) 게이트웨이 엔드포인트와 인터페이스 엔드포인트를 대상 서비스, 동작 방식, 온프레미스 접근, 요금으로 비교.

(1) NAT 게이트웨이는 AZ 하나에 만들어지고 그 AZ 안에서만 이중화되므로, AZ마다 하나씩 퍼블릭 서브넷에 두고 각 AZ의 프라이빗 라우팅 테이블이 같은 AZ의 NAT를 가리키게 한다. AZ 간 데이터 전송 비용도 줄어든다.

(2) 게이트웨이: S3·DynamoDB 전용, 라우팅 테이블의 접두사 목록 라우트, 온프레미스 불가, 무료. 인터페이스: 다수 AWS 서비스와 PrivateLink 서비스, 서브넷의 ENI·사설 IP와 DNS, 온프레미스 가능, AZ별 시간당 + GB당 요금.
