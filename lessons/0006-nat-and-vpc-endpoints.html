프라이빗 서브넷에서 밖으로:
NAT 게이트웨이, VPC 엔드포인트, PrivateLink

프라이빗 서브넷에 격리된 인스턴스가 안전하게 외부 서비스와 통신할 수 있는 길은 크게 세 가지입니다. 공용 인터넷 전체로 나가는 안전한 단방향 출구인 NAT 게이트웨이, S3와 DynamoDB로 향하는 추가 비용 제로의 고속 지름길인 게이트웨이 엔드포인트, 그리고 다양한 AWS 서비스 및 내부 비즈니스 서비스로 통하는 사설 통로인 인터페이스 엔드포인트(PrivateLink)입니다. 시험과 실무에서는 언제나 "고가용성"과 "비용 최적화"라는 두 가지 핵심 잣대로 최적의 통로를 선택하게 만듭니다.

왜 NAT와 VPC 엔드포인트를 깊이 있게 배워야 할까요?

시험 관점에서: AWS Certified Solutions Architect - Associate (SAA-C03) 시험의 비용 최적화(도메인 4) 및 고성능 네트워킹(도메인 3) 영역에서 가장 빈번하게 출제되는 시나리오가 바로 "프라이빗 서브넷의 인스턴스가 매일 대량의 데이터를 S3에 업로드하는데 NAT 게이트웨이 비용이 너무 많이 나온다. 가장 비용 효율적인 해결책은?"(정답: S3 게이트웨이 엔드포인트)입니다.[8] 또한 "온프레미스 본사에서 전용선(Direct Connect)을 통해 사설 IP로 S3에 안전하게 접근하는 방법은?"(정답: S3 인터페이스 엔드포인트)처럼 엔드포인트 종류와 물리적 차이를 묻는 문제가 단골로 출제됩니다.

실무 관점에서: 실제 운영 환경에서 NAT 게이트웨이는 인스턴스 시간당 유지 요금뿐만 아니라 통과하는 기가바이트(GB)당 데이터 처리 요금이 함께 청구되어, 월말 클라우드 비용 청구서에서 가장 큰 비중을 차지하는 비용 주범 중 하나가 되곤 합니다.[3] S3나 DynamoDB, SQS 등 AWS 내부 서비스로 향하는 트래픽을 무료 또는 최적화된 VPC 엔드포인트로 우회시켜 NAT 처리 비용을 수백~수천 달러씩 절감하는 것은 클라우드 아키텍트의 필수 실무 역량입니다.

NAT 게이트웨이: 프라이빗 인스턴스의 안전한 외출 통로

NAT 게이트웨이 (Network Address Translation Gateway)는 프라이빗 서브넷의 인스턴스가 외부 인터넷 서비스(예: OS 보안 패치 다운로드, 외부 결제 API 호출 등)로 **먼저 연결을 시작(아웃바운드)**할 수는 있게 하되, 외부 인터넷의 해커가 해당 인스턴스로 **먼저 연결을 시작(인바운드)하는 것은 원천 차단**해 주는 완전 관리형 서비스입니다.[1]

퍼블릭 NAT 게이트웨이의 핵심 원리 (기본값)

  • 반드시 퍼블릭 서브넷에 생성: NAT 게이트웨이 자체는 인터넷과 직접 통신해야 하므로, 인터넷 게이트웨이(IGW)로의 라우트가 존재하는 퍼블릭 서브넷에 배치해야 합니다.[1]
  • 탄력적 IP (Elastic IP) 필수 연결: 생성 시 고정 공인 IPv4 주소인 탄력적 IP를 반드시 연결해야 합니다. 외부 인터넷 서버의 관점에서는 모든 프라이빗 인스턴스의 요청이 이 탄력적 IP 하나에서 출발한 것으로 보이게 됩니다.
  • 라우팅 구성: 프라이빗 서브넷의 라우팅 테이블에는 0.0.0.0/0(모든 외부 트래픽)의 타깃을 이 NAT 게이트웨이로 등록합니다. (만약 NAT 게이트웨이를 프라이빗 서브넷에 잘못 만들면, NAT 게이트웨이 자신도 인터넷으로 나갈 길이 없어 트래픽이 완전히 고립됩니다!)
  • 프라이빗 NAT 게이트웨이: 인터넷이 아닌 다른 사설 VPC나 온프레미스 네트워크로만 패킷을 보낼 때 사용하며, 탄력적 IP를 연결할 수 없습니다.[1]
  • 대역폭 자동 확장: 5 Gbps에서 시작하여 트래픽 부하에 따라 최대 100 Gbps까지 AWS가 내부적으로 자동 확장(Auto-scaling)해 줍니다.[2]
  • 보안 그룹 연결 불가: NAT 게이트웨이 자체에는 보안 그룹을 연결할 수 없습니다. 트래픽 제어가 필요하다면 뒤편 인스턴스의 보안 그룹을 조절하거나, NAT 게이트웨이가 위치한 서브넷의 네트워크 ACL(NACL)을 활용해야 합니다.[2]
  • 요금 체계: 프로비저닝된 시간당 요금과 통과한 데이터 처리량(GB당 요금)이 합산 청구됩니다.[3]

가용 영역(AZ)마다 하나 vs 단일 NAT 게이트웨이 공유: 고가용성과 비용의 딜레마

NAT 게이트웨이는 특정 가용 영역(AZ)에 생성되며, **해당 AZ 내부에서만 고가용성으로 이중화**됩니다. 즉, 다른 가용 영역의 물리적 장애까지 대신 막아주지는 못합니다.[2]

만약 인프라 비용을 아끼기 위해 3개 AZ의 프라이빗 서브넷들이 AZ-a에 있는 단 하나의 NAT 게이트웨이를 공유하도록 설정했다고 가정해 보겠습니다. 이 상황에서 만약 AZ-a에 정전이나 지진 같은 장애가 발생하면, 멀쩡히 살아 있는 AZ-b와 AZ-c의 인스턴스들까지 외부 인터넷 접속이 일제히 끊어지는 단일 장애 지점(SPOF)이 발생합니다.

따라서 진정한 고가용성(High Availability) 아키텍처를 구현하려면: **각 AZ의 퍼블릭 서브넷마다 NAT 게이트웨이를 하나씩 생성하고, 각 AZ의 프라이빗 서브넷 라우팅 테이블이 '같은 AZ에 위치한 NAT 게이트웨이'를 가리키도록 독립적으로 라우팅**해야 합니다.[2]

비교 항목AZ마다 NAT 게이트웨이 배치 (권장 모범 사례)단일 NAT 게이트웨이 공유 (비용 절약형)
단일 AZ 장애 시 영향해당 AZ만 영향, 나머지 AZ의 인터넷 통신은 완벽히 정상 유지NAT가 있는 AZ 다운 시 전체 AZ의 인스턴스가 인터넷 통신 두절
시간당 인프라 비용AZ 개수만큼 배수 발생 (예: 3개 AZ = 3대분 요금)단 1대분 요금만 발생 (비용 최소화)
가용 영역 간 데이터 전송 요금동일 AZ 내부 통신이므로 AZ 간 데이터 전송료(Cross-AZ) 없음다른 AZ의 트래픽이 경계를 넘어가므로 추가 데이터 전송료 발생
시험 및 실무 선택 기준"고가용성 확보", "단일 AZ 장애 격리", "엔터프라이즈 프로덕션""개발/테스트 환경", "비용 최소화가 최우선", "가용성 요건 낮음"

참고: AWS에서는 최근 특정 AZ에 종속되지 않고 트래픽이 있는 AZ로 자동 확장되는 리전 NAT 게이트웨이 (Regional NAT Gateway)도 출시했습니다.[4] 다만 자격 시험에서는 전통적인 "AZ 독립적 고가용성 배치" 패턴이 핵심 문제로 출제되므로, 이 논리를 반드시 먼저 완벽하게 마스터해 두어야 합니다.

관리형 NAT 게이트웨이 vs 구형 NAT 인스턴스 비교

비교 속성관리형 NAT 게이트웨이 (AWS 권장)직접 구축하는 NAT 인스턴스 (EC2)

출처: Amazon VPC 사용 설명서의 NAT 게이트웨이와 NAT 인스턴스 비교표[5]

NAT 인스턴스 구성 시 필수 시험 포인트: 일반 EC2 인스턴스는 기본적으로 자신이 출발지이거나 목적지가 아닌 패킷은 보안상 폐기합니다. 하지만 다른 인스턴스의 트래픽을 중계해 주는 NAT 인스턴스로 동작하려면, 인스턴스의 소스/대상 확인(Source/Destination Check) 기능을 반드시 비활성화(Disable)해야만 합니다.[6] 현재 AWS는 구형 NAT AMI의 보안 지원이 종료되었으므로 신규 시스템에는 관리형 NAT 게이트웨이 사용을 강력히 권고합니다.[7]

VPC 엔드포인트: 인터넷을 거치지 않고 AWS 서비스로 직통 연결

프라이빗 서브넷의 인스턴스가 S3 버킷에 데이터를 저장하거나 DynamoDB 테이블을 조회할 때, 굳이 비싼 비용을 내면서 NAT 게이트웨이와 공용 인터넷을 거쳐갈 필요가 있을까요? VPC 엔드포인트(VPC Endpoint)를 생성하면 모든 트래픽이 공용 인터넷으로 전혀 빠져나가지 않고, AWS의 안전하고 초고속인 내부 프라이빗 글로벌 백본 네트워크를 통해 직접 연결됩니다.[8]

게이트웨이 엔드포인트 (Gateway Endpoint: S3와 DynamoDB 전용)

  • 대상 서비스: 오직 **Amazon S3**와 **Amazon DynamoDB** 단 두 가지 서비스에만 사용할 수 있습니다.[8]
  • 비용: PrivateLink 기술을 사용하지 않으며, 추가 요금이 전혀 없는 완전 무료(Free) 서비스입니다.[8]
  • 동작 원리: 생성 시 지정한 프라이빗 서브넷의 라우팅 테이블에 "대상 = AWS 서비스 접두사 목록 (Prefix List, 예: pl-xxxx), 타깃 = 게이트웨이 엔드포인트 ID" 형태의 라우트가 자동으로 추가됩니다. 가장 긴 접두사 일치 원칙 덕분에 전체 인터넷 기본 라우트(0.0.0.0/0)보다 항상 우선하여 엔드포인트로 직통 연결됩니다.[8]
  • 물리적 한계 (시험 단골 함정!): 접두사 목록은 리전 단위로 동작하므로 다른 리전의 S3 버킷으로 가는 트래픽은 이 엔드포인트를 타지 못합니다. 또한 온프레미스 본사 네트워크에서는 VPN이나 Direct Connect를 타고 이 게이트웨이 엔드포인트로 접근할 수 없습니다.[8][9]

인터페이스 엔드포인트 (Interface Endpoint: PrivateLink 기반)

  • 동작 원리: 지정한 각 서브넷마다 **탄력적 네트워크 인터페이스(ENI)**가 생성되고, 해당 서브넷 IP 대역의 **사설 IP(Private IP)**를 부여받습니다. 외부 서비스로 향하는 트래픽은 DNS를 통해 이 사설 IP로 변환되어 전달됩니다.[10]
  • 폭넓은 지원: CloudWatch, SQS, SNS, KMS, Secrets Manager, 그리고 S3를 포함한 거의 모든 AWS 서비스와 타사 SaaS 서비스를 지원합니다.
  • 프라이빗 DNS (Private DNS): 이 기능을 활성화하면 기존 애플리케이션 코드를 수정하지 않고 표준 퍼블릭 엔드포인트 주소(예: sqs.ap-northeast-2.amazonaws.com)를 그대로 호출해도, 자동으로 엔드포인트의 사설 IP로 연결됩니다. AWS는 이를 켤 것을 강력히 권장합니다.[10]
  • 고가용성 권장: 가용 영역 장애에 대비하기 위해 **최소 2개 이상의 가용 영역(AZ)**에 엔드포인트 ENI를 배치해야 합니다.[10]
  • 요금 체계: ENI가 프로비저닝된 AZ별 시간당 요금과 통과하는 데이터 처리량(GB당 요금)이 청구됩니다.[10]
S3 연결 기준 비교게이트웨이 엔드포인트인터페이스 엔드포인트 (PrivateLink)
사용하는 통신 IPS3 퍼블릭 IP (라우팅 테이블로 AWS 내부 직통)서브넷의 **사설 IP (ENI)**
온프레미스 (VPN · DX)에서 직접 접근불가능 (직접 접근 불가)가능 (사설 IP이므로 전용선 타고 접근 가능)
다른 리전 VPC에서 접근 (피어링 · TGW)불가능가능
엔드포인트 자체 요금완전 무료 (0원)시간당 요금 + GB당 처리 요금 발생

출처: Amazon S3 사용 설명서의 엔드포인트 유형 비교표[9]. 실무에서는 두 엔드포인트를 같은 VPC에 함께 구성할 수 있습니다. VPC 내부 인스턴스의 트래픽은 무료인 게이트웨이 엔드포인트로 보내고, 온프레미스 데이터 센터에서 오는 트래픽만 인터페이스 엔드포인트로 유도하는 것이 비용 최적화의 정석입니다.

PrivateLink로 내 비즈니스 서비스 사설 공개하기

AWS PrivateLink는 단순히 AWS 관리형 서비스를 호출하는 데만 쓰이지 않습니다. 내 VPC에 구축한 API 서비스를 다른 AWS 계정(파트너사나 고객사)에 안전하게 제공할 때도 핵심적인 역할을 합니다.[11]

서비스 제공자(Provider)는 Network Load Balancer(NLB) 뒤에 백엔드 서버를 두고 **엔드포인트 서비스(Endpoint Service)**를 생성한 뒤, 특정 AWS 계정에 접근 권한을 부여합니다. 서비스 소비자(Consumer)는 자기 VPC 안에 **인터페이스 엔드포인트**를 만들어 연결합니다. 통신 연결은 오직 소비자가 시작하며, 모든 트래픽은 공용 인터넷을 1%도 거치지 않습니다.[11]

VPC 피어링과의 결정적 차이

VPC 피어링은 두 VPC의 모든 리소스가 양방향으로 연결되지만, PrivateLink는 오직 지정된 단 하나의 특정 서비스(포트)만 안전하게 노출합니다. 또한 두 VPC의 CIDR 대역이 서로 겹치더라도(Overlapping CIDR) 아무런 문제 없이 통신할 수 있다는 것이 엄청난 장점입니다.

시험에 자주 나오는 핵심 패턴

"프라이빗 인스턴스가 인터넷으로 패치를 받아야 하지만, 외부에서 접속은 불가" → 퍼블릭 서브넷의 NAT 게이트웨이.
"NAT 게이트웨이 고가용성 및 단일 AZ 장애 격리" → 가용 영역마다 NAT 게이트웨이를 하나씩 두고 각 AZ별 라우팅 테이블 연결.
"프라이빗 서브넷에서 S3/DynamoDB 접속 시 가장 비용 효율적인 방법" → 게이트웨이 엔드포인트 (추가 요금 없는 완전 무료).
"온프레미스 본사에서 VPN/DX를 타고 사설 IP로 S3에 접근" → S3 인터페이스 엔드포인트.
"수백 개 고객사 VPC에 내 서비스만 안전하게 사설 제공 (IP 중복 가능)" → AWS PrivateLink (엔드포인트 서비스).
"최소한의 운영 오버헤드로 NAT 구성" → 관리형 NAT 게이트웨이 (NAT 인스턴스 지양).

실전 연습: 시나리오 퀴즈로 확인하기

NAT 게이트웨이와 VPC 엔드포인트의 실전 시험 8문항입니다. 고가용성과 비용 최적화 원칙을 떠올리며 풀어보세요.

Q1. (시험형) 프라이빗 서브넷에 위치한 EC2 인스턴스들이 인터넷에서 최신 OS 보안 패치를 주기적으로 다운로드해야 합니다. 반면 외부 공용 인터넷에서 이 인스턴스들로 먼저 인바운드 연결을 시작하는 것은 보안상 절대 불가능해야 합니다. 가장 적절한 네트워크 구성은 무엇일까요?

퍼블릭 NAT 게이트웨이는 반드시 퍼블릭 서브넷에 생성해야 하며, 탄력적 IP(EIP)를 할당받아야 인터넷과 통신할 수 있습니다.[1] 그런 다음 프라이빗 서브넷 라우팅 테이블의 0.0.0.0/0을 이 NAT 게이트웨이로 보내야 합니다. NAT 게이트웨이를 프라이빗 서브넷에 만들면 NAT 자신도 인터넷으로 나갈 수 없습니다. 탄력적 IP 직접 할당은 인스턴스를 외부에 노출하므로 보안 요건에 위배되며, 게이트웨이 엔드포인트는 S3/DynamoDB 전용이므로 일반 인터넷 패치를 받을 수 없습니다.

Q2. (시험형) 한 회사의 애플리케이션 서버들이 3개 가용 영역(AZ-a, AZ-b, AZ-c)의 프라이빗 서브넷에 분산 배치되어 있으며, 인터넷 통신을 위해 AZ-a의 퍼블릭 서브넷에 위치한 단 하나의 NAT 게이트웨이를 함께 공유하고 있습니다. 어느 날 AZ-a 전체에 데이터 센터 정전 장애가 발생하자, AZ-b와 AZ-c에 있던 정상 서버들까지 외부 결제 API를 호출하지 못해 서비스가 마비되었습니다. 이러한 단일 장애 지점(SPOF)을 해결하고 고가용성을 확보하는 올바른 아키텍처는 무엇일까요?

NAT 게이트웨이는 단일 가용 영역 안에서만 이중화됩니다. 진정한 AZ 독립적 고가용성을 구현하려면 가용 영역마다 NAT 게이트웨이를 각각 하나씩 생성하고, 각 AZ의 프라이빗 서브넷 라우팅 테이블이 같은 AZ에 있는 NAT 게이트웨이를 가리키도록 구성해야 합니다.[2] 동일한 AZ(AZ-a)에 아무리 장치를 추가하거나 사양을 올려도, 그 AZ 자체가 죽으면 함께 중단됩니다. NAT 게이트웨이는 완전 관리형이므로 인스턴스 유형 변경 개념도 없습니다.

Q3. (시험형) 프라이빗 서브넷에 위치한 데이터 분석 배치 서버들이 매일 수십 테라바이트(TB)의 대용량 로그 파일을 동일 리전의 Amazon S3 버킷에 업로드하고 있습니다. 현재 이 트래픽은 모두 NAT 게이트웨이를 통과하고 있어 매월 막대한 데이터 처리(GB) 비용이 발생하고 있습니다. 보안을 유지하면서 가장 비용 효율적으로 문제를 해결하는 방법은 무엇일까요?

동일 리전의 Amazon S3로 향하는 트래픽에는 **추가 요금이 전혀 없는 완전 무료(Free)인 게이트웨이 엔드포인트(Gateway Endpoint)**가 가장 비용 효율적인 정답입니다.[8] 인터페이스 엔드포인트도 NAT를 우회할 수는 있지만 AZ별 시간당 요금과 GB당 데이터 처리 요금이 발생하므로 최저 비용이 아닙니다. NAT 게이트웨이를 늘리면 시간당 비용이 오히려 증가하며, 서버를 퍼블릭 서브넷으로 옮기는 것은 보안 원칙을 훼손합니다.

Q4. (시험형) 온프레미스 본사 데이터 센터가 AWS Direct Connect 전용선을 통해 회사의 VPC와 연결되어 있습니다. 온프레미스 내부 서버들이 공용 인터넷을 전혀 거치지 않고 오직 사설 IP(Private IP)만을 사용하여 AWS S3 버킷에 안전하게 접근해야 합니다. 어떤 구성 요소를 사용해야 할까요?

게이트웨이 엔드포인트는 온프레미스 환경(VPN, Direct Connect)에서 직접 접근할 수 없습니다. 반면 **인터페이스 엔드포인트 (AWS PrivateLink)**는 서브넷 대역의 사설 IP(ENI)를 할당받으므로, 온프레미스 서버에서 Direct Connect나 VPN 전용선을 타고 사설 IP로 S3에 직접 접근할 수 있습니다.[9] 시험에서 "온프레미스 + 사설 IP로 S3 접근"이 나오면 항상 인터페이스 엔드포인트가 정답입니다.

Q5. EC2 인스턴스를 활용하여 NAT 인스턴스를 직접 구축할 때, 다른 인스턴스들의 아웃바운드 패킷을 정상적으로 중계하기 위해 반드시 구성해야 하는 필수 작업은 무엇일까요?

EC2 인스턴스는 기본적으로 자신이 출발지이거나 최종 목적지가 아닌 트래픽을 보안상 차단합니다. 다른 인스턴스의 트래픽을 대신 받아 인터넷으로 라우팅해 주는 NAT 인스턴스는 이 보호 장치인 소스/대상 확인(Source/Destination Check) 기능을 반드시 비활성화(Disable)해야만 중계 패킷을 처리할 수 있습니다.[6] NAT 인스턴스는 퍼블릭 서브넷에 위치해야 하며 보안 그룹도 지원합니다. 관리형 유지 관리는 NAT 인스턴스가 아니라 NAT 게이트웨이의 장점입니다.[5]

Q6. **게이트웨이 엔드포인트(Gateway Endpoint)**의 고유한 특징으로 옳은 것을 **두 개** 고르세요.

게이트웨이 엔드포인트는 ① S3와 DynamoDB 전용이며, ② 라우팅 테이블에 접두사 목록(Prefix List) 라우트로 동작하고, ③ 추가 요금이 전혀 없는 완전 무료 서비스입니다.[8] 서브넷 사설 IP(ENI) 생성과 온프레미스 직접 접근 지원은 인터페이스 엔드포인트(PrivateLink)의 고유한 특징입니다.

Q7. (시험형) 한 SaaS 소프트웨어 기업이 자사 VPC에서 구동 중인 백엔드 분석 API 서비스를 수백 개의 고객사 AWS VPC에 사설망으로 안전하게 제공하고자 합니다. 그런데 다수의 고객사 VPC IP 대역(CIDR)이 자사 VPC의 대역과 겹치는(Overlapping) 경우가 많고, 보안 규정상 고객사에게 자사 VPC의 다른 내부 리소스는 절대 노출되어서는 안 됩니다. 가장 적절한 아키텍처는 무엇일까요?

AWS PrivateLink (엔드포인트 서비스)는 고객사에게 VPC 전체가 아닌 **오직 지정된 단 하나의 특정 서비스(NLB)**만 안전하게 노출할 수 있는 최적의 솔루션입니다.[11] 또한 VPC 피어링과 달리 두 네트워크의 CIDR 대역이 서로 겹치더라도 아무런 문제 없이 안전하게 통신할 수 있습니다. VPC 피어링은 IP 대역이 겹치면 아예 생성할 수 없으며 VPC 전체가 상호 연결되는 위험이 있습니다.

Q8. (0005 복습) 한 시스템 엔지니어가 NAT 게이트웨이를 통과하는 아웃바운드 트래픽을 엄격하게 제한하기 위해, NAT 게이트웨이에 직접 보안 그룹을 연결하려 했으나 콘솔에서 설정할 수 없음을 알게 되었습니다. NAT 게이트웨이 트래픽을 보안상 안전하게 제어하기 위한 올바른 대안은 무엇일까요?

NAT 게이트웨이에는 구조적으로 보안 그룹을 연결할 수 없습니다. 따라서 트래픽 제어는 실제 요청을 발생시키는 프라이빗 EC2 인스턴스의 보안 그룹에서 1차로 통제하고, NAT 게이트웨이가 위치한 퍼블릭 서브넷의 네트워크 ACL(NACL)을 통해 서브넷 경계에서 패킷을 필터링해야 합니다.[5] 라우팅 테이블에는 거부(Deny) 규칙이 없으며, IAM 정책은 네트워크 패킷을 필터링하는 도구가 아닙니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 머릿속에서 내용을 직접 정리해 적어보세요.
(1) NAT 게이트웨이를 고가용성(High Availability)으로 설계할 때의 올바른 배치 구조와 그 이유는 무엇인가요?
(2) 게이트웨이 엔드포인트와 인터페이스 엔드포인트를 지원 서비스, 통신 동작 방식, 온프레미스 접근 가능 여부, 비용 관점에서 비교해 보세요.

(1) NAT 게이트웨이 고가용성 배치:
NAT 게이트웨이는 단일 가용 영역(AZ)에 묶이며 그 AZ 안에서만 이중화되므로, 각 가용 영역의 퍼블릭 서브넷마다 NAT 게이트웨이를 각각 하나씩 생성해야 합니다. 그리고 각 AZ의 프라이빗 서브넷 라우팅 테이블이 동일한 AZ에 위치한 NAT 게이트웨이를 가리키도록 구성합니다. 이렇게 하면 특정 AZ 전체에 장애가 발생해도 다른 AZ의 인터넷 통신이 단절되지 않으며, AZ 간 데이터 전송 요금(Cross-AZ Traffic)도 발생하지 않습니다.

(2) 게이트웨이 엔드포인트 vs 인터페이스 엔드포인트:
- 게이트웨이 엔드포인트: S3와 DynamoDB 전용, 라우팅 테이블에 접두사 목록(Prefix List) 라우트로 동작, 온프레미스에서 VPN/DX를 타고 직접 접근 불가, 완전 무료.
- 인터페이스 엔드포인트 (PrivateLink): S3를 포함한 거의 모든 AWS 서비스 및 사내 커스텀 서비스 지원, 서브넷에 사설 IP를 가진 ENI 생성 및 프라이빗 DNS 활용, 온프레미스에서 전용선을 타고 직접 사설 접근 가능, AZ별 시간당 요금 + GB당 처리 요금 부과(유료).

추가 학습 및 실습

1차 공식 문서 (권장, 약 10분): AWS PrivateLink 사용 설명서의 "Gateway endpoints"를 꼭 읽어보세요. 엔드포인트가 있을 때와 없을 때의 트래픽 라우팅 흐름 비교도와 가장 긴 접두사 일치(Longest Prefix Match) 원리가 알기 쉽게 설명되어 있습니다. 한국어 페이지는 URL의 docs.aws.amazon.com/ 뒤에 ko_kr/을 넣어 확인하실 수 있습니다.

콘솔 실습 (선택 사항, 비용 주의): 0004 레슨에서 생성했던 VPC에 Amazon S3 게이트웨이 엔드포인트를 생성하고 프라이빗 서브넷의 라우팅 테이블을 체크해 보세요. 라우팅 테이블에 pl-로 시작하는 접두사 목록 라우트가 자동으로 등록되는 것을 확인할 수 있습니다. 게이트웨이 엔드포인트는 무료입니다.
⚠️ 주의사항: NAT 게이트웨이와 인터페이스 엔드포인트는 생성해 두기만 해도 시간당 요금이 부과됩니다. 만약 실습으로 생성했다면 테스트 후 즉시 삭제하고, NAT 게이트웨이에 연결했던 탄력적 IP(EIP)도 잊지 말고 해제(Release)하세요.
