보안 그룹 vs 네트워크 ACL

둘 다 "방화벽"이지만 성격이 정반대입니다. 상태 저장 대 상태 비저장, 허용만 대 허용·거부, 인스턴스 대 서브넷. 이 세 쌍을 표로 외우고, 응답 트래픽이 어떻게 돌아오는지만 이해하면 됩니다.

⏱ 약 18분🎯 오늘의 승리: 시나리오 8문항📌 VPC 치트시트

왜 이것인가

시험에서: "특정 IP 대역을 차단하라"(NACL), "웹 서버에서 오는 트래픽만 DB에 허용하라"(보안 그룹 참조)는 거의 매회 나오는 유형입니다.
실무에서: 연결이 안 될 때 원인의 상당수가 NACL의 응답 포트 누락입니다. 상태 비저장이 무엇을 뜻하는지 알면 디버깅 시간이 줄어듭니다.

한 장으로 비교

특성보안 그룹 (SG)네트워크 ACL (NACL)
동작 수준인스턴스 수준서브넷 수준
적용 범위그 SG에 연결된 인스턴스연결된 서브넷의 모든 인스턴스
규칙 종류허용만허용과 거부
규칙 평가모든 규칙을 보고 결정번호 오름차순, 처음 일치한 규칙 적용
응답 트래픽자동 허용 (상태 저장)명시적으로 허용해야 함 (상태 비저장)

출처: VPC 사용 설명서의 비교표[1]

AWS는 보안 그룹을 주된 네트워크 접근 제어 수단으로 쓰고, NACL은 특정 트래픽을 거부하는 보조 수단이나 서브넷 단위 가드레일로 쓰라고 권합니다. NACL은 서브넷 전체에 적용되므로, 누군가 SG를 잘못 붙여 인스턴스를 띄워도 막아 주는 심층 방어가 됩니다.[1]

보안 그룹의 세부

  • 허용 규칙만 만들 수 있고 거부 규칙은 없습니다. 새로 만든 SG에는 인바운드 규칙이 없고(아무것도 못 들어옴), 모든 아웃바운드를 허용하는 규칙이 하나 있습니다.[2]
  • 한 리소스에 SG를 여러 개 붙일 수 있고, 이때 모든 SG의 규칙을 합친 하나의 규칙 집합으로 판정합니다.[2] 허용만 있으니 합쳐도 충돌이 없습니다.
  • 상태 저장: 인스턴스가 보낸 요청의 응답은 인바운드 규칙과 무관하게 들어오고, 허용된 인바운드의 응답은 아웃바운드 규칙과 무관하게 나갑니다.[3]

보안 그룹이 보안 그룹을 참조하기

규칙의 소스(또는 대상)로 IP 대신 다른 SG의 ID를 쓸 수 있습니다. 그러면 그 SG에 연결된 인스턴스들의 사설 IP에서 오는 트래픽이 허용됩니다. 참조된 SG의 규칙이 복사되는 것은 아닙니다. 같은 VPC이거나 피어링 연결된 VPC 사이 등에서 쓸 수 있습니다.[2]

SG인바운드 규칙 (AWS 문서의 예)
ALB용 SGHTTP/HTTPS, 소스 0.0.0.0/0
웹 서버 SGHTTP/HTTPS, 소스 ALB용 SG
DB SGDB 포트, 소스 웹 서버 SG

Auto Scaling으로 웹 서버의 IP가 계속 바뀌어도 DB SG 규칙은 고칠 필요가 없습니다.[2]

NACL의 세부

  • 모든 서브넷은 NACL 하나에 연결되어야 하며, 지정하지 않으면 기본 NACL에 연결됩니다. 한 NACL을 여러 서브넷에 연결할 수 있지만, 한 서브넷은 한 번에 NACL 하나만 가집니다.[4]
  • 규칙 번호는 1~32766이고 가장 낮은 번호부터 평가해, 일치하는 규칙이 나오면 그 뒤는 보지 않습니다. 나중에 끼워 넣을 수 있게 10이나 100 단위로 번호를 매기라고 권합니다.[4]
  • 모든 NACL에는 번호가 *인 규칙이 있어, 어떤 번호 규칙에도 맞지 않는 패킷을 거부합니다. 이 규칙은 삭제할 수 없습니다. 기본 NACL은 100번 규칙으로 모든 인바운드·아웃바운드를 허용합니다.[5]
  • NACL은 트래픽이 서브넷에 들어오고 나갈 때 평가되며, 서브넷 안에서 라우팅될 때는 평가되지 않습니다.[4]
  • 넓은 포트 범위를 열면서 그 안의 일부만 막으려면, 거부 규칙에 더 낮은 번호를 줘야 합니다.[6]

임시 포트(ephemeral port)

클라이언트가 서버의 443번에 접속하면, 서버의 응답은 클라이언트가 고른 임시 포트로 돌아갑니다. NACL은 상태 비저장이므로 이 응답 경로를 따로 열어야 합니다. 범위는 클라이언트의 OS에 따라 다릅니다.[7]

요청을 보낸 쪽임시 포트 범위
다수의 Linux 커널(Amazon Linux 포함)32768–61000
Windows Server 2008 이후49152–65535
Elastic Load Balancing, NAT 게이트웨이, Lambda1024–65535

실무적으로는 다양한 클라이언트를 받기 위해 1024–65535를 열고, 그 안의 악성 포트는 더 낮은 번호의 거부 규칙으로 막을 수 있습니다.[7] 반대로 VPC 안의 인스턴스가 클라이언트일 때(예: 패치 다운로드)는 NACL 인바운드에 그 인스턴스 OS의 임시 포트를 열어야 합니다.

시험 단골

"특정 IP(대역)를 차단" → NACL 거부 규칙. 보안 그룹에는 거부가 없다.
"웹 계층에서 오는 트래픽만 DB에 허용" → DB SG의 소스로 웹 SG를 참조.
"인바운드는 열었는데 응답이 안 감" → NACL 아웃바운드에 임시 포트(1024–65535) 누락.
"SG 아웃바운드를 다 지웠는데 웹 응답은 나감" → 상태 저장이라 정상.
"NACL 규칙 순서" → 낮은 번호가 먼저, 첫 일치로 끝. 거부를 허용보다 낮은 번호에.

연습

Q1. (시험형) 보안팀이 198.51.100.0/24 대역에서 웹 애플리케이션으로 들어오는 공격 트래픽을 확인했습니다. 이 대역만 즉시 차단하고 다른 사용자는 계속 접속해야 합니다. 가장 적절한 방법은?

보안 그룹에는 거부 규칙이 없습니다. 특정 대역만 막는 것은 허용·거부가 모두 되는 NACL의 몫입니다.[1] 거부 규칙은 기존 허용 규칙보다 낮은 번호로 넣어야 먼저 적용됩니다. 나머지 보기는 정상 사용자까지 막습니다.

Q2. 서브넷 NACL의 인바운드 규칙이 아래와 같습니다. 203.0.113.7에서 SSH(TCP 22)로 접속하면?

100  TCP 22  0.0.0.0/0        ALLOW
200  TCP 22  203.0.113.0/24   DENY
*    ALL     0.0.0.0/0        DENY

NACL은 낮은 번호부터 평가해 처음 일치한 규칙을 적용하고 멈춥니다.[6] 100번이 이미 일치하므로 200번은 보지도 않습니다. "더 구체적인 것이 이긴다"는 라우팅 테이블(0004)의 규칙이고, "거부가 항상 이긴다"는 IAM(0001)의 규칙입니다. 섞지 마세요. 대역을 막으려면 거부 규칙 번호를 100보다 낮게 줘야 합니다.

Q3. 퍼블릭 서브넷의 웹 서버에 사용자 지정 NACL을 붙였습니다. 인바운드: TCP 443 허용(0.0.0.0/0). 아웃바운드: TCP 443 허용(0.0.0.0/0). 보안 그룹은 443 인바운드를 허용합니다. 사용자들이 페이지를 받지 못합니다. 원인은?

서버의 응답은 클라이언트의 443번이 아니라 클라이언트의 임시 포트로 나갑니다. NACL은 상태 비저장이라 아웃바운드에 그 범위(실무적으로 1024–65535)를 열어야 합니다.[7] 보안 그룹은 상태 저장이라 응답에 아웃바운드 규칙이 필요 없습니다. 인바운드 임시 포트는 서버가 클라이언트일 때 필요합니다.

Q4. 웹 서버 SG의 인바운드는 TCP 443(0.0.0.0/0) 허용이고, 운영자가 아웃바운드 규칙을 모두 삭제했습니다. NACL은 기본 NACL입니다. 인터넷 사용자의 HTTPS 요청에 대한 응답은?

보안 그룹은 상태 저장입니다. 허용된 인바운드 요청의 응답은 아웃바운드 규칙과 상관없이 나갑니다.[3] 다만 SG도 아웃바운드를 검사합니다. 아웃바운드 규칙이 없으면 서버가 먼저 시작하는 연결(예: 외부 API 호출)은 나가지 못합니다.[2] 기본 NACL은 모두 허용입니다.

Q5. (시험형) 3계층 애플리케이션에서 웹 서버는 Auto Scaling 그룹으로 수시로 교체됩니다. DB 인스턴스는 웹 서버에서 오는 MySQL(3306) 트래픽만 받아야 합니다. 운영 부담이 가장 적은 방법은?

SG 참조를 쓰면 웹 서버 SG에 연결된 인스턴스라면 IP가 바뀌어도 자동으로 허용됩니다.[2] IP를 손으로 관리하는 보기는 Auto Scaling과 맞지 않고, 0.0.0.0/0은 최소 권한에 어긋납니다.

Q6. 보안 그룹에 대한 설명으로 옳은 것을 두 개 고르세요.

보안 그룹: 허용만, 모든 규칙 평가, 인스턴스 수준, 상태 저장. 번호 순서 평가와 서브넷 수준은 NACL의 특성입니다.[1]

Q7. (0004 복습) EC2 인스턴스에 퍼블릭 IP가 있고, SG는 TCP 80(0.0.0.0/0)을 허용하며, 서브넷은 기본 NACL을 씁니다. 그래도 인터넷에서 웹 페이지가 열리지 않습니다. 서브넷 라우팅 테이블에는 10.0.0.0/16 local만 있습니다. 가장 먼저 고칠 것은?

IGW 라우트가 없는 서브넷은 프라이빗 서브넷이라, 방화벽이 다 열려 있어도 인터넷과 통신할 수 없습니다(0004).[8] 기본 NACL은 이미 모두 허용이고, SG는 상태 저장이라 응답용 규칙이 필요 없습니다. 연결 문제는 라우팅 → NACL → SG 순서로 점검하세요.

Q8. 프라이빗 서브넷의 앱 서버 앞에 Application Load Balancer가 있습니다. 앱 서브넷의 사용자 지정 NACL은 아웃바운드에 TCP 32768–65535만 허용합니다. 로드 밸런서의 요청 일부가 간헐적으로 응답을 받지 못합니다. 가장 알맞은 수정은?

Elastic Load Balancing이 보내는 요청은 1024–65535 범위의 임시 포트를 씁니다. 32768 미만 포트로 돌아가야 하는 응답이 NACL에서 버려집니다.[7] NACL은 서브넷에 반드시 하나 연결되므로 "지운다"는 선택지가 될 수 없고, SG에는 거부 규칙이 없습니다.

기억에서 꺼내기

보지 말고 비교표를 다시 그려 보세요: 동작 수준, 규칙 종류, 규칙 평가 방식, 응답 트래픽. 그리고 NACL에서 임시 포트를 열어야 하는 방향은 언제 아웃바운드이고 언제 인바운드인가?

SG: 인스턴스 수준, 허용만, 모든 규칙 평가, 상태 저장(응답 자동 허용). NACL: 서브넷 수준, 허용·거부, 번호 오름차순 첫 일치, 상태 비저장(응답 명시 허용).

VPC 안의 인스턴스가 서버라면 응답이 나가므로 NACL 아웃바운드에 클라이언트의 임시 포트를, 인스턴스가 클라이언트라면 응답이 들어오므로 NACL 인바운드에 자기 OS의 임시 포트를 엽니다. 실무 범위는 1024–65535.

실습 (선택, 프리 티어): 퍼블릭 서브넷에 프리 티어 EC2 하나를 띄우고 웹 서버를 켠 뒤, 서브넷에 새 NACL을 만들어 연결하고 인바운드 80만 허용해 보세요. 페이지가 안 열리는 것을 확인한 다음 아웃바운드 1024–65535를 추가하면 열립니다. 끝나면 인스턴스를 종료하고 서브넷을 기본 NACL로 되돌리세요.
