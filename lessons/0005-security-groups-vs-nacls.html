보안 그룹 vs 네트워크 ACL:
AWS 가상 방화벽의 두 축 완벽 비교

둘 다 VPC의 핵심적인 가상 방화벽이지만 동작 계층과 상태 유지 방식이 완전히 정반대입니다. 상태 저장(Stateful) 대 상태 비저장(Stateless), 허용 규칙만 대 허용·거부 규칙, 인스턴스 수준 대 서브넷 수준이라는 세 가지 핵심 차이점을 명확히 정리하고, 임시 포트를 통한 응답 패킷의 흐름을 이해하면 시험과 실무 문제를 막힘없이 해결할 수 있습니다.

왜 보안 그룹과 네트워크 ACL을 함께 비교해야 할까요?

시험 관점에서: AWS Certified Solutions Architect - Associate (SAA-C03) 시험에서는 "특정 악성 IP 대역의 공격 트래픽을 즉각 차단하라(정답: NACL 거부 규칙)", "웹 서버 계층에서 들어오는 트래픽만 데이터베이스에 안전하게 허용하라(정답: 보안 그룹 참조)"와 같은 문제가 거의 매 시험마다 출제됩니다.[1] 두 방화벽의 특성과 지원 규칙의 차이를 혼동하면 오답의 함정에 빠지기 쉽습니다.

실무 관점에서: 서버에 인바운드 포트를 정상적으로 열어 두었는데도 외부 클라이언트가 응답을 받지 못해 연결 시간 초과(Timeout)가 발생하는 장애가 실무에서 자주 일어납니다. 그 원인의 상당수는 상태 비저장인 네트워크 ACL에서 클라이언트의 임시 포트(Ephemeral Port)로 나가는 아웃바운드 트래픽을 열어주지 않았기 때문입니다. 이 원리를 꿰뚫고 있으면 네트워크 장애 해결(트러블슈팅) 시간을 대폭 단축할 수 있습니다.

출처: Amazon VPC 사용 설명서의 보안 그룹과 네트워크 ACL 비교표[1]

AWS 모범 사례에서는 **보안 그룹(Security Group)**을 애플리케이션 보안을 지키는 주된 1차 접근 제어 수단으로 사용하고, **네트워크 ACL(NACL)**은 특정 악성 IP 대역을 차단하는 블랙리스트 수단이나 서브넷 전체를 보호하는 가드레일(심층 방어, Defense in Depth)로 활용할 것을 권장합니다. 누군가 실수로 개별 EC2의 보안 그룹을 너무 넓게 열어두더라도, 서브넷 앞단의 NACL이 단단히 막아주면 보안 사고를 미연에 방지할 수 있습니다.[1]

보안 그룹(Security Group)의 핵심 특징

  • 허용(Allow) 규칙만 지원: 보안 그룹에는 특정 IP를 거부(Deny)하는 규칙을 둘 수 없습니다. 새로 생성한 사용자 지정 보안 그룹은 기본적으로 인바운드 규칙이 하나도 없어서 모든 외부 유입 트래픽을 차단(화이트리스트 방식)하며, 아웃바운드는 모든 트래픽(0.0.0.0/0)을 허용하도록 설정되어 있습니다.[2]
  • 다중 보안 그룹 연결과 규칙 병합: 단일 EC2 인스턴스에 여러 개의 보안 그룹을 동시에 연결할 수 있습니다. 이때 AWS는 연결된 모든 보안 그룹의 규칙을 하나로 합쳐서(Union) 종합적으로 평가합니다.[2] 오직 허용 규칙만 존재하므로 여러 규칙이 합쳐져도 충돌이 일어나지 않습니다.
  • 상태 저장(Stateful)의 마법: 보안 그룹은 연결의 '상태(State)'를 기억합니다. 따라서 인바운드 규칙에 의해 정상적으로 허용되어 들어온 요청에 대한 응답 트래픽은, 아웃바운드 규칙에 해당 포트가 열려 있지 않더라도 자동으로 인스턴스 밖으로 전송됩니다.[3] 반대로 인스턴스에서 외부로 먼저 시작한 아웃바운드 요청의 응답 역시 인바운드 규칙과 무관하게 자동으로 수신됩니다.

보안 그룹 간 참조 (Security Group Referencing - 시험 최빈출!)

보안 그룹 규칙을 작성할 때 소스(Source)나 대상(Destination)에 IP 주소나 CIDR 대역 대신 다른 보안 그룹의 ID(예: sg-xxxx)를 지정할 수 있습니다. 이렇게 하면 "해당 보안 그룹이 연결된 인스턴스들의 프라이빗 IP에서 출발한 트래픽만 허용하겠다"는 의미가 됩니다. (참조된 그룹의 규칙이 복사되는 것이 아닙니다.) 같은 VPC 내부는 물론이고, VPC 피어링으로 연결된 다른 VPC 사이에서도 활용할 수 있습니다.[2]

보안 그룹 구분인바운드 허용 규칙 (AWS 권장 모범 사례)설계 의도
ALB용 보안 그룹HTTP/HTTPS (포트 80/443), 소스: 0.0.0.0/0전 세계 인터넷 사용자 누구나 접속할 수 있도록 개방

데이터베이스용 보안 그룹MySQL (포트 3306), 소스: 웹 서버용 보안 그룹 ID오직 인증된 웹 애플리케이션 서버에서 보낸 DB 쿼리만 허용

이 설계의 가장 큰 장점은 **유지 관리의 편의성**입니다. Auto Scaling에 의해 웹 서버 인스턴스가 2대에서 100대로 늘어나고 개별 사설 IP가 계속 바뀌더라도, 새 인스턴스에 웹 서버 보안 그룹만 붙어 있다면 데이터베이스 보안 그룹 규칙을 단 한 줄도 손댈 필요가 없습니다.[2]

네트워크 ACL(Network ACL)의 핵심 특징

  • 서브넷 단위 방화벽: 모든 서브넷은 반드시 하나의 네트워크 ACL에 연결되어야 합니다. 사용자가 지정하지 않으면 VPC 생성 시 자동으로 만들어진 기본 NACL(Default NACL)에 연결됩니다. 하나의 NACL을 여러 서브넷에 연결할 수는 있지만, 하나의 서브넷이 동시에 여러 NACL을 가질 수는 없습니다.[4]
  • 규칙 번호 오름차순 순차 평가: 규칙 번호는 1부터 32766까지 지정할 수 있으며, 가장 낮은 번호부터 차례대로 평가됩니다. 트래픽과 일치하는 규칙을 발견하면 즉시 허용 또는 거부를 결정하고 평가를 종료하며, 그 뒤의 더 높은 번호 규칙은 절대 검사하지 않습니다. 따라서 나중에 새로운 규칙을 중간에 끼워 넣을 수 있도록 10, 20, 30 또는 100, 200, 300 단위로 여유를 두고 번호를 매기는 것이 좋습니다.[4]
  • 기본 규칙 및 `*` 규칙: 모든 NACL의 맨 끝에는 번호가 *인 규칙이 있으며, 위의 어떤 번호 규칙에도 일치하지 않는 모든 패킷을 거부(Deny)합니다. 이 기본 * 규칙은 수정하거나 삭제할 수 없습니다. VPC의 기본 NACL은 100번 규칙으로 모든 인바운드와 아웃바운드 트래픽을 기본 허용(Allow)하고 있습니다.[5] 반면 사용자가 직접 새로 생성한 커스텀 NACL은 모든 인바운드와 아웃바운드가 기본 거부(`*` DENY) 상태로 시작합니다.
  • 서브넷 경계 통과 시에만 동작: NACL은 트래픽이 서브넷 경계를 넘나들 때(들어오거나 나갈 때)만 동작합니다. 같은 서브넷 안에 있는 두 인스턴스 사이의 통신에는 NACL이 개입하지 않습니다.[4]
  • 거부 규칙의 올바른 배치: 전체 대역을 열어두면서 그 안의 특정 악성 IP만 차단하려면, 거부(Deny) 규칙에 허용(Allow) 규칙보다 더 낮은 번호를 부여해야 합니다.[6]

임시 포트(Ephemeral Port)의 비밀: 상태 비저장 방화벽의 필수 지식

외부 클라이언트(사용자 웹 브라우저)가 서버의 443(HTTPS) 포트로 접속할 때, 클라이언트는 자신의 운영체제에서 사용 가능한 임의의 남는 포트 하나를 골라 출발지 포트로 사용합니다. 이를 임시 포트(Ephemeral Port)라고 부릅니다. 서버가 처리를 마치고 클라이언트에게 응답을 보낼 때, 목적지 포트는 443이 아니라 **클라이언트가 열었던 임시 포트 번호**가 됩니다.[7]

보안 그룹은 상태 저장이므로 이 응답을 자동으로 통과시키지만, 네트워크 ACL은 상태 비저장(Stateless)이므로 아웃바운드 규칙에 클라이언트의 임시 포트 대역이 명시적으로 열려 있지 않으면 응답 패킷을 가차 없이 버립니다.

요청을 시작한 주체 (클라이언트 OS)임시 포트 범위
다수의 Linux 커널 (Amazon Linux 포함)32768–61000
Windows Server 2008 및 이후 버전49152–65535
Elastic Load Balancing (ALB/NLB), NAT 게이트웨이, AWS Lambda1024–65535

실무에서는 다양한 운영체제를 사용하는 전 세계 클라이언트의 요청을 안정적으로 처리하기 위해, NACL 아웃바운드 규칙에 1024–65535 범위를 열어주는 것이 표준입니다.[7]

반대로 VPC 안의 인스턴스가 클라이언트가 되어 외부 인터넷에서 패키지를 다운로드할 때(예: yum update): 요청은 아웃바운드 80/443으로 나가고, 외부 서버의 응답은 인스턴스 자신의 임시 포트로 들어오게 됩니다. 따라서 이때는 NACL 인바운드 규칙에 임시 포트 대역이 허용되어 있어야 정상적으로 응답을 받을 수 있습니다.

시험에 자주 나오는 핵심 패턴

"특정 IP 또는 CIDR 대역을 차단" → 네트워크 ACL의 거부(Deny) 규칙. 보안 그룹에는 거부 규칙이 아예 없습니다.
"웹 계층에서 들어오는 트래픽만 DB에 허용" → DB 보안 그룹의 소스 규칙에 웹 서버 보안 그룹 ID를 참조.
"인바운드 포트를 열었는데 외부에서 응답을 못 받음" → 서브넷 NACL 아웃바운드 규칙에 임시 포트(1024–65535)가 빠져 있는지 확인.
"보안 그룹의 아웃바운드 규칙을 모두 삭제했는데도 웹 응답이 정상 전송됨" → 보안 그룹은 상태 저장(Stateful)이므로 허용된 인바운드 연결에 대한 응답은 자동 통과됩니다.
"NACL 규칙 평가 순서" → 번호가 낮은 규칙부터 우선 평가되며, 처음 일치한 규칙으로 판정이 끝납니다. 따라서 거부 규칙은 항상 허용 규칙보다 낮은 번호에 두어야 합니다.

실전 연습: 시나리오 퀴즈로 확인하기

시험에 반드시 출제되는 보안 그룹과 네트워크 ACL의 실전 시나리오 8문항입니다. 방금 배운 개념을 되새기며 풀어보세요.

Q1. (시험형) 회사의 보안팀이 특정 IP 대역인 198.51.100.0/24에서 웹 애플리케이션으로 대규모 악성 공격 트래픽이 유입되고 있음을 확인했습니다. 일반 사용자의 정상적인 서비스 이용은 유지하면서, 이 공격 대역만 즉시 차단하고자 합니다. 가장 적절한 조치는 무엇일까요?

보안 그룹에는 거부(Deny) 규칙을 생성할 수 없습니다. 특정 IP 대역만 콕 집어서 차단하려면 허용과 거부를 모두 지원하는 네트워크 ACL(NACL)을 사용해야 합니다.[1] 이때 거부 규칙의 번호는 기존의 전체 허용 규칙(예: 100번)보다 반드시 더 낮은 번호(예: 50번)로 지정해야 먼저 평가되어 차단이 적용됩니다. 나머지 보기들은 정상적인 사용자 접속까지 모두 차단해 버립니다.

규칙 번호   프로토콜   포트 범위    소스 CIDR        허용/거부
100        TCP        22          0.0.0.0/0        ALLOW
200        TCP        22          203.0.113.0/24   DENY
*          ALL        ALL         0.0.0.0/0        DENY

네트워크 ACL은 가장 낮은 규칙 번호부터 순서대로 평가하여 처음 일치한 규칙을 적용하고 즉시 평가를 종료합니다.[6] 패킷이 도착했을 때 100번 규칙(0.0.0.0/0 허용)에 이미 부합하므로 즉시 허용되며, 200번 거부 규칙은 검사조차 하지 않습니다. "더 구체적인 대역이 이긴다"는 라우팅 테이블(0004)의 규칙이고, "거부가 항상 이긴다"는 IAM(0001)의 규칙입니다. NACL에서는 오직 규칙 번호가 빠른 쪽이 승리합니다. 따라서 차단하려면 200번이 아니라 100번보다 작은 번호(예: 50번)를 주어야 합니다.

Q3. 퍼블릭 서브넷의 웹 서버에 새로운 커스텀 네트워크 ACL을 연결했습니다. 인바운드 규칙으로 TCP 443 허용(0.0.0.0/0), 아웃바운드 규칙으로 TCP 443 허용(0.0.0.0/0)을 설정했고, EC2 보안 그룹에서도 443 인바운드를 정상 허용했습니다. 하지만 외부 사용자들이 웹 페이지를 전혀 불러오지 못하고 있습니다. 근본적인 원인은 무엇일까요?

서버가 클라이언트에게 웹 페이지 응답 패킷을 보낼 때, 목적지 포트는 443이 아니라 클라이언트 브라우저가 임의로 생성한 임시 포트(Ephemeral Port)입니다. 네트워크 ACL은 상태 비저장(Stateless)이므로 아웃바운드에 해당 임시 포트 범위(실무적으로 1024–65535)를 명시적으로 열어주지 않으면 응답 패킷이 서브넷 밖으로 나가지 못하고 폐기됩니다.[7] 보안 그룹은 상태 저장이므로 응답용 아웃바운드 규칙이 없어도 통과합니다.

Q4. 웹 서버 보안 그룹의 인바운드는 TCP 443(0.0.0.0/0)을 허용하고 있습니다. 그런데 시스템 관리자가 실수로 보안 그룹의 아웃바운드 규칙을 모두 삭제해 버렸습니다. 서브넷은 VPC 기본 네트워크 ACL(모두 허용)을 사용 중입니다. 인터넷 사용자가 보낸 HTTPS 요청에 대해 웹 서버의 응답은 어떻게 될까요?

보안 그룹은 상태 저장(Stateful) 방화벽입니다. 인바운드 규칙에 의해 정상적으로 허용된 요청에 대한 응답 트래픽은 아웃바운드 규칙의 존재 여부와 상관없이 자동으로 허용되어 밖으로 나갑니다.[3] 다만 보안 그룹도 아웃바운드를 분명히 검사합니다. 아웃바운드 규칙이 모두 삭제되면 서버가 *먼저 시작하는* 외부 연결(예: 외부 API 호출이나 패치 다운로드)은 나가지 못합니다.

Q5. (시험형) 3계층 웹 애플리케이션에서 웹 서버들은 트래픽에 따라 Auto Scaling 그룹에 의해 수시로 생성되고 교체됩니다. 데이터베이스(DB) 인스턴스는 오직 웹 서버들에서 오는 MySQL(TCP 3306) 트래픽만 수신해야 합니다. 운영 오버헤드가 가장 적고 안전한 보안 그룹 구성 방식은 무엇일까요?

보안 그룹의 규칙 소스로 **다른 보안 그룹 ID를 참조(Security Group Referencing)**하면, Auto Scaling에 의해 웹 서버의 개수가 바뀌거나 사설 IP가 동적으로 변경되더라도 해당 보안 그룹이 붙은 인스턴스의 트래픽을 자동으로 허용합니다.[2] IP를 수동으로 등록하는 것은 오버헤드가 크고 확장에 대응할 수 없으며, 0.0.0.0/0 개방은 심각한 보안 결함입니다.

Q6. **보안 그룹(Security Group)**의 고유한 동작 특성으로 옳은 것을 **두 개** 고르세요.

보안 그룹의 핵심 특징은 ① 허용 규칙만 존재, ② 모든 규칙 종합 평가, ③ 인스턴스(ENI) 수준 적용, ④ 상태 저장(Stateful)입니다. 규칙 번호 순차 평가와 서브넷 단위 일괄 적용은 네트워크 ACL(NACL)의 고유한 특성입니다.[1]

Q7. (0004 복습) EC2 인스턴스에 퍼블릭 IP가 정상 할당되어 있고, 보안 그룹은 TCP 80(0.0.0.0/0)을 허용하며, 서브넷은 기본 네트워크 ACL을 사용 중입니다. 그럼에도 불구하고 외부 인터넷에서 웹 페이지에 전혀 접속되지 않습니다. 서브넷 라우팅 테이블을 확인해 보니 10.0.0.0/16 local 라우트만 등록되어 있었습니다. 가장 먼저 취해야 할 조치는 무엇일까요?

IGW로 향하는 라우트가 없는 서브넷은 프라이빗 서브넷입니다. 방화벽(보안 그룹, NACL)이 아무리 활짝 열려 있고 인스턴스에 퍼블릭 IP가 있더라도, 라우팅 테이블에 IGW 규칙이 없으면 패킷이 인터넷으로 오갈 수 없습니다(0004 레슨 참조).[8] 기본 NACL은 이미 모두 허용 상태이고, 보안 그룹은 상태 저장이므로 응답용 아웃바운드 규칙이 필요 없습니다. 통신 장애 시에는 항상 **라우팅 테이블 → 네트워크 ACL → 보안 그룹** 순으로 점검하세요.

Q8. 프라이빗 서브넷에 위치한 애플리케이션 서버 앞단에 Application Load Balancer(ALB)가 배치되어 있습니다. 앱 서브넷의 커스텀 네트워크 ACL은 아웃바운드에 TCP 32768–65535 포트만 허용하고 있습니다. 그런데 로드 밸런서가 앱 서버로 전달한 요청 중 일부가 간헐적으로 응답을 받지 못하고 유실되는 현상이 발생했습니다. 가장 적절한 해결책은 무엇일까요?

AWS Elastic Load Balancing(ALB, NLB)이 백엔드 인스턴스로 요청을 보낼 때는 1024–65535 범위의 임시 포트를 사용합니다.[7] 따라서 NACL 아웃바운드가 32768 이상만 열려 있으면, ALB가 1024–32767 포트로 보낸 요청에 대한 앱 서버의 응답이 NACL에서 버려지게 됩니다. 서브넷은 반드시 하나의 NACL에 연결되어야 하므로 NACL을 삭제할 수는 없으며, 보안 그룹에는 거부 규칙이 없습니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 머릿속에서 내용을 직접 정리해 적어보세요.
(1) 보안 그룹과 네트워크 ACL의 네 가지 핵심 차이점(동작 수준, 규칙 종류, 규칙 평가 방식, 응답 트래픽 처리)을 비교해 보세요.
(2) 네트워크 ACL에서 임시 포트(Ephemeral Port)를 열어주어야 하는 방향은 인스턴스가 서버일 때와 클라이언트일 때 각각 어느 방향인가요?

(1) 보안 그룹 vs 네트워크 ACL 핵심 비교:
- 보안 그룹: 인스턴스(ENI) 수준, 허용(Allow) 규칙만 지원, 모든 규칙을 종합 평가, 상태 저장(Stateful: 인바운드 허용 시 아웃바운드 응답 자동 허용).
- 네트워크 ACL: 서브넷 수준, 허용(Allow) 및 거부(Deny) 모두 지원, 규칙 번호 오름차순 순차 평가(첫 일치 시 즉시 종료), 상태 비저장(Stateless: 응답 트래픽도 규칙으로 명시적 허용 필수).

(2) 임시 포트 허용 방향:
- 인스턴스가 서버인 경우(예: 외부 사용자의 요청을 수신): 요청을 처리하고 응답을 클라이언트에게 돌려보내야 하므로, NACL 아웃바운드에 클라이언트의 임시 포트 대역(1024–65535)을 열어야 합니다.
- 인스턴스가 클라이언트인 경우(예: 외부 인터넷에서 OS 패치를 다운로드): 인스턴스가 먼저 요청을 보내고 외부 서버의 응답을 수신해야 하므로, NACL 인바운드에 인스턴스 자신의 임시 포트 대역(1024–65535)을 열어야 합니다.

추가 학습 및 실습

1차 공식 문서 (권장, 약 8분): AWS VPC 사용 설명서의 "Custom network ACLs for your VPC"를 꼭 읽어보세요. 권장 규칙 구성 표와 임시 포트(Ephemeral Ports) 절에서 왜 1024–65535 대역을 열어야 하는지 상세한 배경 설명이 나와 있습니다. 한국어 페이지는 URL의 docs.aws.amazon.com/ 뒤에 ko_kr/을 넣어 확인하실 수 있습니다.

콘솔 실습 (선택 사항, 프리 티어 활용): 퍼블릭 서브넷에 프리 티어 EC2 인스턴스를 하나 실행하고 간단한 웹 서버(Nginx나 Apache)를 구동해 보세요. 그런 다음 해당 서브넷에 새로운 커스텀 NACL을 만들어 연결하고 인바운드 80 포트만 허용해 보세요. 브라우저에서 웹 사이트 접속이 무한 로딩되다가 실패하는 것을 확인한 후, NACL 아웃바운드에 1024–65535 규칙을 추가하면 즉시 페이지가 뜨는 것을 직접 체험할 수 있습니다. 실습이 끝나면 인스턴스를 종료하고 서브넷을 기본 NACL로 원복해 두세요.
