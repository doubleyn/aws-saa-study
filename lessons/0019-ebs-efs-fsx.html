Amazon EBS: 가용 영역(AZ)에 종속된 고성능 블록 스토리지

Amazon Elastic Block Store(EBS)는 EC2 인스턴스에 네트워크로 연결되는 고성능 가상 하드 드라이브입니다. EBS를 다룰 때 가장 중요한 대원칙은 "EBS 볼륨은 특정 가용 영역(AZ)에 생성되며, 볼륨과 동일한 AZ에 속한 EC2 인스턴스에만 연결(Attach)할 수 있다"는 물리적 제약입니다.[2] (예: us-east-1a에 생성된 볼륨은 us-east-1b의 인스턴스에 직접 연결할 수 없습니다.)

하지만 탄력적 볼륨(Elastic Volumes) 기능을 통해 인스턴스를 중지하거나 볼륨을 떼어내지 않고도 운영 중에 볼륨 크기를 늘리거나, IOPS를 조정하거나, 볼륨 유형(gp2 → gp3)을 무중단으로 실시간 변경할 수 있습니다.[2]

gp3 vs gp2: 시험과 실무에서 가장 빈출되는 비교

  • gp2의 한계: 볼륨 용량 1GiB당 3 IOPS가 할당되므로, 3,000 IOPS를 상시 안정적으로 확보하려면 실제 데이터 저장 공간이 200GiB만 필요하더라도 억지로 1TiB(1,024GiB) 크기로 볼륨을 생성해야 했습니다. 1TiB 미만의 볼륨은 I/O 크레딧 버스트 방식에 의존하므로, 피크 부하가 지속되어 BurstBalance 메트릭이 0이 되면 성능이 급격히 저하됩니다.[4]
  • gp3의 혁신: 볼륨 크기(용량)와 상관없이 기본 3,000 IOPS와 125 MiB/s가 가격에 기본 포함되어 있습니다. 더 높은 성능이 필요하면 저장 공간을 늘릴 필요 없이 오직 IOPS나 처리량 수치만 별도로 추가 결제할 수 있습니다. GiB당 기본 요금도 gp2보다 20% 저렴하므로, 시험에서 "gp2를 비용 효율적으로 개선하라"는 시나리오가 나오면 "인스턴스 중단 없이 gp3로 볼륨 유형 변경"이 언제나 최선의 정답입니다.[4]

EBS Multi-Attach와 스냅샷을 통한 AZ 이동

  • EBS Multi-Attach (다중 연결): 오직 프로비저닝된 IOPS SSD(io1, io2)에서만 지원됩니다. 동일한 가용 영역(AZ) 내의 Nitro 기반 EC2 인스턴스 최대 16대에 단일 볼륨을 동시에 마운트할 수 있습니다. 단, ext4나 XFS 같은 일반 파일 시스템은 여러 서버가 동시에 쓰면 파일이 깨지므로 클러스터 인식 파일 시스템(GFS2 등)이 필요합니다. 따라서 "여러 인스턴스가 일반적인 파일을 공유"하는 요구사항의 정답은 Multi-Attach가 아니라 EFS나 FSx입니다.[5]
  • EBS 스냅샷과 가용 영역 이동 원리: EBS 스냅샷은 변경된 블록만 백업하는 증분(Incremental) 방식으로 S3 인프라에 안전하게 보관됩니다. 중요한 점은, EBS 볼륨 자체는 특정 AZ에 갇혀 있지만 스냅샷 데이터는 리전 전체의 모든 AZ에 공유된다는 것입니다. 따라서 한 AZ(예: 1a)의 EBS 볼륨을 다른 AZ(예: 1b)로 옮기고자 할 때는 "스냅샷을 생성한 후, 대상 AZ(1b)에서 해당 스냅샷을 복원하여 새 볼륨을 생성"하는 것이 표준적인 방법입니다.[6]
  • Fast Snapshot Restore (FSR): 스냅샷에서 새 EBS 볼륨을 복원하면 백그라운드 지연 로딩(Lazy Loading)으로 인해 첫 I/O 접근 시 일시적인 지연이 발생합니다. FSR을 활성화해 두면 볼륨이 생성되자마자 모든 블록이 사전 초기화(Pre-warmed)되어 즉각 최대 프로비저닝 성능을 발휘합니다.[7]

EC2 인스턴스 스토어: 초고속이지만 휘발성인 임시 스토리지

인스턴스 스토어(Instance Store)는 EBS처럼 네트워크를 경유하지 않고, EC2 호스트 서버 컴퓨터의 물리적 메인보드에 직접 꽂혀 있는 초고속 로컬 NVMe SSD 드라이브입니다. 추가 요금 없이 인스턴스 비용에 기본 포함되어 있습니다.[8]

호스트 및 인스턴스 이벤트인스턴스 스토어 데이터 보존 여부
OS 소프트웨어 재부팅 (Reboot)데이터 안전하게 유지됨

인스턴스 유형 변경 (Resize)다른 물리 호스트로 이동하므로 데이터 영구 소멸됨
기반 하드웨어 물리 디스크 고장해당 디스크의 데이터 영구 소멸됨

인스턴스 스토어는 인스턴스를 처음 시작할 때만 매핑할 수 있으며, 실행 중에 떼어내어 다른 인스턴스에 붙일 수 없습니다.[9] 따라서 인스턴스 스토어는 데이터가 날아가도 비즈니스에 아무런 영향이 없는 버퍼, 캐시, 스크래치 연산 공간이나 소프트웨어 계층에서 여러 노드에 복제본을 유지하는 빅데이터 분산 클러스터(Hadoop/HDFS 임시 디스크)에만 사용해야 합니다.

파일 스토리지: EFS와 FSx 제품군 완벽 비교

Amazon EFS (Elastic File System)

  • 완전관리형, 서버리스, 완전 탄력적 파일 시스템으로 용량을 미리 프로비저닝할 필요 없이 데이터를 저장하는 만큼만 자동으로 기가바이트(GB)에서 페타바이트(PB)까지 늘어나고 줄어듭니다.[10]
  • NFS (v4.0 / v4.1) 프로토콜을 사용하며 POSIX 표준 파일 시스템 권한을 지원합니다. EC2 인스턴스뿐만 아니라 ECS 컨테이너, EKS 파드, AWS Lambda 함수에서도 마운트할 수 있습니다. (주의: Windows 인스턴스는 지원하지 않으며 Linux 전용입니다!)[10]
  • Regional 배포 (기본 및 강력 권장): 리전 내 여러 가용 영역(AZ)에 걸쳐 데이터를 분산 저장하므로 단일 AZ 전체 장애에도 데이터 무결성과 접근성을 유지합니다. 각 AZ마다 마운트 타깃(Mount Target)을 생성하여 여러 AZ의 수천 대 인스턴스가 동시에 공유 마운트할 수 있으며, Direct Connect나 VPN을 통해 연결된 온프레미스 Linux 서버에서도 마운트 가능합니다.[11]
  • 스토리지 계층: 자주 접근하는 활성 파일을 위한 Standard 티어, 분기에 몇 번 열어보는 파일을 위한 Infrequent Access(IA) 티어, 1년에 몇 번 열어보는 Archive 티어로 구성되며 수명 주기 관리를 통해 자동으로 비용을 절감합니다.[12]

Linux, Windows, macOS 모두 지원		온프레미스 NetApp 스토리지 마이그레이션, NetApp SnapMirror 복제 도구 사용, 블록(iSCSI LUN)과 파일(NFS/SMB)을 단일 스토리지에서 동시에 제공하는 진정한 멀티 프로토콜. 데이터 중복 제거 및 지능형 자동 계층화.[15]
FSx for OpenZFSNFS (v3 ~ v4.2)
Linux, Windows, macOS 지원		온프레미스 ZFS 기반 Linux 파일 서버를 애플리케이션 코드나 설정 변경 없이 AWS로 이전. 백만 IOPS와 밀리초 미만 지연 시간, 즉각적인 ZFS 스냅샷 및 무용량 데이터 클로닝.[16]

시험에 자주 나오는 핵심 패턴

  • "gp2 볼륨을 사용 중인데 비용을 절감하거나 IOPS 확보를 위해 볼륨 크기를 억지로 키우는 중" → gp3 볼륨으로 무중단 전환 (기본 3,000 IOPS 제공, GiB당 20% 저렴).
  • "수십만 IOPS, 0.5ms 미만의 극초저지연, 대규모 미션 크리티컬 RDBMS" → io2 Block Express.
  • "빅데이터 EMR 분석이나 로그 스트리밍, 대용량 순차 I/O, 저비용" → st1 (처리량 최적화 HDD).
  • "거의 읽지 않는 콜드 데이터 순차 처리, 블록 스토리지 최저가" → sc1 (콜드 HDD).
  • "OS 부팅용 루트 볼륨으로 HDD(st1/sc1) 선택" → 오답 (HDD는 부팅 디스크 불가, SSD만 가능).
  • "임시 캐시, 스크래치 연산 공간, 최고 성능, 인스턴스 중지 시 데이터 소멸 감내" → EC2 인스턴스 스토어 (Instance Store).
  • "한 AZ의 EBS 볼륨 데이터를 다른 AZ의 EC2 인스턴스로 전달" → 스냅샷 생성 후 대상 AZ에서 새 볼륨으로 복원.
  • "여러 AZ에 걸친 수천 대의 Linux 웹 서버가 공유 디렉터리를 마운트" → Amazon EFS (Regional).
  • "Windows 환경, SMB 프로토콜, Microsoft Active Directory 통합 및 NTFS 권한" → FSx for Windows File Server.
  • "머신러닝/HPC 학습, S3 버킷에 저장된 수백 TB 데이터셋을 고속 파일로 읽고 결과 기록" → FSx for Lustre (S3 데이터 리포지토리 연동).
  • "온프레미스 NetApp 이전, SnapMirror 복제, NFS와 SMB 및 iSCSI 동시 지원" → FSx for NetApp ONTAP.

실전 연습: 직접 풀어보세요

문제마다 "몇 대가 마운트하는가?", "어떤 OS/프로토콜인가?", "IOPS인가 처리량인가?"를 메모하며 최적의 스토리지를 판정해 보세요.

Q1. 200GiB 크기의 gp2 EBS 볼륨을 사용하는 관계형 데이터베이스가 있습니다. 트래픽 피크 시간대마다 EBS의 BurstBalance 지표가 바닥나면서 심각한 데이터베이스 응답 지연이 발생합니다. 시스템 관리자는 상시 안정적으로 3,000 IOPS를 확보하면서도 월간 스토리지 비용을 현재보다 오히려 줄이거나 최소화하고자 합니다. 가장 적절한 조치는 무엇입니까?

200GiB 크기의 gp2 볼륨은 기준 성능이 600 IOPS(200 × 3)에 불과하며, 3,000 IOPS는 I/O 크레딧이 남아있을 때만 일시적으로 버스트됩니다. 반면 gp3는 볼륨 크기와 무관하게 3,000 IOPS와 125 MiB/s를 기본 무료로 제공하며, GiB당 요금도 gp2보다 20% 저렴합니다. 또한 Elastic Volumes 기능을 통해 인스턴스 재부팅 없이 실시간으로 변경 가능합니다. gp2를 1TiB로 늘리면 3,000 IOPS는 나오지만 사용하지 않는 800GiB 용량에 대한 비용이 낭비되며, io2는 이 요구사항에 비해 지나치게 비쌉니다. st1은 작은 랜덤 I/O를 수행하는 트랜잭션 DB에 적합하지 않습니다.

Q2. 매일 밤 수 테라바이트(TB) 크기의 웹 애플리케이션 로그 파일을 대용량 순차(Sequential) 블록 단위로 읽어 집계하는 배치 분석 작업이 EC2 인스턴스에서 실행됩니다. 이 작업은 높은 대역폭 처리량(Throughput)이 핵심이며 임의 I/O 속도(IOPS)는 중요하지 않습니다. 데이터는 매일 규칙적으로 읽힙니다. 가장 비용 효율적인 EBS 볼륨 유형은 무엇입니까?

대용량 순차 읽기/쓰기 처리량 중심의 빅데이터 및 로그 분석 작업에는 st1 (처리량 최적화 HDD)이 가장 적합합니다. sc1이 GiB당 비용은 더 저렴해 보이지만, sc1의 공식 설계 용도는 "자주 접근하지 않는(Infrequently accessed) 콜드 데이터"이며 최대 처리량도 st1의 절반(250 MiB/s)에 불과합니다. 매일 규칙적으로 대량의 로그를 처리해야 하므로 최대 500 MiB/s를 제공하는 st1이 올바른 정답입니다. SSD 유형(gp3, io1)은 순차 처리량 작업에 쓰기에는 불필요하게 비싼 IOPS 비용을 지불하는 셈입니다.

Q3. 3개의 가용 영역(AZ)에 걸쳐 배포된 Auto Scaling 그룹 내부의 Linux 기반 웹 서버들이 사용자가 업로드한 문서 파일을 동일한 디렉터리 경로에서 실시간으로 공유하여 읽고 쓸 수 있어야 합니다. 특정 AZ 하나에 재해가 발생해도 다른 AZ의 서버들이 파일에 계속 접근할 수 있어야 하며, 스토리지 용량 부족을 관리자가 수동으로 증설하고 싶지 않습니다. 가장 적합한 아키텍처는 무엇입니까?

"여러 AZ의 다수 Linux 서버가 공유 마운트 + 다중 AZ 고가용성 + 자동 용량 확장(서버리스)"을 완벽히 만족하는 서비스는 Amazon EFS (Regional)입니다. Multi-Attach EBS는 단일 AZ 내부에서만 작동하므로 다중 AZ 고가용성을 보장하지 못합니다. 인스턴스 스토어는 인스턴스 중지 시 데이터가 영구 소멸되는 치명적인 위험이 있으며, AZ마다 따로 생성한 EBS 볼륨은 독립된 디스크이므로 파일이 공유되지 않습니다.

Q4. 한 기업이 온프레미스 데이터센터에서 실행 중이던 대규모 레거시 Windows 파일 서버를 AWS로 이전하려 합니다. 기존 Windows 클라이언트들은 SMB 프로토콜을 통해 접속하고 있으며, 기존 사내 Microsoft Active Directory 도메인 인증 및 세부적인 NTFS 파일 접근 권한(ACL)을 수정 없이 그대로 유지해야 합니다. 또한 운영팀은 하드웨어 관리 부담이 없는 완전관리형 서비스를 원합니다. 무엇을 선택해야 합니까?

"Windows 파일 공유 + SMB 프로토콜 + Active Directory(AD) 도메인 통합 + NTFS 권한"을 완벽히 지원하는 완전관리형 서비스는 Amazon FSx for Windows File Server입니다. Amazon EFS는 Linux 전용 NFS 서비스로 Windows 인스턴스 마운트를 지원하지 않습니다. FSx for Lustre는 Linux HPC 머신러닝용입니다. EC2에 직접 Windows 공유를 띄우는 것은 가능하지만 패치, 백업, HA 구성을 직접 관리해야 하므로 "완전관리형 서비스"라는 요구조건을 충족하지 못합니다.

Q5. 인공지능 연구팀이 Amazon S3 버킷에 저장된 수백 테라바이트(TB) 분량의 이미지 데이터셋을 활용하여 수천 대의 분산 Linux GPU 컴퓨팅 노드에서 머신러닝 모델 학습을 수행하려 합니다. 학습 중에는 밀리초 미만의 극초저지연과 수백 GB/s 수준의 초고속 처리량이 필요하며, 학습이 완료되면 생성된 체크포인트 파일과 분석 결과가 S3 버킷에 자동으로 다시 저장되어야 합니다. 가장 적합한 스토리지는 무엇입니까?

"HPC/머신러닝 학습 + 밀리초 미만 지연과 수백 GB/s 처리량 + S3 버킷과의 자동 양방향 연동"은 FSx for Lustre의 독보적인 고유 기능입니다. FSx for Lustre를 S3 버킷과 연결하면 S3 객체들을 파일 시스템의 파일로 즉시 투명하게 마운트하여 초고속으로 학습을 수행하고, 연산 결과 파일을 다시 S3로 원활하게 동기화해 줍니다. EFS나 ONTAP은 대규모 분산 GPU 노드가 요구하는 수준의 HPC 병렬 I/O 대역폭을 감당하기에 부적합합니다.

Q6. EC2 인스턴스 스토어(Instance Store) 볼륨의 데이터 지속성(Persistence) 및 동작 특성에 대해 올바른 설명 2가지를 고르세요.

정답은 첫 번째(재부팅 시 데이터 유지)와 세 번째(인스턴스 중지 시 데이터 소멸)입니다.
① 인스턴스 스토어는 호스트 서버의 물리적 NVMe 드라이브에 매핑되어 있으므로, 동일 물리 호스트 내에서 일어나는 소프트웨어 재부팅(Reboot) 시에는 데이터가 안전하게 보존됩니다.
② 하지만 인스턴스를 중지(Stop), 최대 절전(Hibernate), 종료(Terminate)하거나 인스턴스 유형을 변경하면 다른 물리 서버로 마이그레이션되므로 기존 물리 디스크의 모든 데이터가 암호학적으로 즉시 소멸됩니다.
(인스턴스 스토어는 분리하여 다른 서버에 붙일 수 없으며, AWS가 스냅샷을 자동으로 생성해 주지도 않습니다.)

Q7. us-east-1a 가용 영역에 위치한 EC2 웹 서버에 연결되어 있던 중요한 EBS 데이터 볼륨이 있습니다. 비즈니스 연속성을 위해 us-east-1b 가용 영역에 새로 생성한 대기 인스턴스에서 이 볼륨의 데이터를 그대로 활용하여 서비스를 시작해야 합니다. 가장 올바르고 신속한 절차는 무엇입니까?

EBS 볼륨은 특정 가용 영역(AZ)에 묶여 있으므로 다른 AZ의 인스턴스에는 직접 마운트할 수 없습니다. 하지만 EBS 스냅샷은 리전 전체의 모든 AZ에 공유되므로, 기존 볼륨의 스냅샷을 생성한 뒤 대상 가용 영역인 us-east-1b를 지정하여 새로운 EBS 볼륨으로 복원하고 새 인스턴스에 연결하면 됩니다. Multi-Attach 역시 동일한 AZ 내부에서만 지원되며, 볼륨 유형을 바꾼다고 해서 AZ 종속성이 사라지지는 않습니다.

Q8. 온프레미스 데이터센터에서 NetApp 스토리지를 사용하고 있는 기업이 있습니다. 현재 Linux 서버는 NFS, Windows 서버는 SMB를 사용해 데이터를 공유하며, 데이터베이스 서버는 iSCSI LUN 블록 장치를 마운트하여 사용 중입니다. 이 복합 환경을 기존 운영 방식과 클라이언트 설정을 최대한 바꾸지 않고 AWS 완전관리형 서비스로 이전하고자 합니다. 가장 적합한 것은 무엇입니까?

"온프레미스 NetApp 스토리지 마이그레이션 + NFS, SMB, iSCSI LUN을 단일 스토리지에서 동시 지원하는 멀티 프로토콜" 요구사항은 Amazon FSx for NetApp ONTAP의 완벽한 사용 사례입니다. NetApp의 SnapMirror 기술을 이용해 온프레미스 데이터를 AWS로 손쉽게 복제 이전할 수 있습니다. FSx for Windows는 SMB만 지원하고, EFS와 OpenZFS는 NFS 중심이라 iSCSI 블록 디바이스 마운트를 지원하지 못합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 다음 3가지 핵심 질문에 대한 답을 머릿속에서 인출하여 직접 적어보세요.
(1) EBS 6가지 볼륨 유형을 SSD와 HDD로 나누고, 각각의 대표 용도와 부팅 디스크 지원 여부를 적어보세요.
(2) gp3가 구세대 gp2에 비해 비용과 성능 아키텍처 측면에서 혁신적으로 개선된 점 2가지는 무엇인가요?
(3) EFS와 FSx 제품군 4종류(Windows, Lustre, ONTAP, OpenZFS)를 핵심 프로토콜과 결정적 사용 키워드로 각각 요약해 보세요.

(1) EBS 볼륨 유형별 특성:
- SSD 계열 (부팅 가능):
• gp3: 범용 최신 표준, 기본 3,000 IOPS 제공, IOPS/처리량 독립 증설, gp2 대비 20% 저렴.
• gp2: 구세대 범용, 크기 비례 성능(GiB당 3 IOPS), 크레딧 버스트 방식.
• io2 Block Express: 최고 성능(256,000 IOPS, 0.5ms 미만 지연), 99.999% 내구성, 미션 크리티컬 대형 RDBMS.
• io1: 16,000 IOPS 초과 I/O 집약 DB.
- HDD 계열 (부팅 불가!):
• st1: 빅데이터/로그 집계 등 대용량 순차 처리량(Throughput) 중심.
• sc1: 접근 빈도가 낮은 콜드 데이터 순차 처리, 블록 스토리지 최저가.

(2) gp3가 gp2보다 나은 결정적 이유:
① 용량과 성능의 완전한 분리: 크기와 상관없이 기본 3,000 IOPS / 125 MiB/s 무료 포함. 용량 증설 없이 IOPS/처리량만 독립 추가 가능하여 낭비가 없음.
② 비용 절감: GiB당 저장 요금이 gp2보다 20% 저렴하며, 중단 없이 Elastic Volumes로 실시간 전환 가능.

(3) EFS 및 FSx 4종 핵심 요약:
- EFS: Linux, NFS, 서버리스 탄력 확장, Multi-AZ 공유 (Windows 미지원).
- FSx for Windows: Windows, SMB, Active Directory 연동, NTFS ACL.
- FSx for Lustre: Linux HPC/ML 딥러닝, POSIX, 초고속 병렬 처리, S3 버킷 양방향 연동.
- FSx for NetApp ONTAP: 온프레미스 NetApp 마이그레이션, NFS + SMB + iSCSI 멀티 프로토콜, SnapMirror.
- FSx for OpenZFS: Linux ZFS 파일 서버 이전, 즉각적 ZFS 스냅샷 및 클로닝.

추가 학습 및 실습

1차 공식 문서 정독 (권장, 약 10분): AWS EBS 사용 설명서의 "Amazon EBS volume types"와 AWS 스토리지 가이드의 "Choosing an AWS storage service"를 꼭 읽어보세요. 다양한 워크로드 환경에서 스토리지를 결정하는 의사결정 매트릭스가 시험 문제의 출제 기준 그 자체입니다. (한국어 번역본은 URL의 docs.aws.amazon.com/ 뒤에 ko_kr/을 넣어 확인 가능합니다.)

콘솔 실습 안내 (선택 사항, 소액 과금 주의): 실행 중인 프리티어 EC2 인스턴스의 EBS 루트 볼륨을 콘솔에서 선택한 뒤 "작업(Actions) → 볼륨 수정(Modify Volume)"으로 들어가 gp2에서 gp3로 무중단 유형 변경을 테스트해 보세요. 또한 테스트용 볼륨의 스냅샷을 생성한 뒤 다른 가용 영역(AZ)을 지정하여 새 볼륨으로 복원해 보면, 가용 영역 간 데이터 마이그레이션 원리가 명확히 체감됩니다. (실습 종료 후 생성된 스냅샷과 추가 볼륨은 반드시 삭제하세요.)

궁금한 점이 있으신가요?

8문항 퀴즈를 풀면서 헷갈렸거나 오답을 골랐던 문제가 있다면 언제든 편하게 질문해 주세요. 특히 Q1(gp2의 버스트 한계와 gp3의 독립 성능 모델)과 Q5(FSx for Lustre와 S3의 결합)는 SAA-C03 시험뿐만 아니라 실무 아키텍처 설계에서도 가장 자주 쓰이는 핵심 기법입니다.
