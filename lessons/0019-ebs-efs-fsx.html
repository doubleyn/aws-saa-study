블록 · 파일 · 객체:
EBS 볼륨 유형, 인스턴스 스토어, EFS, FSx

"어떤 스토리지를 써야 하나?" 문제는 세 질문으로 끝납니다. 몇 대가 동시에 붙는가, 어떤 OS·프로토콜인가, IOPS와 처리량 중 무엇이 중요한가. 오늘은 이 세 질문으로 EBS 볼륨 유형과 파일 서비스 다섯 가지를 가려냅니다.

왜 이것부터인가

시험에서: Task 3.1(고성능 스토리지 선택)과 4.1(비용 효율 스토리지)이 "gp2 → gp3", "Windows + SMB → FSx for Windows", "HPC → FSx for Lustre" 같은 짝짓기로 자주 나옵니다.
실무에서: EBS가 AZ에 묶인다는 사실을 모르면 DR 설계가 무너지고, 인스턴스 스토어에 중요한 데이터를 두면 인스턴스를 중지하는 순간 사라집니다.

EBS: AZ에 묶인 블록 볼륨

EBS 볼륨은 인스턴스 수명과 무관하게 유지되는 블록 장치이며, 볼륨과 인스턴스가 같은 AZ에 있어야 연결할 수 있습니다. 운영 중에도 크기·IOPS·볼륨 유형을 바꿀 수 있습니다(Elastic Volumes).[2]

유형매체최대 IOPS최대 처리량쓰임부팅
gp3SSD80,0002,000 MiB/s대부분의 워크로드, 부팅, 중간 규모 DB, 개발·테스트가능
gp2SSD16,000250 MiB/s위와 같음(이전 세대)가능

[3] SSD는 작은 I/O가 잦은 트랜잭션(IOPS 중심), HDD는 큰 순차 스트리밍(처리량 중심)에 맞춥니다. 내구성은 io2 Block Express만 99.999%이고 나머지는 99.8–99.9%입니다.[3]

gp3 vs gp2: 시험이 가장 좋아하는 비교

  • gp3: 크기와 무관하게 기본 3,000 IOPS · 125 MiB/s가 가격에 포함되고, IOPS·처리량을 크기와 따로 추가할 수 있습니다. 버스트 방식이 아니라 프로비저닝한 성능을 계속 유지합니다. GiB당 가격이 gp2보다 20% 낮습니다.[4]
  • gp2: 성능이 크기에 비례합니다(GiB당 3 IOPS, 최소 100). 1TiB 미만 볼륨은 I/O 크레딧으로 3,000 IOPS까지 버스트합니다. 그래서 "IOPS가 부족해 크기를 키우는" 낭비가 생깁니다.[4]
  • gp2 → gp3 전환은 Elastic Volumes로 인스턴스 중단 없이 할 수 있습니다.[4]

Multi-Attach

Provisioned IOPS(io1·io2) 볼륨만, 같은 AZ의 Nitro 기반 인스턴스 최대 16대에 동시에 붙일 수 있습니다. XFS·EXT4 같은 일반 파일 시스템은 동시 접근용이 아니므로 클러스터 파일 시스템이 필요하고, 부팅 볼륨으로는 쓸 수 없습니다.[5] 즉 "여러 서버가 파일을 공유"하는 일반적인 요구의 답은 Multi-Attach가 아니라 EFS·FSx입니다.

스냅숏

  • 증분 백업: 마지막 스냅숏 이후 바뀐 블록만 저장합니다. 사용자가 직접 볼 수 없는 S3 버킷에 저장됩니다.[6]
  • 스냅숏 데이터는 리전의 모든 AZ에 복제되므로 같은 리전의 어느 AZ에서나 볼륨을 복원할 수 있습니다. EBS 볼륨을 다른 AZ로 "옮기는" 방법이 바로 이것입니다.[6]
  • AWS는 EBS를 자동 백업하지 않습니다. Amazon Data Lifecycle Manager나 AWS Backup으로 자동화합니다.[6]
  • Fast Snapshot Restore: 복원한 볼륨이 생성 즉시 완전히 초기화되어 첫 접근 지연 없이 프로비저닝 성능을 냅니다. 스냅숏·AZ 조합마다 켜고 시간당 과금됩니다.[7]

인스턴스 스토어: 빠르지만 임시

호스트 컴퓨터에 물리적으로 붙은 디스크로, 추가 요금 없이 인스턴스 가격에 포함됩니다. 버퍼, 캐시, 스크래치 데이터, 여러 인스턴스에 복제해 두는 임시 데이터에 적합합니다.[8]

파일 스토리지: EFS와 FSx 네 형제

Amazon EFS

  • 서버리스·완전 탄력형 NFS(v4.0/v4.1) 파일 시스템. EC2, ECS, EKS, Lambda, Fargate에서 마운트합니다. Windows 인스턴스는 지원하지 않습니다.[10]
  • Regional(권장): 여러 AZ에 중복 저장, AZ 장애에도 계속 사용. One Zone: 한 AZ에만 저장해 AZ 손실 시 데이터를 잃을 수 있음.[10]
  • AZ마다 마운트 타깃을 하나씩 만들고, 여러 AZ의 인스턴스가 동시에 같은 파일 시스템을 씁니다. Direct Connect나 Site-to-Site VPN으로 연결된 온프레미스 Linux 서버에서도 마운트할 수 있습니다.[11]
  • 스토리지 클래스: Standard(활성 데이터, 밀리초 미만) · Infrequent Access(분기에 몇 번) · Archive(1년에 몇 번 이하, 최소 보관 90일, Elastic 처리량 필요). 수명 주기 관리가 접근 없는 파일을 자동으로 내립니다.[12]

FSx for Windows File ServerSMB, Windows(최신 Linux에서도 접근 가능)Windows 앱 리프트 앤 시프트, Active Directory 인증, Windows ACL, 홈 디렉터리. Single-AZ / Multi-AZ(다른 AZ에 대기 파일 서버)[13]

AWS 선택 가이드는 FSx를 "이미 쓰고 있는 파일 시스템에 맞춰 고르라"고 정리합니다. 혼합(Linux + Windows) 환경에서 같은 데이터에 NFS와 SMB로 동시에 접근해야 하면 ONTAP입니다.[1]

시험 단골: 키워드 → 답

gp2를 더 싸게 / IOPS 때문에 크기를 키우는 중 → gp3 · 수십만 IOPS, 밀리초 미만 → io2 Block Express · 로그·빅데이터 순차 처리, 저렴 → st1 · 거의 안 읽는 콜드 데이터, 최저가 블록 → sc1 · 부팅 볼륨 → HDD(st1·sc1)는 탈락.

임시 캐시·스크래치, 최고 성능, 사라져도 됨 → 인스턴스 스토어 · 다른 AZ에서 같은 데이터 → 스냅숏 후 그 AZ에서 복원 · 여러 AZ의 Linux가 공유 → EFS · Windows + SMB + AD → FSx for Windows · HPC·ML + S3 데이터셋 → FSx for Lustre · NetApp·iSCSI·NFS+SMB 동시 → FSx for NetApp ONTAP · ZFS 이전 → FSx for OpenZFS.

연습

기억으로 푸세요. 각 문제에서 "몇 대 · OS·프로토콜 · IOPS냐 처리량이냐"부터 표시해 보세요.

Q1. 200GiB gp2 볼륨을 쓰는 DB가 피크 때 BurstBalance가 바닥나 느려집니다. 안정적으로 3,000 IOPS가 필요하고, 비용은 지금보다 늘리고 싶지 않습니다. 가장 적절한 조치는?

200GiB gp2의 기준 성능은 600 IOPS이고, 3,000 IOPS는 크레딧이 있을 때만 버스트됩니다. gp3는 크기와 무관하게 3,000 IOPS를 기본 제공하고 GiB당 가격도 20% 낮으며, Elastic Volumes로 중단 없이 바꿀 수 있습니다. 1TiB로 키우면 3,000 IOPS 기준선은 얻지만 쓰지 않는 용량 비용을 냅니다. io2는 이 요구에 과하고, st1은 작은 랜덤 I/O의 DB에 맞지 않습니다.

Q2. 매일 수 TB의 로그를 큰 블록 단위로 순차 읽어 집계하는 EC2 배치 작업이 있습니다. 처리량이 중요하고 IOPS는 중요하지 않으며, 데이터는 매일 읽힙니다. 가장 비용 효율적인 EBS 유형은?

빅데이터·로그 처리, 순차 처리량 중심이면 st1입니다. sc1이 더 싸 보이지만 AWS가 정한 용도는 "자주 접근하지 않는" 처리량 데이터이고 최대 처리량도 st1의 절반(250 MiB/s)입니다. 매일 읽는 작업에는 st1이 맞습니다. SSD 유형은 IOPS에 돈을 내는 셈입니다.

Q3. 세 AZ에 걸친 Auto Scaling 그룹의 Linux 웹 서버들이 사용자 업로드 파일을 같은 디렉터리에서 읽고 써야 합니다. 한 AZ가 장애 나도 파일에 접근할 수 있어야 하고, 용량 관리는 하고 싶지 않습니다.

여러 AZ의 Linux가 공유 + 용량 관리 없음 = EFS(Regional)입니다. Multi-Attach는 같은 AZ 안에서만 되고 클러스터 파일 시스템이 필요합니다. 인스턴스 스토어는 인스턴스를 중지·종료하면 사라지고, AZ마다 따로 붙인 EBS는 서로 다른 디스크라 공유가 아닙니다.

Q4. 온프레미스 Windows 파일 서버를 AWS로 옮깁니다. 사용자는 SMB로 접근하고, 기존 Active Directory 계정과 NTFS 권한을 그대로 써야 하며, 관리형 서비스를 원합니다.

SMB + AD + Windows ACL + 관리형 = FSx for Windows File Server입니다. EFS는 Windows 인스턴스를 지원하지 않는 NFS이고, Lustre는 Linux HPC용입니다. EC2에 공유 폴더를 직접 만들면 동작은 하지만 패치·백업·장애 대응을 직접 해야 하므로 "관리형" 요구를 어깁니다.

Q5. 연구팀이 S3에 있는 수백 TB 데이터셋으로 수천 개 Linux 노드에서 ML 학습을 돌립니다. 학습 중에는 밀리초 미만 지연과 매우 높은 처리량이 필요하고, 결과는 다시 S3에 남겨야 합니다.

HPC·ML + S3 데이터셋 + 결과를 S3로 = FSx for Lustre(S3 연결)입니다. S3 객체를 파일로 보여 주고 결과를 S3로 다시 쓸 수 있습니다. EFS도 공유는 되지만 이 정도 HPC 처리량 요구의 대표 답이 아니고, ONTAP은 엔터프라이즈 멀티 프로토콜 NAS입니다. Express One Zone은 객체 API라 "파일 시스템으로 학습" 요구와 다릅니다.

Q6. EC2 인스턴스 스토어에 대해 옳은 것은? (두 개를 고르세요)

재부팅은 유지, 중지·최대 절전·종료는 소멸입니다. 인스턴스 스토어는 시작 시에만 붙고 다른 인스턴스로 옮길 수 없습니다. 자동 백업도 없습니다(EBS조차 AWS가 자동으로 백업하지 않습니다). 그래서 캐시·스크래치·복제된 임시 데이터에만 씁니다.

Q7. (0016 복습) us-east-1a의 인스턴스가 쓰던 EBS 데이터 볼륨을, 장애 대비로 us-east-1b에 새로 띄운 인스턴스에서 써야 합니다. 올바른 방법은?

EBS 볼륨은 AZ에 묶이고 같은 AZ의 인스턴스에만 붙습니다. 스냅숏은 리전의 모든 AZ에 복제되므로 1b에서 새 볼륨으로 복원하면 됩니다. Multi-Attach도 같은 AZ 안에서만 되고, 볼륨 유형은 AZ 제약과 관계없습니다. AZ는 독립된 장애 단위라는 0016의 내용이 여기서 설계 제약으로 나타납니다.

Q8. 온프레미스 NetApp 스토리지에서 Linux 앱은 NFS, Windows 앱은 SMB, DB 서버는 iSCSI LUN을 씁니다. 운영 방식을 크게 바꾸지 않고 관리형 서비스로 옮기려 합니다.

NFS + SMB + iSCSI 멀티 프로토콜, 그리고 "NetApp"이라는 단어가 곧 FSx for NetApp ONTAP입니다. SnapMirror로 직접 이전 경로도 있습니다. FSx for Windows는 SMB, EFS와 OpenZFS는 NFS 중심이라 iSCSI LUN 요구를 만족하지 못합니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) EBS 여섯 유형을 SSD/HDD로 나누고, 각각 한 줄 용도와 부팅 가능 여부를. (2) gp3와 gp2의 성능 모델 차이. (3) EFS와 FSx 네 종류를 "프로토콜 · 결정적 키워드"로.

(1) SSD: gp3(대부분, 기본 선택), gp2(이전 세대), io2 Block Express(최고 IOPS, 밀리초 미만), io1(16,000 IOPS 초과 DB). HDD: st1(빅데이터·로그 순차 처리), sc1(콜드, 최저가). HDD 두 개는 부팅 불가. Multi-Attach는 io1·io2만.

(2) gp3: 크기와 무관하게 3,000 IOPS · 125 MiB/s 기본, IOPS·처리량 별도 추가, GiB당 20% 저렴. gp2: GiB당 3 IOPS로 크기에 비례, 1TiB 미만은 크레딧으로 3,000까지 버스트.

(3) EFS: NFS, Linux, 서버리스, 여러 AZ. FSx for Windows: SMB, AD. Lustre: HPC·ML, S3 연결. ONTAP: NFS·SMB·iSCSI 멀티 프로토콜, NetApp. OpenZFS: NFS, ZFS·Linux 파일 서버 이전.
