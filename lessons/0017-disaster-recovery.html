RPO/RTO와 DR 전략 네 가지

레슨 0016에서 단일 가용 영역(AZ) 장애를 극복하는 다중 AZ 설계를 배웠다면, 이번 레슨에서는 리전(Region) 전체가 물리적으로 마비되거나 데이터가 광범위하게 손상되는 대재앙에 대비하는 재해 복구(Disaster Recovery, DR) 전략을 다룹니다. AWS 공식 백서 기준의 4가지 DR 모델(백업 및 복원, 파일럿 라이트, 웜 스탠바이, 다중 사이트 액티브-액티브)의 비용과 복구 속도 트레이드오프를 완벽히 정리하고, 비즈니스 목표에 맞는 가장 경제적인 아키텍처를 도출해 냅니다.

왜 재해 복구(DR) 전략을 배워야 할까요?

시험 관점에서: SAA-C03 시험 문제 지문에 구체적인 시간 수치(예: "RPO 15분 이내, RTO 2시간 이내")와 함께 "가장 비용 효율적인(most cost-effective) 솔루션"이라는 표현이 나오면 십중팔구 4가지 DR 전략 중 하나를 선택하는 문제입니다. 무조건 복구가 빠른 고가의 솔루션을 고르는 것이 아니라, 제시된 RPO·RTO 목표를 충족하는 가장 저렴한 전략을 정확히 집어내는 것이 합격의 열쇠입니다.[2]

실무 관점에서: 재해 복구 목표는 엔지니어링 팀이 임의로 정하는 기술적 희망사항이 아니라, 회사의 비즈니스 영향 분석(BIA)과 업무 연속성 계획(BCP)에 따라 결정되는 경영 지표입니다. 무조건 "다운타임 0초, 데이터 손실 0바이트"를 외치면 매달 수억 원의 유휴 인프라 비용이 낭비됩니다. 반대로 비용만 아끼려다 복구에 며칠이 걸리면 회사가 존폐 위기에 처할 수 있습니다. 비즈니스가 감내할 수 있는 데이터 손실량과 다운타임을 정확한 클라우드 아키텍처 비용으로 환산해 내는 능력이 바로 솔루션즈 아키텍트의 핵심 가치입니다.[1]

RPO와 RTO: 재해 복구의 양대 핵심 지표

재해 복구 계획을 수립할 때 가장 먼저 정의해야 하는 두 가지 절대적인 기준이 바로 RPO(복구 시점 목표)와 RTO(복구 시간 목표)입니다.[1]

구분RPO (Recovery Point Objective, 복구 시점 목표)RTO (Recovery Time Objective, 복구 시간 목표)
공식 정의마지막 정상 데이터 복구 지점 이후 재해 발생까지 허용 가능한 최대 시간. 즉 허용 가능한 데이터 손실량을 의미합니다.[1]재해가 선언된 시점부터 서비스가 복원되어 정상 트래픽을 처리하기까지 허용 가능한 최대 지연 시간. 즉 허용 가능한 다운타임을 의미합니다.[1]
핵심 질문"데이터를 최대 몇 분(또는 몇 시간) 분량까지 잃어버려도 비즈니스가 감내할 수 있는가?""서비스가 중단된 후 최대 몇 분(또는 몇 시간) 안에 다시 정상 가동되어야 하는가?"
결정 요소백업 주기 및 데이터 복제(Replication)의 빈도에 의해 결정됩니다. (예: 1일 1회 백업이면 RPO는 최대 24시간, 실시간 연속 복제면 RPO는 수 초~수 분)복구 절차의 자동화 수준 및 대기 리전 인프라의 가동 상태에 의해 결정됩니다. (예: 서버가 이미 켜져 있으면 RTO 수 분, 새 서버를 밑바닥부터 배포해야 하면 RTO 수 시간)

AWS DR 공식 백서는 "재해 복구 솔루션을 구축하고 유지하는 비용이 장애로 인한 잠재적 비즈니스 손실액보다 커서는 안 된다"는 비용 대비 효용의 원칙을 강조합니다.[1] 또한 동일 리전 내의 다중 AZ(Multi-AZ) 구성만으로도 일반적인 하드웨어 고장, 전력 장애, 국소적 침수 등 인프라 위험의 99% 이상을 방어할 수 있으므로, 리전 간 교차 복구는 지진·전쟁·대규모 광역 단전과 같은 극단적인 리전급 재난을 대비할 때 도입합니다.

클라우드 DR 전략 4가지 완벽 비교

AWS는 비용, 복잡성, 복구 속도에 따라 재해 복구 아키텍처를 다음 4가지 스펙트럼으로 분류합니다.[2]

전략DR 리전에 평소 무엇이 배포되어 있나?장애 발생 시 복구 절차아키텍처 특징 및 핵심 주의점
1. 백업 및 복원
(Backup & Restore)		컴퓨팅 서버 없음. EBS 스냅샷, RDS 스냅샷, S3 백업 데이터만 DR 리전으로 정기 복사해 둠.[2]CloudFormation/Terraform 같은 IaC를 실행해 VPC, 서브넷, 인스턴스 등 인프라 전체를 밑바닥부터 새로 생성하고 백업에서 데이터를 복원함.비용이 가장 저렴함 (평소 스토리지 백업 비용만 발생). 하지만 대용량 데이터 복원과 인프라 프로비저닝에 긴 시간이 걸려 RTO/RPO가 가장 긺(수 시간 ~ 수십 시간). 신속한 복원을 위해 IaC 템플릿과 골든 AMI 관리가 필수적임.
2. 파일럿 라이트
(Pilot Light)		가장 복구하기 어려운 핵심 데이터베이스(DB)와 스토리지 계층만 상시 가동하며 실시간 복제(Replication) 유지. 애플리케이션 서버는 완전히 꺼진 상태(Stopped)이거나 배포되지 않고 준비만 되어 있음.[2]복제 중이던 대기 DB를 마스터(읽기/쓰기)로 승격(Promote)시키고, 앱 서버를 켜거나 Auto Scaling으로 인스턴스를 빠르게 프로비저닝한 뒤 Route 53 트래픽을 전환함.가스레인지의 작은 불씨(Pilot Light)에서 유래한 명칭입니다. 실시간 복제로 RPO는 수 분 이내로 매우 짧지만, 앱 서버를 켜고 기동하는 시간이 필요하므로 추가 조치 없이는 즉각 트래픽을 처리하지 못함(RTO 수십 분).
3. 웜 스탠바이
(Warm Standby)		본 운영 환경과 완벽히 동일한 구성을 갖추되, 최소한의 축소된 용량(Scaled-down, 예: 본 서버 10대 대비 2대만 가동)으로 전체 스택이 상시 100% 정상 실행 중.[2]DNS를 전환하면 축소된 용량으로 즉시(Immediately) 트래픽을 수용하기 시작하며, 동시에 Auto Scaling이 발동하여 본래 운영 규모로 신속히 자동 확장(Scale-out)함.서버가 이미 켜져 있으므로 RTO가 수 분 이내로 매우 짧음. 상시 동작하므로 주기적인 헬스체크와 테스트가 용이함. 파일럿 라이트보다 상시 가동 비용이 높음.
4. 다중 사이트 액티브-액티브
(Multi-site Active-Active)		2개 이상의 리전에 동일한 규모의 완전한 인프라가 상시 100% 가동되며, 전 세계 실제 사용자 트래픽을 동시에 분산 처리함.[2]'장애 복구'라는 별도 절차가 필요 없음. Route 53이나 Global Accelerator가 장애 리전으로의 유입만 차단하면 정상 리전이 트래픽을 계속 처리함.RTO와 RPO가 0에 수렴함(Near Zero). 하지만 리전 간 양방향 데이터 동기화, 충돌 해결 등 비용과 아키텍처 복잡성이 극도로 높음. 비즈니스 미션 크리티컬 워크로드에만 한정 적용.

파일럿 라이트 vs 웜 스탠바이의 결정적 차이 (시험 단골 함정!)

AWS 공식 백서에서도 이 두 전략의 경계가 시험이나 실무에서 가장 혼동하기 쉽다고 명시하고 있습니다.[2] 명확한 구분 기준은 다음과 같습니다.

  • 파일럿 라이트: 앱 서버가 평소에 꺼져 있으므로, 장애 발생 시 서버를 "켜고(Start/Deploy)" 준비가 끝날 때까지 기다려야 합니다. 즉, 즉시 요청을 처리할 수 없습니다.
  • 웜 스탠바이: 앱 서버가 이미 켜져서 돌고 있으므로, 장애 조치 즉시 "축소된 용량으로라도 요청을 즉각(Immediately) 처리하기 시작"하며 이후에 Auto Scaling으로 늘어납니다.
  • 참고로 대기 리전에 본 운영 환경의 전체 트래픽(100%)을 감당할 수 있는 대규모 인프라를 풀 사이즈로 켜둔 채 대기하는 구성을 핫 스탠바이(Hot Standby, Active-Passive)라고 부릅니다.

교차 리전 복제 패턴과 데이터 보호의 함정

재해 복구를 위한 데이터 복제 아키텍처를 설계할 때는 각 AWS 서비스의 교차 리전 복제 특성을 정확히 이해해야 합니다.[2]

  • 연속 비동기 복제 서비스 (낮은 RPO 달성):
    • S3 Cross-Region Replication (CRR): 버킷 간 객체 비동기 자동 복제.
    • RDS Cross-Region Read Replica: 비동기 읽기 전용 복제본. 장애 시 마스터로 승격(Promote)하는 데 수 분이 소요되며 DB 인스턴스 재부팅이 수반됩니다.
    • Aurora Global Database: 전용 스토리지 복제 계층을 통해 보조 리전으로 보통 1초 미만 지연으로 복제됩니다. 리전 전체 장애 시에도 보조 리전을 1분 이내에 완전한 읽기/쓰기 클러스터로 승격할 수 있어 금융권이나 엔터프라이즈의 핵심 DR 데이터베이스로 활용됩니다.
    • DynamoDB Global Tables, DocumentDB Global Clusters, ElastiCache Global Datastore 등.
  • "복제(Replication)는 백업(Backup)이 아닙니다" (절대적인 설계 원칙!):
    실시간 비동기 복제는 데이터센터의 하드웨어 고장이나 전원 단절 같은 '인프라 장애'는 완벽히 방어하지만, '데이터 자체의 재해'는 방어하지 못합니다. 예를 들어 관리자가 실수로 중요한 테이블을 DROP TABLE하거나 애플리케이션 버그, 악성 랜섬웨어로 데이터가 오염되면, 그 오염된 상태가 1초도 안 되어 보조 DR 리전으로 그대로 복제되어 버립니다! 따라서 진정한 DR을 구현하려면 실시간 복제와 별개로 과거 특정 시점으로 롤백할 수 있는 특정 시점 복원(Point-in-Time Recovery, PITR) 백업 체계나 S3 버전 관리(Versioning)를 반드시 함께 갖추어야 합니다.[2]
  • 트래픽 전환의 데이터 플레인(Data Plane) 원칙:
    대규모 재난 상황에서 새로운 리소스를 생성하는 컨트롤 플레인 API 호출은 지연되거나 실패할 위험이 있습니다. 따라서 재해 시 트래픽을 보조 리전으로 전환할 때는 Route 53 상태 확인 기반의 DNS 페일오버나 AWS Global Accelerator처럼 이미 전 세계 엣지 네트워크에 견고하게 구축된 데이터 플레인(Data Plane) 메커니즘을 사용해야 최고의 신뢰성을 보장받을 수 있습니다.[2]

DR 리전 확장 시 반드시 점검해야 할 두 가지: 서비스 할당량과 정기 훈련

파일럿 라이트나 웜 스탠바이 환경에서 장애가 발생하면 Auto Scaling이 DR 리전에서 수십~수백 대의 EC2 인스턴스를 급격히 증설하게 됩니다. 이때 가장 흔히 발생하는 비극이 바로 DR 리전의 EC2 vCPU 서비스 할당량(Service Quotas) 초과 오류입니다. AWS의 서비스 할당량은 계정 전체가 아니라 각 리전별로 독립 적용되므로, 평소에 사용량이 적은 DR 리전은 기본 할당량이 낮게 묶여 있을 수 있습니다. 따라서 DR 리전의 vCPU 및 탄력적 IP(EIP) 한도를 본 운영 리전 규모만큼 미리 상향 요청해 두어야 합니다.[2] 또한 실제 재해 상황에서 당황하지 않고 복구 절차가 매끄럽게 동작하려면, 모의 재해 훈련(DR GameDay)을 주기적으로 실시하여 확장 절차와 데이터 무결성을 검증해야 합니다.

AWS Backup: 엔터프라이즈 통합 백업 관리

AWS Backup은 클라우드 전반의 데이터를 중앙에서 정책 기반으로 자동 백업하고 규정 준수를 보장하는 완전관리형 백업 서비스입니다.[3]

핵심 기능상세 설명 및 아키텍처 역할
중앙 집중 관리EC2 인스턴스, EBS 볼륨, RDS/Aurora DB, DynamoDB, EFS 파일 시스템, FSx, S3 버킷 등 서로 다른 AWS 서비스의 백업을 개별 콘솔에 들어가지 않고 단일 대시보드에서 일괄 관리합니다.[3]
백업 계획 (Backup Plan)백업 주기(예: 매일 자정), 백업 실행 시간 창(Backup Window), 보존 기간(예: 30일 보관 후 삭제)을 정의한 정책입니다. 특정 리소스를 직접 지정하거나 태그(예: Environment=Production)를 기준으로 자동 할당할 수 있습니다.[5]
수명 주기 자동화자주 접근하는 웜 스토리지에 보관하다가 일정 기간이 지나면 비용이 훨씬 저렴한 콜드 스토리지로 백업 데이터를 자동 아카이브하여 스토리지 비용을 최적화합니다.[3]
교차 리전 및 교차 계정 복사백업 계획의 한 단계로 백업 복구 지점(Recovery Point)을 다른 DR 리전이나 다른 격리된 AWS 계정으로 자동 복사합니다. AWS Organizations와 연동하면 마스터 계정에서 조직 전체의 모든 계정에 백업 정책을 강제할 수 있습니다.[3]
AWS Backup Vault Lock
(WORM 스토리지)		백업이 저장되는 볼트(Vault)를 잠가 랜섬웨어나 악의적인 침입자가 백업을 영구 삭제하거나 보존 기간을 줄이는 행위를 원천 차단합니다.[4]
- 거버넌스 모드 (Governance Mode): 특정 권한(backup:DeleteRecoveryPoint 등)이 있는 관리자는 필요 시 백업을 삭제하거나 잠금을 해제할 수 있습니다 (유연한 내부 테스트용).
- 규정 준수 모드 (Compliance Mode): 설정 후 유예 기간(최소 3일)이 지나면, AWS 계정의 루트(Root) 사용자조차도, 심지어 AWS 고객지원팀도 보존 기간 만료 전에는 백업을 절대 변경하거나 삭제할 수 없습니다! 법적 컴플라이언스 준수 및 랜섬웨어 방어의 최종 병기입니다.

시험에 자주 나오는 핵심 패턴

  • "가장 비용 효율적인 솔루션", RPO와 RTO가 수 시간에서 하루 이상 허용됨 → 백업 및 복원 (Backup & Restore) (스냅샷 교차 리전 복사 + CloudFormation/IaC 재배포).
  • "DB는 실시간 복제하되 평소 앱 서버 비용은 최소화", "백업 및 복원보다 빠른 RTO 요구" → 파일럿 라이트 (Pilot Light).
  • "축소된 규모로 전체 시스템이 상시 실행", "장애 조치 즉시 트래픽을 수용하고 이후 확장" → 웜 스탠바이 (Warm Standby).
  • "다운타임과 데이터 손실이 거의 0이어야 함", "전 세계 사용자를 여러 리전에서 동시 서비스" → 다중 사이트 액티브-액티브 (Multi-site Active-Active).
  • "DR 모의 훈련 중 대기 리전에서 Auto Scaling 인스턴스 시작 실패" → DR 리전의 서비스 할당량(vCPU Quotas) 사전 상향 필요.
  • "랜섬웨어 공격이나 최고 관리자(루트) 계정 탈취 상황에서도 백업 삭제 방지" → AWS Backup Vault Lock (규정 준수 모드, Compliance Mode).
  • "관리자가 실수로 DB 테이블을 삭제했는데 DR 리전에도 삭제가 복제됨" → 복제와 별개로 특정 시점 복원(Point-in-Time Recovery) 백업 체계 구축 필요.

실전 연습: 직접 풀어보세요

각 문제에서 요구하는 비즈니스 지표(RPO, RTO, 비용 최적화, 보안)를 꼼꼼히 대조하며 최적의 아키텍처를 선택해 보세요.

Q1. 기업의 비즈니스 연속성 계획(BCP) 회의에서 다음과 같은 요구사항이 확정되었습니다: "시스템 장애가 발생하더라도 최근 15분 이내의 데이터만 유실된다면 비즈니스 운영상 감내할 수 있으며, 중단된 서비스는 최대 2시간 이내에 정상화되어야 한다." 이 요구사항을 클라우드 재해 복구(DR) 목표 지표로 정확하게 변환한 것은 무엇입니까?

잃어버려도 되는 최대 데이터 분량(마지막 복구 지점과의 시간 간격)을 나타내는 지표는 RPO(Recovery Point Objective)이므로 RPO = 15분입니다. 서비스 중단 후 복구될 때까지 허용되는 최대 지연 시간(다운타임)은 RTO(Recovery Time Objective)이므로 RTO = 2시간입니다. "Point"는 데이터가 어느 '시점'까지 보존되는가, "Time"은 서비스가 복구되기까지 걸리는 '시간'으로 암기하세요.

Q2. 한 회사의 사내 내부 보고서 시스템이 단일 AWS 리전에서 운영되고 있습니다. 리전 전체에 재해가 발생할 경우 최대 24시간 이내에만 복원되면 업무에 지장이 없으며, 몇 시간 분량의 데이터 손실도 비즈니스상 충분히 허용됩니다. 회사는 평상시 지출되는 재해 복구(DR) 인프라 비용을 절대적으로 최소화하고자 합니다. 가장 적합한 전략은 무엇입니까?

RPO와 RTO가 수 시간에서 24시간 수준으로 여유롭고 "비용 최소화"가 핵심 목표일 때는 백업 및 복원 (Backup & Restore)이 정답입니다. 평소에는 대기 리전에 어떤 컴퓨팅 서버도 실행하지 않고 오직 저렴한 스토리지 백업 데이터만 보관하다가, 재해 선언 시 AWS CloudFormation 같은 IaC 템플릿으로 인프라를 자동 프로비저닝하고 데이터를 복구합니다. 나머지 보기들은 평소 대기 리전에서 서버를 가동하므로 불필요한 비용이 발생합니다.

Q3. 기존 '백업 및 복원' 방식으로는 비즈니스가 요구하는 RTO(수십 분 이내 복구)를 맞출 수 없다는 분석이 나왔습니다. 회사는 평소 인프라 비용을 최소로 유지하면서도 복구 시간을 단축하기 위해, DR 리전에 데이터베이스는 실시간 복제 상태로 켜 두되 애플리케이션 서버는 평상시에 일체 실행하지 않고 AMI 및 배포 템플릿만 준비해 두기로 결정했습니다. 이 DR 전략은 무엇입니까?

핵심 데이터 계층(DB)만 상시 가동하며 실시간 복제를 유지하고, 애플리케이션 서버는 꺼진 상태로 두었다가 재해 발생 시 기동 및 확장하는 전략을 파일럿 라이트(Pilot Light)라고 부릅니다. 웜 스탠바이는 애플리케이션 서버까지 축소된 규모로 상시 실행(Running)하고 있다는 점에서 결정적인 차이가 있습니다.

Q4. 금융 서비스 기업의 결제 시스템이 재해 발생 시 보조 리전으로 장애 조치(Failover)된 직후, 축소된 처리 용량으로라도 사용자 요청을 즉시(Immediately) 처리하기 시작해야 합니다. 이후 Auto Scaling을 통해 본래 운영 규모로 신속히 증설하면 됩니다. 평소 두 리전 모두에서 트래픽을 분산 수용할 필요는 없습니다. 가장 비용 효율적인 DR 전략은 무엇입니까?

장애 조치 즉시 "축소된 용량으로라도 트래픽을 즉각 수용 시작 + 이후 정상 규모로 자동 확장"은 웜 스탠바이(Warm Standby)의 핵심 정의입니다. 파일럿 라이트는 앱 서버를 켜고 부팅하는 준비 시간이 필요하므로 즉시 요청을 처리하지 못합니다. 다중 사이트 액티브-액티브는 평소에도 두 리전 전체를 대규모로 가동하므로 비용이 훨씬 비쌉니다.

Q5. 한 기업이 웜 스탠바이 재해 복구 모의 훈련을 진행하던 중, DR 리전의 Auto Scaling 그룹이 본 운영 규모(인스턴스 200대)까지 확장되지 못하고 인스턴스 시작 실패 오류가 대량 발생했습니다. 원인 분석 결과 계정의 DR 리전 EC2 인스턴스 vCPU 할당량 제한 때문이었습니다. 향후 실제 재해 발생 시 이러한 문제를 완벽히 방지하기 위한 조치 2가지를 고르세요.

정답은 두 번째(DR 리전 할당량 사전 상향)와 세 번째(정기적인 DR 훈련 실시)입니다.
① AWS 서비스 할당량은 각 리전별로 독립적으로 관리됩니다. 평소 서버가 적은 DR 리전은 기본 한도가 낮을 수 있으므로, Service Quotas를 통해 DR 리전의 할당량을 미리 상향 요청해 두어야 재해 시 병목이 발생하지 않습니다.
② 백서는 클라우드 DR 아키텍처가 실제로 유효한지 증명하려면 정기적인 모의 훈련(GameDay)을 통해 인프라 증설과 복원 과정을 주기적으로 테스트하라고 강력히 권고합니다.
(기본 리전 할당량은 DR 리전 확장과 아무런 관련이 없습니다.)

Q6. 금융 보안 규정에 따라 모든 데이터 백업본을 7년간 의무 보존해야 합니다. 랜섬웨어 공격이 발생하거나 최고 권한의 AWS 관리자(루트 사용자 포함) 계정이 해킹당하더라도, 지정된 보존 기간 이전에는 그 누구도 백업을 삭제하거나 보존 기간을 단축할 수 없도록 강제하고자 합니다. 가장 적합한 아키텍처는 무엇입니까?

AWS Backup Vault Lock의 규정 준수 모드(Compliance Mode)는 설정 후 유예 기간(최소 3일)이 지나면, 계정의 루트(Root) 사용자나 AWS 지원팀조차도 백업을 수정하거나 삭제할 수 없는 절대적인 WORM(Write Once, Read Many) 스토리지 잠금 기능을 제공합니다. IAM Deny 정책은 루트 사용자나 관리자 권한으로 변경이 가능하고, 거버넌스 모드는 특정 IAM 권한을 가진 관리자가 잠금을 우회할 수 있어 계정 탈취 상황을 방어하지 못합니다.

Q7. 한 전자상거래 플랫폼이 Aurora Global Database를 도입하여 보조 리전으로 데이터를 1초 미만 지연 시간으로 실시간 복제하고 있습니다. 그런데 주 리전의 데이터베이스 관리자가 실수로 핵심 주문 테이블을 DROP TABLE하여 삭제했고, 이 삭제 명령이 1초도 안 되어 보조 리전으로 그대로 복제되어 양쪽 리전의 데이터가 모두 유실되었습니다. 이 DR 설계에서 가장 치명적으로 누락된 요소는 무엇입니까?

"연속 복제(Replication)는 백업(Backup)이 아닙니다." 실시간 복제는 데이터센터의 하드웨어 고장은 막아주지만, 관리자의 실수나 악성 소프트웨어에 의한 데이터 손상까지 1초 이내에 똑같이 복제해 버립니다. 따라서 진정한 재해 복구를 위해서는 실시간 복제 외에도 데이터가 오염되기 직전 시점으로 롤백할 수 있는 특정 시점 복원(Point-in-Time Recovery, PITR) 백업 체계가 반드시 병행되어야 합니다.

Q8. 파일럿 라이트(Pilot Light) 재해 복구 아키텍처를 운영 중입니다. 기본 리전의 Application Load Balancer(ALB)에 장애가 발생하면, 대기 중인 DR 리전의 ALB로 사용자 트래픽을 자동으로 안전하게 전환하고자 합니다. 데이터 플레인(Data Plane) 기반으로 가장 신뢰성 높은 Route 53 구성을 선택하세요.

파일럿 라이트나 웜 스탠바이처럼 주 리전과 대기 리전이 명확히 분리된 액티브-패시브 구조에서는 장애 조치(Failover) 라우팅 정책을 사용해야 합니다. 주 ALB를 가리키는 기본(Primary) 레코드에 상태 확인(Evaluate Target Health)을 연결하고, 장애 발생 시 보조(Secondary) 레코드로 자동 전환되도록 구성합니다. AWS 백서에서도 Route 53 상태 확인 기반의 DNS 페일오버를 신뢰성 높은 데이터 플레인 작업으로 강력히 권장합니다. 다중 값이나 지연 시간 정책은 평소에도 DR 리전으로 트래픽을 보내므로 액티브-패시브 모델에 맞지 않습니다.

학습 내용 되짚어보기 (인출 연습)

교재를 위로 올려보지 말고, 다음 4가지 질문에 대한 답을 머릿속에서 인출하여 직접 적어보세요.
(1) RPO와 RTO의 기술적 정의와 차이점은 무엇인가요?
(2) 4가지 DR 전략을 비용이 저렴한 순서대로 나열하고, 평상시 DR 리전에 무엇이 가동되고 있는지 요약해 보세요.
(3) 파일럿 라이트와 웜 스탠바이를 구분하는 결정적인 차이점 한 가지는 무엇인가요?
(4) DR 리전으로의 빠른 확장을 위해 사전에 반드시 준비해야 할 2가지는 무엇인가요?

(1) RPO vs RTO:
- RPO(Recovery Point Objective): 허용 가능한 최대 데이터 손실량(시간 간격). 데이터 백업/복제 주기가 결정.
- RTO(Recovery Time Objective): 서비스 중단부터 정상화까지 허용 가능한 최대 다운타임. 복구 절차의 자동화와 대기 서버 상태가 결정.

(2) 4가지 DR 전략 스펙트럼 (저비용 → 고비용):
① 백업 및 복원 (Backup & Restore): 서버 없음, 백업 스토리지 데이터만 DR 리전에 보관. 장애 시 IaC로 인프라 전체 재배포.
② 파일럿 라이트 (Pilot Light): DB/핵심 데이터만 상시 실시간 복제. 앱 서버는 꺼진 상태로 대기.
③ 웜 스탠바이 (Warm Standby): 전체 스택(웹/앱/DB)이 축소된 규모(Scaled-down)로 상시 100% 실행 중.
④ 다중 사이트 액티브-액티브 (Multi-site Active-Active): 2개 이상 리전에서 전체 인프라가 상시 가동되며 실제 사용자 트래픽을 동시 분산 처리.

(3) 파일럿 라이트 vs 웜 스탠바이 차이:
파일럿 라이트는 앱 서버를 켜고 프로비저닝을 마쳐야 비로소 요청 처리가 가능하지만, 웜 스탠바이는 이미 서버가 돌고 있어 장애 조치 즉시 축소된 용량으로라도 요청을 즉각(Immediately) 처리하기 시작하며 확장됩니다.

(4) DR 확장 시 필수 준비 사항:
① DR 리전의 서비스 할당량(vCPU, EIP 등) 사전 상향 (할당량은 리전별 적용).
② 정기적인 DR 모의 훈련(GameDay)을 통한 복구 절차 검증.
(+ 실시간 복제는 데이터 오염까지 복제하므로 특정 시점 복원(PITR) 백업 병행 필수)

추가 학습 및 실습

콘솔 실습 안내 (선택 사항, 소액 과금 주의): AWS Backup 콘솔에 접속하여 매일 1회 실행되는 백업 계획(Backup Plan)을 생성해 보세요. 태그 기반으로 테스트용 소형 EBS 볼륨을 할당하고, "Copy to destination" 옵션에서 다른 리전을 대상(Destination)으로 지정하여 교차 리전 백업 복사가 어떻게 설정되는지 확인해 보세요. (실습이 끝나면 불필요한 과금을 막기 위해 생성된 백업 복구 지점과 백업 계획을 반드시 삭제하세요. 특히 Vault Lock 규정 준수 모드는 유예 기간이 지나면 삭제할 수 없으므로 실습에서는 절대 활성화하지 마세요.)
