AWS SAA 시험의 도메인 4(비용 최적화 아키텍처 설계)는 스토리지, 컴퓨팅, 데이터베이스, 네트워크의 4개 영역으로 구성되지만, 이 모든 영역을 관통하는 핵심 지식 블록은 결국 두 가지입니다. 바로 "어디서 네트워크 데이터 전송 요금이 발생하는가"와 "비용을 분석·통제·최적화하는 관리 도구들을 어떻게 조합하는가"입니다. 오늘 레슨에서는 청구서에서 가장 흔히 누수되는 데이터 전송 및 NAT 비용 구조를 명확히 이해하고, 앞선 레슨들에서 다룬 핵심 비용 결정 기준들을 한 번에 총정리합니다.

왜 비용 최적화와 거버넌스를 배워야 할까요?

시험 관점: 시험 가이드의 Task 4.1부터 4.4까지 모든 과제에서 비용 할당 태그(Cost Allocation Tags), 통합 결제(Consolidated Billing), 그리고 AWS Cost Explorer, AWS Budgets, Cost and Usage Report(CUR)의 활용법이 필수 지식으로 반복 출제됩니다. 특히 Task 4.4에서는 단일 공유 NAT 게이트웨이와 가용 영역(AZ)별 배포 간의 비용/가용성 트레이드오프, 리전 간 및 AZ 간 데이터 전송 요금, 그리고 VPC 엔드포인트를 통한 비용 절감 설계가 단골 문제로 다뤄집니다.[1]
실무 관점: 클라우드 도입 후 첫 달 청구서를 받았을 때 가장 당혹스러운 항목 중 하나가 바로 예상치 못한 "NAT Gateway 처리 요금"과 "Cross-AZ Data Transfer 요금"입니다. 데이터가 네트워크 경계를 넘나드는 원리를 미리 알고 설계에 반영하면, 불필요하게 새어 나가는 운영 비용의 수십 퍼센트를 사전 차단할 수 있습니다.

1. 데이터 전송(Data Transfer): 비용이 발생하는 경계와 방향

AWS의 데이터 전송 요금은 리전이나 서비스마다 세부 단가가 조금씩 다르므로 숫자를 외울 필요는 없습니다. 시험과 실무에서 반드시 기억해야 할 것은 "데이터가 어느 경계를 넘는지"와 "데이터 이동 방향"입니다. 공식 Cost and Usage Report(CUR) 가이드가 정의하는 기본 과금 원칙은 다음과 같습니다.[2]

네트워크 이동 경로과금 여부 및 세부 규칙
인터넷 → AWS (인바운드, 수신)100% 무료 (0달러). 외부에서 AWS 내부로 들어오는 모든 트래픽에는 전송 요금이 붙지 않습니다.
AWS → 인터넷 (아웃바운드, 송신)유료 과금 (GB당 과금, 사용량 구간에 따라 단계별 할인).
동일 리전 내 가용 영역 간 (Cross-AZ)유료 과금. 데이터가 AZ 경계를 넘어가면 보내는 쪽(아웃바운드)과 받는 쪽(인바운드) 양쪽 리소스 모두에 GB당 요금이 각각 계량됩니다. (단, S3나 DynamoDB처럼 리전 차원에서 제공되는 엔드포인트는 예외)
서로 다른 리전 간 (Cross-Region)유료 과금. 데이터를 보내는 소스(출발지) 리전의 아웃바운드 요금으로 과금되며, 받는 목적지 리전의 인바운드는 무료입니다.
AWS 오리진(S3, ALB, API Gateway) → CloudFront100% 무료 (0달러). 오리진에서 CloudFront 엣지로 이동하는 트래픽은 무료이며, 오직 CloudFront 엣지에서 사용자(뷰어)로 나가는 아웃바운드만 과금됩니다.[3]

아키텍처 설계 원칙:

  1. 동일 AZ 배치 vs 고가용성의 균형: 서로 통신이 잦은 마이크로서비스나 데이터베이스 클라이언트는 가능한 한 같은 가용 영역에 배치하면 AZ 간 전송 비용을 완전히 아낄 수 있습니다. 하지만 이는 Multi-AZ 고가용성 설계와 상충할 수 있으므로, 프로덕션 환경에서는 "비용 절감"과 "장애 복원력" 사이의 균형을 요구 사항에 맞게 판단해야 합니다.
  2. 리전 간 전송 최소화: 교차 리전 복제(CRR)나 백업 전송은 꼭 필요한 데이터만 선별하여 전송합니다.
  3. CDN 캐싱 활용: 인터넷으로 나가는 대용량 다운로드 콘텐츠는 S3나 웹 서버에서 직접 쏘지 말고 CloudFront 뒤에 두어 오리진 아웃바운드 요금 면제 및 전송 단가 절감 혜택을 극대화합니다(0025).

2. NAT 게이트웨이: 비용 구조와 아키텍처 최적화

VPC 내 프라이빗 서브넷의 리소스들이 외부 인터넷과 통신하기 위해 사용하는 NAT 게이트웨이(NAT Gateway)는 두 가지 항목으로 과금됩니다: (1) 게이트웨이가 프로비저닝되어 있는 시간당 요금(Hour) + (2) 게이트웨이를 거쳐 처리된 데이터양(GB당 처리 요금).[4]
특히 각 NAT 게이트웨이는 특정 가용 영역(AZ) 하나에 종속되어 생성되므로, 네트워크 구성에 따라 비용과 가용성이 크게 달라집니다.[5]

NAT 비용 절감을 위한 두 가지 황금률

  1. AZ 간 데이터 전송량이 많다면 가용 영역(AZ)마다 NAT 게이트웨이를 분리 배포합니다: 단일 NAT 게이트웨이를 모든 AZ가 공유하면 시간당 요금은 1개분만 내지만, 다른 AZ에서 발생하는 트래픽마다 "AZ 간 전송 요금"이 추가로 붙습니다. 또한 NAT가 위치한 AZ-a가 장애로 다운되면 다른 모든 AZ의 인스턴스들까지 인터넷 연결이 끊기는 치명적인 단일 장애점(SPOF)이 됩니다. 따라서 고트래픽 프로덕션 환경에서는 각 AZ마다 NAT 게이트웨이를 두고 동일 AZ의 NAT로 라우팅하는 것이 복원력과 비용 측면 모두에서 정답입니다.[4][5]
  2. S3 및 DynamoDB 트래픽은 게이트웨이 VPC 엔드포인트를 사용합니다: 프라이빗 인스턴스가 S3나 DynamoDB로 대용량 데이터를 읽고 쓸 때 NAT 게이트웨이를 거치게 두면 막대한 GB당 처리 요금이 청구됩니다. 게이트웨이 VPC 엔드포인트(Gateway Endpoint)는 시간당 요금도, 데이터 처리 요금도 완전히 무료(0원)입니다.[6] 라우팅 테이블에 S3 접두사 목록 경로만 추가해 주면 모든 트래픽이 NAT를 건너뛰고 AWS 내부 직통망으로 흐르므로, NAT 처리 요금을 0원으로 만들 수 있습니다.
비교 항목단일 NAT 게이트웨이 공유 구성AZ마다 NAT 게이트웨이 개별 배포
시간당 고정 요금1개 분량만 청구 (경제적)가용 영역 개수만큼 청구 (AZ당 1개)
AZ 간 전송 요금다른 AZ의 인스턴스가 NAT를 이용할 때마다 발생동일 AZ 내부에서 라우팅되므로 발생하지 않음
장애 복원력 (HA)NAT가 속한 AZ 장애 시 모든 서브넷의 아웃바운드 인터넷 마비 (SPOF)특정 AZ 장애 시에도 다른 AZ는 독립적으로 인터넷 통신 유지
적합한 환경개발·테스트 환경, 트래픽이 적은 소규모 시스템트래픽이 많고 무중단 가용성이 중요한 프로덕션 환경

참고: NAT 인스턴스(NAT Instance)는 EC2 인스턴스 위에서 직접 NAT 소프트웨어를 구동하는 방식입니다. 인스턴스 크기 비용만 들지만 대역폭 제한, 소프트웨어 패치, 고가용성 장애 조치 스크립트 작성 등 막대한 운영 부담이 발생합니다. 시험에서 NAT 인스턴스가 정답이 되는 경우는 "운영 오버헤드를 감수하고서라도 극도로 적은 트래픽을 최저 비용으로 처리해야 할 때" 같은 매우 특수한 예외뿐입니다.[7]

3. 핵심 비용 관리 도구 완전 정복

시험에 등장하는 비용 관리 도구들은 겉보기에 비슷해 보이지만 "해결하고자 하는 질문"이 명확히 다릅니다. 이 핵심 역할을 구별할 수 있어야 합니다.

도구 이름핵심 질문 및 목적상세 기능 및 시험 포인트
AWS Cost Explorer"과거에 어디에 얼마를 썼고, 앞으로의 지출 추세는 어떠한가?"비용 및 사용량을 다각도로 시각화 분석하는 콘솔 도구. 과거 최대 13개월 데이터 분석 및 향후 최대 18개월 예측(Forecasting) 제공. 예약 인스턴스(RI) 및 Savings Plans 추천 기능을 제공하며 콘솔 사용은 무료입니다.[8][9]
AWS Budgets"예산을 초과하기 전에 담당자에게 알리고 자동 조치를 취할 수 있는가?"비용, 사용량, RI/Savings Plans 사용률 및 적용률에 대한 맞춤형 예산 설정. 실제 지출뿐 아니라 예측(Forecasted) 지출이 설정한 임계값(예: 80%, 100%)을 넘을 때 이메일 또는 SNS 알림을 발송합니다. 나아가 예산 작업(Budget Actions)을 연동하여 임계값 초과 시 IAM 정책을 붙여 추가 리소스 생성을 막거나 EC2 인스턴스를 자동 중지하는 적극적 대응이 가능합니다.[10]
Data Exports / CUR 2.0
(Cost and Usage Report)		"원천 청구 데이터를 가장 상세한 수준으로 S3에 저장해 분석할 수 있는가?"AWS에서 제공하는 가장 세분화되고 포괄적인 원천 비용 및 사용량 데이터를 S3 버킷으로 정기 내보내기합니다. 현재는 CUR 2.0이 권장 형식입니다. S3에 저장된 이 대규모 원천 데이터를 Amazon Athena로 표준 SQL 쿼리하거나 Amazon QuickSight 대시보드와 연동하여 커스텀 비용 보고서를 제작합니다.[11]
비용 할당 태그
(Cost Allocation Tags)		"특정 프로젝트나 부서별로 비용을 세부적으로 분류해 추적할 수 있는가?"리소스에 붙인 메타데이터 태그를 결제에 매핑합니다. AWS 생성 태그와 사용자 정의 태그가 있습니다. 핵심 주의점: 리소스에 태그를 달았다고 해서 자동으로 결제에 반영되지 않으며, 반드시 결제 콘솔의 비용 할당 태그 관리 화면에서 해당 태그를 '활성화(Activate)'해야만 비로소 Cost Explorer나 보고서에 집계되어 나타납니다(반영까지 최대 24시간 소요).[12]
통합 결제
(Consolidated Billing)		"여러 계정의 결제를 하나로 묶고 볼륨 할인을 공유할 수 있는가?"AWS Organizations를 기반으로 다중 계정의 청구를 단일 관리 계정(Management Account)으로 통합합니다. 모든 멤버 계정의 사용량을 합산하여 S3 스토리지나 데이터 전송 볼륨 할인 구간을 더 빠르게 달성할 수 있으며, 한 계정에서 구매한 RI나 Savings Plans 할인을 조직 내 다른 멤버 계정들과 자동 공유합니다(추가 비용 없음).[13]
AWS Compute Optimizer"현재 프로비저닝된 인스턴스 크기가 적절한가, 자원이 낭비되고 있지는 않은가?"머신 러닝을 활용해 CloudWatch의 과거 사용률 지표(최소 14일 이상)를 분석하여 적정 크기 조정(Rightsizing) 권장 사항과 과대 프로비저닝되거나 유휴 상태인 리소스를 찾아냅니다. 대상: EC2, Auto Scaling 그룹, EBS 볼륨, Lambda 함수, ECS on Fargate, RDS 인스턴스, NAT 게이트웨이 등. (사용을 위한 사전 옵트인 필요)[14]
AWS Trusted Advisor"AWS 모범 사례 관점에서 시스템 전체의 약점과 비용 낭비를 점검할 수 있는가?"5대 기둥(비용 최적화, 성능, 보안, 내결함성, 서비스 한도) 전반을 자동 검사하는 종합 감사 도구입니다. 비용 최적화 점검 항목에는 사용률이 극히 낮은 EC2, 유휴 상태인 로드 밸런서, 미사용 EBS 볼륨, 인스턴스에 연결되지 않은 탄력적 IP(EIP), 비활성 NAT 게이트웨이 등이 포함됩니다.[15][16]

참고: Trusted Advisor의 전체 검사는 Business Support 이상 플랜에서 활성화되며, Basic 플랜에서는 핵심 보안 점검과 서비스 한도 점검 등 일부만 제공됩니다.[15]

자주 헷갈리는 도구 쌍 비교:

  • Cost Explorer vs Budgets: Cost Explorer는 과거 사용 추이를 분석하고 미래를 예측하는 조회·분석 도구이고, Budgets는 임계값을 정해 두고 넘기 전에 경고를 보내고 조치를 취하는 사전 알림·대응 도구입니다.
  • Compute Optimizer vs Trusted Advisor: Compute Optimizer는 CloudWatch 메트릭을 바탕으로 인스턴스 vCPU/메모리 사양을 올리거나 내리는 Rightsizing(적정 사이징)에 집중하고, Trusted Advisor는 미연결 EIP나 유휴 ELB 등 AWS 모범 사례 체크리스트 관점에서 인프라를 종합 진단합니다.

접근 빈도는 낮지만 필요 시 수 밀리초 내 즉시 응답 필요 → S3 Standard-IA (최소 보관 30일, 조회 요금 부과)
재생성 가능한 부차적 데이터의 저비용 저장 → S3 One Zone-IA (단일 AZ 저장)
규정상 보관하며 연 1회 미만 접근, 몇 시간의 복원 지연 허용 → S3 Glacier Deep Archive (최저 스토리지 비용, 최소 보관 180일)[18]

DynamoDB 용량 모드
(레슨 0022)		신규 런칭, 트래픽을 예측할 수 없거나 갑작스러운 스파이크 발생 → 온디맨드 모드 (On-Demand) (사전 프로비저닝 없이 실제 요청당 과금, 기본 권장)

시험에 자주 나오는 핵심 패턴: 키워드 → 정답 공식

프라이빗 서브넷에서 S3로의 대용량 트래픽, NAT 처리 비용이 과다 → S3 게이트웨이 VPC 엔드포인트(무료) 추가 · 여러 AZ가 공유하는 NAT로 인한 AZ 간 전송비 및 가용성 문제 → AZ마다 NAT 게이트웨이 개별 배치 및 동일 AZ 라우팅 · 예상 지출이 예산 한도를 초과할 것으로 예측될 때 선제적 알림/자동화 조치 → AWS Budgets (예측 알림 및 Budget Actions) · 과거 1년 비용 추세 분석, 향후 지출 예측, RI 추천 → AWS Cost Explorer · 프로젝트별/부서별 비용 분리 집계 → 결제 콘솔에서 비용 할당 태그(Cost Allocation Tags) 활성화 · 여러 계정의 사용량을 합산하여 볼륨 할인 및 할인 약정 공유 → AWS Organizations 통합 결제(Consolidated Billing) · 과대 프로비저닝된 인스턴스 사양 최적화 → AWS Compute Optimizer 권장 사항 · 미사용 탄력적 IP, 유휴 ELB, 비활성 리소스 점검 → AWS Trusted Advisor 비용 점검표 · 가장 세분화된 원천 결제 데이터를 S3에 저장하고 Athena로 SQL 분석 → AWS Cost and Usage Report (Data Exports CUR 2.0) · 전 세계 인터넷 아웃바운드 데이터 전송 비용 절감 → Amazon CloudFront 엣지 캐싱

연습

비용 최적화 도메인은 이전의 컴퓨팅, 스토리지, 데이터베이스, 네트워크 지식이 복합적으로 얽혀 출제됩니다. 아래 문항들을 통해 실전 문제 해결력을 점검해 보세요.

Q1. 프로덕션 VPC 내 3개의 가용 영역(AZ-a, AZ-b, AZ-c)에 각각 프라이빗 서브넷이 존재하며, 현재 모든 서브넷의 아웃바운드 인터넷 트래픽이 AZ-a에 배치된 단일 NAT 게이트웨이 하나를 공유하여 외부로 나가고 있습니다. 월간 청구서에서 가용 영역 간(Cross-AZ) 데이터 전송 요금이 매우 크게 발생하고 있으며, 보안 및 운영팀은 AZ-a에 장애가 발생할 경우 다른 두 AZ의 인스턴스들까지 외부 결제 API를 호출할 수 없게 되는 단일 장애점(SPOF)을 지적했습니다. 비용과 고가용성을 동시에 만족하는 가장 올바른 조치는 무엇입니까?

정답은 각 AZ마다 NAT 게이트웨이를 하나씩 배포하고 동일 AZ의 NAT로 라우팅하는 것입니다.
각 가용 영역마다 NAT 게이트웨이를 독립적으로 배치하면 인스턴스들의 인터넷 아웃바운드 트래픽이 동일 AZ 내부에서만 순환하므로 AZ 간 데이터 전송 요금이 원천적으로 발생하지 않습니다. 또한 특정 AZ에 재해가 발생하더라도 다른 AZ의 NAT 게이트웨이는 정상 작동하므로 AZ 독립적 고가용성 구조가 완성됩니다.
- 오답 분석: - NAT 인스턴스 교체: 여전히 단일 인스턴스이므로 SPOF 문제가 해결되지 않으며, 관리 부담이 증가합니다. - NAT 게이트웨이 크기 업그레이드: NAT 게이트웨이는 사용자가 크기나 인스턴스 타입을 선택하는 제품이 아니며(트래픽에 따라 최대 100Gbps까지 자동 확장), 단일 AZ 집중 구조를 바꾸지 못합니다. - 퍼블릭 서브넷 전환: 프라이빗 인스턴스를 직접 인터넷에 노출시키는 치명적인 보안 위반입니다.

Q2. 프라이빗 서브넷에서 실행되는 대규모 데이터 분석 애플리케이션 EC2 인스턴스들이 매일 수십 테라바이트(TB)의 데이터를 동일 리전의 Amazon S3 버킷에서 지속적으로 읽어 들이고 있습니다. 현재 이 모든 S3 트래픽이 NAT 게이트웨이를 통과하고 있어 매달 엄청난 양의 데이터 처리 요금이 청구되고 있습니다. 아키텍처를 변경하여 NAT 처리 요금을 가장 비용 효율적으로 없애는 방법은 무엇입니까?

정답은 S3 전용 게이트웨이 VPC 엔드포인트를 생성하고 라우팅 테이블에 연결하는 것입니다.
Amazon S3용 게이트웨이 VPC 엔드포인트(Gateway Endpoint)는 시간당 요금도, 데이터 처리 요금도 완전히 무료(0원)입니다. 프라이빗 서브넷의 라우팅 테이블에 엔드포인트 경로를 등록하면 S3로 향하는 모든 트래픽이 NAT 게이트웨이를 완벽히 우회하여 AWS 내부 직통망으로 흐르므로, 수십 TB에 달하던 NAT 데이터 처리 요금을 단 1원도 들이지 않고 0원으로 절감할 수 있습니다.
- 오답 분석: - S3 Transfer Acceleration: CloudFront 엣지를 활용한 원거리 전송 가속 기능으로 추가 요금이 발생하며, VPC 내부 인스턴스의 NAT 통과 문제를 해결하지 못합니다. - NAT 게이트웨이 추가: NAT를 여러 개 만들어도 트래픽의 총합에 따라 부과되는 GB당 NAT 데이터 처리 요금은 전혀 줄어들지 않고 오히려 시간당 요금만 늘어납니다. - CloudFront 배포: VPC 내부 리소스가 S3를 읽는 데 적합하지 않으며 여전히 인터넷/NAT 경로를 탈 수 있습니다.

Q3. 한 기업의 재무 관리자가 당월 AWS 청구 금액이 사전에 설정한 예산을 초과할 것으로 예측되는 시점에 이메일과 모바일 SNS로 선제적 알림을 받기를 원합니다. 또한 개발(Dev) 계정에서는 지출 예측치가 예산 한도에 도달했을 때 추가적인 비싼 리소스 생성을 막기 위해 특정 IAM 거부 정책을 자동으로 적용하는 조치까지 구현하고자 합니다. 최소한의 관리 노력으로 이를 구현할 수 있는 도구는 무엇입니까?

정답은 AWS Budgets의 예산 설정 및 예산 작업(Budget Actions)입니다.
AWS Budgets는 실제 누적 지출뿐 아니라 머신러닝 기반의 예측(Forecasted) 지출이 설정한 한도를 초과할 것으로 예상될 때 사전에 이메일과 SNS 알림을 발송할 수 있습니다. 또한 예산 작업(Budget Actions) 기능을 연결하면 임계값 도달 시 특정 IAM 정책을 자동으로 적용하여 리소스 생성을 차단하거나 특정 EC2/RDS 인스턴스를 자동으로 중지하는 등 사전 정의된 조치를 자동 실행할 수 있습니다.
- 오답 분석: - Cost Explorer: 과거 지출을 분석하고 시각화하는 도구이며, 임계값 기반의 자동 경보 및 자동화 액션을 지원하지 않습니다. - Trusted Advisor: 인프라의 모범 사례 준수 여부를 점검하는 정적 체크리스트 도구입니다. - Compute Optimizer: 개별 리소스의 사이징 최적화를 제안하는 도구입니다.

Q4. 한 단일 AWS 계정 내에서 여러 개발 프로젝트 팀이 인프라 리소스를 공유하고 있습니다. 재무팀은 AWS Cost Explorer에서 각 프로젝트별(Project) 월간 지출을 나누어 확인하고 싶어 합니다. 엔지니어링팀이 모든 AWS 리소스에 이미 Project라는 태그 키와 프로젝트명을 정확히 달아 두었음에도 불구하고, Cost Explorer의 태그 필터 목록에 Project 태그가 전혀 나타나지 않습니다. 어떤 필수 설정 단계가 누락되었습니까?

정답은 결제 및 비용 관리 콘솔에서 Project 태그를 비용 할당 태그로 활성화해야 한다는 것입니다.
AWS 리소스에 태그를 달아 두었더라도 결제 시스템이 이를 자동으로 인식하지 않습니다. AWS 결제 콘솔(Billing and Cost Management)의 '비용 할당 태그(Cost Allocation Tags)' 메뉴에서 해당 태그 키를 찾아 명시적으로 '활성화(Activate)'해 주어야만 비로소 Cost Explorer 및 CUR 보고서에서 해당 태그를 기준으로 비용을 그룹화하고 필터링할 수 있게 됩니다(활성화 후 적용까지 최대 24시간 소요).
- 오답 분석: - 별도 VPC 분리: 비용 태그 분류와 무관하며 불필요한 인프라 복잡성을 초래합니다. - AWS Config 규칙: 태그 정책 준수 여부를 검사하는 도구일 뿐 비용 집계와 직접 관련이 없습니다. - Compute Optimizer 옵트인: 인스턴스 적정 사이징 분석 도구로 비용 태그 활성화와 무관합니다.

Q5. 한 회사가 클라우드 인프라 전반의 낭비를 조사하여 비용을 절감하고자 합니다. 과도하게 큰 사양으로 프로비저닝된(Over-provisioned) EC2 인스턴스들과, 어떤 인스턴스에도 연결되어 있지 않은 유휴 탄력적 IP(EIP), 그리고 트래픽이 전혀 없는 미사용 로드 밸런서를 찾아내려 합니다. 이러한 점검과 최적화 권장안을 제공하는 두 가지 서비스는 무엇입니까? (두 개를 고르세요)

정답은 AWS Compute Optimizer(1)와 AWS Trusted Advisor(3)입니다.
1. AWS Compute Optimizer: CloudWatch의 CPU, 메모리 등의 실제 사용률 데이터를 머신러닝으로 분석하여 과대 프로비저닝된 EC2 인스턴스를 적정 크기(Rightsizing)로 축소하도록 구체적인 패밀리와 사양을 권장합니다.
2. AWS Trusted Advisor: 비용 최적화 카테고리 검사를 통해 실행 중이지 않은 인스턴스에 연결되지 않은 탄력적 IP(EIP, 시간당 페널티 요금 부과), 트래픽이 없는 유휴 로드 밸런서, 저활용 EBS 볼륨 등을 식별하여 즉각적인 비용 회수 포인트를 알려줍니다.
- 오답 분석: - AWS Budgets: 예산 임계값 초과 알림 도구이지 유휴 리소스 탐색 도구가 아닙니다. - 통합 결제: 다중 계정의 결제를 합산하고 볼륨 할인을 공유하는 청구 기능입니다. - GuardDuty: 악성 행위 및 보안 위협을 탐지하는 보안 모니터링 서비스입니다.

Q6. (복습 0010) 매일 자정부터 새벽 사이에 수 시간 동안 실행되는 대규모 비디오 트랜스코딩 배치 작업이 있습니다. 이 작업은 주기적으로 진행 상태를 체크포인트로 저장하므로 실행 도중 인스턴스가 중단되더라도 언제든 중단된 지점부터 안전하게 재개할 수 있으며, 다음 날 업무 시작 전까지만 완료되면 됩니다. 가장 비용 효율적인 EC2 구매 옵션은 무엇입니까?

정답은 스팟 인스턴스(Spot Instances)입니다.
"작업 중단(Interruption)을 허용할 수 있음 + 체크포인트 재개 가능 + 완료 시간에 여유가 있음"은 스팟 인스턴스를 선택해야 하는 완벽한 교과서적 시나리오입니다. 스팟 인스턴스는 AWS의 여유 유휴 컴퓨팅 자원을 온디맨드 대비 최대 90%까지 저렴한 비용으로 활용할 수 있어 배치 작업에 최상의 비용 절감 효과를 제공합니다.
- 오답 분석: - 3년 표준 RI: 하루 24시간 연중무휴 상시 가동되는 안정적 워크로드에 적합하며, 하루 몇 시간만 실행되는 배치 작업에 3년 약정을 거는 것은 막대한 비용 낭비입니다. - 전용 호스트: 물리적 서버 독점 및 기존 라이선스(BYOL) 준수용으로 가장 고가의 옵션입니다. - 온디맨드: 안정적이지만 할인이 전혀 적용되지 않아 비용 최적화 조건에 미달합니다.

Q7. (복습 0018) 한 금융 회사가 금융 규제 준수를 위해 회계 감사 로그 데이터를 10년간 장기 보관해야 합니다. 이 데이터는 연 1회 미만으로 극히 드물게 감사 시에만 조회되며, 데이터 열람이 필요할 경우 몇 시간의 복원 지연 시간(Retrieval time)이 허용됩니다. 10년 보관 비용을 가장 저렴하게 유지할 수 있는 S3 스토리지 클래스는 무엇입니까?

정답은 S3 Glacier Deep Archive입니다.
"연 1회 미만의 극히 드문 접근 + 수 시간의 복원 대기 허용 + 수년 이상의 장기 보관" 요구에는 S3 Glacier Deep Archive가 AWS 전체 스토리지 중 가장 저렴한 비용(GB당 월 $0.00099 수준)을 제공합니다. 최소 보관 기간 180일 조건도 10년 보관 요구에 완벽히 부합합니다.
- 오답 분석: - S3 Intelligent-Tiering: 데이터의 접근 패턴을 알 수 없거나 자주 바뀔 때 유리하며, 장기 아카이빙 목적으로는 모니터링 비용 등으로 인해 Deep Archive보다 보관 단가가 높습니다. - S3 Standard-IA: 월 1회 수준의 접근과 밀리초 단위 즉시 조회가 필요한 데이터용으로 보관 단가가 Deep Archive 대비 수십 배 높습니다. - S3 Express One Zone: 초당 수십만 트랜잭션과 한 자릿수 밀리초 초저지연을 요하는 초고성능 티어로 가장 고가의 스토리지입니다.

Q8. (복습 0022) 새롭게 출시된 모바일 앱의 백엔드 데이터베이스로 Amazon DynamoDB를 도입하려 합니다. 갓 출시된 서비스라 일일 트래픽 패턴을 전혀 예측할 수 없으며, 불규칙한 마케팅 프로모션에 따라 순간적으로 트래픽이 폭증했다가 다시 급감하는 특성을 보입니다. 복잡한 용량 계획(Capacity Planning) 없이 실제 사용한 읽기/쓰기 요청 건수에 대해서만 비용을 지불하고 싶습니다. 가장 적합한 DynamoDB 용량 모드는 무엇입니까?

정답은 온디맨드(On-Demand) 용량 모드를 선택하는 것입니다.
DynamoDB의 온디맨드 모드는 용량 단위를 사전에 예측하거나 프로비저닝할 필요 없이, 인입되는 트래픽 워크로드에 맞춰 즉각 자동으로 확장되며 실제로 실행된 읽기/쓰기 요청 수에 비례해서만 과금됩니다. 예측할 수 없거나 급격한 스파이크가 발생하는 신규 서비스에 가장 이상적인 기본 모드입니다.
- 오답 분석: - 프로비저닝 모드 대량 할당: 사용 여부와 상관없이 할당된 RCU/WCU에 대해 시간당 고정 요금이 계속 청구되므로 유휴 시간에 막대한 비용 낭비가 발생합니다. - 예약 용량 구매: 트래픽을 예측할 수 없는 신규 서비스에는 장기 약정(1년/3년)이 맞지 않습니다. - DAX 클러스터 배치: 읽기 성능을 극대화하는 인메모리 캐시일 뿐, 예측 불가한 트래픽에 대한 용량 모드 관리 해법이 아닙니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속에서 직접 떠올려 적어 보세요.
(1) 데이터 전송 요금의 5대 규칙(인터넷 인바운드/아웃바운드, 동일 리전 AZ 간, 리전 간, AWS 오리진→CloudFront)은 각각 어떻게 과금되나요?
(2) 프라이빗 서브넷의 NAT 게이트웨이 비용을 최적화하는 두 가지 방법과, 단일 공유 NAT 구성의 치명적 단점은 무엇인가요?
(3) Cost Explorer, AWS Budgets, CUR 2.0(Data Exports), Compute Optimizer, Trusted Advisor의 핵심 차이점을 한 문장씩 정리해 보세요.

(1) 데이터 전송 5대 과금 규칙:
- 인터넷 → AWS (인바운드): 100% 무료.
- AWS → 인터넷 (아웃바운드): GB당 유료 과금.
- 동일 리전 내 AZ 간 (Cross-AZ): 보내는 쪽과 받는 쪽 양방향 모두 GB당 유료 과금.
- 리전 간 (Cross-Region): 데이터를 보내는 출발지 리전의 아웃바운드만 유료 과금 (도착지 인바운드는 무료).
- AWS 오리진 → CloudFront: 100% 무료 (오직 CloudFront에서 사용자 뷰어로 나가는 아웃바운드만 과금).

(2) NAT 비용 최적화 및 공유 NAT의 한계:
- 최적화 방법 1: 고트래픽 환경에서는 각 AZ마다 NAT 게이트웨이를 두고 동일 AZ로 라우팅하여 AZ 간 전송 요금을 원천 차단.
- 최적화 방법 2: S3 및 DynamoDB 트래픽은 비용이 완전 무료인 게이트웨이 VPC 엔드포인트로 우회시켜 NAT 처리 요금을 0원으로 절감.
- 단일 공유 NAT의 문제: 다른 AZ 인스턴스들의 트래픽에 AZ 간 전송료가 이중 부과되며, 해당 NAT가 위치한 AZ 장애 시 모든 AZ의 아웃바운드 인터넷이 마비되는 단일 장애점(SPOF) 발생.

(3) 비용 관리 도구 핵심 요약:
- Cost Explorer: 과거 13개월 지출 분석, 미래 18개월 지출 예측 및 RI/SP 추천 시각화 도구.
- AWS Budgets: 실제 또는 예측 지출이 임계값을 넘을 때 선제적 알림 발송 및 IAM/인스턴스 자동 제어(Budget Actions).
- CUR 2.0 (Data Exports): 가장 상세한 원천 결제 데이터를 S3에 주기적으로 내보내어 Athena 및 QuickSight로 심층 분석.
- Compute Optimizer: CloudWatch 메트릭 기반 머신러닝 분석으로 EC2/EBS/Lambda 등의 과대 프로비저닝을 찾아 적정 사양(Rightsizing) 권장.
- Trusted Advisor: 미사용 EIP, 유휴 ELB 등 5대 기둥 모범 사례 체크리스트를 점검해 즉각적인 비용 낭비 요소를 진단.
