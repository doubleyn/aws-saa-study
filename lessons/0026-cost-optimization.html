2. NAT 게이트웨이: 시간 + 처리량, 그리고 AZ

NAT 게이트웨이는 사용 가능한 시간마다, 그리고 처리한 GB마다 과금됩니다.[4] 각 NAT 게이트웨이는 특정 AZ 하나에 만들어지고 그 AZ 안에서만 중복 구현됩니다.[5]

AWS가 직접 권하는 절감법은 두 가지입니다.[4]

  1. AZ 간 트래픽이 크면 리소스를 NAT 게이트웨이와 같은 AZ에 두거나, 리소스가 있는 AZ마다 NAT 게이트웨이를 만듭니다.
  2. NAT를 지나는 트래픽 대부분이 AWS 서비스로 간다면 그 서비스의 게이트웨이 엔드포인트나 인터페이스 엔드포인트를 만듭니다. S3와 DynamoDB용 게이트웨이 엔드포인트는 추가 요금이 없습니다.[6] 인터페이스 엔드포인트는 PrivateLink 요금이 따로 있으니 비교가 필요합니다.

NAT 인스턴스는 인스턴스 유형·크기와 사용 시간으로 과금되고, 가용성(장애 조치 스크립트)·패치를 직접 관리해야 합니다. AWS는 가용성·대역폭·관리 부담 면에서 NAT 게이트웨이를 권장합니다.[7] 시험에서 NAT 인스턴스가 정답이 되는 경우는 "운영 부담을 감수하고 아주 작은 트래픽을 최저 비용으로" 같은 특수한 조건뿐입니다.

연습

도메인 4는 앞 유닛과 섞여 나옵니다. 아래 문항도 일부러 섞었습니다.

Q1. 프로덕션 VPC의 세 AZ에 프라이빗 서브넷이 있고, 모두 AZ-a의 NAT 게이트웨이 하나로 인터넷에 나갑니다. 청구서에 AZ 간 전송 요금이 크고, 보안팀은 AZ-a 장애 시 다른 AZ도 외부 API를 못 부르는 점을 지적했습니다. 가장 적합한 조치는?

AZ마다 NAT 게이트웨이를 두고 각 서브넷이 같은 AZ의 NAT를 쓰게 라우팅하면 AZ 간 전송을 피하고 AZ 독립적 구조가 됩니다. NAT 게이트웨이는 크기를 고르는 제품이 아니며, NAT 인스턴스 한 대는 여전히 단일 장애점입니다. 퍼블릭 서브넷 전환은 보안 요구와 반대입니다(0004, 0006).

Q2. 프라이빗 서브넷의 분석 서버들이 매일 수 TB를 같은 리전의 S3에서 읽고, 이 트래픽이 NAT 게이트웨이를 지납니다. NAT 비용을 가장 비용 효율적으로 줄이는 방법은?

S3 게이트웨이 엔드포인트는 추가 요금이 없고, 라우팅 테이블의 접두사 목록 경로로 S3 트래픽이 NAT를 거치지 않게 합니다. NAT를 늘려도 GB당 처리 요금은 그대로이고, Transfer Acceleration이나 CloudFront는 트래픽이 NAT를 지나는 경로 자체를 바꾸지 않습니다.

Q3. 재무팀은 월 지출이 정해진 금액을 넘을 것으로 예측되는 시점에 이메일과 SNS로 알림을 받고, 개발 계정에서는 추가 리소스 생성을 막는 조치까지 자동으로 걸고 싶어 합니다. 어떤 도구입니까?

Budgets는 실제 또는 예측 지출이 임계값을 넘으면 이메일/SNS로 알리고, 예산 작업으로 IAM 정책 적용 같은 조치를 걸 수 있습니다. Cost Explorer는 분석과 예측 화면이지 임계값 알림·조치 도구가 아닙니다.

Q4. 한 계정에서 여러 프로젝트가 리소스를 공유합니다. 경영진이 Cost Explorer에서 프로젝트별 비용을 보고 싶어 합니다. 리소스에 Project 태그는 이미 붙어 있는데 Cost Explorer에 나타나지 않습니다. 무엇이 빠졌습니까?

사용자 정의 태그도 AWS 생성 태그도 결제 및 비용 관리 콘솔에서 비용 할당 태그로 활성화해야 Cost Explorer와 비용 할당 보고서에 나타납니다(나타나기까지 최대 24시간). Config 규칙은 태그 준수 점검이지 비용 집계가 아닙니다.

Q5. 회사가 과대 프로비저닝된 EC2 인스턴스와 연결되지 않은 탄력적 IP, 유휴 로드 밸런서를 찾아 비용을 줄이려 합니다. 어떤 서비스가 이런 점검이나 권장을 제공합니까? (두 개를 고르세요)

Compute Optimizer는 CloudWatch 지표로 EC2 적정 크기 권장과 유휴 리소스를 찾아 주고, Trusted Advisor 비용 점검에는 사용률 낮은 EC2, 연결 안 된 탄력적 IP, 유휴 로드 밸런서가 있습니다. Budgets는 임계값 알림, 통합 결제는 할인 합산, GuardDuty는 위협 탐지(0009)입니다.

Q6. (복습 0010) 매일 밤 몇 시간 도는 이미지 변환 배치는 중간에 끊겨도 체크포인트에서 다시 시작할 수 있고, 완료 시각에 여유가 있습니다. 가장 비용 효율적인 구매 옵션은?

중단 가능하고 시간이 유연한 배치는 Spot의 전형입니다. 여유 용량을 크게 할인된 가격에 쓰되, 용량이 필요해지면 2분 전 알림 후 중단될 수 있습니다. 매일 몇 시간만 도는 작업에 3년 예약은 낭비가 크고, 온디맨드는 할인이 없습니다.

Q7. (복습 0018) 규정상 감사 로그를 10년 보관해야 하지만, 실제로 읽는 일은 연 1회도 안 되며 필요하면 몇 시간 뒤에 받아도 됩니다. 가장 저렴한 스토리지 클래스는?

연 1회 미만 접근, 몇 시간 복원 허용, 장기 보관이면 Glacier Deep Archive입니다(최소 보관 180일은 10년 보관에 문제없음). Intelligent-Tiering은 접근 패턴을 모를 때 고르고, Standard-IA는 밀리초 접근이 필요한 드문 접근용입니다. Express One Zone은 초저지연용이라 정반대입니다.

Q8. (복습 0022) 출시 직후라 트래픽을 전혀 예측할 수 없고, 마케팅 이벤트 때마다 요청이 급증했다가 금방 줄어드는 새 앱이 DynamoDB를 씁니다. 용량 계획 부담 없이 쓴 만큼만 내려면?

온디맨드 모드는 용량 계획 없이 요청당 과금되고, 예측 불가 트래픽에 맞으며 대부분 워크로드의 기본·권장 옵션입니다. 프로비저닝 모드는 사용 여부와 관계없이 설정한 용량에 시간당 과금되므로 꾸준하고 예측 가능한 트래픽에서 유리합니다. DAX는 읽기 캐시이지 용량 모드 문제의 답이 아닙니다.

보지 말고 써 보세요. (1) 데이터 전송 요금: 인터넷 인바운드·아웃바운드, AZ 간, 리전 간, AWS 오리진 → CloudFront는 각각? (2) NAT 비용을 줄이는 두 가지 방법과, 공유 NAT의 복원력 문제. (3) Cost Explorer, Budgets, CUR/Data Exports, Compute Optimizer, Trusted Advisor를 한 줄씩.

(1) 인터넷 → AWS 무료, AWS → 인터넷 과금, AZ 간 과금(양방향 계량, 일부 서비스 예외), 리전 간은 보내는 리전 아웃바운드에 과금, AWS 오리진 → CloudFront 무료(뷰어로 나가는 전송만 과금).

(2) AZ마다 NAT를 두고 같은 AZ로 라우팅(또는 리소스를 NAT와 같은 AZ에), AWS 서비스 트래픽은 VPC 엔드포인트로(S3·DynamoDB 게이트웨이 엔드포인트는 추가 요금 없음). 공유 NAT는 그 AZ가 다운되면 다른 AZ 리소스도 인터넷 접근을 잃음.

(3) Cost Explorer: 13개월 분석·18개월 예측·RI 권장. Budgets: 실제/예측 임계값 알림과 예산 작업. CUR 2.0/Data Exports: 가장 상세한 데이터를 S3로, Athena 조회. Compute Optimizer: CloudWatch 지표 기반 적정 크기·유휴 리소스 권장. Trusted Advisor: 비용·성능·보안 등 모범 사례 점검표.
