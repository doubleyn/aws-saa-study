엣지 두 형제:
CloudFront vs Global Accelerator

둘 다 "전 세계 사용자에게 빠르게"를 약속하고 둘 다 AWS 엣지와 글로벌 네트워크를 씁니다. 차이는 하나입니다. CloudFront는 HTTP 콘텐츠를 캐시하고, Global Accelerator는 TCP/UDP 패킷을 프록시합니다. 이 한 줄이 보기 넷 중 둘을 지워 줍니다.

⏱ 약 20분🎯 오늘의 승리: 시나리오 8문항📌 치트시트 · 용어집

왜 이것부터인가

시험에서: Task 3.4가 엣지 네트워킹 서비스로 CloudFront와 Global Accelerator를 콕 집어 적고, Task 4.4는 CDN·엣지 캐싱의 전략적 필요와 Global Accelerator를 비용 관점에서 다시 묻습니다.[1]
실무에서: 정적 사이트·API 앞에 CloudFront를 두는 것은 거의 기본값이고, 게임·VoIP·고정 IP 요구가 나오면 Global Accelerator를 검토합니다.

CloudFront: 가장 가까운 엣지에서 캐시로 응답

CloudFront는 엣지 로케이션이라는 전 세계 데이터 센터 네트워크로 콘텐츠를 전달합니다. 요청은 지연 시간이 가장 낮은 엣지로 라우팅되고, 거기에 콘텐츠가 있으면 즉시 응답(캐시 적중), 없으면 오리진에서 가져옵니다.[2] 정적 콘텐츠뿐 아니라 동적 콘텐츠의 배포도 빠르게 합니다.

오리진

S3 버킷, Application Load Balancer, Network Load Balancer, Lambda 함수 URL, API Gateway, EC2 같은 커스텀 HTTP 서버를 오리진으로 쓸 수 있습니다. 오리진 그룹을 만들면 기본 오리진이 특정 HTTP 오류를 돌려줄 때 보조 오리진으로 자동 전환(오리진 장애 조치)합니다.[3]

S3 오리진 잠그기: OAC

사용자가 S3 URL로 우회하지 못하고 CloudFront를 통해서만 받게 하려면 오리진 액세스 제어(OAC)를 씁니다. AWS는 레거시 OAI 대신 OAC를 권장합니다. OAC는 모든 리전, SSE-KMS 암호화 객체, PUT/DELETE 같은 동적 요청을 지원하기 때문입니다.[4]

// S3 버킷 정책: 이 배포(distribution)를 통한 요청만 허용
{ "Effect": "Allow",
  "Principal": { "Service": "cloudfront.amazonaws.com" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::amzn-s3-demo-bucket/*",
  "Condition": { "StringEquals": {
    "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/EDFDVBD6EXAMPLE" } } }

0002의 리소스 기반 정책이 그대로 나옵니다. Principal은 CloudFront 서비스이고, Condition이 "내 배포만"으로 좁힙니다. SSE-KMS 객체라면 KMS 키 정책에도 CloudFront를 허용해야 합니다.[4] 주의: S3 웹사이트 엔드포인트로 설정한 버킷은 커스텀 오리진으로 다뤄져 OAC를 쓸 수 없습니다.[4]

ALB/EC2 오리진을 인터넷에 노출하고 싶지 않다면 VPC 오리진을 씁니다. 프라이빗 서브넷의 ALB, NLB, EC2를 오리진으로 두어 CloudFront를 단일 진입점으로 만듭니다.[5]

얼마나 오래 캐시하나: TTL

  • 캐시 정책을 쓰지 않으면 기본 TTL은 24시간입니다. 캐시 동작의 최소·최대·기본 TTL이나, 오리진이 보내는 Cache-Control: max-age(또는 s-maxage, Expires)로 조절합니다.[6]
  • TTL이 길면 캐시 적중이 늘고 오리진 부하가 줄어 성능이 좋아지고, 짧으면 동적 콘텐츠에 맞습니다.[6]
  • 만료 전에 지우려면 무효화(invalidation), 또는 파일 이름에 버전을 붙이는 방법이 있습니다. 자주 바뀌는 파일은 버전 이름이 권장되고 무효화 비용도 들지 않습니다.[7]

누가 볼 수 있나: 서명된 URL/쿠키, 지리적 제한

제한된 파일 여러 개(HLS 영상의 모든 조각, 회원 전용 영역), 지금 URL을 바꾸고 싶지 않음서명된 쿠키[8]

엣지에서 코드 실행 (포인터만)

CloudFront Functions: 1밀리초 미만의 가벼운 JavaScript. 헤더 조작, URL 리다이렉트·재작성, 캐시 키 정규화, 토큰 검증. 뷰어 요청/응답 이벤트만. Lambda@Edge: Node.js·Python, 더 긴 실행, 네트워크·파일 시스템·요청 본문 접근, 오리진 요청/응답 이벤트까지.[10] 시험 감각: "간단한 헤더/URL 처리, 초대량" → CloudFront Functions, "외부 서비스 호출, 본문 처리" → Lambda@Edge.

Global Accelerator: 고정 애니캐스트 IP + AWS 백본

Global Accelerator는 기본으로 정적 IPv4 주소 두 개(듀얼 스택이면 IPv4 2개 + IPv6 2개)를 주고, 이 주소는 AWS 엣지 네트워크에서 애니캐스트됩니다. 표준 가속기는 트래픽을 AWS 글로벌 네트워크로 실어 상태, 클라이언트 위치, 설정한 정책에 따라 최적의 리전 엔드포인트로 보냅니다. 엔드포인트는 NLB, ALB, EC2 인스턴스, 탄력적 IP이고 여러 리전에 둘 수 있습니다. 상태나 설정 변화에 즉시 반응해 정상 엔드포인트로만 보냅니다.[11]

  • TCP/UDP 애플리케이션 전반을 엣지에서 패킷을 프록시하는 방식으로 가속합니다. CloudFront는 캐시 가능한 콘텐츠와 동적 콘텐츠 쪽입니다.[12]
  • 리전 장애 조치: 기본 리전 엔드포인트가 실패하면 다음으로 가까운 가용 리전으로 즉시 재라우팅합니다. [13] 비정상 엔드포인트는 1분 이내에 감지해 제외합니다. 클라이언트와 리졸버가 DNS 응답을 오래 캐시할 수 있다는 점과 대비되는 것이, DNS 기반 장애 조치(Route 53, 0016) 대신 Global Accelerator를 고르는 이유입니다.[12]
  • 고정 IP 허용 목록: 클라이언트·방화벽에 IP 두 개만 한 번 등록하면, 뒤에서 엔드포인트를 추가·제거하거나 블루/그린 배포를 해도 IP가 바뀌지 않습니다. 진입점은 기본으로 AWS Shield의 DDoS 보호를 받습니다.[13]
  • 사용 사례: 게임, 미디어, 모바일, 광고 기술, 금융 같은 지연 민감 앱. 커스텀 라우팅 가속기는 사용자를 특정 EC2 인스턴스·포트에 매핑해야 하는 멀티플레이 게임, VoIP용입니다.[13]

시험 단골: 키워드 → 정답

정적 콘텐츠·이미지·영상, 전 세계, 오리진 부하 감소 → CloudFront · S3를 CloudFront로만 → OAC + 버킷 정책 · 유료 회원만 다운로드 → 서명된 URL(1개)/쿠키(여러 개) · 특정 국가 차단 → 지리적 제한 · UDP, 게임, VoIP, 비 HTTP → Global Accelerator · 고정 IP 두 개, 방화벽 허용 목록 → Global Accelerator · 멀티 리전, DNS 캐시 없이 빠른 장애 조치 → Global Accelerator

비용 덧붙임: S3, ELB, API Gateway 같은 AWS 오리진에서 CloudFront로 가는 전송은 무료이고, CloudFront에서 뷰어로 나가는 전송에만 과금됩니다.[2] 자주 접근되는 객체라면 S3에서 직접 내려보내는 것보다 CloudFront가 더 비용 효율적일 수 있다고 문서가 설명합니다.[3] 0026에서 이어집니다.

연습

Q1. 전 세계 사용자가 접속하는 멀티플레이어 게임이 UDP로 통신합니다. 지연과 지터를 줄이고, 리전 장애 시 다른 리전으로 빠르게 넘겨야 합니다. 가장 적합한 서비스는?

UDP는 HTTP 캐시 대상이 아니므로 CloudFront가 아닙니다. Global Accelerator는 TCP/UDP 트래픽을 애니캐스트 엣지에서 받아 AWS 백본으로 가까운 정상 리전에 보내고, 장애 시 즉시 다른 리전으로 재라우팅합니다. Route 53 지연 시간 라우팅도 리전을 고르지만 DNS라서 클라이언트의 DNS 캐시 때문에 전환이 느릴 수 있습니다(0016).

Q2. 정적 웹사이트를 S3에 두고 CloudFront로 배포합니다. 사용자가 S3 객체 URL로 직접 접근하지 못하게 하고, 객체는 SSE-KMS로 암호화되어 있습니다. 가장 적합한 방법은?

OAC는 SSE-KMS를 지원하며, 버킷 정책에서 cloudfront.amazonaws.com 서비스 주체와 AWS:SourceArn 조건으로 내 배포만 허용합니다(KMS 키 정책에도 허용 추가). 레거시 OAI는 SSE-KMS를 지원하지 않거나 우회가 필요하고, 웹사이트 엔드포인트는 커스텀 오리진이라 OAC를 쓸 수 없습니다.

Q3. 온라인 강의 플랫폼이 유료 회원에게만 강의 영상(HLS, 영상 하나당 수백 개 조각 파일)을 제공하려 합니다. 기존 URL 구조는 바꾸고 싶지 않습니다. 무엇을 써야 합니까?

여러 제한 파일(HLS 조각 전부)에 접근을 주고 URL을 바꾸지 않으려면 서명된 쿠키입니다. 서명된 URL은 파일 하나 단위라 조각마다 URL을 바꿔야 합니다. 지리적 제한은 회원 여부가 아니라 국가 기준입니다.

Q4. 금융 회사의 B2B 고객사들은 방화벽에서 IP 주소를 허용 목록으로만 열어 줍니다. 회사의 API는 두 리전의 NLB 뒤에서 돌고, 엔드포인트는 앞으로 자주 바뀝니다. 가장 적합한 설계는?

Global Accelerator의 정적 애니캐스트 IP는 가속기가 존재하는 동안 유지되므로, 고객사는 IP 두 개만 한 번 허용하면 됩니다. 뒤에서 엔드포인트를 추가·제거해도 IP는 그대로입니다. 도메인 공유는 IP 허용 목록 요구를 충족하지 못하고, CloudFront 엣지 IP 범위는 넓고 고정 두 개가 아닙니다.

Q5. 뉴스 사이트가 CloudFront로 이미지와 HTML을 배포합니다. 오리진 부하를 줄이면서, 기사 수정 시 바뀐 이미지가 빨리 보이게 하려 합니다. 적절한 조치는? (두 개를 고르세요)

긴 TTL(Cache-Control: max-age)은 캐시 적중을 늘려 오리진 부하를 줄이고, 바뀐 파일은 버전 이름으로 배포하면 즉시 새 파일이 나갑니다(무효화 비용도 없음). TTL 0초는 매번 오리진에 확인하러 가므로 부하 감소와 반대이고, CloudFront를 빼면 엣지 캐싱 이점이 사라집니다.

Q6. CloudFront 뷰어 요청마다 간단한 헤더를 추가하고 URL을 재작성해야 합니다. 초당 요청이 매우 많고, 외부 서비스 호출은 필요 없습니다. 운영과 비용 면에서 가장 적합한 것은?

CloudFront Functions는 1밀리초 미만의 가벼운 함수로 헤더 조작, URL 재작성에 맞고 초당 수백만 요청까지 확장됩니다. Lambda@Edge는 네트워크 접근이나 본문 처리처럼 더 무거운 작업이 필요할 때 고릅니다.

Q7. (복습 0011) CloudFront 오리진으로 쓰는 ALB가 인터넷에 노출되어 있어, 공격자가 CloudFront를 우회해 ALB로 직접 요청합니다. ALB와 EC2를 인터넷에서 완전히 숨기려면?

VPC 오리진은 프라이빗 서브넷의 ALB, NLB, EC2를 CloudFront 오리진으로 쓰게 해 CloudFront를 단일 진입점으로 만듭니다. NLB로 바꾸거나 Global Accelerator를 더해도 공개 진입점이 남습니다. 0.0.0.0/0 인바운드는 정반대 방향입니다(0005).

Q8. 영상 스트리밍 회사가 라이선스 계약상 특정 국가에서는 콘텐츠를 제공하면 안 됩니다. 배포 전체에 국가 단위로 적용하면 됩니다. 운영 오버헤드가 가장 적은 방법은?

배포 전체, 국가 단위라면 CloudFront의 지리적 제한이 가장 간단합니다(차단 시 403). 서드파티 위치 서비스는 국가보다 세밀하거나 일부 파일만 제한할 때 씁니다. Route 53 지리 위치 라우팅은 위치별로 다른 엔드포인트로 보내는 기능이지 접근 차단 기능이 아닙니다(0016).

기억에서 꺼내기

보지 말고 써 보세요. (1) CloudFront와 Global Accelerator를 가르는 기준 네 가지(프로토콜, 캐싱, 진입점, 장애 대응). (2) S3 오리진을 CloudFront로만 열 때의 설정 두 가지. (3) 서명된 URL과 서명된 쿠키는 각각 언제?

(1) CloudFront: HTTP/HTTPS, 엣지 캐시, 도메인 이름 진입, 오리진 그룹 장애 조치. Global Accelerator: TCP/UDP, 캐시 없음(패킷 프록시), 고정 애니캐스트 IP 두 개, 리전 엔드포인트 간 즉시 장애 조치.

(2) 배포에 OAC 연결 + 버킷 정책에서 Principal cloudfront.amazonaws.com, Condition AWS:SourceArn = 내 배포. SSE-KMS면 KMS 키 정책에도 허용. 웹사이트 엔드포인트 버킷은 OAC 불가.

(3) URL: 개별 파일, 쿠키 미지원 클라이언트. 쿠키: 여러 제한 파일, URL을 바꾸고 싶지 않을 때.
