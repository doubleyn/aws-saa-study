엣지 두 형제:
CloudFront vs Global Accelerator

Amazon CloudFront와 AWS Global Accelerator는 둘 다 "전 세계에 흩어진 사용자들에게 지연 시간을 최소화하여 최상의 속도를 제공한다"는 목표를 공유하며, 전 세계 AWS 엣지 인프라와 글로벌 사설 전용 백본망을 활용합니다. 하지만 두 서비스의 핵심 동작 원리는 완전히 다릅니다. CloudFront는 HTTP/HTTPS 웹 콘텐츠를 엣지에 캐싱하여 배포하고, Global Accelerator는 고정 애니캐스트 IP를 통해 일반 TCP/UDP 패킷을 엣지에서 받아 사설 백본망으로 프록시 전송합니다. 이 명확한 차이점 하나만 이해해도 시험 문제의 오답 보기 절반을 단번에 지울 수 있습니다.

왜 CloudFront와 Global Accelerator를 배워야 할까요?

시험 관점: SAA-C03 시험 가이드의 Task 3.4는 고성능 네트워크 아키텍처 설계를 다루며 CloudFront와 Global Accelerator의 차이와 사용 사례를 명시적으로 요구합니다. 또한 Task 4.4(비용 최적화)에서는 CDN 캐싱을 통한 데이터 전송 비용 절감 및 Global Accelerator의 네트워크 비용 효율성을 다각도로 평가합니다.[1]
실무 관점: 웹 사이트나 API 서버 앞단에 CloudFront를 두는 것은 성능 개선뿐 아니라 DDoS 방어 및 오리진 보호를 위한 필수 표준 설계입니다. 반면 전 세계를 무대로 하는 온라인 게임, 음성 통화(VoIP), 사설 방화벽의 IP 허용 목록 연동, 혹은 빠른 멀티 리전 장애 조치(Failover)가 필요할 때는 Global Accelerator가 대체 불가능한 핵심 솔루션이 됩니다.

CloudFront: 가장 가까운 엣지에서 캐시로 응답

Amazon CloudFront는 전 세계 수백 곳의 엣지 로케이션(Edge Location)과 리전 엣지 캐시(Regional Edge Cache)로 구성된 AWS 글로벌 네트워크를 통해 웹 콘텐츠를 신속하게 전달하는 콘텐츠 전송 네트워크(CDN: Content Delivery Network) 서비스입니다.[2]

동작 원리는 직관적입니다. 사용자의 웹 요청은 DNS 라우팅을 통해 물리적으로 가장 가까운 CloudFront 엣지 로케이션으로 연결됩니다. 요청한 파일이 해당 엣지의 캐시에 존재하면 오리진 서버까지 갈 필요 없이 즉시 응답(캐시 적중, Cache Hit)합니다. 캐시에 없다면(캐시 미스, Cache Miss) AWS의 최적화된 내부 네트워크 경로를 타고 오리진(Origin) 서버에서 원본을 가져와 캐시에 저장한 뒤 사용자에게 전달합니다. 정적 파일(이미지, CSS, JS, 동영상)의 캐싱은 물론이고, 동적 웹 요청 역시 엣지에서 사용자 연결을 빠르게 맺고(TLS 핸드셰이크 가속) 오리진과의 지속 연결 풀(Keep-alive)을 재활용하므로 전체적인 통신 속도가 크게 향상됩니다.

오리진(Origin)과 오리진 그룹(Origin Group)

CloudFront가 콘텐츠를 가져오는 원본 서버를 오리진(Origin)이라고 부릅니다. 지원되는 오리진은 다음과 같습니다:

  • Amazon S3 버킷: 정적 웹 호스팅 및 파일 저장소
  • Application Load Balancer (ALB) 및 Network Load Balancer (NLB): 동적 웹 애플리케이션 진입점
  • Amazon EC2 인스턴스: 자체 웹 서버
  • AWS Lambda 함수 URL 및 Amazon API Gateway: 서버리스 REST/HTTP API 백엔드
  • 온프레미스 웹 서버: 외부 퍼블릭 HTTP/HTTPS 엔드포인트

특히 고가용성이 필수적인 시스템에서는 오리진 그룹(Origin Group)을 구성할 수 있습니다. 기본 오리진(Primary)과 보조 오리진(Secondary)을 묶어 두고, 기본 오리진이 특정 HTTP 오류 코드(500, 502, 503, 504)를 반환하거나 연결 시간 초과가 발생하면 CloudFront가 사용자에게 에러를 보여주는 대신 보조 오리진으로 즉각 요청을 재시도(자동 오리진 장애 조치)합니다.[3]

S3 오리진 완벽 격리: OAC (Origin Access Control)

정적 웹사이트나 미디어 자산을 S3에 저장하고 CloudFront로 서비스할 때, 사용자가 S3의 직접 URL(bucket.s3.amazonaws.com/...)로 우회 접근하지 못하게 막고 오직 CloudFront 배포를 통해서만 데이터를 가져가도록 강제해야 합니다. 이를 구현하는 AWS의 최신 표준 기술이 바로 오리진 액세스 제어(OAC: Origin Access Control)입니다.[4]

과거에 사용되던 OAI(Origin Access Identity)는 이제 레거시 기술로 분류됩니다. OAC는 전 세계 모든 AWS 리전 지원, AWS KMS(SSE-KMS)로 암호화된 객체 완벽 지원, 그리고 PUT/DELETE 같은 동적 HTTP 메서드 지원 등 모든 면에서 우수하므로 시험과 실무 모두 OAC를 선택해야 합니다.

// S3 버킷 정책: 오직 특정 CloudFront 배포를 통한 s3:GetObject 요청만 허용
{
  "Version": "2012-10-17",
  "Statement": {
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": {
      "Service": "cloudfront.amazonaws.com"
    },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-secure-bucket/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/EDFDVBD6EXAMPLE"
      }
    }
  }
}

원리는 간단합니다. S3 버킷 정책에서 Principal로 CloudFront 서비스 주체(cloudfront.amazonaws.com)를 지정하고, Condition 절의 AWS:SourceArn으로 내 계정의 특정 CloudFront 배포 ARN을 지정하는 것입니다. 만약 S3 객체가 고객 관리형 KMS 키(SSE-KMS)로 암호화되어 있다면, 해당 KMS 키 정책(Key Policy)에도 CloudFront 서비스 주체에 대한 kms:Decrypt 권한이 추가되어야 합니다.[4]
주의할 점: S3 버킷의 "정적 웹 사이트 호스팅(Static website hosting)" 기능을 활성화하여 나오는 웹사이트 엔드포인트는 CloudFront에서 일반 커스텀 HTTP 오리진으로 취급되므로 OAC를 적용할 수 없습니다. OAC를 적용하려면 반드시 S3의 표준 REST API 엔드포인트를 오리진으로 지정해야 합니다.[4]

VPC 오리진: 프라이빗 ALB/EC2 오리진 보호

만약 CloudFront의 오리진이 프라이빗 서브넷에 위치한 내부 Application Load Balancer(ALB)나 EC2 인스턴스라면 어떻게 해야 할까요? 과거에는 ALB를 퍼블릭에 노출하고 사용자 정의 비밀 헤더를 검증해야 했지만, 이제는 CloudFront VPC 오리진(VPC Origins) 기능을 사용하여 프라이빗 서브넷에 있는 내부 ALB, NLB, EC2로 직접 안전한 트래픽을 전달할 수 있습니다. 인터넷에 애플리케이션 진입점을 전혀 노출하지 않고 CloudFront만을 단일 보안 관문으로 운영할 수 있습니다.[5]

캐시 유효 기간(TTL)과 무효화(Invalidation)

  • TTL (Time To Live): 객체가 엣지 캐시에 머무는 유효 기간입니다. 캐시 정책(Cache Policy)을 명시하지 않을 경우 기본 TTL은 24시간입니다. 최소(Min), 최대(Max), 기본(Default) TTL을 설정하거나, 오리진 웹 서버가 응답 헤더로 보내는 Cache-Control: max-age=... (또는 s-maxage, Expires)를 기준으로 동작합니다.[6]
  • 오리진 부하 절감: 자주 변경되지 않는 정적 파일에 긴 TTL(예: 30일)을 지정하면 엣지 캐시 적중률이 극대화되어 오리진 서버의 CPU 및 네트워크 부하를 거의 제로에 가깝게 줄일 수 있습니다.[6]
  • 캐시 갱신 전략: 파일이 변경되었을 때 엣지의 캐시를 갱신하는 방법은 두 가지입니다.
    1. 버전이 포함된 파일명 사용 (권장, Best Practice): main.v2.css, logo_20261117.png처럼 파일명 자체에 버전을 부여하는 방식입니다. 배포 즉시 새로운 파일로 인식되므로 전 세계 엣지에서 즉시 새 파일이 서비스되며, 캐시 갱신 비용이 전혀 들지 않습니다.[7]
    2. 캐시 무효화 (Cache Invalidation): 동일한 파일명을 유지하면서 강제로 엣지 캐시를 비우려면 무효화 요청(예: /images/*, /index.html)을 생성합니다. 매월 첫 1,000개 경로는 무료이지만 이후 건당 비용이 발생하므로 빈번한 변경에는 버전화된 파일명이 훨씬 유리합니다.[7]

접근 제어와 보안: 서명된 URL/쿠키, 지리적 제한

요구 사항권장 솔루션 및 동작 방식
단일 개별 파일(예: 설치 파일 다운로드, 특정 문서 열람)에 대한 임시 권한 부여, 또는 쿠키를 지원하지 않는 모바일 클라이언트CloudFront 서명된 URL (Signed URL): 만료 시간, 허용 IP 등의 조건이 암호화된 URL 파라미터로 포함되며, 지정된 시간이 지나면 링크가 자동 만료됩니다.[8]
여러 개의 제한된 파일(예: 유료 회원 전용 강의 페이지의 수백 개 HLS 영상 세그먼트 파일들), 또는 기존 애플리케이션의 URL 구조를 전혀 바꾸고 싶지 않은 경우CloudFront 서명된 쿠키 (Signed Cookie): 클라이언트 브라우저에 서명된 세션 쿠키를 한 번 발급하면, 사용자는 URL을 변경하지 않고도 권한이 필요한 여러 미디어 파일이나 웹 페이지를 자유롭게 요청할 수 있습니다.[8]
저작권 계약이나 규제로 인해 특정 국가에서의 접속을 배포 전체 수준에서 원천 차단하거나 특정 국가만 허용하려는 경우CloudFront 지리적 제한 (Geographic Restrictions): 전 세계 엣지에서 사용자의 접속 IP를 기반으로 국가 단위 허용 목록(Allowlist) 또는 차단 목록(Blocklist)을 구성합니다. 차단된 국가의 사용자는 오리진에 도달하기 전 엣지에서 즉시 HTTP 403 Forbidden 응답을 받습니다.[9]

엣지 컴퓨팅: CloudFront Functions vs Lambda@Edge

CloudFront 엣지에서 가벼운 로직을 서버 없이 실행할 수 있는 두 가지 도구가 있습니다:

  • CloudFront Functions: 전 세계 600개 이상의 모든 엣지 로케이션에서 1밀리초 미만의 초고속으로 실행되는 경량 JavaScript 런타임입니다. 초당 수백만 건의 대규모 요청도 매우 저렴하게 처리할 수 있습니다. 뷰어 요청(Viewer Request) 및 뷰어 응답(Viewer Response) 이벤트에서만 동작하며, 외부 네트워크 호출이나 요청 본문(Body) 접근은 불가능합니다. HTTP 헤더 조작, URL 리다이렉트 및 재작성(Rewrite), 캐시 키 정규화, 간단한 JWT 토큰 검증에 최적화되어 있습니다.[10]
  • Lambda@Edge: 리전 엣지 캐시에서 실행되는 정규 Node.js 및 Python 런타임입니다. 최대 수초 동안 복잡한 로직을 수행할 수 있으며, 외부 API나 서드파티 데이터베이스 네트워크 통신, 파일 시스템 접근, HTTP 요청 본문(Body) 조작이 가능합니다. 뷰어 요청/응답뿐 아니라 오리진 요청/응답(Origin Request/Response) 이벤트에서도 실행됩니다. 복잡한 인증 로직, 서버 측 렌더링, 외부 인증 서비스 연동 등에 사용됩니다.[10]

Global Accelerator: 고정 애니캐스트 IP + AWS 백본망

AWS Global Accelerator는 전 세계 사용자를 대상으로 로컬 및 글로벌 애플리케이션의 가용성과 성능을 극대화해 주는 고성능 네트워크 서비스입니다.[11]

Global Accelerator를 생성하면 인터넷 진입점으로 두 개의 고정(정적) Anycast IPv4 주소가 부여됩니다. 전 세계 사용자가 이 고정 IP로 접속하면, 공용 인터넷망을 타고 길게 돌아가는 대신 물리적으로 가장 가까운 AWS 엣지 로케이션을 통해 즉시 AWS 사설 글로벌 백본망에 진입합니다. 그리고 혼잡이 없고 모니터링되는 초고속 AWS 전용망을 거쳐 대상 리전의 엔드포인트(ALB, NLB, EC2, 탄력적 IP)로 직접 패킷이 전송됩니다.[11]

  • TCP/UDP 전 프로토콜 지원: CloudFront가 HTTP/HTTPS 캐싱 중심이라면, Global Accelerator는 일반 TCP 및 UDP 패킷 전체를 엣지에서 가속합니다. 온라인 게임, 음성 및 화상 통화(VoIP), IoT(MQTT), 금융 거래 등 지연 시간에 극도로 민감한 비 HTTP 애플리케이션에 이상적입니다.[12]
  • DNS 캐싱 없는 즉각적인 리전 장애 조치(Instant Failover): 글로벌 액셀러레이터는 백엔드 엔드포인트들의 상태(Health Check)를 지속적으로 감시합니다. 주 리전에 장애가 발생하면 1분 이내에 트래픽을 다음으로 가까운 정상 리전으로 자동 전환합니다.[13] Amazon Route 53의 DNS 기반 장애 조치는 클라이언트나 ISP의 DNS 리졸버가 캐시(TTL)를 만료시키기 전까지 장애 리전으로 계속 요청을 보내는 문제가 있지만, Global Accelerator는 IP 자체가 고정되어 있고 AWS 내부 네트워크 레벨에서 라우팅을 즉각 전환하므로 DNS 캐싱 지연 문제가 원천적으로 발생하지 않습니다.[12]
  • 방화벽 허용 목록용 불변의 고정 IP: 고객사 기업 방화벽이나 클라이언트 보안 정책상 도메인 이름이 아닌 "고정 IP 주소 허용 목록(Allowlist)"을 요구하는 B2B 엔터프라이즈 환경에 완벽합니다. 백엔드에서 서버를 교체하거나 블루/그린 배포를 수행하거나 리전을 추가하더라도, 고객이 바라보는 2개의 애니캐스트 IP 주소는 절대 바뀌지 않습니다. 또한 진입점에는 AWS Shield Standard가 기본 적용되어 자동 DDoS 보호를 제공합니다.[13]
  • 사용자 지정 라우팅(Custom Routing): 특정 사용자를 특정 EC2 인스턴스의 특정 포트(예: 배틀로얄 게임 세션 룸, 실시간 음성 채널)로 결정론적으로 매핑해야 하는 특수 워크로드를 지원합니다.[13]

시험에 자주 나오는 핵심 패턴: 키워드 → 정답 공식

비용 팁: AWS 오리진(S3 버킷, ALB, API Gateway 등)에서 CloudFront로 이동하는 데이터 전송 요금은 100% 무료(0달러)입니다. 오직 CloudFront 엣지에서 사용자(뷰어)로 나가는 아웃바운드 트래픽에 대해서만 과금되며, 대용량 트래픽의 경우 S3에서 인터넷으로 직접 데이터를 쏘는 것보다 CloudFront를 거치는 것이 데이터 전송 단가 면에서 훨씬 경제적입니다.[2][3]

연습

Q1. 전 세계 사용자가 접속하는 글로벌 실시간 멀티플레이어 액션 게임 서버가 UDP 프로토콜을 사용해 통신하고 있습니다. 지연 시간과 네트워크 지터를 최소화해야 하며, 주 리전의 인프라 장애 발생 시 수초~수분 이내에 대기 리전으로 트래픽을 즉각 안전하게 넘겨야 합니다. 가장 적합한 서비스는 무엇입니까?

정답은 AWS Global Accelerator 표준 가속기입니다.
게임 애플리케이션의 핵심 조건은 UDP 프로토콜 지원과 DNS 캐싱 지연 없는 신속한 리전 페일오버입니다. Global Accelerator는 TCP 및 UDP 패킷을 가장 가까운 AWS 엣지에서 애니캐스트로 수신하여 초고속 사설 백본망으로 중계하며, 백엔드 헬스체크를 통해 장애 발생 시 DNS 캐싱과 무관하게 내부 네트워크 레벨에서 1분 이내에 트래픽을 다른 정상 리전으로 즉시 우회시킵니다.
- 오답 분석: - CloudFront + Lambda@Edge: CloudFront는 HTTP/HTTPS 웹 트래픽 전용 CDN 서비스이므로 UDP 통신을 지원하지 않습니다. - Route 53 지연 시간 라우팅: DNS 기반 라우팅은 클라이언트 기기나 로컬 ISP 리졸버의 DNS 캐시(TTL) 때문에 장애 발생 후에도 이전 IP로 계속 패킷을 보내는 지연 문제가 발생합니다. - S3 Transfer Acceleration: S3로의 대용량 파일 업로드/다운로드 전용 기능입니다.

Q2. 한 기업이 S3 버킷에 저장된 정적 웹사이트 자산을 CloudFront 배포를 통해 서비스하고 있습니다. 모든 S3 객체는 AWS KMS 고객 관리형 키(SSE-KMS)로 암호화되어 있습니다. 사용자가 S3 객체 URL로 직접 우회 접근하는 것을 원천 차단하고 오직 CloudFront를 거쳐서만 접근하도록 구성하려 합니다. 가장 적합한 방법은 무엇입니까?

정답은 오리진 액세스 제어(OAC)를 설정하고 버킷 정책에서 해당 배포 ARN만 허용하는 것입니다.
AWS의 최신 표준인 OAC(Origin Access Control)는 SSE-KMS 암호화된 S3 객체를 완벽히 지원합니다. S3 버킷 정책에서 cloudfront.amazonaws.com 서비스 주체를 허용하고, AWS:SourceArn 조건으로 특정 CloudFront 배포 ARN을 지정하면 직접 우회 접근이 완벽히 차단됩니다(KMS 키 정책에도 복호화 권한 추가).
- 오답 분석: - 퍼블릭 버킷 + Referer 헤더: Referer 헤더는 클라이언트가 손쉽게 위조할 수 있어 보안 통제로 적합하지 않으며, 버킷을 퍼블릭으로 여는 것은 심각한 보안 결함입니다. - 레거시 OAI: 기존 OAI(Origin Access Identity)는 SSE-KMS로 암호화된 S3 객체에 대한 접근을 지원하지 않습니다. - S3 웹사이트 엔드포인트: 정적 웹 호스팅 엔드포인트는 일반 커스텀 HTTP 오리진으로 취급되어 OAC 기능을 적용할 수 없습니다.

Q3. 한 온라인 교육 플랫폼이 유료 구독 회원에게만 프리미엄 동영상 강의를 스트리밍(HLS 프로토콜, 비디오 하나당 수백 개의 .ts 세그먼트 조각 파일로 분할됨)으로 제공하려 합니다. 애플리케이션의 기존 비디오 URL 구조를 일일이 변경하지 않고 회원 인증을 처리할 수 있는 가장 적합한 CloudFront 보안 기능은 무엇입니까?

정답은 CloudFront 서명된 쿠키(Signed Cookies)를 발급하는 것입니다.
HLS 스트리밍처럼 하나의 콘텐츠가 수백~수천 개의 미디어 파일 조각들로 구성되어 있거나, 웹사이트의 URL 체계를 그대로 유지하면서 다수의 보호된 리소스에 한 번에 접근 권한을 부여해야 할 때는 서명된 쿠키(Signed Cookies)가 유일하고 완벽한 해법입니다. 사용자가 로그인하면 인증 서버가 서명된 쿠키를 브라우저에 설정해 주고, 이후 브라우저가 요청하는 모든 세그먼트 파일에 동일한 쿠키가 자동으로 실려 가므로 URL 수정이 전혀 필요 없습니다.
- 오답 분석: - 서명된 URL: 개별 파일 하나마다 서명 파라미터가 붙은 고유 URL을 생성해야 하므로, 수백 개의 HLS 영상 조각 파일들을 매번 URL 변경하며 처리하기에는 극도로 비효율적입니다. - 지리적 제한: 국가 단위 접근 통제일 뿐 개별 유료 회원 인증 기능이 아닙니다. - S3 미리 서명된 URL: CloudFront 캐싱 이점을 활용하지 못하고 S3로 직접 유입되며, 세그먼트마다 URL을 발급해야 하는 한계가 동일합니다.

Q4. 한 금융 핀테크 기업의 글로벌 B2B 고객사들은 사내 엄격한 보안 규정으로 인해 방화벽의 아웃바운드 규칙에 오직 고정된 IP 주소만을 허용 목록(Allowlist)으로 등록할 수 있습니다. 기업의 API 백엔드는 두 개 AWS 리전의 Network Load Balancer(NLB) 뒤에서 가동 중이며, 향후 인프라 업데이트 시 백엔드 엔드포인트가 변경될 수 있습니다. 고객사 방화벽 변경을 최소화하는 가장 적합한 아키텍처는 무엇입니까?

정답은 AWS Global Accelerator를 생성하고 2개의 고정 Anycast IP 주소를 공유하는 것입니다.
Global Accelerator는 가속기가 유지되는 동안 절대로 변경되지 않는 2개의 정적 Anycast IPv4 주소를 제공합니다. B2B 고객사 방화벽에 이 2개 IP만 최초 1회 등록해 두면, 백엔드에서 서버를 교체하거나 다른 리전으로 페일오버하더라도 고객사 방화벽 설정을 다시 수정할 필요가 전혀 없습니다.
- 오답 분석: - 각 NLB IP 전달: 백엔드 변경이나 리전 전환 시마다 고객사 보안팀에 방화벽 변경을 계속 요청해야 하므로 심각한 운영 오버헤드가 발생합니다. - CloudFront 엣지 IP 대역: CloudFront의 엣지 IP 범위는 전 세계 수백 개 대역으로 구성되어 있으며 수시로 동적으로 변경되므로 기업 방화벽 허용 목록용으로 사용할 수 없습니다. - Route 53 도메인 공유: 고객사는 도메인이 아닌 고정 IP 주소 허용 목록만을 지원하므로 요구 사항을 충족하지 못합니다.

Q5. 대형 뉴스 포털 웹사이트가 CloudFront를 통해 기사 본문과 수만 개의 이미지 자산을 배포하고 있습니다. 오리진 웹 서버의 CPU 및 대역폭 부하를 대폭 줄이면서도, 기사 수정 시 교체된 이미지가 전 세계 독자들에게 지연 없이 즉시 반영되도록 구성하려 합니다. 가장 비용 효율적인 두 가지 조치는 무엇입니까? (두 개를 고르세요)

정답은 버전이 포함된 파일명 배포(1)와 긴 max-age 헤더 설정(4)입니다.
1. 긴 max-age 설정: 정적 이미지에 긴 TTL을 지정하면 전 세계 엣지 캐시 적중률이 극대화되어 오리진 서버로 들어오는 중복 요청과 부하를 거의 완벽하게 없앨 수 있습니다.
2. 버전이 포함된 파일명(Versioned Filename): 이미지가 수정되었을 때 URL 파일명을 변경하면(예: header_v2.png), 엣지는 이를 즉각 새로운 파일로 인식하여 오리진에서 새로 가져옵니다. 추가적인 캐시 무효화(Invalidation) 비용이 전혀 들지 않고 즉각적인 변경 반영이 가능한 공식 모범 사례입니다.
- 오답 분석: - TTL 0초 설정: 엣지 로케이션이 매 요청마다 오리진에 유효성을 검증하러 가므로 오리진 부하 감소 목표와 정반대 결과를 초래합니다. - NAT 게이트웨이 추가: 아웃바운드 인터넷 접속 장치일 뿐 인바운드 웹 트래픽 캐싱과 무관합니다. - CloudFront 제거: 전 세계 엣지 캐싱 혜택을 포기하고 모든 트래픽이 원본 S3로 집중되어 비용과 부하가 폭증합니다.

Q6. CloudFront로 들어오는 뷰어 요청(Viewer Request)마다 간단한 HTTP 헤더를 추가하고 특정 URL 경로를 표준 형식으로 재작성(Rewrite)해야 합니다. 초당 수백만 건의 대규모 요청이 지속적으로 인입되며, 외부 서드파티 네트워크 호출이나 데이터베이스 조회가 전혀 필요하지 않습니다. 가장 비용 효율적이고 지연 시간이 짧은 솔루션은 무엇입니까?

정답은 CloudFront Functions를 뷰어 요청 이벤트에 연결하는 것입니다.
CloudFront Functions는 초당 수백만 건 이상의 대규모 요청을 1밀리초 미만의 초저지연으로 처리할 수 있도록 설계된 초경량 JavaScript 엣지 컴퓨팅 엔진입니다. 외부 네트워크 호출이 필요 없는 단순 헤더 조작, URL 재작성, 토큰 검증 시나리오에서 Lambda@Edge 대비 약 1/6 수준의 저렴한 비용으로 최고의 성능을 제공합니다.
- 오답 분석: - Lambda@Edge: 외부 네트워크 호출, 본문(Body) 파싱, 복잡한 컴퓨팅이 필요한 고중량 작업에 적합하며, 단순 헤더/URL 조작에 쓰기에는 비용과 실행 지연(수십 밀리초)이 상대적으로 큽니다. - ALB 리스너 규칙: 엣지가 아닌 오리진 리전까지 요청이 도달해야 하므로 엣지 레벨의 지연 시간 단축 효과를 누릴 수 없습니다. - EC2 리버스 프록시: 인프라 관리 부담, 고가용성 구성, 높은 상시 인스턴스 비용이 발생합니다.

Q7. (복습 0011) CloudFront 배포의 오리진으로 사용 중인 Application Load Balancer(ALB)가 현재 인터넷에 퍼블릭으로 노출되어 있습니다. 이로 인해 일부 악성 사용자들이 CloudFront의 보안 검사와 WAF를 우회하여 ALB의 DNS 주소로 직접 HTTP 요청을 보내고 있습니다. ALB와 백엔드 EC2 인스턴스들을 인터넷에서 완전히 은폐하고 오직 CloudFront만을 유일한 공개 진입점으로 강제하는 가장 안전한 설계는 무엇입니까?

정답은 ALB를 프라이빗 서브넷의 내부 로드 밸런서로 두고 CloudFront VPC 오리진을 연결하는 것입니다.
CloudFront의 VPC 오리진(VPC Origins) 기능을 사용하면, VPC 내부 프라이빗 서브넷에 위치한 내부 ALB나 NLB, EC2를 CloudFront의 오리진으로 직접 연결할 수 있습니다. ALB에 퍼블릭 IP나 인터넷 게이트웨이 경로를 부여할 필요가 전혀 없으므로, 외부 공격자가 ALB로 직접 우회 접속하는 경로가 물리적으로 원천 차단됩니다.
- 오답 분석: - NLB 교체: 퍼블릭 IP가 여전히 인터넷에 노출되어 우회 공격을 막지 못합니다. - 0.0.0.0/0 개방: 전 세계 누구나 ALB로 직접 들어올 수 있게 만드는 최악의 보안 구성입니다. - Global Accelerator 추가: 공개 진입점이 하나 더 늘어날 뿐 인터넷 직접 접근 차단 해결책이 아닙니다.

Q8. 글로벌 미디어 스트리밍 플랫폼이 콘텐츠 배급 라이선스 계약에 따라 특정 국가의 사용자들에게는 동영상 콘텐츠를 일절 제공해서는 안 됩니다. 이 제한은 배포 전체에 국가 단위로 일괄 적용되어야 합니다. 개발 및 운영 오버헤드가 가장 적은 구현 방법은 무엇입니까?

정답은 CloudFront 지리적 제한(Geographic Restrictions) 차단 목록을 구성하는 것입니다.
CloudFront에 기본 내장된 지리적 제한(Geographic Restrictions) 기능은 배포 전체에 대해 국가 단위의 허용 목록(Allowlist) 또는 차단 목록(Blocklist)을 클릭 몇 번으로 손쉽게 설정할 수 있습니다. 차단된 국가에서 들어오는 요청은 엣지 로케이션에서 오리진으로 가지 않고 즉각 HTTP 403 Forbidden 에러로 차단되므로, 별도의 코드 작성이나 외부 서비스 연동 없이 최소한의 관리 노력으로 라이선스 요건을 완벽히 준수할 수 있습니다.
- 오답 분석: - 서드파티 위치 서비스 연동: 외부 API 호출 비용과 추가적인 애플리케이션 개발/유지보수 부담이 발생합니다(도시 단위나 특정 파일별 제한 같은 고도로 세분화된 요구에만 필요). - Route 53 지리 위치 라우팅: 사용자의 위치에 따라 서로 다른 리소스 엔드포인트로 안내(라우팅)해 주는 기능이지, 특정 국가의 접근을 차단하는 보안 장치가 아닙니다. - Lambda@Edge 코드 개발: 내장 기능으로 해결 가능한 요구에 불필요하게 커스텀 코드와 추가 실행 비용을 유발합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속에서 직접 떠올려 적어 보세요.
(1) CloudFront와 Global Accelerator의 4대 차이점(지원 프로토콜, 엣지 캐싱 유무, 클라이언트 진입점, 장애 대응 방식)은 무엇인가요?
(2) S3 버킷을 오직 CloudFront 배포를 통해서만 접근하도록 제한할 때 필요한 두 가지 핵심 구성(OAC 및 정책)은 무엇인가요?
(3) CloudFront 서명된 URL(Signed URLs)과 서명된 쿠키(Signed Cookies)는 각각 어떤 상황에서 선택해야 하나요?

(1) CloudFront vs Global Accelerator 4대 기준:
- 프로토콜: CloudFront는 HTTP/HTTPS 웹 콘텐츠 / Global Accelerator는 TCP 및 UDP 전반(게임, VoIP, IoT 등)
- 엣지 캐싱: CloudFront는 지원(오리진 부하 및 전송비 절감) / Global Accelerator는 캐싱 없음(사설 전용망 패킷 프록시)
- 진입점: CloudFront는 도메인 이름(d111.cloudfront.net) / Global Accelerator는 2개의 고정 Anycast IP 주소(방화벽 허용 목록에 유리)
- 장애 대응: CloudFront는 오리진 그룹(5xx 에러 시 보조 오리진) / Global Accelerator는 1분 이내 AWS 내부 네트워크 차원의 즉각적인 리전 페일오버(DNS 캐싱 지연 없음)

(2) S3 오리진 보호 (OAC):
- CloudFront 배포 설정에서 S3 오리진에 최신 OAC(Origin Access Control)를 연결.
- S3 버킷 정책에서 Principal을 cloudfront.amazonaws.com으로 지정하고, Condition에서 AWS:SourceArn을 해당 CloudFront 배포 ARN으로 제한.
- (SSE-KMS 암호화 객체인 경우 KMS 키 정책에도 CloudFront 서비스 주체 복호화 허용 추가. S3 웹사이트 엔드포인트는 OAC 불가)

(3) 서명된 URL vs 서명된 쿠키:
- 서명된 URL: 개별 파일 하나(다운로드 설치 파일, 특정 PDF 문서), 또는 쿠키를 지원하지 않는 클라이언트.
- 서명된 쿠키: 여러 개의 보호된 파일(HLS 비디오 스트리밍의 수백 개 세그먼트 파일, 유료 회원 전용 영역), 또는 기존 웹사이트의 URL 경로를 변경하고 싶지 않을 때.

추가 학습 및 실습

공식 1차 자료 추천 (필독, 약 10분 소요): AWS 공식 문서의 "Restrict access to an Amazon S3 origin (OAC)"를 꼭 정독해 보세요. OAC와 레거시 OAI의 차이점, 버킷 정책 실제 작성 예시, SSE-KMS 키 정책 연동까지 시험에 출제되는 모든 S3+CloudFront 보안 요소가 한눈에 정리되어 있습니다. Global Accelerator의 실전 적용 패턴은 "Understanding AWS Global Accelerator use cases" 문서를 함께 참고하세요. (한국어 번역 문서는 URL의 docs.aws.amazon.com/ 뒤에 ko_kr/를 추가하면 열람 가능합니다.)

간단 실습 가이드 (비용 거의 없음): 퍼블릭 액세스가 완전히 차단된 S3 버킷을 하나 생성하고 index.html을 업로드한 뒤, CloudFront 콘솔에서 새 배포를 생성해 보세요. 원본 도메인으로 해당 S3 버킷을 선택하고 "오리진 액세스 제어(OAC)"를 활성화한 후 콘솔에서 복사해 주는 S3 버킷 정책을 버킷에 붙여넣습니다. 브라우저에서 S3 객체 URL로 접근하면 AccessDenied(403)가 뜨지만, CloudFront 배포 도메인 주소로는 정상적으로 웹페이지가 열리는 것을 직접 확인해 보세요. (실습 완료 후 생성된 CloudFront 배포는 비활성화 후 삭제하세요. Global Accelerator는 가속기 생성 시 고정 시간 요금이 발생하므로 실습은 콘솔 구경 정도로만 진행하시길 권장합니다.)
