Q1. 대형 온라인 쇼핑몰의 주문 접수 시스템에서 반짝 타임세일 프로모션 때마다 주문 요청이 일시적으로 수십 배 폭증하여 백엔드 주문 처리 서버가 부하를 감당하지 못하고 일부 주문 데이터가 유실되는 심각한 장애가 발생하고 있습니다. 비즈니스 요건상 주문 처리가 몇 분 정도 지연되는 것은 허용되지만, 접수된 주문이 단 한 건도 유실되어서는 안 됩니다. 최소한의 개발 및 운영 오버헤드로 이 문제를 해결할 수 있는 가장 적합한 아키텍처는 무엇입니까?

정답은 주문 웹 서버와 백엔드 처리 서버 사이에 Amazon SQS 대기열을 배치하는 것입니다.
"예측할 수 없는 일시적 트래픽 폭증(Spike) + 처리 지연 허용 + 데이터 유실 절대 불가"는 메시지 큐인 Amazon SQS를 도입하여 생산자와 소비자를 비동기적으로 분리(Decoupling)하고 버퍼링해야 하는 대표적인 시나리오입니다. SQS는 사전 프로비저닝 없이도 무제한에 가깝게 메시지를 수신하여 안전하게 보관하며(기본 4일, 최대 14일), 백엔드 서버는 자신의 처리 능력에 맞춰 큐에서 주문을 하나씩 안정적으로 폴링해 처리하므로 부하 폭증에도 데이터 유실이 원천적으로 방지됩니다.[3]
- 오답 분석: - 인스턴스 Scale-Up: 평소에는 막대한 비용 낭비가 발생하고, 서버가 감당할 수 있는 최대치를 넘는 순간 다시 장애가 발생하므로 근본적인 해결책이 아닙니다. - SNS 직접 푸시: SNS는 구독자에게 즉시 메시지를 밀어 넣는(Push) 방식입니다. 처리 서버가 과부하로 다운되어 있으면 메시지를 받을 수 없어 유실 위험이 여전히 남습니다(AWS 공식 가이드도 유실 방지를 위해 SNS 뒤에 SQS를 두는 팬아웃 패턴을 권장함).[3] - Route 53 가중치 라우팅: DNS 수준의 트래픽 분배일 뿐 백엔드 인스턴스들의 전체 처리 용량 부족 문제를 해결하지 못합니다.

도메인 2 (복원력) · 0014 느슨한 결합

Q2. 한 기업의 데이터 수집 애플리케이션 EC2 인스턴스들이 VPC 내 프라이빗 서브넷에 배치되어 있으며, 동일 리전의 Amazon S3 버킷으로 매일 수십 테라바이트의 분석 데이터를 저장하고 있습니다. 사내 보안 규정상 이 데이터 전송 트래픽이 퍼블릭 인터넷 게이트웨이나 NAT 장치를 일절 경유하지 않아야 하며, 재무팀은 추가적인 네트워크 게이트웨이 시간당 비용이나 데이터 처리 요금이 발생하지 않기를 요구합니다. 어떤 조치를 취해야 합니까?

정답은 S3 전용 게이트웨이 VPC 엔드포인트를 생성하고 라우팅 테이블에 연결하는 것입니다.
Amazon VPC의 게이트웨이 엔드포인트(Gateway Endpoint)는 인터넷 게이트웨이나 NAT 장치 없이도 VPC 내부에서 S3 및 DynamoDB로 사설 직통 연결을 제공하며, 시간당 요금과 데이터 처리 요금이 완전히 무료(0원)입니다.[4] 라우팅 테이블에 엔드포인트 대상 경로만 등록하면 모든 보안 및 비용 제약 조건을 완벽히 충족합니다.
- 오답 분석: - NAT 게이트웨이 배포: "NAT를 거치지 말아야 한다"는 보안 요건을 정면 위반하며, 수십 TB에 달하는 막대한 GB당 NAT 데이터 처리 요금이 청구됩니다. - 탄력적 IP(EIP) 할당: 퍼블릭 IP로 인터넷 게이트웨이를 통해 통신하게 되므로 프라이빗 서브넷의 보안 원칙을 파괴합니다. - Site-to-Site VPN: 온프레미스 IDC와 VPC를 연결하는 IPsec VPN 기술로 동일 리전 내 VPC-S3 연결에 사용되지 않습니다.

Q3. 한 미디어 기업이 매일 자정부터 수 시간 동안 대규모 동영상 인코딩 및 렌더링 배치 작업을 실행합니다. 이 애플리케이션은 분산 아키텍처로 개발되어 5분마다 진행 상황을 외부 스토리지에 체크포인트로 저장하므로, 작업 도중 특정 컴퓨팅 인스턴스가 갑자기 중단되더라도 언제든 마지막 체크포인트부터 안전하게 이어서 실행할 수 있습니다. 또한 작업은 다음 날 오전 8시 전까지만 완료되면 충분합니다. 가장 비용 효율적인 EC2 인스턴스 구매 옵션은 무엇입니까?

정답은 스팟 인스턴스(Spot Instances)를 사용하는 것입니다.
"중단(Interruption)을 허용할 수 있음 + 체크포인트 재개 가능 + 완료 시간에 유연성이 있음"은 스팟 인스턴스 도입을 위한 완벽한 전제 조건입니다. 스팟 인스턴스는 AWS의 유휴 여유 컴퓨팅 용량을 온디맨드 대비 최대 90%까지 파격적으로 할인된 가격으로 제공합니다. AWS가 용량 회수를 위해 2분 전 중단 통지를 보내더라도 체크포인트가 있으므로 안전하게 작업을 복원할 수 있습니다.[5]
- 오답 분석: - 예약 인스턴스(RI) 및 Savings Plans: 하루 24시간 연중무휴 실행되는 고정 워크로드에 대한 장기 약정(1년/3년) 할인 모델입니다. 매일 밤 몇 시간만 실행되는 작업에 장기 약정을 거는 것은 막대한 미사용 유휴 비용을 발생시킵니다. - 온디맨드: 안정적이지만 할인이 전혀 적용되지 않아 비용 최적화 요구를 충족하지 못합니다.

Q4. 한 모바일 게임의 실시간 글로벌 리더보드 데이터가 Amazon DynamoDB 테이블에 저장되어 있습니다. 수백만 명의 활성 플레이어로 인해 동일한 상위 랭킹 데이터 항목들을 반복해서 읽어 들이는 읽기 요청이 극단적으로 집중되고 있습니다. 이로 인해 읽기 응답 지연 시간이 한 자릿수 밀리초(ms) 수준으로 측정되고 있는데, 이를 마이크로초(μs) 수준으로 대폭 단축해야 합니다. 또한 기존 게임 애플리케이션의 데이터베이스 액세스 코드는 거의 수정하지 않아야 합니다. 어떤 조치를 취해야 합니까?

정답은 DynamoDB Accelerator(DAX) 클러스터를 배치하는 것입니다.
DynamoDB Accelerator(DAX)는 DynamoDB 전용 완전 관리형 인메모리 캐시 서비스로, 초당 수백만 건의 읽기 요청에 대해 응답 지연 시간을 밀리초에서 마이크로초(Microseconds) 단위로 획기적으로 줄여줍니다. 특히 DAX는 기존 DynamoDB API 호출과 100% 호환되므로 애플리케이션 코드의 엔드포인트 변경 수준 외에 비즈니스 로직 수정을 최소화할 수 있습니다.[6]
- 오답 분석: - RCU 증설: 처리할 수 있는 초당 읽기 처리량(Throughput)은 증가하지만, 디스크 I/O 기반인 DynamoDB의 본질적인 응답 지연 시간 자체가 마이크로초로 내려가지는 않습니다. - 글로벌 테이블: 여러 리전 간의 다중 활성 복제 기능으로 지리적 분산 읽기/쓰기에 쓰이며, 단일 리전 내 마이크로초 캐싱 해법이 아닙니다. - RDS 마이그레이션: NoSQL에서 관계형 DB로의 대대적인 애플리케이션 재작성이 필요하므로 "코드 변경 최소화" 요건에 정면으로 위배됩니다.

Q5. VPC의 퍼블릭 서브넷에 위치한 웹 애플리케이션 서버로 특정 외부 IP 대역(203.0.113.0/24)에서 대규모 악의적 무차별 대입 공격(Brute Force) 패킷이 인입되고 있습니다. 보안팀은 다른 정상적인 사용자 트래픽에는 일절 영향을 주지 않으면서, 오직 해당 공격자 IP 대역으로부터의 모든 인바운드 트래픽만을 즉시 차단하고자 합니다. 가장 적절하고 간단한 보안 구성은 무엇입니까?

정답은 네트워크 ACL(NACL)에 기존 허용 규칙보다 낮은 번호로 거부(Deny) 규칙을 추가하는 것입니다.
AWS 네트워킹 보안에서 보안 그룹(Security Group)은 오직 허용(Allow) 규칙만 지원하며 거부(Deny) 규칙을 생성할 수 없습니다. 반면 서브넷 수준에서 동작하는 네트워크 ACL(NACL)은 허용(Allow)과 거부(Deny) 규칙을 모두 지원합니다. NACL은 규칙 번호가 낮은 순서부터 엄격하게 순차 평가되므로, 기존의 기본 허용 규칙(예: 규칙 100)보다 더 앞선 낮은 번호(예: 규칙 50)로 공격자 IP 대역(203.0.113.0/24)에 대한 DENY 규칙을 등록해야 트래픽이 즉시 차단됩니다.[7][8]
- 오답 분석: - 보안 그룹 거부 규칙: 보안 그룹에는 Deny 기능 자체가 아예 존재하지 않는 대표적인 함정 선택지입니다. - IAM 정책 Deny: IAM은 AWS API 호출(제어 플레인)을 통제하는 인증 도구이며, EC2 운영체제로 인입되는 네트워크 레이어(L3/L4) 패킷을 차단할 수 없습니다. - 라우팅 테이블 경로 삭제: 라우팅 테이블은 목적지(Destination) CIDR 기반으로 아웃바운드 패킷을 전달할 게이트웨이를 결정하는 장치이지, 인바운드 출발지(Source) IP를 필터링하는 방화벽이 아닙니다.

Q6. 한 회사가 핵심 주문 처리 데이터베이스로 Amazon RDS for PostgreSQL 단일 가용 영역(Single-AZ) 인스턴스를 운영하고 있습니다. 데이터 센터 화재 등 가용 영역(AZ) 전체에 장애가 발생하더라도 관리자의 수동 개입 없이 수 분 내에 자동으로 복구되어야 하며, 애플리케이션 소스 코드나 환경 설정의 DB 연결 엔드포인트(DNS) 문자열을 일일이 변경하지 않아야 합니다. 가장 적합한 고가용성 조치는 무엇입니까?

정답은 RDS 인스턴스를 다중 AZ(Multi-AZ) 배포로 수정하는 것입니다.
Amazon RDS Multi-AZ 배포는 다른 가용 영역에 동기식(Synchronous) 대기(Standby) 복제본을 자동으로 프로비저닝하고 유지합니다. 기본(Primary) 인스턴스에 장애가 발생하면 RDS 서비스가 이를 감지하여 관리자 개입 없이 자동으로(보통 60~120초 내) 대기 인스턴스로 장애 조치(Failover)를 수행합니다. 이때 RDS가 기본 엔드포인트의 CNAME DNS 레코드를 대기 인스턴스의 IP로 자동 전환하므로, 애플리케이션의 연결 문자열을 전혀 수정할 필요가 없습니다.[9][10]
- 오답 분석: - 읽기 전용 복제본(Read Replica): 비동기식(Asynchronous) 복제로 읽기 트래픽 분산이 주 목적이며, 장애 조치 시 데이터 유실 가능성이 있고 관리자가 수동으로 승격(Promote)해야 하므로 자동 페일오버 요건을 만족하지 못합니다.[11] - 스냅샷 복원: 수동 작업이 필요하고 새 인스턴스가 생성되어 엔드포인트 URL이 완전히 변경됩니다. - 동일 AZ 스케일업: 가용 영역 장애 시 함께 정지되므로 가용성 확보가 불가능합니다.

Q7. VPC 내 프라이빗 서브넷에 배치된 백엔드 EC2 인스턴스들이 보안을 위해 외부 인터넷에서 최신 OS 보안 패치 파일들을 안전하게 다운로드해야 합니다. 사내 보안 정책상 외부 인터넷의 임의 호스트에서 프라이빗 인스턴스로의 직접적인 인바운드 연결은 철저히 차단되어야 합니다. 이 네트워크 아키텍처를 구현하기 위해 함께 수행해야 하는 두 가지 단계는 무엇입니까? (두 개를 고르세요)

정답은 퍼블릭 서브넷에 NAT 게이트웨이 생성(1)과 프라이빗 라우팅 테이블에 0.0.0.0/0→NAT 경로 추가(3)입니다.
1. 퍼블릭 서브넷에 NAT 게이트웨이 생성: NAT 게이트웨이는 인터넷 게이트웨이(IGW)로 나가는 경로를 가진 퍼블릭 서브넷에 위치해야 하며 탄력적 IP(EIP)가 연결되어 있어야 정상 동작합니다.
2. 프라이빗 라우팅 테이블 경로 추가: 프라이빗 서브넷의 라우팅 테이블에서 인터넷행 트래픽(0.0.0.0/0)을 방금 생성한 NAT 게이트웨이로 전달하도록 구성합니다. NAT 게이트웨이는 상태 저장(Stateful) 특성을 가지므로, 내부에서 외부로 나간 요청의 응답 패킷만 통과시키고 외부 인터넷에서 시작된 인바운드 연결 시도는 원천적으로 차단합니다.[12]
- 오답 분석: - 프라이빗 서브넷에 NAT 생성: 인터넷 게이트웨이로 나갈 수 있는 경로가 없으므로 패킷이 외부로 나가지 못합니다. - 퍼블릭 IP 할당 / 보안 그룹 0.0.0.0/0 인바운드 개방: 외부 인터넷에서 인스턴스로 직접 접속할 수 있게 되므로 보안 격리 원칙을 완전히 파괴합니다.

Q8. 한 기업이 미디어 콘텐츠 관리 시스템(CMS)을 3개의 가용 영역에 걸쳐 분산된 수십 대의 Linux EC2 인스턴스에서 운영하고 있습니다. 모든 인스턴스가 동일한 대용량 파일 시스템을 POSIX 표준 파일 인터페이스를 통해 동시에 읽고 쓸 수 있어야 하며(Shared File Storage), 저장 공간 용량을 사전에 프로비저닝할 필요 없이 데이터 증감에 따라 스토리지가 완전 자동으로 확장 및 축소되어야 합니다. 가장 운영 오버헤드가 적은 스토리지는 무엇입니까?

정답은 Amazon EFS 파일 시스템을 생성하여 모든 인스턴스에 마운트하는 것입니다.
Amazon EFS는 완전 서버리스이자 탄력적인 공유 파일 스토리지로, 용량을 사전에 계획하거나 프로비저닝할 필요 없이 데이터가 추가되거나 삭제됨에 따라 자동으로 기가바이트에서 페타바이트까지 확장 및 축소됩니다. 리전별 EFS 파일 시스템은 여러 가용 영역(Multi-AZ)에 걸쳐 데이터를 안전하게 분산 복제하며, 수천 대의 Linux 인스턴스가 표준 NFSv4 프로토콜을 통해 동시에 읽고 쓸 수 있습니다.[13]
- 오답 분석: - EBS + rsync 동기화: 동시 다중 쓰기 환경에서 데이터 정합성 충돌이 발생하며, 실시간 동기화 지연 및 심각한 스크립트 관리 오버헤드가 발생합니다. - S3 SDK 전면 수정: POSIX 파일 시스템 인터페이스가 아닌 객체 스토리지이므로 애플리케이션 코드를 대대적으로 수정해야 합니다. - 자체 EC2 NFS 서버 구축: 인스턴스 장애 시 전체 CMS가 중단되는 단일 장애점(SPOF)이 되며, 패치 및 용량 확장을 엔지니어가 직접 관리해야 합니다.

AWS Secrets Manager는 데이터베이스 자격 증명, API 키 등의 비밀 정보를 안전하게 암호화 저장하고 세밀하게 제어할 수 있는 완전 관리형 서비스입니다. 특히 Amazon RDS와의 기본 통합을 통해 내장된 자동 교체(Automatic Rotation) 기능을 지원하여, 사전 구성된 주기에 맞춰 애플리케이션 중단 없이 실제 RDS 데이터베이스의 비밀번호와 Secrets Manager의 비밀값을 동시에 자동으로 안전하게 교체해 줍니다.[14]

Q10. 회사가 재해 복구(DR) 계획의 일환으로 보조 AWS 리전에 재해 복구 환경을 구축하려고 합니다. 주 리전에 대규모 정전이나 천재지변이 발생했을 때, 보조 리전의 시스템은 새로운 인스턴스를 처음부터 프로비저닝하거나 빌드하는 지연 시간 없이 즉시 실제 사용자 트래픽을 처리(처음에는 축소된 최소 용량이어도 무방함)할 수 있어야 합니다. 이 복구 시간 목표를 만족하면서 평상시 인프라 유지 비용을 가장 최소화할 수 있는 재해 복구 전략은 무엇입니까?

AWS 재해 복구(DR) 백서의 4대 전략 중 웜 스탠바이(Warm Standby)는 축소된 최소 규모(Scaled-down)이지만 웹, 앱, DB를 포함한 완전한 엔드투엔드 시스템이 보조 리전에서 24시간 실제로 가동 중인 상태를 의미합니다. 따라서 장애 조치 시 인스턴스를 띄우는 지연 시간 없이 즉각 트래픽을 수용할 수 있으며, 이후 Auto Scaling을 통해 정상 규모로 신속히 확장합니다.[15]

Q12. 한 글로벌 엔터프라이즈 기업이 AWS Organizations를 통해 40개 이상의 멤버 계정을 운영하고 있습니다. 사내 데이터 주권 규정 준수를 위해 허가된 2개 리전(예: ap-northeast-2 및 ap-northeast-1) 이외의 전 세계 다른 리전에서는 어떠한 신규 리소스도 생성할 수 없도록 강제해야 합니다. 각 멤버 계정의 로컬 관리자가 AdministratorAccess 권한을 가지고 있더라도 예외 없이 이 제약을 강제할 수 있는 가장 효율적인 거버넌스 방법은 무엇입니까?

정답은 조직 구성 단위(OU)에 서비스 제어 정책(SCP)을 연결하는 것입니다.
서비스 제어 정책(SCP: Service Control Policy)은 AWS Organizations 환경에서 하위 계정들이 행사할 수 있는 최대 허용 권한의 가드레일(최대 권한 한계선)을 정의합니다. SCP는 멤버 계정 내부의 루트(Root) 사용자는 물론 AdministratorAccess 권한을 가진 로컬 관리자에게도 예외 없이 강제 적용되며, 로컬 관리자가 스스로 정책을 수정하거나 우회할 수 없습니다. 따라서 최상위 OU에 비승인 리전 작업을 거부(Deny)하는 SCP를 단 1회 연결하는 것만으로 40개 전 계정에 완벽한 중앙 통제가 적용됩니다.[17]

Q19. 한 기업이 두 개 리전에서 다양한 인스턴스 패밀리의 EC2 인스턴스와 AWS Fargate, AWS Lambda를 연중 안정적으로 대규모 사용하고 있습니다. 전체적인 컴퓨팅 지출 규모는 향후 몇 년간 일정하게 유지될 예정이지만, 향후 1년 이내에 현재 사용 중인 EC2 인스턴스 패밀리를 차세대 패밀리로 업그레이드하고, 일부 워크로드를 다른 리전으로 이전하거나 Fargate 컨테이너로 점진적 전환할 계획을 가지고 있습니다. 유연성을 극대화하면서 비용을 가장 크게 절감할 수 있는 구매 약정 옵션은 무엇입니까?

- 오답 분석: - 스팟 전면 전환: 중단 위험이 상존하므로 24/7 상시 운영되어야 하는 안정적인 핵심 프로덕션 환경 전체에 적합하지 않습니다. - EC2 Instance Savings Plans: 할인율은 소폭 더 높을 수 있으나 특정 리전의 특정 인스턴스 패밀리(예: us-east-1의 c5)에 고정되므로, 향후 패밀리 변경, 타 리전 이전, Fargate 전환 시 할인이 적용되지 않습니다.[28] - 온디맨드 유지: 아무런 할인을 받지 못하므로 비용 최적화 요구를 무시하는 선택입니다.

Amazon Kinesis Data Streams는 대규모 스트리밍 데이터를 실시간(보통 1초 미만, 수백 밀리초)으로 수집하고 처리하는 플랫폼입니다. 특히 샤드 기반 저장 구조를 통해 서로 다른 소비자 애플리케이션들이 각자의 샤드 오프셋 포인터를 유지하며 동일한 스트림 데이터를 동시에, 독립적으로 소비할 수 있습니다. 또한 보관 기간(최대 365일)이 제공되므로 장애 발생 시 과거 시점부터 데이터를 다시 읽어 재처리(Replay)할 수 있습니다.[29]
- 오답 분석: - SQS 표준 대기열: 한 소비자가 메시지를 읽어 처리하면 대기열에서 삭제되므로, 두 애플리케이션이 동일한 메시지를 독립적으로 각각 읽어가야 하는 구조에 부합하지 않습니다.[3] - 1시간 단위 배치 업로드 / 1분 단위 Athena 쿼리: 실시간 요건(1초 내외 지연)을 전혀 만족하지 못하는 준실시간 또는 배치 처리 방식입니다.

Q21. 전 세계 사용자를 보유한 엔터프라이즈 서비스가 Amazon Aurora MySQL을 기본 데이터베이스로 사용하고 있습니다. 비즈니스 연속성 계획(BCP)에 따라 주 리전의 물리적 재난 발생 시 보조 리전으로의 데이터 손실(RPO)은 1초 이내여야 하고, 보조 리전의 서비스 복원 시간(RTO)은 1분 안팎이어야 합니다. 또한 평상시에는 전 세계 다른 대륙의 사용자들이 각자 지리적으로 가까운 리전에서 짧은 지연 시간으로 읽기 쿼리를 수행할 수 있어야 합니다. 가장 적합한 아키텍처는 무엇입니까?

정답은 Amazon Aurora 글로벌 데이터베이스(Global Database)를 구성하는 것입니다.
Amazon Aurora Global Database는 스토리지 계층의 전용 AWS 사설 네트워크 인프라를 활용하여 기본(Primary) 리전의 데이터를 최대 5개의 보조(Secondary) 읽기 전용 리전으로 보통 1초 미만의 복제 지연 시간으로 복제합니다. 전 세계 사용자들은 로컬 보조 리전에서 지연 시간 없이 고속 읽기 작업을 수행할 수 있으며, 주 리전의 대규모 재해 발생 시 1분 이내에 보조 리전 중 하나를 독립적인 읽기/쓰기 클러스터로 승격(RTO < 1분, RPO < 1초)시켜 즉시 서비스를 정상화할 수 있습니다.[30][15]
- 오답 분석: - 동일 리전 복제본 증설 / Multi-AZ 구성: 동일 리전 내부의 가용 영역(AZ) 장애에 대비하는 기술일 뿐, 리전 전체 정전이나 재해 시 함께 서비스가 불가능해집니다. - 일일 스냅샷 교차 복사: RPO가 최대 24시간에 달하고, 수백 GB의 스냅샷을 새 DB로 복원하는 데 수십 분~수 시간(RTO)이 소요되어 요건을 충족하지 못합니다.

Q22. 정적 웹사이트 자산을 Amazon S3 버킷에 저장하고 Amazon CloudFront 배포를 통해 전 세계로 제공하고 있습니다. 사용자가 S3 버킷의 다이렉트 URL로 직접 우회 접속하는 것을 원천 차단하고 오직 CloudFront 배포를 통해서만 접근하도록 강제하려 합니다. 이를 안전하게 구현하기 위해 반드시 함께 구성해야 하는 두 가지 조치는 무엇입니까? (두 개를 고르세요)

정답은 오리진 액세스 제어(OAC) 구성(0)과 S3 버킷 정책에 CloudFront 서비스 주체 허용(2)입니다.
1. CloudFront 오리진 액세스 제어(OAC) 설정: CloudFront가 S3 오리진으로 보내는 모든 요청에 암호화 서명을 첨부하도록 배포 설정을 구성합니다(AWS 최신 표준 모범 사례).
2. S3 버킷 정책 수정: Principal을 CloudFront 서비스 주체인 cloudfront.amazonaws.com으로 지정하고, Condition 절에서 AWS:SourceArn을 내 CloudFront 배포 ARN으로 제한하여 s3:GetObject 권한을 부여합니다. 이렇게 하면 사용자가 직접 S3 객체 URL로 접근할 때는 AccessDenied로 차단되고 오직 지정된 CloudFront 배포를 통해서만 객체가 제공됩니다.[31]
- 오답 분석: - 정적 웹사이트 호스팅 활성화: S3 웹사이트 엔드포인트는 일반 커스텀 HTTP 오리진으로 취급되어 OAC 기능을 적용할 수 없습니다.[31] - Principal "*" 설정 / 퍼블릭 액세스 차단 해제: 버킷을 전 세계 누구나 직접 접근할 수 있도록 인터넷에 무방비로 공개하는 정반대의 위험한 조치입니다.

Q23. 한 회사의 Amazon S3 버킷에 수 테라바이트(TB)의 웹 서버 액세스 로그 파일이 축적되어 있습니다. 사내 데이터 분석가들이 필요할 때마다 비정기적으로 표준 SQL 문법을 사용해 임의의 즉석(Ad-hoc) 쿼리를 실행하여 특정 에러 패턴을 조사하고자 합니다. 회사는 데이터베이스 서버나 클러스터를 사전에 프로비저닝하거나 관리하고 싶지 않으며, 오직 실제로 실행된 쿼리가 스캔한 데이터 양에 비례해서만 비용을 지불하기를 원합니다. 가장 적합한 서비스는 무엇입니까?

정답은 Amazon Athena를 사용하여 S3 데이터를 직접 표준 SQL로 쿼리하는 것입니다.
Amazon Athena는 S3에 저장된 정형 및 반정형 데이터를 표준 SQL을 사용해 서버 없이 즉시 분석할 수 있는 완전 서버리스 대화형(Interactive) 쿼리 엔진입니다. 사용자가 관리할 인프라가 전혀 없으며, 실제로 실행된 SQL 쿼리가 스캔한 데이터양(TB당 $5 수준)에 대해서만 비용을 지불하므로 비정기적인 애드혹(Ad-hoc) 분석에 최적의 비용 효율성을 제공합니다.[33]
- 오답 분석: - EC2 자체 DB 설치 / 상시 EMR 클러스터: 사용하지 않는 시간에도 24시간 인스턴스 비용이 청구되며, OS 패치 및 클러스터 관리 등 막대한 운영 부담이 발생합니다. - RDS 적재: 매일 S3에서 DB로 데이터를 밀어 넣는 추가적인 ETL 파이프라인과 비싼 고용량 RDS 스토리지 비용이 발생합니다.

Q24. 회사의 웹 애플리케이션이 주(Primary) AWS 리전의 Application Load Balancer(ALB) 뒤에서 서비스되고 있으며, 재해 복구를 위해 보조(Secondary) 리전에도 동일한 대기 환경을 준비해 두었습니다. 평상시에는 100%의 모든 DNS 트래픽이 주 리전으로만 전달되어야 하며, 오직 주 리전의 애플리케이션 상태에 이상이 감지되었을 때만 DNS 쿼리 응답이 보조 리전의 대기 ALB 엔드포인트로 자동 전환되어야 합니다. Amazon Route 53에서 어떤 구성을 해야 합니까?

정답은 Route 53 상태 확인(Health Check)과 장애 조치(Failover) 라우팅 정책을 구성하는 것입니다.
장애 조치(Failover) 라우팅 정책은 전형적인 액티브-패시브(Active-Passive) 재해 복구 구성을 위한 전용 정책입니다. 주 리소스(Primary)와 보조 리소스(Secondary)를 지정하고, Route 53 상태 확인(Health Check)이 주 엔드포인트를 감시합니다. 주 리전이 정상일 때는 모든 트래픽이 주 리전으로만 전달되며, 상태 확인이 실패를 감지하는 즉시 자동으로 보조 리전의 엔드포인트를 반환하도록 장애 조치를 수행합니다.[35][15]
- 오답 분석: - 가중치 기반 라우팅: 평상시에도 지정한 비율(50:50)대로 대기 리전에 트래픽이 유입되므로 액티브-패시브 요건에 맞지 않습니다. - 지리 위치 라우팅: 사용자의 접속 국가/대륙 위치에 따라 라우팅할 뿐 인프라 장애 시 자동 전환되지 않습니다.[34] - 단순 라우팅: 상태 확인 기반 자동 페일오버 기능을 지원하지 않습니다.[34]

Q25. 금융 규제 지침에 따라 고객의 모든 금융 거래 기록 아카이브 데이터를 10년간 안전하게 보존해야 합니다. 정기 감사 시에만 데이터를 열람하므로 실제 조회 빈도는 연 1회 미만으로 극히 드물며, 감사 요청 시 데이터를 조회하기까지 수 시간의 복원 지연 시간(Retrieval time)이 허용됩니다. 10년간의 장기 보관 비용을 가장 최저로 유지할 수 있는 Amazon S3 스토리지 클래스는 무엇입니까?

정답은 Amazon S3 Glacier Deep Archive입니다.
Amazon S3 Glacier Deep Archive는 AWS 전체 클라우드 스토리지 중 가장 저렴한 보관 비용(GB당 월 $0.00099 수준)을 제공하는 장기 아카이빙 전용 클래스입니다. 1년에 1~2회 미만으로 극히 드물게 접근하고 수 시간(표준 복원의 경우 12시간 이내)의 복원 대기 시간이 허용되는 규제 준수 데이터 보관에 완벽히 부합하며, 최소 보관 기간 180일 정책도 10년 보존 요건에 완벽히 충족됩니다.[36]
- 오답 분석: - Glacier Instant Retrieval: 분기 1회 수준의 접근과 밀리초 단위의 즉시 조회가 필요한 데이터용으로, Deep Archive 대비 보관 단가가 약 4배가량 높습니다. - S3 Standard-IA: 월 1회 수준의 빈번한 조회용으로 장기 아카이빙에는 보관 비용이 지나치게 높습니다. - S3 One Zone-IA: 데이터를 단 하나의 가용 영역(Single AZ)에만 저장하므로, 해당 AZ 파괴 시 데이터가 영구 유실되어 규정 준수 필수 아카이브 데이터 보관용으로는 절대 사용해서는 안 됩니다.[36]

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속에서 직접 떠올려 적어 보세요. 시험 문제 지문에서 아래 표현을 마주쳤을 때 1초 만에 떠올려야 할 표준 AWS 서비스나 아키텍처 패턴은 무엇인가요?
(1) "일시적 트래픽 급증, 처리 지연 허용, 데이터 유실 절대 불가"
(2) "하나의 이벤트를 여러 개의 독립된 시스템이 각각 안전하게 비동기 수신"
(3) "특정 악성 IP 대역의 인바운드 트래픽만 즉시 차단"
(4) "작업 중단 허용 가능, 체크포인트 재개, 극단적인 비용 최소화"
(5) "새 서버 프로비저닝 없이 즉시 트래픽을 처리할 수 있는 축소 규모의 최소 DR 환경"
(6) "조직 내 모든 멤버 계정의 로컬 관리자(Admin)에게도 예외 없이 강제되는 리전/서비스 차단 가드레일"

(1) SQS 대기열 버퍼링: 생산자와 소비자를 분리하고 스파이크를 흡수하여 유실 방지.
(2) SNS → 다중 SQS 대기열 팬아웃(Fanout) 패턴: SNS로 1회 발행하고 각 마이크로서비스 전용 SQS 큐로 안전하게 복제 전달.
(3) 네트워크 ACL(NACL) 낮은 번호의 거부(Deny) 규칙: 보안 그룹은 거부 규칙이 없으므로 반드시 서브넷 NACL에서 처리.
(4) 스팟 인스턴스(Spot Instances): 여유 컴퓨팅 용량을 최대 90% 할인받아 사용.
(5) 웜 스탠바이(Warm Standby) DR 전략: 파일럿 라이트와 달리 축소된 엔드투엔드 시스템이 상시 가동되어 즉시 트래픽 처리 가능.
(6) AWS Organizations 서비스 제어 정책(SCP): 멤버 계정 관리자나 루트 사용자도 우회할 수 없는 조직 최상위 권한 가드레일 (단, 관리 계정 자체에는 미적용).

더 많은 시험 핵심 키워드와 문제 풀이 공식은 시험 전략 시트에 일목요연하게 정리되어 있습니다.
