데이터 모양이 DB를 고른다:
목적별 데이터베이스와 DMS 마이그레이션

AWS에는 15개가 넘는 데이터베이스가 있고 시험은 "이 데이터에 맞는 DB"를 고르게 합니다. 오늘은 데이터 모델 → 서비스 매핑을 외우고, 같은 엔진(동종)과 다른 엔진(이기종) 마이그레이션에서 DMS와 Schema Conversion이 각각 무슨 일을 하는지, 그리고 비용 관점의 선택 기준을 정리합니다.

⏱ 약 18분🎯 오늘의 승리: 시나리오 8문항📌 데이터베이스 치트시트

왜 이것부터인가

시험에서: "친구의 친구", "사기 탐지" → 그래프, "IoT 센서 시계열" → 시계열, "페타바이트 분석·BI" → 데이터 웨어하우스, "Oracle에서 Aurora PostgreSQL로 최소 다운타임" → Schema Conversion + DMS(CDC). 보기 네 개가 모두 실존 서비스라 데이터 모델로 걸러야 합니다.
실무에서: 한 애플리케이션에 여러 DB를 섞는 것이 정상입니다. AWS도 전자상거래 예로 카탈로그는 DocumentDB, 빠른 조회는 DynamoDB, 재고·주문은 Aurora를 함께 쓰는 구성을 듭니다.[1]

데이터 모델 → 서비스

AWS 선택 가이드는 OLTP 데이터베이스를 관계형과 비관계형으로 나누고, 비관계형은 키-값, 문서, 인메모리, 그래프, 시계열, 와이드 컬럼 등 특정 데이터 모델용이라고 설명합니다. 대량 데이터 분석(OLAP)은 Amazon Redshift로 안내합니다.[1]

데이터 모델서비스언제 (시험 키워드)
관계형RDS (PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, Db2), Aurora구조화된 데이터, 조인, 트랜잭션, 기존 온프레미스 관계형 이전[1]
키-값DynamoDB세션 저장소, 장바구니, 엄청난 처리량, 한 자릿수 밀리초[1]
문서DocumentDB (MongoDB 호환)JSON 유사 문서, 필드 단위 풍부한 쿼리. 기존 MongoDB 코드·드라이버를 그대로 사용[2]
인메모리ElastiCache (캐시), MemoryDB (내구성 있는 주 DB)마이크로초 읽기 캐시 / 완전한 데이터 영속성이 필요한 인메모리 주 DB[1]
그래프Neptune고도로 연결된 데이터: 추천 엔진, 사기 탐지, 지식 그래프, 소셜 네트워크. Gremlin, openCypher, SPARQL[3]
와이드 컬럼Keyspaces (Apache Cassandra 호환)온프레미스 Cassandra 워크로드 이전, 대량 읽기·쓰기[1]
시계열TimestreamIoT 데이터, 애플리케이션 지표, 자산 추적 등 타임스탬프 데이터[1]
데이터 웨어하우스 (OLAP)Redshift대규모 분석 쿼리, 소수 컬럼 × 대량 행 집계[4]

Redshift가 분석에 빠른 이유: 컬럼 기반 저장

OLTP는 한 번에 몇 개 레코드의 거의 모든 컬럼을 읽고 쓰므로 행 기반 저장이 맞습니다. 데이터 웨어하우스 쿼리는 보통 매우 많은 행의 소수 컬럼만 읽으므로, 컬럼별로 블록에 저장하면 디스크 I/O가 크게 줄고 같은 타입끼리 모여 압축도 잘 됩니다. AWS 예시로 100개 컬럼 중 5개만 쓰는 쿼리는 데이터의 약 5%만 읽습니다.[4]

최근 변경: 오래된 문제집 주의

Timestream for LiveAnalytics는 2025년 6월 20일부터 신규 고객 접근이 닫혔고, 기존 워크로드는 영향이 없습니다. AWS는 신규 고객에게 Timestream for InfluxDB를 대안으로 권장합니다.[5] 시험 보기에서는 여전히 "시계열 → Timestream"으로 판단하면 됩니다.
원장(ledger) DB: 현재 AWS 데이터베이스 선택 가이드(2026년 6월 갱신)의 대상 서비스 목록에는 원장 데이터베이스가 없습니다.[1] 오래된 자료에서 QLDB가 나오면 공식 문서로 현재 상태를 확인하세요. 이 과정에서는 QLDB의 현재 상태를 공식 문서로 확인하지 못해 다루지 않습니다.

마이그레이션: 동종 vs 이기종

AWS DMS는 관계형 DB, 데이터 웨어하우스, NoSQL 등을 AWS로(또는 클라우드·온프레미스 사이에서) 옮기는 서비스입니다. 본질은 AWS 클라우드의 복제 서버로, 소스·타깃 엔드포인트를 정하고 태스크를 돌려 데이터를 옮깁니다.[6] 같은 엔진을 유지하는 이전도, 지원 엔진 사이의 완전한 이기종 이전도 지원합니다.[6]

동종 (homogeneous)이기종 (heterogeneous)
예온프레미스 MySQL → RDS for MySQLOracle → Aurora PostgreSQL, SQL Server → Aurora MySQL
스키마엔진이 같아 변환 불필요먼저 스키마·코드 변환: DMS Schema Conversion(관리형, 웹 기반) 또는 로컬 PC용 AWS SCT[6]
데이터DMS변환 코드를 타깃에 적용한 뒤 DMS로 데이터 이전[6]

DMS Schema Conversion은 테이블, 뷰, 저장 프로시저, 함수 등을 타깃(Aurora, RDS, Redshift) 형식으로 변환하고, 무엇이 자동 변환되고 무엇이 수작업인지 평가 보고서를 만듭니다. AWS SCT 변환 엔진 기반이며, 스키마만 변환하고 데이터는 옮기지 않습니다.[7]

최소 다운타임의 열쇠: 전체 로드 + CDC

DMS 태스크 유형은 전체 로드, 전체 로드 + CDC(기존 데이터를 옮긴 뒤 소스 변경을 계속 반영), CDC만입니다. CDC는 소스 엔진의 트랜잭션 로그에서 변경을 읽습니다.[8] 그래서 소스를 계속 운영하면서 타깃을 따라잡게 한 뒤 짧게 전환(cutover)할 수 있습니다. 단, DMS CDC는 실시간 복제가 아니며 지연에 대한 SLA가 없습니다.[8]

비용 효율적인 DB 선택

  • 서버리스 vs 프로비저닝: AWS 서버리스 DB는 사용량 기반 과금과 내장 고가용성으로 수요에 맞춰 확장합니다. 목록: Aurora DSQL, Aurora Serverless, DynamoDB, ElastiCache, Keyspaces, Timestream for LiveAnalytics, Neptune Serverless.[1] 변동이 큰 워크로드는 Aurora Serverless(0021), 예측 불가한 키-값 트래픽은 DynamoDB 온디맨드(0022)가 맞고, 꾸준하고 예측 가능한 부하는 프로비저닝이 비용을 예측하기 쉽습니다.[9]
  • Aurora 스토리지 구성: I/O 비용이 전체 Aurora 비용의 25% 이상이면 I/O 요금이 없는 Aurora I/O-Optimized, 25% 미만이면 I/O 요청당 과금하는 Aurora Standard가 낫습니다.[10]
  • 상용 라이선스 탈피: AWS는 Oracle·SQL Server 같은 상용 DB에서 Aurora로 옮기는 것을 마이그레이션 선택지로 제시하며, DMS가 더 비용 효율적인 엔진으로 전환하는 것을 돕는다고 설명합니다.[1][6]
  • 재호스팅 vs 재플랫폼: EC2에 DB를 직접 설치하면 가장 빨리 이전하지만 패치·백업·가용성 운영이 남습니다. RDS로 재플랫폼하면 그 운영을 AWS가 맡습니다.[1] "최소 운영 오버헤드"가 조건이면 관리형이 정답입니다.

시험 단골: 키워드 → 정답

  • "관계", "친구의 친구", "사기 탐지", "추천", "지식 그래프" → Neptune
  • "MongoDB 호환", "JSON 문서" → DocumentDB · "Cassandra" → Keyspaces
  • "IoT 센서", "시간에 따른 지표" → Timestream
  • "페타바이트 분석", "BI 대시보드", "컬럼 기반", "데이터 웨어하우스" → Redshift
  • "인메모리인데 데이터 손실 불가(주 DB)" → MemoryDB · "캐시" → ElastiCache
  • "다른 엔진으로 이전" → Schema Conversion(또는 SCT) + DMS · "다운타임 최소" → 전체 로드 + CDC

연습

Q1. 소셜 앱이 "친구의 친구가 좋아한 상품"을 실시간 추천하려 합니다. 관계를 여러 단계로 따라가는 쿼리가 핵심이며, 관계형 DB의 다중 조인으로는 너무 느립니다. 가장 적합한 DB는?

Neptune은 수십억 개 관계를 저장하고 밀리초 지연으로 탐색하도록 만든 그래프 DB이며, AWS는 추천 엔진과 사기 탐지를 대표 사례로 듭니다. DynamoDB는 키 기반 조회에 강하지만 JOIN이 없고 다단계 관계 탐색에 맞지 않습니다. Redshift는 분석용입니다.

Q2. 공장의 센서 수만 개가 초마다 온도·진동 값을 보냅니다. 최근 데이터 추세를 실시간으로 보고, 시간 범위별 집계를 해야 합니다. 데이터 모델에 가장 맞는 서비스 범주는?

IoT 센서처럼 타임스탬프에 묶인 데이터는 시계열 DB의 대표 사례입니다. 참고로 Timestream for LiveAnalytics는 2025년 6월부터 신규 고객을 받지 않으며 AWS는 Timestream for InfluxDB를 권장합니다. ElastiCache는 캐시일 뿐 시계열 저장·분석용이 아닙니다.

Q3. 분석팀이 수년 치 판매 데이터(수백 TB, 컬럼 수백 개)에서 몇 개 컬럼만 골라 지역별·월별 집계를 하는 BI 대시보드를 만듭니다. 가장 적합한 서비스는?

많은 행의 소수 컬럼을 집계하는 OLAP 쿼리는 컬럼 기반 저장의 Redshift가 맞습니다. 필요한 컬럼 블록만 읽어 I/O가 크게 줄어듭니다. MySQL은 행 기반 OLTP 엔진이라 복제본을 늘려도 이런 쿼리는 느립니다.

Q4. 회사가 온프레미스 Oracle DB(저장 프로시저 다수)를 Aurora PostgreSQL로 옮기려 합니다. 이전 중에도 Oracle은 계속 운영해야 하며 전환 다운타임을 최소화해야 합니다. 올바른 순서는?

이기종 이전이므로 먼저 DMS Schema Conversion(또는 AWS SCT)으로 스키마와 저장 프로시저를 변환해 적용하고, DMS 전체 로드+CDC로 데이터를 옮기며 변경을 계속 반영한 뒤 짧게 전환합니다. DMS 데이터 이전은 저장 프로시저 같은 코드를 변환하지 않습니다. 덤프 복원은 다운타임이 깁니다.

Q5. AWS DMS와 DMS Schema Conversion에 대한 설명으로 옳은 것은? (두 개를 고르세요)

DMS는 지원 엔진 사이의 완전한 이기종 이전을 지원하고, 전체 로드+CDC는 기존 데이터를 옮긴 뒤 소스 변경을 계속 반영합니다. Schema Conversion은 스키마만 변환하며 데이터는 DMS가 옮깁니다. DMS CDC는 실시간 복제가 아니며 지연 SLA가 없다고 문서에 명시되어 있습니다.

Q6. 자체 관리하는 MongoDB 클러스터를 운영 부담이 적은 관리형 서비스로 옮기려 합니다. 애플리케이션 코드와 드라이버는 가능한 한 그대로 쓰고 싶습니다. 가장 적합한 것은?

DocumentDB는 MongoDB 호환 관리형 서비스로, 같은 애플리케이션 코드·드라이버·도구를 쓸 수 있습니다. EC2 재호스팅은 운영 부담이 그대로이고, DynamoDB나 Aurora는 코드 변경이 큽니다.

Q7. (0022 복습) 모바일 게임이 수백만 플레이어의 점수를 실시간으로 순위화한 상위 100명 리더보드를 보여 줘야 합니다. 점수는 계속 바뀝니다. 가장 적합한 구성은?

Valkey/Redis OSS 정렬 집합은 원소가 추가될 때마다 실시간으로 순위를 다시 매겨 리더보드 계산을 클러스터로 옮깁니다. Memcached는 단순 데이터 타입만 있어 정렬 집합이 없습니다. 매번 Scan은 비싸고 느립니다.

Q8. (0021 연결) Aurora 클러스터의 청구서를 보니 I/O 요금이 전체 Aurora 비용의 40%입니다. 애플리케이션 변경 없이 비용을 줄이는 가장 적절한 방법은?

AWS 기준으로 I/O 비용이 전체의 25% 이상이면 읽기·쓰기 I/O 요금이 없는 I/O-Optimized가 유리합니다. Aurora에서는 라이터와 리더의 I/O가 같은 방식으로 집계되며, 복제본을 지우면 가용성만 잃습니다. RDS Proxy는 연결 풀링이지 I/O 캐시가 아닙니다.

기억에서 꺼내기

보지 말고 써 보세요. (1) 관계형, 키-값, 문서, 인메모리(2개), 그래프, 와이드 컬럼, 시계열, 데이터 웨어하우스에 각각 맞는 AWS 서비스. (2) 동종과 이기종 이전의 단계 차이. (3) 다운타임을 최소화하는 DMS 태스크 유형.

(1) 관계형 RDS·Aurora, 키-값 DynamoDB, 문서 DocumentDB, 인메모리 ElastiCache(캐시)·MemoryDB(내구성 주 DB), 그래프 Neptune, 와이드 컬럼 Keyspaces, 시계열 Timestream(신규 고객은 InfluxDB 권장), 데이터 웨어하우스 Redshift(컬럼 기반).

(2) 동종: DMS로 데이터만. 이기종: DMS Schema Conversion(또는 AWS SCT)으로 스키마·코드를 변환해 타깃에 적용한 뒤 DMS로 데이터 이전.

(3) 전체 로드 + CDC: 기존 데이터를 옮긴 뒤 소스 트랜잭션 로그의 변경을 계속 반영하다가 전환.
