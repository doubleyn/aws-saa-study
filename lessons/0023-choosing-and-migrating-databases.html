데이터 모양이 DB를 고른다:
목적별 데이터베이스와 DMS 마이그레이션

AWS에는 15개가 넘는 특화된 데이터베이스 엔진이 존재하며, 시험에서는 제시된 비즈니스 시나리오와 데이터 모델에 가장 적합한 최적의 데이터베이스를 고르는 문제가 끊임없이 출제됩니다. 모든 데이터를 관계형 테이블 하나에 억지로 욱여넣는 시대는 끝났습니다. 데이터 모델별 최적의 서비스 매핑을 완벽히 정리하고, 같은 엔진(동종)과 다른 엔진(이기종) 마이그레이션에서 AWS DMS와 Schema Conversion(SCT)이 각각 어떤 역할을 맡아 다운타임을 최소화하는지, 그리고 클라우드 비용 효율 관점의 선택 기준까지 깊이 있게 살펴봅니다.

⏱ 약 18분🎯 오늘의 승리: 시나리오 8문항📌 데이터베이스 치트시트

왜 목적별 데이터베이스와 마이그레이션을 배워야 할까요?

시험에서: "소셜 네트워크에서 친구의 친구 관계를 탐색하거나 금융 사기 탐지(Fraud Detection)를 수행한다" → 그래프 DB인 Neptune, "공장 IoT 센서의 시간별 온도 측정값" → 시계열 DB인 Timestream, "수백 TB의 대규모 데이터에서 소수 컬럼을 집계하는 BI 리포팅" → 데이터 웨어하우스인 Redshift, "온프레미스 Oracle을 Aurora PostgreSQL로 중단 없이 이전한다" → DMS Schema Conversion(SCT) + DMS(전체 로드 + CDC). 시험에 나오는 모든 보기는 실존하는 AWS 데이터베이스이므로, 데이터의 본질적인 모양과 워크로드 특성으로 정확히 필터링할 수 있어야 합니다.
실무에서: 현대적인 클라우드 마이크로서비스 아키텍처(MSA)에서는 하나의 애플리케이션 안에서도 여러 데이터베이스를 목적에 맞게 혼용하는 '다중 언어 지속성(Polyglot Persistence)'이 표준입니다. 실제로 대규모 전자상거래 시스템은 상품 카탈로그는 DocumentDB, 장바구니와 빠른 세션 조회의 경우 DynamoDB, 주문 및 결제 트랜잭션은 Aurora, 실시간 랭킹은 ElastiCache, 판매 분석은 Redshift로 분리하여 구성합니다.[1]

데이터 모델에 따른 최적의 AWS 데이터베이스 매핑

AWS 공식 의사결정 가이드에 따르면, 실시간 트랜잭션을 처리하는 온라인 트랜잭션 처리(OLTP) 데이터베이스는 크게 관계형과 비관계형으로 나뉩니다. 비관계형 데이터베이스는 키-값, 문서, 인메모리, 그래프, 시계열, 와이드 컬럼 등 고유한 데이터 모델에 최적화되어 있습니다. 반면 대규모 비즈니스 인텔리전스(BI)와 복잡한 대량 데이터 집계 분석(OLAP)은 전용 클라우드 데이터 웨어하우스인 Amazon Redshift가 담당합니다.[1]

Amazon Redshift가 대규모 분석에서 압도적으로 빠른 이유: 컬럼 기반 스토리지 (Columnar Storage)

트랜잭션을 처리하는 일반적인 OLTP 데이터베이스(MySQL, PostgreSQL 등)는 디스크 블록에 데이터를 행(Row) 단위로 연속해서 저장합니다. 고객 1명의 주문 정보를 조회할 때는 주문 번호, 고객명, 배송 주소, 결제 금액 등 거의 모든 컬럼을 한꺼번에 읽어야 하므로 행 기반 저장이 매우 효율적입니다.
하지만 데이터 웨어하우스(OLAP) 분석 쿼리는 정반대입니다. "지난 3년간의 전체 매출액 합계와 평균 주문 금액을 지역별로 계산하라"는 쿼리는 테이블에 100개의 컬럼이 존재하더라도 실제로 필요한 것은 주문일자, 결제금액, 지역 단 3개의 컬럼뿐입니다. 대신 읽어야 할 레코드 수는 수억~수십억 행에 달합니다.

  • 디스크 I/O의 획기적 절감: Redshift의 컬럼 기반 스토리지(Columnar Storage)는 디스크 블록에 동일한 컬럼의 데이터들만 모아서 저장합니다. 100개 컬럼 중 3개 컬럼만 사용하는 분석 쿼리를 실행하면, Redshift는 나머지 97개 컬럼이 저장된 디스크 블록은 아예 건너뛰고 오직 3%에 해당하는 블록만 읽어 들입니다. 디스크 I/O가 97%나 줄어들기 때문에 쿼리 처리 속도가 수십~수백 배 빨라집니다.[4]
  • 압도적인 데이터 압축률: 같은 디스크 블록 안에 동일한 데이터 타입(예: 모두 정수형 금액이나 날짜)만 모여 있으므로, 데이터 압축 효율이 극대화되어 디스크 저장 공간과 메모리 캐시 적재량을 대폭 줄여줍니다.

Timestream for LiveAnalytics는 2025년 6월 20일부터 신규 고객의 가입 및 생성이 중단되었습니다(기존 고객은 계속 사용 가능). AWS 공식 문서는 신규 시계열 워크로드에 대해 오픈소스 InfluxDB 엔진 기반의 Amazon Timestream for InfluxDB를 정식 대안으로 권장하고 있습니다.[5] 다만 SAA-C03 시험 문제에서는 여전히 "IoT 센서, 시계열 데이터 → Timestream"이라는 기본 서비스 분류만 기억하시면 쉽게 정답을 맞힐 수 있습니다.
원장(Ledger) 데이터베이스: 과거 시험 자료에 등장하던 Amazon QLDB(양자 원장 DB)는 현재 공식 AWS 데이터베이스 선택 가이드(2026년 기준)의 주요 서비스 목록에서 제외되었습니다.[1]

데이터베이스 마이그레이션: 동종(Homogeneous) vs 이기종(Heterogeneous)

AWS Database Migration Service (AWS DMS)는 관계형 데이터베이스, 데이터 웨어하우스, NoSQL 데이터베이스를 가동 중단 없이 AWS 클라우드로 마이그레이션하거나 복제할 수 있도록 지원하는 완전관리형 서비스입니다. 본질적으로 AWS VPC 내부에 고성능 복제 인스턴스(Replication Instance)를 프로비저닝하고, 소스 엔드포인트와 타깃 엔드포인트를 지정한 후 마이그레이션 태스크를 실행하여 데이터를 고속으로 복제합니다.[6]

비교 항목동종 마이그레이션 (Homogeneous)이기종 마이그레이션 (Heterogeneous)
마이그레이션 경로 예시온프레미스 MySQL → Amazon RDS for MySQL
온프레미스 PostgreSQL → Aurora PostgreSQL		온프레미스 Oracle → Amazon Aurora PostgreSQL
온프레미스 Microsoft SQL Server → Amazon Aurora MySQL
스키마 호환성소스와 타깃의 데이터베이스 엔진이 동일하므로 데이터 타입과 스키마 구조가 100% 호환됩니다. 별도의 스키마 변환 작업이 전혀 필요 없습니다.소스와 타깃의 엔진이 서로 다르므로 테이블 데이터 타입뿐만 아니라 뷰, 트리거, 저장 프로시저(PL/SQL, T-SQL) 등의 문법이 완전히 호환되지 않습니다.
마이그레이션 절차기본 데이터베이스 덤프 도구(mysqldump 등)나 AWS DMS 태스크를 사용해 곧바로 데이터를 복제합니다.[6]반드시 2단계로 진행해야 합니다:
① DMS Schema Conversion(웹 콘솔 기반) 또는 AWS SCT(Schema Conversion Tool, 설치형 도구)를 사용하여 소스의 스키마, 저장 프로시저를 타깃 엔진 언어로 변환하여 타깃 DB에 먼저 적용합니다.[7]
② 타깃 DB에 스키마 테이블 구조가 생성된 후, AWS DMS를 실행하여 실제 데이터를 복제합니다.

DMS Schema Conversion / AWS SCT의 핵심 원리와 시험 포인트

DMS Schema Conversion(또는 데스크톱 설치형 AWS SCT)은 소스 데이터베이스의 저장 프로시저, 함수, 패키지, 데이터 타입 등을 분석하여 대상 데이터베이스(Aurora, RDS, Redshift) 엔진의 표준 문법으로 자동 변환해 줍니다. 또한 변환 불가능한 특수 코드에 대해 어떤 수작업 코드 리팩토링이 필요한지 상세한 마이그레이션 평가 보고서(Assessment Report)를 작성해 줍니다.
가장 중요한 시험 함정: Schema Conversion / SCT는 오직 스키마 구조와 SQL 프로시저 코드만 변환할 뿐, 실제 테이블의 행 데이터는 단 1건도 이전하지 않습니다! 실제 데이터 복제는 반드시 AWS DMS가 수행합니다.[7]

최소 다운타임(Near-Zero Downtime)을 달성하는 비결: 전체 로드 + CDC

DMS 태스크의 복제 방식은 3가지가 있습니다:[8]

  1. 기존 데이터 전체 로드 (Full Load): 현재 소스 테이블에 들어있는 원본 데이터를 타깃으로 1회성 전체 복사합니다.
  2. 전체 로드 + 지속적 복제 (Full Load + CDC, Change Data Capture): 먼저 전체 데이터를 복제하고, 전체 복제가 진행되는 동안 및 완료된 이후에도 소스 DB에서 발생하는 모든 실시간 데이터 변경(INSERT, UPDATE, DELETE)을 지속적으로 캡처하여 타깃 DB에 실시간 반영합니다.
  3. 지속적 복제만 수행 (CDC only): 이미 타깃에 데이터가 적재되어 있을 때 특정 시점 이후의 트랜잭션 변경분만 추적 복제합니다.

무중단 전환의 핵심 메커니즘: 프로덕션 운영 중인 소스 데이터베이스를 절대 끄지 않고 정상 운영하면서, 전체 로드 + CDC 태스크를 가동합니다. CDC는 소스 데이터베이스의 트랜잭션 로그(Transaction Log, 예: Oracle Redo Log, MySQL Binary Log)를 직접 읽어서 변경분을 타깃으로 전송하므로 소스 데이터베이스에 부하를 주지 않습니다. 타깃 DB가 소스 DB를 완벽히 따라잡아 복제 지연이 0에 수렴하면, 짧은 점검 시간 동안 애플리케이션의 연결 엔드포인트를 타깃 DB로 전환(Cutover)함으로써 다운타임을 수 분 이내로 최소화할 수 있습니다.[8]

비용 관점의 데이터베이스 선택 및 최적화 전략

  • 서버리스 vs 프로비저닝: 트래픽 변동이 극심하거나 간헐적인 워크로드는 Aurora Serverless v2나 DynamoDB 온디맨드를 선택하여 사용한 만큼만 비용을 지불하는 것이 훨씬 경제적입니다. 반대로 24시간 일정한 베이스라인 트래픽이 꾸준히 유지되는 워크로드는 프로비저닝 인스턴스에 예약 인스턴스(RI)나 Savings Plans를 적용하는 것이 총소유비용(TCO)을 크게 낮춥니다.[9]
  • Aurora 스토리지 구성 선택 (Standard vs I/O-Optimized):
    • Aurora Standard: 기본 스토리지 요금이 저렴하지만 읽기/쓰기 I/O 요청 건당 요금이 청구됩니다. 전체 데이터베이스 청구서에서 I/O 비용 비중이 25% 미만인 일반적인 워크로드에 가장 경제적입니다.[10]
    • Aurora I/O-Optimized: 스토리지 기본 단가는 약간 높지만 읽기 및 쓰기 I/O 비용이 0원(완전 무료)입니다. 전체 Aurora 비용 중 I/O 비용이 25% 이상을 차지하는 대규모 결제 시스템이나 전자상거래 등 I/O 집약적 워크로드에서는 I/O-Optimized로 전환하는 즉시 큰 비용 절감 효과를 볼 수 있습니다.[10]
  • 상용 라이선스 탈피 (Commercial to Open-Source): 비싼 상용 데이터베이스(Oracle, Microsoft SQL Server)에서 오픈소스 호환 데이터베이스인 Amazon Aurora(MySQL/PostgreSQL 호환)로 마이그레이션하면 막대한 상용 소프트웨어 라이선스 비용을 영구적으로 제거할 수 있습니다.[1]
  • 재호스팅(Rehost) vs 재플랫폼(Replatform): 온프레미스 DB를 단순히 EC2 인스턴스에 설치하는 재호스팅(IaaS)은 가장 빠르게 이전할 수 있지만, OS 패치, 데이터베이스 버전 업그레이드, 백업, 고가용성 구성을 운영팀이 직접 관리해야 합니다. 반면 Amazon RDS나 Aurora로 재플랫폼(PaaS)하면 운영 오버헤드가 극적으로 줄어듭니다. 문제에서 "운영 오버헤드 최소화"가 언급되면 무조건 완전관리형 서비스(RDS/Aurora)가 정답입니다.

시험에 자주 나오는 핵심 패턴

  • "소셜 네트워크 친구 관계", "추천 엔진", "사기 탐지(Fraud Detection)", "지식 그래프" → Amazon Neptune (그래프 DB)
  • "MongoDB 호환", "JSON 문서 모델" → Amazon DocumentDB
  • "Apache Cassandra 호환", "와이드 컬럼" → Amazon Keyspaces
  • "IoT 센서 데이터", "시간 순서 메트릭" → Amazon Timestream
  • "페타바이트(PB)급 대규모 분석", "BI 대시보드 리포팅", "컬럼 기반 스토리지" → Amazon Redshift (데이터 웨어하우스)
  • "인메모리 속도이면서 영속적인 트랜잭션 주 데이터베이스" → Amazon MemoryDB (단순 캐시는 ElastiCache)
  • "서로 다른 데이터베이스 엔진으로 마이그레이션 (이기종)" → DMS Schema Conversion (또는 AWS SCT) + AWS DMS
  • "운영 중인 DB를 마이그레이션하면서 서비스 다운타임 최소화" → DMS 전체 로드 + CDC (지속적 복제) 태스크
  • "Aurora 클러스터에서 I/O 비용이 25% 이상을 차지할 때 비용 절감" → Aurora I/O-Optimized 스토리지 구성

연습

Q1. 한 소셜 커머스 앱에서 "내가 팔로우하는 친구들의 친구가 최근 한 달간 가장 많이 구매한 상품"을 실시간으로 추천하는 신규 기능을 개발하려 합니다. 데이터 간의 복잡한 다단계 관계망을 따라가는 그래프 탐색 쿼리가 핵심이며, 기존 관계형 데이터베이스(RDBMS)의 다중 JOIN 연산으로는 극심한 지연 시간이 발생합니다. 이 추천 시스템의 백엔드로 가장 적합한 AWS 데이터베이스는 무엇입니까?

정답은 Amazon Neptune입니다! Neptune은 수십억 개의 복잡한 연결 관계를 저장하고 밀리초 단위의 초저지연으로 탐색할 수 있도록 최적화된 완전관리형 그래프 데이터베이스입니다. AWS 공식 문서에서도 추천 엔진, 소셜 네트워크, 사기 탐지(Fraud Detection)의 표준 해법으로 Neptune을 지정하고 있습니다. DynamoDB는 키 기반 단건 조회에 강력하지만 테이블 간 JOIN이 없어 다단계 관계 그래프 탐색에 부적합하며, Redshift는 OLAP 분석용입니다.

Q2. 스마트 팩토리의 수만 개 제조 설비에 부착된 IoT 센서들이 매초마다 온도, 진동, 압력 측정값을 클라우드로 전송하고 있습니다. 공장 운영팀은 최신 측정값 추이를 실시간 모니터링 대시보드로 시각화하고, 특정 시간 범위별 통계 집계를 주기적으로 수행해야 합니다. 데이터 모델과 워크로드 특성에 가장 부합하는 AWS 서비스 범주는 무엇입니까?

정답은 시계열 DB인 Amazon Timestream입니다! 센서 계측값, 서버 메트릭처럼 시간의 경과에 따라 순차적으로 축적되는 타임스탬프 데이터는 시계열 데이터베이스의 전형적인 워크로드입니다. Timestream은 초당 수백만 건의 시계열 데이터를 효율적으로 수집하고 시간 범위별 집계 쿼리를 신속하게 처리하도록 설계되었습니다. DocumentDB는 JSON 문서용, Neptune은 복잡한 관계망용이며, ElastiCache는 캐시용입니다.

Q3. 한 기업의 데이터 분석팀이 지난 5년간 축적된 수백 테라바이트(TB) 규모의 전자상거래 판매 이력 데이터에서, 경영진을 위한 월별 및 지역별 매출 추이 BI 대시보드를 구축하려 합니다. 원본 테이블에는 150개의 컬럼이 존재하지만, 대시보드 집계 쿼리는 오직 4~5개의 특정 컬럼만을 참조합니다. 대량의 행 집계 쿼리를 가장 빠른 속도로 처리할 수 있는 최적의 서비스는 무엇입니까?

정답은 Amazon Redshift입니다! 수백 TB 규모의 빅데이터에서 소수 컬럼에 대해 대량의 행 집계(SUM, AVG 등)를 수행하는 워크로드는 전형적인 OLAP 분석이며, 컬럼 기반 스토리지(Columnar Storage)를 사용하는 Amazon Redshift가 가장 최적의 성능을 냅니다. 필요한 4~5개 컬럼의 디스크 블록만 읽어 디스크 I/O를 획기적으로 줄이기 때문입니다. MySQL 같은 행 기반 RDBMS는 모든 컬럼을 디스크에서 다 읽어야 하므로 복제본을 늘려도 심각한 성능 저하가 발생합니다.

Q4. 한 기업이 온프레미스 데이터센터에서 운영 중인 엔터프라이즈 Oracle 데이터베이스(다수의 PL/SQL 저장 프로시저 및 트리거 포함)를 AWS의 Amazon Aurora PostgreSQL로 마이그레이션하려 합니다. 마이그레이션이 진행되는 수 주 동안 기존 온프레미스 Oracle DB는 무중단으로 정상 서비스되어야 하며, 최종 컷오버 시 시스템 다운타임을 최소화해야 합니다. 올바른 엔지니어링 수행 절차는 무엇입니까?

정답은 DMS Schema Conversion(또는 AWS SCT) 스키마 변환 후 DMS 전체 로드 + CDC 실행입니다! 서로 다른 엔진 간의 이기종(Heterogeneous) 마이그레이션이므로, 먼저 DMS Schema Conversion이나 AWS SCT를 사용해 Oracle의 스키마와 PL/SQL 프로시저를 PostgreSQL 문법으로 변환하여 타깃 Aurora에 미리 적용해야 합니다. 그 후 AWS DMS의 전체 로드 + CDC(Change Data Capture) 태스크를 실행하여 기존 데이터를 이전하면서 소스 트랜잭션 로그의 실시간 변경을 계속 동기화하다가 마지막에 짧은 점검을 거쳐 전환합니다. DMS 자체는 저장 프로시저 코드를 변환해주지 않으며, 덤프 복원은 서비스 중단이 너무 깁니다.

Q5. AWS Database Migration Service (AWS DMS) 및 DMS Schema Conversion에 대한 기술적 설명으로 옳은 것 두 가지를 고르세요.

정답은 첫 번째(이기종 데이터 이전 지원)와 세 번째(전체 로드 + CDC 지속 동기화)입니다!
DMS는 Oracle에서 Aurora PostgreSQL과 같은 서로 다른 이기종 엔진 간의 데이터 복제를 완벽히 지원하며, '전체 로드 + CDC'를 통해 초기 적재 이후에도 소스 트랜잭션 로그의 변경을 계속 반영하여 최소 다운타임 마이그레이션을 가능하게 합니다.
오답 분석: Schema Conversion은 오직 스키마 구조와 프로시저 코드만 변환하며 데이터는 전혀 옮기지 않습니다(데이터는 DMS가 담당). 또한 DMS CDC는 비동기식 복제 방식이며 AWS 문서에 복제 지연에 대한 SLA가 없다고 명시되어 있습니다.

Q6. 한 기업이 온프레미스 가상 서버에서 자체 관리하던 대규모 MongoDB 클러스터의 인프라 관리 부담(패치, 장애 조치, 백업 등)을 없애기 위해 AWS의 완전관리형 데이터베이스로 이전하려 합니다. 기존 애플리케이션의 MongoDB 드라이버, 쿼리 코드, 도구들을 거의 수정하지 않고 그대로 재사용하고자 할 때 가장 적합한 서비스는 무엇입니까?

정답은 Amazon DocumentDB입니다! DocumentDB는 MongoDB와 완벽하게 호환되는 완전관리형 문서 데이터베이스로, 개발팀이 기존에 사용하던 MongoDB 드라이버, 애플리케이션 코드, 관리 도구를 변경 없이 그대로 사용하여 마이그레이션할 수 있습니다. DynamoDB나 Aurora로의 이전은 방대한 애플리케이션 코드 재작성이 필요하며, EC2 재호스팅은 운영 관리 오버헤드를 줄이지 못합니다.

Q7. (0022 복습) 한 모바일 게임 서비스에서 수백만 명의 활성 플레이어 점수를 기반으로 실시간으로 변동하는 '상위 100위 글로벌 랭킹 순위표(Leaderboard)'를 구현해야 합니다. 플레이어의 점수가 갱신될 때마다 즉각 순위가 재계산되어야 할 때 가장 적합한 아키텍처는 무엇입니까?

정답은 ElastiCache for Valkey / Redis OSS의 정렬 집합(Sorted Sets) 활용입니다! Valkey 및 Redis OSS의 정렬 집합(ZSET)은 원소가 추가되거나 점수가 수정될 때마다 $O(\log N)$의 매우 빠른 시간 복잡도로 순위를 즉시 재정렬하여 실시간 리더보드를 완벽하게 지원합니다. Memcached는 단순 문자열/객체 캐시이므로 정렬 집합과 같은 고급 자료구조가 없습니다. 매번 DynamoDB 전체 Scan이나 Redshift 쿼리를 돌리는 것은 극심한 부하와 지연을 유발합니다.

Q8. (0021 연결) 한 기업의 Amazon Aurora 클러스터 월별 청구서를 분석한 결과, 스토리지 I/O 요청 비용이 전체 Aurora 데이터베이스 청구 금액의 40%를 차지하며 가장 큰 비용 요인으로 지목되었습니다. 데이터베이스를 사용하는 애플리케이션의 코드를 전혀 수정하지 않고 Aurora 인프라 비용을 가장 효과적으로 절감할 수 있는 방안은 무엇입니까?

정답은 Aurora I/O-Optimized 스토리지 구성으로 변경입니다! AWS 공식 가이드에 따르면, 전체 Aurora 청구 비용 중 I/O 비용이 25% 이상을 차지하는 I/O 집약적 워크로드에서는 읽기 및 쓰기 I/O 요청 요금이 0원인 Aurora I/O-Optimized를 선택할 때 전체 비용을 즉시 절감할 수 있습니다. 애플리케이션 변경 없이 콘솔에서 클릭 한 번으로 전환할 수 있습니다. 복제본을 삭제하는 것은 고가용성과 읽기 성능을 파괴하는 행위이며, RDS Proxy는 커넥션 풀러이지 디스크 I/O를 캐싱하지 못합니다.

학습 내용 되짚어보기 (인출 연습)

교재를 보지 말고 머릿속 기억만으로 정리해 보세요.
(1) 관계형, 키-값, 문서, 인메모리(캐시용 vs 주 DB용 2가지), 그래프, 와이드 컬럼, 시계열, 대규모 분석(OLAP)에 각각 가장 최적화된 AWS 데이터베이스 서비스 명칭을 적어 보세요.
(2) 동종(Homogeneous) 마이그레이션과 이기종(Heterogeneous) 마이그레이션의 절차적 차이점을 설명하고, 이기종 마이그레이션 시 DMS Schema Conversion(또는 AWS SCT)이 수행하는 역할과 수행하지 못하는 역할을 명확히 설명해 보세요.
(3) 운영 중인 데이터베이스를 마이그레이션할 때 서비스 다운타임을 수 분 이내로 최소화하기 위해 선택해야 하는 AWS DMS 태스크 유형과 그 동작 원리는 무엇인가요?

(1) 데이터 모델별 최적의 AWS 데이터베이스:
- 관계형 (Relational): Amazon RDS, Amazon Aurora
- 키-값 (Key-Value): Amazon DynamoDB
- 문서 (Document): Amazon DocumentDB (MongoDB 호환)
- 인메모리 (In-Memory): Amazon ElastiCache (캐시 레이어) / Amazon MemoryDB (내구성 있는 주 트랜잭션 DB)
- 그래프 (Graph): Amazon Neptune (친구의 친구, 추천, 사기 탐지)
- 와이드 컬럼 (Wide-Column): Amazon Keyspaces (Cassandra 호환)
- 시계열 (Time-Series): Amazon Timestream (신규 워크로드는 Timestream for InfluxDB 권장)
- 대규모 집계 분석 (OLAP): Amazon Redshift (컬럼 기반 스토리지)

(2) 동종 vs 이기종 마이그레이션 차이:
- 동종 마이그레이션: 소스와 타깃 엔진이 같으므로 스키마 변환 없이 AWS DMS로 직접 데이터를 복제.
- 이기종 마이그레이션: 소스와 타깃 엔진이 다르므로 2단계로 진행. 1단계로 DMS Schema Conversion(또는 AWS SCT)을 통해 소스의 스키마 및 저장 프로시저 코드를 타깃 문법으로 변환하여 타깃 DB에 적용한 후, 2단계로 AWS DMS를 실행하여 실제 데이터를 복제함.
- Schema Conversion의 역할 한계: 스키마 구조와 프로시저 코드만 변환하며, 실제 테이블 행(Row) 데이터는 단 1건도 이전하지 못함 (데이터 복제는 DMS가 전담).

(3) 최소 다운타임 달성 태스크:
- '전체 로드 + 지속적 복제 (Full Load + CDC)' 태스크 선택.
- 동작 원리: 초기 원본 데이터를 복제하는 동안 및 완료된 이후에도, 소스 데이터베이스의 트랜잭션 로그에서 실시간 변경 사항을 계속 캡처하여 타깃 DB에 끊임없이 반영(CDC)하다가 복제 지연이 0에 도달했을 때 짧은 점검 시간 동안 엔드포인트를 타깃으로 전환(Cutover)함.

추가 학습 및 실습

1차 공식 문서 정독 (10분 투자): AWS 공식 의사결정 가이드의 "Choosing an AWS database service" 문서를 정독하세요. 각 데이터 모델별 장단점과 "Choose" 섹션에 정리된 상세 비교 표가 시험 준비의 강력한 나침반이 되어 줍니다.

실습 가이드 (비용 무료 확인 실습): AWS DMS 콘솔에 들어가 "Schema conversion" 메뉴를 클릭하고 마이그레이션 프로젝트(Migration Project) 생성 마법사를 둘러보세요. 인스턴스 프로필, 소스 데이터 공급자, 대상 데이터 공급자, 프로젝트 정의의 4단계를 눈으로 확인해 보세요. (주의: 실제 DMS 복제 인스턴스(Replication Instance)나 Neptune, Redshift 클러스터를 프로비저닝하면 시간당 과금이 발생하므로 실제 생성하지 마시고 설정 화면 구성만 확인하세요.)
